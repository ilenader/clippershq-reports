# BL-1095 — mining the tool survey: one number reversed, three ideas killed, and the cheapest action nobody took

**Date:** 2026-08-03 · **Type:** Tool re-survey + five trials · **Spend:** **$0.00** of a $1.00 cap

No product code modified. No data uploaded. No credential entered anywhere. Every trial ran on
free, locally-installed software in **one directory, `scratch/bl1095_work`, 561 MB, now deleted.**

---

## The one number

> **`clip_ocr.py` still claims watermark recall of 14.3%. On the engine it actually runs it is
> 78.6% [0.605, 0.898].** BL-1057 swapped the engine and wrote down, in its own report, that
> the module's figures "must be re-derived on the new engine before the module header is
> allowed to keep claiming them, **or the module lies**". Nobody re-derived them. It has been
> lying — conservatively — ever since, and three gates reason from that number.

And the money is not the cost: **BL-1039 measured that only 4 of the 21 existing hook windows

buys twenty new hand-marking jobs and, on that evidence, about four usable hooks.

**Cheapest untried route to the same gain, and nobody has tried it: Pixabay Music — $0,
commercial-OK, no subscription.** It is row 28 of the survey, marked TRIAL FURTHER, and it

## 3. The five trials, scored against our own hand labels only

### 3.1 Temporal persistence — BL-1057's own best idea, finally scored, and REFUTED

BL-1057 built it and could not score it: of four labelled watermark positives, none had
multi-frame media. **BL-1082 changed that** — 40 clips hand-read off frames, **34 marks, and
all 40 have staged media on disk.** So the experiment ran on 34 positives, not 2, using
BL-1057's feature code verbatim.

| feature | AUC (28 marks vs 5 clean) | mark median | clean median |
|---|--:|--:|--:|
| `static_textured_frac` | **0.221** | 0.0395 | 0.0851 |
| `corner_static_textured` | **0.307** | 0.0030 | 0.1202 |
| `static_frac` | **0.379** | 0.5794 | 0.6888 |

**Every AUC is below 0.5 — the signal points the wrong way.** Watermarked clips have *less*
static-textured area than clean ones. The mechanism is visible in the sample: a large share of
the marks are fake-tweet identity cards, which are big *flat* slabs (static, not textured),
while the clean film clips carry letterboxing and burned-in subtitles that are static *and*
textured. The feature measures "has subtitle-like static texture", not "has a logo".

**And the precision ceiling settles it without needing more negatives.** On BL-1004's 50 clips
— drawn at RANDOM, seed 1004, a real base rate — every threshold fires on 62–100%:

```
static_textured >= 0.0399   recall 13/28 = 0.46 [0.30,0.64]   fires on 62% of a random sample
                            -> precision CANNOT exceed 0.197 against a 12.2% library mark rate
corner_static   >= 0.0030   recall 14/28 = 0.50 [0.33,0.67]   fires on 74%   -> ceiling 0.165
```

**0.197 is below the 0.23 that already killed dead-canvas gating.** It dies the same way, and
BL-1057 said in advance that it should. **This idea is now closed with a number.**

### 3.2 RapidOCR precision/recall, re-derived — the finding of the round

`clip_ocr.py`'s header still carries EasyOCR-era figures. Re-measured against 28 marks a human
found in the pixels — never against the old engine, which would be scoring a detector against a
detector:

| what the gate asks | fires | precision (enriched) | **recall** |
|---|--:|---|---|
| any text at all | 33/33 | 0.848 [0.691, 0.933] | 1.000 [0.879, 1.000] |
| an `@handle` (`handles_in`) | 14/33 | 1.000 [0.785, 1.000] | 0.500 [0.326, 0.674] |
| the account's own name | 15/33 | 0.933 [0.702, 0.988] | 0.500 [0.326, 0.674] |
| **either → identifies a page** | 23/33 | 0.957 [0.790, 0.992] | **0.786 [0.605, 0.898]** |

> **Watermark recall: 14.3% claimed → 78.6% measured. A 5.5x under-claim.**

The sample is **enriched** (34 of 40 are marks), so the precision column is not a library figure
and is not claimed as one. **Recall is the number that was wrong, and recall is what this
measures**, on marks a human found first.

**Why it matters beyond the docstring:** "watermark recall is 14.3%" is cited as the reason
several categories are left ungated and as the justification for the emptiness rule. One of
those premises is now off by 5.5x. Nothing should be re-opened on my say-so — but the modules
that quote 14.3% should quote 78.6%, and whoever owns `clip_ocr.py` should update the header.

`SECONDS_PER_CLIP` declares **1.96 s**; measured **p50 2.07 s**. That constant is honest.

### 3.3 A local VLM on dead canvas — the cost rejection re-checked, and it HOLDS

SmolVLM-256M-Instruct, Apache-2.0, 527 MB, CPU, **27x smaller than the 7B model BL-1057
rejected**. Asked the question BL-1004 said a threshold cannot answer — *is this mostly picture,
or mostly flat border?* — on its 50-clip **random** sample:

```
answered BORDER on 19 of 50
precision 3/19 = 0.158  [0.055, 0.376]
recall    3/6  = 0.500  [0.188, 0.812]
```

**0.158 is worse than the 0.23 geometric threshold it was supposed to beat**, and its upper
bound (0.376) is under half the 0.80 bar. The judgement instrument does not beat the ruler.

### 3.4 The same VLM on watermarks — degenerate

```
answered YES on 0 of 33
```

**It never says yes.** At 256M there is no figure to report; a detector that never fires has no
precision. Recorded as a null result, not as a low score.

### 3.5 What filling the OCR field would cost and buy — the cheapest real action

```
clips                              : 2,731
with ocr_gate_text (RapidOCR)      :   512  (18.7%)   <- was 281 when this round began
with vision_on_screen_text         : 1,929  (70.6%)
with NEITHER, no pixel text at all :   711  (26.0%)

sweeping the remaining 2,219 at p50 2.07s : 1.28 hours
                                at p99 5.81s : 3.58 hours
```

**A quarter of the library has no pixel text at all, and one to four hours of CPU fixes that.**
On the 512 already read the widened term finds a mark on 31.1%. **That 31.1% is not a library
rate** — those clips were chosen by earlier rounds, not sampled — so the ~689 extrapolation is
an upper bound, not a forecast. BL-1033's rule is that fill, not cleverness, moves output; this
is the largest blank field left and the cheapest to fill.

## 4. Wall clock on this machine, under real load

Never a mean. 23 python processes were live throughout; the suite ran concurrently.

| measurement | n | p50 | p90 | p99 | min | max | spread |
|---|--:|--:|--:|--:|--:|--:|--:|
| RapidOCR `ocr_frame` | 33 | **2.07 s** | 3.86 s | 5.81 s | 1.01 s | 5.81 s | 5.7x |
| SmolVLM-256M `generate()` | 83 | **26.84 s** | 40.17 s | 46.47 s | 16.62 s | 49.36 s | 3.0x |

**A single isolated VLM call I timed separately took 56.5 s — more than the batch p99.** That is
the load-variance point made against itself: one sample, taken at the wrong moment, would have
overstated the cost by 2.1x. It is also why the mean is useless here.

**Sweep cost at p50: RapidOCR 1.57 h for 2,728 clips; SmolVLM 20.3 h.** Paid vision is
$1.50–2.00 per 1,000 clips — about **$5 and minutes** for the same library. The local VLM loses
on wall clock by roughly three orders of magnitude and loses on accuracy too.

## 5. What would actually move the postable rate

It has read **13 → 10 → 10 → 13/40** across four audits with overlapping intervals. The failures
are dead canvas, competitor watermarks, and captions that read as plot rather than hook.

**No tool in this survey addresses any of the three. I checked all 61 and I will say it plainly.**

| failure | what the survey offers | verdict |
|---|---|---|
| **dead canvas** | geometric thresholds (BL-1004: best 0.23); a local VLM (**this round: 0.158**) | **nothing works.** Two instruments, two refusals |
| **competitor watermarks** | OCR + patterns (**recall is 78.6%, not 14.3% — better than anyone thought**); temporal persistence (**this round: ceiling 0.197**); YOLO logo models (needs training) | **detection is largely solved and was mis-documented.** What is left is *fill*, not cleverness |
| **captions that read as plot** | **nothing. The category does not exist in the survey.** | and it cannot be bought: MEMEBOT-119 measured that `white_frame` ships `caption.enabled: false`, so **the caption we write is never drawn at all** — the visible hook is the source page's own text. There is no tool for "choose a better clip whose own burned-in hook is good" |

**The honest answer to "what would move the rate" is: not a tool.** The two things this round
can point at are (a) **fill the OCR field** — 1.28 hours, closes a 26% blank — and (b) **watch
more clips**, because BL-1082 measured that only 3.3% of the library has ever been judged and
every ranking attempt has died for want of labels, not for want of algorithms.

## Honest limits

- **The watermark sample is ENRICHED.** 34 of 40 are marks because BL-1082 chose clips where
  some pattern fires. Recall is sound; **precision on that set is not a library figure** and I
  have not claimed one. A real precision number needs 40 clips drawn at random and hand-read.
- **7 of 40 clips dropped out of the persistence trial** (28 marks / 5 clean scored, not 34/6)
  because my frame extractor seeks at a fixed 20 s and short clips returned fewer than the 4
  frames the feature needs. **That biases the persistence sample toward longer clips.** The
  precision-ceiling argument does not depend on it — it rests on the firing rate over the random
  42 — but the AUCs do.
- **Five negatives cannot carry an AUC.** The 0.221 is directionally clear and statistically
  thin; what closes the idea is the ceiling, not the AUC.
- **One model is not the category.** SmolVLM-256M is the smallest real VLM; Moondream2 (1.8B)
  or Florence-2 might do better on accuracy. They would be 7–14x slower than the 20.3 h I
  measured, so they lose the cost argument by more, which is what the re-check was about.
- **I did not run maigret, Instaloader, curl_cffi or TikTokApi.** All four require sending real
  identifiers or requests to third parties from this machine. That is the operator's call and I
  did not pre-empt it.
- **I did not re-derive `clip_ocr.py`'s handle-card P=80.0/R=100.** My 40 labels are marks in
  general, not the handle-card subset that figure describes.
- **The 31.1% mark rate on OCR'd clips is not a library rate.** Those 512 were selected by
  earlier rounds; the extrapolation to 689 is an upper bound and is labelled as one.
- **`clip_ocr.py` depends on a 259 MB directory inside `scratch/`** (`scratch/bl1061_pkgs`,
  via `pip --target`). It is intact today. It is also exactly the kind of path a disk-pressure
  cleanup deletes, and this session hit 100% disk once already. Worth someone's attention; not
  mine to move.
