## What was built

### 1. `send_suppress.py` — one policy, both send paths

A leaf module (stdlib + `role_policy`, no config, no network). `classify()` returns `{exclude, reasons, flags, agency, role, days_since_post}`. Both `writer.bot_ready_rows` and `send_list.build` call it, so the two paths cannot drift.

**The MX table is allowed to say "unknown."** `suppress_mx.json` (141 domains, copied out of a concurrent round's scratch artifact into a file this change owns) is consulted; a domain **absent from it is UNKNOWN, never dead**. A missing or corrupt table loads as `{}` and suppresses *nothing* on MX grounds rather than failing closed and emptying a send list. This is the honesty of the layer: it removes the bounces we are **certain** of — 20 rows, 1.2% — and makes no claim about the rest.

Two flags where BL-768 had one: `stale_180d` when the date came from a deep check, `stale_180d_unverified` when it did not. A matched date is wrong by up to 1,059 days, so the flag must not claim a verified 180 days it cannot support.

### 2. The agency flag, computed where the file is written

BL-768's option analysis was adopted unchanged: not a 23 MB backfill of a pure function, not `email_finder.py` (list-driven mode only, which is exactly why 0 crawl rows carried `?verify-third-party`). `role_policy.looks_agency()` needs email + handle + display name, and **all three are already in the candidate dict** — one call per exported row, 2,636 rather than 57,386. `email_quality` stays empty deliberately: a derived value with no owner is how it reached 0-of-57,386 in the first place.

`BOT_READY_COLUMNS` grew append-only — `lead_kind, agency, role, days_since_post, flags` after the stable five, so an existing n8n consumer is untouched. `write_bot_ready_csv` now emits **by column name against the contract** instead of a hardcoded field list; that hardcoded list is what left the two shipped files disagreeing (4 columns against a 5-column contract).

### 3. The self-contradiction, honoured

```python
# send_list.py:58   _ACT_RANK = {"ALIVE": 0, "UNKNOWN": 1, "DORMANT": 2}
# send_list.py:233  if activity != "ALIVE": continue      # <- cut every UNKNOWN
```

The cut is gone; the rank table that was written for this moment now does the work. **1,189 UNKNOWN rows kept**, labelled in `activity`, ranked below ALIVE and above DORMANT.

`writer.bot_ready_rows` already did this correctly and always had — it carries the identical rank table and says *"Sort ONLY — NOTHING is cut here."* One send path was right and the other was not; they now agree.

**BL-767's warning #4 was load-bearing and is handled.** `send_list.build` had *no* verdict gate and *no* curation gate; nothing exploited that only because the ALIVE filter happened to remove every non-editor emailable row. Widening that filter would have converted data luck into a live defect. Both gates land in the **same change**: verdict (clipper only) and curation (both kinds).

### 4. `lead_kind` — declared, never inferred

`clipper` = we want to hire them. `client` = we want to sell to them. Written at append time by **every** funnel: crawl and repost → `clipper`; Spotify, Twitch, Google Play, YouTube → `client`; `email_finder` takes a **caller-supplied** `lead_kind` and, unset, writes blank — because it is list-driven and nothing in the row reveals which kind it is. Guessing there is the very inference the column exists to end.

**Missing kind is unroutable**: excluded from every send path and reported loudly, never defaulted. `writer.lead_kind_of()` maps blank / unknown / `None` → `unroutable`.

Gate applicability is now stated in code:

| gate | clipper | client |
|---|---|---|
| editor verdict | **applies** — still blocks non-editors | **does not apply** — 0 distinct values across 1,935 |
| business account | applies | does not apply (a client is often a business) |
| liveness | ranked, not cut | ranked, not cut |
| curation page | applies | applies |
| suppression, dedup, bio-link quarantine | applies | applies |
| campaign attribution | hashtag pools | client campaign, else `DIRECT` |

`qualified_by` records the **thresholds** each client funnel actually applied (`spotify:min_listeners=…,countries=…`), stamped once per run onto every result — including a partial run's, since it is stamped after the loop. It records thresholds rather than the funnel name so that loosening a funnel's gates is visible in the data.

### 5. The third gate — campaign attribution

Campaigns are defined by hashtag pools; a client row's `source_hashtag` is the literal string `spotify_finder`, matching no pool. `attribute()` returned `UNATTRIBUTED` for 100% of client rows and `build()` dropped them. **A verdict-and-liveness-only fix would have unstranded nothing on this path.**

`attribute_client()` sends a client row to a campaign that claims its funnel (via an optional per-campaign `client_funnels` list, absent on all five today) and otherwise to **`DIRECT`** — never `UNATTRIBUTED`. `AMBIGUOUS` still refuses to guess, exactly as on the clipper path.

### 6. The migration — the one judgement call worth challenging

All 57,386 pre-existing rows predate the column. Left blank they are all unroutable and **no send file can be built at all** — the unstranding delivers nothing.

`migrate_master_csv` therefore backfills `lead_kind` **from each row's own recorded `source_hashtag`**. This is deliberately *not* the inference the column exists to end: that bug read routing out of a field that happened to be **empty**. This reads a **populated** provenance field, and only for the question it can answer — which funnel wrote this row. It is the same category as the migration's existing recency and views backfills, both justified in-code as *"a statement of fact about how the row was written, not a guess."*

Result: 55,391 clipper, 1,935 client, **60 left blank**. The 60 are all `email_finder` (54 pure, 6 with mixed `email_finder+tt:hashtag:…` provenance). Their kind is genuinely unrecoverable, so they stay unroutable and are reported. **1,935 matches BL-767's independently measured client-row count exactly.**

### 7. The stale file

`ALL_BOT_READY.csv` was regenerated (17 July → today) and its meta now carries a **real timestamp** — the field previously held the literal string `"derived-from-master"`, which reads like provenance and carries no time at all, so nothing downstream could tell a fresh file from a fortnight-old one. It now also records `generated_at`, `master_mtime` and `master_rows`.

`LATEST_BOT_READY.csv` is left as it is, because BL-768 is right that 2 rows **is** the contract — it is the newest *run's* editors, and the last run found two. The hazard is a sender aiming at it. So the staleness is now impossible to miss:

```
  !!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
  STALE: output\LATEST_BOT_READY.csv
    holds 2 row(s), written 2026-07-18 13:37:28
    master was written 2026-07-31 13:52:09 (13 days newer)
    That file is the newest RUN's editors, NOT the full send list. If a
    sender points at it, it will mail those few and miss everyone else.
    The current, complete list is output\ALL_BOT_READY.csv.
  !!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
```

## What this means for the first send — read this before sending

**The 1,079 client addresses now shipping have no per-row evidence of quality at all.** Measured on today's master:

| column | populated |
|---|---|
| `country` | **0 / 1,935** |
| `email_quality` | **0 / 1,935** |
| `spotify_monthly_listeners` | **0 / 1,935** |
| `qualified_by` | **0 / 1,935** |

BL-761 added the first three and this round added the fourth, and **all four are written only by future runs**. Every client row in master today was written before the write paths existed.

So: these leads are qualified by **funnel membership alone**. The claim "a Spotify artist above the listener floor, in an allowed country, singing in an allowed language" is true of how they were *found*, and there is **no per-row record of it** — the gates ran, and their output was discarded before it reached master. The `qualified_by` column that exists to make that auditable is empty on every one of them.

**A second consequence: the `DIRECT` list's rank order is arbitrary today.** Every ranking key is zero on every row — `quality_score` 0/1,086, `followers` 0/1,086, `deep_median_views` 0/1,086. `rank=1` means nothing. The top three entries are corporate publisher inboxes (`@2k.com`, `@activision.com`, `@garena.com`) sitting there by input order, not merit. Anyone sending down this list from the top is not sending best-first.

**The honest options** are to re-run the client funnels so the context is written (the code now persists it), to send a small calibration batch and let the outcome columns earn the ranking, or to send on funnel membership with eyes open. What should *not* happen is a future reader assuming the context was checked because the columns exist.

Related, and unchanged by this round: **there is still no send history.** `date_sent` is empty on all 57,386 rows. The suppression layer already honours it (`already_sent` is a hard exclude) but nothing writes it, so nothing prevents re-sending on the next run. BL-768 specifies the bulk marker; it was **out of scope here** and is not built.

## Honest limits

- **Suppression cannot reach the observed ~10% bounce rate.** It removes 20 rows — **1.2%**, a floor, not the observed figure. The gap depends on live SMTP behaviour nobody can establish without sending. Role exclusion is a reputation judgement, not a bounce fix.
- **The MX table is a 141-domain snapshot** taken by a concurrent round and may already have moved. Every domain outside it is treated as unknown.
- **Agency detection is heuristic and unverified by hand.** 166 flagged. BL-768 counted 27 on the smaller stale export and flagged one `outlook.com` hit via a local-part rule as worth an eyeball; that caution carries over at this larger scale. It is a flag and never a cut, so a false positive costs a differently-worded first line.
- **The `role` column is empty on every exported row** whenever `send_exclude_role` is on (the default) — role rows are excluded, so no survivor carries the flag. It becomes informative only when the toggle is off. That is correct but easy to misread as "no role inboxes exist".
- **`qualified_by` is written but unpopulated**, as above. The mechanism is tested; the data is not there yet.
- **Liveness was made kind-aware, not generalised.** BL-767 §3 proposes replacing `last_post_date`/`date_source` with kind-neutral `last_activity_date`/`activity_source`. That was **not** done: it touches every funnel's write path, and adding columns nothing populates would repeat the `dominant_lang` mistake this schema already learned from. Client rows are simply never cut on liveness. Spotify's `latest_release_date` is still computed and still discarded.
- **The 6 mixed-provenance rows** (`email_finder+tt:hashtag:…`) were left unroutable. One of the two funnels that found them is the crawl, so `clipper` would be defensible; refusing to pick is the conservative choice and costs 6 rows of 57,386.
- **`repost_finder` still exports nothing**, correctly. Its 42 rows are `clipper` with 0 emails and 0 profile URLs — it stores pages, not people. The gates are not what stops it; the missing contact is.
- **No live funnel run was performed**, so the `lead_kind` / `qualified_by` write paths in the four client funnels are covered by tests and code review, not by a production run.
