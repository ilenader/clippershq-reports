## 1. CORRECTION: item 1's premise was half wrong, and the wrong half was the fix

The brief asked me to make `claim.py`'s writes atomic — "temp then `os.replace`, the pattern `append_leads` already uses." **`start()` has done exactly that since it was written.** `tools/claim.py:182-187`, with a comment saying so:

```python
with open(tmp, "w", encoding="utf-8") as fh:
    json.dump(rec, fh, indent=1); fh.flush(); os.fsync(fh.fileno())
os.replace(tmp, p)   # atomic: another agent never reads a half-written claim
```

I did not take the comment's word for it. **VERIFIED under a reader hammering the directory — 240 write cycles, 12,292 concurrent reads, zero torn records.** The claim record was never once seen half-written, before or after anything I changed. `os.replace` does what it promises.

**So the two incidents this session were never torn claim records.** BL-901 and BL-903 were `claim.py`'s *source file* being saved in place by another agent while a round imported it. Nothing inside `claim.py` can fix that — which is precisely why BL-906 built a reader with no code path through it.

If I had stopped at the brief's wording I would have reported item 1 as already done. The test I wrote to *prove* it was already done is what found the real bug.

## 2. The real defect: atomic is not the same as succeeds

The test crashed. Not on a torn read — on the delete:

```
PermissionError: [WinError 32] The process cannot access the file
because it is being used by another process: '.claims\R-0.json'
```

on the **first iteration**. Then, once that was fixed, the other half:

```
PermissionError: [WinError 5] Access is denied: 'R.json.tmp' -> 'R.json'
```

**POSIX and Windows disagree about a fundamental here.** `rename(2)` and `unlink(2)` over an open file are fine on POSIX — the directory entry moves, the reader keeps its inode. Windows has no equivalent: CPython's `open()` shares a file for read and write but **not for delete**. So while *any* other process holds the file open, both calls fail.

`start()` caught nothing. `end()` caught only `FileNotFoundError`.

**VERIFIED, before and after, under one concurrent reader:**

| | reads | torn records | claims filed | **releases FAILED** |
|---|---|---|---|---|
| before (bare `os.replace` / `os.remove`) | 3,213 | **0** | 120/120 | **65 of 120** |
| shipped (`claim._retry_win32`) | 9,079 | **0** | 120/120 | **0** |

**65 of 120 releases failed.** That is the number that matters, and its consequence is worse than a crash: a round whose `end` raises has *finished* but has not *released*. Its claim file outlives it. **That is how a ghost claim is born — and a ghost claim is exactly what six consecutive rounds stopped on when BL-849 still appeared to hold files it had long since finished with.** A failing `start` is at least loud; a failing `end` is silent and misleads everyone who reads the registry afterwards.

`WinError 5` on the replace fired once, under a longer-held handle, and did not reproduce in the final harness. Rarer, not absent — I have wrapped both.

**Shipped: `tools/claim.py::_retry_win32`**, used by `start()` and `end()`. 12 × 0.1 s, which is orders of magnitude longer than any reader here holds a claim file (they all `with open(...)` and parse ~1 KB). Retrying is the whole fix because the blocker is transient by construction, and both operations are idempotent. `FileNotFoundError` propagates **immediately** — "already gone" is not "blocked", and the callers distinguish them. A `PermissionError` that outlasts the budget is **re-raised**, because a caller that could not write the registry must never be told that it did.

Pinned in `tests/test_claim.py`: retry-then-succeed, immediate `FileNotFoundError`, permanent-block-raises-after-full-budget, and a live `start`/`end` round trip.

## 5. The pipe limit, recorded with the half BL-906 got wrong

BL-906 — mine — wrote in `PUBLISHING.md` that piping the script is "harmless". **That was an overclaim and it is now corrected in place.**

**VERIFIED, the direct way, on a report the scanner rejects:**

```
HEAD before: 677c4d7
  FAIL: long opaque literal in report
PIPED  EXIT=0          <- tail's status, exactly as before
DIRECT EXIT=1          <- the script's own
HEAD after:  677c4d7   UNCHANGED
BL-BAD.md in clone? NO -- never copied
```

**Piping `publish_report.py` still loses its exit status.** That is what a pipe *is*, and nothing in this repo can change it. What changed is **where the decision is made**:

| | old shell recipe | `publish_report.py` |
|---|---|---|
| where the scan's status is read | by the shell, after the pipe | inside the process, off `.returncode` |
| what a swallowed status **causes** | **the push happens anyway** | nothing — the refusal already happened |
| what it costs | a report with secrets in it, public | the operator does not see the refusal |

The failure mode has moved from *"published something it should not have"* to *"did the right thing quietly"*. So: do not pipe it, you want to see the refusal — but if someone does, the gate holds.

## 10. Three mistakes of mine, all the same mistake

- **I ran the verification script as `bash … | tail -26; echo "EXIT=$?"`** and reported `EXIT=0` from `tail`. In a round about swallowed exit codes. I flagged it in-line and re-ran it unpiped; the numbers above are from the unpiped run.
- **Then I did it again with a semicolon instead of a pipe.** I launched the suite as `python tests/run_all.py > out 2>&1; echo "SUITE EXIT=$?"`, and my own harness reported the job as **"completed (exit code 0)"** — the status of `echo`, not of the suite, which had gone **red**. A `;` chain reports its last command exactly as a pipeline does. Caught by reading the output file rather than trusting the code. **Seventh instance this session**, second in this round, and the first where the swallowing mechanism was not a pipe at all — which is worth recording, because every warning in `PUBLISHING.md` and every rule in the BL-906 sweep is written about `|`.
- **I passed `--quiet` to `stillness.py`, which takes `--quiet-s`**, and got two spurious FAILs.
- **My harness then asserted `stillness.py` must exit 0.** It exits 1, correctly — with ten rounds in flight the tree *is* not still, and **1 is its verdict, not its failure.** I had read "the answer is no" as "the tool did not answer", which is the exact error this entire round is about, committed by the script written to check for it. The check now compares the verdict across corruption instead of demanding a particular one.

That is the sixth instance this session of a text/exit check confusing an answer with a failure; the first five are catalogued in BL-892 and BL-906.

- **32 bare `os.replace`/`os.remove` sites remain**, including four that finalise `master_leads.csv`. Found, measured, not fixed, not mine.
- **`WinError 5` on `os.replace` is evidenced by one observation**, not a rate. I fixed it anyway because the retry is free and the failure is silent.
- **The retry budget is 1.2 s and it is a guess informed by one workload.** If a reader ever holds a claim file longer than that, `end` raises — loudly, which is the intended failure, but it is a threshold nobody has stress-tested against a slow disk.
- **`_retry_win32` is in `claim.py` only.** Every other writer in the tree would need the same wrapper, and copying it is how logic drifts; somebody should hoist it, and that somebody is not a round holding `claim.py` alone.
- **I did not test the fix against a real second process**, only a second thread. Threads share a process handle table; a separate process is the true condition. The failure reproduced under threads, so the bug is real, but the *rate* may differ across processes.

## Say it plainly

The brief asked for atomicity and the code already had it. What it did not have was any handling for the case where the atomic call *fails* — and on Windows, with a dozen rounds reading `.claims/` continuously, it failed 54% of the time. Every one of those failures returned a round to work believing it had released a claim it still held.

That is the same shape as the last three incidents here, one level down. A dead `claim.py` returned zero rounds; a piped scanner returned success; and now an `os.remove` that raised was read, by the round calling it, as a release. In each case the code could not tell *"it did not work"* from *"it worked"* — and the fix is never more care. It is making the failure representable: `None` instead of `0`, a refusal decided inside the process, and an exception that reaches the caller instead of a claim quietly left on disk.
