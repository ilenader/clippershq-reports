## 1. The six severity-90 swallows are loud, and graded by consequence

The "never fatal" instinct was right and stays: a ledger that cannot be written must not take down the run whose work it is recording. What was wrong is that **"never fatal" had quietly become "never mentioned"**.

| site | now | why that level |
|---|---|---|
| `spend_ledger` counter read | **ERROR** | this value *is* the cap check |
| `spend_ledger` `meter.sync` | **ERROR** | money is being spent the ledger will not know |
| `spend_ledger.write_marker` | WARNING | a kill becomes indistinguishable from a failure — clarity, not money |
| `run_status.write` | WARNING, **once per run** | the dashboard goes blind; no money, no work lost |
| `ig_client._warn_unflushed` | stderr **then** logger | at interpreter exit the logging machinery may already be gone |
| `repost_finder` sync + marker | ERROR / WARNING | same two mechanisms, same reasoning |

**One of them was worse than silent.** `metered_spend_fn` caught a failed counter read and returned `0.0`. That value is what every funnel compares against `max_run_usd`, so a broken counter told the run it had spent **nothing** and the cap could never bind again. It now returns the **last known figure**, which can only ever stop a run *earlier* than the truth:

```
a counter that dies mid-run keeps the last figure
   before=$0.1200 after=$0.1200   (a reset to $0.00 would un-bind the cap)
```

Repeat failures are counted, not repeated: first occurrence logs in full, then every hundredth. A failing disk on a 3,000-call run must not produce 3,000 identical lines, and `spend_ledger.silent_failures()` exposes the counts.

### Proved by breaking each one

A fix to a *silent* failure cannot be proved by reading the code — the defect was that nothing was emitted. `scratch/bl900_prove.py` forces the exact exception each site used to swallow:

```
14/14 planted failures are now heard.
swallow counters this process: {'counter_fn': 2, 'meter.sync': 1, 'write_marker': 1}
```

Thirteen of these are now permanent tests in `tests/test_headless.py` (46 tests, all green).

## 2. The error-watch was deaf to `control`, and the fix is one line at the root

`run.py` attached its `_ErrWatch` to `logging.getLogger("clippershq")`. `control.py` — the single largest module in the funnel path — logs to `logging.getLogger(__name__)`, which is **`"control"`**, a sibling tree. Every ERROR it raised was inaudible, so no control failure could ever mark a headless run FAILED.

BL-896 worked around this by routing one message through `getLogger("clippershq")`. That is a workaround every future module must remember. **BL-914 moved the watch to the root logger instead**, so a module can log where it belongs:

```python
_logging.getLogger().addHandler(_watch)
if _logging.getLogger().level == _logging.NOTSET:
    _logging.getLogger().setLevel(_logging.WARNING)
```

Then the BL-896 workaround was **reverted** — that line logs on control's own logger again, deliberately, so it stands as a live end-to-end proof:

```
! google_play reported success but logged 1 error(s); recording FAILED.
  google_play: failed  leads=0  spend=$0.0000  0s
```

An ERROR raised on `getLogger("control")` now fails a real headless run. Before today that was structurally impossible.

## 3. email_finder no longer eats its own input

It opened the input file for **writing** a moment before reading it. Interactively the order happens to be safe — truncate, operator pastes, read — which is why it survived: the file was only ever filled by hand *between* those two steps. It is unsafe for every other way of supplying input.

BL-891 made the fix headless-only, which cured the symptom in one mode and left the trap in the other. The rule that is right in both is simpler: **an existing non-empty file is data.** It is kept, and the run says so. Clearing it stays a deliberate act.

## 4. The dead knob is deleted — function, three parameter layers, and the config key

BL-896 measured `_ig_prescreen_ok` inert three independent ways. All of it is gone:

- the function
- `ig_prescreen_followers_only` from `run()`, from `_drain_source`'s signature, and from the call between them
- `config["ig_prescreen_on_followers_only"]` — which the operator had explicitly set to **`false`**, expecting the non-followers-only screen, and which did nothing

**The cleanest evidence that removing it changed no behaviour:** `tests/test_funnel.py` passed a `ig_prescreen_followers_only=False` argument to ask for "the full hashtag-level screen", and asserted *"only 1 profile call — the editor"* and *"2 profile calls saved"*. With the parameter deleted, **those same assertions still pass**. The full screen was always what ran.

The deletion note in `main.py` records why BL-896 nearly reported the opposite — comparing the dead gate (kept 143/143) against the live one (kept 8/143) produced a confident "94.4% more cuts" for a knob that steers nothing. **A dead knob that looks consequential is more dangerous than one that looks trivial: it invites a confident change.** Checking call sites is what settled it, and grepping the parameter name would never have prompted that.

## 5. The seventh funnel runs — and proving it exposed a live money bug

tiktok cleared its fourth gate: a bare `input("\n  Proceed? [y/N]: ")` at `main.py:4686`, outside control and therefore outside every earlier fix. It now goes through `_proceed_ok()`, which auto-approves headless (the `--cap` is the stated bound) and treats an unanswerable prompt as **No**.

It then ran, headless, end to end:

```
ClippersHQ · #footballedithub (TikTok) · Leads: 417
BL900-TIKTOK-PROOF   ->   437 master rows
```

**Attribution: 6 rows → 475 rows.** Items 5 and 6 in one run.

### The incident, stated plainly

I passed `--cap 0.05`. The run spent **$0.0668** — and would have kept going, because:

1. **`tiktok_max_run_usd` is read by nothing.** It appears exactly once in the tree, in `run.py`'s funnel table. `--cap` for this funnel writes a config key no code consults. **The cap is a no-op for tiktok.**
2. **The tiktok path has no `IncrementalMeter`.** email_finder, twitch, spotify and clip_walk each build one; this path does not. So when my own 1,500-second timeout killed the run, it never reached its metering `finally` and **the ledger recorded $0.0000** — the exact failure BL-830 built the incremental meter to prevent, on the one funnel that never got it.

The work survived the kill (437 rows appended incrementally); only the money record did not. That asymmetry is worth naming: half of BL-830's design is wired here and half is not.

**Measured, not estimated from the run's own display.** The funnel printed `Spent: ~$0.27`. The vendor's balance API is the authority:

```
balance at run start : $275.98        (printed by the run itself)
balance now          : $275.9132
actual spend         : $0.0668        — the display over-stated by 4x
```

Recorded to the ledger as `TIKTOK / BL900_tiktok_killed_unmetered`, `estimated: true`. Total round spend **$0.0668 of the $0.10 budget** — inside it, but by luck rather than by the cap, and I would rather say so than round it off.

That flag was not my idea: another round's `tests/test_estimated_flag.py` — a canary over the real ledger — went red on my new row and named it. It was right, and the fix is now in. A ledger row that is an estimate must declare it rather than rely on a word in its label.

## What this leaves

1. **`--cap` does nothing on the tiktok funnel.** `tiktok_max_run_usd` is read nowhere. This is the highest-value open item in the tree: a mandatory safety gate that silently does not exist on a paid path.
2. **The tiktok path needs an `IncrementalMeter`**, like the four funnels that have one. Until then any kill loses the spend record.
3. **The other funnels' `cap_key`s should be audited the same way** — one was dead; nobody has checked the rest.
4. **The spend ledger still has no `run_id`** (BL-866). Master can answer "which rows came from this run"; `spend.json` cannot answer "what did it cost".
5. **Two append paths still stamp `run_id` by different code** (`writer._append_master`, `crossdedup.append_leads`).
