### Why this is a hard blocker and not caution

Section 2 requires that **the ledger reconciles against the vendor receipt**. That
reconciliation is arithmetic over `spend.json`, which is a single global file with a single
`total_spent_usd`. There is one marker directory (`scratch/runs/`), one checkpoint directory
(`scratch/resume/`), and one campaign spend scope (`campaign:SPOTIFY_FINDER`).

If two rounds each start funnels and each kill one, neither can attribute a receipt to its own
run — **the reconciliation this round exists to prove is the first thing a second concurrent
tester destroys.** Section 3 has the same problem in sharper form: it asks me to prove that two
concurrent runs count separately, while a third and fourth run from another round are running
against the same checkpoint. That is not a test, it is noise.

The money makes it worse. The brief's own warning — *"a hard kill once lost 958
receipt-counted requests from the ledger, understating spend by ~$0.57, and a kill on Windows
exits 0xC000013A so no finally and no atexit runs"* — describes a failure mode where spend
goes **unrecorded**. Two rounds killing runs against one ledger, with a known path that loses
receipts on kill, is how you get a spend figure nobody can reconstruct afterwards.

## Section 5, delivered in full — the wedge, measured

`clippershq/bio_parser.py` and `clippershq/enrich_links.py` are **unclaimed and clean**, so
this section needed nothing from BL-1167.

### The duplicate is real

```
bio_parser._EMAIL_RE    [A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}
enrich_links._EMAIL_RE  [A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Za-z]{2,}
IDENTICAL: True
```

Two independent copies of the same pathological pattern, exactly as the brief says.

### The regex is still quadratic — confirmed, and it is cleanly O(n²)

One unbroken run of email-legal characters with no `@`. The greedy run matches to the end,
fails on the required `@`, and retries from every start position:

| chars | seconds | x previous |
|---:|---:|---:|
| 2,000 | 0.0037 | — |
| 4,000 | 0.0142 | 3.88x |
| 8,000 | 0.0611 | 4.32x |
| 16,000 | 0.2323 | 3.80x |
| 32,000 | 1.0366 | 4.46x |

**Mean ≈ 4.0x per doubling — textbook quadratic** (2² = 4).

### Three numbers in the repo are wrong, and here are the measured ones

`clippershq/artist_search.py:432` states, and my brief repeats:

> *"measured 1.95 s at 32 kB, 3.2x per doubling, ~589 s at the real cap"*

| Claim in the repo | Measured here (3.11.9) |
|---|---|
| 1.95 s at 32 kB | **1.04 s** |
| 3.2x per doubling | **~4.0x** |
| ~589 s at the real cap | **~63 s** at 250,000 chars |

The 589 s figure came from extrapolating with the understated 3.2x. The true exponent is
worse and the true constant is better, and the two nearly cancel — but the published number
is off by roughly 9x and should be corrected in the comment.

Separately, `enrich_links.py:220` quotes *"250,000 chars -> ~3,856 s (1.1 h)"*. That is a
different regex — `_EMAIL_CANDIDATE_RE`, which is worse — not `_EMAIL_RE`. The two figures sit
eleven lines apart in the same file and are easy to conflate.

### Both live paths are safe, measured

**Path A — `artist_search.emails_from_bio`** caps the input at `BIO_CAP_CHARS = 4000` before
`bio_parser` sees it. At 4,000 chars the measured worst case is **0.0142 s**. An Instagram bio
is capped at 150 characters by Instagram, so the cap is ~27x past anything legitimate.

**Path B — `enrich_links.extract_from_html`** applies `_defuse_long_runs(html)` at line 313
before every email pass. Measured on the same pathological input:

```
 32,000 chars: defuse 0.0002s + regex 0.0031s = 0.0033s   (vs 1.0366s undefused ->   314x)
250,000 chars: defuse 0.0011s + regex 0.0227s = 0.0238s   (vs   ~63s extrapolated -> ~2,600x)
```

**The wedge cannot fire through either live path today.** The 14-minute GIL-holding freeze
that silenced the heartbeat in BL-1160 is defused at both call sites.

### The residual, named precisely

`bio_parser.py` has **no defusing and no cap of its own** — `grep -n "defuse" clippershq/bio_parser.py`
returns nothing, and line 471 runs `_EMAIL_RE.finditer(text)` on raw `text`, with line 474
running the worse `_EMAIL_CANDIDATE_RE` on the same raw text.

**The protection lives at the two call sites, not in the module that owns the regex.** Any new
caller that reaches `bio_parser` with uncapped, undefused text inherits the full quadratic —
and both regexes hold the GIL while they do it, so the symptom is a silent whole-process
freeze, not a slow function. `artist_search.py:432` says this itself: *"any new path that
parses pages inherits the wedge unless it caps too."*

That is the standing risk: **it is one new call site away from returning**, and it will return
as a wedged run with a dead heartbeat rather than as an error.
