## 2. The recurring leak is closed

```python
got = parse(raw)
if not got:
    logf.write(...)     # the cost is logged
    continue            # and the library is never touched
```

The next run's filter was exactly *"no `vision_scene`"*, so a clip whose call was **paid for and produced nothing** was selected and paid for again, every run, forever — 23 of 380 measured, 6.1%, $0.15 per 1,000 recurring.

`record_failure()` now writes a negative marker at a bumped rev: `vision_attempts`, `vision_last_error`, `vision_last_attempt_ts`. **Two attempts, then never again** — one retry separates a transient model wobble from a clip the model simply cannot read; a third has never been observed to help.

It never invents a label: a failure row leaves `vision_scene` absent, so nothing downstream mistakes a failure for a description. Pinned by a test.

## 3. Unreachable clips are excluded before payment, not discovered by it

**149 of the 2,003 clips cannot be reached within `max_pages=2`** and would each cost two paid calls to find that out. They are now dropped by the selector.

`estimated_pages()` is a deliberate **lower bound** — rank is computed over clips we hold, and the live feed contains posts we never stored. It therefore *under*-excludes, which is the safe direction: excluding a reachable clip costs a video, including an unreachable one costs $0.0012.

**`max_pages` stays at 2.** Cap 5 buys 3.8 percentage points of reachability for 6% more per success — the argument against it was always wall clock rather than cash, and this round makes wall clock the thing we are optimising.

## 4. `ig_client` has a real limiter, and 429s are no longer billed

**There was no limiter at all** — a 150 ms `time.sleep` per call, which paces one single-threaded process and nothing else. Two clip rounds simply doubled the rate against a shared quota.

`_Pacer` reserves slots rather than sleeping: N callers get N slots spaced ≥ `min_interval`, instead of all sleeping the same 150 ms and firing together. It is the `musicbrainz.py` reservation shape, **extended across processes** through a shared slot file under the project's own `filelock` — because these funnels run as separate processes far more often than as threads. It degrades to process-local if the lock or file is unavailable: pacing must never fail a run, and a stale slot from a dead process is treated as garbage rather than obeyed.

### The billing order

The counter incremented **before** the send, so a 3-attempt 429 storm read as 3× the spend on calls that returned nothing. It now counts what the provider **serves**:

| outcome | billed? |
|---|---|
| 200 | **yes** |
| 404 | **yes** — not an assumption; `PROBE:TRACK_404_BILLING` in the ledger is someone having paid to find out |
| 400 / 422 | yes — a served validation response |
| **429** | **no** — refused, not served. Counted in `throttled_requests` |
| 5xx, network failure | no — counted in `unbilled_requests` |
| unknown but served | **yes**, conservatively |

Nothing is dropped: refused requests get their own counters so a throttling problem is *reported* rather than hidden. And an unknown served status still bills, because **under-counting spend is the dangerous direction** — the cap is what stops a run.

Proven by a test that scripts three 429s then a 200: `session.calls == 3`, `http_requests == 1`, `throttled_requests == 2`.

## 5. The vision pass has pacing, retry and 429 handling

Grepping the old pass for `sleep`, `retry`, `429` or `Retry-After` returned **nothing**; a bare `except HTTPError: continue` silently skipped the clip and re-paid it next run.

`VisionPacer` + `call_with_retry` add all three:

- **Retry-After is honoured but CAPPED.** An uncapped one is how a run stalls for an hour — the shape BL-767 hit on Spotify.
- **Only a 429 is retried.** Anything else raises immediately: retrying a malformed request just pays again for the same rejection.
- A bounded attempt budget, so it gives up rather than looping.

`VisionPacer` is **process-local only**, deliberately: unlike HikerAPI this is not currently driven from two funnels at once, and a cross-process file would be ceremony without a measured need. That is a note in the source, not an oversight — if a second vision round ever runs concurrently it needs the shared half too.

## 6. For BL-855 — and BL-854 described this imprecisely

I reported "a clip whose `posted_at` changed between revisions". **It is worse, and I had it wrong.**

```
clip_id 3875969583437895210_53794898624   account zx.rd444
  row A  rev 1  posted_at = 1776271620
  row B  rev 1  posted_at = 1777473024     delta = 13.9 days
```

**Both rows are rev 1.** This is not a mutation on a bump — it is two independent first writes for the same `clip_id` disagreeing on an immutable field, and **last-wins-by-rev cannot resolve it** because there is nothing to compare. Whichever row is read last becomes the truth.

It matters slightly more than one row in 2,003 suggests: `posted_at` is what the depth model keys off, so a wrong date moves a clip's estimated page depth. Written up in `scratch/bl861_note_for_bl855.md` with the two candidate causes I did not distinguish between.

## Limits

- **Nothing was labelled live.** The retry, pacing and billing paths are proven by deterministic tests with a stubbed session, not against a real 429 from either provider. That is a stronger proof of the logic and no proof at all that the providers behave as modelled.
- **The 429-not-billed rule is a judgement, not a receipt.** 404 billing was *measured* by an earlier probe; that a 429 is *not* billed is inference from it being refused rather than served. If HikerAPI does bill 429s, this round now under-counts spend — the direction I said was dangerous. It is worth one probe.
- **`estimated_pages` is still a lower bound** on a model that has never fired against real retrievals. 149 excluded clips is what the model says, not what the API would say.
- **`clip_vision` is not yet wired into a runner.** `scratch/bl849_label.py` is the live vision pass and belongs to BL-849 this round, so I did not touch it: the ordering fix exists, is tested, and **is not yet what runs**. Someone has to point the runner at `select()`, and until they do the 5.1 hours are still being spent.
- **The $6.66 figure assumes 200 videos from a 2,003-clip library.** Change either number and it moves; upstream is amortised, so a smaller library makes it worse.
- **`MAX_ATTEMPTS = 2` is a guess.** One retry separating a wobble from a bad clip is reasoning, not measurement — nobody has counted how many unparseable responses succeed on a second try.
- **The shared pacing file adds a `filelock` acquire to every HikerAPI call.** Measured overhead was not instrumented; at 150 ms intervals it should be noise, but I did not prove it.
- **`config.json`, `clip_pipeline.py` and `clip_library.py` all changed under me** during the round — other rounds' declared files. The campaigns SHA held throughout, and none of my measurements depend on their contents.
