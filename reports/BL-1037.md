## 1. IT COMPLETES NOW, AND THE FIX WAS PARALLELISM

`--jobs N` runs suites concurrently, each worker with **its own ledger sandbox**. That detail
is not incidental: a shared throwaway `spend.json` under `--jobs` would let two suites write
the same file and produce a red that is an artefact of the runner — the exact class this round
exists to remove.

**483.8s against a 1,151s serial worst case, and it was not killed.** A and B bracket the
realistic range; the spread between them is other rounds' load, not the runner.

**The slowest suites are printed every run now**, because under `--jobs` the wall clock hides
them — the run is only as fast as its slowest file, and nobody can shard or cut what they
cannot see.

### What I did not build, and why

**Sharding by what a change touches** was not built. The mechanical attribution in §3 asks the
same question far more cheaply, and it answers the useful half: you do not need to run only
your own suites if you can tell in one line whether a red is yours.

## 2. THE ORPHAN-PROBE CLASS — ALREADY CLOSED, AND THE KILL PATH ADDED

**INFRA-023 had already fixed the cause the brief describes.** The plant no longer goes in the
live `tests/` and the prefix assertion is gone: it writes to a tempdir it owns and the check is
scoped to that directory, so two concurrent runs cannot redden each other. **No orphan exists
on disk** — `find . -name "bl932_probe_*"` returns nothing.

What it still lacked is the case that created the orphan in the first place: **`addCleanup`
runs when the test finishes, and a killed run finishes nothing.** Three layers now, each
covering what the one before it cannot:

| layer | covers |
|---|---|
| `addCleanup(rmtree)` | a normal or failing test |
| `atexit.register(rmtree)` | SIGTERM and interpreter exit |
| a sweep of `bl932_plant_*` left by earlier runs | a hard kill, which reaches neither |

The third is why the plant lives in the system temp area rather than in `tests/`: the OS reaps
what nothing else does, and litter cannot accumulate across sessions.

## 3. ATTRIBUTION IS MECHANICAL NOW, DEMONSTRATED ON A REAL RED

`--mine ROUND` reads that round's own claim and reports, per failing suite, whether it imports
anything the round declared it would write. On run A's red:

```
attribution for BL-1037: 4 declared path(s)
  tests/test_no_unchecked_stdout.py     touches nothing you declared
```

**It reports, it never decides.** A suite that touches none of your paths can still be red
because of you — through a shared fixture, a config, a data file. What it removes is the common
case and the hand-waving around it, and it names which paths matched when they do.

The import walk is **deliberately one level, not transitive**. A transitive walk over this tree
reaches almost everything from almost anywhere and would attribute every red to every round —
the same uselessness as attributing none.

## 4–5. THE HEAD EXTRACT IS NOT THE NUMBER, AND THAT IS THE FINDING

The brief's premise — *"a clean clone has repeatedly been GREENER than this tree, and it is the
only number describing what anyone else gets"* — **is refuted by measurement.**

```
working tree (B) : 188 suites, ALL GREEN
HEAD extract (C) : 163 suites, 32 RED
```

**`git archive HEAD` carries only tracked files.** It has no `memebot/` (a separate, gitignored
repository), no `config.json`, no `clip_library/`, no `master_leads.csv`, no
`scratch/songs.json`. Twenty-five fewer suites are even discovered, and a fifth of what remains
fails for want of data rather than for want of correctness.

So `--head` **is built, is reported, and is not the default.** It answers a narrower question —
*does the tracked half of the repository stand up alone?* — and the answer today is no, which is
worth knowing and is not the same as "the suite is red".

A run that genuinely describes what a clone gets would have to fetch `memebot` from its own
remote and supply the operator's data files. That is a real piece of work, and it is named here
rather than half-done.

## Method / limits

**A and B differ by 2 reds and 15 minutes on the same tree.** That is the phenomenon this round
is about, measured directly: the two reds in A were another round mid-edit and were gone by B.
It is also why no single run is evidence on its own — the rounds-in-flight count beside the
number is doing real work.

**`--jobs 6` on 12 cores.** Not tuned; 6 leaves room for the concurrent rounds whose load is
the problem. A higher number may be faster and may also make everyone else's run slower, which
is a trade nobody should make unilaterally.

**Nothing here makes a red impossible under load.** A suite that reads a file another round is
mid-write will still fail. What changed is that the run now finishes, and that whether the red
is yours is a line of output instead of an argument.
