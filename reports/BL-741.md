## What changed

Applied verbatim from `scratchpad/fixed_fetch.py`, verified there in BL-740 before it ever
touched the repo. `clippershq/enrich_links.py`, `fetch_link` body plus two constants:

- **`allow_redirects=False` + a manual hop loop under ONE shared deadline.** `t_end` is
  computed once; every hop's timeout is clamped to `min(per_hop, remaining)`, so the last hop
  cannot restart a full budget. `urljoin` handles relative `Location` headers.
- **`DEFAULT_TOTAL_FETCH_SECONDS = 15.0`** — total wall seconds for the chain *and* the body.
- **`DEFAULT_MAX_REDIRECTS = 5`**, replacing requests' default of 30. At the config's
  `enrich_links_timeout = 6`, the old worst case was 30 × 11s = **330s for one page**.
- **Body read under the same deadline** via `stream=True` + `iter_content`, because a per-read
  timeout is reset by every byte a trickling server sends and therefore never fires.

Config wiring at **both** call sites (`control.py:1898` and `:2127`), alongside the existing
`enrich_links_timeout`:

```python
total_seconds=config.get("enrich_links_total_seconds", 15),
max_redirects=config.get("enrich_links_max_redirects", 5)
```

**Partial bodies are kept**, as the owner directed. When the deadline expires mid-read the
bytes already received are parsed rather than discarded. Case B is the evidence: the old code
held a worker **40.5s and returned nothing**; this returns at 15.00s **with** the bytes it had.

## Two things I had to add beyond the specified patch

Both were forced by evidence, not preference, and both are noted because they were not in the
brief.

**1. `test_spotify_serial_fix.py` went red, and it was my regression.** Its `PageSizeCap` tests
inject a stub session whose response exposes only `status_code`, `headers` and `text` — no
`iter_content`, no `close`. The new streaming path raised, the broad `except` swallowed it, and
`fetch_link` returned `None`:

```
TypeError: object of type 'NoneType' has no len()
AssertionError: None != '<html>hello ...</html>'      (fixture address redacted)
```

Rather than edit a committed test to match new behaviour, I made the code tolerant: if a
response has no `iter_content`, fall back to `resp.text` and apply the same size cap. A real
`requests` response always streams, so **production behaviour is unchanged**; an injected
transport now keeps working. Suite back to green, and `chain_proof` re-verified **still
BOUNDED** afterwards — the fallback does not open a hole.

**2. A `_close(resp)` helper.** `resp.close()` on a stubbed response would raise. Releasing a
socket must never be the thing that fails a fetch, so closing is now best-effort.
