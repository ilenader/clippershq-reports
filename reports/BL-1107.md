## 1. The leak, reproduced and closed at source

`IgClient(api_key=None, config_path="config.json")` — the **first positional is the KEY**.
BL-1093 passed the config dict there; it went into `session.headers`; `requests` raised
`InvalidHeader`, whose message **contains the offending header value**. Reproduced here with
a sentinel:

```
exception type : InvalidHeader
SENTINEL present in the exception text: True
SENTINEL present in the TRACEBACK     : True
```

Now:

```
$ IgClient({"api": {"key": "<sentinel>"}})
CredentialShapeError: IgClient(api_key=...): expected a string API key, got a dict of
1 item(s). The value is NOT shown because it would then be in this message. The FIRST
positional parameter is the KEY, not the config -- did you mean IgClient(config_path=...)?

SENTINEL anywhere in message or traceback: False
```

`secrets_guard.assert_credential_header_safe()` refuses **six shapes** — dict/list, non-str,
empty, whitespace-padded, control characters, non-latin-1 — and none of them quotes the
value. It also catches the *other* route to `InvalidHeader`: a correctly-typed key that is
malformed would have been quoted by `requests` exactly like the dict was.

**One policy, imported by all four auth-header sites**: `ig_client`, `api_client` (×2, the
client and the legacy `make_session` that `probe.py` uses), `tikhub_client`. A test walks
those modules with `ast` and fails if any function that sets an auth header does not call the
guard first — wired, not merely available.

## 3. The scanner's rule is now in the logging filter — and it was the gap

`secrets_guard.redact()` had two rules: config VALUES, and `_PATTERNS`. Every pattern is a
vendor **prefix** — `AIza`, `sk-`, `ghp_`, `Bearer …` — and **this project's keys have no
prefix**: they are 32-character all-lowercase alphanumerics. Measured on a synthetic key of
exactly that shape:

| | before |
|---|---|
| `looks_like_credential()` | **True** |
| `credential_tokens()` finds it | **True** |
| `redact()` changes the line | **False** |

The module already knew the rule and the redactor did not call it — two implementations of
one policy, which is the defect class this file exists to prevent. `redact()` now calls
`credential_tokens`, **imported, exemptions and all**: by LINE CONTEXT, never by alphabet,
because excluding hex blinds the rule to hex keys and requiring uppercase blinds it to the
all-lowercase live keys.

Plants caught, through the real `logging` filter on a real handler: a key in a message, a key
in a **traceback** (`exc_text`, the field that carried BL-1093's leak), and a key in a URL
query string (urllib3 logs full URLs at DEBUG). An ordinary line is left alone, and a cited
hash on a line that names it is still exempt.

### Confirmed three ways, because two of my own instruments disagreed

The full-tree `grep -rlaI` pass reported the parent's tracked files **CLEAN**; a targeted
`git grep -F` reported **2 files**. One of them was wrong, and a leak report is not something
to publish on a disagreement, so the question was settled by reading the bytes of the version
**in HEAD** — not the working copy:

```
scratch/bl1041_config_stage1.json   tracked=True  on_disk=True  IN_HEAD=True
scratch/bl979_config_ranked.json    tracked=True  on_disk=True  IN_HEAD=True
commits touching that value: 2

```

`git grep` and the direct HEAD read agree; the filesystem walk missed them (`-I` skips what
it judges binary, and its path normalisation never had to be right once it found nothing).
**The finding stands on the two instruments that agree and on the commit ids.**

### The false positive that would have caused a false alarm

The first pass reported **8 public report files and 28 tracked files** carrying
`tikhub_api.auth_header`. That key's **value is the word `Authorization`** — 13 characters,
`credential-shaped = False`. It was picked up because `is_secret_leaf("auth_header")` matches
on `"auth"`, the same over-match BL-1043 documented. **The public repo is clean.** Reporting
those 8 files as a published leak would have been the worst kind of wrong.

## 5. Rotation options

The keys are in git history, so deleting the files does not un-leak them. In order of what
actually helps:

1. **Rotate all 7 at the vendors** — HikerAPI, LamaTok, TikHub, YouTube, Twitch, Gemini,
   OpenRouter. This is the only action that makes the history harmless, and it is cheap:
   `config.json` is gitignored, so a new key needs no code change.
2. **Then** consider `git rm --cached` on the two files so future `git archive HEAD`
   extracts and fresh clones stop carrying them. Second, not first — on its own it gives
   false comfort while history retains the values.
3. **A history rewrite was NOT attempted** and is not recommended here: ~10 rounds share this
   working tree and a rewrite would strand every one of them. It is also unnecessary once
   the keys are rotated.
4. The repo is **private**, which bounds the exposure to anyone with clone access — but
   BL-1043 shipped a bootstrap whose whole purpose is making fresh clones easy, so "private"
   is doing more work than it should be.

## 7. The metering hole

Both halves proven on an injected run — no network, no money:

```
client billed requests : 3
run() paid_calls       : 3      <- was 2x: one per account whose pk master already knew
ledger writes          : 1
calls written          : 3      <- was ig_calls=None, cost $0.000000
any row with calls None: False
```

`run()` gains `free_pks`: the runner cannot tell a free dictionary lookup from a paid HTTP
call through an injected `resolve_pk`, so the caller — which knows — says so. A second test
asserts that **without** `free_pks` the resolve is still charged, because a guard that
silently stops charging is the same defect pointing the other way.

The `ig_calls=None` rows were a consequence of BL-1093's hand-built meter, not of the meter
itself; with the constructor built correctly the ledger gets real counts, and the new
constructor guard makes the wrong construction impossible to write.
