# BL-1219 — seven addresses harvested, six of them new, and none of them belong in the TikTok send file

**The round is judged on addresses delivered, so here is the number without decoration: the
harvest found 7 addresses across 120 TikTok authors, 6 of them not already in the master —
and 0 of them reached `TIKTOK_PAGES_BOT_READY.csv`.** They are editors, not TikTok pages,
and the send-list builder was right to exclude them.

Every figure came from **`.venv\Scripts\python.exe`, Python 3.11.9**. Bare `python` is 3.13
and lacks the packages. **Vendor receipt: 120 TikTok calls + 102 Instagram calls =
$0.1332** against a $2.00 cap, both recorded to `spend.json` under
`bl1219_harvest_tt` / `bl1219_harvest_ig`.

**Route B was worth exactly one address.** BL-1217 followed only aggregator hosts

payload has no business field and no contact button; Instagram's has both, and they are 40
hits and 31 addresses (**51% of all yield**) respectively. Three of seven addresses came

**The caveat on 105 of 120 naming an Instagram: that is not a base rate.** The corpus is
`output/tt_xlink_resolve_run.jsonl`, which *is* a resolved cross-link run — every row in it
resolved to an Instagram by construction. I flagged this same trap last round and then fed
the same file to the harvest anyway. The honest cross-link share remains the previously
measured **4.6% floor / 10.3% [4.8, 20.8]**, and at that share route C yields ~3–6 Instagram
handles per 120 authors, not 105.

## 2. Where the six new addresses actually went

`crossdedup.append_leads` reported **appended=0, merged=7**. Every one attached to a person
already in the master — by handle or by Instagram — which is the "a TikTok page and its
Instagram are the same lead" rule working correctly in the data.

Their verdicts in the master:

| verdict | n |
|---|---|
| `LIKELY` | 3 |
| `EDITOR` | 3 |
| blank | 1 |

**None is a `TIKTOK_PAGE`.** So `tiktok_send_list.build()` excluded all seven, correctly: an
editor is somebody we *hire* and belongs in `ALL_BOT_READY.csv`; a TikTok page is somebody we
*pay to post* and belongs in this file. The three-way partition held.

**What that means plainly:** this round enriched six existing editor leads with an address
they did not have. That is real and it is useful. It is **not** what the brief asked for, and
the TikTok-pages send file is no longer than it would have been without me.

## 4. The app

Taken over from **BL-1159 under the 480-minute rule** — idle **7,185 minutes** (~5 days) with
`dashboard/server.py` and `dashboard/static/app.js` both clean. Recorded in the claim and
here. Two defects were targeted, both located by the prior audit:

1. **Clearing a finished run did not exist anywhere.** `/api/stop` explicitly refuses a dead
   pid (`server.py:3835`) and `app.js:419` renders a control only when
   `withStop && live && r.pid`, so a finished run had no control at all.
2. **The start path scanned 10 ports while the stop path scanned 30**
   (`dashboard_launcher.py:331` vs `:353`), so a dashboard on :8799 was invisible to start
   and a second server got launched.

**Both are done and tested.**

| | before | after |
|---|---|---|
| clear a finished run | **no endpoint anywhere** | `POST /api/run/clear` (`server.py:4069`), refuses a LIVE run — that is what `/api/stop` is for |
| the control on the card | rendered only when `withStop && live && r.pid` | `clearControl()` (`app.js:452`) gives a finished card a real `<button>`; an already-cleared card draws none |
| start-path port scan | 10 ports | **`SCAN_SPAN = 30`** (`dashboard_launcher.py:86`) |
| stop-path port scan | 30 ports | `STOP_SCAN_SPAN = SCAN_SPAN` (`:89`) — **one span, both paths** |

The asymmetry is closed by making the two names the same object, so they cannot drift apart
again. A dashboard on :8799 is now visible to the start path and gets reused instead of
duplicated.

`tests/test_bl1219_clear_run.py` — **29 checks, OK**, offline with no server.
`tests/test_dashboard.py` — **100 checks, OK**, not reddened.

**Not done from §5:** the launcher/icon consolidation (three `.bat` files still start the

## 5. What I did not do, and the one I got wrong

- **§1 the supply bug and the OCR wiring: NOT DONE.** Videos-per-author is still 1.15 and
  `clippershq/frame_text.py` is still not imported by the TikTok path. This is the second
  round running that this has been deferred, and it remains the thing that makes every
  TikTok verdict meaningless.
- **§2 his seven account rules: NOT IMPLEMENTED**, for the same reason — they are judgements
  about a body of work and the supply is one video per author.
- **GOT WRONG:** I identified `tt_xlink_resolve_run.jsonl` as a post-selection corpus in the
  previous round's report, wrote that down as a warning, and then used it as the harvest
  population anyway. The 105-of-120 Instagram figure is therefore meaningless as a rate, and
  the 7 addresses come from a population already picked over by an earlier cross-link run —
  which is very likely why 6 of 7 merged rather than appended. A fresh discovery population
  would have been the right input and would have cost the same.
- The first harvest attempt crashed on `extract_instagram` returning a list where I expected
  a string. The `finally` recorded the one billed call and **re-raised** rather than
  swallowing — which is the fix for last round's lost-60-calls defect working as intended.
