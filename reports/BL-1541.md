# BL-1541 — the email harvester: 103 addresses for 8.9 cents in 2.6 minutes

**Round:** BL-1541
**Cap:** $1.00 · **Spent:** $0.1878 (313 billed vendor requests at $0.000600)
**Platform:** TikTok only, hashtag route only. No model call, no picture, no video, no paid profile.
**Touches:** a new module beside the funnel. `tiktok_finder.py` and `meme_finder.py` are unchanged.

---

## THE PARAGRAPH AT THE TOP

The harvester walked **16 specific hashtags**, touched **1,842 distinct accounts**, and came back
with **103 accounts carrying an email — 102 distinct addresses, 66 of them not already in
master.** It cost **$0.0888** and took **2.6 minutes**. Every tag saturated; none was walked
twice; nothing was written to any seen store. Both spreadsheets are on your desktop:
`%USERPROFILE%\Desktop\clipper_emails_BL1541.csv` (103 rows, one per address, with the bio the
address came from) and `%USERPROFILE%\Desktop\clipper_no_email_BL1541.csv` (1,739 rows — the
accounts with no address, which is what tells you whether the ceiling is extraction or
publication). **On this measurement 400 emails costs $0.34 and takes 10 minutes, against
roughly $12.42 and 11.5 hours through the funnel — 36x cheaper and 68x faster.**

Three things did not go the way the brief expected, and they matter. **The follower count is
not on this route at all** — 0 of 1,842, so a follower filter is not merely unwise here, it is
impossible without buying a profile. **No free signal separates a content creator from an
editor**, so I shipped no filter, which you already said was an acceptable outcome. And **the
link-tree idea has almost no surface**: 7.19% of bios carry a link and **0 of 116 of them are
link aggregators**.

## 2. WHAT THE TOOL REUSES, AND WHAT IS GENUINELY NEW

**Reused, not rewritten** — five pillars, imported or lifted from the shipped source:

| pillar | where from | why not rewrite it |
|---|---|---|
| the vendor client and both hashtag endpoints | `api_client.LamaTokClient` | one client, one key path, one retry policy |
| the payload unwrapper | `tiktok_finder._envelope_items` | the nested-payload bug is already solved there; a copy drifts |
| email extraction + deliverability guard | `bio_parser.extract_emails` | it already rejects prose and bio-link fakes |
| the Windows-safe atomic rename | `atomic_io.replace` | a bare `os.replace` raises when the file is held open |
| the spend counter and cap | `harvest_run.Budget`, **lifted by AST** | see below |
| the Wilson interval | `tools/mark_reader.wilson`, **lifted by AST** | so this round's intervals are the same function everyone else quotes |

`Budget` is lifted rather than imported because `harvest_run` imports the whole clip pipeline
at module scope; compiling just the two class nodes gets the shipped source without the
freight, and it cannot drift from the class the rest of the repo uses.

**Genuinely new, because it did not exist:**
- **author-level extraction.** The funnel's `_video_of` carries `signature`, but nothing read
  the free per-author block (`verified`, `privateAccount`, `secret`, `shortDramaCreator`).
- **saturation by net-new account ID**, and the tag ledger.
- **the lane pool with the stop checked inside the worker.**

**FIX CATEGORY: GENERAL, and the site count is 1** — one new module, `clippershq/email_harvester.py`.
No existing file was modified, and **`.gitignore` needed no change** -- `output/` was
already excluded, which is why the run's rows (the only artefact carrying handles and
addresses) are never committed.

**WHAT IT WRITES, EXPLICITLY.** The module has a `writes()` function so the answer is not
"read the source": the **tag ledger** (`email_harvest_tags.json`, atomically), the caller's
**JSONL rows**, and nothing else. **No seen store, ever.** This tool walks accounts it does not
judge; a rejection written into the page store would latch a page out of the real funnel
forever on the strength of a question this tool never asks. `master_leads.csv` is opened
read-only and only to flag overlap.

**The unit is the TikTok price and it is passed explicitly.** `Budget`'s own default is the
Instagram HikerAPI price ($0.00069064); this reads the named config key `api.cost_per_call_usd`
= $0.000600. The shipped comment in `harvest_run.py` records that exact mispricing letting a
$3.00 cap spend $3.45.

## 3. THE LANE CURVE — PEAK AT 4, AND 8 IS WORSE

There is no model call to wait on, so the clock is vendor latency and lanes are the whole
speed story. **Every arm walks the same four tags to saturation on a throwaway ledger**, so
the arms do identical work — comparing disjoint tag sets would confound the lane count with
whichever tags happen to be deeper.

| lanes | wall clock | calls | accounts | accounts/min | errors | speedup |
|---|---|---|---|---|---|---|
| 1 | 144.9 s | 35 | 570 | 236.0 | 0 | 1.00x |
| 2 | 81.0 s | 37 | 570 | 422.5 | 0 | 1.79x |
| **4** | **34.0 s** | 37 | 555 | **980.4** | 0 | **4.27x** |
| 8 | 41.8 s | 36 | 565 | 810.9 | 0 | 3.47x |

**Throughput stops improving at 4 lanes and 8 is measurably worse.** Zero errors in every arm,
which matters: an arm that is fast because it is being refused is not fast, and a free surface
elsewhere died in under five seconds at four lanes. This one did not — but the ceiling is real
and 8 lanes buys nothing. The run used 4. Cost of the curve: 145 calls, $0.0870.

**One caveat, stated rather than buried:** each arm is a single timing, not a repeat. The 4-vs-8
ordering is a two-point comparison on one sample each, and last round a bench timed the same
work at 85 s and 167 s on consecutive attempts. The 1→4 direction is large enough to survive
that noise; the 4-vs-8 gap may not be.

## 4. WHAT IT SHIPS AND HOW THE LOOP STOPS

```
for each tag (4 in parallel):
    one call resolves the tag id (once per tag)
    for each page until saturation:
        one call -> up to 30 videos -> the distinct authors on them
        for each author: extract any email from the FREE bio
        record: handle, email, tag, page, bio state, verified, private
```

**Saturation is by net-new account ID, never `has_more`, never a count.** One surface reported
`has_more: true` on 7 of 7 pages while pages 3 and 4 came back byte-identical to page 2; and a
count cannot be trusted either, because a bogus cursor once returned *more* "new" accounts than
the real one when the cache key changed rather than the results. The loop stops a tag after two
consecutive pages that add no ID it has not seen, and **records the page where each tag
saturated**.

**Validation is on list length, never on status.** This endpoint returns HTTP 200, code 200,
`status_code: 0` and "No more videos" *with the list absent*.

**Never more than 30 per call** — 40, 50 and 100 are HTTP 400 on hashtags.

**An absent bio is `unknown`, never `empty`.** A torn response or a missing field is a
measurement not taken, and a row that reports one is worse than a blank. On this run: 0
unknown of 1,842, so the distinction cost nothing here and will matter the first time the
vendor tears a page.

**The stop is checked at the top of the worker and again before every page.** A run-level stop
tested only by the dispatching loop works serially and does nothing at lanes>1, because the
pool is handed every task before the first one finishes. The test file demonstrates the broken
shape first — 16 of 16 tasks run despite the flag — so the fixed version is proved against
something, not merely described.

**The cap is hard and test-and-take is atomic.** `Budget.reserve` reads, compares, then assigns:
three steps. Two lanes each reading "one call left" turns a hard cap into an advisory one, so
it runs under a lock. Driven with 8 threads against a 50-call cap: exactly 50.

**The ledger refuses to start from empty.** A corrupt ledger raises rather than silently
re-walking and **re-paying** for every tag ever walked, and it saves through the atomic helper
because a bare `os.replace` raises on Windows when any process holds the destination open.

## 6. THE CONTENT-CREATOR FILTER — MEASURE IT, THEN SHIP NOTHING

Your words: if the money to remove content creators is too high, take every clipper and editor
and accept a few creators slipping through. **On this route nothing separates them cheaply, so
I shipped no filter.**

**Fill first, because a signal that is absent cannot separate anything.**

| free signal | fill on 1,842 accounts | TRUE count |
|---|---|---|
| `verified` | 1,842 / 1,842 (100.0%) | 7 |
| `privateAccount` | 1,842 / 1,842 (100.0%) | 0 |
| `secret` | 1,842 / 1,842 (100.0%) | 0 |
| `shortDramaCreator` | 1,842 / 1,842 (100.0%) | 0 |
| **`follower_count`** | **0 / 1,842 (0.0%)** | — |

**THE FOLLOWER COUNT IS NOT ON THIS ROUTE.** The brief said three signals ride free in the same
call — bio, verified, follower count. Only two do. I enumerated every author key the hashtag
payload carries: **21 keys, each present on 296 of 296 author blocks, and not one of them is a
follower field.** `aweme_type` is absent here too, as already known. So a follower floor is not
merely unwise on this route — and it is already measured and refused, because the pages you
reject are the *bigger* ones — it is **impossible without buying a profile**, which this tool
does not do. The row records followers as `None` and never `0`, so no later reader can mistake
an absent field for a measurement.

**Of the three flags that do fill, two are constant and one is nearly so.** `privateAccount`,
`secret` and `shortDramaCreator` are FALSE on all 1,842 — a column with one value separates
nothing. `verified` is TRUE on 7 of 1,842: email rate 1 of 7 = 14.29% [2.57, 51.31] against
102 of 1,835 = 5.56% [4.60, 6.70]. **The intervals overlap almost entirely on a denominator of
seven.** That is not a signal, it is noise with a wide bar drawn around it.

**Conclusion: no free signal on this route separates a content creator from an editor. Ship no
filter.** A filter that costs money and does not work is worse than none, and you have already
said this outcome is acceptable. The bio *text* remains unexamined as a classifier — that is a
real option and it is free, but it is a piece of work, not a flag, and it is not this round.

## 7. THE LINK-TREE IDEA — SPECIFIED, PREREQUISITE MEASURED, NOT BUILT

The technique is real: follow the bio link, find a link tree, find the creator's other
profiles, read an address off one of those. It adds **one fetch per account**, which fights the
one thing this tool is for. So I measured only whether the surface exists.

| prerequisite | measured | 95% Wilson |
|---|---|---|
| a link in the bio, among accounts with a bio | 116 of 1,614 = **7.19%** | [6.03, 8.55] |
| of those, a link **aggregator** rather than a direct site | **0 of 116 = 0.00%** | [0.00, 3.21] |
| has a link but **no** email — the actual prize | 17 of 1,614 = **1.05%** | [0.66, 1.68] |

**The prize is about one account in a hundred, and not one of the links found was a link tree.**
Clock: one vendor page took a median 3.34 s, so 116 extra fetches at 4 lanes adds roughly 1.6
minutes to a run that took 2.6 — a **62% increase in wall clock to reach at most 1.05% more
accounts**, and on this sample the aggregator step has nothing to walk.

⚠️ Note the denominator honestly: this counts URLs **in the bio text**. TikTok's dedicated
`bioLink` field is **paid-only** and worth a measured 1 address in 60, so it was not bought.
A future version that buys `bioLink` might find more links than 7.19% — that is a different
measurement and this one does not settle it.

**The match-confidence problem must be solved before this ships.** The same username on another
platform is not proof of the same person, and **a wrong address is worse than no address** — it
is indistinguishable from a correct one in a spreadsheet. Any future version needs an explicit
confidence rule (exact handle match plus at least one corroborating signal, and a recorded
confidence on every row so a low-confidence address can be filtered out later), not an implied
one. **Recommendation: do not build this next.** The niche split in section 5 is worth far more
per unit of effort.

**AGAINST THE FUNNEL**, at its measured $1.94 per 1,000 delivered pages, 6.46 s per page, and
about 1 email per 16 good pages:
400 × 16 = 6,400 pages → 6,400/1000 × $1.94 = **$12.42**; 6,400 × 6.46 s = 41,344 s = **11.48 hours**.

> **The harvester is 36.0x cheaper and 67.8x faster for the same 400 addresses.**

**AND THEY ARE DIFFERENT PRODUCTS, WHICH MATTERS MORE THAN THE RATIO.** The funnel finds pages
you *want* — it judges, it photographs, it produces a grading sheet. **This tool does none of
that.** It gives you an address and the bio it came from, with no opinion about whether the
account is any good. 8,719 of the 10,164 addresses already collected are clients and only 120

⚠️ And note the caveat that cuts the other way: this run's 400-email projection assumes the
5.59% rate holds as tags are consumed. It will not hold forever — every tag saturated, and the

## 9. WHAT YOU GOT WRONG

**My first control declared a healthy extractor blind.** I planted a test address on the reserved
`example.com` domain to prove `extract_emails` fires, and it returned nothing. The extractor was fine — it runs every
hit through a deliverability guard that rejects `example.com` by design. Had I trusted the
control I would have "fixed" a working component; had I ignored it I would have run with an
unproven one. A positive control has to be built from something the system under test accepts.

**A lifted function compiled cleanly and raised on first call.** `wilson` lifted out of
`mark_reader` by AST died with `NameError: math` — the body needed its own imports. It imports
cleanly and is still unrunnable, which is exactly the failure this repo has hit before. It is
now driven once at import so the failure happens at load, not mid-run.

**My own test's grep detector was wrong twice before it was right.** First it fired on the
module's *docstring* discussing the seen store; I blanked docstrings by AST. Then it fired on
the `writes()` declaration string that exists precisely to say "NONE". A mention is not a
write. It now requires a write verb on the line, with a planted write proving it still fires
and a bare mention proving it does not.

**My dispatcher control did not reproduce the bug it claimed to demonstrate.** I wrote the
"broken" shape as check-then-break inside the submit loop, which actually works — 2 of 16 ran,
not 16. The demonstration would have passed while proving nothing. Rewritten to submit all 16
first, which is the real shape: the pool is handed every task before anything can set the flag.

**I counted spreadsheet rows with the wrong instrument and got 346 and 3,755.** Bios contain
newlines, so counting physical lines counts fragments. The CSV parser says 103 and 1,739, which
match the run. A row count is not a line count the moment a field can contain a newline.

**The brief's premise about the follower count was wrong and I nearly inherited it.** It is
stated as one of three free signals. It is absent on this route — 0 of 1,842. I only caught it
because I enumerated every author key rather than reading the one field I expected to find.
Section 6 reports the enumeration, not my expectation.

**I shipped a regression and an existing guard caught it.** The first full suite came back
`FAILED -- 28 red of 471` — one more than the 27 standing red. By name it was
`test_bl1513_cost_arithmetic`, and it was right: my AST lift needs *some* value for
`HA.USD_PER_CALL` so the class body can be built, and I had typed the HikerAPI price there.
The repo's rule is that only `ig_client` may state that number, precisely so it cannot drift
in two places. The fix is better than the rule requires: the stub is now a value that **fails
closed** — so large that any caller who forgot to pass `unit=` is refused on the first call
instead of being quietly charged the Instagram rate. Re-run clean at 27 of 471.

**My leak scan's handle detector fired on the word "edits".** One of the 1,842 accounts is
literally named `edits`, so the detector flagged my report, my run script and a test file
written months before this round. The rule is now: a token already present in the committed
tree at HEAD is an ordinary word, not this round's data. And the first version of that check
ran one `git grep` per handle up front — hundreds of full-tree searches, which did not finish
at all; it now runs only on tokens that actually matched, which is a handful.

**And one number in section 1 does not match section 5.** Bio fill is 92.65% on the ten
page-1-only tags and 87.62% on the sixteen walked to saturation. They are different
populations — page 1 of a hashtag is not a random sample of the hashtag — and the deeper pages
carry slightly fewer bios. I have not established why, and I am not going to dress a
5-point gap in an explanation I did not measure.

## 10. SAFETY

- **Backups before any spend**, all eight files, sha256-verified copy-side: `config.json`,
  `spend.json` (33,380 rows at `runs`), `master_leads.csv`, and all five seen stores including
  `clip_seen.json` (2,193, a bare list). Paths come from one round constant.
- **All five corruption controls fired on planted damage** before any result was trusted —
  including the one that matters: an **index-qualified** row fingerprint sees the deletion of
  one of a duplicated pair, where a natural-key set is provably blind to it.
- **The cap was proved by lifting `reserve()`'s real source by AST and driving it**: a funded
  cap allows and the meter advances; the ceiling raises; $0.00 raises; **and the meter does not
  advance on either refusal**. The proof wrote nowhere, verified by snapshotting the directory.
- **Nothing was latched.** No seen store was written, by declaration, by AST and by grep.
- **No Python process was killed. No `--no-verify`. No `/T` on any taskkill.**
- **The suite:** `FAILED -- 27 red of 471 suite(s)`, and those 27 are **by name** the identical
  27 red before this round began — attributed per suite name, never by subtracting two runner
  totals. **471 suites and 10,617 checks against 470 and 10,597 before: +1 suite and +20
  checks, both this round's.** The first run of the suite was `FAILED -- 28 red of 471` and the
  extra one was mine; see section 9.

**Committed:** `tests/test_bl1541_email_harvester.py` — 20 tests, every check raising rather
than asserting (`python -O` strips `assert`, which would make the whole file a silent pass; the
last test parses its own source for `ast.Assert` with a planted control proving the detector can
see one). Every negative claim has a positive control required to fire.
