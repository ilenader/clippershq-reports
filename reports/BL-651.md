## What shipped

The clipper `/campaigns` "Completed campaigns" strip already scrolled horizontally (native `overflow-x`, touch momentum, a peeking next card), but a desktop mouse user was stranded because native horizontal scroll needs a trackpad or shift-wheel gesture, and there was no visual cue that more campaigns existed off-screen. The strip is extracted into a new `CompletedRow` component that adds, display only:

* Desktop-only (`sm+`) arrow controls that scroll about 85% of the viewport, so a fresh card leads and the previous one still peeks.
* Soft left and right edge fades that appear only when more content exists in that direction and vanish at each end.

Every card renders exactly what it did before. `MiniCard` is untouched, so somesome's clipper-facing $9,750.00 of $9,750.00 at 100% and BL-535's fully-spent rule are unchanged.

**Which file, and the one I did NOT touch.** The live clipper path is `src/app/(app)/campaigns/CampaignsRedesign.tsx` (`page.tsx` sets `isTestUser = true`, BL-477, so every clipper gets the redesign). The legacy `page.tsx` "Past campaigns" strip renders through a **different** component (`src/components/ui/campaign-card.tsx`) and is dead code under `isTestUser = true`. It does not share `CampaignsRedesign`, so per the brief it was **left as-is**. I touched only `CampaignsRedesign.tsx`.

## PART 1 — horizontal scrolling that works everywhere

* **Touch:** unchanged native `overflow-x-auto` on the flex row, so it flicks with natural momentum. Cards are `w-[62%]` on phones so the next card peeks (the strongest "it scrolls" signal).
* **Desktop mouse:** two arrow buttons (lucide `ChevronLeft` / `ChevronRight`) appear at the row edges on `sm+`. Each calls `scrollBy({ left: Math.round(clientWidth * 0.85) * dir })`. A mouse-only user is no longer stranded.
* **Keyboard:** the scroll region keeps its existing `tabIndex={0}` `role="group"` `aria-label="Completed campaigns"`, so it is focusable and scrolls with the native arrow keys. The arrow buttons are deliberately `tabIndex={-1}` supplements (see PART 4).
* **No fight with the user's scroll:** no scroll-snap was imposed and no wheel hijacking; the arrows are additive, native scroll is untouched.

## PART 2 — the edge fades

Two `aria-hidden` gradient overlays, `from-[var(--bg-primary)] to-transparent`, `w-7` (28px, the peek gutter), `pointer-events-none`, toggled by opacity:

```
left fade  opacity = canLeft  ? 100 : 0
right fade opacity = canRight ? 100 : 0
canLeft  = scrollLeft > 1
canRight = scrollLeft < scrollWidth - clientWidth - 1   (recomputed on scroll + ResizeObserver)
```

They match the page background so they read as a fade, not a grey box, and `pointer-events-none` means a tap or a scroll-drag always reaches the card underneath. They are limited to the 28px gutter so no fully-visible card text is degraded (a11y ruling).

**Proven state machine** (verbatim copy of the shipped `updateEdges`, run in Node, viewport 1000px):

```
== MANY cards (content 2600px) ==
at start   scrollLeft=   0  L-fade=hidden R-fade=SHOWN   L-arrow=faded+disabled R-arrow=clickable
middle     scrollLeft= 800  L-fade=SHOWN  R-fade=SHOWN   L-arrow=clickable      R-arrow=clickable
at end     scrollLeft=1600  L-fade=SHOWN  R-fade=hidden  L-arrow=clickable      R-arrow=faded+disabled
== EXACTLY FITS / SINGLE card (no overflow) ==
           scrollLeft=   0  L-fade=hidden R-fade=hidden  L-arrow=faded+disabled R-arrow=faded+disabled
```

Left fade is hidden at the start, right fade is hidden at the end, both show in the middle, and both are hidden when nothing overflows. Exactly the owner's ask.

## PART 4 — mobile and accessibility

* **One-handed on a phone:** touch scroll with momentum plus the peeking card; the arrows are a desktop supplement (`hidden ... sm:grid`), so mobile is not cluttered.
* **The mobile swipe trap, handled:** the global sidebar swipe handler (`app-layout.tsx:497`) already opts out any `.overflow-x-auto` container, which this row is, so horizontal drags were not eaten. Belt-and-suspenders, `data-no-swipe` was added to the scroll container as well (and to the arrow buttons), per CLAUDE.md and the a11y lead's N2.
* **Keyboard + focus order:** the scroll region is the operable control (tabbable, native arrow-key scroll). The arrow buttons are `tabIndex={-1}` so they can never take then lose focus when they fade out at an end (SC 2.4.3 / 3.2.1); they are never unmounted.
* **Screen reader:** arrows carry `aria-label="Scroll completed campaigns left"` / `"...right"`; the chevrons are `aria-hidden focusable="false"`. The buttons and fades are siblings **outside** the `role="group"`, so the group still contains only campaign cards (SC 1.3.1).
* **Contrast:** each arrow is a solid `--bg-card` chip so the chevron and its focus ring have a known adjacent colour over any card photo (SC 1.4.11); 44px target (`h-11 w-11`, SC 2.5.8).
* **Reduced motion:** the arrow scroll reads `prefers-reduced-motion` at click time and uses `behavior: 'auto'` when set, `'smooth'` otherwise (SC 2.3.3).

**The a11y review ran twice** (once on the plan, once on the final written code). All must-fixes M1 to M5 and should-fixes were applied. Two notes from the final pass: N1 ("code not in file") was the reviewer reading the primary tree rather than this worktree, where the code is present and built; N4 (the pre-existing `grayscale opacity-80` on completed cards, `MiniCard` line 191) is **flagged, not fixed** because `MiniCard` is frozen for this display-only round and predates it.
