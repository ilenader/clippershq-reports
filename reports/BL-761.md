## Item 1 — the 52% discard, closed

One condition in `append_found_to_master`:

```python
if not r.get("email") or r.get("already_in_db") == "yes":     # BEFORE
    continue
```

Now a lead is saved when it has a **handle OR an email**; only a lead with *neither* is skipped. **Proven on a live run:**

```

rows saved with EMPTY email (DM leads) : 6/6
... all of which carry a handle        : True
dropped_fields                         : none
```

All six saved with `email` empty — which is what routes them to the DM list rather than the bot list. The seven with neither handle nor email were still skipped, correctly.

The old test asserted the bug (`test_append_skips_noemail_and_indb`, "appended == 1"). It is rewritten as `test_append_saves_handle_only_and_skips_indb` and now pins all four outcomes — saved-with-email, saved-DM-only, skipped-in-DB, skipped-no-contact — with the reasoning recorded inline so it cannot quietly revert.

## Item 2 — the safety work now survives the write

Master went **62 → 66 columns**. Four added, four existing ones reused.

**Reused (correct semantics, no new column needed):** `display_name` (artist name), `dominant_lang` (language), `source_tag` (provenance), `quality_note` (the verify warning).

**Added:** `country`, `email_quality`, `spotify_monthly_listeners`, `spotify_followers`.

> **Why the size fields are namespaced.** The obvious move is to reuse the existing `followers` column. It is wrong: other funnels fill `followers` with an Instagram/TikTok count, and a Spotify lead's `platform` is usually `instagram` (the handle came from there), so a bare Spotify follower count in that column would read as an IG count and silently corrupt every cross-funnel comparison. Two honest columns beat one ambiguous one — this round exists because of ambiguous and empty columns.

**Migration:** strict append-only (`csv.reader` → append 4 empty fields → `csv.writer`), never line-based (bios carry embedded newlines). Not `writer.migrate_master_csv`, which "fills sensibly" and reconstructs `instagram_url` — benign but a violation of the standard for a schema change.

### A defect found while proving it

The first live run stored `dominant_lang` as **`"lang:english"` / `"language unknown"`** — the classifier's *display* string. Other funnels store a bare value there, so that would have made the column un-comparable across funnels: the exact ambiguity trap this item exists to remove. Added `_lang_cell()`, which stores `english`, or the literal `unknown` when the gate ran and could not decide, or `""` when the gate never ran. The explicit `unknown` is what makes the language-unclear population auditable — the thing BL-746 could not check at all.

## Item 5 — **the finding is inverted, and BL-746 had it backwards**

I reported "one dedup miss" in BL-746. Investigated properly, that is wrong on both halves.

**The duplicate is correct behaviour.** `_is_mergeable_email` deliberately refuses to merge on agency addresses, because two artists sharing a manager are two different leads (the measured Buba Corelli / Jala Brat case). `fullcircle-mgmt.com` contains `mgmt`, so Aaron Rowe and Aubory Bugg were correctly kept as two rows. **Nothing to fix.**

**The pre-run gate cannot see emails at all, also by design.** `build_master_index` returns **58,109 keys, of which 0 contain `@`** — it is handle-keyed. So `already_in_db = "no"` was *correct*: those handles genuinely were not in master.

**The real defect is the opposite one, and it is worse.** The agency guard is word-list bound, so it protects `fullcircle-mgmt.com` and misses management companies whose domains carry no agency word. Three artists were folded into unrelated artists who merely share a manager, and **each lost its master row entirely**:

| artist | folded into | shared address |
|---|---|---|
| **Saya Gray** | `dexterinthenewsagent` | `…@mc1r.co` |
| **K Motionz** | `molliecollinsofficial` | `…@ctrlfrk.co.uk` |
| **Humble the Great** | `pipmillett` | `…@plusfoursmusic.com` |

All three are **absent from master today** — verified, 0 rows each.

### Why no fix shipped, and what I need from you

The obvious guard — *"if both records carry handles and share none, they are different people"* — directly contradicts this module's own documented, tested contract, asserted in `crossdedup._selftest` case 1: *"cross-platform SAME EMAIL, different handles + funnels → one person"* (`me@studio.io` shared by `artistx` and `diffhandle`).

That fixture is **structurally identical** to the Saya Gray failure: a non-free domain whose local part matches neither handle. No heuristic separates "one artist with two accounts" from "two artists with one manager" on that evidence. I implemented the guard, watched it break 7 checks across `test_crossdedup` and `test_gp_keyless_dedup`, and reverted it — changing identity semantics across five funnels to win one case is not a trade I should make silently.

The trade is recorded in `crossdedup.py` as an open issue with three costed options: **(a)** accept the deletions; **(b)** require positive personal evidence for an email key (`role_policy.reaches_person_directly` — fixes it, merges strictly less, needs `_selftest` case 1 re-litigated); **(c)** keep the merge but carry the absorbed artist's handle onto the surviving row so the contact survives even when the row does not. **(c) is my recommendation** — it loses no lead and no merge. **Your call.**

## Item 6 — 'personal' now means it

The gap was never agency mailboxes or agency-word domains — those were already caught. It was **a named human at a company that simply is not the artist**: `…@caa.com` (Creative Artists Agency), `…@threesixzero.com`, `…@bethemusic.co.uk`. No word list wins that.

So the test is inverted: an address counts as personal only with **positive evidence it reaches the person** — a free provider, the artist's own domain, or the artist's own name in the mailbox (`[redacted]@mskd.com`). Added as `role_policy.reaches_person_directly()`.

**Re-measured on the same 476 addresses from the audited run:**

| label | before | after |
|---|---|---|
| personal | 352 | **257** |
| agency | 92 | **180** |
| role | 32 | **39** |

| | n | wrong | **precision** |
|---|---|---|---|
| BEFORE | 352 | 141 | **59.9%** |
| AFTER | 257 | 46 | **82.1%** |

95 addresses moved personal → agency; 7 moved agency → role. BL-746's "140 of 352 (40%)" recomputes here as 141 of 352 — the same number.

**The residual 46 are mostly yardstick conservatism, not error.** The independent classifier counts any non-freemail address as business, but `[redacted]@troydoherty.com`, `[redacted]@daveeastmusic.com` and `[redacted]@jessicabaio.com` are the artist's own domain and do reach them. True precision is above 82.1%; I am reporting the conservative figure.
