## 1. The counter bug — the denominator excludes its own numerator's source

**`passed_filter` counts the expanded pool. `discovered` counts only the seeds.**

`spotify_finder.run()` snapshots the denominator once, before any work:

```
line 706:  stats = {"discovered": len(artists), ...}      # 1,073 seeds — never updated again
line 732:  work = deque((a, 0) for a in artists)
line 805:  _maybe_expand(...)                             # pushes RELATED artists into `work`
line 601:      work.append((ref, depth + 1))
               stats["expanded"] += 1                     # counted here, and ONLY here
```

Related-artist expansion (`spotify_expand_related: true`, `spotify_expand_depth: 2`) appends new artists to the live worklist. They are processed, filtered, tallied and can pass — but `discovered` never learns they exist. `control.py:1332` then prints `passed` over `discovered`.

### The true denominator, measured independently of the counter

From `logs/run.log`, restricted to this run's window (14:02:40 → 17:01:32):

| | |
|---|---|
| `queryArtistOverview` calls | **3,127** |
| distinct artist IDs among them | **3,127** |
| artists queried more than once | **0** |
| seeds the summary reported | 1,073 |
| **added by expansion** | **≈2,054** |

So the honest line is **1,752 of 3,127 examined = 56% passed**, which is entirely sensible. Nothing is double-counted — every artist ID appears exactly once, so this is not a double-tally bug. The counter is measuring a real quantity against the wrong baseline.

**Fix:** increment `discovered` where `expanded` is incremented (line 601), or print `passed of (discovered + expanded)`. One line.

### A second, separate counter bug in the same summary — your email total is understated

`control.py:1308`:

```python
# every email is classified personal or role, across ALL sources -> total emails
emails = _sum(stats, "personal", "role")
```

The comment is wrong for this funnel. Spotify classifies into **three** buckets — `personal`, `role` **and `agency`** — and `agency` is omitted from the sum.

| bucket | count |
|---|---|
| personal | 352 |
| role | 32 |
| **agency** | **92 — not counted** |
| **actual addresses in the sheet** | **476** |

The run reported **384 emails**; it found **476**. The 92 missing are the agency/management addresses, which for a music funnel are often the *correct* contact. Both bugs are in the summary layer only — no lead data is affected.

> You were right to distrust the rest of the summary: two of the numbers on that screen are wrong. But the underlying run data is sound, and everything below is measured from the sheet, the log and the master directly rather than from those counters.
