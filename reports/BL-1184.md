# BL-1184 — parallelising the judge bought 2.95x, and the API limiter was never the wall

**2.95x, measured in one process against its own serial baseline: 54 → 160 pages/hour at 4
workers.** The operator's instinct was right, but two of the assumptions underneath it were
not, and both are worth more than the speedup:

1. **The rate limiter is idle 99% of the time.** In a 562-second parallel run the limiter
   waited **7 seconds**. The API was never the constraint being worked around.
2. **OCR barely parallelises at all.** A thread pool plateaus at **1.77x**; a *process* pool
   goes **backwards** — 0.56x at 12 workers, per-frame p99 **35.5s**. ONNX Runtime already
   uses all 12 cores internally, so Python-level parallelism just contends for them.

The 2.95x came from overlapping stages, not from making OCR faster.

Every figure here came from **`.venv\Scripts\python.exe`, Python 3.11.9**. Bare `python` is
3.13.14 and lacks the packages; it was used only for the stdlib-only claim readers.

## 1. Where the seconds actually go — and the answer changes with load

Two measurements of the same pipeline, minutes apart, **8.0x different**:

| stage | isolated profile (quiet) | live run (5 rounds loaded) |
|---|---:|---:|
| decode (ffmpeg) | 0.86 s/page — 10.5% | **43.85 s/page — 51.2%** |
| OCR | 2.42 s/page — 29.4% | **37.93 s/page — 44.3%** |
| download (CDN) | 3.03 s/page — 36.8% | 3.76 s/page — 4.4% |
| API call | 1.92 s/page — 23.3% | (limiter idle, see below) |
| judge | 0.001 s/page | 0.08 s/page |
| **total serial** | **8.24 s/page** | **66.30 s/page** |

**The network stage is flat and the CPU stages inflate 15–50x.** Download barely moved
(3.03 → 3.76s) because it waits on a socket, not a core. Decode and OCR are CPU and got
crushed by the five other rounds on the box.

So the honest answer to "where do the 10.9 seconds go" is **it depends on what else is
running**, and on a loaded machine it is decode and OCR, overwhelmingly. Six OCR reads per
page (2 posts × 3 frames) is the shape of the work; the frame count is a constant somebody
chose, and it is the obvious next lever.

## 2. The parallel speedup, and where it stops

Measured on 48 cached frames, 3 repeats, median — `scratch/bl1184_scale.json`:

| workers | 1 | 2 | 3 | **4** | 6 | 8 | 12 |
|---|---:|---:|---:|---:|---:|---:|---:|
| **thread pool** | 1.00x | 1.37x | 1.56x | **1.75x** | 1.70x | 1.73x | 1.77x |
| **process pool** | 1.00x | 1.09x | 1.00x | 1.05x | 0.89x | 0.67x | **0.56x** |

**Threads plateau at 4 workers. Processes are worse than serial past 2** — and their
per-frame p99 degrades to 35.5s, which is the 28x-against-itself contention this project has
seen before, reproduced deliberately.

`recommended_workers()` reads the knee out of that JSON, so the number in the code is the
number that was measured: **4**.

**End to end, on 33 real pages:**

| | pages/hour | s/page |
|---|---:|---:|
| serial (1 worker) | 54 | 66.30 |
| **parallel (4 workers)** | **160** | **22.46** |
| **speedup** | **2.95x** | |

2,140 seconds of worker time completed in 562 seconds of wall clock — **3.8x concurrency
achieved on 4 workers**, which is close to the ceiling those workers can give.

## 3. The two legs, separated

```
fetcher (ONE thread)              workers (4 threads)
--------------------              -------------------
seen-set check      (free)
API user_medias     (BILLED)  ->  download -> ffmpeg -> OCR -> judge
resolve_contact     (BILLED)      (all free: CDN HTTP and local CPU)
```

Every billed request is made by one thread paced by `RateLimiter`. **That is why the ledger is
safe: there is exactly one writer to `spend.json`, by construction** — no worker can bill a
request the fetcher did not pace, so there is no ledger lock to contend. The workers do only
free work.

The seen-set *is* shared mutable state and *is* locked: `PageSeen.record_many` holds
`filelock.file_lock` across the whole read-modify-write, and the driver writes **once per
batch**, not once per page. `os.replace` makes one write atomic and cannot order a pair —
`clip_seen.json` lost 12 of 13 records to exactly that race.

**A real bug the tests caught.** The first `RateLimiter` computed its wait once and slept.
Because the wait is computed *after* the lock is dropped, a descheduled thread sleeps for less
than it owes: six threads on a 50 ms interval produced a **31 ms** minimum gap. A limiter that
undershoots by 38% is a limiter that gets the account rate-limited. It now re-reads the clock
until the due instant has genuinely passed.

## 4. Never pay twice — measured, not asserted

The seen-set is consulted **before** the billed call. Running the identical 25-page set twice:

```
PASS 2 -- the SAME 25 pages again.
  receipts before 33 -> after 33   DELTA = 0   ZERO: nothing was re-fetched
  pass 2 fetched 0, skipped 25 as already judged
```

**Vendor receipt delta: 0.** `scratch/bl1184_repeat.json`.

## 5. The new ceiling — and the clock still binds

| | loaded (5 rounds) | quiet |
|---|---:|---:|
| pages judged / hour | **160** | **1,289** |
| passing pages / hour (6.2% rate) | 9.9 | 79.9 |

| budget | pages judged | passing | hours (loaded … quiet) |
|---:|---:|---:|---|
| $3.00 | 4,708 | 291 | 29.4 … 3.7 |
| $10.00 | 15,693 | 972 | 97.9 … 12.2 |
| $50.00 | 78,468 | 4,865 | 489.5 … 60.9 |

Cost per passing page: **$0.0103**, unchanged by parallelism — the same calls are made, just
sooner.

**Which binds?** The API at 0.44 req/s could sustain 1,584 pages/hour. The pipeline does
160–1,289. So the CPU leg is still 1.2x–9.9x slower than the limiter: **the clock binds, the
money never does** — vendor spend is about **$0.10/hour**. And on a loaded box it is not even
this code that binds, it is the other rounds.

> **The single number that would move this most is the frame count.** Six OCR reads per page
> is 44% of the loaded cost and 29% of the quiet cost, and BL-1180 measured that agreement
> across 3 frames is what the refusal rule needs — not 6. Halving posts-per-page from 2 to 1
> is a straight ~2x on the dominant stage and was **not** attempted here.
