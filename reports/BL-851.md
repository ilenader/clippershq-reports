## 0. Two corrections to the brief, both made before spending

**"~755 clips from 66 accounts" is a line count, not a clip count.** BL-845's report says 755;
BL-846's own saved audit (`scratch/bl846_audit.json`) says `n=629`. The library is append-only
with `rev` for updates, so lines ≥ clips permanently. At the moment this round started there were
**831 lines carrying 634 distinct `clip_id`s** — 165 of them `rev=2` rows that BL-849 was
appending live. 634 is the number to grow from, and it is the number this report uses. The gap
was not a loss; nothing disappeared.

**`clip_max_pages_per_account` is 1 in live config, which caps the entire corpus below the
target.** 189 confirmed pages × 12 clips per page = 2,268 gross, against 634 already held and a
view floor that cuts most accounts well short of 12. 2,000 was not reachable at that setting.

This round raised the page cap to 5 **in a scratch copy of the config** (`scratch/bl851_config.json`,
passed via `--config`) rather than in `config.json`, because eight other agents were reading the
live config while this ran. `config.json` is byte-identical: campaigns SHA `8e02f8d6f6307ae8`,
`clip_max_pages_per_account` still 1, 162 keys, `tests/test_config_contract.py` ALL OK.

**The 20,000-view floor was not touched.** The page cap is a mechanical limit on how deep the
walk pages; the floor is the quality gate. Loosening the gate to make a number would have changed
what the library *is*, and that is not a call this round had authority to make.

## 4. `run_id` does NOT land on clip rows. It cannot. There is no such field.

**Measured: 0 of 1,369 new rows carry a `run_id`.** This is not a wiring failure and no run would
have fixed it:

- `run_id` is a **master-CSV column** — declared in `writer.FULL_COLUMNS` (`writer.py:194`) and
  stamped by `writer._stamp_run_id()` as a row is appended to `master_leads.csv`.
- `clip_library.CLIP_FIELDS` does not contain `run_id`, so it has no contract, and
  `clip_library.append()` writes the record as-is with no stamping hook.
- `control.py:2529` does call `writer.set_run_id(writer.new_run_id("clip_library"))` before the
  walk. **The clip walk writes no master rows**, so that call sets a variable nothing reads. It is
  inert in this funnel, not broken — the same line is load-bearing in the five funnels that do
  write leads.

So "all six funnels now stamp it" is true of the six funnels' *lead* output and says nothing about
the clip library. A clip row's provenance today is the account, the permalink and the `rev`. If a
clip needs to be attributable to a run — and for a store that four rounds are now appending to
concurrently, it probably does — `run_id` has to be added to `CLIP_FIELDS` and set in
`clip_runner.clip_record()`. That is a module change, which this round was scoped out of, and
`clip_library.py` is held by BL-849/BL-854 right now.

## 6. A finding this walk produced: the speech pass covers 72%, and the panel says 99.3%

`speech_frac` and `format` landed on **985 of 1,369 new rows (72.0%)**. The other 384 stored with
provenance `absent`. The walk's own audio-split panel reported **"not measurable: 10"** — it reads
as 99.3% coverage against a library that carries 72.0%.

The gap is not random. It is almost perfectly explained by one field:

| | measured (985) | absent (384) |
|---|---|---|
| `audio_type` | `original_sounds` **985 / 985** | `licensed_music` **374**, unknown 9, `original_sounds` 1 |
| `media_renditions` present | 978 | 383 |

Every clip that got measured is `original_sounds`; 97.4% of the clips that did not are
`licensed_music`. The renditions block is present on both, so the clips are not malformed — the
audio simply is not retrievable for licensed-music posts, which is the expected rights behaviour.

Two consequences worth someone's attention, neither of which this round could fix without touching
`clip_speech.py`:

1. **The panel's denominator is the clips the callback saw, not the clips whose measurement
   survived into the record.** A reader takes "10 not measurable" as near-total coverage. That is
   the vacuous-number shape BL-804 warned about and BL-842 already fixed once for the UNWIRED
   stage counters, reappearing in a new panel.
2. **The 27.3% with no verdict are exactly the clips the routing decision matters most for.**
   MEMEBOT-006 routes music-only to mute-and-replace and dialogue to duck-under. A licensed-music
   clip is the strongest mute-and-replace candidate there is, and it is the one category that
   arrives with `format` empty.

The stored `format` on measured rows splits 598 `dialogue-first` / 387 `music-first`, against the
panel's 584 music-only + 688 dialogue-over-music + 82 dialogue-only. Those two shapes cannot both
be describing the same 1,366 clips, and the panel is the optimistic one. I have not read far
enough into `clip_speech.py` to say which side is wrong — flagging, not diagnosing.

## 8. Two clip_library processes were running, and the ledger cannot tell them apart

The run-status file records **$0.2208** for this run; the walk's own counter records **$0.1674**.
Both are correct, and the difference is not a metering bug:

- `ig_client.http_requests` — the client's own counter, monotonic, initialised once — read **279**
  at the end. 250 pages + 29 paid resolves = 279. The model and the counter agree exactly.
- The `CLIP_LIBRARY` campaign ledger took **368 calls across 15 rows** in the run window.
- `scratch/clip_library.status.json` carries **pid 37352, ts 15:34:02, round `clip_library`,
  status running**. This round's pid was **28572**, started 15:29:49. A second clip_library process
  was live inside this run's window and overwrote the marker.

89 calls / $0.0534 of that campaign delta belong to the other process. `run.py`'s own docstring
predicted this: *"Two runs of the SAME funnel at once still share a campaign and would split
wrongly — the ledger has no run_id."* This is that case, observed live. It is also why the library
gained **1,369** clips against this walk's **1,366** — the other three are the second process's.

**The honest per-run cost of BL-851 is $0.1674**, on the client counter, which is the only figure
that isolates one process. The ledger total is correct as a *campaign* total and should not be
adjusted.

## 10. Claims and concurrency

Claimed **BL-851** at start (`tools/claim.py start`), writing `clip_library/`, `clip_seen.json`,
`scratch/bl851_*`. The tool flagged one conflict immediately:

```
! ADVISORY - another live claim intends to write the same path(s):
    BL-849  clip_library/
```

**Proceeded, deliberately.** The library is append-only JSONL sharded by post month, with
last-wins by `(clip_id, rev)`; BL-849/BL-854 append `rev=2` vision rows for clips that already
exist, this round appends `rev=1` rows for clips that do not. The two writers cannot collide on a
record, and the format exists precisely so they do not have to coordinate. Two other rounds
(MEMEBOT-016, BL-855) independently noted this round's live append in their own claims and
correctly restricted themselves to read-only work on the library. The advisory mechanism did its
job in both directions.

All measurement reads went through `read_snapshot.snapshot()` with every shard frozen inside one
`ExitStack`, so the fill table and its denominator come from a single moment even while BL-849 was
appending.
