## 1. It is a SECOND code path, and the code says so in its own comment

`clip_pipeline` has **two** places the corpus can be reached, and the same empty intersection
produces the **right** answer in one and the **wrong** answer in the other:

| | site | when it fires | what the empty pool does |
|---|---|---|---|
| **path 1** | `~1843`, the no-repeat **diversion** | a store song matched but is in `avoid` | `_corpus_joinable` empty → **does not divert** → keeps the match, records `repeat_forced`. **Correct.** |
| **path 2** | `~1938`, the **no-match LRU fallback** | no store song matched at all | `_joinable_pool` empty → **ships an unjoinable record**. **Wrong.** |

Path 1 is the 60-of-60 fix. Path 2 is the recurrence, and the comment there already admits it:

> *"THIS IS A RECURRENCE, not a new defect… an unfiltered LRU does not RISK an unjoinable
> record, it GUARANTEES one."*

**The bug is in its next sentence.** It justifies shipping anyway with *"an empty pool renders
without a track, which is worse"* — a choice between two options, unjoinable bed or no bed.
**There is a third: use a store song.** Path 1 had already established that a repeat is
acceptable. Path 2 never considered it.

## 2. THE NUMBER: I corrected my own headline before recommending on it

My first measurement said option (a) costs **−83.2%** of output. **That is the library rate,
not the render rate**, and using it would have argued against (a) on a number 8× too big. The
ranker picks high-scoring clips, so the fall-through rate among clips that actually render is
far lower:

```
library                         2,731
gets a STORE match                460  (16.8%)
falls through to the corpus     2,271  (83.2%)   <- library rate, NOT the cost of (a)

RENDERED (finished)               369
of those, UNJOINABLE               36  (9.8%)    <- what option (a) would actually refuse
                                                    (22.5% in the most recent 40)
```

### The three options, measured

| option | output | joinable after | real cost |
|---|--:|--:|---|
| **(a) refuse** | **−9.8%** (−22.5% on a recent batch) | 100% | loses real videos, permanently |
| **(b) make corpus joinable** | 0% | 100% | **A NO-OP AS BRIEFED — see §3** |
| **(c) repeat a store song** | **0%** | **100%** | concentration — and it goes the *other* way |

### (c) does not concentrate. It de-concentrates.

The brief warned to watch whether the fix pushes the top song past its 56–62%. Measured, using
the store's own LRU (least-used first), which is what the fallback would use:

```
BEFORE (joinable renders, n=333)      AFTER option (c), n=369
  sng_0004  213  (64.0%)                sng_0004  213  (57.7%)
  sng_0003   57  (17.1%)                sng_0003   57  (15.4%)
  sng_0001   53  (15.9%)                sng_0001   53  (14.4%)
  sng_0002   10  ( 3.0%)                sng_0002   46  (12.5%)

TOP-SONG SHARE: 64.0% -> 57.7%   (-6.2 pt)
```

The 36 unjoinable renders go to the **least-used** songs, so `sng_0002` rises from 3.0% to
12.5% and the top song's share **falls**. Concentration improves.

### RECOMMENDATION: **(c)**, and it is not close

**Zero output cost, joinable rate 100%, top-song share −6.2 points, no operator time.** The
principle is already on this project's record — *a fallback that guarantees an unjoinable
result is worse than a repeat* — and (c) is the only option that costs nothing to obey it.

## 3. Option (b) as briefed is a NO-OP, and it would have cost the operator 17 tracks of hand-marking for nothing

The brief says: give the corpus tracks store entries so a corpus bed produces a joinable
record. **It would not.** The pipeline compares the wrong field:

```
operator adds store entry path = scratch/bl691_audio/1227570025460968.m4a

pipeline compares ledger_song_path(track["file"])
  ->  track_1227570025460968.json          in store_paths?  FALSE

if it compared     track["local"]
  ->  scratch/bl691_audio/1227570025460968.m4a   in store_paths?  TRUE
```

`file` is the **metadata JSON name**; `local` is the audio. So the 17 hand-markable tracks
could all be added to the store, correctly, and the preference would **still** never bind.

**Option (b) therefore requires two changes, not one:** the operator's store entries **and** a
one-line field correction in `clip_pipeline.py` — which BL-1113 holds. Naming this is the most
valuable thing in this round: hand-marking 17 tracks by ear is hours of the operator's time,
and without the field fix it buys zero.

**The proposal is written, not applied.** `scratch/bl1114_songs_proposal.json` carries 17
entries with `enabled: false` and empty `hooks[]`, plus the blocker recorded inside the file.
**`scratch/songs.json` was not touched** — it is the operator's file, and this brief's
authorisation to *propose* is recorded in the proposal's `_consent` field.

Two of the 19 corpus tracks have **no local audio** and cannot be proposed at all.

## Honest limits

- **Nothing was fixed.** This round decides and measures; the code change is blocked on
  BL-1113 and is handed off, not done.
- **The (c) de-concentration figure assumes LRU over the store.** If the fallback instead
  reused the *matched* tier's song, concentration would rise rather than fall. The number is
  conditional on the implementation choosing least-used-first, which is what the existing
  `pick()` does — but it is a projection over the 36 existing unjoinable records, not an
  observation of a shipped fix.
- **The 9.8% and 22.5% are different populations**: 36 of 369 lifetime, versus 9 of the last
  40. I recommend on the lifetime figure and quote both.
- **I did not verify the 17 proposed tracks are usable beds** — only that their audio exists on
  disk. Duration, loudness and whether any is unusable for a 20-second window are unchecked.
- **Option (b)'s field fix is untested.** I demonstrated the comparison succeeds with `local`
  in isolation; I did not change the pipeline or run it that way.
- **`sng_0002` at 12.5% after (c) is still a small share**, and four songs remain a thin
  supply for 2,731 clips. (c) fixes attributability, not variety.
