## 3. Item 2 — account interleaving

**`scratch/bl1020_rank_interleave.patch` IS NOT A GIT PATCH.** `git apply --check` refuses
it: *"No valid patches in input"*. It is a prose handover with `+`-prefixed code blocks —
BL-1020 wrote it that way deliberately ("land the measurement, hand over the code") because
clip_pipeline.py was claimed. The vetted source is `scratch/bl1020_interleave.py`, whose own
15-check self-test passes; that is what was ported.

`interleave_by_account` runs **after** the servable sort and **before** the `limit` cut.
Both halves matter: Python's sort is stable, so interleaving *before* the servable sort
would be undone by it; and after the cut it would reorder a batch whose composition was
already decided.

### The invariant, stated correctly — the brief's phrasing is false by design

The brief says *"assert the returned set is identical"*. **Read against the truncated return
of `rank_candidates`, that is false on correct code, and it has to be.** The list is cut to
`want * over_provision`; reordering necessarily changes who survives the cut. That change
*is* the feature. The only ways to make that assertion pass are to stop interleaving, or to
interleave after the cut — which restores the concentration being fixed.

So three things are measured separately, because collapsing them is how an ordering that
silently drops rows would get through:

| assertion | result |
|---|---|
| `interleave_by_account(x)` is a multiset permutation of `x` (BL-1020's own check) | **True** — 1,720 in, 1,720 out, same objects |
| input list not mutated | **True** |
| `rank_candidates` set-identical when the cut does not bind | **True** — 1,720 both ways |
| every returned clip came from the gated pool | **True** |
| no duplicates | **True** |
| set identical on the **truncated** top-30 | **False — 65 displaced, by design** |

BL-1020 measured the same effect and checked it rather than hiding it: of the clips it
displaced from the top 30, the three carrying a hand verdict were **all three "no"**.

## 4. Item 4 — the permanently-empty field, and the guard that reversed my fix

value and the alias never fired.

**I removed it first. `tests/test_matcher_boundary.py` refused that, and was right.**

    clip_pipeline.dict_of() drops ['clip_duration_s'], which song_library reads.
    A dropped field is INVISIBLE: the clip parks, which looks identical to
    'no rule matched'. Add it to dict_of, or record a reason in EXEMPT.

the intended steady state" — MEMEBOT-081 worked to close it. Re-opening it to fix a naming
trap is a bad trade.

sets the alias to the same resolved value as `duration_s`:

The field stops being a lie, the boundary guard stays green, `EXEMPT` stays empty, and no

## 5. Item 5 — the ceiling's receipt

MEMEBOT-108 measured the duration ceiling binding on **30 of 30** renders while provenance
was **0 of 30**: every output cut to 20.0s with nothing saying by what, or whether the cut
was configured at all. Thirty 20.0s videos from a ceiling and thirty from a short library
look identical and need opposite fixes.

`ceiling_provenance()` reads `memebot/scraper/config.yaml` → `edit.transform.duration_ceiling`
and falls back to `duration.CEILING_S` — **derived, never restated**, the same discipline as
`MIN_DURATION_S`. It is computed **once per batch** and stamped on every record.

**Two bugs in it, both caught by running it rather than reading it:**

1. `MEMEBOT_DIR` is already `memebot/scraper`, so joining `"scraper"` again produced
   `memebot/scraper/scraper/config.yaml`. The function reported *"config unreadable"* — it
   failed honestly instead of guessing a ceiling, which is the design working, and the
   return value named the path it could not read.
2. The block lives at **`edit.transform`**, not top-level `transform`. Reading the wrong
   depth returned `{}`, which renders as *"enabled is False — NO ceiling is applied"*: a
   confident, well-worded, **wrong** receipt on every record. A provenance field that fails
   soft is worse than one that fails loud.

On the live config, and on the real ledger rows written by this round:

    {"applied": true, "ceiling_s": 20.0,
     "source": "config.yaml transform.duration_ceiling.ceiling_s",
     "why": "output trimmed to at most 20.0s; the TAIL only, never the head"}

And the receipt matches the artefact: sources of **52.8s and 77.1s** rendered to **20.00s
and 20.02s**.

### 74 ledger rows carry the receipt saying it could NOT read the config — and that is the design working

Checking the ledger rather than assuming turned up something I did not put there on purpose.
**120 rows now carry `ceiling_provenance`, and 74 of them predate my fix**, all with the
identical four-key shape and all reading:

    "applied": false, "source": "config unreadable",
    "why": "could not read ...\\scratch\\mb116_work\\snap\\scraper\\scraper\\config.yaml"

Note `scraper\scraper` — **that is my doubled-path bug**. A concurrent round (MEMEBOT-116)
snapshotted the worktree into `scratch/mb116_work/snap/` while `clip_pipeline.py` was
mid-edit, and has been running batches against that frozen copy. Two things follow:

1. **The field failed loudly instead of guessing.** Those 74 rows say "I could not read the
   config" and name the exact path. Had `ceiling_provenance` defaulted to a plausible 20.0,
   the ledger would now hold 74 confident, wrong receipts and nothing would ever have said
   so. This is the second time in one round that the fail-loud choice paid for itself.
2. **A snapshot of a live worktree captures half-finished work.** Not my round's to fix, but
   worth naming: those rows are attributable and harmless, and they are only harmless
   because the field is honest about its own failure.

So the accurate claim is narrow: **every record my runs wrote carries an `applied: true`
receipt at 20.0s**. Rows written from MEMEBOT-116's snapshot carry a truthful
`config unreadable` receipt until that snapshot is refreshed.
