## 0. The brief asked me to fix one gate. There were three, and fixing one would have shipped nothing.

BL-862 found that `run.py:203` set the run id and the funnel overwrote it moments later. That is real and it is fixed. But it is the *first* of three doors between `--run-id` and an attributable row, and the other two were also shut:

| gate | state before | why it mattered |
|---|---|---|
| **1. the id survives to write time** | **BROKEN** — every funnel's `set_run_id(new_run_id(...))` clobbered the operator's value | BL-862's finding |
| **2. master HAS a `run_id` column** | **BROKEN** — file was **71** wide, `FULL_COLUMNS` is **72**, and `_stamp_run_id` returns any row narrower than index 71 *unchanged* | no value can land in a column that does not exist |
| **3. the append path stamps it** | **BROKEN** — `crossdedup.append_leads`, the path all five lead funnels use, writes via `DictWriter` and never called `_stamp_run_id` | the row is written with `run_id=''` even when gates 1 and 2 are open |

Gate 2 was found by trying to record a baseline before the proof run: `run_id col index: ABSENT`. Gate 3 was found by testing `append_leads` directly rather than paying a funnel to reveal it.

**This is the point worth carrying forward.** Had this round fixed only what it was asked to fix, every check would have passed — `--run-id` accepted, lock held, `get_run_id()` correct — and not one row would have been attributable. That is the same failure BL-862 reported about BL-861 a round earlier: a mechanism that is correct in isolation and inert in the system.

## 1. Gate 1 — the explicit-wins lock

One rule in one place (`writer.py`), rather than a guard at five call sites:

```python
def set_run_id(run_id, explicit=False):
    if not rid:                                  # clearing releases the lock
        _RUN_ID, _RUN_ID_EXPLICIT = "", False
    if _RUN_ID_EXPLICIT and not explicit:
        return _RUN_ID                           # a default never overwrites an owner's value
```

`run.py` now calls `set_run_id(rid, explicit=True)`. **The five funnel call sites are unchanged.**

Why not `if not get_run_id():` at each call site — the obvious alternative? Two reasons: it is a thing five callers can each forget (and the funnel that forgets is invisible until someone tries to attribute its rows a month later), and it would be **wrong interactively**, where a second funnel in the same menu session would silently inherit the first funnel's id. The lock is only ever set by the headless runner, so interactive behaviour is byte-for-byte unchanged — there is a test for exactly that.

**Locked whether or not the operator passed an id**, deliberately. `rid` is the run's identity either way — it names `scratch/runs/<rid>.json`. If a funnel overwrote a generated id, master and the status file would disagree and the attribution question stays unanswerable even when nobody asked for a custom id. The 25 rows a concurrent repost run stamped with `repost_finder-20260801-192825-38372` are that path working.

Also removed: `except Exception: pass` around the whole thing. The one mechanism that makes rows attributable was failing in silence — the same disease, one layer down. It now prints and logs.

## 2. Gate 2 — master could not hold a `run_id`

`FULL_COLUMNS` is 72 wide with `run_id` last; the live file was 71. `_stamp_run_id` **deliberately** refuses to widen a short row (padding corrupted 6-column callers once already, which `test_filelock.py` caught), so it returned every row untouched.

The migration was proven on an exact copy before the live file was touched:

```
71 -> 72 cols, 58,480 rows in / 58,480 out, every row exactly 72 wide
0 of 58,480 historic rows carry a run_id  <- correctly zero
```

Then run on the live file **under `filelock.file_lock(master_csv)`** — the same lock `crossdedup.append_leads` and `writer._append_master` take, so a concurrent funnel append could not interleave with the rewrite:

```
before: 71 cols, 58,481 rows      after: 72 cols, 58,481 rows
widths: {71: 58481} -> every row exactly 72
migrate's own timestamped backup: master_leads.csv.20260801_182008.bak
```

**Nothing was backfilled, and that is the correct behaviour, not a limitation.** BL-834 measured that 92.1% of master predates the ledger entirely and only 3.8% of the remainder falls inside exactly one run's window. The past is unattributable forever; inventing ids for it would be worse than the gap.

## 3. Gate 3 — the path all five lead funnels use never stamped

`crossdedup.append_leads` builds each output row with a `DictWriter` comprehension over the master header. `writer._stamp_run_id()` is wired only into writer's own `_append_master`, which these funnels do not call. Measured before the fix, on the real function against a migrated temp master:

```
append_leads -> {'appended': 1, 'merged': 0}
run_id on that row: ''
```

The fix stamps **only `genuinely_new`**. `existing` rows are historic rows being rewritten in place so a provenance tag can be merged — putting today's id on them would be backfilling, which gate 2 just established is not honest. Verified on all three cases at once:

| row | before | after |
|---|---|---|
| `old_no_id` (historic, no id) | `''` | `''` — untouched |
| `old_with_id` (historic, old id) | `'RUN-FROM-LAST-WEEK'` | `'RUN-FROM-LAST-WEEK'` — not overwritten |
| `brand_new` | `''` | `'TODAYS-RUN'` — stamped |

`tests/test_crossdedup.py` still passes, including its byte-stable no-op check: a re-add of the same person writes nothing, because a no-op has no `genuinely_new` rows to stamp.

## 5. The sweep — every caller-supplied value overwritten by a default

`scratch/bl866_sweep.py`, 124 files across `clippershq/`, `tools/`, `dashboard/`, `memebot/`.

**The scanner self-tests every run.** A scanner reporting zero because it cannot see reads as an all-clear, so it plants the exact bug plus four correct idioms (`x = x or D`, `x = int(x or 0)`, conditional assignment, read-before-replace) and asserts it catches exactly one:

```
SCANNER SELF-TEST (planted bug + 4 correct idioms): PASS   caught=['bad']
```

| shape | findings |
|---|---|
| **A. parameter rebound before it is ever read** | **0** — no function in the tree discards a parameter unconditionally |
| **B. shared-state setter called from more than one file** | **exactly 1: `set_run_id`** — the bug this round fixed, and nothing else |
| **C. parameter accepted and never read** | 81 raw → **34 module-level** after excluding nested callbacks and fixtures, which legitimately ignore arguments for interface conformance |

Shape B returning exactly one hit is the useful result: the two-layer-setter pattern that produced this bug exists in precisely one place in the codebase, and it is now correct.

**Two of the 34 shape-C findings are consequential:**

- **`clippershq/main.py:1433 _ig_prescreen_ok(followers_only)`** — the parameter is never read; the function only ever applies the follower band. Its caller `_drain_source(ig_prescreen_followers_only)` at `main.py:1938` does not read its copy either. **A dead knob pair**, the same class the repo already fixed once for YouTube. Not touched here: it is a behaviour change that needs its own measurement.
- **`clippershq/run.py:187 run_headless(free_only)`** — accepted and never read. The `--free-only` assertion happens entirely in `main()` (lines 348–353) *before* the call, so the CLI is protected; a programmatic caller passing `cap=0, free_only=True` gets no assertion. Latent, not live.

The remaining 32 are cosmetic (`_view(path)`, `print_csv_inventory(state)`), listed in `scratch/bl866_sweep.json`.

1. **Seven funnels still cannot run headless** (section 4). Until then `--run-id` is provable only on `repost` and `clip_walk`.
