### The credential scan, and why its FAIL was not a stop

Both tools scan clean. Pushing 72 commits blind would have been reckless, so the **entire
unpushed diff** (63,459 lines) went through the scanner too. It **FAILED**: 81 email addresses
and 2 credential-shaped literals.

Neither is a real exposure, and both are worth stating rather than waving through:

- **The 81 emails are lead data in its correct home.** `ilenader/clipper-finder` is
  **PRIVATE**; `ilenader/clippershq-reports` is **PUBLIC**. `scan_report_for_secrets.py` is
  built for the public reports repo, where a lead's email must never appear. Applied to the
  private product repo whose entire purpose is storing those addresses, a FAIL is a
  calibration mismatch, not a finding.
- **The 2 "credential-shaped literals" are a Python class name** — a `unittest.TestCase`
  subclass in `tests/test_governance_rules.py` named `HookChainAbsorbedFrom` + a round id
  ending `018`. Long CamelCase plus digits satisfies the letter-and-digit-and-entropy rule
  (MEMEBOT-056's structural test). A false positive.

**Recorded because a scanner FAIL that gets overridden should never be a silent decision.**

> **And the gate proved itself on this very report.** The first attempt to publish BL-974 was
> **REFUSED** — because the report quoted that class name verbatim, so the scanner flagged it
> exactly as it had in the diff. The name is spelled apart above for that reason. A guard that
> refuses its own author's report, for the same reason it refused the thing being described,
> is a guard that is genuinely running rather than being described. It also confirms the
> finding: the detector fires on a long CamelCase identifier containing digits, which is what
> a false positive here looks like.

## 2. Item 2 — the exemption had no expiry

`tests/test_tools_tracked.py` splits untracked files under `tools/` into *orphans* (no live
claim → red) and *in-flight* (a live claim → allowed). That split is correct and BL-929 added
it for a good reason: as first written the test went red the moment anyone started writing a
new tool, and a suite that is red whenever somebody is mid-write trains people to ignore it.

**It worked exactly as designed here.** BL-966 claimed both tools, so while they were
untracked they read as in-flight, and the test stayed green. That is not a bug — the round
really was working on them, and it really did commit them.

**The hole is that the exemption never expires.** Measured live claim ages in this tree:

| | |
|---|---|
| twelve rounds | ≤ **2.4 h** |
| **MEMEBOT-039** | **18.6 h** |
| **BL-899** | **17.6 h** |

Cleanly bimodal, with a wide gap. A round that has held an untracked tool for eighteen hours
is not "working on it" — the file is orphaned, and the claim was making it *look owned*, which
is worse than plainly unowned because it reads as covered.

`docs/PRECONDITIONS.md` §12 already has the general form: *a deferral needs an expiry, not a
sentence in a report.* **An unbounded exemption is a deferral.**

**`STALE_CLAIM_MINUTES = 480`** (8 h), chosen from that distribution: 3.3× the longest
genuinely active round, far below the two abandoned ones. Deliberately generous, because a
guard that reds a legitimately long round is one people disable — the same reasoning that
created the exemption. A claim with no usable `started_epoch` counts as **stale, not fresh**:
*"I could not tell how old it is"* must not be reported as *"it is new"* (BL-908).

### Four new tests, planting the violation both ways

| test | asserts |
|---|---|
| `test_a_FRESH_claim_still_shelters_an_untracked_tool` | the exemption **keeps working** — BL-929's fix is not undone |
| `test_a_STALE_claim_does_NOT_shelter_it` | same file, same claim, older clock → **reported, naming the round that was hiding it** |
| `test_a_claim_with_no_timestamp_is_treated_as_stale` | unknown age fails closed |
| `test_releasing_a_claim_with_untracked_declared_paths_is_REFUSED` | the **other end** of the same hole |

The last one pins what the brief correctly identified as already fixed: `claim.py end` refuses
to release while declared paths are dirty, `--untracked-files=all`, so the *released* case
cannot leave an orphan. The two ends now both have tests — release-time refusal, and the
never-released case a release-time check can never reach.

**`commit_guard.py`, `commit.py` and both githooks joined the HEAD-pinned name list.** A
tracked guard reached by an untracked hook is still an untracked mechanism.

## 3. Item 3 — every tool stands alone at HEAD

`git status` compares the **worktree** to HEAD. It can say a file is untracked; it can never
say whether the tracked set is *sufficient*, because every import here is satisfied by
whatever happens to be on disk. That is precisely how five tools were found untracked while
working perfectly — nothing anybody ran was reading from HEAD.

`scratch/bl974_extract.py` extracts HEAD with `git archive` into a clean tree and, per tool,
**imports it and then runs it**:

```
HEAD carries 16 python tool(s) under tools/
EVERY TOOL AT HEAD IMPORTS AND RUNS FROM A CLEAN EXTRACT
  tools/commit_guard.py      PRESENT AT HEAD
  tools/commit.py            PRESENT AT HEAD
```

Import alone is not proof — several of these shell out to a sibling on the first real call, so
both are checked and reported separately. `tools/refresh_mx.py` is import-only (no safe
read-only invocation) and **says so** rather than being counted as verified.

### A live exposure this found, and it is not mine

**The worktree's `tools/claim.py` imports `repo_paths` at line 57. `tools/repo_paths.py` is
NOT at HEAD.** HEAD is currently coherent — HEAD's `claim.py` has no such import — so the
extract passes. But BL-973 holds both files and is mid-edit, and **if `claim.py` is committed
while `repo_paths.py` stays untracked, every clean clone breaks on the claim registry.**

The existing `test_every_committed_tool_imports_from_a_HEAD_extract` would catch it. Flagged
for BL-973 rather than touched.

## 4. Item 4 — the allow-path lesson

`docs/TESTING.md` was held by MEMEBOT-075 for this round's whole duration, so the lesson is in
**`docs/GUARD_TESTS.md`**, with §4 paste-ready as rule 12.

> A guard test that only plants violations proves nothing. `_ok_lines` is called **only when
> the guard is about to ALLOW**, so a refuse-only suite stayed green through the entire
> outage. The mirror image is MEMEBOT-065's hook that refused *everything* and was passed by
> a harness that only planted violations. One failure is invisible from the allow side, the
> other from the refuse side.

It also records the harness trap (`PYTHONPATH` cannot shadow a module the test itself
`sys.path.insert(0,…)`s) and — item 5 — that **the fail-open is deliberate and must not be
"fixed"**: it already fails *closed* on blindness, and a guard that can brick a ten-round tree
gets disabled within the hour.
