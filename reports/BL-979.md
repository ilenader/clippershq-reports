## 1. The premise, corrected before any money was spent

BL-968 reported *"~0 clips/day, the library is already walked out"* and *"166 walked"*. The
measured state at the start of this round:

```
confirmed MEME_PAGE rows in master : 239
... already present in clip_library : 172
... NEVER WALKED                    :  67      <- all 67 carry a user_pk
date_added of those 67              : 2026-07-31 .. 2026-08-01
```

At ~12.1 clips/page that is **~810 clips obtainable with zero discovery spend**.

**Why nobody had taken them.** `clip_runner.confirmed_accounts` returns master order and the
walk is round-robin from the top. The 67 were confirmed most recently, so they are the *last*
rows in the file — and a run with a dollar cap halts partway through the first pass. Every
capped walk had been spending its cap re-opening the 172 already-walked pages and stopping
before it reached a single new one. The supply was not missing; it was **behind the cap**.

**The fix was ordering, not code.** `scratch/bl979_walk.py` calls the shipped
`run.run_headless("clip_walk", …)` and patches exactly one thing — the ORDER of the list
`confirmed_accounts` returns, unwalked first. The IgClient, the kill-safe incremental meter,
the seen-cache, round-robin, `clip_max_pages_per_account` and the **locked
`clip_library.merge_append`** are all shipped code, untouched (brief item 6).

## 5. Stage D — labelling

Run through `scratch/bl867_deep_label.py` with `BL867_MIN_DEPTH=1`. **Its default is 3,
leaving depth 1–2 to a "ranked runner" that is retired** (`bl849_label.py.retired`), so the
shallow pool — 588 of the 659 unlabelled clips — had no live driver at all. I used that
driver rather than writing one because it already carries per-clip append (kill-safe),
`clip_vision.record_failure`, and `flush_spend` with a campaign label; a new labeller would
have put the metering at risk, and unmetered spend is the one failure this repo cannot absorb.

```
DONE n=226  parsed=209  declined=208  FABRICATED=1  model_spent=$0.3089
```

- **Parse rate 209/226 = 92.5%** — matching the brief's 93% figure.
- **`declined=208` is the CONTROL PASSING, not a failure.** The prompt asks for `posted_date`,
  which cannot be known from pixels; 208 of 209 correctly answered null. **One fabrication in
  209.** I misread this counter as a failure mid-run and corrected it before acting on it.
- Cost: **$1.48 per 1,000 model-only**, **$2.96 per 1,000 all-in** with retrieval.

## 7. What I got wrong

1. **I read `declined=208` as a failure.** It is the fabrication control passing. Caught before
   it changed any decision.
2. **I attributed 344 HTTP 502s to Instagram.** They were OpenRouter's vision endpoint. The
   final summary said so plainly; my mid-run narration did not.
3. **My first supply script reported 100% of clips matched a song.** `song_library.match`
   *never returns None* — its own docstring says "tier 4 always answers" — so `if match(...)`
   is true for every clip. The real test is `tier != 'PARK'`, which gave 14.3%. This is the
   proxy failure in `PRECONDITIONS.md` §10 exactly: I measured "the call returned something"
   and concluded "a song was found". Fixed before it reached the report.
4. **I deviated from the brief's stated order**, walking before discovering. Stated up front
   in the claim with the measurement behind it; discovery still ran.
