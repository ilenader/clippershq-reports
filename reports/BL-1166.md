## 1. Never the same playlist twice

`spotify_playlists_seen.json` records a playlist when it has been **walked** — never when it
has merely been found, because recording intent as completion is how a resume silently skips
work nobody did.

**The locking is written out in full because `clip_seen.json`'s history is its
specification: an unlocked read-modify-write there lost 12 of 13 records.** Two rules follow,
and only the first is widely known:

1. **The lock spans the READ *and* the WRITE.** Locking only the write is the same bug with a
   smaller window — two processes read `{a}`, each adds one, each writes a two-element set,
   and one addition is gone.
2. **`os.replace` makes ONE write atomic and cannot order a PAIR of them.** Atomicity means a
   reader never sees half a file. It says nothing about which of two concurrent writers lands
   last. Atomic writes are what make the *locked* write safe to read — not a substitute for
   the lock.

Pinned by `tests/test_playlist_harvest.py`, including **12 concurrent writers leaving 12
records**. Proven live: the second harvest **skipped all 300 already-walked playlists**,
saving **520 s** at the measured 1.45 s/playlist. The seen-set now holds **750**.

## 4. The wedge — capped, and it still earns its place

`bio_parser._EMAIL_CANDIDATE_RE` was quadratic. **BL-1165 fixed that regex while this round
was running** (commit `04852a8`, possessive quantifiers + a lookbehind), and their fix works:
measured at **0.002 s for 32,000 chars**.

**It is not the whole wedge.** `bio_parser._EMAIL_RE` — `[A-Za-z0-9._%+\-]+@...`, a greedy
run followed by a *required* `@` — sits in the same function, was not part of that fix, and
is still quadratic. Measured **after** BL-1165 landed, on `'a.b-c'` repeated:

| regex | 16,000 | 32,000 | ratio |
|---|---|---|---|
| `_EMAIL_CANDIDATE_RE` (BL-1165 fixed) | 0.0000 s | **0.0020 s** | linear |
| `_EMAIL_RE` (**not** fixed) | 0.6058 s | **1.9498 s** | **3.2x — quadratic** |

`enrich_links` has its own copy of that same pattern, which it runs over the **full raw
markup**. So this round caps the input instead, in the caller:

`_defuse_long_runs` breaks unbroken runs of email-legal characters longer than 128 chars into
64-char pieces, before every email pass. A real address is far shorter than 128 characters; a
500-character unbroken run is a base64 blob or a hash and never was one.

The arithmetic behind those two constants: after splitting, cost is `(L / 64)` segments each
costing `k·64²`, i.e. **linear in page length** and proportional to the split width. That is
why 64 and not 256.

| `extract_from_html`, 250,000 chars (= `MAX_PARSE_CHARS`) | |
|---|---|
| defuse **off** (post-BL-1165) | **183.6 s** |
| defuse **on** | **0.077 s** |
| | **2,375x** |

**Extraction is unchanged** — nine control shapes (plain, mailto, `(at)`/`(dot)`, bracketed,
JSON blob, alt-text, multi-address, socials, long-run-plus-address) produce byte-identical
results with the defuse on and off.

## What I got wrong

1. **My first pathological input had a space in it** (`"a.b-c "`), which caps the unbroken run
   at six characters and reported **0.020 s at 32,000 chars — no problem at all**. Whitespace
   terminates the candidate; the real input has runs thousands of characters long. That result
   would have closed this round with a clean bill of health on a live defect.
2. **My first defuse only covered the visible-text pass** and took 250,000 chars from ~3,856 s
   to 93.9 s. The remaining 93.9 s was `_EMAIL_RE` on the **raw** markup — a second quadratic
   path I had not looked at. Defusing once, for every email pass, took it to 0.80 s.
3. **My realistic control found 0 emails at every size** because I used `example.com`, which
   `valid_email` rejects. A probe whose control finds nothing is not measuring what it claims.
4. **I read `artist_mbid`; the API returns `artist_mbids`.** Every window reported 0 with-MBID
   and the projection produced 0 artists for feeds of up to 7,309 releases.
5. **My source split used `startswith("playlist")`**, which also matches the seeds' own
   `playlist:<id>` tag — so it filed all 914 seed artists as harvest and reported "seeds: 1
   checked". An exact match fixed it.
6. **The first harvest recorded per-playlist counts and threw the artist ids away.** The
   10,976-artist union could be described but not *used*; the run had nothing to consume.
7. **A bare `os.replace` in my own new module** was caught by `tests/test_atomic_io.py`,
   correctly — "atomic_io could not be imported" is not a reason to reintroduce the failure it
   exists to prevent.

## Still broken — and whose

**1. `bio_parser._EMAIL_RE` is still quadratic — BL-1165's, and they are the right owner.**
Their `_EMAIL_CANDIDATE_RE` fix is measured and good; the sibling pattern in the same function
was not part of it, and `enrich_links` keeps its own copy of the same shape. The fix is
presumably the same one that worked next door: a `(?<![A-Za-z0-9._%+\-])` lookbehind so a
match cannot *start* mid-run. Evidence: `scratch/bl1166_wedge_after1165.json`. My defuse caps
the input and holds either way, so nothing is blocked on it.

**2. Related-expansion cannot be separated from the seeds in the run record.** Expansion
artists carry no distinct `source`, so the 2,365-artist bucket above is
seeds + ListenBrainz + expansion together. The per-hop already-known curve the brief asked
for is therefore *not* delivered at hop resolution — only the aggregate. Tagging expansion
refs with their hop depth is a small change in `spotify_finder._maybe_expand`; I did not make
it because the run was already in flight against that code.

**3. `claim.py start --force` REPLACES `will_write` rather than merging.** Five incremental
re-claims each silently dropped every path named before them, so my claim listed 5 files when
it should have listed 30, and `tools/commit.py` correctly warned that files it was committing
had no live claim. Nothing was lost — I restored the full list — but the next round to use
`--force` for a top-up will hit it. Owner: whoever holds `tools/claim.py`.

**4. 2,546 of the 3,296 found playlists are not yet walked.** One hour of free wall clock.
