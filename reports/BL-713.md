## 1. Quiet tree, and the kill

Sole ownership confirmed before anything was written. Three Python processes existed: two unrelated `http.server` instances serving a `ryan_price` directory, and the livelocked run. No other agent script was running; the only repo files modified in the preceding 20 minutes were the recovery artefacts from the previous pass.

PID 4024 was force-killed at **18:25:37** after 3h06m, final state **CPU 8,551.3 s, RSS 2.77 MB, 26 threads** — one thread spinning at ~98% of a core since 17:11:46, everything else blocked.

**The kill forfeited the in-memory results permanently.** That was understood and instructed: Ctrl-C could not land because the main thread was starved, and the salvage below is what run.log made recoverable. Emails, artist names, listener counts and country for the ~1,708 processed artists died with the process — they were never written to disk.

## 4. The artist-ID hint was not merged, and here is the proof it should never be

Verified three independent ways:

1. The merge script hard-fails if any of `spotify_artist_id_hint`, `hint_gap_seconds`, `hint_confidence` appears in the master schema — it does not (60 columns, unchanged).
2. It hard-fails if any built row carries a key outside the master schema — none did.
3. Post-merge scan of all 483 rows for any field whose value looks like a 22-character Spotify ID: **0 rows**.

The instruction to exclude it was right, and the recovered data makes the case much more strongly than "only 306 of 495 are within 2 seconds". Mapping the 483 confirmed handles onto their hinted IDs:

| | |
|---|---|
| confirmed handles | 483 |
| **distinct artist IDs they point at** | **364** |
| IDs claimed by **more than one** handle | **62** |
| handles sitting on a contested ID | **181 = 37.5%** |
| **therefore provably wrong** (only one handle per ID can be right) | **≥ 119** |

One ID, `0bPAi2zCrxUrPBREWdetZ5`, is claimed by **eight different handles**. Four more are claimed by six or seven each. This is exactly the concurrency-6 interleaving the recovery report predicted, now quantified: the association is not merely noisy, it is demonstrably many-to-one.

## 5. Where these leads actually route — an honest correction

The request was to merge them "so they route to the DM list". **They will not appear in a `writer.dm_list_rows` export, and neither would a normal Spotify lead.**

`writer.py:992` gates the DM list on `verdict in {"EDITOR", "LIKELY"}`, and `writer.py:1000-1003` additionally requires a non-empty `instagram_url` / `tiktok_url` to have something to DM. The merged rows have neither.

This is **not** something the merge introduced. Checking the 282 pre-existing `spotify_finder` rows in master:

| | pre-existing Spotify rows | merged rows |
|---|---|---|
| verdict empty | **282 / 282 (100%)** | 483 / 483 |
| `instagram_url` populated | 14 / 282 (5%) | 0 / 483 |
| email populated | 282 / 282 (100%) | **0 / 483** |

`spotify_finder.append_found_to_master` never writes a verdict. Spotify leads have always been exported through the funnel's own `spotify_*.xlsx`, not through the IG writer's BOT_READY / DM_LIST split. The merged rows are consistent with every Spotify row already in master on that axis.

**I did not fabricate a verdict to force the routing.** These handles were resolved from artists' external links before the run died; nothing scored them as editor or creator, and writing `EDITOR` would inject 483 unvetted rows into an outreach list as though they had passed a gate. Two things are genuinely different about these rows and should be decided by the owner, not by me:

- **They are the first handle-only Spotify rows in master.** Every prior one carried an email, because the normal append path skips rows without one.
- **`instagram_url` is derivable** (`https://www.instagram.com/<handle>`, the exact convention the 14 populated rows use) and would make them DM-actionable. I did not backfill it, because on its own it would not clear the verdict gate — so it would have been an unrequested second write to master that achieved nothing for the stated goal.

## 7. The free name-resolution question — reported, not run

**Answer: don't join it. At best 262 of 483 (54.2%) are defensible candidates, and even those are unverified.**

The 1,714 artist IDs in the log can be resolved to names through the public embed endpoint at $0, and that part is reliable — the ID→name mapping is authoritative. **The broken link is handle→ID, not ID→name.**

| filter | handles | share |
|---|---|---|
| carry any artist-ID hint | 483 | 100% |
| hint gap ≤ 2.0 s | 296 | 61.3% |
| hint gap ≤ 0.5 s | 147 | 30.4% |
| **≤ 2.0 s AND ID not contested by another handle** | **262** | **54.2%** |

Even inside the tight ≤2 s subset, 34 of 296 (11.5%) sit on an ID another handle also claims. And "uncontested" only means no second handle happened to land on that ID in this log — it is not positive evidence the pairing is right. There is no way to validate a pairing from the log alone, because the artist name never appears in it.

A name attached to the wrong handle is worse than no name: it would survive into outreach and address a musician by a stranger's name.

**The worthwhile version of this, if you want it:** resolve all 1,714 IDs to names and keep them as a standalone artist list with **no handle join**. That is fully reliable, free, and still useful — it tells you which artists the run actually reached, which is the input to deciding whether the run is worth restarting from a later offset.
