## 6. The shard warning — and it fired for real

`clip_library.append()` now warns and counts (`LAST_CROSS_SHARD`) when a clip lands outside the current month's shard, with the consumer contract written into the docstring: **keep a byte offset per shard, poll every shard, drop a trailing partial line, then last-wins by (clip_id, rev).**

It is not a hypothetical. During the item-2 walk, three clips triggered it live:

```
clip 3879256091095…_… posted 1776663409 -> shard 2026-04, NOT the current shard 2026-07.
clip 3830730458430…_… posted 1770878706 -> shard 2026-02, NOT …
clip 3891290314716…_… posted 1778097994 -> shard 2026-05, NOT …
```

Three of five new clips in one small run landed outside the current month. **A consumer polling only the newest shard would have missed 60% of that run** and nothing would have looked wrong. A cross-shard write is warned, never treated as an error — back-dated discovery is normal.

## 7. `pick_rendition` — documented, not changed

Only the literal `"best"` selects the highest-bandwidth stream. `"highest"`, `"low"`, a typo or `None` all silently return the **smallest**, with no error. That is the deliberate safe direction (the old bug was a silent fallthrough to the *most expensive* stream), but a bot passing `prefer="highest"` gets the wrong rendition silently.

**Recorded here rather than in the file:** `clip_media.py` is mid-edit by another agent and I would not write into it while it is being changed. The contract lives in BL-802 §2; this is the second recording.
