### The source I did NOT read, and why

`repost_finder.append_found_to_master()` writes confirmed repost pages **into
`master_leads.csv`**. That file holds **59,016 outreach leads**, and its `lead_kind` column
is only `clipper` (56,057), `client` (2,899) and 60 blanks — **there is no kind that

cannot tell which of those are pages without reading lead rows.

`io.open` and the builtin `open` during a real export and asserts the lead file is never
among the paths opened. Grepping for the filename would have failed, because the exporter
*names* it in its own provenance string to explain the exclusion.

**The consequence, stated plainly:** if a page was confirmed but never walked, it is in
master and therefore **not in this sheet**. The 281 here are what exists outside the lead

## 2. Records, never rows — and this one is the worst yet

The eighth such check in this repo, and it is bigger than any on record:

```
clip library     9,741 rows   ->  2,761 records    3.53x   (folded here)
render ledger    1,429 lines  ->    801 records    1.78x   (via clippershq/ledger.py)
                                     455 FINISHED  -- a video actually came out
```

The library is append-only per month file, so a clip re-walked later appears again. Summing
rows would have inflated **every count in every row** by roughly three and a half times.

### The ledger count I got wrong, and the guard that caught it

My first version folded the render ledger **itself**, on a bare `render_id`, and got **770
records. The right answer is 801.** Two kinds of record live in that file and they do not
share a key — outcome lines carry `record_id` and no render key — so one fold on one field
is exactly how a 42.9x error was once produced *"while auditing for exactly this class of
error."*

`clippershq/ledger.py` exists to be the **one accessor** for that file, built after it
produced **seven** rows-versus-records errors. `tests/test_clip_pipeline.py` refuses any
unsanctioned module that so much as *names* the file — prose included — and it refused mine
**twice**: once for reading it, and again for mentioning the filename in the docstring
explaining why I no longer read it. Both times it was right.

**"Ever rendered" also changed meaning as a result.** A render record that never produced a
video is an attempt, not a render, and `ledger.is_finished()` is the shared answer. The sheet
now carries both: @moviezar has **35 attempts and 15 finished**.

### Hand-verified against source, with the arithmetic

**Total 1 — the library's record count**, re-counted by a different route: raw byte scan for
`"clip_id"` across all 55 files, never touching the exporter's loader.

```
TOTAL ROWS (sum of 55 files)  9,741
ids scanned off the bytes     9,741
DISTINCT clip_id (RECORDS)    2,761
duplicates                    9,741 - 2,761 = 6,980
over-count if rows were used  9,741 / 2,761 = 3.53x

exporter said                 rows=9,741  records=2,761      AGREE
```

**Total 2 — one account's renders**, re-counted straight off the ledger:

```
account                       @moviezar
ledger LINES naming it        66
DISTINCT render_id            35
duplicate lines               66 - 35 = 31
over-count if lines used      66 / 35 = 1.89x

spreadsheet said, attempts    35                              AGREE
spreadsheet said, FINISHED    15   <- "ever rendered" means a video came out
```

A third check falls out of the first two: the per-account render counts **sum to no more
than 801**, which is exactly the number of render records that exist. A line-based count
would have summed past it.

**0 blank cells. 1,117 cells reading `not measured`.**

Six of the columns you asked for have no source at all, and each says so on every row rather

| **clips meme-format** | **stored on 0 of 2,761 records.** `format` exists but its values are `dialogue-first` (977) and `music-first` (497) — an **audio** shape, not the meme-format judgement. Reading one as the other is precisely the substitution this sheet avoids |

The gate columns are counted only where the gate input was measured: `speech_frac` is on
1,827 records and `ocr_gate_text` on just **431**, so `clips renderable` carries a
`clips with BOTH gates measured` column beside it. An account with 119 clips and 12 measured
is not an account with 107 failures.
