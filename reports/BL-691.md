## The two findings that change decisions

### 1. `spotify_track_metadata` is empty in clip payloads — the bridge is a PAID enrichment

BL-678 saw a populated `spotify_track_id` and flagged it as a strong lead for exact-ID genre/mood joins. Measured properly, over **311 licensed clips** in the corpus:

| where | `spotify_track_id` present |
|---|---|
| **clip payload** (`music_asset_info.spotify_track_metadata`) | **0 / 311 = 0%** |
| `/v2/track/by/id` response (licensed) | present, both top-level and nested |

The key exists on all 311 clips and is **null on every single one**. It only populates in the track response.

**So the exact-ID join costs one request per track. It is not a free field riding along on data already bought.** Anything scoped on "we already have Spotify ids" needs rescoping.

**It does dedup well, which is the saving grace.** 311 licensed clips carry only **63 distinct** track ids — **4.9×**. The bridge is priced per *track*, not per clip.

For context on what the exact id buys: of those 311 licensed titles, **27 (8.7%)** carry a qualifier that breaks naive string matching —

```
Where Is My Mind? (2007 Remaster)     Sadka (From "I Hate Luv Storys")
Headlights (feat. KIDDO)              Sweater Weather (Slowed Down)
Like a Prayer (Choir Version From "Deadpool & Wolverine")
Let Her Go (Anniversary Edition) (feat. Ed Sheeran)
```

⚠️ **That 8.7% is not comparable to the "53% wrong" figure quoted elsewhere, and does not refute it.** This measures *title-string ambiguity* — how many titles contain a qualifier. That figure measures *match failure against a catalogue*. Different quantities. Both can be true.

### 2. The router mix is unstable across corpora — never hard-code coverage

The `audio_type` router (skip the speech model on non-original audio) was costed at "about a third of clips". Measured twice, on two snapshots of the same growing corpus:

| corpus snapshot | licensed share |
|---|---|
| 229 clips | **16.2%** |
| 642 clips | **48.4%** |

A 3× swing, because other workstreams saved payloads from different surfaces (hashtag feeds vs per-account clips). Neither number is wrong; **the quantity itself is a property of the source, not of Instagram.**

**Any capacity plan that hard-codes router coverage is planning against a number that moves.** Measure it per source, per run.

Original sounds are per-reel and barely dedup at all — **and they are also the ones with no title**, so they are simultaneously the most expensive to count and the least informative to name. Budget ~1 call per original-sound clip.

## What shipped

### The routing chokepoint (`clippershq/track_id.py`)

Two ids exist on every licensed reel and they are **not interchangeable**:

```
licensed_music   ->  clips_metadata.music_info.music_asset_info.audio_cluster_id
original_sounds  ->  clips_metadata.audio_ranking_info.best_audio_cluster_id
```

BL-678 measured the consequence live on one reel, both ids resolved:

| id used | resolves to | clips_count |
|---|---|---|
| `best_audio_cluster_id` | the reel's **own** audio | **5,584** |
| asset `audio_cluster_id` | the licensed track | **837,493** |

**A 150× understatement from a call that succeeds**, returning a plausible integer with no error of any kind. `best_audio_cluster_id` is populated on 100% of clips *precisely because it is not a track identifier* — it is the reel's own audio cluster, which always exists. A field that is never missing was evidence of the wrong question, not of good coverage.

That failure is invisible at the call site, so the call site no longer gets to make the choice:

- `resolve_track_id(clip)` is the **only** supplier of a `TrackRef`
- `TrackRef.__init__` rejects external construction (private token)
- the response reader accepts **only** a `TrackRef` — passing a raw id raises
- there is deliberately **no** `fetch(track_id)` overload to reach for under deadline
- a licensed clip missing its asset id returns `None → UNKNOWN` and **does not fall back** to `best_audio_cluster_id` — that fallback *is* the bug

### The consistency guard: wrong-key is an ERROR, missing is UNKNOWN

On licensed clips the two ids **disagreeing is expected and fine** — BL-678 measured 7 of 20. What is not fine is a count fetched under the wrong key.

The reader cross-checks the response's populated metadata branch against the ref's kind and raises `WrongKeyError` when they contradict, in both directions. Missing data still degrades quietly to UNKNOWN. A wrong-key count is loud, because it is a plausible wrong number rather than an absent one.

### The dead-id sentinel

Established in BL-681 and implemented here: **a dead audio id does not 404.** It returns HTTP 200, `status: "ok"`, `status_code: 200`, with `clips_count: 0` and every metadata branch null — **and it still bills one request**.

- **The negative cache keys on empty metadata** (`music_info == null AND original_sound_info == null`), **never on HTTP status.** A 404-keyed cache would never fire and would re-bill every dead id forever.
- It reuses `resolve_cache` under platform `igaudio`, outcome `audio_dead`, inheriting the existing cross-process lock and merge-on-save. A test asserts the namespaces cannot bleed into handle-resolve outcomes.
- **`clips_count == 0` is a sentinel, not a value.** A zero only passes through once metadata is proven present. Zero + empty metadata is DEAD → UNKNOWN. There is no error to catch here, which is exactly why it needs an explicit rule: the API asserts "nobody uses this sound" in a well-formed successful response, and a naive reader stores that with full confidence.
- A test feeds `"ok"`, `404` and `None` through the same dead body to prove status is never consulted.

### Never-parse

```
response.formatted_media_count
response.metadata.*.formatted_clips_media_count
```

**Two** display strings per response, both localised, both lossy even in English: `"5.5K reels"` for 5,584; `"837K reels"` for 837,493. A documented sample returns Russian with space separators. If the integer is absent the answer is UNKNOWN — never a parsed string. Enforced by `track_id.NEVER_PARSE` and a regression test that plants a formatted string next to a missing integer and asserts UNKNOWN.

### Schema note

`scratch/track_endpoint_schema.md` — a **new** file. The endpoint is a **reels-by-audio feed**, not a scalar lookup: one call returns 12 full media objects with `play_count` and engagement, plus `paging_info.max_id` / `more_available`, `is_trending_in_clips`, the full `music_asset_info`, and `spotify_track_metadata`. Treating it as a count-lookup discards most of what the call already paid for.

`scratch/clip_library_schema.md` is owned by another workstream and was **not touched** (last write 13:28, before this round).

The tripwire worked exactly as designed. It caught four ledger rows that were not mine — `probe:soundlib` (20 calls), `probe:soundlib2` (20), `probe:soundlib_retest` (2), `probe:bl684_energy_step` (9): **51 calls, $0.0306**, ledger `2.8786 → 2.9098`.

**Those were authorized budgets** — $0.03 for the sound-library probe and $0.05 for the energy-step validation. **No instruction was broken.** The detection was correct; the premise it was handed was wrong, and this note exists so the earlier flag does not stand unqualified on a public record.

Worth keeping: the agents metered their spend properly, so the money was visible in the shared ledger rather than hidden. That is the system working.
