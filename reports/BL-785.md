## 1. Re-paying for the same lead — **REFUTED, and it was my error**

BL-754 reported that of 125 Spotify artists re-processed across two runs, **"102 hit the PAID resolve again"**. That is wrong, and the correction is exact.

**The reconciliation closes to zero:**

| | |
|---|---|
| leads with a handle on the 30 Jul run | **811** |
| handles already in the cache *before* that run started | **107** |
| predicted paid calls (811 − 107) | **704** |
| **actual paid calls (`spend.json`)** | **704** |
| **difference** | **0** |

The negative cache did exactly what it was built to do. All 103 repeat artists were present with `outcome: no_email` and timestamps of **24, 25 and 27 July** — written *before* the 30 July run — and every one was skipped at $0.

**How I got it wrong:** I inferred "hit the paid resolve" from the sheet's `Status` column. A lead reads `handle only` whether it was paid-resolved and yielded nothing **or** was skipped for free by the cache. The output cannot distinguish those two, and I read the ambiguous signal as the expensive one. The stat that *does* distinguish them — `resolved_skipped` — exists in the funnel and is not persisted anywhere, which is why the sheet was the only evidence available.

**The re-work finding in BL-754 still stands**: the same artists genuinely were re-discovered and re-processed, and 124 of 125 produced an identical answer. That is wasted *time*. It is not wasted *money*, because discovery is free.

### What the sweep did find

**`repost_finder` has no reject cache.** `crawl_suggested` caches profiled-and-cut accounts (`resolve_cache.mark(..., "rejected", allowed=("rejected",))`) so they are never re-paid inside the window. `repost_finder` pays `client.user_medias` per candidate (`repost_finder.py:627`) and caches nothing. It dedups against master first — correct, and it saves money on accounts that *became* leads — but an account that was paid for and then **rejected** (`non_english`, `thin_accounts`, `gated_out`) is invisible to master and is re-paid on every subsequent run. 7 runs, 201 calls, $0.1206 to date.

**A stranded cache from the CWD foot-gun.** `resolve_cache.cache_path()` returns a bare, unanchored relative filename, resolved against the current working directory — **the identical bug that was fixed for `spend.json`** in commit `39528d1` (`main.repo_path()`), never applied here. The evidence is on disk:

```
<repo root>/resolve_cache.json     145,078 b   1,870 entries
clippershq/resolve_cache.json        6,149 b      80 entries   <- stranded
```

**All 80 stranded keys are absent from the root cache** (53 `no_email`, 27 `email`). They were paid for and are invisible to every run launched from the repo root. Re-earning them costs **$0.048**. The ongoing risk is larger than the one-off: any future run launched from `clippershq/` reads a near-empty cache and re-pays for everything.

## 5. Retries and error billing — **one structural leak**

The metering is honest: billed requests are counted at the HTTP layer, not per logical call, *"so a 429/5xx retry storm isn't under-metered"* (`ig_client.py:106`). And the retry policy is correctly scoped — only `_RetryableHTTP` (429/5xx, free per BL-678) retries; **404, 400, 410 and 422 return `None` immediately with no retry** (`ig_client.py:356-362`). A billable 404 is billed once, not `max_retries` times.

**The leak is the fallback, not the retry.** `hashtag_medias_clips()` falls back to `/top` when the clips surface 404s — *"#theboys 404s on it while working fine on /top"* — and **that fact is never remembered.** There is no `_clips_dead` set, no persisted memo, nothing keyed on the tag. So for every tag whose clips surface is dead, **every page of every run pays for the 404 and then pays again for `/top`** — a permanent doubling on those tags.

**Magnitude unknown.** `logs/run.log*` retains ~6 days and contains no `hashtag/medias` traffic, so I could not measure the 404 rate. The defect is visible in the code; the cost is not measurable from what survives.

**Endpoints that bill on failure** (BL-678, carried): a 404 bills; only 5xx are free; a dead track id returns **HTTP 200 with `clips_count: 0`** and still bills — that last one cannot be detected by status code at all.

## 7. Time

**Spotify's MusicBrainz phase is the single largest sink and is mostly irreducible.** On the 30 July run: **599.7 seconds of pure waiting** across 264 rate-limit waits, plus 110 HTTP 503 retries across 113 artists and 8 timeouts. The limiter is a global 1 req/sec courtesy limit — `control.py:2200-2208` records that raising concurrency from 3 to 6 bought 1.02×, because no amount of concurrency widens it.

The recoverable part is small and specific: **7 artists gave up entirely** after retries and were logged as *"country unknown for a reason we caused"*. A longer per-artist budget recovers those seven; nothing recovers the 599.7 seconds.

**Twitch ends on the clock, not on supply.** `DEFAULT_MAX_RUN_SECONDS = 900` and `MAX_SECONDS_PER_CHANNEL = 30`. A run can terminate having touched a fraction of its pool, which reads as "supply exhausted" in the summary when it was a deadline.

**repost/IG is OCR-bound** at 31.9 s/candidate (BL-732). BL-736 measured that the 640px downscale is decision-neutral, so the OCR cost is already near its floor for the classifier's purposes.

## Limits

- **The headline correction is the most reliable thing here.** 811 − 107 = 704 against a recorded 704 is an exact reconciliation from three independent artifacts (sheet, cache, ledger).
- **Both recurring leaks are unquantified.** The repost reject-cache gap and the clips→top double-bill are visible in code and neither can be sized: the repost runs did not persist per-account outcomes, and the logs rotated before any `hashtag/medias` traffic survived. **I am ranking them first on shape, not on measured dollars** — that ordering could be wrong if their real frequency is low.
- **The BL-678 billing facts are carried, not re-verified.** Re-testing them would require paid calls, which this brief excludes.
- **I read execution order statically.** A gate could be skipped at runtime by a config flag in a way the source order does not reveal.
- **Item 3 is a negative result over the paths I checked** (repost, Spotify, the two BL-748/749 cases). I did not exhaustively diff every free response against every subsequent paid request.
- **Time figures come from one Spotify run and one repost measurement.** No funnel instruments wall-clock, so there is no second sample to compare against — the gap BL-754 §5 specified and BL-773 re-flagged.
