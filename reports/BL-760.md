## The finding that changes how these fields should be used

Item 5 said *"save_count at 66.7% is the one to watch — if that is account-specific rather than
general, the ratio is less useful than it looks."* **It is account-specific, and it is worse
than 66.7%.**

Live run, 4 accounts never sampled before, 48 clips:

| field | 3 original accts (36) | **4 NEW accts (48)** | pooled (84) |
|---|---|---|---|
| `like_count` | 100.0% | **100.0%** | **100.0%** |
| `comment_count` | 100.0% | **100.0%** | **100.0%** |
| **`save_count`** | 66.7% | **0.0%** | **28.6%** |
| **`reshare_count`** | 88.9% | **54.2%** | **69.0%** |
| `follower_count` | 100.0% | **100.0%** | **100.0%** |

**`save_count` is null on all 48 clips across all four new accounts** — 0/12 on each,
individually. It is not a field that is sometimes missing; it is a field that some accounts
report and others never do.

**Verdict on the ratios:**

- `engagement_per_follower` — **reliable.** Its inputs (likes, comments, followers) are 100%
  across all 7 accounts and 84 clips. This is the ratio to build on.
- `reshares_per_view` — **usable but patchy**, 69% pooled and swinging 54–89% by account.
- `saves_per_view` — **do not depend on it.** 28.6% pooled, and absent entirely on 4 of 7
  accounts. The brief called a save "stronger intent than a like", which is true — but it is
  reported too rarely to rank on, and its absence is not random.

Had this landed as `0` instead of `None`, every one of those 48 clips would have read
"saves-per-view = 0.0" — a confident, wrong, unfalsifiable signal on four whole accounts.

## What was built

`clippershq/clip_library.py` only. Six fields captured, three ratios derived, both traps
documented in code.

**Capture** — six `put()` calls in `build_record`, all `DECLARED` (they are the platform's own
counts): `like_count`, `comment_count`, `save_count`, `reshare_count`, `follower_count`, with
`play_count` kept as-is.

**Missing stays None, never 0.** `put()` marks a `None` as `ABSENT`, so `field()` returns
`None` rather than a value. Verified against real payloads:

```
save_count      non-null 24 / None 12 / zeros 0      (matches the 66.7% measured)
reshare_count   non-null 32 / None  4 / zeros 0      (matches the 88.9% measured)
comment_count   non-null 36 / None  0 / zeros 3      <- REAL zeros, correctly kept
FABRICATED ZEROS: 0
```

That `comment_count` line is the proof the guard is discriminating rather than blanket: three
clips genuinely had zero comments and kept the 0, while twelve clips with no reported
`save_count` got `None`.

**Ratios, None-safe by construction.** A helper returns `None` whenever either side is missing
or the denominator is not positive:

```python
def _ratio(numerator, denominator):
    """A rate, or None. NEVER 0 as a stand-in for 'not reported'."""
```

`saves_per_view` is `None` on exactly the 12 clips where `save_count` is, and on all 48 new-
account clips. `engagement_per_follower` sums likes + comments, and adds saves/reshares **only
when reported**, so a missing optional term never deflates the numerator.

**Both traps documented in code**, as a block above `CLIP_FIELDS`:

- **`view_count` is a decoy — do not wire it.** Now confirmed a fourth time, on live data:
  **present on 48/48 new-account clips, non-null on zero of them**, while `play_count` carried
  the number on all 48. The comment records that the same shape exists at TikTok's
  `cha_list[].view_count`.
- **`follower_count` is gql-only** — 100% on `/gql/user/clips`, absent entirely from
  `/v2/user/clips`. The comment states explicitly that if the walk ever falls back to REST (the
  deprecation-safe path per BL-682) the denominator vanishes, and that this is why the ratio
  returns `None` rather than degrading to a raw count.

Sample record from a real clip:

```
play_count 21,579,646   like_count 182,077   comment_count 1,319
save_count 34,291       reshare_count 508,480   follower_count 52,414
saves_per_view 0.001589   reshares_per_view 0.023563   engagement_per_follower 13.854447
```

## Limits

- **7 accounts, 84 clips.** The `save_count` split is stark (66.7% vs 0.0%) but the sample is
  three accounts versus four. What drives it — account settings, region, account age — is not
  established, only that it is not random.
- **`reshare_count` at 54.2% vs 88.9%** is a wide swing on small n; the pooled 69% should be
  treated as provisional.
- The live run used **one page per account** (12 clips). Fill rates on deeper pages are
  unmeasured.
- Nothing consumes these fields yet. The walk yields the media dict and `build_record` now
  records the panel, but no ranking or selection reads the ratios — that is the next piece.
- `master_leads.csv` was backed up but **not written**; the library is JSONL and separate.

## Method

Edits confined to `clippershq/clip_library.py`. Offline verification rebuilt records from all
three saved gql payloads (36 clips) through the walk's own `iter_stream_medias` and
`clip_library.mget`, using a sentinel to separate a missing key from a key present with value
`None`. The live run made **4 paid calls ($0.0024)** against `/gql/user/clips` for four accounts
drawn from master's `repost_finder` rows, hard-capped at 6 calls, and metered real spend via
`record_aux_spend`. Backups were taken before the first paid call. No credential was read,
printed or logged.
