# BL-1153 — The OCR engine was never installed, and the deletion risk was the smaller half of it

**One sentence:** The engine that reads text off every frame was a 264 MB directory in
`scratch/` that the sweeper had already marked `REMOVE` — and the worse problem was not that
it might vanish, but that it carried its **own** cv2, numpy, onnxruntime, PIL and yaml and
put them ahead of site-packages at the first OCR call, so which OpenCV a process ran
depended on whether OCR happened before or after the first `import cv2`.

**Spend: $0.0000 of a $0.10 cap.** Local CPU only; no vendor call was made.

**`config.json`: 162 keys, 5 campaigns.**

---

## 1. What is installed, under every name

The brief was right to insist on this. **Every one of ten spellings returned `None`:**

```
rapidocr_onnxruntime   rapidocr-onnxruntime   rapidocronnxruntime   RapidOCR-onnxruntime
rapidocr               RapidOCR               rapid_ocr             rapid-ocr
rapidocr_openvino      rapidocr-paddle                              -- all None
```

**And not one of them was the wrong name.** The engine was not installed *at all*. The
lookup that settles it without guessing a spelling is

```python
importlib.metadata.packages_distributions()["rapidocr_onnxruntime"]   # -> nothing
```

which maps the **import** name to whatever provides it. That is now the check
`tests/test_ocr_engine.py` runs, and it is the one to reach for next time this question comes
up. The `spotifyscraper` mistake was a *lookup* mistake; this one would have been read as the
same thing and was not.

| | |
|---|---|
| import name | `rapidocr_onnxruntime` |
| pip name | `rapidocr-onnxruntime` — **both correct, for different tools** |
| version | 1.4.4 |
| was at | `scratch/bl1061_pkgs` — 264.0 MB, 3,133 files, **untracked, unclaimed** |
| now at | `…\Python311\Lib\site-packages\rapidocr_onnxruntime\` — 14.9 MB |
| models | 3 ONNX files, **16.2 MB**, inside the wheel — nothing downloads at run time |
| engine build | 2.4 s, once per process |

So of the 264 MB, **the engine and its models are 16.4 MB.** The other 248 MB was copies of
packages this machine already had.

## 2. The ABI question, answered by measuring rather than reasoning

The vendored tree shadowed **five** packages, cv2 across a **major** version:

| import | site-packages | vendored copy |
|---|---|---|
| `cv2` | 4.10.0 | **5.0.0** |
| `onnxruntime` | 1.22.1 | 1.28.0 |
| `numpy` | 2.3.2 | 2.4.6 |
| `PIL` | 12.2.0 | 12.3.0 |
| `yaml` | 6.0.2 | 6.0.3 |

`sys.path.insert(0, PKGS_DIR)` ran **lazily, inside `reader()`**, so the winner depended on
import order. Two real processes, one machine, one code base:

```
import cv2, then OCR   ->  cv2 4.10.0   numpy 2.3.2
OCR, then import cv2   ->  cv2 5.0.0    numpy 2.4.6
```

An AST sweep of `clippershq/`, `dashboard/` and `tools/` found **zero** module-level imports
of cv2/numpy/PIL — **all 18 are inside functions.** The second ordering was not the exotic
case. It was the normal one.

### The intent was the exact opposite of the effect

The comment above that line read: *"RapidOCR is installed with `pip --target` rather than
into site-packages, so the live numpy stays at 2.3.2 and the ABI guard has nothing to
refuse."*

The guard had nothing to refuse **because `pip --target` routes around the guard**. The
mechanism chosen to keep numpy safe was itself performing a numpy substitution — invisibly,
at run time, in the one place `pipguard` cannot look. This is the shape worth remembering: *a
guard that is satisfied because the risky thing moved outside its field of view is not a
guard that passed.*

### Can it be pinned? Yes, and it costs one package

Every requirement was **already satisfied** — `numpy<3.0.0,>=1.19.5` (2.3.2),
`onnxruntime>=1.7.0` (1.22.1), `opencv-python>=4.5.1.48` (4.10.0), `Shapely!=2.0.4,>=1.7.1`
(2.1.2), plus pyclipper, PyYAML, Pillow, six, tqdm. `--no-deps` installs **exactly one**
14.9 MB package and moves nothing.

## 3. A defect I introduced, in the act of checking for defects

**I ran `pipguard install` believing it was a dry run. It dry-runs and then installs if the
resolution is clean** — that is its documented contract and I read the first half of it. It
installed into the `.venv`, and without `--no-deps` it did this:

```
Installing collected packages: six, Shapely, pyclipper, opencv-python, rapidocr-onnxruntime
                                                       ^^^^^^^^^^^^^ 5.0.0.93
```

pip does not know `opencv-python-headless` already provides `cv2`, so it did not *replace*
it — it **added a second distribution alongside**, both writing into one `cv2/` directory,
and `import cv2` in the venv moved **4.13.0 → 5.0.0** as a side effect of installing an OCR
engine.

**pipguard permitted this correctly.** Its rules refuse *downgrades*; this is an upgrade, and
its doc says so explicitly. But the doc also says the opencv variants "normalize onto
`opencv-python`… one replacing another is a real swap" — and pip did not swap, it **added**.
The guard ranks versions; it has no verdict for *two distributions providing one import*.
`DUPLICATE PROVIDER` would be worth having.

**One command, and it has to be you** — the dependency-guard hook blocks the agent from
uninstalling a protected package, which is the right call:

```
.venv\Scripts\python.exe -m pip uninstall -y opencv-python
.venv\Scripts\python.exe -m pip install --force-reinstall --no-deps opencv-python-headless==4.13.0.92
```

The second line is not optional: the two share files, so the uninstall takes some of
headless's with it.

**Blast radius is the `.venv` only.** The main interpreter was installed with `--no-deps` and
shows `opencv-python` absent, cv2 unmoved at 4.10.0.

## 4. Out of the sweeper's reach — proved by removing it

`reader()` now tries the **installed package first** and never touches `sys.path` on the
happy path. The vendored tree survives only as an `ImportError` fallback, and it announces
itself:

```
! OCR: using the UNINSTALLED vendored engine at …\scratch\bl1061_pkgs
!      it puts its own cv2, numpy, PIL, onnxruntime, yaml ahead of site-packages for the
!      rest of this process.
!      fix: SAFE_PIP.bat install "rapidocr-onnxruntime==1.4.4" --no-deps
```

That branch is **execution-tested**, not just written — a one-shot import blocker simulates
the half-migrated machine and the warning above is its real output.

**The proof for the GC question is not a configuration change, it is a removal.** The tree was
renamed away — which is exactly what a sweep does — and OCR kept working:

```
exists after rename: False
engine_status: source=installed version=1.4.4 shadows=none
OCR f000.png -> 1 block(s) in 3.88s
OCR f001.png -> 2 block(s) in 1.46s
OCR f002.png -> 3 block(s) in 4.34s
cv2=4.10.0 numpy=2.3.2
```

`scratch_gc`'s `REMOVE` verdict **was right the whole time.** What was wrong was that the
engine lived there. It currently reads `KEEP — live claim: BL-1153`, and when this round ends
it will return to `REMOVE`, which is now the correct outcome: **264 MB of dead weight.**

## 6. The speed claim, re-measured against a named baseline

A multiple is not a property of an engine. It is a comparison, and without its baseline it is
a rumour.

```
easyocr 1.7.2, CPU, the SAME 8 frames, the SAME process, 2026-08-05
    EasyOCR   p50 14.54 s
    RapidOCR  p50  2.32 s
    ->  6.3x
```

**Not 168x** — inherited, and it did not reproduce. **Not 57–82x** — a moment, on other
frames. The first EasyOCR frame was the **fastest** of its eight, so no warm-up outlier is
propping this up; if anything 6.3x is generous to EasyOCR.

RapidOCR is still plainly the right engine — 6.3x, and a 2.4 s build against EasyOCR's torch
stack. But **the figure this repo has been quoting is about 27x too large**, and it has been
quoted in support of decisions.

## 7. When it is missing, it says so before it spends

```
OCR ENGINE MISSING -- the render path cannot read text without it.
  import name  : rapidocr_onnxruntime
  pip name     : rapidocr-onnxruntime   (they differ -- both are correct, for different tools)
  install with : SAFE_PIP.bat install "rapidocr-onnxruntime==1.4.4" --no-deps
  why --no-deps: without it pip adds a SECOND cv2 provider (opencv-python 5.0.0.93) beside
                 the installed opencv-python-headless.
  interpreter  : C:\…\Python311\python.exe
```

`OcrEngineMissing` is a **typed** exception on purpose. `ocr_frame` swallows per-frame errors
so one bad frame cannot kill a sweep; a missing engine must not go down that path, or one
install problem is filed as *"this frame carries no text"* two thousand times — the exact
mistake `gate_text_for` returns `None` to avoid.

`paste_batch.py` checks **after `--estimate-only`** (estimating needs no engine) and **before
the first paid call** — a 60-link paste spends ~$0.04 fetching media before a frame is read.
It prints and exits 2; a traceback at an operator is not an instruction.

**Where it is not wired:** `dashboard/server.py` is held by BL-1152, so the dashboard's own
start-up does not run this check yet. The paste path — the one that renders — does.

## 10. What I got wrong

* **I ran an installer thinking it was a dry run**, and it changed the `.venv` — leaving two
  cv2 providers and moving `import cv2` a major version. The guard's name has "dry-run" in
  its output; its contract is dry-run-**then-install**. §3, with the command to undo it.
* **I wrote a nonsense expression** in the missing-engine branch —
  `raise OcrEngineMissing(require_engine.__doc__ and "" or "")` — which would have raised an
  empty message in exactly the situation the message exists for. Caught on re-reading, before
  it ran.
* **I judged the engine "broken" on audio-only files.** Six clips returned "could not look";
  the folder was `scratch/acctformat/audio/` and they have no video stream. I chased that for
  two rounds of debugging before reading the path.
* **My own test caught my doc.** The doc said "never reproduced" where the check required
  "did not reproduce" — a small thing, but the test was written to stop exactly the reflex of
  repeating an inherited multiple without its caveat, and it fired on me.
