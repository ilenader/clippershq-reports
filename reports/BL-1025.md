## 1. MEDIA — `--folder --media`, and what it costs

```
10 clips · 10 fetched · 47.5 MB · $0.0060 · $0.000600 per brief · cap $0.0200
```

Every clip re-fetched through the metered path, because the library stores **no playable
URL** — correctly: CDN URLs expire in ~105 h and the rendition ladder is unstable, so a
cached one is wrong within minutes. Durations 9.7–79.5 s, heights 1280–1936p, **10 of 10
confirmed playable.**

### The cap binds BEFORE the call

`fetch_media` refuses when `spent + worst_next > cap`, where `worst_next` is the full
`max_pages`. A cap checked afterwards is a report of an overspend, not a bound on one. The
test asserts **zero calls were made** after a refusal, and a second test asserts a fetch that
fits still goes through — a cap that refuses everything would pass the first test while being
useless.

`--media` without `--cap` **refuses to run**. There is deliberately no default.

### TWO COSTS, because they answer different questions

```
$0.000600 per brief                      what a brief costs to produce
$0.000600 per brief carrying the video   what a USABLE brief costs — failures are billed
```

They are equal here only because 10 of 10 succeeded. `MEDIA.json` records both, and the
second is printed whenever they diverge.

## 2. THE ASSIGNMENT RECORD — `clippershq/editor_assignment.py`

**ONE MECHANISM, NOT THREE.** An accepted editor cut **is** an outcome-loop record. It carries
the same `record_id`, derived by the same rule, and its metrics arrive through
`outcome_loop.append_outcome` unchanged. The module adds only what outcome_loop has no
opinion about: **who cut it**, **which brief**, and **was it taken**.

```
sent  ->  returned  ->  accepted | rejected
```

### The id does not exist until the work does

At assignment time there is no output, so there is **no `record_id`** — and minting one would
put a synthetic id in the same key space as real renders, where it can collide. So:

| state | `record_id` | joins? |
|---|---|---|
| `sent` | `""` | no — *"no output yet — the editor has not returned a cut"* |
| `returned` | derived | no — *"returned but not accepted"* |
| `rejected` | derived | no — *"rejected: `<reason>`"* |
| `accepted` | derived | **yes** |

`join_outcomes` returns `joinable` **and `why`**, because *"no numbers reported"* and *"no id
to join with"* look identical on a count and mean opposite things: one is waiting on a poster,
the other on an editor.

### The three derivations are asserted to agree

`editor_assignment.record_id_for_output`, `client_delivery.record_id_for_deliverable` and
`outcome_loop.record_id_for` are re-derived in three modules — three chances to drift, and a
drift would make `join_outcomes` return nothing while looking exactly like *"no results
yet"*. The test asserts all three on the same inputs, **including the Windows separator**,
which is the only interesting case.

### Four decisions worth naming

* **`accepted` is `None`, not `False`, until judged.** False means *we looked and said no*.
* **A rejection REQUIRES a reason.** An empty one cannot be told apart from a verdict nobody
  recorded, and it is the only field that could ever tell an editor what to do differently.
* **`accept_rate` is `None` until something is judged** — three sent and none returned is not
  a 0% rate, it is no data. A **measured** zero still renders as zero; hiding it is the mirror
  defect.
* **No money.** No rate, no invoice, no total, and a test asserts no field name contains one.
  A rate here would become a rate a real editor is owed, computed by a module nobody audited.

### A CLI defect the tests could not see

`python -m clippershq.editor_assignment join` raised `ModuleNotFoundError: outcome_loop`
**while all 36 tests passed**, because the suite puts `clippershq/` on `sys.path` and the
package import style does not. Same family as `docs/SEND_DAY.md`'s documented
`ModuleNotFoundError: dedup`. Fixed with the lazy path insert `outcome_loop` and `run.py`
already use, and pinned by a test that **spawns a real subprocess with the package import
style** — the only way to reach the path that broke. Found by running it, not by reading it.

## 5. THE TEST-PLACEMENT TRAP — pinned, and it fired

`run_all.py` runs each suite as `python <path>`, so `unittest.main()` executes **at the line it
sits on** and anything below is invisible. BL-991 lost 19 tests; BL-1012 lost 7 in this very
file. **`OK` looks identical either way — only a count sees it.**

Both files now assert it three ways, reading the FILE rather than trusting what unittest
collected (trusting the collection is precisely the mistake — a dropped test is not in it):

```
test_no_test_is_defined_below_the_entry_point
test_every_test_defined_is_a_test_collected      <- the strong one
test_the_file_still_has_at_least_the_tests_it_had
```

**It caught two real things while being written.**

1. **It fired on itself.** `src.index('if __name__ == "__main__"')` matched the literal inside
   the guard's OWN source and reported three of its own tests as dropped. `rindex` fixes it.
   *A guard that fires on itself is not evidence about the file.*
2. **`str.count("    def test_")` was inflated by exactly the number of guards counting** —
   the literal appears in each. Anchoring the pattern to line starts makes
   defined-equals-collected an **equality**, and that slack is where a dropped test hides.

Verified by planting a test below the entry point in both files: **`Ran 36` either way**, and
both guards go red.

```
tests/test_editor_brief.py        27 -> 51 tests   OK
tests/test_editor_assignment.py    0 -> 37 tests   OK   (new)
```
