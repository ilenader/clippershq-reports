## 1 + 2. The deliverable is now nameable and buildable

**New in `control.py`:** `SEND_FILE`, `SEND_FILE_RULE`, `announce_send_file()` and
`_build_send_files()`. The builder is a free, offline wrapper over `all_bot_ready` — master is
opened read-only, no API call, no spend — and it **derives** rather than appends, so running it
twice is a no-op and a damaged file is repaired by re-running.

**Run for real, just now:**

```
  BUILD MY SEND LIST
    Reads master_leads.csv (read-only), applies the send gates, writes ONE file.
    FREE -- no API calls, no spending.
    2,949 leads written (+0 vs last build).

  YOUR SEND FILE: output\ALL_BOT_READY.csv
    2,949 leads  |  just rebuilt
    This is the ONLY file to send from. Every other CSV in output/ is either a
    subset of it or an old snapshot -- sending from a second file just emails
    the same people twice.
```

The `+0 vs last build` is the idempotence proof: a second build of unchanged master changes
nothing.

**After every funnel run, at both entry points**, the same notice prints with one extra line:

```
  YOUR SEND FILE: output\ALL_BOT_READY.csv
    2,949 leads  |  last built 2026-07-31 22:40
    This is the ONLY file to send from. ...
    New leads from this run are NOT in it yet -- rebuild with [b] Build my send list.
```

That last line closes the trap the old flow created: a run finishes, the count goes up, and the
file on disk is still yesterday's. `announce_send_file()` is wrapped so a cosmetic notice can
never break a run, and it handles the not-built-yet case explicitly.
