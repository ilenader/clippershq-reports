## 1. The four `count=` sites — the default was dead, so it is gone

Every caller in the tree passed `count` explicitly: `main.py` from config's `page_count`, the `discover()`/`discover_search()` wrappers from their own argument, and all six test call sites. **The default decided nothing and could not be observed.**

That is not harmless on these four specifically: **`count` is items per page, and every page is a billed request.** A caller who one day forgets the argument would silently inherit a number nobody chose.

**The config value was always authoritative. The default is now impossible.**

| function | before | after |
|---|---|---|
| `discovery.discover_pages` | `count: int = 30` | **required** |
| `discovery.fetch_recent_videos` | `count: int = 12` | **required** |
| `discovery_search.discover_search_pages` | `count: int = 20` | **required** |
| `ig_discovery.fetch_recent_posts` | `count: int = 12` | **required, keyword-only** |

Forgetting it is now a `TypeError`, pinned by test. `tests/test_count_defaults.py`, 6 tests, green.

**One exception, and it is the interesting one.** `discovery.discover()` **keeps** its `count=30`, because `keyword_cooccurrence.py:308` calls it *without* a count:

```python
discover_fn=lambda c, hid, max_items: discovery.discover(c, hid, max_items=max_items)
```

That 30 is live production behaviour; deleting it would be a behaviour change, not a cleanup. So it stays — **and now a test reaches it by omission**, asserting the client is actually asked for 30. That is the half that was missing everywhere: a default is only honest if something exercises it.

## 3. The sweep now sees from-imports and getattr — and the verdict survives

BL-933 stated three limits. Two are closed:

```
from X import a, b        66 previously-invisible sites in this tree
getattr(M, "literal")     2-arg only; a 3-arg getattr has a default, so a
                          missing name is handled by design
```

**From-imports matter more than attribute access**, which is why they went first: a bad attribute fails when the line runs, a bad from-import fails at **import time** and takes the whole module with it.

Re-run against a fresh HEAD extract — 575 files:

```
IMPORT SWEEP        every module in clippershq/, dashboard/, tools/ imports at HEAD
MISSING-ATTRIBUTE   PRODUCTION: no committed caller references a name HEAD does not define
HEAD IS COHERENT for production   (0 import failures, 0 production sites)
```

**The coherent verdict survives the extension.** A computed `getattr` name is still left alone rather than guessed — guessing is what gave the first version a 34-hit false-positive rate.

**The third limit stands: runtime-only breaks.** A module that imports and fails on first call is still invisible. "Every module imports" remains weaker than "everything works", and no static sweep closes that.

## Limits

- **The extended sweep's own output above was produced against the HEAD that existed before my deletion commit**, so it still lists the ten probes. I verified their removal directly (`git cat-file -e HEAD:` — 10 of 10 absent) rather than paying another ~20 minutes for a re-run whose only difference would be a shorter list. The production verdict is unaffected either way.
- **The from-import check costs a subprocess per (file, module) pair** and took ~20 minutes against ~7 before. It should batch per file; I left it slow rather than rewrite a passing check late in a round.
- **Making `count` required is a breaking change to a public signature.** Every in-tree caller is fixed and tested, but anything outside this repo calling `discover_pages(client, tag)` now raises. Nothing outside this repo is known to.
- **I deleted nine files after checking only one kind of dependency.** The import graph said they were unreferenced; the claims record said otherwise for one of them. I did not think to check `docs/claims/` until a test told me to, and the same blind spot would apply to anything else that names a path without importing it — a doc, a runbook, a CI config.
- **The `handle=''` and `campaign=''` gradings are judgement, not measurement.** I argued `campaign` matters more than its bucket suggests and then left it, because its file was held — which is the right call on ownership and an unsatisfying one on substance.
- **"Production omits it" is measured over `clippershq/`, `dashboard/` and `tools/` only.** A `scratch/` caller relying on one of the four defaults would now break; I did not sweep scratch for that before making them required.
- **The five load-bearing defaults remain untested.** They are legitimate, and a wrong value in any of them would still reach production without failing the suite. That is a smaller version of the same problem and is not fixed here.
