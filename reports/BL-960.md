# BL-960 — Can we read every second of a clip affordably?

**READ-ONLY round.** No shipping code changed. Writes confined to `scratch/`.
**Paid calls: $0.0117 of a $0.20 budget** — 18 minimal OpenRouter calls against a *synthetic*
30-second probe clip, plus free Gemini `countTokens`. No library clip was retrieved and no
paid IG call was made.

## 1. What a second-by-second reading actually costs

**The framing in the brief is off by one step, and correcting it is most of the answer.**

The current call already reads every second. Gemini samples video at **1 frame per second**
and tokenises it at ~300 tokens/second (Google's own video-understanding docs: 258 tok/frame
+ 32 tok/s audio). This library's own calls measured **302 tok/s** (BL-838, n=18) and this
round measured **283.2 tok/s** on a synthetic 30 s probe. All three agree.

So the model already receives all 38.6 seconds of the mean clip, and that input is **already
paid for** — it is 79% of today's vision bill. What is coarse is not the reading. It is the
**writing**: a median of 7 beats emitted over a 32.65 s clip.

Second-by-second is therefore an **output-schema change on an input already bought**, and it
is priced accordingly:

- output tokens fit `190.0 + 51.5 × beats` (least squares, n=18, **R² = 0.937**)
- 7–8 beats → 688 output tokens; 38.6 rows → 2,178 output tokens
- the delta is **$0.59 per 1,000 clips**, +27%

That is the honest answer to Q1: **a full per-second reading costs 27% more than today, and
if `media_resolution=LOW` is used it costs 7% less than today.** It is not expensive. It was
never going to be, because the expensive part was already being bought and thrown away.

**Two operational limits, both measured:**

- **`max_tokens=5000` truncates 4.4% of the library at one row per second** (87 of 1,999
  clips — everything past 93 s). Not a blocker; a known clip-length cutoff.
- **OCR does not become affordable at any sampling rate.** Row 5 is cheaper in dollars only
  because it drops the model entirely, and it buys 15 CPU-hours per 1,000 clips to do it.
  Perceptual-hash dedup keeps 82.7% of frames and so removes 17.3% of a large number. That
  result stands exactly as it was.

## 2. Is there a cheaper model?

**Yes — and the reason the usual answer is wrong is worth more than the answer.**

A price list is per **token**. What a clip costs is tokens **× tokens-per-second-of-video**,
and *that rate is a property of the model, not of the price list*. Nobody but Google
documents it. So this round measured it: one minimal call per candidate against an identical
synthetic 30 s clip, reading `usage.prompt_tokens` off the response.

| model | $/1M in | **measured tok/s of video** | $/1,000 clips¹ | vs baseline |
|---|---:|---:|---:|---|
| `qwen/qwen3.7-flash` | 0.03 | 220.8 | **1.35** | **0.62×** |
| `gemma-4-26b-a4b-it` | 0.07 | **80.6** | **1.77** | **0.81×** |
| **`gemini-2.5-flash-lite` (today)** | 0.10 | 283.2 | 2.77 | 1.00× |
| `bytedance-seed/seed-2.0-mini` | 0.10 | 398.5 | 3.32 | 1.20× |
| `bytedance-seed/seed-1.6-flash` | 0.075 | **649.6** | 3.74 | 1.35× |
| `gemini-3.1-flash-lite` | 0.25 | 91.2 | 4.95 | 2.28× |

¹ at one row per second. Prices fetched live from `https://openrouter.ai/api/v1/models` at
run time, not typed from a page.

**Tokenisation rate varies 8.1× across these models (80.6 → 649.6 tok/s). Price varies 8.3×.
The two are uncorrelated.** `seed-1.6-flash` is 25% cheaper per token than the incumbent and
**35% more expensive per clip**. Ranking candidates by list price would have picked it.

*This is the project's own proxy rule (`docs/PRECONDITIONS.md` §10) with a new instance:
price-per-token is a proxy for price-per-clip, and it fails silently in the "everything is
fine" direction.*

### The finding that actually pays: `media_resolution`

Google documents a `media_resolution` parameter that drops frames from 258 to **66 tokens**,
taking video from ~300 to ~100 tok/s. It works, it is reachable through the exact OpenRouter
path production already uses, and it is a **one-parameter change**:

```
media_resolution: "MEDIA_RESOLUTION_LOW"     # TOP-LEVEL, not inside generationConfig
  8,497 prompt tokens  ->  2,737    = 3.10x on the same file
```

Verified twice by two independent routes — free Gemini `countTokens` (303.8 → 105.4 tok/s)
and billed OpenRouter usage (283.2 → 91.2 tok/s). `MEDIUM` and `HIGH` are no different from
default (8,497 / 9,122 tokens).

**GOTCHA, and it is the shape this repo keeps meeting.** Only the **top-level** parameter is
real. `extra_body.media_resolution` and `generationConfig.mediaResolution` were both accepted
with HTTP 200 and **changed nothing** — 8,497 tokens, silently. A wrong *value* on the
top-level key errors loudly with the enum; a wrong *location* is a silent no-op that would
have read as "we tried LOW, it saved nothing."

`gemini-3.1-flash-lite`'s 91.2 tok/s is the same number as 2.5-flash-lite at LOW, which is
consistent with Gemini 3 defaulting to low media resolution. You do not need Gemini 3 to get
Gemini 3's token rate, and at $0.25/1M you would pay 2.5× for it.

## 3. What would the extra detail buy?

**Less than the operator hopes, and the reason is already recorded in this repo.**

`docs/CORRECTIONS.md` carries a section headed *"Vision beats do NOT locate when something
happens — do not re-propose them."* MEMEBOT-038 scored beat timestamps against independent
frame-to-frame pixel change in the content region:

| signal | n | median Δ at claimed time | lift over chance |
|---|---:|---:|---:|
| scene cuts (`clip_cuts`) | 235 | 0.1759 | 4.15× |
| **vision beats** | 114 | 0.0402 | **0.98×** |
| random | 119 | 0.0304 | 1.00× |

**Per clip, beats won 0 of 17.** The `what` text is good — the mood rules rightly use it.
**Only the timestamps are worthless.**

That is decisive for three of the operator's four asks, because they are all timestamp
questions:

| the ask | today | would per-second detail deliver it? |
|---|---|---|
| what happens each second | 19,201 beats, median gap 2.95 s, p10 1.0 s | **more rows, same worthless timestamps** |
| **what text appears when** | clip-level string only, 80.7% coverage, **no timestamps at all** | **YES — this is the one real gap** |
| what the mood is | — | **NO.** Audio mood is CLOSED at 40% reproducibility; the field's own benchmark is PR-AUC 0.11 |
| where the interesting moment sits | nothing | **NO** — see §4 |

A per-second timeline would produce **accurate descriptions attached to unreliable times**.
That is a worse artefact than a coarse one, because it *looks* like a timeline. The
coverage check that makes beats look usable already fooled this project once — `max(t_end_s)
/ duration_s` lands in 0.8–1.2 on 85% of clips, which only says the timeline spans the clip.

**Also worth checking before building on the schema:** `vision_beats` declares `scene` and
`is_action` fields. They are populated on **1 of 1,985 clips**. A requested schema that was
never filled, sitting in the data looking available.

**And the honest ceiling the brief already names:** within an account, 40 clip features were
flat against view count. Nothing here contradicts that. More detail is a **description**
improvement, not a demonstrated **performance** one, and no measurement in this repo yet
connects any clip feature to views.

**The one real gap is timestamped on-screen text.** `vision_on_screen_text` is a single
undated string per clip. No per-beat `on_screen_text` exists on any of 1,985 clips. If the
operator wants "what text appears when", that genuinely is not being bought today, and
adding it to the existing beat schema costs output tokens only — no new input, no OCR, no
CPU-hours. It inherits the same timestamp unreliability, so it should ship as *ordered* text
with rough times, never as a caption track.

## 4. Where should the drop land?

**The unresolved question is more unresolved than the brief states, and the 4.15× does not
mean what it looks like.**

Read `scratch/memebot038_beats_vs_cuts.py`. The score is
`delta[i] = mean |frame[i] − frame[i−1]|` in the content region. The winning signal,
`clip_cuts.find_cuts()`, is **itself a frame-difference detector on that same region**. The
metric and the signal are the same construct.

**4.15× is a detector scoring well on its own definition.** It confirms `find_cuts` finds
cuts. It is not evidence that a cut is where a drop belongs. The genuinely informative number
in that table is the other one: **0.98× proves beat timestamps carry no visual information.**

**There is no ground truth for drop placement anywhere in this repo.** `hookmark/` marks
hook windows **in the song** (4 songs, hand-marked) — song time, not clip time. Nothing has
ever recorded where a human thought a drop should land in a clip. So:

- "scene cuts beat beats 4.15× to 0.98×" compares two signals against a **pixel proxy**
- the 77% coverage figure is real and is the honest ceiling for region-aware detection
- **but no candidate signal — cuts, onsets, motion energy, or text changes — can be ranked
  against the actual question until somebody marks clips by hand**

On the three candidates the brief raises, from measured context rather than new work:

- **Audio onsets in the source** — prior research (`scratch/beatdrop_mood_research.md`) puts
  the published energy baseline at F≈0.756 for locating a highlight, and recommends shipping
  it as `energy_peak_s` **with confidence, never as "the drop"**. Automatic drop detection is
  separately CLOSED at 100% fabrication on real audio. Onsets are cheap and $0, but they
  would land in the same unfalsifiable state as everything else.
- **Motion energy** — this is `frame_deltas` under a different name. Scoring it against pixel
  change would be circular in exactly the way the 4.15× already is.
- **OCR text changes** — a genuinely independent signal, and the only one of the three not
  derived from pixel motion or audio. It is also the most expensive (12.4 CPU-hours/1,000).

**The blocking resource is 30 hand-marked clips, not a better detector.** That is an
afternoon with `hookmark/`, it costs $0, and without it every future round on this question
will produce another number scored against a proxy.

## 5. Recommendation — one path

**Do not buy the second-by-second reading. The current labelling is sufficient for what it
is used for, and the richer version would be accurate text on unreliable timestamps.**

That is the negative result, and it is the main one. Three of the four things the operator
wants — per-second action, mood, and the interesting moment — are blocked by a measured
property of the beats (0.98×, 0/17) and by two CLOSED audio results. No amount of extra
detail moves them, because the failure is not resolution.

**The one thing worth doing, and it saves money rather than spending it:**

> **Measure `media_resolution=MEDIA_RESOLUTION_LOW` against default on ~100 library clips,
> then adopt it if it holds. Budget $0.30.**

- it cuts the input leg **3.10×**, taking the fully-loaded cost from **$2.18 to $1.43 per
  1,000** — a **34% reduction** on every clip labelled from now on
- it is **one top-level parameter** on the call already being made, on the model already in
  production, through the OpenRouter path already in use
- the whole 2,003-clip library could then be re-read for **$4.07**

**The A/B is required, not optional, and here is the specific risk it tests.** Google's own
docs say higher resolution improves *fine text reading*. `vision_on_screen_text` is populated
on 80.7% of the library and is a real deliverable. LOW may cost exactly that field. Score the
100 clips on on-screen-text agreement and beat count against the stored labels; adopt only if
both hold. If text degrades, the fallback is not "keep default everywhere" — it is LOW plus a
default-resolution re-read on the subset where text matters.

**If the operator wants one new field**, it is **timestamped on-screen text** added to the
beat schema — the only ask with no current coverage, costing output tokens alone. Ship it as
ordered text with approximate times, never as a caption track, because it inherits the
timestamp problem.

**Not recommended:** switching model. `qwen3.7-flash` at $1.35/1,000 looks like the winner in
the table, but it is an unvalidated model against a corpus where the incumbent's fabrication
rate is *measured* at 0.2% against an unanswerable control. `media_resolution` gets a 34% cut
with no model risk at all. Re-open the model question only after LOW is settled.

## Reproduce

```
python scratch/bl960_signals.py     # synthetic probe, tok/s per model, hard $0.20 cap
python scratch/bl960_cost.py        # the cost table, from measured constants only
```

`scratch/bl960_cost.json`, `scratch/bl960_routes.json`, `scratch/bl960_small_probe.json`
carry the raw measurements.

**Limits of this round.** The 8-model tokenisation table is one synthetic clip per model,
not a distribution — it establishes the *rate*, which is duration-driven (the same model
returned identical token counts for a 12 MB and a 197 KB encoding of the same 30 s), but it
does not establish label *quality* on any of them. No candidate model was scored for accuracy
or fabrication. The `media_resolution` finding is a token measurement, not a quality one, and
§5 is explicit that the quality A/B has not been run.
