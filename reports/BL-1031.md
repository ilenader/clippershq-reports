## 2. The guard

```
python tools/git_safe.py <ROUND> checkout|restore|clean|unstage|reset-hard -- <paths>
python tools/git_safe.py <ROUND> discard-mine          # the safe path
python tools/git_safe.py --prune-days 3
```

A path is permitted only if it is **declared in the calling round's own claim** *and* **claimed by no other live round**. Everything else refuses, and the refusal names the holder so the caller knows who to talk to.

Three design points that came from the incidents rather than from taste:

**A path-less command is expanded, not waved through.** `clean` and `reset --hard` with no path are aimed at every round at once — which is exactly the shape INFRA-025 took. They are expanded to every dirty path so the same per-path ownership check applies, and the refusal names what it would have hit.

**A clean path still passes the ownership check.** `git clean` removes untracked files that no `git diff` will ever show you, so "not dirty" is not the same as "nothing to lose".

**An unreadable claim is treated as held.** Failing open on a corrupt registry would turn it into a licence to delete.

### The safe path is one command

`discard-mine` drops the caller's own perturbation across the caller's own declared paths, needs no flags, and refuses everything else. This is not politeness: BL-818 measured a gate with no escape hatch reaching **1 round in 40**, disabled by never being installed. A guard people route around protects nothing.

### The snapshot

Every permitted operation copies the affected files **outside the working tree** first — `%LOCALAPPDATA%\clippershq\git_safe_snapshots\`, with a `MANIFEST.json`. Deliberately **not** `backups/`: INFRA-024 measured 252 files sitting on the same disk under the same OneDrive folder as their subject, which is a copy, not a backup. A snapshot destination inside the tree is refused outright.

## 6. What I got wrong

**The refusal exit code was 2 — the same code argparse uses for a usage error.** My first rehearsal reported *"A refuses a foreign dirty file — PASS"*, *"C path-less clean refuses — PASS"*, *"D refuses to unstage — PASS"* while `git_safe` was **not running at all**: argparse was rejecting the command line and exiting 2, and my prover read 2 as "refused".

That is the exact failure this round exists to prevent, in the instrument: **a guard whose failure is indistinguishable from its success**. Refusal is now `EXIT_REFUSED = 3`, and both the prover and the suite raise loudly on any `usage: git_safe.py` in the output rather than scoring it.

Underneath it were two real argparse faults, now fixed: a literal `--` between an optional and a trailing `nargs="*"` is rejected, and argparse cannot backfill that positional once an optional has intervened (`BL-1 checkout --repo X foo.py` left `foo.py` unrecognized). Ordering is not something an operator should have to get right to avoid losing work, so leftovers are collected via `parse_known_args` — with unknown **flags** still an error, since silently ignoring a `--dry-run` typo turns a rehearsal into a deletion.

**I also reached for the wrong instrument on the campaigns check.** I hand-rolled a directory walk and got `e3b0c442…`, the SHA-256 of empty input, because `campaigns/` is not a directory at all. The project already pins that fingerprint pair in `tests/test_governance_rules.py`, which passes (25 tests). The cited `7a029ee5447cddd8` / `8e02f8d6f6307ae8` are the same object under compact versus default JSON separators, exactly as the brief says.
