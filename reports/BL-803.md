### The three zeros are each a different story

### 1b. The clip engine: it has run, and it has never run *with the retrieval layer*

BL-784 reported the clip engine had never executed. That is **no longer true and was already stale**: the ledger shows `clip_library_bl725`, 2 runs, 68 calls, $0.0408 on **30 July**, and the library exists — **20 clips, 2 shards, 4 accounts**.

Three things about it matter more than the fact it ran:

1. **It wrote to `scratch/bl725_library/`, not to `./clip_library`** — the configured `clip_library_dir`. **That directory does not exist.** The production library has never been written.
2. **Every media-retrieval field on those 20 clips is `None`** — `clip_pk`, `account_user_id`, `media_renditions`, `subtitles_available`. The clips were stored on 30 July; the DASH wiring landed 31 July (BL-793). **The engine and the retrieval layer have never run together**, so not one stored clip carries a rendition inventory.
3. **`with_format: 0`.** The speech_frac/format stage has never produced a value — it needs audio, which is a separate fetch that is not wired.

So the honest status is: **walk proven at 20 clips, retrieval proven on 1 clip, never proven together, never written to the real location.**

All three are CLI-only. You can run every funnel from a menu, and you cannot produce a single send file from one. Since BL-786 established that `ALL_BOT_READY.csv` is the one file safe to send from, the artefact the whole system exists to produce is the artefact no menu can make.

## 4. What breaks if you run everything tomorrow

Ordered by how likely it is to bite.

1. **You cannot build the send file from a menu.** Every funnel finishes, and producing `ALL_BOT_READY.csv` requires a CLI invocation nobody has documented in the UI. **This blocks the send, not the runs.**
2. **The export is stale the moment funnels finish.** Master is at 58,325 rows, written 17:54; the export holds 2,787 rows built at 15:52. Suppression is an *export-time filter*, so any run invalidates the current file and it must be rebuilt — see 1.
3. **YouTube hits its quota ceiling fast.** `daily_quota_units: 10000`, `search_unit_cost: 100`. That is **100 searches per day, total**, against `run_target: 50`. One YouTube run per day, maybe two. It has run exactly once and delivered 27 leads.
4. **The clip walk on 200 accounts writes nowhere useful.** `clip_library_dir` is `./clip_library`, which does not exist; the only live run wrote to `scratch/`. At `clip_max_pages_per_account: 10` and ~$0.0006/call, 200 accounts is ~$1.20 — cheap — but the output lands in a directory nothing else reads.
5. **Disk is at 91% (90 GB free).** Fine for JSONL. Fatal for the 8.5 GB/1,000-clip media path BL-787 measured, if anyone ever stores media — which is exactly why BL-793 stores identity only.
6. **A 200-lead send has no ranking on the client half.** BL-786 measured every sort key at zero on client rows; `DIRECT_SEND.csv` rank order is arbitrary. The clipper block sorts correctly.
7. **Personalisation is impossible from the export.** BL-788: the file carries no name, fandom, followers or median views. The handle is the only merge token.

**Nothing here is a crash.** Every failure mode is "produces the wrong artefact quietly" — which is the failure class this codebase has spent 800 reports learning to hate.
