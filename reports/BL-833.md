## The answer to the question that mattered

**No — the permalink is not enough, and the fix is already in the data.**

`clip_media.retrieve()` takes `clip_id`, not a URL:

```python
def retrieve(clip_id, *, fetch_clips_page, http_get, ...):
    pk, uid = split_clip_id(clip_id)      # '<pk>_<user_id>'
```

Its own docstring explains why:

> *"there is no fetch-one-media-by-pk endpoint wired in ig_client — the only clip source is `/gql/user/clips`, which returns an account's clips newest-first."*

So the permalink — a shortcode URL — cannot drive retrieval at all. **`clip_id` is the key, it is 100% populated, and the CSV exports it first**, with `clip_pk` and `account_user_id` beside it so a consumer never parses the `_` encoding.

**Nothing extra needs storing.** BL-753 found `video_id` is captured at discovery and discarded; that is harmless, because `retrieve()` never wanted it.

**But retrieval costs paid calls, and the cost scales with clip age** — it walks the account newest-first, one call per page. So the CSV ships `retrieval_depth_hint`:

| hint | age | share |
|---|---|---|
| `page-1-likely` | ≤ 30 d | ~55% |
| `several-pages` | 31–365 d | ~40% |
| `deep-walk` | > 365 d | **5%** — up to 1,675 days |

A `deep-walk` clip on a prolific account may be unreachable within any sane `max_pages`. The hint is a cost warning, not a promise.

## The provenance rule a bot must follow

The library extends `caption_parser`'s ladder with a fourth tier:

| tier | slots | meaning | fields |
|---|---|---|---|
| `declared` | 11,830 | platform payload verbatim | views, likes, comments, saves, reshares, followers, duration, audio type, track |
| `derived` | 2,212 | this pipeline inferred it | genre, franchise, valence, per-view ratios |
| **`measured`** | **412** | **computed from pixels** | **`layout` only** |
| `absent` | 9,706 | unavailable | any |

```
zero-inference subset  ->  *_src IN ('declared', 'measured')
NOT                    ->  *_src == 'declared'
```

**A bot filtering on `declared` alone silently discards all 412 layout observations** — which are a CV read of the actual frames, arguably *more* trustworthy than metadata a platform could mislabel. This is the single most likely way to misuse the file, so the spec leads with it.

Every populated value with no provenance entry exports as `unattributed` and must read as null. That state does not occur today; the column exists so it stays visible if it returns.

## Renditions — the system was already right

BL-798 proved the ladder is not stable per clip (720×1280 avc1, then 1080×1920 AV1 seconds later). The brief asked me to warn against exporting a rendition URL.

**The library never stored one.** `rendition_inventory()`:

> *"THE STORABLE SUMMARY — identical to parse_renditions() minus every URL … with nothing in it that can expire."*

Verified against the data: stored entries carry `bandwidth, codecs, fps, height, id, kind, mime, width` and **no `url`**. The CSV exports only `rendition_max_height`, `rendition_codecs`, `rendition_count` — enough to decide whether a clip is worth a call. The bot re-fetches a fresh manifest and re-picks. Sanity-checked: **no URL of any kind in the sample except the permalinks.**

## Why the CSV, stated as the argument it is

The library shards on **`posted_at`, not write time** (BL-802). A clip posted in January and discovered today lands in the January shard. So for a consumer:

- "what is new" cannot be answered from the newest shard;
- a full read means opening and merging **all 22 shards**;
- shard membership changes meaning as backfill lands.

**A flat CSV removes the whole class.** One file, one row per clip, `exported_at` on every row. The bot never learns what a shard is. That is the case for the format — not convenience, a removed failure mode.

## The column set — 61, with real fill

100% on the identity and retrieval block (`clip_id`, `clip_pk`, `account_user_id`, `shortcode`, `permalink`, `account`, `posted_at_*`, `age_days`, `retrieval_depth_hint`), and on `views` and `caption`.

The honest middle: `likes` / `comments` / the follower-count column / `engagement_per_follower` / `duration_s` at **55%**, `reshares` **46%**, `track_title` / `track_artist` **43%**, `genre` **38%**, `franchise` **37%**, `saves` **17%**. Layout signals 55%, `valence` 99%, `audio_type` 99%.

Every one of those carries its `*_src` beside it, so a bot filters rather than guesses.

**Deliberately shipped empty: `medium` / `medium_src` (0%).** `content_genre.py` emits medium as a field distinct from genre, but the clip-library writer never persists it. It is one writer change from populated, and a bot will want anime-vs-live-action, so the column exists now to avoid a later schema change.

**Deliberately not exported at all:** `format`, `arousal_audio`, `affect_conflict`, `speech_frac`. Three are absent by design and one is unbuilt; five permanently-empty columns would be noise, and `medium` is the only one with a path to being filled.

## Honest limits

- **The library grew during this round** — 417 in BL-827, 555 earlier tonight, 755 now. Every fill percentage is a snapshot of a moving target and will drift as walks continue.
- **Fill rates are not quality.** 38% genre coverage says the field is populated on 289 clips; it says nothing about whether those genres are right. BL-802 and the `derived` tier are the relevant caveats.
- **I did not exercise `retrieve()` against a live clip.** The contract is read from source and from the stored identity fields; the claim that `clip_id` is sufficient is a code reading, not a round trip. Confirming it costs a paid call, which this round excluded.
- **`retrieval_depth_hint` is an age heuristic, not a measured page count.** A 20-day-old clip on an account posting 30×/day is not on page 1. Turning it into a real estimate needs each account's posting rate, which the library does not store.
- The prototype re-reads all 22 shards on every run; that is fine at 755 clips and will want revisiting well before it matters.
