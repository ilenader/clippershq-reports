## The thing nobody asked for: the wiring was double-counting

While reading the wiring to pick a funnel, the shape looked wrong — the meter flushes DURING
the run, and the `finally` then recorded the **full cumulative counter** on top. Replayed
offline against the real `IncrementalMeter`:

| billed calls | flushes on disk | finally adds | ledger believes | error |
|---|---|---|---|---|
| 10 | 0 | 10 | 10 | 0% |
| **25** | 25 | 25 | **50** | **+100%** |
| **63** | 50 | 63 | **113** | **+79%** |
| **120** | 100 | 120 | **220** | **+83%** |

**It is invisible below the flush threshold.** At 10 billed calls there is no flush and no
error at all — which is exactly why it shipped, and exactly why the one kill test ever run
against it (0 flushes) could not have caught it. The bug needs ≥25 billed calls to exist, and
every test that exercised it stayed under that.

Fixed at **all five paired sites** — `repost_finder`, `youtube_finder`, and `control.py`'s
email / twitch / spotify / clip-library blocks — by replacing the final full-total write with:

```python
_meter.sync(<the same billed counter the meter runs on>)
_meter.flush(force=True)
```

`sync()` is idempotent against a cumulative counter, so this records every billed call exactly
once whether the meter flushed during the run or not. Verified: 25 → 25, 63 → 63, 120 → 120.

**A second defect fell out of the same read.** Twitch and Spotify's final blocks recorded the
funnel's **logical** counters (`_st["ig_calls"]`) while their meter syncs on the **billed**
`client.http_requests`. Those are different numbers — retries and the `/top` fallback bill
twice for one logical call — so the two writes were double-counting in mismatched units. Both
now use the billed counter.

**Has it landed in the live ledger?** The ledger carries 31 rows of exactly 25 calls, and
`REPOST_FINDER` shows the tell-tale alternation of 25-call rows with 26/27/34-call rows.
I could not attribute specific dollars, because **the ledger has no run boundaries** — which
is precisely what item 5 exists to fix, and a neat demonstration of why it was worth doing.

## 2. repost_finder is no longer blind below its first confirmed page

BL-830 called this funnel kill-safe. It was kill-safe **once pages started confirming** and
blind before that: metering was driven only by `on_confirm`, so a run killed during discovery
— or one that simply confirmed nothing — recorded $0 no matter how many pages it had paid for.

The fix needed no new hook. `over_cap()` already calls `spent_fn` once per page for the
`max_run_usd` check, so wrapping `spent_fn` with `metered_spend_fn` meters the page loop at
exactly the cadence the cap already runs at — the same one-line change every other funnel uses.

Proven with a client that bills on every page and confirms nothing:

| | pages billed | pages confirmed | calls on disk |
|---|---|---|---|
| before | 40 | 0 | **0** |
| after (flush 25) | 40 | 0 | **25** |
| after (flush 5) | 40 | 0 | **35** |

## 4. `tools/claim.py` refuses a duplicate id

It previously overwrote unconditionally, and did: a live round's `started`, `pid` and one of
five `will_write` paths were destroyed with no recovery, because the file is the only record.
A tool whose entire purpose is answering "who is doing what right now" silently erased the
answer.

```
$ python tools/claim.py start BL-839 --intent "attempt to clobber" --write foo.py
  REFUSED: a claim for BL-839 already exists (started 2026-08-01T12:44:52, pid 41616,
  8 path(s)). Pick a different round id, or pass force=True/--force to reclaim it.
exit=2
```

The victim's claim was verified intact afterwards (all 8 paths). `--force` still reclaims an
id you own. This is the one blocking behaviour in a deliberately advisory tool, and it blocks
on a **name collision**, never on contention — a collision is never something you want to
resolve by overwriting.

## 5. `run_id`, stamped at write time

`FULL_COLUMNS` 71 → **72**, appended last. Stamped in `writer._append_master` — the single
function every master append passes through — rather than one line per funnel, because a
per-funnel stamp is a thing five callers can each forget, and the one that forgets is
invisible until someone tries to attribute its rows a month later.

Forward-only by construction, per BL-834: 92.1% of master predates the ledger and only 3.8% of
rows fall inside exactly one run's window, so backfill is impossible and the column is blank on
every existing row by necessity, not by choice.

```
run_id set   -> row1 run_id = 'bl839proof-20260801-131121-26176'
run_id unset -> row2 run_id = ''      (blank — never invented)
every row 72 fields wide (== FULL_COLUMNS)
```

> **A regression I introduced and caught.** The first `_stamp_run_id` padded any short row out
> to full width. `tests/test_filelock.py` appends deliberate **6-column** rows to a 6-column
> file, and every one came out 72 fields wide — its torn-row check caught it. `_build_row`
> already emits the column automatically (it comprehends over `FULL_COLUMNS`), so padding was
> never needed. It now fills an existing cell and leaves anything narrower untouched.

  youtube share the identical `metered_spend_fn` wrap and are proven only by that shared
  mechanism plus unit tests, not by their own SIGKILL.

  is accurate to the last batch". By design up to `flush_every - 1` calls are still lost — 24
  at most, ~$0.014.

  has the right shape for it, not how many dollars it added, because run boundaries did not
  exist until this round. Anything before now stays as recorded.
- **`test_filelock` failed once inside the suite and passed 3/3 standalone**, then the full
  suite went green on re-run. Load-flakiness while other agents ran funnels, not a defect I
  could reproduce — but I am reporting the red I saw, not just the green I ended on.
- **`run_id` is set by the caller.** `_build_clip_library` was stamped for the kill run via the

  blank until each entry point sets it. That is the remaining one-line-per-funnel change, and
