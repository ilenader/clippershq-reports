# BL-664 — the human baseline: how often does a human reject a clip and then overturn it?

**2026-07-24 · AUDIT ONLY. READ ONLY.** No code, data or config change; no provider call, no cost. Every timestamp cast `::text` vs DB `now()` = 2026-07-24 18:56 UTC. Clipper handles redacted to 6-char hashes.
**Base:** origin/main `5c667b25` · **Branch:** checkpoint/BL-664 · isolated worktree, no `node_modules` junction. A markdown-only diff cannot change tsc or build, so none was run and none is claimed.

## FIRST LINE (the recoverability answer, plainly)

**Reject-then-approve is recoverable, but ONLY for the scoped reviewers' rejections, which are a minority of all rejections.** The reviewer decision log (`reviewer_audit_log`) records 130 real `REJECT_CLIP` events (all by two REVIEWER-role accounts, 2026-06-01 to 2026-07-22), and of those **2 were later approved = a 1.54% reviewer overturn rate**. The OWNER's rejections (about 465 of the currently-rejected clips) are NOT written as timestamped events, so an owner-rejected-then-approved clip is invisible to history and the owner-side overturn rate is UNRECOVERABLE. So the honest baseline below is a REVIEWER baseline, not a whole-platform one, and it is very low.

## PART 1 — the history: what is stored, and what is recoverable

**Where clip decisions are logged.** `reviewer_audit_log` (Postgres `@@map`, Prisma model `ReviewerAuditLog`). Columns: `id`, `reviewerUserId` (text), `action` (text), `clipId` (text), `campaignId` (text), `payoutRequestId` (text), `rejectReason` (text), `metadata` (jsonb), `requestRoute`, `requestIpHash`, `userAgentHash`, `firedAt` (timestamptz). The timestamp column is `firedAt` (not `createdAt`). Decision actions and their live counts (`::text` ranges):

| action | rows | first fired | last fired |
|---|---|---|---|
| `APPROVE_CLIP` | 1528 | 2026-06-01 20:50:37 | 2026-07-24 15:57:11 |
| `REJECT_CLIP` | 130 | 2026-06-01 23:27:21 | 2026-07-22 00:44:50 |
| `BACKFILL_APPROVE` | 665 | 2026-04-22 21:29:11 | 2026-06-01 19:16:14 |
| `BACKFILL_REJECT` | 211 | 2026-04-24 08:10:03 | 2026-06-01 14:10:43 |
| `PROPOSE_APPROVE` / `PROPOSE_REJECT` / proposals | 13 / 4 / ... | reviewer-proposal workflow | |

The `clips` table itself holds only the CURRENT `status` plus `reviewedAt` / `reviewedById` (the LATEST review), so a prior rejection that was later approved leaves no trace in `clips`; the event log is the only place a reject-then-approve can be seen. `BACKFILL_*` rows are a one-time historical import (their `firedAt` is a batch stamp, so time-to-overturn is meaningless for them). The real, individually-timestamped decision stream is `REJECT_CLIP` / `APPROVE_CLIP` from 2026-06-01 onward.

**The coverage gap, stated because it bounds everything below.** The log does NOT capture most rejections:

| measure | value |
|---|---|
| clips currently REJECTED (total) | 798 |
| clips currently REJECTED (reviewed in last 30 days) | 354 |
| distinct clips with ANY logged reject event (`REJECT_CLIP`+`BACKFILL_REJECT`) | 325 |
| clips currently REJECTED with NO logged reject event | **489** |
| of those 489, rejected by role OWNER | **465** (24 null/deleted reviewer) |

So the owner rejects through a path that writes no event row; only the two scoped reviewers' rejections are event-logged. **Reject-then-approve is therefore recoverable only for the ~325 clips that carry a reject event, and cleanly only for the 130 real-event `REJECT_CLIP` clips.** This is not an approximation of a whole-platform rate; it is the reviewer subset, stated as such.

## PART 2 — the number

### The reviewer overturn rate (the clean, real-event measurement)

Method: a clip is "overturned" if it carries a `REJECT_CLIP` event and is now APPROVED (this catches an overturn via ANY later path, not only a logged `APPROVE_CLIP`; in fact 0 of the 130 had a later `APPROVE_CLIP` event, so both overturns were re-approved through a non-logged path).

| measure | value |
|---|---|
| clips rejected by a reviewer (`REJECT_CLIP`) | **130** |
| of those, now APPROVED (overturned) | **2** |
| **reviewer overturn rate** | **1.54%** |
| date range | 2026-06-01 23:27 to 2026-07-22 00:44 (`::text`) |

**By who rejected:** all 130 `REJECT_CLIP` were by REVIEWER-role accounts (reviewer `9ee3e8`: 124 rejected, 2 overturned; reviewer `31f9e6`: 6 rejected, 0 overturned). ZERO `REJECT_CLIP` by the owner (the owner's rejections are the 465 unlogged ones in PART 1).

**By campaign:** WinGram 38, GainzAlgo REPOST 37, bees.n.honey 29, somesome 14, Panic Baby 6, plus a few single-clip campaigns.

**By time-to-overturn (misclick vs genuine reconsideration):** both overturns were the same clipper (`b1e30e`), both on reviewer `9ee3e8`'s rejections, neither an owner override:
* one rejected 2026-06-02 20:25, approved 2026-06-03 11:49 = **15.4 hours** later (a genuine next-day reconsideration).
* one rejected 2026-06-07 15:54, approved 2026-06-07 16:02 = **0.1 hours (6 minutes)** later (a near-immediate correction, most likely a misclick or instant re-review).

So of the two overturns, one is a real reconsideration and one is a probable misclick. On the genuine-reconsideration reading, the reviewer overturn rate is **1 of 130 = 0.77%**.

### The wider, weaker measurement (includes the backfill)

Including `BACKFILL_REJECT` (imported timestamps, so no reliable time-to-overturn): of **325** distinct clips with any logged reject event, **16 are now APPROVED = 4.92%**. The backfill contributes 14 of those 16 overturns on unreliable timestamps, so this figure is a soft upper bound, not the clean rate.

### The reverse direction (approved then rejected, the missed-catch)

* Via logged sequence (`APPROVE_CLIP` then a later `REJECT_CLIP`): **0**.
* Via current status (a clip with a logged `APPROVE_CLIP` event that is now REJECTED, re-rejected through any path): **107 clips**. So humans (mostly the owner) re-reject far more clips than they re-approve. Once a clip is rejected it is almost never un-rejected (2 of 130), but an approval is reversed to rejection 107 times. The human process treats rejection as sticky and approval as revisable.

## PART 3 — the honest caveat

**An overturn only happens when someone NOTICES.** This measures CAUGHT mistakes, not all mistakes, so the TRUE human error rate is HIGHER than the 1.54% here. A reviewer who wrongly rejected a clip nobody ever looked at again is not counted. **The identical limitation applies to any machine rate measured this same way, so the comparison to a machine stays fair.** It is a floor on human error, not the real figure.

**A separate, weaker signal for uncaught mistakes.** Of clippers who have ever had a clip rejected (163 distinct), **94 never submitted another clip after their last rejection = 57.7%.** This is a candidate signal that a rejection sometimes drives a clipper away silently (an uncaught cost). It is WEAK and confounded: many of those 94 may be one-time or low-effort clippers who would have stopped regardless, and this cannot separate "left because wrongly rejected" from "left anyway." Reported without overclaiming: it is a reason to care about false rejections, not a measurement of them.

## PART 4 — what it means, in real people

At R-5's measured volume (2026-07-17): **2,302 clips/month across 127 clippers**, of which ~15% (about 345) are rejected and ~1,938 approved.

| Rate | Applied to | Wrongly-rejected clips per month |
|---|---|---|
| Human reviewer overturn **1.54%** | of ~345 reviewer rejections | **about 5 clips/month** are caught and reversed |
| Machine **11.05%** (R-2) | of the ~1,938 human-approved clips it would reject | **about 214 clippers/month** wrongly rejected |
| Machine **1%** (hypothetical) | of ~2,300 clips reviewed | **about 23 clips/month** wrongly rejected |

The two rates are not measured on an identical basis (the human number is caught-and-reversed rejections; R-2's is clips-humans-approved-that-the-machine-would-reject), so this is a magnitude comparison, not a like-for-like subtraction. Directionally it is stark: humans catch and reverse roughly 5 wrong rejections a month; a machine false-rejecting at 11.05% would manufacture on the order of 200 wrong rejections a month, and even a 1% machine would produce about 23, still several times the human caught-error volume.

---

## PART 5 — the verdict

**The measured human (reviewer) overturn rate is 1.54% (2 of 130 reviewer rejections, 2026-06-01 to 2026-07-22), and 0.77% if the 6-minute misclick is excluded; the owner's own rejections are not logged and their overturn rate is unrecoverable.** To be an improvement rather than a regression, an automated reviewer's false-rejection rate would have to beat that reviewer baseline, meaning it must sit well under about 1.5%, and honestly below 1% once you account for the fact that the human 1.54% counts only NOTICED mistakes so the real human floor is even lower-looking than the true rate. **R-2's 11.05% is roughly 7x above this bar; on this evidence R-2's verdict stands and the machine bar is brutal, not comfortable.** The humans overturn themselves almost never, which means either they are very accurate or they rarely revisit, and in both cases a machine that wrongly rejects at 11% would be adding errors far faster than the human process ever corrects them. The one genuine softener is honesty, not comfort: this baseline is the reviewers only and counts only caught mistakes, so the true human error rate is higher than 1.54% and unknown; but nothing here suggests it approaches 11%, and the burden is on the machine to prove a rate under about 1% on real shadow data before it could be called an improvement.

---

## What could NOT be measured, and why

* **The owner's own reject-then-approve rate** — the owner's ~465 rejections write no timestamped event, so an owner rejection later reversed is indistinguishable from a clip that was only ever approved. Unrecoverable without a per-clip status-transition log the platform does not keep for that path.
* **The true (uncaught) human error rate** — only noticed-and-reversed mistakes are counted (PART 3).
* **Whether the 489 unlogged rejections behave like the 130 logged ones** — if owner rejections were overturned at a different rate, the reviewer baseline would be unrepresentative of the whole. Unknown.
* **Time-to-overturn for the backfill overturns** — their `firedAt` is an import batch stamp, not the real decision time.
