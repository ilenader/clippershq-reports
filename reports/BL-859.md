### One tooling gap found while publishing this

`scan_report_for_secrets.py` blocked this report because it names a **config value** that is
an ordinary filename — the clip-seen cache. BL-823 already solved this exact shape for the
opaque-literal rule with `_is_repo_path()`, on the argument *"a key is not also a file on
disk."* That exemption is wired to the opaque-literal check only; the config-value check has
no equivalent, so any report listing a tracked data file by name fails the gate.

The row above is therefore written by config **key** rather than value. That is a workaround,
not a fix, and it costs report fidelity every time it recurs.

**I did not patch the scanner**, deliberately: it is shared tooling that every round's push
depends on, twelve rounds are in flight, and this round claimed no writes outside
`scratch/bl859_*`. Weakening a secret scanner as a side effect of publishing is how a real
leak gets through later. The fix is one line — reuse `_is_repo_path()` in the config-value
check — and belongs to a round that can test it properly.
