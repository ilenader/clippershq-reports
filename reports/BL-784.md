## 3. The engagement fields — **0% on disk**, and the keys are not even present

BL-760 landed six fields and measured them on live payloads. **None of that reached the library.** The eight engagement keys are missing from **all 42 records**, in both stores — not null, absent.

The reason is chronological, not a defect: both stores were written **2026-07-29 and 2026-07-30**; BL-760 landed **2026-07-31**. Every record predates the schema change. `clip_library.field()` correctly returns `None` for an absent key, so nothing is broken — but **nothing is populated either.**

**On which ratio is safe to rank:** BL-760's conclusion stands and I did not re-measure it (that would need paid calls). Its inputs — `like_count`, `comment_count`, `follower_count` — were 100% across all seven sampled accounts, so **`engagement_per_follower` is the ratio to rank on**. `saves_per_view` was 28.6% pooled and 0% on four of seven accounts and should not be a ranking key.

**What this audit adds:** that verdict is currently untestable against the library, because the library holds zero engagement values. The first walk run after BL-760 will be the first opportunity to confirm it on stored data.

## 5. Is the cost ladder enforced?

**The ladder is correct and it holds — but it has never run in anger, so I proved it on real data instead.**

`STAGE_ORDER = ("views", "content_genre", "valence", "layout", "speech_frac", "ocr")`, and `run_stages` rebinds `alive` to only the survivors after each stage, so a rejected clip is structurally unreachable by every later stage.

I drove **the real `clip_walk.run_stages`** with all 42 real stored clips. That test was **vacuous** — every stored clip is already above the 20,000-view floor, because the stores contain only post-filter survivors, so there was nothing to discard. I re-ran it with 8 clearly-labelled synthetic below-floor clips (0 to 19,999 views) mixed in:

| stage | clips entered | saw a below-floor clip? | CPU s charged |
|---|---:|---|---:|
| views | **50** | n/a | 0.0 |
| content_genre | 42 | **0 — none** | 0.0 |
| valence | 42 | **0 — none** | 0.0 |
| layout | 42 | **0 — none** | 1.3 |
| speech_frac | 42 | **0 — none** | 67.2 |
| **ocr** | **42** | **0 — none** | **675.4** |

**VERDICT: LADDER HELD.** All 8 rejects died at `views`; not one reached `layout`, `speech_frac` or `ocr`. Avoided cost: **17.7 CPU-seconds per rejected clip** (16.08 OCR + 1.6 speech + 0.032 layout), 141.7s across the 8.

BL-710's cost figures are live in `STAGE_COST_S` and match: OCR **16.08 s/clip**, speech **1.6 s/clip** — the 10× ratio, confirmed in code.

**The caveat that matters:** this exercises the *mechanism*, using the real function and real clips. It is not a production run, because there has not been one. `run_stages` has no production caller (BL-775 listed it as test-only); `clip_runner.py` would be its first, and it is uncommitted.

## 6. What is missing for the handoff, ranked by what blocks the bot most

1. **There is no video.** The record stores a `permalink` and nothing else — no media URL, no `progressive_download_url`, no local file. I confirmed the permalink is **unusable anonymously** (§1). A bot handed this record cannot obtain the pixels. Everything else is secondary to this; it is the difference between a catalogue and a usable asset. (Note the known constraint: CDN URLs expire, so persisting one has its own design problem — but persisting nothing means the clip cannot be re-fetched at all.)
2. **The library is empty.** 42 records in two scratch folders, 7 accounts, no production store. Even a perfect schema delivers nothing at this volume. This is a *run*, not a build — `clip_runner.py` exists and is wired to the Control Panel; it needs committing and executing.
3. **The eight engagement fields are absent on every record.** The ranking signal BL-760 identified as the safe one (`engagement_per_follower`) cannot be computed from anything on disk. Fixed by the first post-BL-760 walk — no code needed.
4. **`layout` and `format` are null on 100% of records.** These are the fields that say *what kind of edit this is* — caption-bar vs full-bleed, the thing the repost-layout CV work was built to detect. A bot rebuilding an edit needs them, and the stage exists (`layout`, 0.032 s/clip — nearly free) but has never been run.
5. **`franchise` is null on 100%.** `content_genre` fires on only 45–55% of clips, and `franchise` never. The caption of the example record literally begins `Title: Two and a Half Men` — the field is extractable from text already stored, at $0.
6. **`track_title` / `track_artist` are 55% in one store and 0% in the other**, and `arousal_audio` / `affect_conflict` are 0% everywhere. Lowest priority: the audio layer is the most expensive and least proven, and BL-705 already found format is a clip property that does not label an account.

**Nothing consumes the library.** No ranking, no selection, no export reads it. The handoff has no receiving end yet — which is worth knowing before more fields are added to it.

## Limits

- **42 clips, 7 accounts, two scratch folders.** Every percentage here is on that. It is a sample of measurement artifacts, not a population.
- **Permalinks were not verifiable.** Three fetches, all served the login/challenge shell. Format claims in §1 rest on stored `duration_s`, `audio_type` and caption text, not on watching the videos.
- **§3 does not re-measure BL-760.** Confirming the fill rates would need paid calls; I confirmed only that the library holds none of them.
- **§5 is a mechanism proof, not a production trace.** The below-floor clips are synthetic and labelled as such. A real run may reject at other stages in ways this cannot show.
- **`clip_runner.py` is another round's uncommitted work** and may change under me. Its docstring, config defaults and wiring were read at one moment in time.
- **`content_genre` at 45–55%** is measured across both stores combined; per-store it is 55% (bl725) and 45% (demo).

## Method

Located every `*.jsonl` in the repo and identified the two clip stores; confirmed `./clip_library` absent and scanned all four `logs/run.log*` for the engine. Read both stores through the module's own `clip_library.iter_lines` and `field()`, so absent/null/populated are distinguished by the shipping accessor rather than by raw key inspection. Field accounting is against the live `CLIP_FIELDS` tuple. The ladder proof drove the real `clip_walk.run_stages` with instrumented stage callbacks recording which clip ids each stage saw. Permalink checks were three plain unauthenticated HTTPS GETs ($0). Consumer search for `view_count` covered `clippershq/` and `tests/`. Zero paid calls, $0 spent, no repo writes.
