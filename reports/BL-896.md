## 1. One switch, not seven patches

The seven funnels each ask one question through control's raw `_read()`, underneath the six `_ask_*` helpers the shim replaces. The fix is in `_read` itself:

```python
_HEADLESS = False

def set_headless(on=True):
    """Turn every raw _read() into the Enter-equivalent. Returns the PREVIOUS value."""

def _read(prompt=""):
    if prompt:
        _emit(prompt)
    if _HEADLESS:
        _emit("  (headless: taking the default, exactly as pressing Enter would)")
        return ""
    ...
```

and two lines in `run._install_headless_prompts` to turn it on and restore it in `undo()`.

**Why `""` is the right answer and not a guess.** Every one of the seven callers already treats an empty answer as "use the default" — `or (sp_cfg.get("seeds") or sp.DEFAULT_SEEDS)`, `if typed:`, `if raw:`. Empty *is* the Enter-equivalent, which is precisely the contract `run.py`'s docstring states for the other six helpers. Nothing is invented; the caller's own default fires.

**Why not seven patches.** BL-866's lesson on `set_run_id`: a guard at each call site is a thing each caller can forget, and the one that forgets is invisible until someone needs it. This is the single function all seven pass through, so it also covers every `_read` added after today. The test asserts *the mechanism*, not seven line numbers.

**The menus are unchanged.** Nothing sets the flag interactively; `_read` takes the identical path it always did. There is a test for exactly that.

### `_Abort` now carries a message

```python
class _Abort(Exception):
    def __init__(self, msg=None):
        super().__init__(msg or "input ended with no answer (EOF/Ctrl-D). ...")
```

It was raised bare, so `str(exc)` was `''` and every handler that formats it produced `! spotify failed:` — a failure that says nothing. Two BL-866 proof runs died that way and the cause took a stack trace to find. An exception raised where no human is watching needs its message more than one raised in front of a menu, not less.

### google_play: made to fail loudly, and a second bug found doing it

`config["google_play"]` is **empty** — no terms, unlike spotify's `seeds`, twitch's `categories`, tiktok's `default_hashtags`. An unanswered prompt leaves genuinely nothing to search, so the honest outcome is a refusal, not a silent success.

Adding `log.error(...)` did not work: the run still reported **completed**. `control.py` uses `logging.getLogger(__name__)` — logger `"control"` — while `run.py`'s `_ErrWatch` attaches to `"clippershq"`. **A different tree.** Every ERROR control logs is invisible to the watcher that decides whether a headless run FAILED. Logged to `"clippershq"` instead, google_play now correctly reports `failed`.

That is a general defect worth its own round: any funnel error logged through control's own logger is currently unable to fail a headless run.

## 3. The bare-swallow sweep — 135, ranked by what they hide

`scratch/bl891_sweep.py`. A *swallow* is a broad catch (`except:` / `except Exception:`) whose entire body is `pass` / `continue` / `break` / a constant return. **A handler that logs is not counted** — it made a choice and left evidence.

Ranked by what the guarded code *does*, because `except Exception: pass` around `os.remove` of a temp file is fine forever, and the same three tokens around `writer.set_run_id` hid the mechanism that makes rows attributable (BL-866). A flat count treats those as one finding.

## 4. The dead knob — measured, and the expected answer is inverted

The brief: *"It is a behaviour change, so measure what turning it on does before enabling it."*

**Measured: turning it on does nothing at all.** Three independent reasons, any one sufficient:

```
1. THE CHAIN — who passes it, who reads it
   main.py:2928  run              (ig_prescreen_followers_only)  loads=0  -> NEVER READS IT
   main.py:2014  _drain_source    (ig_prescreen_followers_only)  loads=0  -> NEVER READS IT
   main.py:1509  _ig_prescreen_ok (followers_only)               loads=0  -> NEVER READS IT

2. IS THE FUNCTION EVEN CALLED?
   _ig_prescreen_ok     called at: NOWHERE
   _ig_prescreen_full   called at: main.py:2278, main.py:2281

3. CAN THE BAND IT APPLIES EVER FIRE?
   143 distinct authors across 5 saved hashtag payloads
   carrying a follower count at hashtag level: 0 (0.0%)
   — the real user dict has is_private, is_verified, username, pk … and no follower field
```

`config["ig_prescreen_on_followers_only"]` is threaded through three layers to steer **a function no code path invokes**. The live gate already applies `_ig_prescreen_full` unconditionally — the stricter behaviour. So the right action is **deletion** of `_ig_prescreen_ok` and its three-layer parameter, a change whose measured behavioural impact is exactly zero — not enablement.

I nearly reported the opposite. An earlier pass compared `_ig_prescreen_ok` (keeps 143/143) against `_ig_prescreen_full` (keeps 8/143) and concluded "honouring the knob would cut 94.4% more before the paid call". That is wrong: the full gate is *already* what runs. Checking the call sites is what settled it, and it is the check a grep for the parameter name would never have prompted.
