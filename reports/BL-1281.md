## 1. `outputs_*` — 5.28 GB → 0.87 GB, and the rule is not an age rule

### 1.1 Why nothing had ever touched them

BL-1273 measured the mechanism and it is not neglect: `round_of_path` is **basename-only**,
so **25 of 25** top-level `outputs_*` directories **map to NO round**. `outputs_` is a prefix
its anchored regex cannot see past, and the round id in `outputs_bl1156_drop` lives in a path
component the matcher discards. Nothing owned them, so nothing pruned them, and no guard
could even see them to complain.

`tools/outputs_gc.py` therefore asks claim ownership with `claim.paths_overlap` directly
rather than through the matcher that answers 0 for 25.

### 1.2 The line the rule is drawn on

An age rule would have been wrong. Everything in these directories was between 99 and 280
hours old — inside any window the `.bak` rule would have used, so a 14-day rule frees
nothing, and a shorter one deletes a 1.8 GB directory purely for being four days old.

BL-1273 had already measured the property that makes a real decision possible:

> "The derived halves (`*__OURS.mp4`, `_frames/`, 1,902 PNGs) are **re-renderable at compute
> cost**. The exposure is the `*__ORIGINAL.mp4` downloaded source media and the paid-for
> measurement results in `_batch.json` / `_frames` manifests: re-fetching costs money,
> depends on posts still being up, and **the stored CDN urls have all expired**."

So the question is asked **per file**, not per directory: *would replacing this cost money,
or only CPU?* Measured on today's tree (`scratch/bl1281_outputs_classify.py`):

| class | files | size | what it is |
|---|---:|---:|---|
| `tracked` | 61 | 0.038 GB | committed evidence — `git ls-files` decides |
| `paid` | 150 | **0.740 GB** | `*__ORIGINAL.mp4` — money, and the urls are dead |
| `record` | 150 | 0.001 GB | `_batch.json`, README, manifests |
| `derived` | **6,213** | **4.410 GB** | `*__OURS.mp4`, `_frames/**`, 5,183 PNGs — CPU only |

**Only `derived` moves.** The 0.85 GB that costs money, or explains the money, stays exactly
where it is. No age threshold could have separated those.

Four vetoes keep a file in place whatever its class, and each is a case that actually exists
in this tree:

1. **tracked by git** — `outputs_bl1155_operator` is **22 of 22 tracked**; an all-or-nothing
   directory rule would have moved a committed README.
2. **a live claim covers the directory** — asked directly, per 1.1.
3. **PROTECTED** — `outputs_for_operator/` is what the operator opens, and is already on
   `scratch_gc.PROTECTED` for the same reason. It kept all 26 files / 124.70 MB.
4. **still being written** — the directory's newest file must be older than `--hours`
   (default 72).

The default class for an unrecognised extension is `record`, **not** `derived`: a new render
format arriving in a workspace should be a file that stays put, not one that quietly starts
being moved.

### 1.4 Quarantine, never remove — and the manifest is written first

Files moved to **`%LOCALAPPDATA%\ClippersHQ\quarantine\20260815_153917`** — outside the

## 4. `tools/commit.py` — the error path was creating the fault the tool exists to prevent

### 4.1 Reproduced, in a throwaway repo, before anything was changed

`scratch/bl1281_index_probe.py` builds a repo shaped like ours — one commit, **another
round's file already staged** — and runs the exact call `commit.py` makes:

```
staged before : theirs.txt
git add -- mine.txt outputs_bl9999_drop/big.mp4   ->  rc=1, "paths are ignored by .gitignore"
staged after  : mine.txt, theirs.txt              <-  mine.txt leaked in, and STAYED
```

`git add` is **not atomic across its pathspec**. It stages what it can, then errors on what it
cannot. So the round reports a failed commit and walks away, and the next bare `git commit`
lands `mine.txt` under someone else's name — which is precisely `b6abeee` and BL-958, the two
faults recorded in this file's own docstring. And the cause was printed **cut to 300
characters** against a real message of **308**, with git's hints ahead of the tail, so a fixed
cut loses the sentence that names the problem.

### 4.2 Three fixes, in the order they now run

1. **`ignored_untracked()` refuses before the index is touched**, naming the `.gitignore`
   file, line and pattern. Only *untracked* paths can be blocked by a rule — `.gitignore` does
   not apply to a path already in the index — and filtering by tracked-ness is what stops it
   refusing legitimate commits to files like `clip_seen.json`.
2. **A failed add prints its complete stderr and stdout**, with the character count, uncut.
3. **`restore_index()` puts our own paths' entries back** with `git update-index -z
   --index-info`. **Per-path plumbing, not a snapshot of `.git/index`**: restoring a whole
   saved index would discard whatever another round staged in the meantime — the same loss,
   caused by the repair. A hook-refused commit rolls back the same way.

After: `index_clean: True`, `leaked_into_index: none`, rc=2 with the rule named.

### 4.3 Three more defects the probe found by capturing a real run

The probe captured stdout rather than reading the source, and that is how these surfaced:

- **`print("  unclaimed : %d path(s) ...")` had no argument** and printed a literal `%d`. It
  had done so for as long as the line existed.
- Feeding paths down `--stdin` in text mode made Windows rewrite `\n` to `\r\n`; git took the
  `\r` as part of the filename, so the new guard reported **`"mine.txt\r"`** — a name matching
  nothing and actionable by nobody. Paths now go as arguments, agreeing with every other git
  call in the file.
- The `check-ignore` output parse **split the whole line on `:`** when the path is
  **TAB**-separated, so the line was dropped for being too short and **the guard silently
  never fired**. It shipped that way for exactly one probe run.

And the rollback itself was wrong on its first draft in a way only a test could catch: fed
down stdin in text mode, it re-instated an entry for `mine.txt\r` while **silently replacing a
staged version of `mine.txt` it had not created**. `test_a_previously_staged_version_of_our_own_path_survives`
is that case.

### 4.4 Held by tests

`tests/test_commit_index.py`, **8 tests, green**: the refusal leaves the index byte-identical;
a tracked-but-ignored path still commits; a real failing add rolls back exactly (including a
pre-existing staged version of our own path); the complete cause is printed; `%d` is a number;
dry run stages nothing.

The rollback test drives a **real** failing `git add` with the pre-flight stubbed out — the
pre-flight now catches the ignore case, so a test that could only reach the rollback through
that one cause would be a test of nothing.

**And the suite reproduced the shared-index fault in its own fixture on its first run**: a
bare `git commit` in a setup step swept `theirs.txt` into an unrelated commit and failed an
assertion for a reason that had nothing to do with the code under test. The fixture uses the
pathspec form now.
