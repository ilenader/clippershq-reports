## 2. `claim.py brief` runs from a clean HEAD extract

**This is the test that matters and it passes.**

```
HEAD extracted with `git archive HEAD` — no untracked files, no ignored files
$ python tools/claim.py brief          (cwd = the extract)
exit 0
  IN-FLIGHT CLAIMS  (paste into a brief)  2026-08-01 23:05
    (none -- the tree is clear)
```

`git archive` is the right instrument precisely because it is *not* the working tree: it
contains only committed objects, which is exactly what a fresh clone or a CI checkout gets.
`(none — the tree is clear)` is the correct answer there — the extract has no `.claims/`
directory, and the tool says so rather than crashing on its absence.

**Why `git status` could not have told us this.** A clean status says the working tree matches
HEAD. It says nothing about whether HEAD *stands on its own*: a tool imports fine here because
an untracked sibling sits beside it, and fails on a clone. That is how `claims_read.py`,
`publish_report.py` and `githooks/pre-commit` were each found untracked within an hour — every
one of them worked perfectly in the tree that created it.

### The test BL-923 specified already existed, and was red

BL-926 shipped `tests/test_tools_tracked.py`. It is good work — it plants an untracked file to
prove the guard fires, and it routes git through `stillness.run_checked` so a crashing git is
loud rather than an empty list that reads as "nothing untracked".

**But it was failing on arrival, and structurally so.** It asserted that *nothing* under
`tools/` is untracked, so `gen_manifest.py` — a round three minutes into writing it — turned it
red. Two of its four tests failed, including the plant test's own cleanup assertion.

That is the failure mode `claim.py`'s design docstring names in its own words: *a gate that
cannot clear in a busy tree gets skipped, and skipping it silently is worse than not having
it.* A suite that goes red whenever anybody is mid-write teaches people to ignore a red suite —
and this tree has a dozen concurrent rounds.

**Fixed with the registry the tools already maintain**, rather than an allowlist that would rot:

| state | verdict |
|---|---|
| untracked **and declared by a live claim** | a round working — **reported, allowed** |
| untracked **and claimed by nobody** | an orphan with no owner and no plan — **fails** |

```
  in-flight (untracked but CLAIMED, not a defect): tools/gen_manifest.py [MEMEBOT-055]
```

The plant test still proves the guard fires, because a planted file is unclaimed by
construction — which also proves the exemption cannot swallow a real orphan. `_claim_owner`
reads `.claims/` directly rather than importing `claim.py`, so the suite keeps working when the
very tool it guards is the broken thing.

**Three tests added:** the coordination symbols pinned **by symbol, not by file** (`claim.py`
was tracked the whole time while four of its functions were not, so a file-level check saw
nothing wrong); `claim.py brief` from a HEAD extract; and every committed tool importing from
one. 7 tests, all green.

## 4. The inversion, recorded as a rule

`docs/TESTING.md` §5 — **"I cannot see it" must not look like "it is not there."**

`verify_claims` resolved every claim against the parent repo's HEAD. `memebot/` is its own
git repository, gitignored by the parent, so a memebot path could never be a blob there. Every
MEMEBOT claim returned **"not committed at HEAD"** — character-for-character what a
**fabricated** claim returns.

**The obvious reading is wrong, and that is why it is written down.** Detection was not
*weakened* on the audio and render path — it was **inverted**. Every honest claim looked like a
phantom, so the output carried **no information in either direction**: a pass was unavailable,
and a failure meant nothing. Measured when the resolver was fixed: **4 of 13 manifests changed
verdict, two going from zero verified to fully verified.**

The rule generalises past this bug: any checker with a lookup step must separate *found and
matching*, *found and not matching*, and **could not look** — and the third must never share a
return value with the second. An unreachable repo, a missing tool, a permission error and a
network timeout all belong in that third row. `publish_report.py` already gets this right: a
**missing** secret scanner refuses the push rather than counting as a clean scan, because *an
absent gate is not an open gate*.

## 5. The text-mode trap, recorded as a rule

`docs/TESTING.md` §3b — **a test must not perturb a file it does not own.**

BL-921 appended a marker to `memebot/scraper/edit.py` to prove the checker reads HEAD rather
than the working tree, then restored it. It read in text mode (universal newlines collapse
`CRLF` → `LF`) and wrote back in text mode (`LF` → `os.linesep`), so the restore **silently
rewrote every line ending in a 118 KB file another round owned**. `git status` showed it
modified with a **zero-line diff** — the content identical, every line terminator changed.

The doc gives the pattern with the part that actually matters: a closing assertion that the
file is byte-identical afterwards. Without it the restore is a hope, and in a tree with a dozen
concurrent writers the damage lands in someone else's diff.

### On the campaigns hash — two encodings, one unchanged object

The brief quotes `7a029ee5447cddd8`; earlier rounds quoted `8e02f8d6f6307ae8`. **Both are
correct and the campaigns have not changed.** They are two encodings of the same object:

```
sha256(json.dumps(campaigns, sort_keys=True))                        = 8e02f8d6f6307ae8
sha256(json.dumps(campaigns, sort_keys=True, separators=(',', ':'))) = 7a029ee5447cddd8
```

Flagged because a changed fingerprint for an unchanged object is exactly the kind of thing that
gets read as drift and triggers an investigation into nothing. Whichever is adopted, it should
be quoted **with its encoding**, the same way a suite count has to be quoted with its discovery
rule.
