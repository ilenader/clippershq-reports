## 1. WHAT WAS ORDERED vs WHAT WAS TRUE

### The memebot carve-out cannot work, for two independent reasons

BL-859 recommended appending four lines after `.gitignore:137`:

```
!memebot/**/*.py
!memebot/**/*.yaml
!memebot/**/*.yml
!memebot/**/*.md
```

**Reason one — the four lines are a no-op.** Git does not descend into an *excluded
directory*, so a negation for a file inside it is never even considered. `gitignore(5)` says
it outright: *"It is not possible to re-include a file if a parent directory of that file is
excluded."* Applied verbatim and tested:

```
$ git check-ignore -v memebot/scraper/duck.py
.gitignore:137:memebot/    memebot/scraper/duck.py      # still ignored
```

The shape that *would* work excludes the contents and re-includes the directories
(`memebot/**` + `!memebot/**/`), so git keeps descending.

**Reason two — and this one is fatal: `memebot/` is its own git repository.** Its own
`.git`, its own remote (`github.com/ilenader/memebot.git`), its own history at `22aaf12`.
The parent can only ever record it as a **gitlink**:

```
$ git add -n memebot/
warning: adding embedded git repository: memebot
```

A gitlink stores a commit pointer no clone can fetch. memebot's files can never be blobs in
the parent repo, **at any `.gitignore` setting**. `verify_claims.py` reads
`git show HEAD:<path>` against the parent, so MEMEBOT claims were never verifiable from
there and never would have been.

**`.gitignore` is therefore unchanged for memebot.** Reverted after testing.

### What actually fixes it — two changes, both proven

**(a) Commit memebot's work in memebot's own repo.** 2,276 lines across eight files had no
git object at all: `duck.py` (693 lines) and its 502-line suite were untracked outright;
`edit.py` and `config.yaml` carried four rounds of uncommitted work. → `memebot@dbbaae1`,
pushed.

**(b) Teach `verify_claims.py` that a nested repo answers for its own files.**
`_nested_repo_for()` walks a path's directories, finds the owning repo, and resolves against
*its* HEAD. Applied to the two places that ask git what exists — `head_text` and
`check_file`. Ordinary paths take the original code path untouched.

**Proven in both directions, which is the only proof that means anything.** A verifier that
passes everything is worse than none:

| Fabricated claim | Result |
|---|---|
| `func memebot/scraper/duck.py::this_function_was_never_written` | **FAIL** |
| `const memebot/scraper/duck.py::FABRICATED_CONSTANT` | **FAIL** |
| `file memebot/scraper/no_such_file.py` | **FAIL** — "NOT committed at HEAD of memebot/" |
| `func memebot/scraper/duck.py::resolve_treatment` (real) | **OK** |

**And it caught a live false claim within a minute of landing.** MEMEBOT-025 — another
round's manifest, written today — claims `window_key` in `clippershq/song_loudness.py`. The
name appears in a comment and is never defined. The tool reports:

> `no def/class window_key in clippershq/song_loudness.py at HEAD — a comment mention is not a definition`

That is the guard working on live work, which is the whole point of restoring it.

## 4. THE SECRET SCANNER FIX

Rule 1 searches a report for every string leaf in `config.json`. Most config values are
ordinary filenames, so it blocks publication over things like the clip-seen cache. That
blocked BL-859 — which had to name the file by its config *key* to publish — and it blocked
**this round's own `.gitignore` commit** an hour later, on `caption_finder.seen_cache_file`.
Two rounds, one rule, one shape.

The fix is the one BL-823 already wrote for the opaque-literal rule: **`_is_repo_path()`,
reused**. Unchanged; only moved above its new caller.

| Proof (`scratch/bl865_prove_scanner.py`, real scanner as a subprocess, exit codes only) | |
|---|---|
| Filename from config — the exact BL-859 blocker | **ACCEPTED** (exit 0) |
| A live credential from the `ig_api` secret block | **CAUGHT** (exit 1) |
| …and reported by the SECRET BLOCK rule, which has no exemptions | **CAUGHT** |
| Credential-named assignment | **CAUGHT** |
| Path-shaped literal for a file that does not exist | **CAUGHT** |

**Two limits, asserted in the proof rather than glossed:**

- The exemption is **existence-based**. A config value naming a cache that has never been
  created is still blocked — the caption-finder seen-cache is exactly that case and is *not* fixed.
  Loosening to "ends with `.json`" would exempt on **shape instead of existence**, which is
  the prefix-allowlist weakness BL-823 replaced. It stays strict.
- **BL-829's standing warning applies, and this round produced fresh evidence for it.** The
  note says a *fourth* narrowing should replace the `>=12-char` heuristic outright rather than
  carve another exception. This is that fourth narrowing, and within the same hour it hit a
  class it does **not** fix — multi-word `ig_niche_keywords` in a mood map. **The heuristic,
  not its exemption list, is what needs replacing next.**

I also caught myself committing a hardcoded fake credential as a test fixture (`4c984d5`
fixes it): a credential-*shaped* literal in the repo trips every future scan of that file and
makes the next reader stop and check whether it's real. Assembled at runtime instead.
