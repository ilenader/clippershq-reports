# BL-1013 — the lifetime cap failed open 50x; it now refuses

`clip_pipeline._ledger_total` returned `0.0` when the ledger could not be read, and
`resolve_budget` computes `lifetime_room = cap − _ledger_total(...)`. So **an unreadable
ledger read as "nothing has ever been spent" and handed back the full cap.**

| ledger | true room | armed |
|---|---|---|
| readable, $9.90 of a $10 cap spent | **$0.10** | $0.10 |
| **unreadable** | $0.10 | **$5.00 — 50×** |

Silently, and most likely *precisely* when another round is mid-write on the file. It is
the ~18th instance of empty-reads-as-a-clean-zero in this project and the first on the money
path. **Fixed:** an unreadable ledger now raises `LedgerUnreadable` and the run refuses.

---

## 1. The trap in the fix, found before writing it

`resolve_budget` already wrapped the subtraction:

```python
try:
    lifetime_room = round(float(lifetime_cap) - _ledger_total(spend_path), 6)
except (TypeError, ValueError):
    lifetime_room = None
```

**Raising `ValueError` or `TypeError` would have been caught right there** and turned into
`lifetime_room = None` — which drops the lifetime bound *entirely*. That is the same
fail-open with a different spelling, and it would have looked like a fix.

So `LedgerUnreadable` subclasses **`RuntimeError`**, outside every handler on this path, and
the subtraction was moved out of the `try` so the intent is legible. A test asserts the
class relationship directly:

```python
self.assertFalse(issubclass(CP.LedgerUnreadable, (TypeError, ValueError)),
                 "LedgerUnreadable would be absorbed by resolve_budget's own except "
                 "clause and the lifetime bound would silently vanish")
```

The old handler is kept for what it was actually for — a **cap** that is not a number, a
config typo — and a test proves that path still degrades rather than raising.

**A missing file raises too, deliberately.** On this path "the file that records spending is
absent" is not a fresh start; it is the exact condition being closed.

## 2. BL-1003's pinned assertion, flipped

BL-1003 could not fix this (the file was held) so it left a **failing-when-fixed** assertion
in `tests/test_vision_failure_reason.py::TheCapMustNotFailOpen`, asserting the defect:

```python
self.assertGreater(gone["run_budget_usd"], near["run_budget_usd"],
    "if this no longer holds, _ledger_total has been fixed … update this test and say so")
```

It is now `test_an_unreadable_ledger_REFUSES_rather_than_granting_the_cap`. There is no
`gone` value at all — refusing is the only honest answer to an unknown total.

**Green for the right reason**, and that is asserted rather than assumed:

* the **readable** case is asserted **first** and still returns `$0.10`, so a fix that
  simply broke everything cannot pass;
* a **truncated** ledger (`{"total_spent_usd": 9.9` — the shape a concurrent write actually
  produces) is tested alongside the missing one;
* the second test pins the swallowing trap above.

## 3. Proven on a real run, with the check named

Refusal alone is not evidence — a run can stop for a dozen reasons. `scratch/bl1013_realrun.py`
asserts the **type**, the **message**, and the **traceback path**:

```
1. CONTROL   readable ledger -> run_budget $0.10        PASS (the fix did not break it)
2. MISSING      -> LedgerUnreadable  "cannot be opened … refusing to compute a budget"
   TRUNCATED    -> LedgerUnreadable  "is not valid JSON … refusing to compute a budget"
   WRONG SHAPE  -> LedgerUnreadable  "no readable total_spent_usd … refusing"
3. run_batch(n=1, spend_path=<truncated>) -> LedgerUnreadable
     PASS  traceback runs resolve_budget -> _ledger_total  (the NAMED check fired)
     PASS  it is NOT UncappedRun — a different guard with a similar outcome
4. UNDER THE OLD CODE, all three: lifetime_room $10.00, run_budget $5.00 — 50x
```

`run_batch` was called with **both fetchers injected**, so nothing could reach the network,
and an `AssertionError` fixture would have fired had the run reached retrieval — it did not.
The live `spend.json` sha is asserted **identical before and after**: `5a3d658d53764d3e`.

## 4. `vision_calls` now lands on the ledger

`scratch/bl872_label.py::record_vision` passed `vision_usd` and **not** `vision_calls`, which
`record_aux_spend` defaults to `0`. Every vision row therefore read **`calls=0` beside real
dollars**, and any cost-per-call derived from the ledger was wrong — in the *cheap*
direction, which is how a spend estimate gets trusted.

`record_vision(cost, calls=1)` now passes it. Proven on a **temp** ledger:

```
vision_calls   1
vision_usd     0.0123
cost per call is now derivable: $0.0123
```

The count does not *price* the spend — OpenRouter bills per token, which is why BL-887 added
a dollars parameter. It makes the spend **divisible**.

**`resolve_budget`'s cap handler is still permissive and I left it that way.** A cap that is
not a number degrades to *no* lifetime bound. That is only safe because `run_batch` refuses
when the budget is `None` **and** `spend_path` is set — **the safety is one layer up, not
here.** If that refusal is ever removed this becomes the same defect. Named rather than
changed, because tightening it is a behaviour change to a config path this round did not
measure.

### The mechanical cross-check caught what my hand list missed

I wrote the hand-read list first and then ran an AST pass for money-named functions whose
`except` branch returns a bare number. It found **16 sites, and one of them was production
code my list did not name**: `run.py::_spend_now`, which returns `0.0` on an unreadable
ledger.

It turns out to be **reporting, not a cap** — its three uses all feed `spend_usd` into a
status record, so an unreadable ledger makes a run *report as free* rather than arming more
money. Exposure $0. But I would have published a sweep that omitted it, and the only reason
I did not is that the mechanical pass disagreed with me. The reconciled count is now **0
unnamed sites**.

Two of the sixteen are **snapshot copies of `clip_pipeline.py`** under `scratch/mb089_head`
and `scratch/mb095_head` that still carry the old `_ledger_total`. They matter only if
somebody runs a snapshot as if it were live.

### The regression I caused, and the one I inherited

`test_the_binding_cap_is_the_smaller_of_the_two` passed `spend_path=os.devnull` as a
shortcut for "no ledger to speak of". Under this fix devnull reads as an empty file — an
unreadable ledger — and now raises. **That is the fix working**, but it was a real break in
a green suite and I caused it.

The fixture now says what it always meant: a ledger recording **zero spent**. The test's
subject is the `min()` arithmetic; its ledger content was never the point. I checked before
changing it that **`os.devnull` appears nowhere in `clippershq/` or `tools/`**, so nothing
real depended on the old leniency — changing a test to fit the code is only defensible when
the test was expressing something it did not mean, and that is checkable, so I checked it.
A second test in that file now pins the distinction so a later tidy-up cannot reintroduce
the shortcut.

**And one I have to own from an earlier round.** `test_secret_scanner` is flagging a real
talent-agency address belonging to a real lead, inside `scratch/bl961_messages_clipper.txt`,
**a file I committed in BL-961**. (The address is not reproduced here — the publish scanner
rejected an earlier draft of this very paragraph for quoting it in masked form, which is the
guard working on the round that is describing the guard.) BL-961's *report*
carefully redacted a different address; the committed *artifact* got no such care, and the
two should have had the same rule. It sits in the private parent, whose purpose is lead
data and which already holds 59,006 addresses in `master_leads.csv`, so this is not an
escalation — but it is the kind of thing that is only harmless until an artifact moves.
