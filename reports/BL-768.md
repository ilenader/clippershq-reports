## 1. The suppression layer

A new pure module, `send_suppress.classify(email, handle, name, *, mx, last_post_date, date_sent)` returning `{exclude, reasons, flags}`, called from `writer.bot_ready_rows` — which already builds a per-lead candidate dict, so this is not a new pipeline stage.

| rule | treatment |
|---|---|
| dead MX / no MX route | **hard exclude** |
| **orphan — no master row** | **hard exclude** (new) |
| role inbox | exclude by default, `send_exclude_role` toggle |
| **agency** | **include + flag** — for a big creator the manager *is* the contact |
| >180 days | flag, never exclude |
| `date_sent` non-empty | exclude — available only after §4 |

**The MX table must be allowed to say "unknown".** `bl763_mx.json` covers 141 domains and is a concurrent artifact. Domain-not-in-table means unknown, never dead. This is BL-765's point restated as a rule: suppression removes the **certain** bounces — **1.2% is a floor, not the observed ~10%** — and the rest cannot be established without sending.

**`letsencrypt.org` is in the send list**, and is the only address matching two master rows. A certificate authority scraped off a website is not a lead.

## 2. How the agency flag reaches the file

The flag is derivable everywhere and written nowhere. Three options, one correct:

| option | verdict |
|---|---|
| backfill `email_quality` across 57,386 rows | **no** — a 23 MB rewrite to persist a pure function of columns already present, stale the moment a handle changes |
| set it in `email_finder.py`, where `?verify-third-party` lives | **no** — that path is list-driven mode only, which is precisely why 0 crawl rows carry it |
| **compute at export time in `bot_ready_rows`** | **yes** |

`looks_agency(email, handle, name)` needs three inputs and **all three are already inside the candidate dict** (`email`, `_handle`/`_ig`, `display_name`). One call per exported row — 1,618, not 57,386.

So the answer is that the flag is computed where the file is written and never stored. `email_quality` stays empty deliberately: a derived value with no owner is exactly how it reached 0-of-57,386.

## 4. The bulk outcome marker — one correction to the brief

The brief is right about the write and wrong about the read. Looping before writing fixes the 23 MB rewrite, but **`match_indices` re-scans all 57,386 rows for every key.**

| approach | measured on the real files |
|---|---|
| `match_indices` per key × 1,618 | **73.1 s** CPU (0.045 s/key) |
| one email→indices index, then look up | **0.04 s** |

So: **reuse `apply_outcome`, `normalize_outcome`, `_valid_date`, `filelock`, the timestamped backup and the atomic `os.replace` — every one validated — but do not reuse `match_indices` in a loop.** Build the index once, inside the lock.

```
mark_sent_from_csv(master_csv, export_csv, *, date_sent, channel="email",
                   dry_run=False) -> {keys, matched, updated, unmatched[], ambiguous[], backup}
```

**`dry_run` is not optional.** The first real use stamps 1,618 rows. On today's files the preview reads **1,610 matched · 8 unmatched · 1 ambiguous** — and those 8 are the ghosts. `record_outcome` already refuses to write on an ambiguous key; the bulk version must do the same per key and return the list rather than guess.

One function plus a menu entry beside `[o]`. No schema change — the seven outcome columns already exist.

## 5. Keeping the export current

The root cause is not a bug: **`all_bot_ready.py` is never invoked from the Control Panel.** It is a working CLI script nobody runs — hence a file two weeks old and one column behind its own contract. It already asserts its header against `BOT_READY_COLUMNS` rather than a hardcoded width (`all_bot_ready.py:131-136`), so regenerating repairs the drift by itself.

- Wire it to a menu entry; regeneration is idempotent and derives wholly from master.
- `ALL_BOT_READY.meta.json` currently records `"timestamp": "derived-from-master"` — **a literal string, not a timestamp.** Put the real generation time and master row count there.
- Have the marker refuse, or loudly warn, when the export predates master's last write. That is the exact condition that produced the 8 ghosts.
- **`LATEST_BOT_READY.csv` holding 2 rows is working as designed** — by contract it is the newest *run's* emailable editors, and the last run produced two. The hazard is that a sender would reasonably aim at it.

## Order — smallest change first

| # | change | size | why here |
|---|---|---|---|
| **1** | **Run the existing `all_bot_ready.py`, wire it to the menu** | **zero new logic** | Fixes staleness, the 4-vs-5 drift and the 8 ghosts at once. Everything below operates on what it produces. |
| **2** | **`mark_sent_from_csv` + menu entry** | one function | Precondition for "already sent", and the only step that makes sending measurable. |
| **3** | **Widen `BOT_READY_COLUMNS`** (append-only) | ~10 lines | Five of nine columns already computed and thrown away. |
| **4** | **`send_suppress.classify`, applied in `bot_ready_rows`** | one pure module | Needs a fresh file (1) and `date_sent` (2). Removes 4.4% with certainty. |
| **5** | **Freshness guard in meta + marker** | small | Stops step 4 quietly running on a stale export again. |

**Step 1 is free and should happen before anything is built.** The file on disk is the wrong shape, two weeks old, and contains rows that no longer exist.

## Limits

- **Suppression cannot reach the observed ~10% bounce.** It removes 1.2% certain dead MX plus 0.5% ghosts; role exclusion is a reputation choice, not a bounce fix. Closing the gap needs real send data — which step 2 produces.
- **The MX table is a 141-domain snapshot** from a concurrent round and may already have moved.
- **Agency detection is heuristic and unverified by hand** — 27 here versus BL-765's 26, and it flags `outlook.com` on one row via a local-part rule. Plausible, but worth an eyeball before the flag drives behaviour.
- **The 101 over-180-days figure is carried from BL-765**, not recomputed, because the fields it needs are export-time derivations rather than master columns.
- **Nothing was implemented or executed.** The 73.1 s and 0.04 s figures are timed reads against the real master; no write was performed anywhere.
- **The 4.4% net-suppression figure describes today's stale export.** Regenerating (step 1) will change it, probably downward, since the 8 ghosts disappear by construction.
