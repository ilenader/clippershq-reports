# BL-665 — Why captionPresent is false on every shadow row

## VERDICT (one line): captionPresent is false because the caption never reaches the extractor: for TikTok the live provider (LamaTok) fetches the full item, which DOES contain the caption, but drops it at the provider boundary because the LamaTok `ClipStats` object carries no `raw` field (so `fetchedRawMeta = stats.raw = undefined`); for Instagram the caption IS captured when the Apify actor answers, but the submit path relies on that flaky actor (Hiker is deliberately skipped), so a transient Apify miss at submit time leaves `raw` null. The extractor and the rule engine are fine; the metadata is lost upstream.

**2026-07-24 · AUDIT ONLY. READ ONLY.** No code, data or config change; nothing fixed. Live read-only provider probes were run and are disclosed below with costs; no Apify actor was invoked beyond the app's own submit-path fetch (which is what production runs), one call per media item, captions and handles redacted. A markdown-only diff cannot change tsc or build, so none was run.
**Base:** origin/main `5c667b25` · **Branch:** checkpoint/BL-665 · isolated worktree, no node_modules junction.

## Live-measured starting point
`rule_shadow_decisions` now holds **8 rows: 5 instagram, 3 tiktok, every one `captionPresent=false`, `soundIdPresent=false`** (first 16:09, last 17:58 UTC, `::text`). The 3 TikTok clips are all `vm.tiktok.com` short links; the 5 Instagram clips are `/reel/` URLs.

## PART 1 — the real submit payload, one platform at a time (probed live)

### Provider disclosure and cost
I called the app's own provider functions read-only on real clip URLs pulled from the DB. **TikTok:** `fetchLamatokTiktokByUrl` on 4 URLs (LamaTok, about $0.001 each). **Instagram:** `fetchClipStats(url, {skipHikerOverlay:true})` on 6 reels (this is the exact submit-path call; it runs the Apify `api-scraper` actor, roughly a fraction of a cent per run) plus one direct HikerAPI call. **YouTube:** no probe (no `YOUTUBE_API_KEY` is set; diagnosed from code). Total spend a few cents; no profile endpoint was hit twice.

### TikTok (LamaTok is the live provider; default `SCRAPER_TIKTOK_PROVIDER` resolves to `lamatok`)
Probing the exact vm-short clip from a shadow row, the LamaTok response IS complete:
```
lt.raw top keys: [ ... desc, music, challenges, contents, textExtra, createTime, video, author ... ]
  raw.desc            len 57      <- the caption
  raw.music.id        present     <- the sound id
  raw.challenges[0].title         <- a hashtag
extractClipMetadata(lt.raw): captionPresent=true, soundIdPresent=true, hashtags=1
```
**The caption, sound id and hashtags are all present in `lt.raw`, and the extractor reads them correctly.** But the object handed to the submit path is `lt.stats`, not `lt.raw`, and:
```
lt.stats keys: [views, likes, comments, shares, createdAt, platform]   ("raw" in lt.stats = false)
```
All 3 exact vm-short shadow clips resolved cleanly (`verdict=ok`, views 464 / 273 / 1311), so this is NOT a short-link resolution failure. **The caption is fetched and then thrown away.**

### Instagram (submit path uses Apify `api-scraper`, because `skipHikerOverlay:true` skips Hiker)
This is the surprise that overturns the prior hypothesis. Probing the **exact 5 Instagram shadow clips** through the exact submit-path call, right now:
```
all 5 -> provider=apify-instagram-api, statsNull=false, rawPresent=true, captionPresent=TRUE (capLen 680 to 1545)
IG caption capture on the exact 5: present=5, absent=0
```
So **`skipHikerOverlay:true` does NOT mean Instagram captures nothing.** Apify's `api-scraper` serves the caption at submit, and the extractor reads it via `r.caption`. The stored rows are false because at their submit moment (16:45 to 17:58) the Apify actor returned null (it is slow and flaky), so `fetchedRawMeta` was null; by probe time it had recovered. **Instagram's caption gap is provider reliability, not extraction.** The Apify IG `raw` structure:
```
raw top keys: [ ... caption, hashtags, mentions, timestamp, videoDuration, musicInfo, ownerId, displayUrl, audioUrl ... ]
  caption  -> read by extractClipMetadata (works)
  musicInfo.audio_id = <redacted 15-digit id>  -> the sound id, PRESENT
```
**The Apify raw is not a summary; it is the full item and it contains the caption.** BL-663's "summary not full item" hypothesis is disproven for the live provider.

### The Instagram nested-sound question, settled
BL-663 guessed the sound lived at `clips_metadata.music_info.music_asset_info.id`. **That path is absent** in the Apify provider's raw. The sound id is actually at **`raw.musicInfo.audio_id`**, and `extractClipMetadata` reads none of `r.musicInfo?.audio_id` (its list is `r.music?.id, r.musicId, r.musicMeta?.musicId, r.music_info?.id, r.music?.mid, r.soundId, r.audio?.id`). So even when the IG caption is captured, the **sound id is silently missed because the extractor reads the wrong key**, a separate real bug.

### YouTube (diagnosed from code; no key set, so nothing to probe)
`fetchClipFreshnessWithRetry` builds the YouTube stats as `{ views, likes, comments, shares, createdAt, platform }` with **no `raw` field** (`apify.ts:2440`), so `fetchedRawMeta` is always null for YouTube regardless of anything else. And `YOUTUBE_API_KEY` is unset, so `getYouTubeVideoDetails` returns null anyway. Even with a key, `getYouTubeVideoDetails` fetches view/like counts, not the snippet (title, description, tags), so the caption is not fetched at all today.

## PART 2 — where exactly it breaks, per platform and per field

| Platform | Field | Status | Precise break (file:line) |
|---|---|---|---|
| TikTok | caption | present, then DISCARDED | LamaTok builds `ClipStats` with no `raw` (`lamatok.ts:309-317`); `fetchTikTokStats` returns `lt.stats`, not `lt.raw` (`apify.ts:438`); so `fetchedRawMeta = stats.raw` is undefined (`clipper-submit-core.ts:158`) |
| TikTok | sound id | present in `lt.raw.music.id`, discarded by the same line | same as caption (`apify.ts:438`) |
| Instagram | caption | present when Apify answers, NULL on a transient Apify miss | provider reliability of `api-scraper` inside `fetchInstagramStats`; the extractor and `r.caption` key are correct |
| Instagram | sound id | present in `raw.musicInfo.audio_id`, but read with the WRONG key | `extractClipMetadata` sound-key list omits `musicInfo.audio_id` (`campaign-rules.ts:153-156`) |
| YouTube | caption | never fetched, and no `raw` attached | stats built without `raw` (`apify.ts:2440`); snippet not requested in `getYouTubeVideoDetails`; `YOUTUBE_API_KEY` unset |

So per the brief's four categories: TikTok = present-but-discarded-before-extraction; Instagram caption = present-but-intermittently-absent-from-the-provider; Instagram sound = present-but-extractor-reads-wrong-key; YouTube = absent-from-the-response.

## PART 3 — what it would take to fix, per platform (no new vendor call except YouTube)

**TikTok (the dominant, deterministic fix, unblocks the most).** Attach the already-fetched raw to the TikTok result: add `raw` to the LamaTok `ClipStats` (`lamatok.ts:309`) or return `lt.raw` alongside `lt.stats` from `fetchTikTokStats` (`apify.ts:438`), then let `clipper-submit-core.ts:158` read it. **No new vendor call** (BL-552 confirmed, and the probe proves the desc, music.id and challenges are already in `lt.raw`). This fixes caption, sound id and hashtags for every TikTok clip that LamaTok resolves, deterministically.

**TikTok short links, corrected.** BL-663 stated 69% of TikTok links are `/t/` short links that 500 on `by/url`. Measured here: of 1,065 TikTok clips, `/t/` = 64 (6.0%), `vm.tiktok.com` = 165 (15.5%), canonical `/video/` = 271 (25%), other 565. **LamaTok resolved all 3 `vm.tiktok.com` shadow clips cleanly**, and only the one `/t/` link I tried returned 404 (which may be a deletion, not a format problem). So short-link resolution is a **minor, ~6% edge (the `/t/` form)**, not 69%, and the raw-drop is the real TikTok cause. If `/t/` resolution is wanted, do it as a **backfill** (resolve the redirect to canonical, then re-probe), not at submit, to avoid adding a redirect round-trip and a second provider call to the hot submit path; cost is one HEAD/GET redirect per `/t/` clip plus one provider call, only for the ~6%.

**Instagram.** Two separate fixes. (1) Sound id: add `r.musicInfo?.audio_id` (and defensively the artist/song fields) to the `extractClipMetadata` sound-key list (`campaign-rules.ts:153-156`); **no new vendor call**, the id is already in the raw. (2) Caption reliability: the caption already arrives when Apify succeeds, so the gap is the flaky actor. The cleanest reliability fix is to also read metadata from HikerAPI (which returns `caption.text` fast and does carry the sound), while keeping Apify for the freshness `createdAt` the age-check needs; that is why `skipHikerOverlay:true` exists (BL-137: Hiker returns `createdAt:null`). This is a provider-composition change, not an extraction change, and needs no NEW vendor if Hiker is already called on the tracking path; at submit it would add one Hiker call per IG clip. **State plainly: the IG caption is genuinely returned by the current provider; the fix is to stop losing it on a transient, not to fetch something new.**

**YouTube.** The caption/title/description is NOT fetched today. Fix: request `part=snippet,contentDetails` in `getYouTubeVideoDetails` and attach the item as `raw`. The YouTube Data API is free within quota, so about $0 at roughly 2,300 clips a month, only a quota cost, plus a key must be set (`YOUTUBE_API_KEY` is currently unset). This is the one platform that genuinely needs a field added to a call.

## PART 5 — verdict and fix spec, ranked by what it unblocks

**ONE LINE:** captionPresent is false because the caption is lost before extraction, chiefly by the TikTok provider dropping its full item (`raw`) and secondarily by Instagram's submit relying on a flaky Apify actor; the extractor and rule engine are correct.

| Rank | Fix | File:line | What it unblocks | Proof required | Rollback |
|---|---|---|---|---|---|
| 1 | **Attach LamaTok `raw` to the TikTok result** | `lamatok.ts:309` add `raw` to `ClipStats`, or `apify.ts:438` return `lt.raw`; consumed at `clipper-submit-core.ts:158` | Caption + sound + hashtags for EVERY resolvable TikTok, deterministically. Biggest unblock: it is a hard bug affecting 100% of TikTok, versus IG's intermittent one | Re-probe a live TikTok submit and confirm the shadow row now has `captionPresent=true`; confirm `stats.views` unchanged (money path untouched) | Revert the one-field add |
| 2 | **Add `musicInfo.audio_id` to the extractor sound keys** | `campaign-rules.ts:153-156` | Instagram sound id (a `REQUIRED_SOUND` rule could never fire on IG without it) | A unit check that `extractClipMetadata` on the probed IG raw returns `soundIdPresent=true` | Revert the key-list add |
| 3 | **Make Instagram caption capture reliable** (read metadata from Hiker while keeping Apify for `createdAt`) | `fetchInstagramStats` / the `skipHikerOverlay` decision in `apify.ts:2459` | Turns IG caption from intermittent to consistent | Measure IG `captionPresent` rate over a day of submits before and after | Restore `skipHikerOverlay:true` |
| 4 | **YouTube: fetch `part=snippet` and attach `raw`, set the key** | `getYouTubeVideoDetails` + `apify.ts:2440` | YouTube caption/title/tags (currently zero) | Confirm a YouTube submit yields a non-null caption; Data API quota cost only | Revert the part flag; unset behaviour is byte-identical |

**Ranked by unblock:** fix 1 alone converts every TikTok submit from captionless to fully captured and is a small, reversible, money-neutral change, so it unblocks the most for the least risk. Fixes 2 and 3 complete Instagram. Fix 4 is only needed if YouTube clips are to be judged by caption rules. **Build nothing here; this is the spec.**

## What is UNKNOWN or could not be measured
- **The exact Instagram Apify failure rate at submit.** The 5 stored rows were false and my 5 re-probes were all true, so the miss is real but its frequency is unmeasured; it needs a day of submit-time logging of `captionPresent` per IG clip.
- **Whether `/t/` short links fail on format or were simply deleted.** One `/t/` probe returned 404; `vm` links resolved. A larger `/t/` sample would settle it, but `/t/` is only ~6% and not the main cause.
- **YouTube raw shape**, since no key is set to probe it; the fix is inferred from the Data API contract, not observed.
