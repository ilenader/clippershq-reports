## PART 1 — the TikTok fix

### The bug, confirmed

BL-665 located it exactly. `fetchLamatokTiktokByUrl` builds a `ClipStats` at `lamatok.ts:309-317` out of `views/likes/comments/shares/createdAt/platform` and returns it alongside the full payload as a **separate** `raw` field. `fetchTikTokStats` then returned only `lt.stats`. `ClipStats.raw` is optional, so nothing complained; it was simply always `undefined`. At `clipper-submit-core.ts:158` the submit path does `fetchedRawMeta = (stats as any)?.raw ?? null`, which meant TikTok always evaluated against `null`, and every one of the 44 live shadow rows recorded `captionPresent=false`.

### Why the fix is opt-in and not an unconditional attach

The obvious fix is to attach `raw` inside `lamatok.ts`, or unconditionally at `apify.ts:438`. I did neither, because `fetchClipStats` has three kinds of caller and only one of them should see this:

| caller | today | with an unconditional `raw` |
|---|---|---|
| tracking cron (money path) | no raw | every TikTok stat object drags a full payload through the batch loop |
| `clip-thumbnail.ts:289` | no raw → returns `scrape-empty` | `extractCoverUrl(stats.raw, "tiktok")` starts succeeding → **new `Clip.thumbnailUrl` writes → new images rendered to clippers** |
| submit path | needs raw | fixed |

That second row is the one that matters. An unconditional attach would have silently changed what clippers see, which this round forbids. So the carry-through is an **opt-in**:

• `fetchTikTokStats(videoUrl, options?: { includeRawMeta?: boolean })`
• `fetchClipStats(clipUrl, options?: { skipHikerOverlay?: boolean; includeRawMeta?: boolean })` passes `options` straight through
• `fetchClipFreshnessWithRetry` — the submit path, whose only caller in the entire repo is `clipper-submit-core.ts:138` — sets `includeRawMeta: true`

Nothing else in `src/` or `scripts/` sets it.

### Proof it adds a field and alters nothing else

**Shape.** `ClipStats.raw?: any` already existed (`apify.ts:291`) and the Instagram path has always populated it (`apify.ts:585, 777, 875`). So a `ClipStats` carrying `raw` is not a new shape to any consumer; it is the shape Instagram has always produced. Only three places in `src/` read `.raw` at all: `clipper-submit-core.ts:158` (the intended consumer), and `clip-thumbnail.ts:295 / :298` (which never opts in).

**Numbers.** The new object is `{ ...lt.stats, raw: lt.raw }` — a spread of the same object literal built at `lamatok.ts:309-317`, with one added key. `lt.stats` is never mutated, so the admin `lamatok-shadow` route sees exactly what it saw before. No view, like, comment, share, createdAt or platform value is read, recomputed or written on this path.

**The money path cannot see it.** `tracking.ts` touches `stats.views`, `stats.likes`, `stats.comments`, `stats.shares` and nothing else; it never spreads or serialises the object, and it never calls `fetchClipFreshnessWithRetry`. `tracking.ts` is byte-identical by blob OID (below).

## PART 2 — the Instagram sound key

BL-665 probed the live Apify `api-scraper` payload and found the identifier at **`raw.musicInfo.audio_id`** — camelCase container, snake_case leaf. The extractor's key list at `campaign-rules.ts:153` contained `music_info?.id` but not that path, so IG sound ids came back null even on rows whose caption arrived fine.

The new keys are **appended after** the existing ones, never inserted among them. `firstString` returns the first non-empty value, so every payload that already resolved a sound id resolves to the same id it did before. This can only turn a null into a value.

What I did instead:

## PART 3 — persist what was already fetched and thrown away

Four additive nullable columns on `rule_shadow_decisions` (never on `Clip` — BL-662 was right that machine signals do not belong in the money model):

```prisma
hashtags      String[]
postedAt      DateTime?
durationSec   Int?
source        String?
```

`caption` and `soundId` already existed from BL-659, so all five requested fields are now stored.

A new exported `extractClipExtras(raw)` in `campaign-rules.ts` reads the post timestamp and the duration out of the **same** payload. It is deliberately a separate function rather than a widening of `ClipMetadata`, because `ClipMetadata` is the evaluator's input type and `evaluateRuleShadow` / `composeReviewerNote` must keep being handed exactly what they were handed before. **No verdict reads these values.**

Duration needed real care: providers disagree on the unit. TikTok's aweme `video.duration` is milliseconds while the web `itemStruct` equivalent is seconds, and Instagram's `videoDuration` is seconds. Rather than trust a key name that means two things, the extractor reads the magnitude — TikTok's own hard ceiling is 10 minutes, so any value above 600 can only be milliseconds. Live output confirms it: 10s, 19s, 37s, 20s, 11s, 11s.

`source` is provenance. **NULL means "written by the live submit path"** — every pre-BL-668 row and every organic row after it. A non-null value marks a verification row. **Any false-rejection-rate query must filter `source IS NULL`.**

**Applied to prod with `ADD COLUMN IF NOT EXISTS`**, through `scripts/run-schema-sql.js`, plus `npx prisma generate`. **No `prisma migrate` was run.** The exact statements:

```sql

ALTER TABLE rule_shadow_decisions ADD COLUMN IF NOT EXISTS "postedAt" TIMESTAMP(3);
```

**No new vendor call.** The submit path already downloads this payload for views and the freshness gate; PART 3 stops deleting it.

### What is stored, and for how long

A caption and its hashtags are **the clipper's own public post text**, already fetched at submit. Stored: `caption` (full text), `hashtags` (the parsed tag list), `soundId`, `postedAt`, `durationSec`, plus the per-rule verdicts and the reviewer note.

Retention: only as long as needed to validate the rule engine before auto-reject could ever be considered — the same window BL-659 and BL-666 set for `caption` and `noteText`. A later round should decide the pruning job; that decision is still open and this round did not narrow it. Read only by owner-side tooling; there is no clipper-facing surface. **Redacted to a character count in this report.**

## PART 4 — YouTube, honestly

**BL-665 got this wrong, and the correction is good news.** BL-665 reported that `getYouTubeVideoDetails` "requests no `snippet` component". It does request it — `youtube.ts:79` fetches `part=snippet,statistics`. What the function does is map `snippet.publishedAt` and then **throw away `snippet.title`, `snippet.description` and `snippet.tags`**. It is the same class of bug as PART 1: the data is already downloaded and discarded.

So:

• **Caption on YouTube** (title + description + tags): a **field-mapping change with zero extra quota cost**. `videos.list` costs 1 unit regardless of how many parts you request, and `snippet` is already in the request. Perhaps 20 lines.
• **Duration**: add `contentDetails` to the same `part=` list and parse the ISO 8601 `PT#M#S`. Still one call, still 1 quota unit. Perhaps 10 more lines.
• **Sound id**: **impossible.** No YouTube Data API endpoint exposes any audio or sound identifier. Not the free tier, not any tier. A sound rule can never work on YouTube.

**Is it worth doing now? No, and there is a blocking reason.** `YOUTUBE_API_KEY` is not set — not in `.env.local`, not in `.env`, only commented out in `.env.example`. `getYouTubeVideoDetails` returns `null` on the missing key, so YouTube submits fetch nothing at all today and fall through to the lenient branch, which means **YouTube clips currently skip the freshness gate entirely**. That is a bigger finding than the caption gap and it is out of scope here, so I am reporting it rather than changing it. Wiring the caption before the key exists would ship dead code. Set the key first; then the caption and duration are an afternoon.

### Does the note read a YouTube sound rule as a pass? No — and it now says why

The verdict was already correct before this round: `REQUIRED_SOUND` with no sound id returns `cannot_evaluate`, which `evaluateRulesShadow` routes away from `wouldReject` entirely, and `composeReviewerNote` puts into "WHAT I COULD NOT SEE". It never read as a pass.

What it did not do was distinguish *"we failed to read the sound this time"* from *"this can never be read here"*. BL-666's own design principle says not to collapse genuinely different situations, so I fixed the wording. **The verdict is unchanged** — still `cannot_evaluate`, still fail open, still never a reject. Only the reason string differs, and only on YouTube.
