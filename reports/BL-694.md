## PART 1 — template detection, per account

Templating is **all-or-nothing per account**, which is what makes sampling sound: classify from a handful of posts, then parse the whole catalogue. Measured on the three known accounts:

| account | `templated` | fraction | fields seen |
|---|---|---|---|
| **clipcapture.tv** | **True** | **1.00** | cast, created_by, genre, hashtags, language, ratings, … |
| **culturemeetsonline** | **False** | **0.00** | — |
| **decibeldrops** | **False** | **0.00** | — |

A 5-post sample gives the same answer as a 24-post one — asserted in the suite, because that is the property the design leans on.

### A correction to the field list

BL-682 listed `Original Release:` as a template field. **The marker these accounts actually emit is `Release Date:` — measured 24/24 versus 0/24 for the other spelling.** Both are accepted and normalise to one key, so nothing breaks either way, but a parser built only for the documented name would have silently dropped every release date.

## PART 2 — BL-692 landed mid-build and indicted the matcher

BL-692 published while this was being written, measuring template prevalence across a far wider population. Its finding about *parsers* is the one that mattered here:

> "A permissive matcher finds 1,168 field-lines across the corpus. A parser built for the BL-682 shape (`^Label: value`, ASCII colon, no leading decoration) finds 397 of them = **34.0%**. Two thirds of the metadata is invisible to it."

The misses it counted: **578 to an emoji prefix** (`⭐ Genre:`, `🎬 Director:`), **128 to a zero-width character** before the label, **51 to bullets or `**markdown bold**`**. Separately, **7.1% put a space before the colon**, and at least one account is inconsistent within itself (`Director:` and `Director :` in the same catalogue).

My first matcher was exactly the indicted shape. It now **strips leading decoration per line before matching** — emoji, zero-width, bullets, markdown — and matches the delimiter as `\s*:`. Six decorated variants are asserted in the suite, along with a guard that stripping decoration must not make ordinary prose look templated.

**Honest limit:** this fixes the *syntactic* misses. BL-692 also documented **value-less section headers** (`🔥 Why Watch?`, `📝 Summary:` followed by prose) which need a section parser rather than a key→value parser, and **editor credit codes**, which are a different semantic entirely. Neither is built here. So the coverage is much better than 34% and is **not** 100%, and I have not re-measured it against BL-692's 1,168-line corpus — that corpus is another round's working data.

## PART 3 — coarse valence, and the numbers

Coarse **positive / negative / neutral only**. No 27-way mood wheel: published fine-grained emotion tops out near macro-F1 0.46 while coarse valence lands far higher.

**Measured on 42 hand-labelled real captions** (14 per account, labels in the repo):

```
accuracy 33/42 = 78.6%          MACRO-F1 = 0.643
positive  P=0.95  R=0.80  F1=0.87   (n=25)
negative  P=0.75  R=0.80  F1=0.77   (n=15)
neutral   P=0.20  R=0.50  F1=0.29   (n=2)   <- n=2. Do not trust this class.
```

**The number a consumer actually feels is the sign-error rate: 4 of 40 non-neutral captions (10%) got the sign wrong.** The rest were correct or abstained to neutral. That distinction matters — an abstention is recoverable, a confident wrong sign is not.

The margin was swept 0.5–4.0 and 0.5 chosen; the curve falls monotonically above it (0.5 → 78.6%, 1.0 → 78.6%, 2.0 → 73.8%, 4.0 → 42.9%). **It was deliberately not tuned further.** Squeezing the last nine errors out of 42 samples would be fitting the sample, not the population.

### What the classifier reads, and what it refuses to read

Account boilerplate is pasted onto every post — `Follow @x for…`, keyword-stuffing blocks, fair-use notices, hashtag walls. Left in, every caption on an account scores alike. The **factual template blocks** (Cast, Runtime, Language, Release Date, Ratings, Where to Watch) are stripped for the same reason: a cast list is a bag of proper nouns and says nothing about how a clip feels. **`Storyline` and `Themes` are kept deliberately** — they carry the affect.

Two deliberate refusals:

- **`😭` scores zero.** It appears in this corpus in *both* registers — crying-laughing on one account, genuine dismay on another. Scoring it either way injects error, so it contributes nothing and lets the words decide.
- **An empty or noise-only caption returns `None`, not `neutral`.** Reading nothing is not the same as reading something unemotional.

## PART 4 — two bugs the tests caught that reading did not

**1. Variation selectors scored as positive emoji.** `❤️` is U+2764 + U+FE0F, so `set("…❤️…")` put a bare **U+FE0F into POSITIVE_EMOJI** — and `☹️` put the same codepoint into NEGATIVE_EMOJI, so set-membership order silently decided the sign of any caption containing one. Modifiers are now stripped before the sets are built and before any caption is scanned. There is a regression test asserting U+FE0F and ZWJ are in neither set.

**2. Next-line values swallowed the following field.** The real captions put values on the line *after* the marker (`Cast:\nEmilia Clarke, …`). `Themes:` therefore absorbed `Hashtags:\n#GameOfThrones` because `Hashtags` was not in the field vocabulary and so did not terminate the block. It is now a known marker — parsed but unconsumed — purely so it acts as a stop.

The same class of bug hit noise-stripping: deleting the `Cast:` *line* left the names behind on the next line, so a valence score was being computed over a cast list. Stripping is now block-aware.

## PART 5 — three fields, provenance, and the consumer rule

Never one collapsed `mood` string. Real output:

| | templated caption | plain caption |
|---|---|---|
| `valence_text` | `'negative'` (derived) | `'positive'` (derived) |
| `arousal_audio` | `None` (**absent**) | `None` (**absent**) |
| `affect_conflict` | **`None`** (absent) | **`None`** (absent) |
| `genre` | `['Fantasy','Drama','Adventure']` (**declared**) | `None` (absent) |
| `title` | `'Game of Thrones'` (**declared**) | `None` (absent) |
| evidence | neg: painful, betrayal, war, revenge | pos: funniest, memorable, comedy, heartfelt · 😂 |

**`affect_conflict` is `None`, not `False`.** With the audio axis unfilled the flag is unknowable, and `False` would read downstream as "checked, no conflict" — a fabricated negative. The moment the energy-step work supplies arousal it computes: valence `positive` + arousal `-1` → `affect_conflict = True`, provenance `derived`. The signature already accepts `arousal_audio`, so that work needs no change here.

**The consumer rule is enforced in code, not documented and hoped for.** `field(record, name)` returns the value only when provenance says `declared` or `derived`; a field marked `absent`, or one with no provenance entry at all, reads as `None`. The suite asserts that forging a value onto a record without a provenance entry leaves it invisible.

## PART 6 — what was deliberately not built

- **No music-genre lookup.** 0/108 clips on this population carry track metadata, and the free sources are licence-blocked for commercial use (MusicBrainz associations CC BY-NC-SA; Last.fm and Deezer explicitly non-commercial).
- **No learned fusion model.** Text dominates, so fusion collapses onto the text model at higher cost.
- **No fine-grained mood field.** See PART 3.
- **No menu entry, no `control.py` change, no config key.** Every threshold is a module-level default, overridable per call. The module reads no config file on purpose, so it stays importable and deterministic for offline batch work.
