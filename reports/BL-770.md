## 2. The shape-based check — and why a 3-row threshold would have missed letsencrypt

**4 addresses appear on 3 or more rows. None of them is infrastructure.**

| address | rows | funnels | handles | verdict |
|---|---:|---|---|---|
| `s***@leap.app` | 5 | google_play | Leap Fitness Group ×5 | **duplicate publisher rows**, one company |
| `g***@supercell.com` | 3 | google_play | Supercell ×3 | **duplicate publisher rows**, one company |
| `o***@microsoft.com` | 3 | google_play | Microsoft Corporation ×3 | **duplicate publisher rows**, one company |
| `b***@good-direction.agency` | 3 | spotify_finder | uniiqu3music, hershe, nikki__nair | **legitimate manager**, three real artists (BL-746) |

The distinction you asked for holds cleanly, and it is **not** the row count that separates them — it is whether the handles are the **same entity**:

- Same company repeated → a Google Play dedup defect, not a junk address. Three separate publishers each occupying 3–5 rows.
- Different real artists, one manager → legitimate, exactly the BL-746 pattern.
- **Different unrelated handles, infrastructure domain → junk.**

**And this is the methodological catch: `letsencrypt.org` sits on exactly 2 rows, so a ≥3 threshold never sees it.**

```
handle=ewefangz   platform=tiktok  source=tt:hashtag:hectoredit   added=2026-07-04
handle=sith.cc    platform=tiktok  source=tt:hashtag:vikingsedit  added=2026-07-07
```

Two unrelated editors, from two different hashtags, three days apart. **The correct rule is ≥2 rows with non-matching handles, not ≥3 rows.** A 3-row threshold is tuned to catch the wrong thing.

**The merge damage is already contained.** `crossdedup._is_mergeable_email("s***@letsencrypt.org")` returns `False` today, so it can no longer key an identity. The two rows survived as two rows; nobody was deleted. The address itself is still stored, which is why it keeps surfacing.

## 3. What each guard catches, and what slips

| guard | mechanism | catches | slips past |
|---|---|---|---|
| `bio_parser.valid_email` | `_JUNK_DOMAINS` (106) + syntax | letsencrypt, roblox, stripe, cloudflare, sentry, wixpress, godaddy | **any platform domain not on the list** |
| `bio_parser.rank_emails` | `normalize_email` + `email_kind`; drops hard-role | same junk list **plus** hard-role locals | non-role local on an unlisted domain |
| `PLATFORM_HOP_DOMAINS` (59) | streamer merch / tipping / alert hosts, folded into `_JUNK_DOMAINS` | streamlabs, throne, ko-fi, patreon, onlyfans, kick.com | not aimed at platforms-as-employers |
| `role_policy` | **local-part** words | `p***@tiktok.com`, `s***@`, `i***@`, `c***@` | `f***@youtube.com` — local part is a normal word |
| bio-link quarantine | `is_biolink_source` + non-free domain | 91%-wrong bio-link scrapes | only fires when `email_source` is a bio-link marker |

**The structural gap:** every guard is either a *domain* list that has no platforms on it, or a *local-part* list. An address that is a normal word at an unlisted corporate domain passes both. That is one address today; it is a whole class as more funnels scrape more footers.

**On the OCR confusions specifically — none are present, and structurally none can be.**

- `@` read as `G`: would leave a value with **no `@` at all**. Email cells with no `@`: **0 of 4,208**.
- comma read as `;`: `;` is the multi-value separator, so a stray one would split an address. Malformed fragments: **0**.
- apostrophe dropped: apostrophes inside a local part: **0**.

The reason is structural, and worth stating so this is not re-checked every round: **the OCR path (BL-736) feeds the repost-page detector's overlay-text features. Nothing from it is ever written to master's `email` column.** These confusions cannot reach the send list by this route.

The 16 leading-apostrophe values are a different bug — the Excel text-escape prefix (`'`) that `writer._sanitize` adds for display leaking into a stored value. All 16 fail validation and none reaches the send list, so it is cosmetic today, but it means those 16 leads have an unusable address on file.

## 5. Recommended suppressions

**Priority 1 — regenerate the exports.** Three of the four junk addresses on disk vanish with no code change. `ALL_BOT_READY.csv` is 14 days stale; `PANICBABY_SEND.csv` is 9. This is also BL-765's finding, and it is the cheapest fix in the project.

**Priority 2 — add a platform-employer class to `_JUNK_DOMAINS`.** Match on the **registrable domain, exactly** — never substring, or the five false positives in §1 become real losses.

| class | add | why |
|---|---|---|
| platform corporate | `youtube.com`, `google.com`, `tiktok.com`, `instagram.com`, `facebook.com`, `meta.com`, `twitch.tv`, `apple.com`, `spotify.com`, `snapchat.com`, `linkedin.com`, `twitter.com`, `x.com` | nobody outside those companies holds such an address; **1 live hit today** |
| distribution / aggregator | `distrokid.com`, `linktr.ee`, `beacons.ai`, `komi.io`, `bio.link`, `carrd.co`, `songwhip.com`, `hypeddit.com`, `toneden.io`, `bandsintown.com`, `seated.com` | aggregator defaults, same class as the already-listed hop domains |
| marketing / ESP | `mailchimp.com`, `mailchi.mp`, `sendgrid.net`, `mailgun.org`, `klaviyo.com`, `hubspot.com`, `intercom.io`, `constantcontact.com` | sending infrastructure, never a lead |
| hosting / CDN (extend) | `akamai.com`, `fastly.com`, `digitalocean.com`, `namecheap.com`, `bluehost.com`, `hostgator.com`, `siteground.com`, `wpengine.com`, `kinsta.com`, `ovh.net`, `hetzner.com` | same class as the listed `cloudflare.com`/`godaddy.com` |
| site builder (extend) | `squarespace.com`, `wordpress.com`, `weebly.com`, `webflow.com`, `duda.co`, `jimdo.com` | `wix.com`/`wixpress.com` are listed; the rest are not |

**Priority 3 — a shape rule, correctly specified.** Suppress any address on **≥2 rows whose handles do not match**, unless the domain is free-mail (a real manager on gmail) or the rows are the same entity by name. This catches letsencrypt-class junk at the 2-row threshold the current data actually needs, and leaves the manager and duplicate-publisher cases alone.

**Priority 4 — validate at export, not only at scrape.** Every guard runs when an address is *found*. Nothing re-validates at *export*, so any address stored before a blocklist entry existed ships forever. A single `valid_email` pass inside the exporters makes the blocklist retroactive and would have made this entire round unnecessary.

**Not recommended:** blocking `microsoft.com` / `supercell.com` / `leap.app`. Those are genuine publisher contacts for Google Play leads. Their problem is that each occupies 3–5 duplicate rows — a dedup defect, not junk.
