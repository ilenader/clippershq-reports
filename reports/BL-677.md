# BL-677 — beat-drop timestamp and mood for Instagram Reels: what is free, what is cheap, and what cannot be done

## NEITHER OF THE TWO HEADLINE FIELDS IS ACHIEVABLE. Drop timestamp fails on four independent grounds and mood fails on accuracy that has not moved in six years — **ship neither; leave mood NULL.** What the research did find is better than what was asked for: an exact trending-sound COUNT for **~$0.18 per 1,000 clips**, and audio reachable **without downloading any video** at **~12× less bandwidth**. Certainty replaces inference.

**2026-07-29 · RESEARCH ONLY. READ ONLY on code, config, data and money. No code was written or changed, no paid API call was made, nothing was appended to the master or the ledger.** Web research was carried out by five parallel strands; all primary-source claims are tiered VERIFIED / UNVERIFIED LEAD / REFUTED / GAP.
**Evidence base** a 180-reel corpus of `/v1/user/clips/chunk` payloads already paid for in a prior round (3 confirmed repost accounts × 60 reels), re-analysed offline at $0, plus three live `HEAD` requests to the public Instagram CDN (headers only, no response body, not the metered API).

**Related rounds, same day — independent corroboration.** [BL-675](BL-675.md) and [BL-676](BL-676.md) were produced concurrently by another agent on the *reach* question, and their findings agree with this corpus rather than conflicting with it. BL-675 establishes that `/v2/user/clips` returns `play_count` on **100%** of items while the deprecated `/v2/user/medias` serializer omits it on ~61% — dissolving the "Instagram hides views on ~40% of accounts" belief. BL-676 shows `view_count` is a **decoy that is present and literally `0`** (30/30 on the hashtag-clips surface). This round measured the same shape independently on a different surface and a larger n: on `/v1/user/clips/chunk`, **`play_count` non-zero on 180/180 and `view_count` non-zero on 0/180**. Three surfaces, three samples, one conclusion — `play_count` is the field, `view_count` is a trap.

## PART 1 — local primary evidence (the strongest tier: Instagram's own responses, not claims about them)

180 reels, licensed 59 / `original_sounds` 121. All figures below are counted, not estimated.

### 1.1 `highlight_start_times_in_ms` — present, and **not** what the brief assumed

| fact | value |
| --- | --- |
| licensed clips where the key exists | **59/59 (100%)** |
| licensed clips with a non-empty array | **48/59 (81.4%)** |
| `original_sounds` clips with highlights | **0/121 (0%)** |
| timestamps per track | 1 → 38 tracks · 2 → 9 · 3 → 1 |
| **distinct TRACKS behind those 48 clips** | **15** ← the real n |

Position within the track, n=59 timestamps:

```
min 0.00   p25 0.02   MEDIAN 0.05   p75 0.24   max 0.83     (fraction of track length)
```

**The median highlight sits 5% into the track.** Concrete arrays observed: `[500]`, `[2500]`, `[3000]`, `[11500]` — half a second to three seconds in. That is not a drop or chorus marker. The deep example that motivated the question (`[230000, 121000, 155000]`) belongs to the single 260 s trailer-music track in the corpus and is the exception.

Two structural facts pin down what the field is:

* **Same audio cluster → identical array, every time. 15 clusters, 0 with a differing array.** The value is **track-level catalogue metadata**, not computed per post. This REFUTES any per-reel derivation.
* **Arrays are not sorted ascending — 38/48 sorted, 10 not.** The order therefore carries information; nobody documents what.

**Sampling caveat, and it is load-bearing.** The 15 tracks are dominated by Meta Sound Collection production music. Production music often has its best part at the top by design. Treat "median 5%" as VERIFIED for this corpus and an UNVERIFIED LEAD for commercial pop, which is not represented here.

### 1.2 The structural blocker that outranks everything else — GAP

`music_info` carries exactly three keys: `music_canonical_id`, `music_asset_info`, `music_consumption_info`. **No field states where the reel's excerpt begins inside the licensed track.** Checked and absent on all 59 licensed clips: `audio_asset_start_time_in_ms`, `overlap_duration_in_ms`, `derived_content_start_time_in_composition_in_ms`. Those three fields *do* exist on the `original_sounds` branch and are **0 on all 121** — trivially, because there the original audio *is* the reel's audio.

Meanwhile **57/59 licensed reels (97%) are shorter than the track they use** (reel median 57.3 s vs track median 97.7 s), so they genuinely are excerpts.

**Consequence:** `highlight_start_times_in_ms` is in **track time**, and for licensed music there is no metadata to map track time onto **reel time**. The two fields that would allow the subtraction never co-occur — the marker is licensed-only, the offset is original-only.

* *"Where do I cut this reel?"* → unanswerable from metadata.
* *"Which sound, and where do I start it in a new edit?"* → answered directly, free, on the licensed third.

## PART 2 — what `highlight_start_times_in_ms` actually is

**VERIFIED — it is a suggested START POINT for attaching a track to a reel, not a drop marker.**

* **It lives on the music-catalog `Track` object**, appearing in the audio *browse* feeds (`MusicSearchFeedResponseTrack`, `MusicTrendingFeedResponseTrack`, and the mood and genre equivalents); a reel merely embeds a copy. This matches §1.1's finding that every post sharing a cluster returns an identical array.
* **Behavioural proof of intent.** The `instagrapi` client takes element `[0]` and feeds it straight into `audio_asset_start_time_in_ms` — the same slot the app's own trimmer writes — trimming the audio to start there. A faithful app-emulator treats it as *where to start the track*.

**REFUTED — it is not a licensor-supplied preview start.** Every industry precedent is a **single scalar in seconds** (Apple Music's `preview_start_index`, TikTok's distributor-submitted "Clip Start Time"). Instagram's is a **variable-length array in milliseconds** quantised to 500 ms. Licensors do not supply three preview starts. Strong shape argument, not proof.

**UNVERIFIED LEAD — crowd-derived usage peaks is the best remaining fit.** Third-party how-to writing describes the audio slider's marker dots as the parts other reels use most; the 500 ms quantisation fits binned aggregate usage far better than a DSP onset detector, which would emit sample-accurate offsets. A reconciliation supports this: `instagrapi`'s documented **pop** examples land at 0:20 / 0:35 / 1:26 — plausible hook positions — while this corpus's **production-library** tracks cluster at the head. That is exactly what crowd aggregation would produce, since listeners start a pop song at its hook but library music has no hook to seek. It also means §1.1's "median 5%" is an artifact of *this* corpus, not a property of the field.

**GAP — Meta has documented nothing.** No developer doc, no engineering blog, no paper. Across 362 GitHub code hits mirroring the field, there are **zero** substantive issues: in the field's entire public life nobody has asked what it means.

## PART 3 — drop detection from audio: four independent disqualifications

**1. Accuracy. VERIFIED.** The only peer-reviewed drop detector (Yadati et al., ISMIR 2014) reports **F1 = 0.62 at ±5 s**, 0.61 at ±3 s, peaking at 0.71 only when the tolerance is widened to ±15 s. Its corpus is **100 SoundCloud tracks / 190 drops**, dubstep–electro–house only, averaging ~4 minutes. A ±5 s error inside a 20–52 s reel is a quarter to a tenth of the entire clip.

**2. The wrong primitive. VERIFIED.** librosa's own documentation describes `onset_detect` as locating **note onset** events — hundreds per clip. A drop is a *change in the statistics* of energy and onset density, i.e. a segmentation problem. Treating onset detection as drop detection is a category error. **GAP: no published accuracy exists for librosa at this task.**

**3. Licence. VERIFIED, and decisive on its own.** madmom's pretrained models are **non-commercial**. **Essentia is AGPLv3 and licensed for non-commercial use**; commercial use requires a paid UPF licence. The only commercially-free option, **librosa (ISC)**, is the weakest at the task. Both strong toolkits are also abandoned at the release level: madmom's last PyPI release is **0.16.1, 2018-11-14** (Python 2.7–3.7 classifiers; NumPy-2 fixes exist on main but were never released), aubio's is **0.4.9, 2019-02-08**.

**4. The premise collapses.** **67% of this corpus (121/180) is `original_sounds`** — the audio *is* the creator's own export, so there is no upstream song sitting at an unknown offset in which to locate a drop. A separate clipper-account probe measured 36/36 original. **GAP: no study exists on where drops fall in short-form video.**

**CPU was never the constraint** — roughly 32 ms per 30 s clip, about 32 CPU-seconds per day at 1,000 clips. Cost is not what kills this; accuracy and licensing are.

> **Correction to an existing repo document.** `beatdrop_mood_research.md` cites an audioFlux figure of "2.41958 s" as a per-clip cost. That figure is **per 1000 samples**, not per clip, overstating DSP cost by roughly 1000×. Any plan built on it was solving a cost problem that does not exist.

**What to ship instead.** An honest local measure — *"largest sustained energy step within this clip"* — computed with librosa (ISC, commercially free, near-zero CPU). Name the column for what it is, e.g. `energy_step_ts`, **never `drop_ts`**. And note the free supervision sitting in plain sight: **the creator's own cut points** are a label nobody has to pay for.

## PART 4 — mood: leave it NULL

**The accuracy numbers, VERIFIED.**

* **MTG-Jamendo mood/theme** (18,486 tracks, 56 tags; the field's standard benchmark, official metric PR-AUC-macro): best-ever system **0.161** (2020); 2025 state of the art **0.1543**; trivial "predict the popular tags" baseline **0.032**. **The number has not moved in five to six years.** ROC-AUC of ~0.78 is often quoted instead and is misleading — with rare positives, ROC stays flattering while precision sits near zero.
* **Essentia's binary mood models** are trained on **230–446 tracks each**, and the two anyone would actually want are the weakest: `mood_happy` **0.79–0.86** (n=302) and `mood_sad` **0.85–0.89** (n=230), in-domain only. Essentia's own model page publishes no accuracy figures at all.

**Every free input is closed.**

* **Spotify audio features are unreachable for a new application. VERIFIED, with a date correction:** Audio Features and Audio Analysis were withdrawn from **new** applications on **27 November 2024** — not February 2026. A real but *different* change on **6 February 2026** restricted Development Mode (Premium required, one client ID, five authorised users). The practical outcome is the same: **valence is gone**, and it was the single best free mood proxy.
* **AcousticBrainz** stopped accepting submissions in **June 2022** and the site went down in early 2023. Dumps remain downloadable (~7.5M recordings) but are frozen at 2022, keyed by MBID, and carry those same weak Essentia values — so they miss essentially all currently-viral Reels audio.
* **Last.fm**'s API is alive and free to key, but its rate limit is undefined and reserved to Last.fm's sole discretion, and **the free licence is explicitly non-commercial**. Mood is a small minority of tags behind genre and locale, and the labels are head-biased and described in the literature as noisy and weakly supervised.
* **MusicBrainz** promotes genre tags but not mood. **OpenL3 and similar embeddings are not classifiers** — they are the inputs the PR-AUC 0.15 systems are already built on, so a better embedding does not escape the ceiling. **Deezer** exposes BPM and gain but never valence.

**The deepest reason, and the one that will not be engineered away:** music-emotion inter-annotator agreement (Krippendorff α) falls **below the acceptability threshold for valence**; only arousal reaches "fair". **There is no ground truth to hit.** That is why the benchmark number is frozen.

**Coverage × accuracy, done explicitly.** Declared title exists on ~33% of clips. At a generous 70% accuracy on those: **0.33 × 0.70 ≈ 23% of rows correct, 0.33 × 0.30 ≈ 10% of all rows confidently wrong**, 67% null regardless. A staged estimate (title → catalogue match → has a mood tag → tag is right) lands worse: ~17% filled, ~11% right, ~6% wrong. Running Essentia on the reel's own audio instead reaches 100% coverage but pushes the wrong-value rate to ~30–40% of *all* reels. **In every variant there is no confidence signal separating the right values from the wrong ones.**

**The one defensible fallback, if a field is ever required.** Not mood — **arousal**: a single high-energy-versus-calm bit derived from `mood_aggressive`/`danceability`, validated against hand-labelled real reels before it is trusted. Never happy/sad. This matches the human-agreement finding exactly: arousal is learnable, valence is not.

## PART 5 — speech over music: detect, never separate

**`webrtcvad` is unsuitable, bluntly. REFUTED for this task.** It is a GMM likelihood ratio over a handful of sub-band energies with exactly two hypotheses — speech versus *noise*. **There is no music class**, so music is pushed toward the speech hypothesis by construction. Its README states it is for telephony and speech recognition. No music false-positive benchmark exists anywhere — **GAP**, because nobody uses it this way.

**`silero-vad` is good, cheap, and answering the wrong question.** MIT, ~2 MB, under 1 ms per 30 ms chunk on one CPU thread, ROC-AUC 0.97 — all VERIFIED. But its own quality-metrics documentation evaluates on **zero music datasets** (GAP), and the structural problem is fatal by itself: **a sung vocal is a human voice**, so a perfect VAD fires on every track with lyrics. Usable as a cheap first stage, never as the gate. Version-pin it: v4 regressed 2–3× against v3 on noise-only material.

**The recommendation is `inaSpeechSegmenter` — MIT licence VERIFIED by reading the LICENSE file.** Its `smn` engine emits speech / music / noise as distinct classes, which is the actual task; the `sm` variant won MIREX 2018 speech detection. Costs: a TensorFlow and ffmpeg dependency, and **GAP — it publishes no speed figure**. Runner-up worth a look: **YAMNet** (Apache-2.0), which has an explicit `Singing` class.

**Separation is not affordable and not needed.** At 1,000 clips/day of ~30 s each = 30,000 audio-seconds:

| option | real-time factor | tier | **wall clock per day** |
| --- | --- | --- | --- |
| demucs, CPU (vendor's own figure) | 1.5 | VERIFIED | **12.5 h** ✗ |
| demucs, CPU (third-party desktop) | 0.49 | UNVERIFIED | 4.1 h |
| demucs, GPU | 0.041 | UNVERIFIED | 20 min |
| spleeter, GPU (vendor claim) | 0.01 | VERIFIED | 5 min |
| **silero, detect only** | <0.033 | VERIFIED | **17 min, one core** ✓ |
| **inaSpeechSegmenter, detect only** | ~0.10 | ESTIMATE | ~50 min ✓ |

`30,000 × 1.5 = 45,000 s ÷ 3600 = 12.5 h`. demucs already saturates every core, so that is 12.5 hours of *wall clock* daily with no parallelism left to buy. **Detection is 15–50× cheaper.**

**REFUTED — "demucs is non-commercial".** demucs is **MIT** (Meta Platforms). spleeter is **also MIT**, with 2.4.2 shipped 2025-04-03, so "spleeter is dead" is only half true — it is stale and capped at Python <3.12, and roughly 3 dB worse SDR.

**Separation would not replace detection anyway.** Strip the vocals from a talking-head clip and what remains is room tone plus a beat tracker hallucinating on it; the detector is still needed to tell the two cases apart. The honest counter-argument, flagged as such: demucs' `drums` stem genuinely *is* a better input for beat analysis. That is a quality upgrade with its own budget, not a fix for speech — gate it behind the detector at ≤5% of the corpus and it costs ~37 min/day, which is affordable.

## PART 6 — the audio itself: no video download is required

**VERIFIED by live `HEAD` requests** (headers only, no body transferred; the public CDN is not the metered API, so $0):

| asset | HTTP | advertised type | size | duration | implied bitrate |
| --- | --- | --- | --- | --- | --- |
| licensed `progressive_download_url` | **200, no auth** | `video/mp4` | **2.19 MB** | 260.6 s | **67 kbps** |
| original `progressive_download_url` | **200, no auth** | `video/mp4` | **0.19 MB** | 20.6 s | **74 kbps** |
| `video_url` (the reel itself) | **200, no auth** | `video/mp4` | **2.26 MB** | 20.6 s | **880 kbps** |

1. **`progressive_download_url` is present on 100% of all 180 clips**, licensed and original branches alike. An earlier inference that it was licensed-only is **REFUTED**.
2. **It is audio-only despite advertising `video/mp4`.** 67–74 kbps is an audio bitrate; the reel's own video is 880 kbps from the same CDN. This mislabelling is an easy source of bugs — do not trust the content type.
3. **No authentication is needed.** Plain GET, no cookies, no headers; the signature travels in the URL.
4. **`Accept-Ranges: bytes` on all three**, so ffmpeg can range-read and seek without pulling whole files. The common claim that a non-faststart mp4 forces a full download is wrong wherever Range is supported — a trailing moov atom costs one extra round trip, not the file.
5. **REFUTED — "Instagram CDN URLs expire in a few hours".** Measured expiry: **~104 h (≈4.3 days) on audio**, **~32 h on video**. Batched fetching is comfortable. Note the CDN's `Cache-Control: max-age` is its own caching hint and is **not** the URL's validity window; do not confuse the two.
6. **REFUTED — the widely-quoted "3.5–5 Mbps delivered" figure.** Real delivery is **~0.86–0.88 Mbps at 720×1280**, derived from captured stream metadata and confirmed within 2.5% by live measurement.

**Bandwidth at 1,000 clips/day: ~5.4 GB via video versus ~0.5 GB audio-only — about 12× less.** (Sizes are an ESTIMATE from median bitrate × median duration; the per-asset figures above are measured.)

## PART 7 — the cheaper substitute, and the best result in this report

The owner's instinct in framing the question was right: **a hard usage count beats an inferred mood, because certainty beats inference.**

**VERIFIED against the provider's public OpenAPI specification** (downloaded and inspected locally; 154 paths). Three audio endpoints exist, taking a single opaque track identifier and returning the raw Instagram dictionary plus a pagination token:

```
GET /v2/track/by/id?track_id={id}
GET /v2/track/stream/by/id?track_id={id}
GET /v2/track/by/canonical/id?canonical_id={id}
```

These map one-to-one onto `instagrapi`'s `track_info_by_id` → Instagram's private `clips/music/`. *(An earlier automated summary of that same specification claimed no such endpoint existed; that was a summarisation artifact. The local inspection of the downloaded file is authoritative — a useful reminder that a fetched summary is not a primary source.)*

**VERIFIED for the Instagram envelope:** the response carries **`media_count.clips_count` as an exact integer**, alongside a formatted display string.

**UNVERIFIED LEAD:** whether the provider passes those keys through unchanged. It is a raw passthrough, so it should — but only a live call proves it. **Also UNVERIFIED:** that `best_audio_cluster_id` is accepted as `track_id`. Encouragingly, `instagrapi` passes the *same* single id into both the cluster and asset slots and lets Instagram ignore whichever does not apply — which is very likely why `best_audio_cluster_id` is populated on 100% of reels regardless of audio type.

**Cost per 1,000 clips**, at the rate this pipeline already pays: **$0.60 worst case** (every clip a unique sound), **~$0.42 realistic**, **~$0.18 with a 24-hour cache keyed on `best_audio_cluster_id`**. Caching is unusually effective here for a structural reason: a *trending* sound is by definition shared across many clips. Against the existing crawl cost that is roughly a 15% uplift.

**Three traps.**

1. The formatted count is a **localised display string** — a documented sample returns a Russian-language value with space separators. **Never regex it; read `media_count.clips_count`.**
2. **The provider bills 404s** (only 5xx are free). Dead audio ids will bill on every retry unless negative-cached.
3. It is a private, undocumented endpoint with no stability guarantee. Parse defensively and **degrade to UNKNOWN, never to zero** — a missing count must not read as an unpopular sound. This matches the pipeline's existing "UNKNOWN never cuts" policy.

**A free version exists today at $0.** `best_audio_cluster_id` groups correctly (§1.4), so *"how many reels in my own library use this sound"* is computable with zero extra calls and sharpens as the library grows. It is **not** the same number as the app's public count and must never be labelled as such.

No free-tier third-party API exposes a real usage count. The one provider that documents it charges about 3.3× the incumbent; the other aggregators strip the count in favour of a unified schema.

## What was deliberately left alone

No code was written or modified. No configuration was touched. Nothing was appended to the master or to the spend ledger. No paid API call was made in this round; the 180-reel corpus was already paid for in a prior round and was re-analysed offline. The only network activity was three `HEAD` requests to the public Instagram CDN — headers only, no response body downloaded, no billing attached — and ordinary public web and documentation reads by the research strands.

One research strand terminated early on an upstream API stall. Because every strand was instructed to write findings incrementally to disk, its log was fully recoverable and no work was lost; its synthesis was completed from that log combined with the local corpus evidence. This is recorded because the failure mode is recurrent and the mitigation worked.
