## PART 2 — can production reach Apify? It reaches it constantly. It just cannot pay.

### The key is not empty. It is an invalid STRING, and that difference is the whole story

`getApiKey()` (`src/lib/apify.ts:157-160`) is `if (!key) throw`. A truly **empty** key throws before any network call. A key set to a junk string such as `DISABLED` is **truthy**, so the function returns it, the code builds a real actor URL and POSTs it to `api.apify.com`, and Apify answers 401.

**Production is demonstrably in the second state, and the ledger proves it rather than assuming it.** In `fetchInstagramStatsApiScraperSingle` the ledger row is written at `apify.ts:743` **only after `fetch` returns a non-ok response**; if `getApiKey()` had thrown, control would jump to the catch at `:779`, which writes no ledger row. So every ledger row is proof that an outbound HTTPS request to Apify actually completed.

## PART 4 — the local-environment problem is bigger than one round

### Forty-one environments hold the working key

Counted this round: **73 git worktrees exist on this machine, 41 of them contain a `.env.local`, and all 41 carry a real `apify_`-prefixed key.** Every round works in a worktree and copies `.env.local` in as a matter of routine. **So the number of environments that could repeat BL-673's accident is not one. It is 41, plus every future worktree, because copying `.env.local` is the standard first step of a round.**

Two rounds have already done it, five days apart, and neither intended to: BL-665 through the Instagram submit-path probe and BL-673 through the TikTok cover fallback. Neither round was about Apify. **This is not a discipline failure that better briefs will fix; it is an environment that hands every round a live payment credential.**

### What BL-673 actually guarded, verified

BL-673 states: *"The harness now sets `process.env.APIFY_API_KEY = "DISABLED"` in-process before anything else, mirroring production exactly, and only runs the integrated TikTok capture on clips whose free oEmbed already answered."*

**That guard is real and it works, but its scope is exactly one file: `scripts/test-bl-673-instagram-cover.ts`, BL-673's own test harness, on BL-673's own branch, which is not merged to main.** It protects that one script and nothing else. It does not protect the other 40 worktrees, any future harness, any `npx tsx` one-liner, or the next round that calls `fetchClipStats` on an Instagram URL. **It covers the path it hit, and only there.** BL-673 described it accurately and did not overclaim; the point is simply that a per-script guard cannot generalise.

### Recommendation for PART 4: both, and the local key first

**Clean the local key AND add a code guard, in that order.**

* **Clean the local key first, because it is the only measure that is immediate, total and free.** Replacing `APIFY_API_KEY` with `DISABLED` in the source `.env.local` and in the 41 worktree copies removes the ability to spend from every environment at once, needs no code change, and makes local behaviour identical to production, which is exactly what a test environment should be. Nothing local needs Apify: every provider a round exercises (HikerAPI, LamaTok, the YouTube Data API, TikTok oEmbed) works without it.
* **Then add the code guard, because the local key will drift back.** Someone will restore a key eventually, and a guard is what makes that harmless.
* **Cleaning the key alone is not enough** (it protects only this machine, not a future key on Railway), and **the guard alone is not enough either** (until it merges, every worktree can still spend today). Together they close both halves.

## PART 5 — the verdict and the ranking

### ONE LINE

**Production cannot spend a cent on Apify today, because its token is invalid, not because the code stopped calling: it fires about 6,000 rejected Apify calls a day and would resume spending roughly $500 a month the moment a valid key were set anywhere.**

### Ranked, with the honest weighting on `apify.ts`

**1. Clean the Apify key out of `.env.local` and its 41 worktree copies. DO THIS FIRST.** Zero risk, zero code, effective immediately, and it makes local match production. It is the only option that stops the two accidents that have actually happened. **Recommended.**

**2. Add BL-611's `APIFY_HARD_OFF` guard, or better, invert the key check.** BL-611 designed it and the one blocker it named (Instagram verification) is now gone, so the design is ready as written. The cheapest correct form is a single helper that treats a key of `DISABLED` or empty as OFF and returns each site's existing null-shaped result **without making the HTTP call** — which also removes 6,000 pointless outbound requests a day. It touches only the guard at the top of eleven functions and returns the exact shape a dead URL already produces, so it exercises only paths BL-543, BL-605 and BL-610 already proved keep last-known and store no 0. **Recommended second.**

**3. Leave it. Not recommended, but not absurd.** Production genuinely cannot spend today, and the failure is genuinely safe. The reason to reject this is that the sole control is a string in an env var that no alarm watches.

**4. Delete the dead call sites from `apify.ts`. NOT recommended, and this is where the honest weighing belongs.** `src/lib/apify.ts` is a money-critical file: it is the fetch layer the tracking cron depends on, and its null-shaped returns are precisely what `tracking.ts:1442` relies on to keep last-known views and never store a 0. Ripping five call sites out of a 2,500-line file means restructuring `fetchInstagramStats`, `fetchTikTokStats` and both batch fan-outs, whose tier ordering, gone-counter skips and carousel quarantines are the accumulated output of BL-543, BL-550, BL-580, BL-590, BL-605 and BL-610. **A refactor there risks a stored 0 or a frozen clip, which costs real clipper money; leaving eleven functions unreachable behind a guard costs nothing.** Deletion is the tidy answer and the wrong one. If the owner ever wants it, it belongs in its own Opus round with a live regression harness, after the guard has been running for a while, and never as a side effect of a cleanup.

### What could not be measured

The Railway environment variables cannot be read from here, so the exact value of the production `APIFY_API_KEY` is **inferred, not read**: the ledger proves it is a truthy string that Apify rejects, which is consistent with BL-614's direct observation of `DISABLED`, but the literal value is UNKNOWN. The post-cutover share of 2026-07-22's $0.6297 is **UNKNOWN**. The exact cause of the rising attempt rate is **INFERRED** from the thumbnail retry loop that BL-670 and BL-673 both flagged, and was not confirmed by any request.
