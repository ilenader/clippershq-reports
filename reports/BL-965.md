# BL-965 — the manifest was never ahead of its code, and the template holds up

Two jobs. The suite red was **not** the failure it looked like: `docs/claims/MEMEBOT-067.claims`
is not ahead of its code and never was. The guard that flagged it was reading a sentence
about a path the manifest deliberately did *not* claim. And BL-961's message template
reproduces its published split exactly on a freshly rebuilt file — with one row-class it
was silently declining, found by reading all 16 GENERIC rows one at a time.

### What actually failed

`ManifestHeaders.test_no_manifest_claims_it_cannot_verify_while_it_verifies` scans a
manifest's header for a denial phrase and flags it if the claims then verify. The rule is
right — BL-890 built it because five manifests carried "THIS MANIFEST CANNOT PASS
verify_claims.py" long after they verified, and a stale caveat teaches the next reader to
distrust a check that works.

MEMEBOT-067's header contains `can never verify`. But the sentence is:

> THE FIX ITSELF IS NOT CLAIMABLE HERE … It lives in `memebot/scraper/run_record.py`, and
> `memebot/` is a SEPARATE git repository … so a memebot path **can never verify** no
> matter how thoroughly it is committed. Claiming it would produce a manifest that fails
> forever.

That is not a claim about the claims. It is an explanation of an **absence** — why a
nested-repo path was left *out* of the list rather than claimed and left failing forever.
Which is precisely the discipline the repo asks for.

**Flagging it told the round to delete the explanation of why the path is missing.** That
makes the manifest less honest, not more, and is the opposite of what the check exists to
protect. So the fix is the guard, not the manifest. **`docs/claims/MEMEBOT-067.claims` was
not edited** — it is another round's file and there was nothing wrong with it.

### The fix, and the two conditions that keep it a guard

`denial_is_out_of_scope()` exempts a denial only when **both** hold, **within the same
header paragraph**:

1. the paragraph carries an explicit not-claimed marker (`not claimable here`,
   `is not claimed`, …); **and**
2. that paragraph names a concrete path that is **genuinely absent** from the manifest's
   own claim list.

Condition 2 is the one with teeth, and it is what stops this being an escape hatch: a
manifest cannot write "not claimable here" over a denial about paths it *does* claim — the
named path has to really be missing, which is checkable and is checked. Paragraph scope
stops a marker anywhere in the prose from excusing a denial elsewhere.

**Six fixtures, four of which must still be caught** (docs/TESTING.md rules 1 and 2 — an
exemption is the easiest place in a check to hide a guard that cannot fire):

| fixture | verdict |
|---|---|
| a bare denial, no marker | **still flagged** |
| marker + denial naming only paths it DOES claim | **still flagged** — the hatch is closed |
| marker + denial naming no path at all | **still flagged** |
| marker in a *different* paragraph from the denial | **still flagged** — scope is the paragraph |
| MEMEBOT-067's shape (marker + an unclaimed nested-repo path) | exempt |
| the real file on disk, asserted directly | exempt, and its claims verify |

The last one is deliberate: the exemption is asserted against the live manifest, not only
against synthetic text, so it cannot quietly stop matching the thing it was written for. It
skips **loudly** if the file is gone.

`tests/test_claims_manifest.py`: **24 tests → 30, green.**

## 3. What reading the 16 GENERIC rows found

Item 4 asked whether any GENERIC row has usable data the rules are declining. **Seven did**,
and my automated flag missed all seven — it fired on six *correctly* declined rows instead.
Dumping every field the renderer looked at, and reading it, is what caught them:

```
[13] PocketGuard, Inc.                       -> "Hi there"
[15] Digitalchemy, LLC                       -> "Hi there"
[8]  Gulooloo Tech Co., Ltd.                 -> "Hi there"
[16] Scopely Explore, Inc.                   -> "Hi there"
[10] DEVFLOOR Co.,Ltd.                       -> "Hi there"
[14] Innovative Language Learning USA, LLC   -> "Hi there"
[7]  Tasks.org, LLC                          -> "Hi there"
```

**A cleanup step ordered after the test its own output would pass is a cleanup step that
does nothing.** `_INTERIOR_DECOR` saw the **comma** in front of the entity tail, called the
whole name decorated, and rejected it — while `_LEGAL_SUFFIX`, which exists precisely to
remove that tail, sat two lines below and never ran, because the name had already been
thrown out. `Beefun Pte. Ltd.` passed only because it happens to have no comma, which is
exactly why the ordering bug survived its own test.

Fixed by stripping the suffix **before** the usability test, then re-testing what is left —
so the fix cannot become a bypass. `Tasks.org, LLC` → `Tasks.org` is still domain-shaped and
correctly stays unnamed; `Sparkle ★, Inc.` → still decorated, still declined.

Six rows recovered a real greeting: `Hi PocketGuard`, `Hi Digitalchemy`, `Hi Gulooloo Tech`,
`Hi DEVFLOOR`, `Hi Scopely Explore`, `Hi Innovative Language Learning USA`.

**The 10 that remain are correct.** Every one is declined by a named rule with nothing
recoverable behind it: 8 domain-shaped names (`4rpit.fr`, `riordan.uk`, `mollyj.tv`,
`zeitic.co`, `karyn.co`, `alcemist.uk`, `vinztech.app`, `Tasks.org`), one name that is the
lead's own email domain with the dots knocked out, and `Diary App & Habit Tracker`, which
is an app name rather than anything to greet.

## 6. The coverage-definition difference — not a regression

Recorded here so nobody reads it as one. BL-961 reports **599 / 20.1%** "hit none of
BL-956's nine defect classes"; BL-956 published **328 / 11.0%**. Recomputed on this file:

| class | here | BL-956 | agree |
|---|---|---|---|

| fandom is a FUNNEL NAME | 1,440 | 1,440 | **yes** |
| no clip date | 1,428 | 1,428 | **yes** |
| no clip views | 1,427 | 1,427 | **yes** |
| no followers | 1,397 | 1,397 | **yes** |
| name lowercase / handle-shaped | 486 | 477 | no |
| name has stray punctuation | 68 | 47 | no |
| name contains an emoji | 14 | 11 | no |

**Six of nine agree to the row.** The three that differ are the three BL-956 states in prose
without giving a predicate, so they are approximations of a rule that cannot be read back.
Because "clean" is the intersection of all nine, three loose classes move it a long way:
599 vs 328. **This is a definition difference, not a change in the data and not a
regression.** Neither number should be quoted as "how many rows merged cleanly" without its
definition attached — the per-class table is the part that is comparable.
