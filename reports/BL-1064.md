## 1. The preview, on the real library, read-only

```
WHAT IT WOULD DO, clip by clip (2728 clips in the library):
   GAINED a song :    33   (parked before, matched now)
   MOVED  song   :     8   <-- these LOSE their current song
   PARKED        :     0
   KEPT          :  2687
   BALANCES   sum = library
```

**Four buckets, not a set difference.** The 8 moves are `hype -> goofy` and `warm -> goofy`,
and each is named with its clip id. A set difference cannot see a move at all: when the same
clips match before and after but individually swap songs, it reports *nothing happened*.

`tests/test_add_song.py::test_a_set_difference_would_have_reported_nothing` is the control for
that claim — it asserts the matched **sets are identical** (failing the fixture if they are
not) and then asserts the four-bucket account still sees the move. Without that control the
extra bookkeeping would be unfalsifiable.

`still_parked: 2235` is also reported, so the number that does not move is visible too.

## 2. Every refusal, demonstrated live

| Input | Refusal |
|---|---|
| path that does not exist | *"there is no file at ..."* |
| zero-byte `.mp3` | *"the file is empty"* |
| `broken.mp3` (17 bytes of text) | *"ffprobe cannot decode it"* |
| `no_audio.mp4` (video, `-an`) | **"NO AUDIO STREAM"** |
| `--hooks 10.0-26.5` | *"A hook longer than 10.0s can NEVER be placed: the code needs the clip to be at least twice the hook, and a finished clip is capped at 20.0s. Mark the ~4s core where the hit actually lands."* |
| window past the end of the track | *"past the end"* |
| no windows at all | *"at least one"* |

The audio checks run **at add time**. The same fault found at render is one paid re-fetch and
forty seconds later, on a clip that ships silent.

The hook ceiling is arithmetic, not preference: `place_at_detail` refuses when
`clip_len < 2 * hook_len`, and `duration.CEILING_S = 20.0` caps the clip. `10.0` passes,
`10.01` does not — pinned by `test_the_boundary_is_exactly_ten_seconds`.

## 3. The placement caveat, printed with the refusal

Marking short windows is necessary and **not sufficient**, and the tool says so rather than
letting the operator mark 21 windows expecting to hear a difference:

1. **the target** — `PLACE_AT_TARGET_S = 5.0`, **landed**
2. **a renderer that reads it** — `hook_chain` has **ZERO shipping callers**. Nothing consumes
   a placement today.
3. **hooks short enough to place** — the operator's half; 4 of his 21 windows (9.24–26.93s)
   can currently place, 21 of 21 after re-marking

`test_the_placement_caveat_names_all_three_halves` fails if the text stops naming any of them.

## 4. Two things the build got wrong, and how they were caught

**The splitter fused ideas.** Treating "and" as filler turned *"reaction faces and dumb
fails"* into one phrase no scene description contains. The rule looked correct and matched
**0 of 2,728**. `and`/`or` now **separate**; filler is trimmed from phrase **edges only**.
Pinned by `test_and_SEPARATES_ideas_rather_than_being_dropped`.

That failure also produced a feature: the preview now prints **per-phrase hit counts**, which
distinguishes *"your words appear but never two together"* from *"none of your words appear at
all"* — two problems with opposite fixes that read identically as "matched nothing".

**The first fixture could not produce the passing case.** A constant-amplitude sine has a flat
40–250 Hz envelope, and the envelope is what the verification correlates — so the fixture was
untestable by construction. Rebuilt with a real loudness contour and **proven before being
trusted: self-recovery r = 1.0000** (docs/TESTING.md RULE 1).

## 5. End to end, on a COPY of the store

Applied to `scratch/bl1064_work/songs_copy.json` (backup taken first, `validate` clean), then
three clips rendered through the real path — `retrieve_video` → `stage_clip` → `pick_song` →
`fit_window` → `build_render_config` → `render_one`.

| clip | duration | r | margin | verdict |
|---|---|---|---|---|
| `3782329526819816247_2634` | 19.98s | 0.9290 | 0.5708 | PASS |
| `3917880461887933523_9717` | 19.97s | 0.9290 | 0.5708 | PASS |
| `3936139974625153630_2272` | 20.02s | 0.9291 | 0.5712 | PASS |

**3/3 on all four measurements** — audio stream 3/3, ≥ 8.0s floor 3/3, ≤ 20.0s ceiling 3/3,
carries the configured track 3/3.

Two things the correlation had to get right:

- **the APPLIED window, not the marked one.** `fit_window` widens the marked hook so the audio
  is never the shorter stream: `[12.0, 16.0]` marked → `[12.0, 62.92]` applied. Correlating
  against the marked hook measures a window the render did not use.
- **a bounded lag.** Every null is a **marked hook window**, so the search cannot slide a
  whole-file reference across its own duration and keep the best of thousands of alignments —
  which is how MEMEBOT-074 scored **0.94 against a track the render never touched**.

**A real finding from the first pass:** the identical check returned **0/3** when the three
matched clips were all `dialogue-over-music` / `dialogue-only`, where `duck.bed_plan` mixes the
bed **7–14 dB under speech**. The fixture self-recovers at 1.0000 and music-only clips pass at
0.929, so that is a **limit of the verifier on dialogue clips, not of the tool** — and it is
worth stating plainly, because a future round measuring song presence on dialogue clips with
this method will get zeros that mean nothing.

## What this does not do

- It does not place a hook on a beat. Nothing does — see §3, part 2.
- It does not judge whether the song *suits* the 33 clips. It shows the operator 10 of them
  with their scene text and lets him decide. That is the fit test, and it is his.
- The matcher tier is `vision_rule`, so a clip with no vision label cannot be reached by any
  description. 2,235 clips remain parked after the demo rule.
