### CORRECTION — that rewrite ran with the real lock FREE

I wrote `filelock.file_lock(filelock.lock_path_for(MASTER))`. `file_lock()` appends `.lock`
itself, so this locked **`master_leads.csv.lock.lock`** — a path no other writer touches —
while the 58k-row rewrite of the actual master proceeded unprotected. I reported it as done
"under the cross-process lock". It was not.

No damage: master was verified byte-identical for all 58,324 surviving rows immediately after
and again at the end of the round, and no other writer touched it in the window. But the
safety property I claimed was absent, and a concurrent appender would have been silently
clobbered. Another agent independently caught this (BL-817/818) and hardened `file_lock()` to
raise `LockPathMisuse` when handed a path already ending in `.lock`, so the mistake is now
unrepeatable rather than merely corrected in my copy.

## 3. THE POOL DID NOT GROW — four runs killed, $0.0330 for zero pages

This is the item that failed, and the first failure is mine.

| attempt | scope | outcome | page pulls | cost |
|---|---|---|---|---|
| 1 | 24 tags, target 100, $0.35 | **killed at ~7 min** — `Select-Object -First 40` in my own pipeline closed stdout and terminated python | 25 | $0.0150 |
| 2 | 24 tags, target 100, $0.30 | **killed** by the environment at ~10 tags | 10 | $0.0060 |
| 3 | 24 tags, target 30, $0.25, detached | **killed** at ~5 tags | 10 | $0.0060 |
| 4 | **6 tags**, target 15, $0.10, bounded | **killed** in the account-gate phase, after confirming 2 pages | 10 | $0.0060 |

**Attempt 1 was my bug.** `Select-Object -First N` stops the upstream pipeline once it has N
objects, which kills the producing process. The clean log ending with no traceback is the
signature. Attempts 2, 3 and 4 were stopped by something outside the run — the environment
did not sustain a long job in this session, and the full path needs ~1.7 h.

### Attempt 4 found two pages and lost them

It got past discovery, deduped correctly (5 candidates skipped as already-known **before**
spending), and **confirmed two new pages** — `@apissarenko85` (100% of recent posts carry the
format) and `@solidshampooz` (75%) — then died. Master is still at 41.

**This funnel appends only at the end of `run_from_config`**, so a killed run loses every page
it confirmed, having already paid for each one's account check. The clip walk, by contrast,
appends per account and would have kept them. An incremental append — or a resume file — is
the difference between four dead runs costing $0.033 and four partial runs that add up to a
grown pool. That is the actionable finding from this failure.

### A killed run is an unmetered run

All four deaths bypassed `run_from_config`'s metering `finally`, so the ledger never learned
about the page calls. I recorded them by hand as `repost_grow_killed*_unmetered`
(55 calls, $0.0330). That is a **floor, not an exact figure**: `hashtag_medias_clips` falls
back to `/top` when a tag has no clips surface, which is two billed requests for one logical
call, so the true cost is $0.033–$0.066.

This applies to every funnel, not just this one: spend is only recorded if the process
survives to its own `finally`. A `kill -9`, an OOM, or a closed stdout means money left the
account and the ledger does not know.

Nothing was corrupted. Attempts 1–3 died during the free discovery phase; attempt 4 reached
the paid gate but this funnel writes master only at the end, so there were no partial writes.
