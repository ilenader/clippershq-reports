## 1. THE MEME FILE — FIXED AT THE EXPORTER, AND THE NAME IS HONESTLY UNAVAILABLE

Two symptoms, one cause: `MEME_PAGES_BOT_READY.csv` carried **no `display_name` column**, so
every row fell through `message_template._name_for()` to the raw-handle branch and to tier
REACH, and `followers` was written as a raw integer.

**`meme_send_list.OUT_COLUMNS` now carries `display_name`, `date_sent` and `touch_number`**,
and `followers` goes through `writer.abbrev_count` — the same helper the primary send file
has always used, which is why `ALL_BOT_READY.csv` never had this defect. `9575159` → `9.6M`.

### THE NAME IS NOT AVAILABLE, AND I AM NOT GOING TO INVENT ONE

Measured, this interpreter:

| source | rows carrying a name |
|---|---|
| `master_leads.csv`, `source_hashtag == meme_pages` | **0 of 917** |
| the funnel's own resume store `scratch/resume/meme_pages.*.jsonl` | **0 of 303** (no `full_name` key at all) |

`meme_finder.profile_facts()` **fetches** `full_name` and nothing ever persisted it. So the
column is now carried through — `display_name` → `full_name` → `name`, first non-empty — and
will fill itself as the funnel re-walks pages. Today it is empty on all 874.

**A name derived from the handle is not acceptable and is not what I did** — that is the
exact defect (`Hi @cykl0psfilm,`). **The fallback is no name at all: `Hi there,`.** It is a
real greeting, the file already builds it, and it is the only honest option when the name was
never stored.

**The fallback he should be offered instead**, and it is cheap: `profile_facts` already
returns `full_name` on every profile call the funnel makes. Persisting it costs nothing new —
one field on the record — and every future meme row would greet a real name.

## 2. TIKTOK — 0 OF 115 BECAME 115 OF 115

`TIKTOK_PAGES_BOT_READY.csv` had **no `lead_kind` column**, so `render()` raised
`ValueError: lead_kind '' is not routable to a message` on every row. It also had no
`date_sent`/`touch_number`, so a send could not have been recorded even if it had rendered.

`COLUMNS` now carries `lead_kind`, `display_name`, `date_sent`, `touch_number`, and

repost partner, which is the clipper audience by definition, and master carries no
`lead_kind` for these rows at all. Naming the decision beats inventing one per row from
absent data.

**All 115 render.** `tests/test_bl1252_send_guard.py` asserts it over the whole file, not a
sample.

## 3. THE GREETING — A DEFENDED DECISION, OVERTURNED ON ITS OWN EVIDENCE

`@handle` greetings were deliberate (BL-977): *"One character converts a defect into a
convention."* That argument rested on a measurement in the same comment — **"only 36 rows
ever reach the handle branch at all."**

**Measured today: 1,300 of 4,852 — 26.8%.** ALL 436 of 3,978; MEME 864 of 874. The branch is
not a rare fallback any more; on the meme file it is essentially the whole file. A 36× change
in the population invalidates the trade-off it was priced against — and the operator has now
rejected it twice with an example each time.

`GREET_BY_HANDLE = False` in `message_template.py`. **The branch is kept behind the flag, not
deleted** — removing it would take BL-965's ordering fix (strip the leading `@` *before* the
usability test) with it, so `test_the_at_is_never_doubled` now flips the flag on deliberately
to keep that fix covered.

### AND A SECOND DEFECT THE FIRST ONE HID

Turning the greeting off dropped **436 primary rows to GENERIC and stripped their evidence** —
FULL 1,114 → 995, REACH 464 → 402, GENERIC 11 → 447. `pick_tier` required `f["name"]` for
FULL and REACH, so a row with a fandom and real view counts but no usable name lost its
numbers as well as its greeting. That coupling was invisible while the handle branch made
the name almost always truthy.

**He objected to the greeting, not the evidence.** `_clipper_message` already renders a
nameless row correctly (`name = f["name"] or "there"`), so only `pick_tier` tied them
together. Evidence now decides FULL/REACH; the name decides only whether we can do better
than "Hi there". After the fix: **FULL 1,116, REACH 464** — at or above the original, with
GENERIC at 264 (the rows that genuinely have nothing to say).

## 4. THE GUARD — IT RENDERS REAL ROWS OFF DISK

`clippershq/send_guard.py`. Refuses a send file that: is missing a column the send path
needs; RAISES in `render()`; greets a raw `@handle`; prints an unformatted number; or still
carries an `[[OPERATOR_PLACEHOLDER]]`.

**It opens the CSV that was just written and renders ACTUAL rows.** That is the whole point:
this project's most repeated failure is a test that manufactures its own input — a
reachability suite stayed green for two rounds by injecting the very field the runner never
produced. A guard for "the file's shape is wrong" that builds its own file cannot see the
defect it exists for.

Run against the files **before** the fix, it caught exactly the right things:

```
ALL_BOT_READY.csv          rows 3978  NOT SENDABLE   (13 unformatted numbers)  <- FALSE POSITIVE, see below
MEME_PAGES_BOT_READY.csv   rows 874   NOT SENDABLE   missing display_name, date_sent, touch_number
TIKTOK_PAGES_BOT_READY.csv rows 115   NOT SENDABLE   missing lead_kind…; 60 raised in render()
```

**The 13 on the primary were my own bug and I caught it by reading the output.** `\d{4,}`
matched the **year** in "the one from June 2026 did 1.4M views" — a correctly formatted
sentence on the one file that was already fine. A guard that cries wolf on a correct file is
a guard nobody keeps. `_unformatted_number()` now skips 4-digit runs in 1900–2099, and
`test_a_year_is_not_an_unformatted_number` pins it.

`tests/test_bl1252_send_guard.py`, **11 tests, green.** Four rebuild each historical defect
as a file and prove the guard refuses it; three read the shipped files off disk; three pin
the greeting policy and the tier decoupling.

## 9. WHAT I GOT WRONG

**I broke the meme file's ranking and shipped it before noticing.** Formatting `followers`
to `9.6M` *before* the sort meant `int("9.6M")` raised, every formatted row scored 0, and the
file went out with a 986-follower page at rank 1 and a 961k page at rank 870. Found by
reading the rebuilt file, not by any test. Fixed with a private `_followers_n` that
`DictWriter(extrasaction="ignore")` drops before writing, so the sort uses the raw count and
the file shows the compact one. Rank 1 is now 56.3M.

**My own guard's first version raised 13 false positives** on the one file that was already
correct, by matching a year as an unformatted number. Caught by reading its output.

**I clobbered my own baseline record.** `scratch/bl1252_before.json` held the master hash;
the defect census then wrote the same path and overwrote it. The hash was recoverable from
the round's own printed output and corroborated independently against BL-1250's copy stored
outside the repo — but the file should not have been reused for two purposes.
