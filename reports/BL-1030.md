# BL-1030 — the retrieval leg is under a ceiling, and the ceiling was proven by spending

**Four live paid runs. $0.040377 of the $0.05 authorised.** Every one stopped **on the
retrieval leg**. `config.json` untouched (161 keys, 5 campaigns, sha `8e02f8d6f6307ae8`),
`master_leads.csv` byte-identical.

| run | budget | retrieval | model | total | stopped by |
|---|---|---|---|---|---|
| 1 | $0.020 | $0.007200 | $0.009136 | $0.016336 | **retrieval** |
| 2 | $0.020 | $0.010800 | $0.006380 | $0.017181 | **retrieval** |
| 3 | $0.008 | $0.001800 | $0.000000 | $0.001800 | **retrieval** |
| 4 | $0.012 | $0.003000 | $0.002060 | $0.005060 | **retrieval** |

---

## What was actually wrong

`scratch/bl867_deep_label.py` accumulated `spent` from the **OpenRouter receipt only** and
broke on `spent >= BUDGET`. The IG retrieval that precedes every model call was metered and
flushed — and compared to nothing:

```
declared stage 3 cap : $0.25          (BL867_BUDGET)
model leg            : $0.1831   <-  OBEYED the cap and stopped under it
retrieval leg        : $0.4200   <-  700 calls at $0.0006, NO CEILING CHECKED
```

The cap did not fail. **It was never asked about the leg that spent the money.**

### The half that makes it worse than a missing check

Retrieval runs **first** and fails ~74% of the time, and a failed retrieval `continue`s
before any model call is made. So **the iterations that fail are exactly the iterations that
never advance the counter the cap reads.** The budget could not bind on the money actually
leaving, and the leg it could not see was the leg with the worst yield — three of every four
paid retrievals bought no label at all.

That is also why "just add the other leg to the total" is not sufficient: any fix that
charges only *successful* retrievals rebuilds the identical hole. The charge is taken from
the client's own receipt counter, whether the fetch worked or not.

## 1. One budget, both legs — `spend_ledger.TwoLegBudget`

Put in the money module rather than in the driver, because the sweep found eight drivers
with the same shape. `resolve_run_budget()` is `min(per-run, lifetime room)`; `ledger_total()`
raises `LedgerUnreadable` rather than returning a permissive number — BL-1013's rule, which
exists because a lifetime cap once armed $5.00 against a true $0.10 spend.

Three properties the class enforces that a hand-rolled check kept getting wrong:

- **Asked before the call.** `can_afford(leg, usd)` is consulted first; a budget consulted
  after the call has already spent the money it was meant to prevent. The retrieval leg is
  priced at the **worst case the driver permits** (`MAX_PAGES`), not the best.
- **Charged on failure too**, from `client.http_requests` read as a delta, so retries inside
  `retrieve()` are counted as the requests they really made.
- **A typo cannot create a free leg.** `charge("retreival", ...)` raises `KeyError` instead
  of silently opening a new untracked bucket.

`run_budget_usd=None` is refused outright — that is the BL-914 shape, where a run capped at
$0.05 was armed at ~$41.50.

## 2. PROVEN BY SPENDING — two live runs, both stopped by retrieval

Reading the code is not proof, so this ran for real.

### Run 1 — the cap binds

```
BUDGET  run $0.020000 = min(per-run $0.02, lifetime room $38.755578)  -- governs BOTH legs
BUDGET REACHED -- retrieval leg would take spend to $0.023536, over the $0.020000 run
                  budget (retrieval $0.007200 + model $0.009136 already spent)
  model leg     $0.009136  (4 call(s))
  retrieval leg $0.007200  (12 call(s))
  TOTAL         $0.016336   remaining $0.003664
  STOPPED BY    the retrieval leg
```

**The old rule would not have stopped here.** `spent` was $0.009136 — 46% of the $0.02
budget. The run halted because the *combined* total plus the next reservation crossed the
ceiling.

### The second defect, found by running it

The ledger moved by **exactly the retrieval leg**:

| | before | after | delta |
|---|---|---|---|
| `total_spent_usd` | 11.244422 | 11.251622 | **+0.007200** |
| `ig_spent_usd` | 8.032442 | 8.039642 | **+0.007200** |
| `vision_spent_usd` | 2.240780 | 2.240780 | **+0.000000** |

The model leg's **$0.009136 of real money never reached `spend.json`**. `flush_spend` has
recorded the retrieval half since BL-876; nothing here ever recorded the model half, so 56%
of this driver's true cost has been invisible on every pass it has ever made.

**This is not only a reporting gap.** `resolve_run_budget` computes the lifetime bound as
`cap − total_spent_usd`, so dollars that never land make lifetime room read *larger than it
is* — the same wrong-quantity family as BL-1013, arriving from the other side. Fixed with a
`record_vision()` modelled on `bl872_label`'s, including the `vision_calls` argument that
BL-1003 and BL-1013 each had to add after a row landed with real dollars beside `calls=0`.

### Run 2 — both legs reach the ledger, and it still stops on retrieval

```
BUDGET REACHED -- retrieval leg would take spend to $0.024380, over the $0.020000 run budget
  model leg     $0.006380  (2 call(s))
  retrieval leg $0.010800  (18 call(s))
  TOTAL         $0.017181   remaining $0.002819
  STOPPED BY    the retrieval leg
```

| | before | after | delta |
|---|---|---|---|
| `ig_spent_usd` | 8.039642 | 8.050442 | **+0.010800** ← retrieval leg exactly |
| `vision_spent_usd` | 2.240780 | 2.247160 | **+0.006380** ← model leg exactly |
| `total_spent_usd` | 11.251622 | 11.268802 | **+0.017180** |

The run's own arithmetic said **$0.017181**. The ledger moved **$0.017180**. Both legs are
now governed *and* recorded, and the books agree to a hundredth of a cent.

## 4. `flush()` raises on a wrong signature

`IncrementalMeter._record` is called by keyword — `calls=`, `label=`, `campaign=`. A
`record_fn` that does not take those names raised `TypeError`, which the handler counted as a
write failure and logged as *"could not write … Retrying on the next flush"*. It then failed
identically on every subsequent flush and at the final force-flush, so the run ended with
**every call unmetered** and a log that read like a flaky ledger.

Checked with `inspect.signature().bind` rather than by catching `TypeError`, because a
`TypeError` raised **inside** a correctly-shaped `record_fn` is a genuine runtime failure and
must keep its retry — catching the type cannot tell those apart. Verified all three ways:

- wrong signature → `MeterSignatureError` **raised**
- correct signature → flushes normally
- transient `OSError` → still returns `False`, keeps `pending`, counts the failure, and the
  **retry succeeds**

An uninspectable callable (C builtin, some `partial` shapes) is allowed through: an
inspection failure is not evidence of a wrong signature.

The guard proved itself immediately — it caught a wrong signature in **my own first draft of
its test**, where naming a counter dict `calls` had forced the parameter to be renamed.

## 5. Item 3 — already fixed, verified not re-done

BL-1000 reported a walk printing `spend $0.2094 of $0.1500 cap`, and **fixed it in the same
round** (`f3356d6`). `clip_runner.build_decision_log` now prefers the metered figure and
notes the divergence. Confirmed by driving it:

```
usd = 0.15   cap = 0.15
notes = ['halted on max_run_usd',
```

Both halves of the requirement hold: the displayed number **is** the governed one, and the
other is **labelled** rather than dropped. Three regression tests added so it stays that way,
including one asserting no note appears when the two agree.

Two files were deliberately left alone:

- **`clippershq/clip_pipeline.py`** — held by BL-899 (stale 36h) *and* BL-1028 (live). Its

That constraint has a cost worth recording: `LedgerUnreadable` now exists in **both**
`spend_ledger` and `clip_pipeline` with identical contracts. `clip_pipeline` imports
`spend_ledger`, so the canonical home is the one added here and clip_pipeline's should become
an alias — noted in the docstring rather than left to be rediscovered.
