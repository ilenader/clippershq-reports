## PART 0 — how production was protected while it was investigated

**Concurrency cap: exactly ONE database connection, held by me, never more.**

Two prior rounds exhausted the pool and one contributed to an outage, so the design put the risk beyond reach
rather than managing it:

- **All ten subagents were forbidden the database in writing.** Every brief carried a hard rule: no
  `run-select.js`, no Prisma client, no npm, no build. Where an agent needed a figure it wrote me the SELECT
  and I ran it. That is why several sections below carry queries the agents specified.
- **I ran every query myself, serially, one shell at a time.** At no point were two queries in flight.
- **The pool-analysis agent was additionally forbidden from opening a connection at all**, since touching the
  pool is the exact harm it was analysing.
- **Read-only throughout.** `scripts/run-select.js` refuses any write keyword.

**Measured while working: `max_connections` 90, 25 in use, 65 free, 1 active, 0 idle in transaction.** My
contribution was 1 of 90. The limit was never approached.

**One deliberate deviation, stated plainly:** the read-only queries ran from the main repository rather than
from `C:/w860`, because `run-select.js` needs only `pg` and `dotenv`, the main repo already had them, and a
second `npm ci` would have competed with BL-859 for disk and network while changing nothing. Read-only SELECTs
modify no file in either tree.

**Not run, deliberately:** no load test, no vendor API call, no Apify actor, no `EXPLAIN ANALYZE` on a large
table, no `pg_dump`, no write of any kind.

## PART 1 — a health check that actually checks

### What it returns today, probed rather than asserted

```
GET https://clipershq.com/api/health
{"ok":true,"ts":1788902945586}
HTTP 200 in 0.289465s
```

The source is twelve lines (`src/app/api/health/route.ts`): `NextResponse.json({ ok: true, ts: Date.now() })`.
**No database, no external call, no cache header.** Its own comment calls it a "Railway healthcheck target.
Deliberately lightweight."

**During the outage this endpoint returned 200 the entire time.** That is the whole finding, measured.

### THE CORRECTION THAT CHANGES THE FIX: do not make this endpoint touch the database

The obvious remedy is wrong, and the reason is in `railway.json`: **there is no `healthcheckPath`**, so Railway
is using a default TCP check today. The correct next step is for the owner to set `healthcheckPath`, and if
that path hits the database then **a Supabase blip during a deploy makes Railway refuse to promote a perfectly
healthy container** — turning a database incident into a deploy outage. That is the flap the route's comment
warns about.

**Two endpoints, two questions:**

| endpoint | question | consumer | must |
| --- | --- | --- | --- |
| `/api/health` | is this container alive? | Railway | stay twelve lines, unchanged |
| **`/api/health/ready`** (new) | is the system working? | an external monitor | reach the database and fail loudly |

Nothing else in the repo consumes `/api/health`, so adding a second endpoint costs nothing in compatibility.

### The spec for `/api/health/ready`

**The query**, chosen to prove two things at once with one indexed read:

```sql
SELECT "firedAt" FROM cron_runs WHERE kind = 'tracking' ORDER BY "firedAt" DESC LIMIT 1
```

`CronRun` carries `@@index([kind, firedAt])`, so this is a single index scan returning one row, and it proves
both *the database is reachable* and *the money cron is alive*. Import `db` from `@/lib/db`; never construct a
`PrismaClient`, which would add a whole new pool.

**The timeout must bound the wait for a pool slot, not just the query.** A `Promise.race` does not cancel the
underlying query and the connection stays checked out. Use the house pattern:
`db.$transaction(async (tx) => { await tx.$executeRawUnsafe("SET LOCAL statement_timeout = 2000"); … },
{ maxWait: 1500, timeout: 3000 })`. `maxWait` is the important knob: pool exhaustion then returns fast and
distinctly instead of hanging.

**No write probe on a public route.** There is no zero-row write available, and a write on an unauthenticated
endpoint is an abuse surface. If writability must be proven, do it inside the `CRON_SECRET`-gated watchdog as a
transaction that writes and then throws to roll back.

**Responses.** 200 `{"ok":true,"db":"up","cron":"ok"}`; 200 `{"ok":true,"db":"up","cron":"stale"}` when the
tracking heartbeat is older than 45 minutes (200 on purpose, because a stale cron is not "the site is down" and
paging for it trains the owner to ignore the alert); **503** `{"ok":false,"db":"down"}` on any failure, timeout
or unavailable pool slot.

**Headers:** `Cache-Control: no-store` plus `export const dynamic = "force-dynamic"`. The current endpoint sends
**no cache header at all** and sits behind `x-railway-edge`; a cached 200 in front of a dead app is a monitor
that lies.

**Cost:** one round trip on an already-warm pooled connection, roughly 1 to 3 ms server side, about 20 ms of
connection hold. At once a minute that is 1,440 calls a day, about 29 seconds of connection hold, roughly
0.03% duty cycle on one slot, and **zero new connections**. Safe against 90 and safe against the 60 the code
still assumes.

**What an unauthenticated caller may see, exhaustively:** `ok` (boolean), `db` (`"up"`/`"down"`), `cron`
(`"ok"`/`"stale"`). Three fields, all booleans or closed enums.

**What must never appear:** any exception or Prisma error message (they leak host, database and role names and
sometimes the connection string), any table or column name, any row count, the heartbeat timestamp or minutes
since it (which tells an attacker the money cron's cadence and when the platform is unattended), measured query
latency (a timing oracle for pool pressure), and any version, region or pool size.

**Checked for existing leaks:** only 7 of 252 API routes carry no auth import. `dev-auth` 404s in production
before reading anything; the Resend webhook hard-fails 401 without its secret; both click trackers are
length-bounded and IP-rate-limited. An unauthenticated `GET /api/admin/users` returns **401 with body `[]`**,
no error text and no stack. **No leak found.**

### The alerting, and how little the owner has to do

**What is already there and needs no setup at all.** `sendOwnerAlert` exists (`src/lib/email.ts:1183-1207`),
goes through Resend, retries, and is already used for budget and cron alerts. The owner-bell path has a 24-hour
per-type dedup and a global cap of 3 alerts an hour, both deliberate after an earlier round emailed 15 false
alarms in one run. `scripts/notify-owner-build.ts` proves the Resend path from outside the app and **returned
status 200 several times during this very session.** An internal alerter is a small addition to an existing
system, not a new one.

**THE LIMIT, AND IT IS STRUCTURAL, NOT THEORETICAL.** The watchdog runs **in the same process it watches**:
`instrumentation.ts` starts the scheduler inside the Next server, which fires jobs at `127.0.0.1`. A dead
container is a dead scheduler. Worse, the alert path itself needs the database and the pool, so a
pool-exhaustion outage disables the alerter through the same fault that caused it.

- **An internal alerter CAN catch:** a money cron stopped while the web app is alive, server-error spikes,
  earnings drift, budget locks, vendor quota.
- **It structurally CANNOT catch:** a container crash-loop, an OOM, a failed deploy, database or pool
  exhaustion, an edge failure, DNS or TLS expiry. **That is every shape the 24-hour outage actually took.**

**So the monitor must be outside the platform. That is the one genuinely external thing, and it is smaller
than expected.**

**Measured: there is NO Discord webhook anywhere.** A grep for `DISCORD_WEBHOOK` across `src` and `scripts`
returns **0 hits**. It would be a new secret and a new failure surface, and the project's Discord posture is
deliberately ban-cautious. Email already reaches him and is already proven.

**The shortest path, and it is not a new signup.** The owner **already has a cron-job.org account**, and it
already pings `/api/cron/tracking` every 10 minutes. In that same account:

1. **Turn on "notify on failure" for the existing tracking job.** When Railway is down the ping gets a 502.
   **This one setting, alone, would have cut a 24-hour blind outage to about 20 minutes.** Zero code, zero
   deploy.
2. **Add one job** pointed at `/api/health/ready`, every minute, notify on failure. About four clicks.

**Sentry is already wired** (`@sentry/nextjs` 10.50, server, edge and client configs, `withSentryConfig`) and
does offer uptime monitoring, which is the better long-term home because it correlates uptime with the errors
already flowing in. It is more clicks and whether it is included is a plan question the owner must check. **Do
not sign up for a third pinger.**

**What should alert, kept small so every alert means something:**

| condition | threshold | channel | cooldown |
| --- | --- | --- | --- |
| `/api/health/ready` not 200 | **3 consecutive** failures (never 1, a redeploy blip must not page) | cron-job.org to owner email, external | one page, then silence until recovery |
| tracking cron stale | 45 min | owner email | 24 h dedup, already implemented |
| `SERVER_ERROR` rows | over 20 in an hour | bell only | 1 h, already implemented |
| every other cron stale | per kind | bell only | 24 h, already implemented |

Only the first is new.

### Today's real numbers

**Snapshots written per day, measured:**

| 2026-09-08 | 807 | outage until 19:51 |

**BL-856's figure of about 4,320 a day is arithmetically correct for the code default and is NOT a hard cap.**
The ceiling is `6 ticks/hour × CLIPS_PER_TICK × 24`, and `CLIPS_PER_TICK` defaults to 30 (clamped 5 to 500) with
a kill switch. **Every normal day measured exceeds 4,320, and 6 September reached 8,483.** The figure was
inherited rather than verified; it is now verified and it is wrong as a ceiling.

### CORRECTION ONE: the backlog is 1,316, not 6,783

The naive count of `isActive AND nextCheckAt <= now()` is **6,783** with the oldest due since **2026-05-14**.
That is what the route's own probe counts, and it is an **upper bound that applies none of the cron's
eligibility filters**. Applying the filters the cron actually uses:

| --- | --- | --- | --- | --- |
| 60 | 15 | 360 | 0 | **0** |
| 120 | 154 | 1,848 | 0 | **0** |

| 480 | 327 | 981 | 0 | **0** |
| 720 | 25 | 50 | 0 | **0** |
| 1,440 | 467 | 467 | 357 | **0** |
| 2,880 | 212 | 106 | 120 | **0** |
| 4,320 | 2,212 | 737 | 780 | **0** |
| 7,200 | 363 | 73 | 55 | **0** |
| 21,600 | 79 | 5 | 4 | **0** |
| **TOTAL** | **4,196** | **6,677** | **1,316** | **0** |

**Every fast rung has zero jobs due. The cron is keeping up perfectly with everything that can still earn.**

### CORRECTION TWO: the 2,006 "starved earning clips" are not starved. I nearly published that they were

My first pass found 3,100 active jobs unchecked for over 30 days, 2,006 of them on APPROVED, non-unavailable
clips, and that reads like silent money loss. **It is not.** Every one is excluded for a legitimate reason:

| why the job is not polled | jobs | approved clips |
| --- | --- | --- |
| **campaign is PAST, COMPLETED or DRAFT** | **2,307** | **2,006** |
| video is gone from the platform | 787 | 608 |
| clip deleted | 6 | 0 |
| **genuinely eligible and starved** | **0** | **0** |

**Not one clip that could still earn has gone unpolled.** The campaign is over; polling it would change
nothing. **The starvation hypothesis is refuted by measurement.**

### What IS true, and it is a fragility rather than a fire

- **Demand is 6,677 checks a day against a nominal ceiling of 4,320.** It keeps up only because the tick
  claims its hour only when it fully drains, so with a backlog present **all 144 ticks a day run a full batch
  instead of 24**. That roughly 6× amplification is doing the work, and it is also a 6× vendor call exposure.
  If the backlog ever fully drains, the amplification stops and capacity halves.
- **The 3,100 excluded jobs are never marked inactive.** They inflate every naive backlog count including the
  platform's own probe. `retire-dead-clips`, the job that would clear the 787 unavailable ones, **has never run
  once** (PART 3).
- **At saturation the order is `checkIntervalMin ASC` then `nextCheckAt ASC`.** Fast rungs preempt slow ones
  absolutely, with no aging term, and a starved job is never polled so its rung never changes and it can never
  rise. Today nothing is starved, so this is latent. Under launch load it is the mechanism that would bite, and
  it would bite **established clippers whose earnings freeze while new clippers work fine.**
- **Nobody would notice.** The watchdog tests heartbeat freshness only and reads green while the cron fires
  perfectly and polls nothing useful. The zero-work monitor requires `processed === 0`, and a saturated tick
  processes 30. **There is no overdue-job detector anywhere in the codebase.** A clipper's own screen says
  "Updates hourly" regardless.

### The fix, classified

**Code, and it costs nothing in vendor spend:** add an aging term to the due-jobs ordering, collecting most of
each tick by the current priority and a slice by pure `nextCheckAt ASC`. Same number of polls, allocated so no
rung can starve forever.

**Config, free:** enable `retire-dead-clips`, which has never run, to clear the 787 unavailable jobs and stop
them inflating the queue.

**Schedule, the cheapest capacity lever:** 10 minutes to 5 doubles ticks per hour and doubles the ceiling.
It does not over-poll, because `nextCheckAt` is clock-aligned, so each clip is still polled at most once per
its own interval.

**Cost against the existing roughly $139 a month for Instagram:** the ordering fix adds **$0**. The schedule
change adds at most **+$139 a month** in the worst case where poll volume genuinely doubles, and less in
practice because the ceiling only binds in saturated hours. **Not an instance size question:** nothing here is
CPU or memory bound.

on recovery the external pinger refreshes the heartbeat within 10 minutes while the watchdog only looks every
30 — **so an outage of any length produces no alert roughly two thirds of the time**, and when it does the
alert arrives after service is restored.

*(`tracking-timeout` last fired 2026-09-07 21:10:47, inside the outage window. A genuine artefact of it.)*

**Alerts today:** only for tracking, and only if the process is alive. **First symptom: a clipper complains.
Time to notice: hours to a day.**

### 2. A vendor key expiring — **for the two that carry money, nobody would ever know**

- **`LAMATOK_KEY` dead:** all TikTok views freeze. The batch path discards the error unless the verdict is
  "gone". **Nothing visible changes anywhere. Detection: never.**
- **`HIKERAPI_KEY` dead:** all Instagram views freeze. A 401 is filed as "this post is not a reel" rather than
  an error, so the outage detector's failure ratio stays at 0% forever. **Detection: never**, except as clipper
  support messages about bio verification.
- **`YOUTUBE_API_KEY` dead:** fails closed with a message naming the variable. The fastest human signal of the
  eight, and the only one that fails closed.

**No vendor failure reaches Sentry.** The only Sentry calls for vendors sit behind an Apify token that is
hardcoded `null`, so the best vendor observability in the repo is unreachable dead code. And
`sentry.server.config.ts` **drops any exception whose message contains `Unauthorized`, `Forbidden` or
`rate limit`** — so the obvious fix would be discarded by the filter meant to reduce auth noise.

**Why silence costs money:** on a total provider miss the tracker writes no snapshot, no strike, no flag, and
just advances `nextCheckAt`. Views stay at last known, earnings are computed off that stored count, and every
dashboard looks healthy while a clipper stops earning on views they genuinely got.

**Spend:** one vendor has a dollar ledger, one has a real budget cap. `HIKERAPI_DAILY_BUDGET_USD` is an email,
not a cap; the gate was deliberately deleted. A runaway burns prepaid quota rather than dollars, and the
genuinely uncapped exposure is ScrapeBadger at 60 accounts × 5 credits per run with no counter.

**Worth building: one freshness alarm** — count snapshots written in the last 2 hours, and count approved live
clips whose newest snapshot is older than 6 hours. It needs no vendor cooperation and catches a dead key, a
silent-empty provider and a stalled cron with one query.

### 3. Storage filling — **one tile, and it stops moving exactly when it matters**

The only storage instrument on the platform is a command-center tile running `pg_database_size`. It has a
hardcoded **500 MB** denominator on a 2 GB instance and a `Math.min(100, …)` clamp, so **once the database
passed 500 MB it reads a flat 100% forever and conveys nothing**. It is wrapped in a bare catch, so on failure
it shows a dash that looks like a UI nit.

**Measured: the database is 718 MB.** So the gauge has been pinned and useless for some time.

**`POST /api/upload` is open to every logged-in user**, 5 MB per file, 20 per hour, into a public bucket, with
**no role check** despite its own comment claiming it is owner-gated, and **no userId in the object key**, so a
file cannot be attributed or cleaned up. That is 2.4 GB a day per account and no delete path exists.

**Nothing writes to the container filesystem** (zero `fs` writes under `src/`), which is genuinely good.

### 4. The connection pool — **third on the list, and both prior incidents were self-inflicted**

Web pool 48, cron pool 10, and **`connection_limit=1` in the URL is inert** because the driver adapter reads
`max` and never that parameter.

**A real config drift, measured:** the code sizes the pool against a documented **60-connection ceiling** and
says "Do NOT raise above 50", while the live limit is **90**. The instance was upgraded and the comment now
gives wrong guidance to the next person. About 32 connections of headroom are unused.

**`connectionTimeoutMillis` is never set**, so a request waiting for a slot waits forever. That is the "loads
forever" symptom rather than a fast failure.

**Both documented pool incidents were caused by agent dev servers, not by users, and neither produced a code
fix.** The mechanism is unchanged. And a pool timeout today is mapped to a friendly 503 **without a
`console.error`**, so it never reaches Sentry and produces zero trace.

**64 interactive transactions were checked and not one holds a connection across a vendor call.** That is good
engineering and I could not break it.

### 6. An endpoint returning empty on error — **about thirty-five of them, and this is how the platform looked green**

BL-837 fixed three. **All three are still fixed**, confirmed on current code. But the pattern is widespread,
and during the outage, for as long as Railway served pages:

- a clipper opening `/earnings` saw **$0.00 earned, $0.00 available, no campaigns** — not an error
- a clipper opening `/payouts` saw **$0.00 available and a dead withdraw button**
- a clipper opening `/campaigns` saw **every campaign at 0% of budget spent**
- anyone locked out who requested a magic link was told **"check your email"** and no email was sent
- **the owner's command center showed $0 revenue, $0 paid, no top clippers and no overdue payout — and cached
  that for five minutes at a time, so it kept showing after recovery**

**The failure was reported by five endpoints and concealed by roughly thirty-five.**

**The worst instance is not a display defect.** `getCampaignBudgetStatus` returns `null` both when a campaign
has no budget and when the read failed. Four budget defences read that one function and every one treats
`null` as permission, including **the L1 budget hard lock in the earnings writer**. It is the heaviest read in
the write path, and BL-857 measured heavy paths failing about two hours before light ones on 7 September, so
the window was open. **I cannot say it fired without a query I did not run; the path is open and the conditions
were present.**

**The house rule to apply:** an empty list, a zero and a null are *answers*. A route may return one only when
the database answered and the answer was genuinely empty. If the query threw, the response carries a 5xx and a
sentence. And **a helper must never return, on error, a value it also returns on success.**

Every money-critical DB-only object was checked directly and **all eight exist, unique and valid**:
`uq_payout_open_per_user_campaign`, `uq_trainer_active_per_trainee`, `uq_clip_norm_open_per_campaign`,
`marketplace_clip_posts_submissionId_platform_key`, `mla_campaign_clipacct_active_unique`, both campaign ticket

- **BL-835's audit cascade is fixed:** `audit_logs_userId_fkey` is **SET NULL** with `userId` **nullable**.
- **BL-845's missing unique index exists.**
- The `marketplace_chat_threads` CHECK **exists** (`CHECK (("userAId" < "userBId"))`) **despite having no

**The finding is the absence of a gate.** Two drift scripts exist; **neither runs in the build** and both

**Both known historical defects would have returned "no drift detected."** And the schema runner refuses
`ALTER COLUMN`, `DROP CONSTRAINT` and `ALTER TYPE`, so nullability, FK-rule and enum drift can never be
repaired automatically — which is why the audit cascade survived from May to September.

## PART 5 — what breaks first under launch load

**The first thing to break is the tracking cron, and it is already at its limit.**

**The number: demand is 6,677 checks a day against a nominal ceiling of 4,320.** It keeps up only because the
backlog prevents the hour being claimed, so all 144 ticks run a full batch instead of 24.

**A new clip costs 54 checks in its first five days**, amortising to **10.8 checks a day**. Against measured
throughput of roughly 5,000 to 8,500 a day and existing demand of 6,677, **marginal headroom is close to
zero.** Every marketplace clip enters this same queue.

**The symptom is not an error page.** Collection sorts fastest-cadence first, so new clips are served and the
slowest rungs starve. **Launch-day harm lands on established clippers whose earnings freeze while new clippers
work fine**, which reads as a money bug and generates tickets.

**Second: the Postgres instance**, which is what actually caused the outage. The Small upgrade bought +50%, not
an order of magnitude. The load is query volume rather than connections. The largest multiplier is the streak
walk, which issues **one query per day of streak, up to 400**, on every dashboard load and every clip submit.
**BL-857 just protected streaks, so streaks are about to get longer.**

**Third: the connection pool**, at an estimated 13 concurrent submissions per second, roughly 47,000 clips an
hour. **Users will not reach it.** Both documented incidents were caused by an agent's dev server, and with
`connectionTimeoutMillis` unset the symptom is requests queuing forever rather than failing fast.

**Fourth: RAM**, with no memory monitor anywhere. One owner-triggered spike exists: opening the growth admin
page asks for up to 180,000 rows in three concurrent queries.
