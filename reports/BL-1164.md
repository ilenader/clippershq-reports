## Fault 1 — "leads 0" while the log showed leads

**The counter is not wrong. It is written once, at the end.** Hand-checked on disk: while the
run was live, `scratch/runs/spotify-resume-20260806-145616.json` contained `leads: 0` with
`stage` updating on every single artist. At completion the sibling run's file contained
`leads: 43`. So the funnel rewrites `stage` ~1,000 times and fills `leads` exactly once, when
it is too late to be useful. For a 28-minute run the card shows `0` for 28 minutes and then
the truth for a moment.

**The real fix is in `clippershq/`, and I could not make it.** `run.py`, `spotify_finder.py`,
`run_status.py` and `control.py` are all held by **BL-1160** and all four are ` M` mid-edit.
The precondition is explicit that a dirty file I do not hold means stop, so I did not touch
them.

**What ships instead is not a workaround.** Every decision is already printed by the funnel,
one line per artist, in a shape stable for many rounds — the operator was being told to read
that log to find out whether his run worked. `GET /api/run_breakdown` counts those lines and
the card renders them live. It is labelled **"counted from the run's own log"** on screen,
always, and it never silently replaces the funnel's own figure: when both have a number and
they differ, the card shows both and names which is which.

**`unclassified` is what makes it trustworthy, and it earned its keep immediately.** The
first draft recognised six outcomes and left **19 lines unclassified** on the live log. Those
19 were `wrong language`, `audience size unknown`, and — the one that mattered — **`got a
business/manager email`, which is a contactable lead**. A count that had merely looked
plausible would have reported 38 instead of 43. It is now 0 unclassified, and the card says
the breakdown is incomplete if that ever rises.

## Fault 4 — "no report for 448s", and what the run was really doing

The heartbeat **was** installed and **did** run: `ticks: 966` in the status file. Then it
stopped, at **15:22:40** — the same second as the log's last content line. They did not fail
independently; the whole process went quiet at once.

What I measured next is the part that matters:

- the log did not grow by **one byte** in 733 s, and the status file not in 902 s
- the process was **not** idle: **19.27 CPU-seconds in 20 wall-seconds**, ~96% of one core
- 20 threads, and the sibling pids (18700, 17512) were dead stubs at 0% — pid 9228 was the
  only thing doing anything
- the last log lines were `enrich_links` parsing **250,000-character** documents
  (linktr.ee 253,793; open.spotify.com 251,088), and before that a **174-second** country
  lookup

So the run was **spinning at full CPU for 17 minutes producing nothing** — not blocked on a
vendor call, which would sleep near 0%.

**Why the heartbeat could not reach the panel.** The heartbeat is a Python thread. A thread
cannot be scheduled while another thread holds the GIL inside a long native call, so a
heartbeat thread cannot escape the condition it exists to report. That is consistent with
every measurement above — ticks and log stopping in the same second, full CPU, no output.
**I could not confirm it with a stack**: `py-spy dump --nonblocking` failed at `OpenProcess`
with error 87 because the process had exited seconds earlier. I am naming this as the
explanation that fits the evidence, not as a proven cause.

**The process died on its own at ~15:39–15:40.** I did not kill it: every probe I ran was
read-only (`Get-Process`, `OpenProcess` with `PROCESS_QUERY_LIMITED_INFORMATION`), and the
one attach I attempted never attached — it failed because the pid was already gone. BL-1160
then restarted it as `spotify-resume-20260806-154053`, which ran 365 s, wrote the spreadsheet
and **completed** with `leads: 43`.

`enrich_links` is **FREE** in the claim registry, so a size or time bound on the parse is
available to whoever takes it. I did not take it: I could not reproduce the wedge without a
live run to observe, and shipping a speculative bound to a file nobody holds, on the strength
of an inference I could not confirm with a stack, is how a plausible fix becomes a permanent
one.

## A defect I introduced this round, caught in the browser

The first version of `leadsCell` preferred the log-derived count whenever the funnel's own
figure was 0 — and rendered **"leads 0 from its log"** over a completed run whose real answer
was **43**.

The cause is worth recording: **a resumed run opens a NEW log file.** The card points at the
newest log for that funnel, which was the 3.7 KB resume segment holding zero decisions, while
the 118 KB segment holding 1,044 decisions was the previous file. Deriving a zero from a file
that simply has nothing in it is a fabricated zero, and it is worse than the counter it was
meant to fix, because it overrides a right answer with a wrong one. `decision_lines` is now
the guard: no decisions, no derivation. A test pins it.

This is also the standing limitation of the breakdown: **for a resumed run it counts the
current segment only.** The run-ids differ between segments (`...-145616`, `...-154053`), so
there is nothing to group them by without changes in `clippershq/`, which I do not hold.
