## 1. The named branch, and the one next to it

### `bl895_finish.py:195` — closed, and proven by running it

The brief is exactly right about the shape. `ask()` raised, the `except urllib.error.HTTPError` handler counted the code into a `Counter` that dies with the process, printed a line, and `continue`d. **`vision_attempts` is bumped by `record_failure` alone** (`clip_vision.py:497`), so the clip stayed at `attempts=0`, matched `not is_labelled(r) and attempts_of(r) < MAX_ATTEMPTS` on every later pass, and was re-bought forever. The fix that closes it sat **two lines below**, in a handler carrying a comment saying the leak was closed.

**VERIFIED by driving the real `main()` loop** — real `record_failure`, real library writer, real selector, with only the two things that cost money replaced (`CM.retrieve` returns bytes, `ask` raises a chosen code). `$0.00`, no request left the machine. 25 assertions, all green (`scratch/bl959_paidsilent.py`):

```
HTTP 429   record written 'openrouter HTTP 429'  kind=transport  attempts=0  rev 1->2  still selectable
HTTP 502   record written 'openrouter HTTP 502'  kind=transport  attempts=0  rev 1->2  still selectable
HTTP 400   record written 'openrouter HTTP 400'  kind=content    attempts=1  rev 1->2
           ...and on the second 400: RETIRED. The silent branch could never do this.
the leak, reproduced: with nothing written, the clip is re-selected on 5 of 5 passes
```

**The code is carried into the reason string on purpose, and that is the part worth arguing with.** `is_transport_error` matches `"http 5"` and `"http 429"`, so 429/5xx record **without** charging the retirement budget — correct, they are facts about the vendor that minute. A 400/404/413 matches nothing, falls to **content**, and **does** count toward retirement — also correct, those are facts about this clip's payload. **The generic handler below could not have made that distinction**: its reason string contains `"HTTPError"`, which matches the transport list unconditionally, so routing every code through it would have made a permanently-rejected clip immortal. That is why this is a new handler rather than a deletion.

**The price. The brief's $2.16 per 1,000 is confirmed and re-derived** — `$0.000807` retrieval + `$0.001355` model = `$0.002162` per item that hits the branch. The $0.15 in circulation predates the retrieval leg being counted at all (BL-886/887) and counts no model call. Five metered passes ran with this open.

## 2. Two undeclared fields were three — and the third was exempted by hand

`field()` returns a value only when the key is in `CLIP_FIELDS` **and** the record carries a provenance entry in `READABLE`. Both halves, or nothing comes back.

### CORRECTION — `vision_reopened_by` is the third, and the sweep was told to ignore it

`bl928_reopen.reopen()` writes, on consecutive lines:

```python
new["vision_reopened_by"]  = "BL-928"     # line 84   <- undeclared, NOT reported
new["vision_reopened_why"] = why          # line 85   <- undeclared, reported by BL-954
prov["vision_reopened_by"]  = CL.DECLARED # line 87
prov["vision_reopened_why"] = CL.DECLARED # line 88
```

BL-954's sweep reported line 85 and skipped line 84. **Not a parsing miss — `"vision_reopened_by"` was sitting in a hand-written `machinery` exemption set inside the sweep** (`bl951_paidsilent.py:145`). A guard's exemption list is the first place to look when it has never fired on something it should.

**It is not machinery, and its own writer says so.** `prov["vision_reopened_by"] = DECLARED` is a statement that a consumer is meant to read it. Real machinery — `rev`, `provenance`, `schema_version`, `ts` — is never attributed by anybody. So the sweep no longer honours a hand list silently: **it cross-checks the exemption set against every `prov[...] =` line in the tree and fails loudly on any entry that is attributed somewhere.** Exit code is non-zero on either finding, because a guard that can be quietly wrong is not a guard.

```
WRITTEN-BUT-NEVER-DECLARED SWEEP
   declared fields          81
   undeclared keys assigned 0
   exemption list           7 entries, 0 wrongly exempted
```

### `derivation` — the library writing a field its own reader cannot return

`build_record` set `rec["derivation"]` and gave it no provenance entry at all, so `field(rec, "derivation")` returned `None` for a value that function had just computed. **Declaring it would have been half a fix and the half that looks complete** — the same trap `speech_frac` sat in for a round. It now goes through `put()` like every other field, so the value and its tier are written together, and the empty case is stored as `ABSENT` rather than left as a hole, because *"no versioned field on this row carries a value"* is a different fact from *"nobody looked"*.

It is a **field**, not machinery, and the distinction is worth being exact about because it looks like machinery: `provenance` is the block `field()` consults, so it cannot be read through the mechanism it implements; `derivation` is a fact **about the clip** that `stale_fields()` reads to decide whether the row needs recomputing, with exactly the same standing as `vision_model`, declared since BL-849 to answer the same question for a model instead of a constant.

**VERIFIED end-to-end through the real write path** — `build_record → append → read_all → field()`, not a hand-built dict (`scratch/bl959_fields.py`, 20 assertions green):

```
build_record wrote a token   {'format': 'f25f8f13'}      and ATTRIBUTED it  'derived'
field() returns it in memory · after a disk round-trip · in readable_fields()
stale_fields() still reads current                       []
no versioned field -> field() is None, not {} ; tier is ABSENT, not missing
reopen(): field(vision_reopened_by)='BL-928'  field(vision_reopened_why)='vendor outage...'
```

### GAP — 1,950 stored rows are still unreadable, and I did not run the backfill

**MEASURED: 1,950 of 2,003 clips carry a derivation token and 0 of them are attributed.** Declaring the field does not retroactively attribute what is already on disk. `merge_over` now attributes it on any rewrite, so a row becomes readable the moment anything touches it — but a row nothing touches stays unreadable.

The backfill costs $0 and makes no network call. **I did not run it**: it appends ~1,950 rows to a live 2,003-clip store that nine other rounds are reading this minute, and roughly doubling the file is the owner's call, not a side effect of a declaration.

**`stale_fields()` therefore still reads `derivation` with a raw `.get()`, deliberately, and this is the one place that is right.** Switching it to `field()` would return `{}` for all 1,950 — and that function counts a missing token as **stale** — silently reclassifying every one of those rows as needing recomputation. That is a migration disguised as a one-word change. The reason is written into the source, not left for the next reader to rediscover.

## 3. Paid for, then discarded — six values, each priced

**Two different shapes, and BL-952 swept only one of them.**

| | |
|---|---|
| **RECEIVED**-then-discarded | a key the vendor **sent** us and no line reads. BL-952 measured this over 170 stored media: 15 kept, 16 read-then-dropped, 106 never read, 87 always-empty. |

The second shape is worse, and it is where `audio` lives: a vendor key can at least be re-read from a stored envelope for $0, while a computed value **dies with the process** and can only be recovered by paying for the call again.

**The route it changes, and the confound it leaves.** `audio_decodable` is only ever produced on the `AUDIO_OK` path (`clip_media.py:536`). On a mux failure it is never computed — so a stored `None` means **either** "this clip has no audio track" **or** "nobody looked". That is precisely the tri-state `CLIP_FIELDS` warns about, collapsed one level up, and **only `audio` separates the two.** BL-940's split is 50.6% keep-original / 49.4% mute-and-replace, and its single render failure was the intersection: `keep-original` **must** decode.

**A sharper reading of BL-947 falls out of this.** BL-947 declared `audio_decodable` and the field is at **4.3% (87/2,003)** — and every one of those 87 came from BL-947's own backfill over media already on local disk. **The retrieval path has still never written it.** The declaration was fixed; the producer was not. Same two-halves failure as §2, one layer out.

### B. Received on a paid response — `original_lang_for_translations`

**VERIFIED, 42.9% (73 of 170) on BL-952's exact sample scope, re-measured.** Values are ISO-639-1: `en=51, pt=10, hi=5, es=4, ja=1, ru=1, id=1`. Read at `ig_discovery.py:364` into `post_lang` — **on the LEAD path only**. It reaches no clip record.

**CORRECTION to the obvious fix — the brief points at the wrong destination field.** The clip library's `language` column (21/2,003 = 1.0%) is **the spoken language of the WORK**, parsed from a `Language:` label an account wrote in a caption. Its stored values are free text:

```
'English' x16 · 'English / Multilingual' · '​English' · 'Turkish'
'Mandarin / Cantonese / Hindi / English' · 'English / French'
```

`original_lang_for_translations` is an ISO code for **the language of the caption text**. Writing one into the other is the MEMEBOT-046 units bug with different nouns, and the 1.0% column is not the hole it fills.

**The thing it actually answers for is real, and the brief is right about that half.** `quality_gate.detect_language(text)` is a hand-rolled offline guess over caption/bio text, and `repost_finder.py:517` carries an **accent-blind fallback** built by BL-873 precisely because OCR of an all-caps caption bar drops the diacritics the detector identifies Portuguese/Spanish/Italian by — measured on identical words, `"SE VOCÊ É FÃ DO FÉLIX..."` rejects with accents and is **kept** without them. An ISO code has no diacritics to lose. It is free, on 42.9% of media we already buy, and unwired on both the clip path and the gate. **Cost to keep: $0.0000. Cost to re-acquire: one page, $0.0006.**

## Honest limits

- **The 16 ONESHOT branches are still open and I left them on purpose.** BL-952 priced them at $0.60–$0.81 per 1,000 that hit one, and each is a one-shot measurement where a failure shrinks the sample rather than recurring. That is a judgement about recurrence, hand-read by BL-952, and if it is wrong for any of those files the branch is worse than reported. **GAP.**
- **`bl842_gemini`'s failure rows make a clip permanently `done`, including after a transient 502.** For a RERUN measurement runner that is the intended trade — the spend becomes visible and is not repeated blindly — but it is a real behaviour change: recovering such a clip now needs the row deleted from the JSONL. It has no downstream readers (verified), so nothing else is affected.
- **`bl838_gemini_n100`'s bound is a range, not a number.** I cannot tell a billed-then-raised call from one that never opened a socket, so the report gives both ends. Narrowing it needs a receipt from the client, and BL-897 already established a receipt is only authoritative if the calls went through that client.
- **The derivation backfill is named, measured and NOT run.** 1,950 rows, $0, local CPU — and roughly a doubling of a live store nine rounds are reading. Until it runs, `field(rec, "derivation")` is None for 97% of the library and only `stale_fields()`' raw read keeps working.
- **The three field fixes are unit-proven, not run in production.** They are exercised through the real write path on a temp library; no live labelling pass has written one.
- **`bl867_deep_label.py:174` is a static fix.** The branch is argued from reading and from BL-954's own forced-error proof of the same `record_failure` call; **no live run has hit the patched oversize path.**
- **The discarded-value sweep reads `clip_media.retrieve` only.** `clip_pipeline`, the funnels and the crawlers also compute values inside paid calls and none was swept. The `audio` finding is one function's result dict, not the tree's.
- **I did not measure `original_lang_for_translations` on the REPOST funnel's own response**, which is where the accent-blind fallback actually runs. The 42.9% is on `/gql/user/clips` and hashtag envelopes. Whether the repost path's payload carries the key at all is **unmeasured** — and if it does not, the cheapest fix for that gate does not exist. **GAP.**
- **I did not get a fully green tree and I am not going to describe one.** `test_claims_manifest.py` is red on another round's manifest header and will stay red until that round fixes it. Two other suites flipped red mid-run and pass standalone. Every one of the three is diagnosed above; none touches a file this round changed.
- **`bl842_gemini` and `bl838_gemini_n100` were BL-952's to leave and I took them.** BL-952 said stopping at the two UNBOUNDED-adjacent files was a judgement call a reader might disagree with. I disagreed with it, and the reason is in the classification rather than in ambition: RERUN re-pays, and a class that re-pays is the same defect at a different rate.
