## 1. `touch_number`, end to end

Master carries the column and **0 of 59,006 rows had a value**. Three legs; one was already
fine and two were not.

### The blocker's diagnosis was wrong, and that matters

`docs/SENDING.md` BLOCKER 5:

> *"Re-importing a stamped list returns `matched=3, updated=0` — already-sent rows are
> refused by design, but that means `touch_number=2` never lands."*

Reading `apply_outcome` and `mark_sent_from_csv`, no such refusal exists: `updated` is
`len(targets)` and `apply_outcome` sets fields unconditionally. A doc and a reading of the
code disagreeing is the case where you **run it**. Against a copy of the real master:

```
--- stamp TOUCH 1 ---   keys=3 matched=3 updated=3 unmatched=[] ambiguous=[]
--- stamp TOUCH 2 ---   keys=3 matched=3 updated=3 unmatched=[] ambiguous=[]
    touch_number 1 -> 2, date_sent 2026-08-02 -> 2026-08-09
```

**The write path was never broken.** Had I trusted the blocker I would have "fixed" a
working code path and left the two real gaps open.

### What was actually missing

| leg | before | after |
|---|---|---|
| **export** | `BOT_READY_COLUMNS` did not carry it — no follow-up list could be built, and a first contact could not be told from a second | carries `date_sent` **and** `touch_number`, appended last so existing columns keep their byte positions |
| **record** | already worked | pinned by `tests/test_touch_number.py` so it cannot regress unnoticed |
| **analyse** | `outcome_stats` had no touch dimension — the one question a follow-up is run to answer could not be asked | groups by `touch` and `variant`; `format_stats` prints both |

`date_sent` ships with `touch_number` deliberately, and it is not scope creep: a touch number
with no date cannot schedule anything, and a follow-up list is exactly *"touch 1, sent more
than N days ago, no reply"*. One without the other reads as wired and cannot be used.

**Stated rather than discovered later:** the master holds the **latest** touch, not a
history — touch 2 overwrites touch 1's date. That is sufficient for the measurement, because
a reply is attributed to the touch last sent.

**Why this leg is worth the trouble:** measured across 100M+ emails, a single follow-up lifts
replies ~65% and follow-ups produce ~42% of positive replies. Most of the return lives in
touch 2, and it was unrecordable and ungroupable.

| 1 | no deliverable address (a `…@gmajl.com` typo domain `bio_parser` rejects) | yes |

**Nothing was folded in, because nothing should be.** The five files holding them are stale
exports predating the gates. The superset property, correctly stated, **holds**: every
address outside the primary is outside because a gate excluded it.

### I got this wrong twice before getting it right

Both failures produced *confident wrong answers*, not errors, and both came from inventing an
interface instead of reading one:

1. I called a role-checking function that does not exist, wrapped in `except Exception: pass`.
   Every address then silently passed the role check and **13 obvious shared inboxes**
   (`contact@`, `info@`, `mgmt@`, `office@`) came back "sendable".
2. I read `verdict["reason"]` from `send_suppress.classify`. The key is **`reasons`**, plural,
   so `.get("reason", "")` returned `""` for every address and everything "passed".

Both are now asserted: the classifier raises if `classify` disappears or its contract
changes. A swallowed `AttributeError` in a classifier does not produce an error — it produces
a finding-shaped lie.

A third correction came from the address form itself: comparing raw master cells against the
exporter's repaired ones reported **3 false defects** (a `www.`-prefixed gmail address and its repaired form are one person). Repair first, then normalise — the `build_key_index` invariant.

### The test, and why it holds fingerprints

`tests/test_send_superset.py` asserts the *set* of addresses outside the primary, so a sixth
file — or an old file gaining a row — turns the suite red and names the count. It
deliberately does **not** re-derive the gates: duplicating gate logic in a test is how the
test and the code drift apart, and then the test certifies the drift.

It stores **sha256 fingerprints, not addresses**. These are real people's email addresses;
committing 59 of them to make a test pass would be a worse outcome than the bug.

A planted-file canary proves it can still fail (docs/TESTING.md rule 1).

## 3. The 20-lead pilot — built, checked, and READ

`scratch/bl977_pilot.csv` + `scratch/bl977_messages.txt`. Top of the clipper block, 10/10 on
`message_variant`. **Every row re-checked at build time** rather than trusted from the export
— a domain can die between build and send, and "it was fine when we built the file" is how
the 470-unprobed-domain hole happened.

```
#   email                              arm  live_mx not_role not_agency not_suppressed not_sent
1   are***@gmail.com                   A    True    True     True       True           True
...  (all 20 rows True on all five checks)
arm split: {'A': 10, 'B': 10}
every row passes every safety check: True
```

### The finding: the two arms receive IDENTICAL COPY

Found by **reading the rendered output**, not by reading the code. `message_template.render()`
derives its own `variant` from the row's **data tier** — `clipper/full` (14) when a fandom and
a clip are present, `clipper/reach` (6) when they are not. **There is no A/B copy variant in
the template at all.**

So the 10/10 split rehearses that the variant column records and groups correctly. It is not
a copy test, and calling it one would fabricate an experiment.

Worse, the tier is **confounded with lead quality** — a richer row gets the richer message.
Even alternating strictly by position, the pilot landed **6 full / 4 reach in arm A against
8 / 2 in arm B**. A reply-rate difference between those tiers would be reading the lead
quality, not the copy. A real A/B needs a second copy variant in `message_template.py`.

### Three copy defects, found by reading, measured across all 1,578 clipper rows

| defect | pilot | whole file | example |
|---|---:|---:|---|
| greeting is not a human first name | **6/20** | **484 (30.7%)** | `Hi J J E D I T Z,` · `Hi nicol4s_de_castro,` · `Hi Cykl0psFilm,` |
| `your The X edits` — article collision | 2/20 | 125 (7.9%) | `your The Time Traveler's Wife edits` |
| featured clip below the recipient's own median | 10/20 | 198 (12.5%) | `@areqaep` clip 4.4M vs median 8.1M |

A fourth is correct behaviour with a cost worth knowing: **92 of 1,578 (5.8%) open with the
generic "your edits on TikTok"** rather than naming a fandom — 82 because the fandom is a
CHARACTER name (`moana`, `rapunzel`), which the template suppresses so it does not read as a
person, and 10 because there is no fandom at all. The rule is right; that is its price.

**The first is the one that matters: roughly a third of the file opens with a username where
a name should be**, and 6 of the 20 pilot messages do. None are fixed here — all three render
in `clippershq/message_template.py`, which BL-971 holds.

The third is **not strictly a defect** and I am not going to call it one: the median is cited
as evidence the account is consistently big, so a median above the featured clip supports the
sentence. It does mean the message rarely cites the recipient's best work.

## 4. The stamp round trip, on a copy

`scratch/bl977_roundtrip.py` copies master to a temp directory and refuses to run against the
live file — the guard is the first thing in the module, because a harness that can write the
real master is a harness that eventually will.

```
touch 1 stamps             : YES
touch 2 stamps             : YES   <-- BLOCKER 5 as written is WRONG
export carries touch_number: YES
analysis groups by touch   : YES
stamped ONLY the 3 intended: YES   <-- 3 of 59,006 rows changed
live master untouched      : YES
```

The blast-radius check is the one worth keeping. `matched=3, updated=3` says three rows
changed; it does **not** say they were the three you meant. A key matching a shared inbox
produces the same summary and fabricates send history for somebody real, so the harness counts
stamped rows across the **whole** master.

## 5. The statistics, stated honestly — and enforced where the number prints

> At recruiting's measured **4–8% reply rate, 20 sends expects 1–2 replies.** Ten per arm
> yields **0–1 each**, and any gap between the arms is noise. Separating a 4% arm from an 8%
> arm at conventional power needs roughly **400–500 PER ARM**.
>
> The purpose is the **MECHANISM**: deliverability, the stamp, the follow-up, and whether a
> reply has anywhere to go. **A zero-reply run is not a failure at this size.**

That warning is in the pilot's own header — and `format_stats` now prints it itself whenever a
touch or variant group has fewer than `MIN_ARM_N` (30) sends:

```
    ^ n < 30 per group: reply rates here are NOISE, not a result. Use this to check the
      MECHANISM records correctly, never to pick a winner.
```

A percentage beside n=10 looks exactly like one beside n=1,000, and the arithmetic will not
stop you comparing them. The label lives next to the number, not only in a report.

## The one thing my change broke, and what it taught

The full suite came back **1 of 143 red: `tests/test_funnel.py`, "merge columns appended
LAST"**. It was mine, and it is worth reporting rather than quietly fixing:

```python
check(w.BOT_READY_COLUMNS[9:] == [...the nine merge columns...],
      "merge columns appended LAST")
```

The append-only **discipline** was intact — every pre-existing column kept its index, which
is the invariant that protects a consumer reading by position. What broke is that the
assertion pinned `[9:]`, i.e. *"the merge block is the FINAL block"*, which was true only
because nothing had been appended after it yet.

> **A test that asserts the current shape rather than the rule fails the next time somebody
> obeys the rule.** That is the opposite of what an append-only guard is for: it fired at a
> correct append and would not have fired at an incorrect insert any more loudly.

Fixed by expressing the invariant instead: merge columns hold positions 9–17, send-history
appended last, and no duplicate names. `tests/test_funnel.py` was FREE; I claimed it before
touching it rather than editing another round's file.
