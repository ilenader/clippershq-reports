## 1. The trap, closed structurally

`clippershq/ledger.py` is now **the one accessor** for `memebot/runs.jsonl`, and it does not
merely centralise the rule — it **refuses**.

```
records(path)    -> {render_key: record}   RENDERS ONLY, folded LAST-WINS
outcomes(path)   -> {record_id: outcome}   OUTCOMES ONLY, folded LAST-WINS
census(path)     -> every count this file has ever been miscounted on, derived once
assert_homogeneous(recs)  -> raises MixedRecordKinds, naming the counts
key_of(rec)      -> raises on an outcome line instead of returning the `?@?` phantom
```

**There is deliberately no function that returns both kinds in one dict.** The only thing a
caller can do with a mixed dict is group it, and grouping it is the bug. The one place a mixed
*stream* is legitimate — `resolve()`, which exists to join the two — gets `iter_lines()`, a
generator, because you cannot group a generator by accident.

The guard is exercised on every real read, not just in tests: `records()` and `outcomes()`
call `assert_homogeneous` on their own output.

### Every reader routed

| reader | before | after |
|---|---|---|
| `clip_pipeline.iter_records` / `_key_of` / `read_records` | **correct**, and the only one that was | delegates to `ledger` |
| `tools/run_status.read_renders` | grouped on `render_id or clip_id` — **correct by accident**: outcomes have neither, so they fell out | `ledger.records()`, and reports `outcome_lines` explicitly |
| `outcome_loop.load_runs` | its own parse loop | `ledger.iter_lines()`, docstring now says **DELIBERATELY MIXED** and names what every other caller should use |
| `memebot/scraper/run_record.rows()` | documented "every recorded render", **returned outcome lines too** | filters them; gained `outcome_rows()` |

`tools/backup.py` and `tools/scratch_gc.py` reference the path but never parse it — listed and
left alone rather than touched to look thorough.

**The nested repo's filter is local on purpose.** `memebot/` has its own remote and must check
out standalone; importing the parent's accessor would make it permanently depend on its
parent to save three lines. Both implementations now agree exactly — **937 render lines, 48
outcome lines, 985 total** — which is the useful kind of duplication: independent, and
cross-checked.

`run_record.rows()` was harmless *by coincidence* (`already_used()` compares `clip_id`, which
an outcome never has). That is precisely the standing this trap had in three other readers
before it produced a wrong number.

## 2. The eighth discrepancy, and it was live in production

Two readers key renders two different ways, and **both are right for their own job**:

```
clip_pipeline / ledger.key_of   render_id  ->  output  ->  clip_id@ts
outcome_loop.record_id_for      record_id  ->  output  ->  clip_id@ts
```

**893 of 937 render lines carry both a `render_id` and an `output`**, so the two disagree on
893 lines: the same file resolves to **463 records under one key and 503 under the other**.

That stayed harmless while every outcome referenced an `output` path — **all 22 historical
outcomes do, and they join 22/22**. Then BL-1092 put a *Record an outcome* button on the
dashboard and populated it from `START_HERE.md`, **which publishes the `render_id` form**.

**Only 3 of 22 outcomes join under `render_id`. And an outcome that matches no render does not
fail.** `resolve()` emits it as a standalone record:

```
views 1234   has_outcome True
clip_id MISSING   song MISSING   hook_id MISSING   output MISSING   status MISSING
```

`analyse()` groups by song, hook and duration_band. **An orphan has none of them**, so every
number the operator typed on the page landed on the ledger, counted as `has_outcome`, and was
invisible to the analysis it was collected for. The loop looked like it was working.

**Fixed in the accessor**: `ledger.render_aliases(rec)` returns *every* identity a render
legitimately answers to, and `resolve()` maps an outcome's `record_id` through it. Additive by
construction — the old key is still in the set, so no join that worked before can stop working.

```
before fix:  503 -> 504 records, a NEW orphan key, clip_id MISSING
after fix:   503 -> 503 records, clip_id 3739691966683559087_..., status ok
             historical joins preserved: 22 -> 23
```

## 3. NEVER RAN and DEGRADED, forced in real runs

BL-1092 proved the **renderer** on a fixture and left the **writer** unproven. Both are now
proven end to end, with no fixture anywhere.

**NEVER RAN — $0, no paid call.** Forced with an empty `library_root`, so ranking yields no
candidates and `clip_pipeline` **returns before `with dlog.stage("retrieval")` is ever
entered** (the `if not cands:` return, `stopped: "no_candidates"`). Those stages never exist:

```
stopped   : no_candidates
NEVER RAN : ['retrieval', 'render']
SILENT    : ['gating', 'ranking']
```

**I got the mechanism wrong first, and the wrong answer is the useful one.** `max_run_usd=0.0`
does **not** produce NEVER RAN — retrieval and render still *open*, take input and emit
nothing, which is **SILENT**. A different state with a different diagnosis, and the writer was
right to distinguish them. That is the whole reason these three states exist.

**DEGRADED — $0.0006.** Forced with an empty `song_store`, which is the brief's condition
verbatim: *a render that succeeds with a bed outside the store.*

```
made 1   cost $0.0006   DEGRADED: ['render']
render: "1 render(s) matched NO song rule and fell through to the local corpus. They are
         FINISHED videos that can never earn rotation — the store cannot hold their join
         key (MEMEBOT-067). Nothing downstream will report this."
```

Both then rendered on the page **from the live decision log**, at 1440 and 700, with **0
console errors and 0 external requests**:

```
1440   DEGRADED=True  measured=True  NEVER RAN=True  errors=0 external=0
700    DEGRADED=True  measured=True  NEVER RAN=True  errors=0 external=0
```

Worth noting: **one of the two DEGRADED runs on the live log is not mine.** Another round

## 4. New drops carry the measured value

`0 of 335` became **5 runs carrying measured values**, exactly as BL-1092 predicted. And a
non-moving threshold renders the brief's format precisely:

```
duration Ns outside [N N]     3.1s-7.41s < 7.626s
```

**But not always, and the exception is correct.** On the real run the value came out
`3.135s–179.933s` with **no threshold** — because clips fell off *both* ends and
`threshold: None` is a **deliberate sentinel** meaning "the threshold moves between clips".
The duration gate has a floor *and* a ceiling under one normalised reason; BL-1081 has a scar
where the missing `is None` check took down a whole render batch.

So the honest reading of item 3: **the value is there, the comparison is legitimately absent
when two thresholds share a reason.** The page already handles it — `measuredPhrase()` returns
the range alone rather than `< None`.

Item 4 was not ceremony. **Every guard was handed a known-wrong input and had to reject it

   page requested endpoints its in-memory module never had. The inverse of INFRA-017's

## What I got wrong

1. **The NEVER RAN mechanism** — `max_run_usd=0.0` gives SILENT, not NEVER RAN.
2. **The measured-value formatter** — concatenated a documented sentinel and misread the
   result as a defect.
3. **The stale server** — attributed another process's 404s to the page before checking.
4. **`work_dir` outside the repo** — the pipeline refused it before any paid call. Its guard,
   working exactly as written.
5. **`import run_status`** — there are **two** modules with that name (`clippershq/` and
   `tools/`) and a bare import silently picked the wrong one. A cheap version of the same
   mistake this whole round is about: two things sharing one name.
6. **My own new AST guard flagged a string method.** `test_the_read_accessor_never_writes`
   matched any call named `replace` and fired on `str(...).replace(BACKSLASH, "/")` inside
   `ledger.py`. Fixed to check the receiver (`os`/`shutil`), then re-verified against a
   planted `os.replace` **and** a planted `open(mode="a")` — it catches both.
7. **I shifted line numbers under a doc citation.** Removing the three inlined reader bodies
   from `clip_pipeline.py` moved `hook_chain` from line 1377 to 1379, and
   `docs/FINAL_STATE.md:168` cites it by line. That suite was green in BL-1092; **this round
   turned it red.**
