## PART 2 — can the sound actually be resolved to a stable id?

**Yes, all four, and three of them for free. But not the way BL-668 implies.**

### The LamaTok probe failed on every short link, and the reason matters

One LamaTok `/v1/media/by/url` call per campaign, never per clip, on the three short links:

```
bees.n.honey   vt.tiktok.com/ZS921b4wPX2Dr-Aenf8/   -> network timeout, no id
Panic Baby     vt.tiktok.com/ZS9jBJTRKHJYk-vdYfm/   -> HTTP 500 {"detail":"Response error"}, no id
STRAENGE       vt.tiktok.com/ZS9jBb6htXqsP-YzjtW/   -> network timeout, no id
```

**0 of 3 resolved.** This is not a provider outage and it is not the short-link problem BL-668 studied. **A campaign's `soundLink` is a share link to a SOUND PAGE, not to a video.** `fetchLamatokTiktokByUrl` calls the *media* endpoint, so handing it a sound URL asks the wrong question and it answers with a 500 or a hang.

**This corrects BL-668's PART 5 in one specific respect.** BL-668 concluded that "LamaTok resolves all three short forms natively", and for **video** short links that is right and is well evidenced. It does **not** extend to **sound** share links, which is the only form that matters here. Nobody had tested that case, because there were no sound rules to test it with.

### Following the redirect resolves all three instantly, for nothing

A plain redirect follow (no API key, no provider call, no cost) lands on the canonical `/music/<slug>-<id>` page, and TikTok puts the music id in the slug:

| campaign | `soundLink` form | resolves to | **stable `music.id`** | cost |
|---|---|---|---|---|
| BAD BITCH ANTHEM (2.50 CPM) | `/music/` page, already canonical | `original-sound-7621960336325446431` | **`7621960336325446431`** | 0 calls, id was already in the stored URL |
| bees.n.honey | `vt.tiktok.com` short | `music/daylight-7641624164701259777` | **`7641624164701259777`** | 1 free redirect |
| Panic Baby | `vt.tiktok.com` short | `music/glitter-in-the-night-7644917591970039809` | **`7644917591970039809`** | 1 free redirect |
| STRAENGE | `vt.tiktok.com` short | `music/Read-My-Mind-Every-time-I-talk-7643440054148303649` | **`7643440054148303649`** | 1 free redirect |

**The slug corroborates the requirement text in three of four cases**, which is a useful independent check that the right sound was resolved: Panic Baby's requirement names *"glitter in the night"* and the slug is `glitter-in-the-night`; STRAENGE's names *"Read My Mind"* and the slug is `Read-My-Mind-Every-time-I-talk`; bees.n.honey's names the artist and the slug is the track title `daylight`. The fourth is the problem below.

### CRITICAL: one campaign's sound IS an original sound, and it is the one whose id was already in hand

**BAD BITCH ANTHEM (2.50 CPM)'s sound is `original-sound-7621960336325446431`. The slug literally says `original-sound`.** This is exactly the failure mode BL-663 listed. Stated loudly and precisely, because the nuance decides whether the rule is safe:

* On TikTok, when a creator posts with their own audio, that audio is minted as an **original sound with its own stable music id**, and other users *can* attach to that same id from the sound page. So the id is reusable and a fixed-id rule is **not automatically wrong**.
* The danger is the opposite direction. A clipper who **re-uploads, speeds up, or re-creates** the audio gets a **brand new per-post original-sound id**, and a fixed-id rule flags them.
* **For this campaign that is the desired behaviour, not a bug.** The requirement is literally *"no re-uploads, sped-up, or copies"*. A per-post original-sound id is precisely the signature of a re-upload, so the rule would flag exactly what the requirement forbids.

**So it is safe in intent but fragile in practice, and the live data already shows the fragility.** The single organic shadow row on this campaign carries sound id `7618661683770853392`, which is **not** `7621960336325446431`. That clip would have been flagged. It is still PENDING, so no human has ruled on it and I cannot say whether the flag would have been right. **Do not add this rule until at least one such clip has been humanly judged.**

The other three are ordinary library tracks with named slugs and are not original sounds.

## PART 4 — the exact spec

### Three campaigns qualify. Enforcement is `rank`, and the reason is structural

**`enforcement: "rank"`, never `auto_reject`.** The justification is BL-664's measurement: the human reviewer overturn rate is **1.54%**, or **0.77%** excluding a misclick, so humans wrongly reject roughly 5 clips a month, while a machine at R-2's **11.05%** would manufacture roughly 214. Nothing has earned the roughly 1% bar.

**`rank` is the correct value and it is not a compromise, because the evaluator branches on TYPE, not on enforcement.** Verified in `src/lib/campaign-rules.ts`:

* `evaluateRuleShadow` dispatches on `rule.type` at **line 285**, so a `REQUIRED_SOUND` rule is fully machine-evaluated and still returns `would_pass` or `would_reject` regardless of its enforcement label.
* `evaluateRulesShadow` sets `wouldReject` **only** for `enforcement === "auto_reject" && verdict === "would_reject"` (**line 333**). A `rank` rule can therefore **never** contribute to an auto-reject **even if `RULES_AUTO_REJECT_LIVE` were switched on**. That is a structural guarantee, not a dependency on a flag staying off.
* The per-rule verdict is still persisted: `rule_shadow_decisions.results` is `jsonb` and live rows confirm it carries `{type, enforcement, verdict}` per rule, so the disagreement rate accrues and is queryable.

So `rank` buys the full shadow signal with the reject path removed at the code level.

### How the owner adds these: a DATA OPERATION, not the campaign form

**The admin form cannot produce these rules, and would silently produce the wrong thing.** `src/app/(app)/admin/campaigns/page.tsx:329` writes `enforcement: defaultEnforcementForType(r.type)`, and `defaultEnforcementForType("REQUIRED_SOUND")` returns **`auto_reject`** (`campaign-rules.ts:60`). The form exposes no enforcement picker at all. **Choosing "Required sound" in the UI therefore writes an `auto_reject` rule**, which is exactly what this round forbids. It would also not set `params.soundId`, so the rule would evaluate to `cannot_evaluate` forever and gather nothing.

So it must be a data operation. Per the repo's rules this is a data mutation, so it goes through `scripts/run-mutation-once.js` or the manual Supabase SQL editor, never `run-schema-sql.js`:

```sql
-- Panic Baby
UPDATE campaigns
   SET "rulesJson" = "rulesJson" || '[{"id":"r9","text":"Use the official \"glitter in the night\" sound.","type":"REQUIRED_SOUND","params":{"soundId":"7644917591970039809"},"platforms":["tiktok"],"enforcement":"rank"}]'::jsonb
 WHERE id = 'cmqcnzpzk00370pqjov9d6tlc'
   AND NOT ("rulesJson" @> '[{"type":"REQUIRED_SOUND"}]'::jsonb);

-- bees.n.honey
UPDATE campaigns
   SET "rulesJson" = "rulesJson" || '[{"id":"r7","text":"Use ONLY the official bees.n.honey TikTok sound do not upload the audio from Spotify, YouTube, or anywhere else. Wrong audio = rejected.","type":"REQUIRED_SOUND","params":{"soundId":"7641624164701259777"},"platforms":["tiktok"],"enforcement":"rank"}]'::jsonb
 WHERE id = 'cmppnmhb3000g0po2gih2jt75'
   AND NOT ("rulesJson" @> '[{"type":"REQUIRED_SOUND"}]'::jsonb);
```

The `NOT (@>)` guard makes each statement idempotent, so a double run cannot duplicate the rule.

**Print the before value first**, then apply, then confirm `jsonb_array_length` went up by exactly 1. **Rollback** is a single statement per campaign, removing only the new element and touching nothing else:

```sql
UPDATE campaigns
   SET "rulesJson" = (SELECT jsonb_agg(e) FROM jsonb_array_elements("rulesJson") e WHERE e->>'type' <> 'REQUIRED_SOUND')
 WHERE id IN ('cmqcnzpzk00370pqjov9d6tlc','cmppnmhb3000g0po2gih2jt75');
```

**One caution about editing these campaigns in the admin UI afterwards.** The form rebuilds `rulesJson` from its own state on save and re-derives enforcement from the type, so **opening and saving one of these campaigns in the form would flip the rule back to `auto_reject`**. Until the form learns to preserve enforcement, treat these two campaigns' rules as owned by the data operation. That is a genuine sharp edge and it is worth a follow-up round to fix the form rather than to remember a rule.

## The query that measures whether these rules were right

Once the rules are live, this is the disagreement rate, and it is the number that decides whether a sound rule could ever be trusted:

```sql
SELECT c.name,
       e->>'verdict'                                            AS verdict,
       cl.status                                                AS human_verdict,
       count(*)                                                 AS clips
  FROM rule_shadow_decisions r
  JOIN campaigns c ON c.id = r."campaignId"
  JOIN clips cl    ON cl.id = r."clipId",
       LATERAL jsonb_array_elements(r.results) AS e
 WHERE r.source IS NULL
   AND e->>'type' = 'REQUIRED_SOUND'
   AND e->>'verdict' IN ('would_pass','would_reject')
   AND cl.status IN ('APPROVED','REJECTED')
 GROUP BY 1,2,3
 ORDER BY 1,2,3;
```

**Read it like this:** rows where the verdict is `would_reject` and the human verdict is `APPROVED` are the false rejections. That count over the total is the number to compare against BL-664's **0.77%** human baseline. Do not consider `auto_reject` for a sound rule until that figure exists and is below roughly 1%.
