# BL-681: the speech detector was NOT installed — two independent stop conditions, both confirmed live

**Date:** 2026-07-29
**Task:** benchmark `inaSpeechSegmenter` and close [BL-677](BL-677.md)'s speed GAP.
**Outcome:** **install refused at the pre-flight gate.** Nothing was installed; the shared environment is byte-for-byte as it was found (`numpy 2.3.2`, `torch 2.11.0+cpu`, `PIL 12.2.0`).
**Spend:** $0 — no API calls. Audio came from CDN URLs already known to need no auth.
**BL-677's speed GAP remains OPEN.** It is not closed by this round, and this report does not pretend otherwise.

---

## Stop condition 1 — a major-version numpy downgrade

The pre-flight dry-run (`pip install --dry-run --report`, which resolves without touching site-packages) returned an unambiguous verdict.

```
inaSpeechSegmenter 0.7.14
   -> tensorflow 2.13.1
      -> tensorflow-intel 2.13.1   requires: numpy (<=1.24.3,>=1.22)
```

| package | installed now | pip would install | verdict |
|---|---|---|---|
| **numpy** | **2.3.2** | **1.24.3** | **major-version DOWNGRADE** |
| typing_extensions | (torch dependency) | 4.5.0 | downgrade risk for torch 2.11 |
| onnxruntime-gpu | `onnxruntime` 1.22.1 (CPU) installed | 1.28.0 (GPU) | same import namespace — classic conflict |
| protobuf | not installed | 4.25.9 | new |

That is precisely the gate condition set for this round, so the install stopped there.

`numpy 2.x → 1.24.3` is not a routine pin nudge. It crosses the NumPy 2.0 ABI boundary, underneath a `torch 2.11.0+cpu` build that expects NumPy 2.x, plus `PIL 12.2.0` and `onnxruntime 1.22.1`. The realistic outcome is not a slower funnel — it is import errors across the vision and OCR paths that currently work.

### Why pip reached back to a 2023 TensorFlow

Worth recording, because it is the root cause rather than bad luck. The current release, **inaSpeechSegmenter 0.8.0 (MIT)**, declares:

```
tensorflow[and-cuda]
onnxruntime-gpu
```

Both are **GPU-flavoured**. On this Windows CPU box the `and-cuda` extra does not exist for the resolvable TensorFlow builds — the resolver emitted a run of `does not provide the extra 'and-cuda'` warnings and backtracked roughly two years to **TensorFlow 2.13.1**, whose numpy ceiling is what produces the downgrade.

So this is not "a heavy dependency". It is a **GPU-targeted package being force-fitted onto a CPU host**, and the numpy downgrade is the cost of that fit.

**Install footprint, for the record:** 43 packages. The four largest wheels alone are **341 MB** of download (`tensorflow-intel` 276.6 MB, `scipy` 41.3 MB, `numpy` 17.3 MB, `tensorboard` 5.6 MB), before Keras, pandas, matplotlib, h5py, grpcio, Pyro4 and the rest — comfortably over 1 GB installed.

## Stop condition 2 — another agent was installing into the same environment, live

This is the hazard the round was warned about, and it was not hypothetical. Three independent signals inside one 60-second monitoring window:

1. **`python -m pip install ...` observed running** as a separate process (PID 9948).
2. **A long-running python task present in 17 of 20 samples** across the full 60 seconds (PID 29192) — not a transient probe.
3. **`site-packages` gained `librosa 0.11.0` and `soundfile 0.14.0`, timestamped mid-window.** Another agent's install *completed while this round was measuring*.

Earlier, at the very first check, a process was caught importing `librosa, soundfile, torchaudio, transformers, laion_clap, msclap` — a concurrent audio workstream occupying the same dependency space.

The overlap is direct: `soundfile 0.14.0` is the exact package-and-version `inaSpeechSegmenter` also wanted. Two concurrent resolvers writing the same shared `site-packages`, one of them dragging numpy backwards across a major version, is how an environment gets corrupted for every agent using it.

**Either condition alone justified stopping. Both together made it clear-cut.**

## What was measured anyway, at zero cost and zero install

### Fetch benchmark — the half of the wall clock that needs no model

30 clips, audio only via `progressive_download_url`, CDN, no auth, `requests` (already installed):

| metric | value |
|---|---|
| success | **30 / 30**, zero failures |
| seconds per clip | **median 0.40, mean 0.50** (min 0.17, max 1.48) |
| audio payload | **median 478 KB, mean 730 KB** (max 2.3 MB) |
| audio duration | median 61 s, mean 87.5 s |
| fetch speed vs real time | **176× faster than real time** |

**Projected at 1,000 clips/day: ~8 minutes and ~0.7 GB for the fetch stage.**

This is a real contribution to the open speed question. BL-677 estimated ~0.10 real-time factor for the model, i.e. ~50 min/day. If that estimate holds, fetch adds ~8 min — so I/O is **not** the bottleneck and the pipeline stands or falls on the model, which is exactly the part still unmeasured.

### The `audio_type` router — measured, and weaker than assumed

BL-677 proposed skipping the model where `audio_type != original_sounds`, estimating that covers about a third of the corpus.

Measured across **229 unique clips** (the saved corpus has grown past the 180 BL-677 used):

| audio_type | clips | share |
|---|---|---|
| `original_sounds` | 156 | 68.1% |
| `licensed_music` | **37** | **16.2%** |
| absent (no `clips_metadata`) | 36 | 15.7% |

**The router covers 16.2%, not ~33% — roughly half the claimed benefit.** It is still free and still worth having, but it is a minor optimisation, not a way to halve the workload. Any capacity plan built on "a third for free" should be revised.

**A precision note on `progressive_download_url`.** BL-677 recorded 100% presence. Across this wider corpus it is **83.8%** (192/229) — but the shortfall is entirely the 36 clips that carry no `clips_metadata` at all (they come from surfaces that do not emit it). Among clips that *do* carry `clips_metadata`, presence is **192/193 = 99.5%**. BL-677's figure was right for its corpus; the caveat is that the field is only reliable where `clips_metadata` exists, which is not everywhere.

## What was NOT done, stated plainly

1. **The model was never run**, so BL-677's ~0.10 real-time-factor estimate is **still an estimate**. The speed GAP is untouched.
2. **The accuracy measurement was not performed, and could not be.** Scoring precision/recall requires ground-truth labels, and producing those means *listening* to 30 reels. I have no audio perception — I cannot hear the clips. Inventing labels from a proxy (audio_type, captions) and presenting them as hand labels would have produced a number that looked like evidence and was not. No labels were fabricated.
3. **The silero sung-vocal failure mode was not confirmed on real clips.** BL-677's structural objection — that a sung vocal *is* a human voice, so a perfect VAD fires on any track with lyrics — remains a sound argument that has not been empirically demonstrated here.

### What was done about the reproducibility problem

BL-677's stated grievance was that a prior measurement became unreproducible because its ground truth was never persisted. That is addressed even though the labels themselves do not exist yet: `speech_label_worksheet.csv` (30 rows) is written and keyed on the **Instagram post id**, which is permanent — deliberately **not** on the CDN URL, which is signed and expires within hours. It carries `audio_type`, duration, payload size and fetch time per clip, with `label` / `labeller` / `labelled_at` columns left **empty** and a fixed vocabulary (`speech_over_music | music_only | speech_only | silence`).

So whoever or whatever labels these clips next produces a result that is reproducible against the same 30 clips, which is what was actually missing.

## The recommendation

**Do not install `inaSpeechSegmenter` into the shared environment. Not now, and not after the other agent finishes.** The numpy ceiling is structural, not a scheduling problem — it follows from a GPU-targeted package resolving onto a CPU host. Waiting for a quiet moment does not change the constraint.

If it is genuinely wanted, it must be **isolated**: a dedicated virtualenv, or a subprocess/container boundary, invoked as a service. It must never share `site-packages` with the funnels.

**Prefer silero-vad as the first stage.** Its install was dry-run costed in this round and is clean:

| package | installed now | would install | verdict |
|---|---|---|---|
| silero-vad | not installed | 6.2.1 | new |
| torchaudio | not installed | **2.11.0** | **exact match to `torch 2.11.0+cpu`** |

**Two packages, zero downgrades, nothing the funnels import is touched.** It was still not installed this round, solely because another agent was mid-install in the same environment — not because of any dependency objection. It is ready to go the moment the environment is quiet.

Two conditions on that recommendation, both from BL-677 and neither yet tested:

- **Pin the version.** v4 regressed 2–3× against v3 on noise-only material. Pin explicitly; do not float.
- **Treat it as a first-stage filter only, never as the speech-over-music decision.** The sung-vocal objection means a VAD that fires on lyrics is behaving correctly and still answering the wrong question. It can cheaply rule out *silence and pure instrumental*; it cannot distinguish a voiceover from a chorus.

Net: **silero as a cheap pre-filter is viable and near-free to adopt. A true speech/music/noise separator remains unbenchmarked, and on this host it needs process isolation before it can even be measured.**
