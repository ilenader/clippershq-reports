## 2. main ADVANCES AUTOMATICALLY

**`tools/ff_main.py`** does the advance and owns the safety. **`tools/wip_commit.py`** — the
thing that already runs unattended — calls it after a successful `--push`, on by default,
`--no-ff-main` to opt out. `--ff-main` advances the ref *without* committing, so it also works
on a clean tree.

### It advances a REF. It never checks anything out.

This is the part worth being loud about, because checking `main` out and merging is what a
reasonable person would try. The working tree here routinely holds **200–311 uncommitted
entries** belonging to rounds running *right now*, and `git checkout` rewrites the working
tree. Using it to fix a **ref** problem would cause a worse version of the incident this
exists to prevent — and unlike a reset, it would look like it worked.

A test asserts the advance leaves branch, `git status` output, and an uncommitted file
byte-identical.

### The exit code is not the check

`git push` exits 0 for a forced update exactly as it does for a fast-forward. Only the status
line distinguishes them:

```
  4cc7790..a6fdb48   work -> main                    two dots        ACCEPT
+ 4cc7790...a6fdb48  work -> main (forced update)    plus/three dots REFUSE
```

**`..` is a substring of `...`,** so the obvious `".." in line` test **passes on a forced
push** — the exact case it exists to catch. `classify_push_output` matches `...` first, and
`tests/test_ff_main.py` pins that ordering with a fixture that asserts `".." in line` is true
before asserting the classifier still says `forced`.

`--force` is never passed, and **no code path can pass it** — asserted at runtime by
intercepting every git call, not by grepping the source. (The first version of that test *did*
grep the source, and failed on the module's own `# no --force, ever` comment. A text scan
cannot tell a promise from a prose mention, in either direction.)

### What it refuses, proven on the live repo and not only in fixtures

| Condition | Behaviour |
|---|---|
| `origin/main` holds a commit the source lacks | **REFUSE** — would orphan it |
| `main` is the checked-out branch | **REFUSE** |
| push reports a forced update | **REFUSE** |
| source or `origin/main` does not resolve | **REFUSE** |

```
$ python tools/ff_main.py --source HEAD~2
  ff_main: NOT a fast-forward: origin/main has 2 commit(s) not on HEAD~2.
           Refusing — advancing would orphan them.
exit 1;  origin/main unchanged at 9a39e00
```

A refusal never fails the WIP commit. The commit is the safety net; losing it because a ref
could not advance would invert the priority.

### It advanced three times during this round

| | |
|---|---|
| `51ffd1b..0499e2d` | +2 commits, fast-forward asserted |
| `0499e2d..9a39e00` | +2 commits, fast-forward asserted |
| dry-run before each | ref confirmed unmoved |

`main` had already drifted again between BL-869 publishing and this round starting. That is
the behaviour the automation exists for.

**Suite: 12/12 green** — classification (5), real-repo end-to-end (7), including
working-tree-untouched, dry-run-moves-nothing, and no-force-flag.

## 3. THE CLONE DEPENDENCY, WRITTEN DOWN

`tools/clone_check.py` answers the question BL-869 had to discover by cloning.

A fresh clone of `main` gets the complete, current tree and **still fails two suites**:

```
tests/test_clip_pipeline.py    ModuleNotFoundError: No module named 'run_record'
tests/test_claims_manifest.py  MEMEBOT-009 and MEMEBOT-021 do not verify
```

Neither is a defect and neither is a regression — both pass in a working copy. `run_record.py`
and the memebot claim targets live in **`memebot/`, a separate git repository**, gitignored
here and *not* a submodule, so `git clone` cannot bring it and never will.

**Counting files does not catch this: the tree is complete, the dependency is not.** So the
check probes a concrete file rather than the directory — an empty leftover `memebot/` passing
would be worse than no check at all.

Verified in both directions:

```
live repo:     memebot present (memebot/scraper/run_record.py at dbbaae1)   COMPLETE   exit 0
fresh clone:   memebot MISSING ... breaks test_clip_pipeline, test_claims_manifest,
               clip_pipeline.py;  fix: git clone .../memebot.git ./memebot  INCOMPLETE exit 1
```

Documented in `RECOVERY.md` under *"A fresh clone is not self-sufficient"*, so it is found
before someone concludes the project is broken.

## 7. A REGRESSION I CAUSED, CAUGHT BY THE SUITE AND FIXED

The commit in §6 turned `tests/test_claims_manifest.py` **red**, and it was my doing.

The triage rule — *no live round claims this path, therefore it is finished* — is true and
**not sufficient for a claims manifest**. A manifest is only committable once the things it
*claims* are themselves committed. Three went in whose targets were not:

| Manifest | Cited | Fix |
|---|---|---|
| MEMEBOT-022 | `scratch/memebot022_audit.py`, untracked | committed → **10/10** |
| MEMEBOT-028 | three `scratch/memebot028_*` artefacts | committed → **9/9** |
| MEMEBOT-027 | `can_use_for_class` + `DIALOGUE_CLASSES` in `song_library.py` | **un-tracked** |

MEMEBOT-027 is the interesting one. Both symbols exist in the **working copy** and not at
HEAD — they are an in-flight edit owned by **MEMEBOT-032**, which holds that file right now.
The tempting fix was to commit `song_library.py` so the manifest verifies. That would be
snapshotting another round's half-finished module **to make a test pass**, which is the wrong
direction: the manifest waits for the code, never the reverse. Its manifest is removed from
the index and left on disk, untracked, becoming committable the moment MEMEBOT-032 lands.

**13 committed manifests, all green.** The invariant that makes phantom detection worth
anything — *a committed manifest verifies at HEAD* — holds again.

The other red, `tests/test_filelock.py`, was **not** a regression: it passes standalone
(4 tests, OK) and failed only under the parallel run, with twelve rounds writing. Same class
of live-writer artefact BL-859 recorded for `test_dashboard.py`.

### Method / limits

- `ff_main` advances by push only; it has no code path that checks out, resets, or cleans —
  asserted at runtime, not by inspection.
- The advance rides `--push`. A round that commits without pushing does not trigger it; `main`
  then waits for the next push or an explicit `--ff-main`. That is deliberate — advancing
  `main` past commits nobody has pushed would put the shared ref ahead of the branch.
- `wip_commit --push` commits *everything in scope*, including in-flight files. Correct for an
  unattended safety net, wrong for this round, so this round's own commits were staged by hand
  and pushed directly.
- The temp-file hole in `wip_commit.py`'s filter is reported, not fixed.
- Triage counts are a snapshot of a tree that twelve rounds are still writing.
