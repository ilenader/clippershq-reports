## 1. The logging filter — the half that matters

The panel was never the threat; it is an allowlist by construction and always was. **The threat is the client that has not been written yet.** Every API client here logs at DEBUG and `logs/run.log` keeps full detail including tracebacks, so one `log.debug("GET %s", url)` with a key in the query string writes it to disk in plain text. That cannot be prevented by reviewing code that does not exist, so it is stopped centrally at emit time.

`secrets_guard.install()` attaches one `SecretRedactingFilter` to the **handlers** — not to a logger — inside `main.setup_logging()`. Handler attachment is the important detail: it covers `urllib3` and `httpcore`, which log full request URLs at DEBUG and are the likeliest leak path in this repo.

It is seeded by reading `config.json` directly, because `setup_logging()` runs *before* `load_config()` in `main()` and the protection has to exist from the first line logged.

**Proved against the real key from config** (never printed — the test asserts absence):

| case | result |
|---|---|
| app logger, key in a Gemini-shaped URL | `?key=***REDACTED***` |
| **third-party `urllib3` logger** | `"GET /v?key=***REDACTED***"` |
| **key inside a traceback** | `RuntimeError: auth failed for key=***REDACTED***` |
| **`AIza…` key not in config at all** | `token from env: ***REDACTED***` |
| real 60-char key present in run.log? | **NO** |

Two layers, deliberately independent: **value** redaction (the actual strings from config) and **pattern** redaction (`AIza…`, `sk-…`, `ghp_…`, `hf_…`, `xox…`, `Bearer …`). The pattern layer is what covers a key that arrives by environment variable or in an upstream error body — the Gemini case *before* a key is ever written to config.

The filter never drops a line: on any internal error it substitutes a marker rather than leaking or losing the record.

### Two over-redaction bugs found by testing this against the real config

Both were in code I wrote this round, and both were caught by checking whether any redaction needle appeared in committed source:

1. **Short values as needles.** Two config values under credential-named leaves are 6 and 11 characters. As needles they matched unrelated text — the 6-char one inside `secrets_guard.py`'s own Slack regex, the 11-char one inside `main.py`'s literal `"PASTE_YOUR_…"` placeholder. Redacting on those would corrupt ordinary log lines. Fixed with `NEEDLE_MIN_LEN = 16` plus a placeholder skip-list (redacting `PASTE_YOUR_KEY` would also hide the useful *"you have not set your key"* signal).
2. **Routing values as needles.** `tikhub_api.user_posts_endpoint` is a 44-character **path**, and it cleared the length bar through the unrecognised-leaf fallback. Using it as a needle would redact the endpoint out of every log line naming it. Fixed by skipping values starting with `http://`, `https://` or `/`.

Needles went 13 → 8 → **7**, all now 30–60 characters. The only files containing one are `config.json` and its `config.backup.*.json` siblings — both correct, both untracked and covered by `.gitignore:28`. Verified after the fix that the real key is still redacted **and** the endpoint path survives intact.

## 2. control.py now enforces the tuple instead of documenting it

`SECRET_BLOCKS` is re-exported from `secrets_guard` under its original name, so the hand-kept duplicate in `scratch/scan_report_for_secrets.py` no longer has a second definition to drift from.

**Layer 1 — import-time refusal.** At the end of `control.py`, all three spec lists are checked and `ValueError` is raised if any row names a credential field. A menu offering to display or edit a key is a disclosure bug, so the panel refuses to start rather than logging a warning nobody reads.

**Layer 2 — runtime filter.** Each of the three menus (`_edit_advanced`, `_global_settings`, `_funnel_filters`) now builds its rows through `visible_specs()` **and indexes the filtered list**, so a row added after import cannot be displayed or selected. Indexing the filtered list matters: filtering for display while indexing the raw list would silently edit the wrong field.

The rule handles all three spec shapes — `_FUNNEL_FILTERS` carries a block, `_ADVANCED` and `_GLOBAL_TOGGLES` are top-level keys — so a credential can be caught whether it arrives as `("gemini_api", "key", …)` or as a bare `("gemini_api_key", …)`.

**Measured:** shipped lists are clean and lose no rows (14 / 30 / 33 before and after). Four synthetic credential rows are refused; three ordinary rows are not. A row appended after import is dropped by the runtime filter.

**The allowlist is kept.** Belt and braces was the instruction and it is the right call — the named spec lists remain the outer boundary; what changed is that the declared intent is now checked as well.

## What was deliberately not done

- **The three dead declarations and nine config keys are untouched**, per the brief. They are a list, not a change.
- **`scratch/scan_report_for_secrets.py` still carries its own copy of the block names.** It now *could* import the canonical list; it is scratch tooling and outside this round's blast radius.
- **The filter redacts, it does not alert.** A leak attempt is silently cleaned rather than raising. Alerting on a redaction would be a useful signal that a client is mishandling a key, and is not built.
- **Console output is not covered.** The filter is on the logging handlers; a bare `print()` of a key would bypass it entirely. The Control Panel's `_emit` is a `print`, which is why layer 2 of the panel guard still matters.
- **No environment-variable sweep.** `secret_values()` reads config only. A key held solely in an env var is covered by the pattern layer, not the value layer.
