## The correction that matters

**Deleting `"kick_finder": LEAD_KIND_CLIENT` from `_SOURCE_TO_KIND` made things worse, not better.** An unmapped source falls through to the hashtag-shaped default at the bottom of `lead_kind_from_source`, which returns **CLIPPER**. Measured immediately after the deletion:

```
kick_finder -> clipper        # not unroutable
```

The 35 Kick rows disappeared from the export, but for the wrong reason — they were being caught by the *verdict* gate as low-quality clippers, not refused as a retired source. Any Kick row that happened to carry an `EDITOR` verdict would have sailed through.

The real fix is an explicit retirement list checked **before** the fallback:

```python
_SOURCE_RETIRED = frozenset(("kick_finder",))
...
if not s or s in _SOURCE_KIND_UNKNOWABLE or s in _SOURCE_RETIRED:
    return ""
```

`kick_finder` now resolves to `''` → `unroutable` → excluded and counted. The self-test asserts **the absence**, not a mapping, so re-adding the line fails the suite.

## 4. `LATEST_BOT_READY.csv` — full header

`write_bot_ready_csv` already emitted by column name, so the code was right and only the **file** was stale at 5 columns. It is now refreshed from the same rows as the cumulative list.

```
ALL_BOT_READY.csv     10 cols, matches contract: True   2,572 rows
```

**This is a deliberate contract change, flagged for objection.** LATEST used to mean "the newest RUN's emailable editors" — which is why it sat at 2 rows for two weeks. That contract is wrong for an automation target: a sender aimed at it mails 2 people out of thousands. A live run still overwrites it with its own rows; this keeps it correct in between.

**I hit the CWD foot-gun I documented in BL-785 while doing it.** My first version wrote to the module-level `LATEST_CSV`, a bare relative path, and crashed when run from `clippershq/`. It now derives from `--out`'s directory. The crash is the good outcome — the same bug silently stranded `spend.json` and `resolve_cache.json`.

## Limits

- **The LATEST contract change is a judgement I made, not one the brief specified.** It is reversible in one line if the per-run snapshot is wanted back.
- **`release_link` is an untested predictor.** It is reasonable — a smart-link means an active release — but nobody has sent to these rows, so its correlation with replies is **0 measured**. It changes ordering only, never inclusion, so the downside is bounded.
- **`FOSSIL_DAYS` is a hardcoded date set**, not a rule. A second fit-test day would need adding by hand. I chose that over a heuristic because the rows carry no marker distinguishing a fit-test row from a real one, and a heuristic would risk cutting good days.
- **The 107 / 90 gap is explained by duplicate addresses across dates**, verified on one case by hand rather than all of them.
- **`role_inbox` still suppresses 185 rows** on a default that is a judgement, not a measurement. Unchanged this round.
- **262 dead addresses remain on disk.** Nothing deletes them; the marker is a document, and a determined sender can still open a ZHUS file.
