## What did land: the guard, before the key

The one instruction that needed no credential is done, and it is the one worth doing first.

**`openrouter_api` added to `clippershq/secrets_guard.SECRET_BLOCKS`** and to the report scanner. That is deliberately the same order BL-723 used for `gemini_api` — list the block *before* the client exists, so protection is never racing a paste. From that module's own docstring: the threat is *"the client that has not been written yet."*

Verified, using a synthetic key of the right shape (never a real one):

```
SECRET_BLOCKS            : (..., 'gemini_api', 'openrouter_api')
is_secret_field(openrouter_api, key) : True
would redact a future key            : True
  "Authorization: Bearer sk-or-v1-..."  ->  "Authorization: Bearer ***REDACTED***"
  "GET https://openrouter.ai/api/v1/chat" -> base_url NOT redacted (still debuggable)
```

**The scanner no longer keeps its own copy.** `scratch/scan_report_for_secrets.py` had a hand-maintained duplicate of the block list — the exact drift hazard BL-723 removed one level up. It now imports `secrets_guard.SECRET_BLOCKS`, with the literal retained only as a standalone fallback. Confirmed identical at runtime:

```
scanner SECRET_BLOCKS resolved to: ('api','ig_api','tikhub_api','youtube_api','twitch_api','gemini_api','openrouter_api')
identical to secrets_guard: True
```

Suites **50/50, 2,249 checks**. Campaigns SHA **`8e02f8d6f6307ae8`**. `config.json`, `spend.json`, `master_leads.csv` all byte-identical to backups `.bak_20260730_132549`.
