## 1. The index — and why both address forms is the whole point

`build_key_index()` makes one pass over the master and returns `key -> [row indices]`. `index_lookup()` then replaces a full 58k-row scan per key with a dict hit.

**Measured on the live files, 58,324 rows, 2,949 keys:**

| approach | time |
|---|---:|
| **build index once + 2,949 lookups** | **0.269 s** (0.231 build + 0.038 lookup) |
| looped `match_indices` (measured on 40 keys, projected) | **205.4 s** |
| **speedup** | **763×** |

Correctness is not traded for speed: on 60 randomly sampled live keys the index and `match_indices` returned **identical row sets, 0 disagreements**. That equivalence is now a permanent test.

### The subtle half — 8 → 0

The master stores the **raw scraped cell**; the exporter writes the **cleaned** address that `bio_parser.normalize_email` repairs out of it. Two different strings for the same person. I measured a raw-only index against a both-forms index over the same 2,949 keys:

| index | unmatched |
|---|---:|
| raw form only | **8** |
| **both forms** | **0** |

All eight are consumer Gmail addresses, redacted here. Three distinct damage classes, exactly as BL-797 described:

| damage in the master cell | count | what the exporter writes |
|---|---:|---|
| CSV-injection sanitizer prefix `'-…` | 5 | prefix stripped |
| glued URL fragment `www.…` | 1 | fragment stripped |
| run of seven dots before the `@` | 2 | dots collapsed |

**What those 8 would have cost:** they can be *mailed* — they are in the export — but not *stamped*. An unstamped lead has no `date_sent`, so `send_suppress.classify()` never returns `already_sent` for it, and it goes out again on **every future send**. Eight people receiving a duplicate cold email every cycle. The invariant the index now enforces, and a test locks: **anything the exporter can emit, the marker must be able to stamp.**

## 2. The marker

`mark_sent_from_csv(csv_path, date_sent, sent_channel, touch_number, message_variant, *, master_csv, dry_run=False)`.

The index is built **once, inside the lock**. Everything already validated is reused — `normalize_outcome`/`apply_outcome`, `filelock.file_lock`, the timestamped backup, the atomic `os.replace` + `fsync`. The only thing deliberately not reused is `match_indices` in a loop.

**Unmatched and ambiguous come back as key LISTS, never counts.** A count says something went wrong but not who, and "8 leads were mailed and never stamped" is only actionable if you can see which 8.

**Ambiguous keys are refused, not guessed.** The live dry run finds the same 6 shared agency inboxes BL-797 did — United Talent, nexaecho, Spires — where one address represents several artists. Putting a send date on the wrong artist fabricates history for a real person.

## 3. The validator was rejecting its own columns — plus one bug the tests found

`normalize_outcome` validated against `OUTCOME_COLUMNS`, so it raised `unknown outcome field: touch_number` for a column that **already existed in the live master header**. It now validates against `RECORDABLE_COLUMNS`. The same one-word fix was needed in `record_outcome`'s output-header loop, where the narrower list would have let `DictWriter` silently drop a value.

| input | result |
|---|---|
| `touch_number=0` | **rejected** — "there is no zeroth contact" |
| `touch_number=-1` | rejected |
| `touch_number='x'` | rejected — "must be a whole number" |
| `message_variant` 41 chars | rejected — cap is 40 |
| `touch_number=1, message_variant='A'` | accepted → `{'touch_number': '1', 'message_variant': 'A'}` |

**And a real bug, caught by a test I wrote rather than by inspection.** I filtered empty fields with `str(v or "").strip()`. `0` is falsy, so an explicit `touch_number=0` was **silently dropped instead of rejected** — a sender typing 0 would get rows stamped with no touch number at all, and no error. The guard `touch_number` exists to provide would have been bypassed by the one value it was written to catch. Now `v is not None and str(v).strip()`.
