# BL-673 — Instagram cover capture works again, off HikerAPI instead of dead Apify

**2026-07-29 · SHIPPED to `checkpoint/BL-673` @ `74fcab74`, verified on origin. Base main `c8321777`.** Tags `pre-BL-673` / `post-BL-673`. Display only: the only DB field written anywhere in this round is `Clip.thumbnailUrl`.

## PART 1 — the fix

`clip-thumbnail.ts` sent Instagram into `fetchClipStats(..., { skipHikerOverlay: true })`. That flag exists precisely to route Instagram **past** the HikerAPI branch and into a tier chain that is entirely Apify. Apify has 401'd on every call since the key was emptied at 2026-07-22T11:12Z, so Instagram covers ran at 0 of 169 while TikTok held 54 of 54 (BL-670). Instagram now never reaches that call.

**No new HTTP plumbing was needed, and no provider file was touched.** BL-670 read the HikerAPI cover as unavailable because `HikerResult.raw` is deliberately reduced to a tiny diagnostic blob. But the same result object also carries **`rawBody`**, documented at `hikerapi.ts:97` as *"Full top-level JSON parsed from the response body, verbatim"*, populated on every 200 by `probeHiker` (`hikerapi.ts:378`). And `extractCoverUrl` was already probing exactly the right path, `image_versions2.candidates.0.url` (`clip-thumbnail.ts:113`). The payload and the extractor both already existed; they had simply never been introduced. So the fix is one existing call plus the same unwrap `classifyV2Media` performs:

```ts
const res  = await fetchHikerInstagramByUrl(clipUrl);          // /v2/media/info/by/code → by/url
const body = res.rawBody;
const media = body.media_or_ad ?? body.media ?? body.item ?? body.data ?? body;   // hikerapi.ts:492
const cover = extractCoverUrl(media, "instagram");             // already knew this shape
```

**Byte-identical by blob OID, proving the blast radius:** `hikerapi.ts` `cba6a277`, `apify.ts` `5ab4cefb`, `ClipCardNew.tsx` `fd1f99c0`. The entire source change is one file, `src/lib/clip-thumbnail.ts`.

**Cost:** exactly ONE HikerAPI media call per capture attempt, about $0.001 at the repo's own ledger rate. There is no retry loop.

### Fail safe, every branch, never a throw

The whole capture already sits inside a `try/catch` that returns `{ url: null, reason: "capture-error" }`, so a thumbnail failure cannot block or throw on the submit path. Each case now reports a **specific** reason instead of a generic `scrape-empty`:

| case | reason | behaviour |
|---|---|---|
| provider outage cooldown | `hiker-cooldown` | no call is made at all |
| deleted or private post | `hiker-not-found` | placeholder stands |
| any other non-2xx, network, timeout, no key | `hiker-http-<code>` | placeholder stands |
| body absent or unparseable | `hiker-no-body` | placeholder stands |
| no media object | `hiker-no-media` | placeholder stands |
| **post with no image candidate** | `hiker-no-image-candidate` | placeholder stands |
| download fails | `download-http-<code>` etc. (unchanged) | placeholder stands |
| storage unavailable | `storage-not-configured` | **stores nothing** |

**An image-only carousel is a SUCCESS, not a failure.** HikerAPI cannot sum its views, so BL-610 quarantines it for tracking — but its first child still carries a perfectly good cover, and a cover is all this module wants. Views and covers are independent questions, so the classification verdict is deliberately not consulted. Proven below.

**The re-host stays mandatory.** Measured live this round: the Instagram candidate is a signed URL carrying `oe`/`oh` params. `rehostImage` is unchanged and is structurally incapable of returning a provider URL, since it ends at `supabase.storage.getPublicUrl(...)`.
