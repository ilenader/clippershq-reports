**Date:** 2026-07-29 · **Type:** Feasibility, read-only · **Spend:** $0.00
**Nothing was installed.** No account created, no terms accepted, no model weights downloaded, no credential read or printed. Every install candidate went through `pipguard.py --check-only`.

Follow-up to [BL-717](BL-717.md), which closed the 7B class on measured arithmetic and named these two as the surviving leads.

**And this does not displace Gemini.** ~2 s of decode per clip on 12 cores against ~$2 per 1,000 clips is a real trade, but the local path is still unbenchmarked for *accuracy*. Gemini remains a perfectly good answer.

## 1. Mellow — licence clean, two BL-717 corrections, then a hard stop

### Corrections to BL-717

**The Hugging Face page does not 401.** Re-checked anonymously:

```
https://huggingface.co/soham97/mellow            -> HTTP 200
https://huggingface.co/api/models/soham97/mellow -> HTTP 200
```

BL-717's 401 was transient or an artifact of its fetch method, not a gate. The model is **not gated** and needs no terms acceptance.

**"Not on PyPI" was right, and the real channel is git.** There is no `setup.py` or `pyproject.toml` in the repo (both 404) — it is not a package at all. The documented install is:

> `pip install -r requirements.txt` … `python example.py`

with weights at `huggingface.co/soham97/Mellow` (capital M) and a Zenodo mirror (`records/15036628`).

### Licence — CONFIRMED, and it is the clean one

- **Code: MIT.** Read from the raw file, not a badge: `raw.githubusercontent.com/soham97/mellow/main/LICENSE` → `MIT License / Copyright (c) 2024 Soham`.
- **Weights: MIT.** The HF model card declares `license: mit`, ungated.

This matters because BL-717 flagged the MU-LLaMA trap — MIT on the repo covering LLaMA-derived weights with their own conditions. **Mellow does not have that problem**: it is built on HTSAT + SmolLM2, and both code and checkpoint carry MIT directly. Commercial use is clear.

### The blocker: its pins are the CLAP-killer

`requirements.txt`, in full:

```
importlib_resources==5.12.0
librosa==0.10.0.post2
PyYAML==6.0
torch==2.0.0
torchaudio==2.0.1
torchlibrosa==0.1.0
transformers==4.46.3
numpy==1.23.5
```

Against what is installed:

| package | installed | Mellow pins | direction |
|---|---|---|---|
| torch | **2.11.0+cpu** | 2.0.0 | **downgrade** |
| transformers | **5.12.1** | 4.46.3 | **downgrade** |
| numpy | **2.3.2** | **1.23.5** | **downgrade** |
| librosa | 0.11.0 | 0.10.0.post2 | downgrade (unprotected) |

`pipguard.py --check-only` on each pin:

| pin | verdict |
|---|---|
| `torch==2.0.0` | **REFUSED** |
| `transformers==4.46.3` | **REFUSED** |
| `numpy==1.23.5` | **REFUSED** |
| `torchaudio==2.0.1` | **REFUSED** (drags torch back) |
| `librosa==0.10.0.post2` | CLEAN |

**4 of 5 refused.** The guard's own words on the decisive one:

> `numpy 2.x is this repo's ABI floor -- torch, PIL, onnxruntime, numba and cv2 are all compiled against it. A downgrade does not error cleanly, it segfaults at import. This has now been caught twice (BL-681, BL-682).`

This is precisely the class of near-miss BL-693 documented. **Nothing was installed; the environment is untouched.**

### Is that fatal? Honestly: not proven fatal, but not worth it

Two escapes exist and neither is attractive:

1. **A separate venv + subprocess boundary** — the guard's own suggested route. That is the "heavy-ML venv" idea already considered and **cancelled** in an earlier round. Reviving it for a 167M model means a second multi-GB torch install to save a $2/1,000 API call.
2. **Ignore the pins and run on current torch/transformers.** Plausible — the pins are what the authors tested, not necessarily hard floors, and SmolLM2 is supported in transformers 5.x. But `transformers 4.46 → 5.12` is a major-version jump, and verifying it means downloading weights and running the model. That is a real experiment, not a paper check, and it was out of scope for a read-only round.

**Mellow is parked, not dead.** If it is ever revived, the order is: current-versions trial first, separate venv only if that fails.

## 2. LFM2-Audio-1.5B — viable, and the audio path is confirmed in source

### The GGUF really does audio, not text-only

This was the specific question, and the answer is unambiguous. Both GGUF repos ship an **`mmproj`** — the multimodal projector that carries the audio encoder:

| repo | files |
|---|---|
| **`ggml-org/LFM2-Audio-1.5B-GGUF`** | `LFM2-Audio-1.5B-Q8_0.gguf` + **`mmproj-LFM2-Audio-1.5B-Q8_0.gguf`** |
| `LiquidAI/LFM2.5-Audio-1.5B-GGUF` | F16/Q8_0/Q4_0 + **3 mmproj** + vocoder + tokenizer + runners |

The first is published by **ggml-org — llama.cpp's own organisation**, which is the strongest available signal of upstream support.

**Confirmed in upstream source**, since llama.cpp's `docs/multimodal.md` does *not* list LFM2-Audio (it names only Ultravox, Voxtral and Qwen3-ASR) and that discrepancy needed resolving:

```
tools/mtmd/mtmd.cpp:713    case PROJECTOR_TYPE_LFM2A:
tools/mtmd/clip.cpp        case PROJECTOR_TYPE_LFM2A:   (x6, lines 1000-5030)
```

`LFM2A` is the audio projector, distinct from `PROJECTOR_TYPE_LFM2` (vision, line 596). **Audio input is first-class in upstream mtmd; the docs are simply behind.**

### Version trap worth knowing: 2.0 is the supported one, not 2.5

The brief named **LFM2.5**. The upstream-supported, ggml-org-published GGUF is **LFM2-Audio (2.0)**. LFM2.5's own GGUF repo ships Liquid's *forked* runners:

```
runners/llama-liquid-audio-android-arm64.zip
runners/llama-liquid-audio-macos-arm64.zip
runners/llama-liquid-audio-ubuntu-arm64.zip
runners/llama-liquid-audio-ubuntu-x64.zip
```

**There is no Windows build**, and the name implies a fork rather than stock llama.cpp. `clip.cpp` mentions `LFM2.5-VL-1.6B` (the *vision* 2.5 model), so 2.5-vision is upstream; 2.5-**audio** is not confirmed there.

**Use `ggml-org/LFM2-Audio-1.5B-GGUF` (2.0).** It needs no vendor runner and no fork.

### Licence — usable, with one condition that must be checked, not assumed

`LFM Open License v1.0`, read from the repo's own LICENSE file. It is Apache-2.0-shaped with one substantive addition:

> **§ "Threshold"** — *"annual revenue of 10 million United States dollars ($10,000,000) or more."*
> **§5(a)** — *"The rights granted under this License for Commercial Use are conditioned upon You or Your Legal Entity not exceeding the Threshold."*
> **§5(b)** — *"Any Commercial Use of the Work or a Derivative Work by a Legal Entity that exceeds the Threshold is not licensed under this Agreement."*
> **§11** — *"This License will terminate automatically and immediately if You fail to comply."*

"Legal Entity" includes entities under common control, and "Commercial Use" is *"any use … for direct or indirect commercial advantage or monetary compensation"* — lead generation plainly qualifies.

**So: commercially usable while annual revenue stays under $10M; not licensed above it.** That is a business fact the owner must confirm, not a technical one. It is a weaker grant than Mellow's MIT, and it is the one thing that could still disqualify this path.

### Guard verdict: CLEAN

```
pipguard: dry-running `pip install llama-cpp-python` ...
pipguard: resolution is CLEAN (no protected package moves backwards).
          --check-only was set, so nothing was installed.
```

`llama_cpp` is **not currently installed**. GGUF's hand-written integer kernels are exactly the right shape for this box — they sidestep the AVX-512 gap BL-717 measured, because they never touch fp16/bf16 at all.

`ffmpeg 8.0` is already present for the AAC-in-MP4 → wav demux.

## 3. Footprint, speed, and enum pinning

### RAM — comfortable, but note the headroom

Measured file sizes (HTTP range request, **no download**):

| build | model | mmproj | **total** |
|---|---|---|---|
| LFM2-Audio-1.5B **Q8_0** | 1,246,253,184 B (1.16 GiB) | 332,716,256 B (0.32 GiB) | **1.47 GiB** |
| LFM2.5-Audio-1.5B **Q4_0** | 695,750,880 B (0.65 GiB) | 219,511,136 B (0.20 GiB) | 0.85 GiB |

Plus KV cache and runtime, call it **~2 GB resident** for Q8_0.

**A caveat BL-717 did not surface: this box had 15.9 GB total but only 2.6 GB *free* at measurement time.** The model fits, but not alongside much else — and BL-701 measured a Spotify run reaching 147 MB… while an IG crawl with the vision stack loaded is far larger. **Do not plan to run this concurrently with a vision-enabled funnel.**

### Speed — and a correction to BL-717's estimate

BL-717 projected LFM2.5 at "~93 tok/s" from 2 FLOPs/param against 278 GFLOP/s. **That is the wrong bound.** Quantised decode is *memory-bandwidth* limited, not FLOP limited — every token streams the whole weight file.

Measured on this box:

```
memcpy (read+write)   : 24.9 GB/s
stream read (fp32 sum):  8.8 GB/s
=> effective read      : ~12.5 GB/s
```

| build | weights | decode bound | 20-token enum answer | 60-token answer |
|---|---|---|---|---|
| Q8_0 | 1.25 GB | **~10 tok/s** | **~2.0 s** | ~6.0 s |
| Q4_0 | 0.70 GB | ~18 tok/s | ~1.1 s | ~3.3 s |

**~5–9× slower than BL-717 projected, and still perfectly usable** for four enum answers — which need ~20 tokens, not 60.

**These are decode only and are UPPER bounds.** They exclude the audio-encoder prefill for a 30 s clip, the KV cache, and llama.cpp's own overhead. **A real seconds-per-30s-clip figure cannot be produced without installing**, which this round did not do. Expect a few seconds per clip; treat anything more precise as unmeasured.

### Enum pinning — stronger than Gemini's

Yes, and it is a better mechanism than the one it replaces. llama.cpp constrains output with **GBNF grammars**:

```
root ::= "electronic" | "hiphop" | "rock" | "pop" | "unknown"
```

plus a JSON-schema-to-grammar converter in which *"enums become alternation rules automatically"*, driven by `--json` on `llama-cli` or the `json_schema` field on `llama-server`.

This is a **sampler-level hard constraint**: tokens outside the vocabulary get zero probability and literally cannot be emitted. Gemini's structured-output enum is a request-side instruction the decoder is asked to honour. For pinning to a fixed answer vocabulary, GBNF is the stronger guarantee, not merely the equivalent one.

## 5. Recommendation

**If the local path is wanted: `ggml-org/LFM2-Audio-1.5B-GGUF` (Q8_0) + `llama-cpp-python`, with GBNF-pinned answers.** Guard-clean, ~1.5 GB, audio input confirmed in upstream source, ~2 s of decode per clip, $0 per call. **Two things to settle first:** confirm annual revenue is under the $10M licence threshold, and run one clip end-to-end — nothing here proves accuracy, only feasibility.

**Do not revive Mellow for this.** Its licence is the cleanest of anything examined across BL-717 and this round, and that is worth recording for future use. But installing it as documented is refused four ways by the guard, and the two workarounds are a cancelled venv project or an untested major-version jump — a lot of risk to avoid a $2/1,000 API call.

**Gemini remains the sensible default**, exactly as the brief allows. The local path is now *known viable* rather than *maybe*, which is what this round was for; it is not yet known *accurate*, and that gap costs a benchmark to close.

## What was not established

- **Seconds per 30 s clip, end to end.** Only the decode bound was computed. The audio-encoder prefill for 30 s of input is unmeasured and needs an install.
- **Accuracy of either model on this corpus.** No clip was processed. BL-717's deciding number is still missing.
- **Whether Mellow runs on torch 2.11 / transformers 5.12.** Its pins say otherwise; whether they are real floors is untested.
- **Whether LFM2.5-Audio (2.5) works on stock llama.cpp on Windows.** `PROJECTOR_TYPE_LFM2A` confirms 2.0; 2.5-audio appears only via Liquid's forked runners, which have no Windows build.
- **Quality difference between Q8_0 and Q4_0.** Q4_0 is 1.7× faster and half the size; whether it degrades genre/energy judgements is unmeasured.
- **The $10M revenue position.** A business fact, not checkable from here.

## Method

All licences were read from primary files — `raw.githubusercontent.com/.../LICENSE` for Mellow, the repo's own `LICENSE` for LFM. Audio support was confirmed by reading `PROJECTOR_TYPE_LFM2A` in llama.cpp's `tools/mtmd/mtmd.cpp` and `clip.cpp` at master, after the official `docs/multimodal.md` was found not to list the model. File sizes came from HTTP range requests with no body download. Memory bandwidth was measured with a 400 MB `numpy` memcpy and stream-read, best of five, after an initial `int8.sum()` attempt was discarded as compute-bound (it reported an implausible 1.7 GB/s). Decode bounds are weights-streamed-per-token against measured bandwidth and are upper bounds. Every install candidate went through `pipguard.py --check-only`; nothing was installed.
