## 1. BLOCKER 1 — spend now survives a hard kill, reconciled against the vendor's receipt

### The defect was not missing machinery. It was an opt-in nobody took.

`ig_client.configure_autoflush` has existed since BL-888 and its docstring already makes the
whole argument: a hard kill on Windows exits `0xC000013A`, so **no `finally` and no `atexit`
runs**, and the only spend that survives is the spend already on disk. It bounds the loss to
25 calls **or** 60 seconds, whichever trips first — a count bounds dollars, only a clock
bounds a stall.

Counted on this tree: **16 `IgClient(` construction sites, and 2 of them armed it**
(`control.py:3096` clip_label, `editor_brief.py:954`). The Spotify funnel — the one about to
run for 1,000 leads — was one of the 14 that did not.

### The fix is in the constructor, so the next caller cannot forget

`IgClient.__init__` now arms autoflush itself. It arms **only when a real config file was
loaded**, because `flush_spend` writes to a money ledger and a client built in a test must
never do that; test clients construct with `config_path="nonexistent.json"` and stay silent.
`autoflush=False` disables it, `autoflush=True` forces it. Re-pointing it with
`configure_autoflush` changes attribution and never the amount — `flush_spend` writes only
requests made since the last flush, so nothing can double-charge.

`control.py`'s Spotify site now names the campaign, so the money is *attributable* and not
merely *recorded*: without it the spend lands under `IG_AUX / unattributed` and "what did the
Spotify run cost" cannot be asked of the ledger by any query an operator would write.

### Proven by killing a real run — `scratch/bl1167_kill.py`

Two children, each making real billed requests, each destroyed with `taskkill /F /T` after 38
receipt-counted requests. Neither got to run any exit path. The vendor receipt is written to a
side file, fsynced after **every** call, so the parent can read it once the child no longer
exists — `spend.json` is the thing on trial and cannot also be the reference.

| arm | exit | receipt (vendor) | on the ledger | lost | understated |
|---|---|---|---|---|---|
| **OFF** — what 14 of 16 sites had | hard kill | **38** | **0** | 38 | **100%** ($0.0228 invisible) |
| **ON** — BL-1167 default | hard kill | **38** | **38** | **0** | **0%** |

The ON arm's ledger rows are `16` then `22`, written 32 seconds apart. **Both were written by
the CLOCK, not the count** — the calls are slow enough (polite delay + network) that 25 was
never reached. That is the exact case BL-888's docstring predicted and the reason a count
alone would not have been enough here.

### One thing I got wrong, and it is the same shape as the bug

The first run of this probe reported **both** arms as 100% lost — including the one that had
written a perfect 38. My reader guessed the ledger's shape (`entries`/`rows`, `ig_calls`)
and the real shape is `runs` / `calls`, so it found no rows and reported zero. *A reader that
cannot find the rows reports the same zero as a spend path that never wrote them.* I had
reproduced the round's own bug inside the instrument. The reader now raises on an unknown
shape rather than returning a confident zero, and the corrected figures above were recomputed
from evidence already on disk — **no calls were re-spent to fix my mistake.**

## 2. BLOCKER 2 — two concurrent runs each report only their own, and stop losing records

### The reported defect

`run_resume.path_for` is funnel-keyed **on purpose**: a resume has to find what the *previous*
run did and does not know that run's id. Correct for resume, and a shared mailbox for
reporting — nothing in the file said who wrote what, so `run.py`'s heartbeat `_leads_in_flight`
counted every record in it and two concurrent Spotify runs both reported the **union**: 88
when each had ~44.

### A second defect the first test found, which is worse

Two processes appending to one `.jsonl` do not merely confuse the reader — **they lose
records.** `io.open(path,"a")` resolves the append position through the CRT, which seeks to
end and then writes, and those two steps are not atomic across processes. Measured with two
real processes writing 50 records between them:

```
45 lines on disk   0 torn   0 malformed   -- and 5 records simply GONE
run A wrote 23 and 21 survived
```

Nothing was corrupt, so nothing complained. The checkpoint exists so a killed run keeps what
it found; one that silently drops 10% of it under concurrency is failing at its one job, in
the direction that costs money — every lost record is a unit a resume pays for again.

### The fix: stamp the record, and give each run its own file

- Every record carries `run_id`.
- **Writes go to `<funnel>.<run_id>.jsonl` — one writer per file, so the race is unreachable
  rather than smaller.** Reads glob them all back together, plus the pre-BL-1167 shared file,
  so resume is unchanged.
- The two questions are answered by two different methods, and the asymmetry is the design:
  `done_keys()` → **every** run's work (skipping work another run paid for is right);
  `records(mine=True)` → **this** run's (what a heartbeat and a summary are asking).
- Records written before this change carry no `run_id` and are counted as **prior work, not
  mine** — the safe direction.
- `run.py` pins the id once, where it already owns this run's identity, so the writer
  (`control.py`) and the reader (`run.py`, thirty seconds later) agree rather than guess.

### Proven — `scratch/bl1167_concurrent.py`, two real OS processes

| run | wrote | **reported** | records visible for resume |
|---|---|---|---|
| A | 20 leads | **20** *(was 44)* | 45 |
| B | 24 leads | **24** *(was 44)* | 50 |

```
resume still sees every run's work : done_keys() = 50 of 50   (was 45 of 50)
a third run's own view             : records(mine=True) = 0
```

Two processes, not two threads — the run id is process-global, which is the right scope
precisely because a run is a process; two threads would share it and the test would pass for
the wrong reason.

## 3. BLOCKER 3 — the fourth line-counting site

`control.py` counted `sum(1 for _ in open(SEND_FILE)) - 1` at **two** sites: the send-file
notice and the `(+N vs last build)` delta. Both now call `all_bot_ready.count_records()`.

Measured on this tree today:

```
master_leads.csv      60,241 records   across 134,701 lines   = 2.24x
output/ALL_BOT_READY.csv   2,970 records   across   2,970 lines   = 1.00x
```

**It is harmless at this site today and that is exactly the problem.** The send file is built
by `all_bot_ready.build`, which happens not to emit a multi-line column right now. Nothing
enforces that and nothing would announce it changing — the number would simply begin to
drift, plausibly, which is how the master one survived to report 133,474 leads for a file
holding 59,016.

The guard is an **AST** check, not a grep: it walks `control.py` for `sum(...)` over a
generator whose iterator is an `open(...)` call, so reformatting cannot slip past it.

## 5. WHY NOT AN EMAIL-FINDER TOOL — settled on the vendor's own documentation

Hunter, Apollo, Snov and the rest are `first.last@COMPANY-DOMAIN` permuters: name + corporate
domain → guess → verify against MX. **Hunter's own documentation says it cannot function with
personal addresses.** Our leads are independent musicians on gmail. There is no domain to
permute. Buying one spends money on a mechanism that structurally cannot answer our question.

**A web search was tried first and is not reachable from this machine** (measured, free):

```
html.duckduckgo.com/html/   HTTP 202  anti-bot challenge page   0 results parsed
lite.duckduckgo.com/lite/   HTTP 202  same                      0
www.bing.com/search         HTTP 200  73 KB of markup           0 result blocks
```

So the search leg uses **`/v2/fbsearch/accounts`** — Instagram's own account search, through
HikerAPI, the vendor already being paid, already used by `crawl_suggested.py`. It returns
`username` **and** `full_name`, which is what makes verification possible for free.

## 6. THE NEW PATH, AND ITS PRECISION — measured against ground truth

### The ground truth was free and already on disk

2,810 artists in the live-run checkpoints already have a handle the funnel resolved **from
the artist's own Spotify link** — the artist's own word, not a judgement. Running the search
path on those artists' names and comparing against the handle we already know is a labelled
test set that cost nothing to build.

**n = 120 artists, seed 1167, 106 billed requests.** 14 of 120 (11.7%) were refused *before*
any call by `searchable()` — a name too short or too generic to identify anyone.

### Name similarity alone: 76.0% precision — and it does not improve at any bar

| bar | accepted | correct | precision | recall |
|---|---|---|---|---|
| 0.55 | 25 | 19 | 76.0% | 23.6% |
| 0.72 | 25 | 19 | **76.0%** | 23.6% |
| 0.85 | 24 | 19 | 79.2% | 22.6% |
| 0.95 | 24 | 19 | 79.2% | 22.6% |

**The curve is flat, and that is the finding that decided the design.** Raising the threshold
does nothing because the wrong matches score at the top:

| artist (public) | matched | score | what it actually was |
|---|---|---|---|
| Rachel Chinouriri | `ra**@…#a7f21c` | 0.98 | **a fan page** |
| Scarface | `sc**@…#4be0d9` | 0.98 | a namesake, unrelated person |
| La Biggie | `la**@…#77c1e4` | 1.00 | a namesake |
| Songer | `so**@…#2d9b06` | 0.98 | a different act |
| Bfb Da Packman | `of**@…#c53a18` | 0.98 | an `official…` variant of the same name |
| D. Ramirez | `ra**@…#e81f7b` | 0.80 | a namesake |

A namesake's name is not *less* similar — it is **identical**. A fan page contains the
artist's name *more* completely than the artist's own account does, so it ranks first. No
threshold on a name can separate these.

### Guard 1 — derived accounts (free): 76.0% → 79.2%

A fan page announces itself. `derived_account()` looks for `fan`, `updates`, `daily`,
`archive`, `stan`, `tribute`, `lyrics`… **in the part of the handle or display name that the
artist's own name did not supply**, so an artist genuinely called "Daily Bread" is not
refused for containing "daily". Re-evaluated offline against the same 120 rows — **no new
spend**: it killed **1 wrong match and 0 correct ones**.

### Guard 2 — profile confirmation (1 extra call): 79.2% → **92.3%**

Name evidence is exhausted, so the next signal has to be a different question: **who is this
account?** One `enrich_profile` call returns IG's own `category` label and the account's
outbound links, neither of which comes from the name. A random namesake is not categorised
*Musician/Band* and does not link to Spotify.

| | accepted | correct | precision |
|---|---|---|---|
| after the fan-page guard | 24 | 19 | 79.2% |
| **and profile-confirmed** | **13** | **12** | **92.3%** |

**All four namesakes were correctly rejected** by confirmation. The single surviving error is
the `official…` variant of *Bfb Da Packman* — plausibly a second genuine account of the same
artist rather than a wrong person, but I have counted it as wrong because I cannot prove
otherwise.

**Say the honest thing about this number: n = 13.** The 95% Wilson interval on 12/13 is
roughly **[66%, 99.6%]**. The *mechanism* is demonstrated — confirmation removes exactly the
failure mode that name scoring cannot — but 13 accepted matches is a small calibration set,
and a larger one is the first thing the next round should buy.

### The shipping rule

`artist_search.best_match` returns a `Match` whose `handle` is **None** on refusal — never
`""`, never a best-effort guess — and `refused` carries the sentence. Ambiguity is a refusal:
two candidates within 0.08 of each other means the search matched *a name, not a person*, and
neither is returned. `private` is recorded as **reachability, not identity** — an exact-name
private account is still them; what closes is the email path, not the match.

## 7. LANGUAGE — measured, and the answer is "do not ship the reject side"

He wants English primarily, Spanish acceptable, nothing else — meaning the artist's *songs*.

### Signal 0 — the artist's own track titles (what the funnel uses today)

The right signal, and the funnel already uses it: `_song_text` judges **track titles**, the
language they record in, deliberately not the biography (a Serbian artist whose titles are
English records in English and is a good lead).

**Its problem is coverage, not accuracy: 62.3% of checked artists get no verdict at all.**
Of the 37.7% that do — 3,238 artists — the mix is **96.5% English, 1.1% Spanish, 2.3% other**.

**That number is the headline for this section.** The pool is already almost entirely English,
and `non_target_language` currently cuts **0.8%** of checked artists. A language filter has
very little left to buy.

### Signal 1 — playlist name / query, joined to the artist's own verdict (250 artists)

| playlist name says | artist really is | precision |
|---|---|---|
| **english** | english (83 of 85) | **97.6%** |
| **spanish** | spanish (8 of 11) | 72.7% *(n=11)* |
| **other** | — | **0 observations** |

**The reject side is unmeasurable here and I am not going to guess it.** Not one playlist in
the joined set was named as a non-target language, so I have zero evidence about how often
rejecting a playlist would throw away a good artist — and rejecting a playlist discards every
artist in it, invisibly. **61.6% of artists came from a playlist whose name says nothing at
all.**

**Recommendation:** use the playlist name **positively** — prefer/order by english-named
playlists at 97.6% precision — and **do not ship a reject filter**. `clippershq/playlist_language.py`
was declared in this round's claim and **deliberately not written**: the measurement did not
license it, and shipping a filter that guesses is worse than shipping none.

### Signal 2 — country

Highly predictive where known — US 98.8% english, GB 99.3%, IE 100%, AU 98.9% — but it is
**only known after a paid resolve**, so it cannot act as a playlist-level pre-filter and
cannot save any money. It is a post-hoc label, not a gate.

## 8. END TO END — a capped batch through the fixed pipeline

`scratch/bl1167_e2e.py`, run on **Loss A** — artists that passed every filter and that the
funnel gave up on. The path, with every stage able to refuse:

```
1 searchable()          FREE    a hopeless name never reaches the vendor
2 fbsearch/accounts     1 call
3 best_match()          FREE    name score + derived-account guard
4 enrich_profile()      1 call  ONE request that does both remaining jobs:
5 confirm_by_profile()  FREE      - identity (IG category + outbound music links)
6 emails_from_bio()     FREE      - the address, out of the same response
```

Steps 4–6 share one request, which is why the **marginal cost of the email is zero** once
identity has been confirmed.

### The batch did not complete, and I am reporting that rather than a partial as a whole

`bl1167_e2e.py` **hung reproducibly**, twice, at ~18 billed requests — once under a
background pipe and once writing straight to a file, so a blocked stdout is ruled out. It
stopped advancing the ledger and stopped writing progress lines; both runs were hard-killed.
The script only serialises its rows at the end, so the completed artists were not recoverable.
The cause is not diagnosed and is named in §11.

**One thing it did prove, unplanned:** at the moment of each kill the ledger held **18 and
then 36** calls for `BL1167_E2E`. Those were written by autoflush during a run that never
reached any exit path — Blocker 1's fix working on a kill I did not stage.

### So the stages were measured with the instrument that does work

`bl1167_search.py` completed on both arms. Combined with the confirmation arm, every stage of
the path has a measured rate on real artists:

| stage | measured | n | source |
|---|---|---|---|
| searchable (no call spent) | **95.0%** | 40 | Loss A arm |
| search accepts a match | **13.2%** of searchable | 38 | Loss A arm |
| *(for comparison, artists who already had a handle)* | *23.6%* | *106* | *ground-truth arm* |
| profile confirms identity | **54.2%** | 24 | confirmation arm |
| confirmed handle carries an email | **69.2%** | 13 | confirmation arm |

The email rate is the one that matters most and it is the happiest number here: **9 of 13
confirmed handles had an address in the profile the confirmation call had already paid for.**
Its marginal cost is zero.

### Cost per new lead — a projection from measured stages, labelled as one

Per **100 Loss-A artists**:

```
 95 search calls        (95.0% searchable)
 12.5 accepted          (13.2% of searchable)
 12.5 profile calls     (one per accepted, does identity AND email)
  6.8 confirmed handles (54.2% of accepted)
  4.7 emails            (69.2% of confirmed)
-----------------------------------------------------------
107.5 billed requests = $0.0645 at the config price
   -> $0.0137 per NEW EMAIL
   -> $0.0095 per NEW CONTACTABLE lead
```

Across the whole Loss A pool of **1,276**: roughly **87 new confirmed handles and 60 new
emails for about $0.82**.

**What that does to the headline rate**, on the same 4,086 passed artists:

| | before | after | change |
|---|---|---|---|
| contactable | 2,810 (68.8%) | ~2,897 (**70.9%**) | +2.1 pts |
| email | 1,212 (29.7%) | ~1,272 (**31.1%**) | +1.4 pts |

**This is a projection, not a run.** Two assumptions are doing work and both are stated
rather than buried: the 54.2% confirmation rate and the 69.2% email rate were measured on the
ground-truth arm (artists who already had a handle), not on Loss A, and Loss A is the harder
population — its accept rate was already 13.2% against 23.6%. If confirmation and email hold
up worse there, the yield falls and the cost per email rises. **The completing end-to-end run
is what would settle it and it is the first thing the next round should finish.**

### A recall cost worth naming

Five of the 38 Loss-A refusals were **ties** — `@_rubypoole` vs `@rubypoole`,
`@dry__season` vs `@dry.season`, `@rogue_wave2026` vs `@roguewaveband`. Several of those
pairs are plausibly the same artist with two accounts, or the artist plus a squatter. The tie
rule refuses both, which is the right call against a 0.81% bounce ceiling but is not free:
**13% of the Loss-A sample was lost to ambiguity alone.** Resolving a tie by fetching both
profiles and confirming identity would recover some of it for one extra call.

## 9. THE WEDGE, INHERITED AND CAPPED

`bio_parser._EMAIL_RE` is **still quadratic** — 1.95 s at 32 kB, 3.2x per doubling, ~589 s at
the real cap — and `enrich_links` holds its own copy. Neither is fixed and neither is this
round's to fix. **Any new path that parses text inherits it.** `artist_search.emails_from_bio`
truncates to `BIO_CAP_CHARS = 4000` before `bio_parser` sees anything; an Instagram bio is
limited to 150 characters, so the cap is far past anything legitimate. A test feeds it a
400 kB hostile string and asserts it returns in under 5 seconds.
