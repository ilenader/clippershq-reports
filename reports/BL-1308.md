## 2. MX IS A REFUSAL NOW — ON BOTH PATHS

**The carried item said "not enforced on the `[B]` path". The true state was worse.** Verified:

```
refresh_mx                      0 matches in clippershq/control.py
send_suppress.table_health      all_bot_ready.py:316, inside main()
[B] -> control._build_send_files calls all_bot_ready.build(), never main()
the CLI path itself             try/except Exception -> "never let a warning break the build"
```

So it was **a swallowed print, never a refusal, anywhere**. A send file could be built on
domains nobody had probed.

**`send_suppress.refusal()` is new** and refuses on three conditions, in order: a verdict value
the code does not understand (*a certain bounce can ship*), coverage below **100%** (*the vacuity
itself*), and a table older than 7 days. The `except Exception` is gone from the CLI path — *"never
let a warning break the build"* is right for a warning and wrong for a gate. On `[B]` the refusal
sits **before the write**, and **an unrunnable check is treated as a refusal, not a pass**.

**The escape is one environment variable**, `CLIPPERSHQ_ALLOW_UNVERIFIED_MX`, deliberately not a
config key: a value in `config.json` gets set once and forgotten, where something you have to
type is something you remember. A test asserts it never becomes a config key.

## 3. scratch_gc QUARANTINES. NOTHING WAS DELETED

`shutil.rmtree(p)` at `:318` is gone. Qualifying directories are **moved** to
`quarantine/<batch>/` — the same directory and batch shape `tools/outputs_gc.py` already uses —
and **the manifest is written before the first move**. That order is the rule: a process killed
halfway through still leaves a manifest naming everything that was supposed to go, so
`--restore <batch>` can finish or reverse the job. A manifest written last names nothing at
exactly the moment it is needed. `read_manifest` **raises** on a missing manifest rather than
returning `[]` — it is the function somebody reaches for when they need their data back.

The module docstring said *"removes what qualifies"* and *"unrecoverable"*. Both were now false,
so both were rewritten.

## 5. WHAT WENT WRONG IN THIS ROUND, AND WHAT CAUGHT IT

**Four suite reds after the first pass. Two were mine, and the first is worth reading twice.**

1. **My banner named a marked page.** The first draft said *"recovers one page
   (`armour__mindset`)"* — putting a leaked handle **into the very brief I was marking as
   leaky**. `tests/test_bl1269_presort.py` caught it within the hour. The handle is out; v9 now
   leaks **zero** handles, which means my banner had introduced the only one it had.
2. **My rebuild wrote the CSVs without their companion metas** — reproducing the exact BL-1304
   defect the same evening it was fixed, because `writer.write_bot_ready_csv` writes the CSV and
   nothing else while `control.py` refreshes the pair. Caught by
   `tests/test_bl1304_meta_companion.py`; both metas refreshed.
3. `test_brief_leakcheck` — same cause as (1), cleared with it.
4. `test_bl1307_veto_refused` — **not mine**: another round's prompt, §1.

**And one thing I could not explain, so I did not ship it.** My first fix for (4) checked
polarity per line. Replicated outside the test it returned no offenders; inside the test it
returned one, deterministically, and I could not account for the difference. **A fix I cannot
demonstrate is not a fix**, so it was replaced with a simpler whole-file rule that I could verify,
and the comment in the test says exactly that.

**A note on redaction.** The brief warns that a round's own redactor emitted `local[:2] + "@" +
domain`, so for a two-character local part **that is the whole address** — 2 of 50 "fingerprints"
were complete real emails. **This round did not redact anything, because it never put an address
anywhere.** The rebuild reports counts and domain coverage only; no per-row output was produced.
The safest redactor is the one you never have to call.
