# BL-772 — Platform-change exposure: the loud-zero guard exists in exactly one funnel, five funnels have no saved baseline at all, and an empty 200 is silent everywhere including the guarded one

**Date:** 2026-07-31 · **Type:** Audit, READ-ONLY · **Spend:** $0.00 · **Paid API calls: 0**
Free endpoints only (SpotifyScraper, MusicBrainz, google-play-scraper). HikerAPI / LamaTok / TikHub were never called — they bill per request. The YouTube Data API was skipped because its quota is that funnel's discovery ceiling. Nothing implemented.

---

## The two findings that matter most

**1. The shape-drift guard exists in one funnel, and it is the only funnel that works.**

`ApiShapeDriftError` is raised in exactly three modules — `discovery.py`, `discovery_search.py`, `ig_discovery.py` — all of them the IG/TikTok hashtag crawl. Every other funnel has **zero** drift detection and instead swallows exceptions into empty returns:

| module | shape-drift raises | swallow-and-return-empty | `except Exception` |
|---|---:|---:|---:|
| discovery.py / discovery_search.py / ig_discovery.py | **5** | 0 | 0 |
| spotify_finder.py | **0** | 6 | 14 |
| twitch_finder.py | **0** | 4 | 16 |
| youtube_finder.py | **0** | 3 | 10 |
| repost_finder.py | **0** | 2 | 12 |
| enrich_links.py / listenbrainz.py | **0** | 2 | 4 |

The one funnel that produces **1,592 of your 1,600 sendable leads** (BL-764) is the one with the guard. The five funnels that export nothing are also the five with no way to tell a platform change from a quiet day.

**2. An empty 200 is silent everywhere — including inside the guarded funnel.**

The guard does not do what its name suggests. It fires only when rows come back and *none of them parse*:

```python
# discovery.py:273
if raw_items and not norm_items:
    raise ApiShapeDriftError(...)          # rows returned, 0 parsed -> LOUD
```

An actually-empty response takes a different branch, eleven lines earlier:

```python
# discovery.py:256
if not raw_items:
    log.info("discover_pages: empty itemList ... — stopping")
    return                                  # <-- INFO log, silent return
```

**So the exact failure you named — "returned an empty 200 tomorrow" — is a quiet zero on every funnel in the project, including the guarded one.** The guard catches envelope *reshaping*; it does not catch the provider handing back `{"itemList": []}`. Given this provider has six documented cases of a valid-looking-but-wrong response, that is the gap that matters.

## 4. Canaries — the cheapest check that fails loudly

**One fixture per endpoint, asserted on shape, run before the funnel spends anything.**

```
for each endpoint:
    call it with ONE known-good, stable input      (free where possible)
    assert: HTTP 200
    assert: the envelope key exists                 (itemList / response.items / data)
    assert: the row count is > 0
    assert: EVERY field the code reads is present on the first row
    -> any failure = STOP THE RUN LOUDLY, before the paid loop starts
```

**Cost:** one request per endpoint per run. For the free dependencies that is $0. For HikerAPI/LamaTok it is one billed call each — roughly **$0.0018 per run** against runs that already spend $0.42.

**Two design constraints the data imposes:**

- **Assert on fields present in ALL samples, not any one sample.** Comparing three same-day captures of the same endpoint, `lat`, `lng`, `location`, `video_subtitles_locale` and `video_subtitles_uri` appear on one account and not the other two. Those are *account-level optional fields*. A canary asserting them would fire constantly and be switched off within a week.
- **Assert row count > 0 separately from shape.** They are different failures with different causes, and today only the second is detected.

The one existing guard should also be extended: `if not raw_items` on the *first* page of a tag known to have content is a canary failure, not an empty tag.

## 5. What has already changed that nobody noticed

**The `/v2/user/medias` → `/v2/user/clips` migration moved every field one level deeper.**

Comparing the 2026-07-16 capture against the 2026-07-29 one:

```
ig_user_medias.json   response.items.<field>          224 keys unique to it
ig_user_clips_*.json  response.items.media.<field>    137 keys unique to it
```

Every media field is now nested under `response.items.media.*` instead of `response.items.*`. **This is the same class as `image_versions` vs `image_versions2`** — a path change that a reader keying on the old location resolves to `None` for every row, producing a full run of empty results with a 200 on every request. The flip shipped, and my own BL-746-era note records the symptom: the `/v2/user/clips` wrappers "silently emptied the account gate."

Also visible in the sample set:

- **Two captures are 0 bytes** — `tt_web_itemlist_davidfilmsss.json`, `tt_web_itemlist_zain.vfx.json`. A failure was captured and frozen as a "sample". Nothing consumes these, but nothing flagged them either.
- The v2 hashtag endpoint and the chunk endpoint share almost no envelope: **18 keys unique to v2, 173 unique to chunk.** Two code paths reading "the hashtag feed" are reading two different documents.

| endpoint | status | in use | replacement | migration cost |

**The expensive one is `/v2/hashtag/medias/clips`.** It is deprecated, still in use, and its replacement is not a URL swap — the two envelopes share almost nothing. That is the migration most likely to "work" in testing and return zero in production.

## Honest limits

- **The live Twitch GQL call was not exercised.** `panels_fn` requires a constructed client and `parse_panels` is a pure parser; its rank is from structure (internal endpoint, no policy), not a probe.
- **The paid providers could not be probed at all** — HikerAPI, LamaTok and TikHub bill per request. Their ranking rests on saved samples and prior rounds, so "nothing is broken today" is **not** established for the highest-risk dependency in the table.
- YouTube was skipped to protect quota; its failure mode is inferred from the code path, not observed.
- The swallow-and-return-empty counts come from a regex over `except Exception` blocks. It is a good proxy for "this cannot raise", not a proof that every one of those sites is reachable from a live failure.
- `_probe_samples/` has no manifest — no captured-at timestamp, endpoint URL or request parameters inside the files. File mtime is the only provenance, and that is not a reliable record of when the payload was actually served.
