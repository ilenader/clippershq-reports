## 1. The append lock — proven with two real processes, not asserted

`append()` relied on `O_APPEND` atomicity. That is correct for one line and **useless against a rewriter**: a migration reads a whole shard and writes it back, so anything appended in between is not torn — it is **silently deleted**.

`append`/`append_many` now take the same cross-process `filelock` the migration takes. The proof spawns the race deliberately:

```
A. appender uses clip_library.append_many() (LOCKED)
   rows before 200  appended 5  expected 205  ACTUAL 205  -> NO LOSS

B. appender writes the OLD lock-free way
   rows before 200  appended 5  expected 205  ACTUAL 200  -> LOST 5 ROWS

  PROVEN: the lock is what prevents the loss, not luck.
```

**The lock is on the DATA path.** `file_lock()` appends `.lock` itself; passing `lock_path_for(path)` would lock `<shard>.jsonl.lock.lock` — a path nothing contends for, leaving the real lock free. That is the BL-817 shape that rewrote 58,000 rows believing itself protected. A test asserts no `.lock.lock` path is ever created.

**`append_many` now groups one lock per shard**, not one per row. A walk stores ~12 clips at a time, and twelve acquire/release cycles is both slower and a wider window for a rewriter to interleave.

## 4. `git log -S` vs `-G`, recorded next to `DERIVED_FROM`

```

#   -S counts how many times a string OCCURS and reports commits where the count CHANGED.
```

## Honest limits

- **My commit was swept into another round's commit.** `df8abd8` ("Wire vision to select()…") did a broad `git add` that picked up my staged files before my own `git commit` ran. **The code is complete and correct in HEAD** — verified line by line: the lock, the shard grouping, the `-S`/`-G` note, and both test classes. What is lost is my commit message, not the work. This is the same concurrent-tree hazard that produced the shared-file commits in BL-848, BL-853 and BL-856, in a new form.
- **The lock protects writers that start after it landed.** A process that imported `clip_library` before this change does not take the lock and cannot be made to. During the run that risk was carried by the 97-second quiet window plus the per-shard size/mtime abort — not by the lock. It decays as long-running rounds finish.
- **The liveness guard narrows a race; it does not close one.** It requires 20 s of quiet plus a 6 s sample, and aborts any shard that grew mid-computation. A writer starting in the gap between check and rewrite is still possible.
- **`stale_fields()` still only knows about constants in `clip_library`.** If the Silero VAD threshold, `repost_layout`'s constants or `caption_parser`'s lexicon move, `speech_frac`, `layout` and `valence_text` go stale and nothing notices. Each of those modules would need to expose its own token.
- **`tests/run_all.py` is left broken.** It is another round's file, mid-edit, and repairing it would have collided. Anyone needing an aggregate number today should run the suites directly.
- **1,012 rows now carry a stamp; 1,576 do not** — those have no `speech_frac`, so there is nothing to invalidate. If a future field derives from a constant, those rows will read as stale on first check, correctly.
