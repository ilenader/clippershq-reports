# BL-1165 — the pool was the ceiling, and the "obvious" regex fix was still quadratic

Four things are settled here, and two of them are settled against my own first answer.

**Spotify did not truncate a 2,000-lead target — the target was never reachable.** Six
playlists hold **914 artists between them**, and a run already asks each one for **2,100**.
You cannot buy more artists by asking louder. Adding the 17 seeds already measured and
demoted in the code takes the pool to **2,756**, and those seeds are **4.1x more productive
per artist** than the current six — not because they are better playlists, but because the
current six have been mined until **52.9% of what they return is already in master**.

**The regex fix that everyone reaches for first does not fix it.** Making the quantifiers
possessive is 4x faster and *still quadratic*: at the 250,000-char input the code actually
passes, it takes **589 seconds — measured, not extrapolated**. It would have passed a
benchmark and wedged the run anyway.

**`uvicorn --reload` is broken on Windows here, and it says it is working.** It logs
"Reloading...", never replaces the worker, and then wedges so nothing further is detected.
Shipping it would have been a fix that reports success — which is the exact bug this whole
round is about.

## 1. The seeds, the pool, and why it caps near 1,000

The live config carries **6 seeds**, and a config list *replaces* the module's 7 defaults
entirely (`spotify_finder.py:62`), so `Fresh Finds Country` is silently not in play:

| seed | artists returned |
|---|---:|
| Fresh Finds R&B | 179 |
| RADAR Early Noise | 67 |
| RADAR Canada | 62 |
| RADAR UK & Ireland | 328 |
| RADAR AU & NZ | 54 |
| Fresh Finds Electronic (community) | 467 |
| **unique across all six** | **914** |

**Asking for more cannot work, and this is the arithmetic that proves it.**
`control.py:2280` sets `per_seed = max(config per_seed or 50, target * 3)`. At the configured
`run_target = 700` that is **2,100 artists requested per seed**. I asked one seed for 2,100
and got **179 in 1.4 seconds** — the playlist returned everything it has. A Spotify editorial
playlist is a fixed entity of ~50–470 tracks. **The binding constraint is the NUMBER OF
SEEDS.** Raising the target raises only the request, never the pool, which is precisely why a
2,000 target silently produced 43.

The 1,001 the operator saw is these 914 plus ListenBrainz and related-artist expansion.

### The free options, measured

Every leg below is free — SpotifyScraper, ListenBrainz and MusicBrainz are all keyless. **No
paid call was made by any probe.**

| option | new artists | already in master | notes |
|---|---:|---:|---|
| **current 6 seeds** (baseline) | 914 | **52.9%** | mined repeatedly; the yield is exhausted |
| **+17 DEMOTED_SEEDS** (already in the code) | **+1,842 net-new** | **1.4%** | pool → **2,756**, a 3.0x increase |
| **ListenBrainz, 1 day** (already ON) | +87 net-new | — | **612 SECONDS** for one day |
| ListenBrainz, 30 days | ~30x the above | — | ~**5 hours** of MusicBrainz at 1 req/sec |
| deeper related expansion | already on, depth 2 | — | fires only on a *new qualified* lead, so it is bounded by leads, not by depth |

**The ListenBrainz number that matters is the clock, not the count.** It is free in dollars
and expensive in time: the MBID→Spotify join is one MusicBrainz request per release at a
global ~1/sec. One day cost 612 seconds. A 30-day window is that arithmetic times thirty. It
is not worth widening for ~90 artists a day when 1,842 are sitting in `DEMOTED_SEEDS`.

### The only figure that decides where to spend

Sampled n=70 per source through a free artist-detail fetch, using the funnel's own
handle-keyed dedup test:

| source | already in master | in band | **new, in band, reachable** |
|---|---:|---:|---:|
| current 6 seeds | **52.9%** | 67.1% | **10.0%** |
| the 17 demoted seeds | **1.4%** | 67.1% | **41.4%** |

**4.1x.** Both sources sit in the listener band equally well (67.1% each) — the entire
difference is that one has been mined and the other has not. The demoted seeds were demoted
on *fit* (median listeners, country-confirmation rate); nothing recorded that they were also
**unmined**, which turns out to dominate. This is a sample, not a census; the interval on
n=70 at 41% is roughly ±12 points, and it does not come close to touching the conclusion.

### What is a realistic run size

The run below produced **525 contactable leads from 23 seeds** — **22.8 per seed**. So:

> seeds needed for 2,000 ≈ 2,000 ÷ 22.8 ≈ **88 playlists**

**2,000 leads needs roughly 88 seeds, not 6 — about fifteen times the current count.** And
88 is a *floor*, for two reasons that both push it up: the run was stopped at my budget line
rather than exhausted, and the already-in-master share rises as you mine, so the 88th seed
will convert worse than the first. A target larger than the pool does not fail loudly; it
stops early and looks like a crash, which is exactly what the operator saw.

**Where 88 seeds come from is already answered — by another round, running beside this one.**
BL-1166 measured `client.search(q, types=["playlist"])`: **214 queries → 3,296 playlists**,
free, with harvested artists **1.9% already-in-master**. That is the same diagnosis carried
one step further — if the ceiling is the *number of playlists*, then *finding* playlists is
the fix, and 88 stops being a stretch. Their run and mine shared a checkpoint tonight; the
numbers below are separated by seed provenance.

## 3. The wedge: two changes, and only one of them mattered

**The big inputs are not bios.** The longest real bio in `master_leads.csv` is **160
characters**. `enrich_links.py:232` feeds *scraped website text* to the same
`extract_emails`, capped at `MAX_PARSE_CHARS = 250_000` (`enrich_links.py:263`). That is the
wedge's real input, and it is why enrich_links was blamed first — it supplies the size;
`bio_parser` owns the quadratic pattern.

Measured on the 3.11 venv, worst case = an unbroken run of local-part characters:

| input | shipped (greedy) | possessive only | **possessive + lookbehind (shipped)** |
|---:|---:|---:|---:|
| 16,000 | 11.04 s | 2.07 s | **0.00045 s** |
| 64,000 | *(too slow to measure)* | 34.42 s | **0.0028 s** |
| **250,000** (the real cap) | **~2,622 s extrapolated (0.73 h)** | **589.67 s measured** | **0.0118 s measured** |
| fitted exponent *k* | **1.99** | **2.04** | **1.06** |

**Possessive quantifiers alone leave it quadratic (k=2.04).** They stop the engine
backtracking *into* a run, but it still retries the whole pattern at every offset *inside*
one, and each retry scans to the end. Nearly ten minutes at the real cap. The lookbehind
`(?<![A-Za-z0-9._%+\-])` is what changes the exponent: with possessive quantifiers every
start inside a run fails identically, so trying them is provably waste. **k drops to 1.06 and
250,000 chars costs 12 milliseconds** — a 50,000x improvement over the "obvious" fix.

### Extraction is unchanged, proved not argued

Differential over **50,145 real inputs** — every non-empty bio in `master_leads.csv` (50,130)
plus 15 hand-built obfuscation shapes, because the corpus is naturally thin on the `(at)` /
` dot ` forms the pattern exists for:

- **0 disagreements.** Identical lists, in identical order (order matters — callers take `[0]`).
- 2,768 emails across 2,752 bios, unchanged.
- The corpus pass also got **2.3x faster** (1.40s → 0.60s).

A **bounded-quantifier** variant (`{1,64}`) was measured and **rejected**: it disagreed on one
input, *fabricating a second address* out of an over-length local part. Possessive+lookbehind
is provably equivalent — the only token that can follow the local part and is itself built
from local-part characters is the literal `at`, and `_deobfuscate_email` rewrites `at`/`dot`
only when whitespace-delimited or bracketed, both of which stop a greedy run on their own.

Pinned by `tests/test_bio_parser_backtrack.py`, whose timing test is deliberately set at a
size **possessive-only would fail**, so dropping the lookbehind later is caught.

## 4. Hot reload — and why it is not `uvicorn --reload`

**`--reload` detects the change and never replaces the worker.** Measured four ways: with
`watchfiles` installed and without, and with a console and detached. Every run produced
exactly **one** `Started server process` line, a `Reloading...` line, and then nothing —
while the old worker kept serving old code. The cause is in
`uvicorn/supervisors/basereload.py::restart`:

```python
os.kill(self.process.pid, signal.CTRL_C_EVENT)   # a console-GROUP signal
self.process.join()                              # blocks forever if it missed
```

`CTRL_C_EVENT` only reaches a process group attached to a console, and the worker (spawned
via multiprocessing) is not its own group. The signal lands nowhere and `join()` never
returns — **the reloader is wedged, not merely ineffective**, so nothing after the first edit
is ever detected. *(I first suspected `DETACHED_PROCESS` from BL-1160 was the cause; the
isolation test disproved it — both console-attached and detached fail identically.)*

**Shipped instead:** a watcher in `tools/dashboard_launcher.py`, spawned detached *after* the
server is proven up, polling `*.py` under `dashboard/` and `clippershq/` and restarting the
server with `taskkill` — which needs no console. On by default; `DASHBOARD_NO_RELOAD=1` opts
out. Verified end to end on port 8096, **10/10**:

| verified | result |
|---|---|
| `dashboard/server.py` → restart | **PASS** |
| a route module (`paste_routes.py`) → restart | **PASS** |
| **an edit to `clippershq/all_bot_ready.py` changes what the RUNNING server returns** | **PASS** — `/api/files` rows `2970 → -4242`, no manual restart |
| reverting propagates too | **PASS** |
| `app.js` / `index.html` served byte-identical from disk | **PASS** |
| a *new* static file served with **no** restart | **PASS** |
| writing `runs.json` does **not** restart it (no boot loop) | **PASS** |
| killing the dashboard does **not** resurrect it | **PASS** |

Two rules make it safe, and both were earned:

- **`*.py` only.** The server writes `dashboard/static/runs.json` continuously *inside a
  watched tree*. A watcher noticing any file would restart forever — a boot loop that appears
  only once a run produces output, i.e. never in a test and always in front of the operator.
- **If the child dies unasked, the watcher exits.** That is what lets `stop()` stay exactly as
  it is; without it, STOP_DASHBOARD would be undone by a helpful resurrection.

A third rule came from a bug I shipped and caught: the watcher first treated **one** failed
probe as death and exited mid-restart, making everything after that edit invisible again. It
now requires three consecutive misses.

**Static files never needed reload** — `StaticFiles` reads them from disk per request, so an
`app.js` edit is live on the next refresh. **The freshness banner is untouched** and still
reads *"RESTART THE DASHBOARD — this page is showing old logic."* Reload replaces the
restart; it does not replace the warning that you need one.

`watchfiles` was installed through `clippershq/pipguard.py` (a bare `pip install` is blocked,
correctly); numpy is still 2.3.2.

## 5. Making the screen trustworthy

**The master row count was 2.26x too big.** `sum(1 for _ in fh) - 1` counts *newlines*, and
`bio` values legally contain them:

| | reported | real |
|---|---:|---:|
| `master_leads.csv` | **133,520** | **59,060** |

Fixed with `csv.reader` behind one accessor, `all_bot_ready.count_records()`, used at both
sites named in the brief (`staleness_of`, and the `master_rows` meta write) **and at a third
the brief did not name**: `run.py::_leads_now`, where being a *delta* hid it — both operands
were inflated, so the difference looked sane.

**The send list says how stale it is.** `output/ALL_BOT_READY.csv`: **2,970 records, built
2026-08-02 21:45:49**, against a master written **2026-08-06 15:46:59** → `stale: true`. The
loud banner already existed (BL-888) and fires correctly; what was wrong was the count it
quoted. *(It reports `age_days: 3` for a 3.75-day gap — an integer floor, not a bug, but it
is why the operator says "four days" and the screen says three.)*

**The leads counter is live.** It was not that the funnel wrote `leads` once — BL-1154 had
already put it on a clock. It was reading the **wrong file**: `_leads_now(master) - leads0`,
and a funnel appends to master **exactly once, after it finishes**. So the number ticked
reliably, at zero, for the entire run. It now counts from the run's own fsynced checkpoint,
using the *same predicate* `append_found_to_master` uses (has an email, not already in the
DB), so the live figure converges on the final one instead of jumping at the end. Verified
against the completed run's checkpoint: **32**, exactly the rows that reached master. Live on
the run above it climbed **0 → 1,072** while the old logic would have shown 0 for all 81 minutes.

`leads_source` (`"checkpoint"` / `"master-delta"`) now travels with it, so a reader can tell
*found nothing yet* from *cannot see it yet* — those were the same 0 on the page. It required
declaring the field in `run_status.py`, because `RunStatus.update()` silently drops unknown
keys: my first version set a field that vanished, which is the same class of bug as the one
it documents.
