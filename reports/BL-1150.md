## 2. The fix, in files nobody else holds

`clippershq/proc_identity.py` (new) and `spend_ledger.marker_state()`.

**Two checks, and the first is free and retroactive.**

1. **The boot rule.** A process cannot have started before the machine booted. Any marker
   whose start stamp predates the last boot is dead *with certainty* — no probing, no new
   field, and **it works on the six markers already on disk**. No migration, nothing to wait
   for.
2. **The creation-time rule**, for anything started since boot. `GetProcessTimes` says when
   the process behind a pid actually started; recording it makes the identity exact. Same pid
   **and** same creation time is the same process; same pid and a different creation time is a
   recycled slot. Compared at second resolution, because the value round-trips through JSON
   and float equality on a filetime is a coin flip.

`GetProcessTimes` is one syscall — no fork, no parsing. `tasklist` appears nowhere; INFRA-013
measured it at 2.77 s per call and 40.2 s in bulk.

**Three states, and the third is load-bearing.** `alive()` returns True / False / **None**.
None means *cannot tell* — no pid, no probe, a marker written before this existed. A caller
reading None as dead clears a live run off the panel; reading it as alive rebuilds the ghost.

`marker_state(marker)` returns `running` | `finished` | `died` | `unknown` with a sentence a
human can read:

> *"it says 'running' but started before this computer last booted, so it cannot still be
> running (pid 10120 now belongs to something else) — so it stopped without recording an
> ending"*

**FINISHED, DIED and NEVER-STARTED are three different facts** and this project has ~18
recorded instances of one rendering as another. A `running` marker beside a recycled pid is
precisely that: it renders DIED as RUNNING, for fifty-four hours. An **absent** marker stays
`unknown` and is never called died — that conflation is what BL-822 got wrong at a cost of a
$0.0060 double-count.

`write_marker` now also records `pid_created_at` and `boot_epoch`, lazily and never fatally: a
marker that cannot be written must not fail the run it describes, and the same goes for one
that cannot be fully identified.

**19 tests** in `tests/test_proc_identity.py`, green, including the real markers on disk as a
pinned regression.

## 3. Why the Spotify run died — the mechanism, confirmed; the instance, not

`clippershq/spotify_finder.py:1323` carries an **unguarded import inside a function**:

```python
from spotify_scraper import SpotifyClient
```

It runs when the funnel builds its client — within a minute of starting, which is exactly the
observed timing. And the module is not present in every interpreter on this machine. There are
**three**:

| interpreter | version | `spotify_scraper` |
|---|---|---|
| `python` | 3.11.9 | **YES** |
| `py` | 3.13.14 | **NO** |
| `.venv\Scripts\python.exe` *(new, BL-1147's)* | 3.11.9 | **YES** |

`dashboard/server.py` spawns funnels with **`sys.executable`** — the server's own interpreter.
So a dashboard started with `py` spawns every funnel under 3.13, and Spotify dies on
`ModuleNotFoundError: spotify_scraper` in under a minute, silently, because that spawn also
used `stdout=subprocess.DEVNULL`.

**What I cannot prove:** that *his* server was the 3.13 one. His run was pid 25212 and it is
gone; nothing on disk records which interpreter it used. Two servers running right now are
3.11 and the venv, both of which have the module. **BL-1149 is capturing the actual traceback
and that will settle it** — this is the confirmed mechanism and the leading candidate, not a
verdict on his instance. Naming it as the cause without their traceback would be the reasoning
the brief told me not to substitute for evidence.

**One thing worth their attention:** BL-1147's new `requirements.txt` states *"no version of it
is installed here — the spotify funnel therefore cannot run here today"* and deliberately omits
`spotify-scraper`. That is **false under 3.11**, where it is installed. Their `.venv` is safe
today only because it resolves the module anyway; a clean rebuild from that file would make the
Spotify funnel unrunnable by construction. `tests/test_env_audit.py` is currently red on
exactly this line.
