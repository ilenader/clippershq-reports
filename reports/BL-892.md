## 1. The pid field is removed, not repaired

It could not be repaired. `start()` recorded `os.getpid()`, which is correct when called as a **library** and worthless when called through the **CLI** — and every round files through the CLI, where the pid belongs to `claim.py` itself, a process that exits milliseconds later.

So every claim on disk carried a pid that was dead before anyone could read it. **That is not a weak signal, it is an inverted one:** a triager checking pids concludes the entire registry is abandoned. BL-880 checked BL-849's pid, found it dead, and nearly declared a live round dead on that basis — on a file it had itself written one round earlier.

**VERIFIED, the new behaviour:**

| | |
|---|---|
| filed via CLI | **no `pid` key at all**, plus `pid_means: "unknown -- filed from the CLI, whose own pid dies immediately. Use claim.py brief for staleness; pid cannot answer it."` |
| filed via the Python API | pid recorded — there it really is the round's process |
| `--pid N` | for a caller that genuinely knows its worker |
| `pid_alive(rec)` | **three-valued: True / False / None.** None when no pid was recorded. |

The three-valued return is the load-bearing part. A boolean would let a caller read *"not alive"* out of *"never recorded"* — which **is** the original bug, one layer up. The duplicate-id message stopped printing a pid too and now points at `brief`.

### The staleness signal

`brief` already existed and already used **file growth under the claim's own declared paths**, which is the real signal. Two fixes this round:

- **A round cannot be stale before it is old.** Added `age <= stale_after_min → never flag`. The previous `quiet > age * 0.75` guard was meant to catch this and collapses at age≈0, where any positive `quiet` beats it.
- The pre-existing test asserting *"an untouched claim is flagged after the threshold"* **passed with a zero-minute-old claim** — it encoded the false positive. It now advances `now` and asserts both halves: a young claim is never flagged; the same claim 200 minutes later is.

**VERIFIED:** MEMEBOT-041 no longer flagged. `test_claim.py`: **ALL PASS** (7 new checks).

## 2. The unparseable loss — two causes, neither of them the fence

Every failed sample in the log starts with ` ```json `, which makes the markdown fence the obvious suspect. **It is not the cause.** The runner's regex `\{.*\}` with `re.S` spans the fence perfectly well:

```
DECISIVE OFFLINE CHECKS
   bare JSON                      current=True  repaired=True
   FENCED, complete               current=True  repaired=True
   FENCED, truncated mid-beats    current=False repaired=True
```

**A caveat this round walked into and caught.** The offline pass over the 28 recorded failures classified **93% as truncated** — but the runner logs `raw[:400]`, so *every* sample was cut by the logger. **A diagnostic that truncates its evidence produces a diagnosis of truncation.** The live probe, recording `finish_reason` on full responses, gives the honest split.

### VERIFIED on 25 live calls, `finish_reason` recorded

| cause | signature | why it breaks the parser |
|---|---|---|
| **1. Truncation** | `finish_reason="length"` | Beat-heavy clips run past `max_tokens=2000`, so the LAST `}` belongs to a nested beat and `json.loads` gets a prefix that is valid syntax and invalid JSON. **BL-844 fixed exactly this once by raising 700 → 2000. It is back at 2000.** |
| **2. `MM:SS` timestamps** | `finish_reason="stop"` | The prompt asks for `t_start_s: <num>`; past about a minute the model answers **`"t_start_s": 1:24`**, which is not JSON. The response is **complete**, so it looks nothing like a truncation and no amount of brace-closing touches it. |

Real example of cause 2, a complete 3,970-character response:

```
: 1:24, "t_end_s": 1:27, "what": "The final segment shows images of ..."}\n ]\n}\n```
```

**Cause 2 also explains the pool dependence** (§3): `MM:SS` requires a clip over a minute, and the full pool carries longer clips than the speech pool.

### The fix, and the before/after

One parser now lives in `clippershq/clip_vision.py::parse_vision_json` — fence-strip → `MM:SS`→seconds → close open braces → drop a partial trailing element, cheapest-first and short-circuiting, so a healthy response takes the path it always did. Every runner carried its own copy of the broken two-liner; `bl864_ranked_label.py` and `bl867_deep_label.py` now delegate.

| | before | after |
|---|---:|---:|
| full-pool probe, parsed | **8 of 11 (73%)** | **11 of 11 (100%)** |
| **live pass, speech pool, n=24** | 12.5% failure (BL-880) | **0 of 24 failed** |
| **$/1,000 labelled, all-in** | **$2.12** | **$1.62** |

Both previously-unrecoverable failures now parse with **all five fields**, not a salvaged fragment.

**A repaired row is still a paid row.** This recovers answers already bought; it does not make a call cheaper. Raising `max_tokens` or capping the beat list would cut cause 1 *at the source* and costs money on every call — a separate decision needing its own measurement. **GAP: not measured.**

| **speech-labelled** | 14 | **0 (0%)** | 13 (**93%**) | **$1.59** |

BL-880 saw 12.5% vs 19% on one run each and called it unconfirmed. It holds, and the **mechanism is now known** rather than assumed: the full pool carries longer clips, longer clips produce more beats (truncation) and `MM:SS` timestamps (cause 2). Both failure modes are length-driven.

**This changes selection, not just cost.** The speech pool was already preferred because it converts half-answered clips into fully-answered ones (BL-872); it is *also* the cheaper pool per successful label, by roughly a third. The two arguments point the same way.

## Limits

- **The probes are 14 and 11 calls.** The pool dependence is confirmed in direction and mechanism on small n; the exact rates are not tight.
- **"0 of 24" is one pass on one pool.** It is a strong result against a 12.5% prior but it is not proof the loss is eliminated — a beat-heavy clip past `max_tokens` will still truncate, and repair recovers the row rather than preventing the waste.
- **Cause 1 is not fixed at the source.** `max_tokens` is still 2000 and the beat list is still unbounded. Repair makes truncation survivable, not absent, and BL-844 already raised this ceiling once.
- **The offline classifier said "93% truncated" and the live probe said 0% on the speech pool.** The offline number is an artefact of the runner's own 400-char failure log. That log should record the full response on failure; **it still truncates at 400 and I did not change it** — the runners' logging is BL-888's and BL-867's territory.
- **`parse_vision_json` is a repair layer and repairs can be wrong.** `MM:SS` → seconds assumes the model meant minutes:seconds and not something else; a dropped trailing element silently shortens a beat list. Rows repaired this way are indistinguishable from clean ones in the library. **GAP: no flag on a repaired row**, and there should be.
- **BL-849's claim is still open at 345+ minutes** declaring a file that no longer exists, and now correctly reads `** nothing written yet`. I did not clear another round's claim.
