## 6. The smallest change that lets you record a send

**Less than you would expect — the write path already works.** `outcomes.py` exists, is wired
into the Control Panel as menu **[o]**, and I ran it against the disposable copy:

```
record_outcome(master_copy, "<redacted>@gmail.com",
               {"date_sent": "2026-07-31", "sent_channel": "email"})
-> {'matched': 1, 'updated': 1, 'backup': '...20260731_120608.outcome.bak',
    'row_label': '@areqaep  Areq  <redacted>@gmail.com  [tiktok]', 'ambiguous': []}
```

It matched, wrote, took a timestamped backup, held the master filelock and left the other
outcome columns untouched. **The machinery is built and functional.**

**The gap is bulk.** `record_outcome` is one-lead-at-a-time: it locks, reads, rewrites and
fsyncs the whole 23 MB master per call. Recording a 1,620-row send means 1,620 full rewrites
driven by hand through a menu.

**Smallest change: a bulk marker that reads back an exported CSV and stamps every row in one
pass.** Concretely — take the export path plus a date and channel, resolve each address through
the existing `outcomes.match_indices`, apply `outcomes.apply_outcome` to each matched row, and
write master **once**. It reuses every validated piece (`normalize_outcome`, `_valid_date`, the
filelock, the backup, the atomic replace); the only new logic is "loop before writing instead
of writing inside the loop". Roughly one function plus a menu entry, no schema change — the
seven columns are already in master.

That single change is what converts sending from an untracked action into a measured one, and
it is also the precondition for the suppression list in §4: once `date_sent` is populated,
"already emailed" becomes a filter the exporters can apply.

## What I would fix before sending, in order

1. **Repoint or rebuild `LATEST_BOT_READY.csv`.** It holds 2 rows. If any automation is aimed
   at it, that is the live hazard. `ALL_BOT_READY.csv` (1,620) is the honest target — but only
   with a sender that keeps its own sent-state.
2. **Suppress the 20 dead-MX rows.** The data already exists in `scratch/bl763_mx.json`; the
   exporters simply never consult it. Cheapest real bounce reduction available.
3. **Add the bulk send-recorder (§6)** — without it nothing you learn from the first send is
   captured, and there is no "already emailed" filter to build on.
4. **Add `agency` / `role` / `days_since_post` columns to `ALL_BOT_READY.csv`.** All three are
   derivable offline at write time; today the file is missing the warnings entirely.
5. **Decide what the 888 stranded non-TikTok emails are worth.** Spotify's 741 is the biggest
   block of contactable leads in the system and no export can currently see it. Giving those
   funnels a verdict — or letting the exporters accept an empty one for funnels that don't
   produce verdicts — unblocks them. This is a design decision, not a bug fix.

## Limits

- **Bounce rate cannot be measured without sending.** §4's 1.2% is the *guaranteed* hard-bounce
  floor from confirmed-dead MX. The true rate is higher and unknowable from here.
- **The MX data is another round's artifact** (`scratch/bl763_mx.json`, 141 domains, produced by
  a concurrent agent). I used it as-is and did not re-resolve; DNS may have moved.
- **Agency counts are `role_policy.looks_agency()` output**, a heuristic, not a verified list.
  26 is that function's verdict on the exported rows, not a hand-checked count.
- **`send_list` was run against the live `config.json`** (read-only, no key printed) because
  campaign tag pools come from it. Campaign counts reflect today's config; changing tag pools
  changes the 1,398.
- **The 1,398 vs 1,409 reconciliation is approximate at the campaign level** — `send_list`
  re-scores independently rather than filtering the bot-ready output, so PANICBABY differs by 7
  from a naive intersection. The union figure of 1,623 is exact.
- **No live sending, no SMTP check, no paid call.** Deliverability beyond syntax and MX is
  untested.
