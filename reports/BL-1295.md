## 1. THE SPOTIFY FUNNEL WAS UNLABELLED, AND IT IS PARTIAL

### 1.1 Where it actually was

There is no per-funnel endpoint for **any** funnel — one generic trio serves all ten:
`POST /api/start` (`server.py:2484`), `GET /api/now` (`:563`), `POST /api/stop` (`:4257`),
with per-funnel form fields from `GET /api/funnel_params` (`:2332`). `spotify` is a registry
row in `run.py:64`, it is one of five funnels in `MARKER_FUNNELS` (`server.py:121`), it
writes a marker at `control.py:2437` and heartbeats from `run.py:425`.

So it was **better wired than funnels that emit no marker at all** — and invisible, because
nothing on the page carried the word *Spotify*. It was an `<option>` inside
`index.html:621`, a `<select>` that is **empty in the HTML** and filled by JavaScript after
the first `/api/now` lands. He was looking for a door.

**It is now a nav entry — "Spotify artists", under DO** — with its own target and cap
inputs, its nine live settings, an estimate, and its output paths.

### 1.2 It runs a PARTIAL funnel, and nothing said so

Both known claims **confirmed against current code**:

* `playlist_harvest` has **no shipping caller**. The only reference inside `clippershq/` is
  a *comment* at `control.py:2370`.
* `spotify_pool_file` is **absent from the live config**, so the pool block at
  `control.py:2379-2398` is skipped — and skipped **silently**. The "could not be read"
  warning at `control.py:2396` only fires when the key is PRESENT and broken. **An absent
  key produces no message at all.**

The cost is measurable. `scratch/bl1166_run.json` is a real `--target 2000` run:

| source | checked | leads |
|---|---|---|
| seeds + ListenBrainz | 2,456 | 293 |
| playlist_harvest | 1,834 | 230 |
| **total** | **4,290** | **523** |

Without the pool leg the funnel loses **42.8% of its supply** and drains near **~293 leads**.
**This was confirmed live during this round**: BL-1288's Spotify run finished while I was
working, with `status: completed`, `stop_reason: "source_drained"` — the predicted failure,
observed. The panel now states the ceiling *before* he presses go.

### 1.3 The gate is the clock, and it is quoted

MusicBrainz is capped at one request per `MIN_INTERVAL` (**1.1 s**) by a **reservation**
limiter (`musicbrainz.py:55`, `:212-221`) that hands slots out that far apart — so
`spotify_concurrency: 3` does **not** divide it.

MusicBrainz is called **4.65 times per delivered lead**, not once. The listener-band gates
return *before* the country gate, so 1,857 of 4,290 artists never cost a MusicBrainz second:

```
checked 4,290
  − low_listeners 1,106 − unknown 22 − too_many 721 − timeout 1 − NotFound 7
  = 2,433 reached the MusicBrainz gate        →  523 leads
cross-check: 374 non_target_country + 21 non_target_language + 2,038 passed = 2,433 ✓
```

Scaled, and served by `POST /api/start/estimate` with `funnel: "spotify"`:

| target | artists | MB requests | wall clock | paid resolves | USD |
|---|---|---|---|---|---|
| 350 | 2,871 | 1,628 | **37 minutes** | 594 | $0.59 |
| 2,000 | 16,405 | 9,304 | **3 h 30 m** | 3,392 | $3.39 |

**One correction to the brief:** `resolve_cache.json` has **no bearing on the wall clock**.
`musicbrainz.py` contains zero cache references — MB lookups are uncached within a run and
across runs. That cache is a negative cache of *paid handle resolves*, keyed
`platform:handle`. It protects dollars. **The clock is protected by nothing.**

The estimator reads `musicbrainz.MIN_INTERVAL` from the module rather than a literal, and
**refuses with `supported: False` if the measured run or the limiter cannot be read** — the
same honest refusal the endpoint already gives unsupported funnels.

`chartRows` — the helper that prints "Loading" and "No data in this range" — guarded only
two of the eight. The other six were `if (series && series.X && $('chY'))` with **no else**,
so a null or empty series drew nothing and said nothing.

**The window is not small.** `/api/series` takes **12.13 s cold** on this machine against

```

/api/spend?range=all             1.20s          0.48s

/api/library?range=all           0.09s          0.03s
```

### 2.2 The reason was computed, fetched, and dropped

`/api/series` returns `range_by[<series>]` for five charts — which **clock** each is bucketed
on (`spend time`, `lead added`, `render time`, `the clip's own post date`), `shown` of
`total`, `undated`, `same_as_all` — and `notes[<series>]` prose for two.

Counted in `app.js` **before** this round: `range_by` **0**, `computed_at` **0**,
`/api/series.notes` **0**. Searching the rendered page for the phrases confirmed it:
`"spend time": 0, "lead added": 0, "undated": 0, "shown": 0`.

**And the renderer already existed.** `clockNote()` (`app.js:120`) takes exactly the shape
`range_by` emits, and `putNote()` mounts it — five *panels* have used them since BL-1106.
**No chart had a mount.** This round added eight mounts and one state machine; it did not
invent a display.

After, on the same page:

> *Filtered on **spend time** — when the money was spent (spend.json, run.ts). Showing **7**
> of 33 in the last 7 days.*
>
> *Filtered on **the clip's own post date** … Showing 2,761 of 2,761 in all time. **17
> undated rows are excluded from any bounded range** — no date is not a recent date.*

That last sentence had never been on screen.

### 2.3 A SECOND defect, found while verifying the first

With the empty states in place, the charts stopped being blank — and started showing the
**previous range's bars under the new range's heading**. `_last` is the cross-poll cache and
nothing cleared it on a range change, so for the whole of `/api/series`' 12-second fetch the
leads chart still showed `2026-08-11 → 104`, which is the 7-day answer, while the heading
said All time.

That is **worse than blank**, because a stale picture reads as an answer. `choose()` now
drops `_last.series` and `_last.spend` and repaints into the honest loading state. Verified:
0.3 s after the click `_last.series === null` and `chSpend` has `svgs=0` with the loading
sentence; 12 s later it reads *Showing 7 of 33 in the last 7 days*.

### 2.4 The AST audit

`scratch/bl1295_fieldaudit.py` → `scratch/bl1295_fieldaudit.json`. **56 routes, 46 fetched
by the page, 489 field reads attributed, 33,555 JS tokens.**

* **READ BUT NEVER WRITTEN: 2.** `/api/dropmark/undo.detail` (app.js:3243) and
  `/api/harvest/estimate.detail` (app.js:4338). Both the same shape — the page prints the
  server's own refusal sentence on `!res.ok`, but **neither route raises `HTTPException`**,
  so `detail` can never arrive and the operator always gets the fallback string.
* **WRITTEN BUT NEVER READ: 196** across 43 endpoints. Worst: `/api/harvest/result` (16),
  `/api/renders` (14), `/api/run_breakdown` (13), `/api/start` (11), `/api/library` (10).

**Why an AST and not a grep**, in one fact: the historical `links`/`items` defect is caught,
and `"links"` **does** appear in the writer file — at `paste_batch.py:447`, in the *estimate*
payload, a different dict entirely. **A grep of the writer for the reader's key clears a
reader that is broken.** Scoping to the `state = {…}` literal inside `run()` does not.

No JS parser is available in the venv (`esprima` is absent), so the JS side is a
character-level lexer plus a worklist that propagates "this binding holds endpoint E"
through `.then` handlers, `.map`/`.forEach` callbacks and `_last.*` aliases. Its blind spots
are declared in the JSON: computed keys `d[name]`, nesting past two levels, non-syntactic
aliasing, `dropmark.html`'s inline fetches, template literals.

`tests/test_bl1295_dashboard_fields.py` (14 tests) ratchets all of it: every chart must have
a mount and go through the state machine, `range_by`/`notes` must be read, the range change
must drop the cache, `/api/series` must still emit both keys (checked by walking the AST),
the estimator must read the limiter rather than a literal, and the audit's
read-but-never-written count may not grow past the two known.
