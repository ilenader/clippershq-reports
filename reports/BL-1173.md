## 2. How the rows were selected — and the run_id question answered

```
date_added starts with 2026-08-06   AND   source_hashtag == 'spotify_finder'
```

`date_added` is the rule, **not** `run_id`. But the brief's premise about run_id needs
correcting, because the answer flips depending on which population you ask about:

| | rows with a run_id |
|---|---:|
| master, all time | 1,750 of 60,241 — **2.9%** |
| **today's rows** | **1,224 of 1,224 — 100%** |

So a strict run_id filter *would* have worked tonight and would have been the wrong habit: it
is 2.9% across master, and an export that depends on a stamp 97% of history lacks will one day
drop rows without saying so. `date_added` cannot miss an unstamped row. `source_hashtag` keeps
one `repost_finder` row out of a Spotify file — that is the whole reason today's 1,225 rows
become 1,224 here.

**`instagram_url` was empty on all 43 rows of the previous export, and that was not an export
bug.** Master's `instagram_url` column is empty on **all 1,224** of these rows — the pipeline
never stores it for Spotify leads. The handle *is* stored (99.9%), so the URL is **derived**
here, and the column is named `Instagram URL (derived)` so nobody mistakes it for something
the pipeline captured.

**Two fields master does not persist were recovered from the runs' own checkpoints.** Master
stores the country *value* but nothing about how it was established, and no Spotify artist id
at all; both live in the fsynced per-artist records under `scratch/resume/`. Joined back **by
handle for 1,223 rows and by name for 1** — 100% coverage, and every row carries the join key
it used so a disputed row can be weighed rather than trusted.

`Country confidence` reads `confirmed via <source>` where the run recorded one, and
*"unresolved — kept and flagged, never dropped"* for the 32.4% MusicBrainz could not settle.
That distinction matters: an unresolved country is not a bad lead, it is usually an instrumental
producer under a stage name.

## 6. What one more run costs and yields

Measured tonight, split by where the artists came from — the widened pool is the honest rate to
plan on:

| source | artists checked | contactable | rate |
|---|---:|---:|---:|
| **playlist_harvest (the widened pool)** | 4,994 | 1,183 | **23.7%** |

| related-artist expansion | 1,141 | 401 | **35.1%** |
| the old 6-seed pool (this afternoon) | 1,044 | 43 | **4.2%** |

**For 1,000 more contactable leads, at the widened pool's 23.7%:**

| | |
|---|---|
| artists to check | **4,219** |
| dollars | **$0.65** — and realistically **~$0.93**, see below |
| hours, MusicBrainz floor at 1 req/sec | **1.2 h** |
| hours at tonight's measured throughput (0.72 artists/s) | **1.6 h** |
| artists available in the 2,546 unwalked playlists | **~92,674** — 22x what is needed |

**The binding constraint is time, not money, and it is not close.** $0.65 buys 1,000 leads;
the same 1,000 leads cost an hour and a half of wall clock, because every artist needs one
MusicBrainz country lookup and MusicBrainz allows one request per second globally. No amount
of concurrency widens that.

> **Why $0.65 is probably $0.93.** The ledger recorded **2,202 vendor requests today
> (a receipt — HikerAPI's own `x-hiker-info` header) at $1.3212** (that dollar figure is the
> receipt count times a config price constant, an assumption, not an invoice). But BL-1165's
> run was killed with **958 requests unflushed**, and those never reached the ledger. Adding
> them back gives ~3,160 real requests, ~$0.000221 per artist, and **~$0.93 for 4,219
> artists**. Both figures are stated because the ledger understates and pretending otherwise
> would set a budget that quietly overruns.
