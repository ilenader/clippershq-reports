## PART 1 — the wallet backfill, answered for the owner directly

### Can the owner still SEE and COPY the full address to send a payout? YES.
The scheme is **AES-256-GCM** (`src/lib/wallet-crypto.ts:33-38`), which is **reversible encryption, not a hash**. `decryptField` (`:89`) turns the stored ciphertext back into the exact original address with the key. `readWalletFields` (`:139-147`) is applied at the two API read boundaries and returns `decryptField(walletAddressEnc) ?? walletAddress ?? null`, so the owner's admin payouts page (`admin/payouts/page.tsx:1323`) receives the **full plaintext address**, exactly as today, and can copy it to send. **Nothing is hashed. No address is ever lost to a one-way function.**

### Does any clipper-facing surface use an address? YES, and it still works.
A clipper sees **their own** address on their payout history (`payouts/page.tsx:629`, `PayoutsRedesign.tsx:158`), served by `payouts/mine/route.ts:45,60`, which also applies `readWalletFields`. After encryption they still see their own address read back, decrypted, unchanged. The address input fields elsewhere are for typing a fresh address into a new request, not reads of stored data, so they are unaffected.

### Does every reader handle BOTH encrypted and plaintext rows during the migration? YES.
There are exactly **two** endpoints that read a stored address, and both apply `readWalletFields`, which is encrypted-preferred with plaintext-fallback in a single expression, so a half-migrated table (some rows encrypted, some plaintext) is read correctly row by row:
- `payouts/route.ts:231-232` (owner admin GET)
- `payouts/mine/route.ts:31,45,60` (clipper own GET)

`payouts/referral-request/route.ts` references an address but is **write-only** (POST) and already dual-writes the encrypted columns (`encryptWalletFields` at `:144-149`); it never reads a stored address back. No reader anywhere bypasses `readWalletFields`. Confirmed by grepping every wallet reference in `src/`.

### Is the key backed up? UNKNOWN from here, and this is the one thing to confirm before any plaintext drop.
The key lives as `WALLET_ENC_KEY` in the Railway environment. It is **live in production** (81 rows are already encrypted, which is only possible with the key set). It is **not** in this audit's local `.env.local`, so I could not independently decrypt a single row to prove round-trip correctness here; that is an honest limitation of this read-only audit, not evidence of a problem. **Whether the key is backed up somewhere durable outside Railway is a fact only the owner can confirm, and it must be confirmed before the plaintext column is ever dropped.**

### If the key were lost TODAY, what happens? Nothing breaks, because plaintext still exists.
Because every one of the 133 rows **still holds its plaintext address**, `readWalletFields` would simply fall through to the plaintext column and every payout would remain sendable. **Key loss is only catastrophic AFTER the plaintext column is dropped.** That is precisely why the plaintext net must stay until the key is proven backed up. Today there is no exposure to key loss at all.

### What EXACTLY changes for a clipper? NOTHING.
Confirmed. A clipper types their address the same way, sees the same address read back, and is paid to the same address. The encryption is entirely server-side and invisible. There is no clipper-facing change of any kind.

## PART 2 — the backfill plan and its risk

### Live state, measured now
| Metric | Value |
|---|---|
| Total payout rows | 133 |
| Rows with plaintext address | 133 (every row) |
| Rows already encrypted | 81 |
| Rows still needing backfill | **52** |
| Rows missing BOTH columns | **0** (no row is un-recoverable) |
| In-flight payouts (REQUESTED / UNDER_REVIEW / APPROVED) | 5 |
| **In-flight rows needing backfill** | **0** |

### The single most reassuring fact: the backfill touches zero in-flight payouts.
All 5 in-flight payouts are **already encrypted**. Every one of the 52 rows to be backfilled is a **terminal** payout (PAID, VOIDED or REJECTED). BL-556 tracked 8 in-flight; there are now 5, all encrypted. **The backfill cannot affect a single payout the owner is about to send.**

### The operation
`scripts/migrations/F-SECURITY-WALLET-ENCRYPT-BACKFILL.ts` selects only rows where `walletAddressEnc IS NULL` (`:29-38`), and for each writes only the three `...Enc` columns (`:47-53`). It is:
- **Idempotent:** re-running only ever processes rows still lacking ciphertext.
- **Plaintext-safe:** it never reads-to-modify or writes the plaintext columns, so an original address cannot be altered.
- **Per-row isolated:** a `try/catch` per row (`:46,60`) means one bad row increments `failed` and the batch continues; a failed row simply keeps its plaintext and stays in the null set for a re-run.
- **Abort-on-no-key:** it exits before writing if `WALLET_ENC_KEY` is unset (`:24-27`), so it can never write nulls that look like success.

### Zero downtime, and half-failure behaviour
It is a background `UPDATE` of 52 terminal rows; no read path is interrupted (readers handle both forms), so it is **zero-downtime**. If it dies halfway, the rows it finished are encrypted, the rows it did not are still plaintext, and both are read correctly; re-running completes the rest. **No half-state is unsafe.**

### The one gap to close BEFORE any plaintext drop
The script's built-in verification only **counts remaining nulls** (`:71-75`). It does **not** prove that each encrypted value decrypts back to the original address. That per-row round-trip proof (`decryptField(walletAddressEnc) === walletAddress` for all 133 rows, zero mismatches) is the true gate before the plaintext column is ever dropped, and it is a separate read-only check that does not exist yet. **Dropping plaintext is not part of this backfill and must not be bundled with it.** The backfill itself is safe precisely because it leaves plaintext untouched; the irreversible step is the later column drop, which needs its own round with the key-backup and round-trip proof both done.

## PART 3 — the auto-reject shadow log

### The decisive finding: the shadow is not in the database.
BL-602 wired the shadow as a **`console.log('[RULES-SHADOW] ...')`** inside an `after()` callback (`clips/route.ts:906-928`). It **writes nothing to any table**. There is no rules-shadow table (the only `%shadow%` table is `scraper_shadow_samples`, an unrelated scraper feature), and `audit_logs` carries no RULES-SHADOW action. **The accumulated shadow decisions exist only in Railway's ephemeral console stream, which a read-only database audit cannot access.**

### And it cannot be reconstructed, because the inputs are not stored either.
The rule the shadow evaluates, `REQUIRED_CAPTION_TOKENS`, checks whether a literal token is present in the clip's caption. **The clips table stores no caption, no sound id and no provider metadata** (the only matching column is `rejectionReason`). So even retrospectively, I cannot recompute what the machine would have decided, because the caption it judged is gone. BL-602 said this itself: the rate is "measured GOING FORWARD from the logs" and "a retrospective rate is NOT computable here."

### What the database CAN tell us: the sample is tiny anyway.
The auto-reject rules exist on **6 campaigns**, and every one is `REQUIRED_CAPTION_TOKENS` (enforcement `auto_reject`); **zero** campaigns carry a `REQUIRED_SOUND` auto-reject rule, so the only rule that could ever fire live is "a required caption token is literally absent." Since BL-602 shipped on 2026-07-20 (4 days ago), those 6 campaigns received:

| Clips submitted | Human-approved | Human-rejected | Pending |
|---|---|---|---|
| **26** | 20 | 4 | 2 |

Twenty-six clips over four days. Even if every shadow line were in hand, **26 decisions cannot establish a false-rejection rate** against R-2's rejected 11.05 percent benchmark; you would need hundreds of evaluations before the rate is anything but noise.

### The measured false-rejection rate
**Unmeasurable today.** Not "low," not "high," genuinely **not computable from the database**, on two independent grounds: the decisions are log-only, and the inputs are not persisted. Any number I produced would be invented, which the safety rule forbids.

## PART 4 — is it safe to switch auto-reject on?

### NO. Not because it is proven dangerous, but because the evidence required to call it safe does not exist in a readable form, and there is no switch to throw yet.

Two hard blockers:
1. **The false-rejection rate is unmeasured** (PART 3). The owner's own bar was set by R-2 rejecting 11.05 percent as far too high, so enabling without a measured rate would repeat exactly the mistake that bar was meant to prevent.
2. **The named flag does not exist.** `RULES_AUTO_REJECT_LIVE` appears **nowhere in the codebase**, and `wouldReject` is never read to set a clip status anywhere. There is currently **no wiring at all** to turn the shadow into a live gate. Enabling is not a config change today; it is unbuilt.

### What the rate would mean in real people, at ~1,959 clips/month
Measured volume is **1,959 clips in the last 30 days** from 109 clippers (near the brief's ~2,300 estimate). If the true false-rejection rate were:
- **1 percent** → roughly **20 honest clippers wrongly auto-rejected every month.**
- **11.05 percent** (R-2's rejected level) → roughly **216 honest clippers wrongly rejected every month.**

Every one of those is a real person who did the work and was refused by a machine. That is why the rate must be measured, not assumed, before any switch exists to flip.

### The design itself is sound, which is worth stating
The rule is genuinely machine-certain in construction: `REQUIRED_CAPTION_TOKENS` returns `would_reject` **only** when the caption is present and the literal token is absent; a null or unfetchable caption returns `cannot_evaluate` and passes silently to a human (`campaign-rules.ts:8-19`). So the "only machine-certain violations auto-reject" rule is respected in the code. The problem is not the rule's logic; it is that **we have no visibility into how often it would fire wrongly**, because that visibility was built as a log line rather than a stored record.

### How long, and what is needed first
Before this can be judged at all, the shadow must become **measurable**: either persist each `[RULES-SHADOW]` decision (clip id, wouldReject, rule id, and the human's eventual status) to a small table, or export the Railway logs and join them to clip outcomes. Then accumulate enough evaluations on the 6 campaigns to be meaningful. At the current 26-clips-in-4-days pace on those campaigns, that is **weeks to months**, and faster only if more campaigns adopt an auto-reject caption rule. **Name the flag `RULES_AUTO_REJECT_LIVE` for the future round; do not create or set it now.**

## PART 5 — the verdict and ordered next steps

**(1) Wallet backfill: SAFE, and nothing changes for the owner or any clipper.** Reversible encryption, owner still sees and copies every full address, all 52 rows are terminal, plaintext stays as the net.

**(2) Auto-reject: NOT safe to enable, and not yet judgeable.** The shadow is log-only and its inputs are unstored, so the false-rejection rate is unmeasurable, and no switch-on wiring exists.

### Next steps, wallet (in order)
1. Owner confirms `WALLET_ENC_KEY` is backed up durably outside Railway. This is the gate for everything downstream.
2. Run the existing backfill on the 52 terminal rows (idempotent, plaintext untouched, zero in-flight risk).
3. Add and run a read-only round-trip proof: all 133 rows decrypt to their exact plaintext, zero mismatches.
4. Only after 1 through 3, in a separate round, drop the plaintext columns. This is the single irreversible step.

### Next steps, auto-reject (in order)
1. Make the shadow measurable: persist each decision plus the human's eventual verdict to a table (or export the logs and join to clip outcomes).
2. Let it accumulate a meaningful sample across the 6 (and any new) auto-reject campaigns.
3. Compute the real false-rejection rate: clips a human APPROVED that the machine would have REJECTED, divided by all it would have rejected.
4. Only if that rate is at or near zero, build the `RULES_AUTO_REJECT_LIVE` gate and enable it. Do not enable before the rate is known.

### What could not be measured, and why
- **The shadow false-rejection rate:** decisions are Railway-log-only and the evaluated captions are not stored; unmeasurable from the DB by construction.
- **Independent decryption round-trip of the 81 encrypted rows:** `WALLET_ENC_KEY` is not in this audit's environment, so I confirmed column presence and the read-path logic but did not decrypt a live row myself.
- **Whether the key is backed up:** an operational fact only the owner holds.
