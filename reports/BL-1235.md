### MX first, and what "first" had to mean

The brief says refresh MX before rebuilding, because suppression over an unprobed domain is
vacuous. A refresh had already run at **18:29:14** covering 1,654 domains, so the honest
question was not "re-probe everything" but "does the table cover the domains **these files
actually contain**". Measured against the three send files:

| file | domains | unprobed | coverage |
|---|---|---|---|
| `ALL_BOT_READY.csv` | 865 | 0 | 100.0% |
| `MEME_PAGES_BOT_READY.csv` | 51 | 1 | 98.0% |
| `TIKTOK_PAGES_BOT_READY.csv` | 26 | 0 | 100.0% |

"First" also has to account for domains that arrive **with** the new rows, which cannot be in
a table probed before them. So the primary was built in memory first, its 6 new addresses
read off, and their domains probed **before** anything was written:

```
probed now : 3     gmail.com -> ok-MX     venmo.com -> ok-MX     massdrop.com -> UNRESOLVED
retained from previous : 1648        entries after : 1650
```

`refresh_table` merges rather than replaces — verified at `mx_probe.py:303-309`, where
domains absent from the probe set keep their entry and are counted in
`_retained_from_previous`. Passing three domains did not cost the other 1,648.

**`massdrop.com` is left UNKNOWN, not dead, and that is deliberate.** It returned `rcode=2`
(SERVFAIL) on three consecutive probes across both resolvers. SERVFAIL is not NXDOMAIN — the
domain may well exist — so it stays **absent from the table**, which the table's own `_rule`
defines as UNKNOWN, and `meme_send_list` prints it and refuses to cut it:

```
! 1 domain(s) UNPROBED (resolver failed, not dead — never cut):
    massdrop.com                 drop
```

That is the 98.0% and it cannot honestly be raised.

### The order, and why it is the whole hazard

`ALL_BOT_READY.csv` is the **primary** and yields to nobody. `meme_send_list` drops anything
already in the primary (`meme_send_list.py:24-26`). `tiktok_send_list` drops anything in
**either** of the other two (`tiktok_send_list.py:42-43`). So a rebuild that runs the primary
**last** leaves the other two having computed their skips against a stale primary — and a row
lands in two files, breaking "no address in two files" in the direction nobody checks.

Built in this order: **MX → primary → meme → tiktok.**

| file | before | after |
|---|---|---|
| `ALL_BOT_READY.csv` | 3,972 | **3,978** (+6, **0 removed**) |
| `MEME_PAGES_BOT_READY.csv` | 158 | **158** |
| `TIKTOK_PAGES_BOT_READY.csv` | 116 | **116** |

**0 removed** matters on its own: this list is documented as one that can only grow, and a

## ITEM 3 — THE SIBLING HOLE IS REAL, AND `songs_backups` WAS THE ONLY REACHABLE ONE

BL-1231 already closed the specific case (`7145c8f`). This round did the audit the brief
asked for: **every** `PROTECTED` entry, checked for the same hole.

`protected_conflict` matches on exactly three relations — equality, candidate-inside-
protected, protected-inside-candidate — and **none of them holds between siblings**. So for
each of the 13 entries, `scratch/bl1235/protected_siblings.py` looks in the parent directory
for a name plainly about it (same stem, or stem plus `_backups` / `.bak` / `_old` / …) and
asks both `protected_conflict` and the GC itself.

**339 uncovered siblings exist. Exactly 0 of them are reachable by the garbage collector.**

That distinction is the finding, and it turns on what `survey()` actually does: it walks
**directories directly under `scratch/`, and nothing else** (`scratch_gc.py:230-241`). A file
under `scratch/` is never surveyed; anything outside `scratch/` is never surveyed. So:

| class | count | risk |
|---|---|---|
| uncovered **and** a directory under `scratch/` | **0** | would be one sweep from deletion |
| uncovered but outside the GC's scope | 339 | `PROTECTED` is not what is saving these |

`scratch/songs_backups` was uniquely exposed because it was the one thing that was *both* a
sibling of a protected path *and* a directory directly under `scratch/`. Nothing else in the
tree is in that position today.

**A separate finding, outside this brief's scope but worth the operator's attention.** The
337 out-of-scope siblings at the repo root — `master_leads.csv.*.bak`, `config.backup.*` —
total **8.40 GB**. No tool prunes them: `scratch_gc` cannot see them and nothing else claims
the job. They are correctly gitignored (`.gitignore:95`), and **0 are tracked**, so no lead
data is in git. Given the disk hit 100% on 2026-08-03, an unmanaged 8.4 GB of backups is
worth a retention decision rather than a discovery during the next outage.

## WHAT I GOT WRONG

**My first pass of the sibling audit reported "not-surveyed" for all 339 and I nearly shipped
it.** `GC.survey(hours)` returns **`(rows, claims)`** — a tuple — and each row is the tuple
`(name, bytes, age_h, verdict, why)`, not a dict and not an object with `.path`. My extractor
matched neither shape, silently built an empty index, and every path came back "not-surveyed".
That is a plausible-looking answer and a completely false one — the same failure shape as
BL-903's `rounds=0`. The corrected pass distinguishes OUT-OF-SCOPE from a real verdict.

A second, smaller one: the first version of that script called `survey()` once per sibling.
`survey()` walks the tree, so 339 siblings × 2 horizons ran past a ten-minute cap before
producing anything.

**I put 3,972 real addresses into the parent repo's history.** `output/` and
`exports_repost_accounts/*.csv|xlsx` are gitignored deliberately — they hold the send list
and the account export. My backup step copied four of them into `scratch/bl1235/backup/`,
and commit `bf6b5be` committed that directory wholesale, which defeats the ignore rule by
the side door. Caught by checking my own commit rather than by any guard: nothing in the
tree refuses a gitignored file re-entering under a different path. All four now live outside
the repo at `C:\ClippersHQ_renders\bl1235_backup\`, and `61f3969` removes them. **The blobs
remain in history**: the parent repo is private, and rewriting a shared history with six
rounds in flight would be far worse than the problem. Worth a guard — a commit that adds a
path whose *content* matches a gitignored file is a shape no check here currently sees.

**And a judgement I would make differently.** I declared `output/*` and `suppress_mx.json`
and then left roughly half an hour between finishing the rebuild and running the suite. A
claim is advisory; it did not stop the 21:03 rebuild and was never going to. Rebuilding a
derived file in a tree where another round is actively appending to its **source** is a race
by construction, and the useful lesson is not "claim harder" but **rebuild derived outputs
last, verify, and timestamp the verification** — which is why every partition figure in this
report carries the minute it was measured.
