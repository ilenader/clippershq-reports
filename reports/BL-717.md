## Blocker 1 — the hardware cannot run this model class. Measured, not assumed.

The box is an **AMD Ryzen 5 5500, 12 logical cores, 17.1 GB RAM, no GPU**
(`torch 2.11.0+cpu`, `cuda=False`), `torch.backends.cpu.get_cpu_capability()` → **AVX2**.

That last value is the whole finding. AVX2 means **no AVX-512, no AVX512-BF16, no AMX**, so
torch has no native half-precision kernel and emulates it in software. Measured on a
1024×1024 GEMM, 12 threads:

| dtype | time | throughput |
|---|---|---|
| **fp32** | 7.70 ms | **278.7 GFLOP/s** |
| fp16 | 3078.14 ms | **0.7 GFLOP/s** |
| bf16 | 2754.01 ms | **0.8 GFLOP/s** |

**Half precision is ~350× slower than fp32 on this CPU.** That inverts the usual trade and
closes both doors at once:

| dtype | weights (8.4B params) | fits in 17.1 GB? | decode bound | 60-token answer |
|---|---|---|---|---|
| fp32 | **33.6 GB** | **no** | 18.9 tok/s | ~3 s |
| bf16 | 16.8 GB | no (+2 GB runtime → 18.8 GB) | **0.05 tok/s** | **~24 min** |
| int8 | 8.4 GB | yes | requires bitsandbytes; CPU int8 support is poor and routes through the same emulated kernels | — |

**The precision that fits does not run; the precision that runs does not fit.** There is no
cell in that table where Qwen2-Audio-7B is usable here. The same applies to every model the
brief named — Audio Flamingo 3, MOSS-Audio and MU-LLaMA are all in the 7B class.

The decode bounds above are *optimistic*: pure GEMM, no attention, no KV cache, no audio
encoder, no memory-bandwidth stall. Real inference is slower than these numbers, not faster.

### One genuine positive: no install was needed, and none was risked

`transformers 5.12.1` **already ships `Qwen2AudioForConditionalGeneration` and
`Qwen2AudioProcessor`** — verified by attribute check. So the model class carried **zero ABI
risk**; the blocker is purely arithmetic.

Every candidate was still passed through `clippershq/pipguard.py --check-only` before
anything was contemplated:

| package | guard verdict |
|---|---|
| `qwen-omni-utils` | CLEAN — no protected package moves backwards |
| `accelerate` | CLEAN |
| `llama-cpp-python` | CLEAN |
| `mellow-audio` | not on PyPI — unresolvable, nothing installed |

**No numpy downgrade was ever proposed, so the stop-condition in the brief was never
triggered.** Nothing was installed regardless.

## Blocker 2 — no Gemini credential, and I did not create one

`config.json` searched for any gemini/google/vertex/palm/genai key: **none**. Environment
`GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `VERTEX_PROJECT`:
**all absent**.

The brief forbade creating an account or accepting terms, so Gemini is documented from
official sources only.

**What signing up requires** (reported, not performed): a Google account, then an API key
generated in Google AI Studio, which requires accepting the Gemini API Additional Terms of
Service. Paid use additionally requires enabling billing on a Google Cloud project. **None of
this was done and no terms were accepted.**

### Gemini audio capability, from the official docs

- **Three input paths**: inline data for requests **under 20 MB total**, the Files API for
  larger, and URI references to previously-uploaded files. It does **not** fetch an arbitrary
  third-party URL — audio must be uploaded, so the CDN link cannot be handed over directly.
- **Length**: up to **9.5 hours of audio per prompt** via the Files API.
- **Token rate**: **32 tokens per second of audio** (1 minute = 1,920 tokens).
- **Formats**: WAV, MP3, AIFF, AAC, OGG Vorbis, FLAC — the corpus is AAC-in-MP4, so a
  container remux would be needed, which `ffmpeg 8.0` (already present) does for free.
- Structured output with enums is supported, which is what would pin answers to the fixed
  vocabulary the brief specifies.

### Cost, computed from the published audio rate

Gemini 2.5 Flash: audio input **$1.00 / 1M tokens**, output **$2.50 / 1M tokens**. Assuming
~80 output tokens for four enum answers:

| clip length | audio tokens | cost/clip | **per 1,000 clips** |
|---|---|---|---|
| 30 s | 960 | $0.00116 | **$1.16** |
| 45 s | 1,440 | $0.00164 | **$1.64** |
| **58 s** (BL-690 measured median) | 1,856 | $0.00206 | **$2.06** |
| 60 s | 1,920 | $0.00212 | **$2.12** |

**~$2 per 1,000 clips at this corpus's real median length.** For comparison, the whole
BL-702 discovery round cost $0.0072. This is affordable but not free, and it is a recurring
per-clip cost rather than a one-off.

**Free-tier limits could not be pinned down.** The pricing page states audio input is "free
of charge" in the free tier for some models but publishes **no RPM or daily cap for audio**.
That number matters and is not documented where the brief assumed it would be.

## Blocker 3 — the "free ground truth" does not exist

The brief states: *"Where a clip has a declared track title and artist (23% do), you have
free ground truth."* Measured on `scratch/bl701/discovered.json` (n=351):

| set | count |
|---|---|
| clips with `music_info` title **and** artist | 80 |
| of those, clips carrying `progressive_download_url` | **0** |

**The sets are disjoint.** BL-702 already established the mechanism: `licensed_music` clips
carry no `original_sound_info`, so they expose no downloadable audio asset (0 of 82 there).
**The clips that tell you the track are exactly the clips whose audio you cannot fetch.**

So even with a working model, the declared-track grading path is unavailable without a paid
re-fetch to obtain `video_versions` URLs and demux with ffmpeg. No budget was given for that.
Grading would have fallen back entirely to the 15-clip hand-check.

Commercial use is mandatory per the brief.

| model | licence | commercial |

**MU-LLaMA's MIT covers the repository code, not the base weights** — it is built on LLaMA,
whose weights carry Meta's community licence with its own conditions. The MIT badge alone
should not be treated as clearance.

**Qwen2-Audio-7B-Instruct is the clean choice on licence.** It is simply unrunnable here.

## What would actually work on this box

The 7B class is out, but the constraint is size, and small audio-LMs exist. In fp32 — the
*fast* dtype on this CPU at 278 GFLOP/s — the arithmetic reverses:

| model | params | fp32 weights | fits? | decode bound (fp32) |
|---|---|---|---|---|
| **Mellow** (CMU) | **167 M** | **0.67 GB** | comfortably | ~830 tok/s |
| **LFM2.5-Audio-1.5B** (Liquid AI) | 1.5 B | 6.0 GB | yes | ~93 tok/s |
| Qwen2-Audio-7B | 8.4 B | 33.6 GB | **no** | — |

**Mellow is the strongest lead**: 167M parameters, purpose-built for audio-text reasoning,
and reported to match Qwen2-Audio on benchmarks with ~50× fewer parameters. It is **not on
PyPI** (`mellow-audio` does not resolve) and its Hugging Face page returned HTTP 401 to an
anonymous fetch, so its licence could not be confirmed this round — that is the first thing
to check before building on it.

**LFM2.5-Audio-1.5B ships llama.cpp-compatible GGUFs**, and `llama-cpp-python` **passed the
guard clean**. GGUF is the right shape for this box: quantised weights with hand-written
integer kernels that do not depend on AVX-512, sidestepping the emulation penalty entirely.

## Recommendation

Two routes, and they are not equivalent.

1. **Gemini, if a key is provided.** ~$2.06 per 1,000 clips, structured enum output, no
   hardware constraint, and a 40-clip pilot costs about **$0.08**. This is the fastest way to
   get the deciding number. It needs a Google account and terms acceptance — **the owner's
   decision, not an agent's.**
2. **Mellow or LFM2.5-Audio-1.5B GGUF locally**, $0 per call, but licence unconfirmed
   (Mellow) and neither benchmarked. The fp32/GGUF path is the only local shape this CPU
   runs well.

Do **not** budget for Qwen2-Audio, Audio Flamingo 3, MOSS-Audio or MU-LLaMA on this machine.
The first is licence-clean but 2× too large for RAM in its only fast dtype; the second is
non-commercial; the others are the same size class.

## Method

Hardware limits were measured with `torch` GEMM at 1024×1024 across three dtypes, 12
threads, after warm-up, repeated to confirm the fp16/bf16 result was not an artifact. Decode
bounds use 2 FLOPs per parameter per token, which is an upper bound on achievable speed.
Memory figures are weights-only plus a 2 GB runtime allowance. Every install candidate went
through `pipguard.py --check-only`; **nothing was installed**. No credential was read,
printed, or created; the key search reported only presence/absence.
