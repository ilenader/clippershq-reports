## 1. The destructive banner — resolved by adoption, not by obedience

**What it said**, printed above the logo before anything else:

> `⚠ master_leads.csv schema drift: header != current 70-column layout. Run 'python main.py --rewrite-master' to realign it.`

**What following it would have done:** master had 71 columns, `FULL_COLUMNS` had 70, and the single difference was **`twitch_login`, populated on 260 rows**. `migrate_master_csv` emits rows as `FULL_COLUMNS`, so realigning would have silently deleted every one of those values. **The app's own first instruction was the one that lost data.**

### Who writes it: nobody, and that is the whole story

`twitch_login` appears **nowhere in `clippershq/`** — all 60 modules. It appears only in `scratch/bl799_run.py`, whose own log reads `twitch_login 260/260` with real channel logins (`theprimeagen`, `supereyepatchwolf`, …). A scratch script wrote a column the schema never adopted.

### The decision: adopt it

A Twitch lead's login **is** its contact identity. The data is real and useful, so the schema catches up to the data rather than the data being destroyed to match the schema. `twitch_login` is now `FULL_COLUMNS[71]`, appended last so every existing column keeps its byte position.

**The drift is therefore gone at the source** — measured on the snapshot, `master_header_status` is now **`ok`** and `extra_master_columns` returns **`{}`**. The banner does not fire at all, because there is nothing left to warn about.

### And the banner can no longer recommend a destructive action

Rewritten to report *what* differs and *whether anything is at risk*, and to suggest the rewrite **only when the rewrite is safe**:

- unknown columns that hold data → *"these hold DATA and will be PRESERVED. Nothing to do."*
- unknown columns that are empty → *"'--rewrite-master' will tidy the header; it is optional and no data is at stake."*

### The guard, which is the part that actually protects you

The banner is advice; this is enforcement. `migrate_master_csv` now **refuses** when the file carries an unknown column containing data:

```
refusing to migrate — it has column(s) this version does not know that CONTAIN DATA:
bogus_col (5 rows). Migrating would delete them. Add the column(s) to
writer.FULL_COLUMNS to keep the values, or clear them deliberately first.
File left untouched.
```

**Proven** by injecting a populated unknown column into a copy: the migration refused and the file was byte-unchanged. This holds for any future column, not just `twitch_login` — a migration is a realignment, never a deletion.

## 2. The clip URL — diagnosed, and the fill rate is not what it looked like

**Why `clip_views` is ~52% of the export, measured on the pinned snapshot:**

| funnel | rows | with a real clip | fill |
|---|---:|---:|---:|
| hashtag crawl | 55,349 | 55,307 | **99.9%** |

| twitch_finder | 877 | 0 | **0%** |
| google_play | 212 | 0 | **0%** |
| email_finder | 60 | 0 | 0% |
| repost_finder | 41 | 0 | 0% |
| **master overall** | **58,324** | **55,307** | **94.8%** |

**This is not data loss. It is a lead-kind boundary.** A clipper has a video; a Spotify artist, a Twitch streamer and an app developer do not. The export's ~52% is the ratio of clipper to client rows in the *export*, not a gap in capture. **Half the file cannot carry that sentence because half the file has no clip to point at** — and no persistence work will change that. Client rows need a different first line, not a recovered URL.

**On the URL itself:** confirmed absent. The master header carries `tiktok_url`, `instagram_url`, `matched_video_date`, `matched_video_views` — and **no `video_id` and no clip permalink**, exactly as BL-753 found. Persisting it is a funnel-side change that only populates on a future run, and validating it requires a live run while two were already writing master. **Deferred rather than half-landed** — adding a column that nothing fills is the `dominant_lang` mistake this schema has already made once.

## 4. The dead export columns

**`role` — REMOVED.** Empty on all 2,949 exported rows, and **structurally unable to be otherwise**: `send_exclude_role` defaults on, so every role inbox is suppressed *before* it reaches the file and no survivor can carry the flag. The one configuration that could populate it (`send_exclude_role=false`) also writes `"role"` into `flags` — so the column was redundant in the only case it could ever be non-empty. An always-empty column in a send file advertises a signal that never arrives.

**`email_source` — NOT an export column.** It is not in `BOT_READY_COLUMNS` and never was; BL-819's finding is about the *master* cell being blank on rows whose address came from the bio. That is a capture defect in the funnel that resolved the address, not a dead knob in the export, and it is a different fix from this one. Recorded, not conflated.

The export contract is now 18 columns; the leading block stays byte-stable and a test locks both the new positions and the absence of `role`.
