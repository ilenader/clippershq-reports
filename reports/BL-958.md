## 3. The registry — and why an empty one needed a self-test

BL-947's `PENDING` works, but it lives inside `test_no_unchecked_stdout.py` and its staleness test asserts each entry *still contains an unchecked `.stdout` read*. A deferral about thread limits or a retirement rule cannot live there. That is why these three lived in prose and were rediscovered by hand every round.

`tests/test_deferrals.py` is the same two-test shape, generalised, with the domain check made per-entry by a **landed-marker**:

- `test_a_deferral_is_still_blocked` — RED the moment nobody holds the file
- `test_a_deferral_is_not_stale` — RED once the marker appears, i.e. somebody did the work

**`DEFERRALS` is empty, and that is the measured result** — there is nothing left to defer. But an empty dict makes both tests pass without evaluating anything, which is the vacuous-proof shape this project keeps correcting. So two `SelfTest` cases drive the same predicates over fixtures and assert they **fire**: held → quiet, free → fires; marker absent → quiet, marker present → fires.

### The marker mistake, pinned as a test

My first draft keyed the semaphore on **`_ABANDONED`** — the symbol BL-939 counted when it *measured* the gap (`_ABANDONED refs: 0/0/0/4`). The registry went red immediately and I nearly recorded three deferrals as outstanding.

`_ABANDONED` is the **bug's symptom**, not the **fix's signature**. BL-954 landed the adoption via `finder_common` imports, and `_ABANDONED` stayed at 0/0/0/1 — so a staleness check keyed on it would have reported the work outstanding *after it shipped*, forever. The rule is now a test:

```
symptom marker  (_ABANDONED)   -> landed() returns []        never notices the fix
fix signature   (finder_common)-> landed() returns 3 files   the fix IS detected
```

**A landed-marker must be something the fix introduces. The bug's traces often survive the fix; the fix's own symbol cannot precede it.**
