## TRAP 1 — `posted_at` is an EPOCH INTEGER, and an ISO filter returns a silent ZERO

This is the one that would have shipped.

I ran the clip hand-count twice by two independent routes. The second used string comparison
against an ISO cutoff, which is the obvious way to write a date filter:

```
posted_at >= 2026-07-27T18:28:11 (7d)  -> 0
posted_at >= 2026-07-04T18:28:11 (30d) -> 0
```

Zero. Not an error, not an exception — **zero, on 2,731 rows**, every one of which has a
perfectly good timestamp:

```
sample posted_at : 1608834988 (int), 1612022861 (int), 1616346132 (int) ...
type histogram   : Counter({'int': 2731})
span             : 2020-12-24  ->  2026-08-03
```

All 2,731 are epoch ints. `str(1608834988)[:19] >= "2026-07-27T18:28:11"` is `False` for every
row, forever. A "last 7 days" panel written this way reads **"0 clips"** and looks entirely
plausible next to a library of 2,728.

This is the silent-mismatch family this project has spent fifteen rounds removing, and it is
sitting directly in the path of the requested feature.

## TRAP 2 — every render is inside 3 days, so 7d / 30d / 60d / 90d / all are IDENTICAL

```
ok renders with finished_at : 365
earliest 2026-08-01   latest 2026-08-03
  2026-08-01    19
  2026-08-02   182
  2026-08-03   164
```

Every render-time panel returns **the same number in all five ranges**. That is not a bug in
the control — it is a fact about the data — but a control that shows 365 / 365 / 365 / 365 /
365 reads as broken, and the operator will reasonably conclude the filter does not work.

Per item 2's own logic, those panels have to **say** it: *"all 365 renders fall within 3 days;
every range shows the same number."* A range selector that silently repeats itself is the
same category of dishonesty as an unsliced number under a 7-day heading.

## TRAP 3 — the ledger, sixth occurrence of rows-versus-records

```
raw lines            : 985
distinct records     : 463    <- pending+ok per render, BY DESIGN
status ok            : 365
inflation if you count lines: 2.13x
```

Counting lines overstates renders by **2.13x**. Two further details that a status-split panel
will get wrong:

- **4 records carry `status: None`** — neither `ok` nor `failed`. They vanish from any
  ok/failed split without appearing anywhere, so the parts will not sum to the whole.
- **59 raw lines have no `render_id` and no `id`.** My independent scan keyed on that field
  and collapsed all 59 into one bucket, giving 460 records against the true 463. Any panel
  that groups by `render_id` inherits exactly this error.

Both methods agreed exactly on the numbers that matter: **ok = 365, failed = 94.**

## ITEM 4 — WHICH TIMESTAMP, PER PANEL

These are **five different clocks**. This is the table the feature needs.

| panel / series | source file | filters on | what that date MEANS |
|---|---|---|---|
| videos rendered | `memebot/runs.jsonl` | `record.finished_at` | when the render finished |
| renders failed | `memebot/runs.jsonl` | `record.finished_at` | when the render failed |
| `clips_by_month` | `clip_library/*.jsonl` | `clip.posted_at` **(epoch int)** | when the SOURCE CLIP was posted to Instagram — **not a render date** |
| `spend_by_day` | `spend.json` | `run.ts` | when money was spent |
| `leads_by_day`, by funnel | `master_leads.csv` | `row.date_added` | when the lead entered the file |
| `cost_per_lead_by_day` | derived | both of the two above | inherits **two** clocks |

**The mixing hazard is real and specific.** `clips_by_month` runs on the source clip's
Instagram post date; every other panel runs on our own activity. A single "last 7 days"
applied across the page compares *"clips posted by other people in the last week"* against
*"renders we made in the last week"* — two unrelated populations under one heading. That is
item 4's "wrong in a way that looks right", and it is not hypothetical here: `posted_at`
spans back to **2020**, while our render history spans **3 days**.

## Finding the live dashboard

The prompt asks how to find it. **Ten are listening right now** — one per concurrent round:

```
127.0.0.1:8777  8787  8791  8797  8807  8817  8827  8837  8847  8899
```

`serve()` defaults to 8787 and walks forward. To find *yours*, match the PID rather than
guessing the port:

```bash
netstat -ano -p tcp | grep -E "127.0.0.1:8[78][0-9][0-9]" | grep LISTENING
```

then match the PID column against the process that your round started. Guessing by port
number will land you on another round's server, which is how a screenshot pass photographs
someone else's page.
