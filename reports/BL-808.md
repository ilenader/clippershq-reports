## 3. Both contract failures fixed — from specification, not intuition

The brief was right to warn against guessing. I did not have to: **for both failures the specification survived inside the repository**, in the very files the checks guard.

### `cut_garbage_min_views` — behaviour provably unchanged

`config_defaults.py:29-32` is the spec, verbatim:

> *"Read at quality_gate.qualify_author's garbage-cut. The guard is `_gmin is not None`, so with no default the low-views limb never fired at all. **0 = no view-based cut, which is the behaviour that was actually shipping** — now stated instead of implied."*

The read is now `cfg.get("cut_garbage_min_views", 0)`. **This cannot change behaviour, and the reason is arithmetic:** the comparison is `_dmv < float(_gmin)`. With no default, `_gmin is None` and the limb never fires. With `0`, the test becomes `_dmv < 0` — false for every real view count, so the limb still never fires. Identical outcome, stated rather than implied.

### `crawl_require_email` — the read is deleted, not defaulted

Its own docstring records what the key does:

> *"BUG FIXED 2026-07-17: this used to write ONLY leads with a deliverable email… For a DM-only pipeline that threw away ~94% of what was paid for."*

The key's **only** possible effect was to restore that bug. Its default was already `False`, so removing the read changes nothing for any current caller — it removes a switch whose sole function was to reinstate a measured failure. The keep-filter is now unconditionally `verdict in ("EDITOR", "LIKELY")`, and the docstring no longer advertises the hatch.

**Neither fix was a guess, and I would have left them red if they had been.**
