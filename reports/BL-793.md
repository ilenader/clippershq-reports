## What shipped

**New module `clippershq/clip_media.py`** — a stdlib leaf (`html`, `re` only). Parses the manifest, exposes the identity, picks a rendition, retrieves the bytes. Every parsing path is unit-tested offline with no network and no key; both fetchers in `retrieve()` are injected.

**`clip_library.py`** gains six contract fields, appended:
`clip_pk`, `account_user_id`, `media_renditions`, `media_duration_s`, `subtitles_available`, `subtitle_text`.

**`clip_runner.clip_record()`** now parses the manifest on every walked clip. **This costs nothing** — the field is already in the payload that was paid for. It stays inside the runner's free-stages-only contract: presence of a subtitle track is read for free from the payload, while fetching the track's *text* is left to an opt-in call.

## 1. Identity stored, URL not

`clip_id` already arrives as `<pk>_<user_id>`; both halves are now stored explicitly so a consumer never has to know that encoding.

```json
{"clip_pk": "3950341933954853385", "account_user_id": "16171807964",
 "clip_id": "3950341933954853385_16171807964", "code": "DbSbw8itWoJ"}
```

Alongside it, a **URL-free inventory** of what exists — enough to decide whether a clip is worth a call *before* spending one:

```json
{"kind": "video", "id": "1594487612019504v", "mime": "video/mp4",
 "codecs": "vp09.00.21.08.00.01.01.01.00", "width": 360, "height": 640,
 "bandwidth": 355172, "fps": 30.0}
```

### The no-URL proof, run on a real serialised library line

Every `http` occurrence in a built record, and every expiring-token probe:

| probe | present in the stored line |
|---|---|
| `https://www.instagram.com/reel/<code>/` | **yes — the permalink, deliberate and durable** |
| any CDN url | **no** |
| `oe=` (the expiry parameter) | **no** |
| `fbcdn`, `bytestart`, `efg=`, `_nc_`, `&amp;`, `BaseURL` | **no** |
| `url` key anywhere in the rendition inventory | **no** |

Inventory keys are exactly `bandwidth, codecs, fps, height, id, kind, mime, width`. `rendition_inventory()` strips the URL that `parse_renditions()` carries for fetch-time use, and the module's self-test asserts `"http" not in json.dumps(inventory)`.

**Why it must not be stored:** measured expiry on a live manifest is **104.6 hours**. Twelve stored samples captured on 29 July all expire 3 August — the same ~105-hour window, for video *and* audio.

## 2. The trap, reproduced live

Not theory. On a real manifest fetched today:

```
escaped url contains '&amp;':        True
escaped fetch FAILED with:           HTTPError HTTP 403
naive param scan on the escaped url: amp;efg
```

Both halves fire exactly as BL-787 described. The parameter that absorbs the `amp;` here is `efg`, not `oe` — it is whichever parameter follows the first escaped ampersand, so anchoring a fix on the *name* would be fragile.

`html.unescape()` is therefore applied at the **top of every function in the module that touches the XML**, not at the call sites — a caller cannot forget it. It is idempotent, so double-unescaping is safe and no one has to track whether it already ran. The self-test locks both halves: that fetched URLs contain a bare `&oe=`, and that `url_expiry()` unescapes before parsing.

**Two real bugs the self-test caught while building this**, both worth recording:

- `clip_walk.paging_token()` returns a **`(token, more_available)` tuple**, not a string. Treating it as a string silently makes page 2 malformed.
- `clip_walk._is_media()` requires **`play_count`** to be present. A fixture without it is invisible to the walk.

## 4. Cost per retrieval — and a correction

| path | calls | cost |
|---|---:|---:|
| retrieve ONE specific clip (found on page 1) | 1 | **$0.0006** |
| the same call amortised over the 12 clips it returns | 1 / 12 | **$0.00005** |
| CDN media download | 0 | **free** |
| subtitle download | 0 | **free** |

**BL-787's $0.00005 is the amortised figure, not the marginal one.** A clips page returns 12 clips for one call, so *walking* costs $0.00005 per clip — but re-fetching one particular clip later costs a whole call, **$0.0006**, twelve times more. Both numbers are right; they answer different questions, and a bot that re-fetches clips one at a time should budget the larger one.

**There is no fetch-one-media-by-pk endpoint wired in `ig_client`.** The only clip source is `/gql/user/clips`, newest-first by account, so a recent clip is found on page 1 and an older one costs a call per page. `retrieve(max_pages=...)` bounds that explicitly rather than letting a deep clip quietly cost ten calls.

## 5. The subtitle premise does not survive contact

This was to be a 500× speedup on the stage that dominates the walk. It is not.

### It is present but not populated — the trap this repo already documented once

Measured across **4 accounts, 48 clips**:

| field | key present | actually populated |
|---|---:|---:|
| `video_dash_manifest` | 48/48 | **47/48 (97.9%)** |
| `video_subtitles_uri` | **48/48** | **4/48 (8.3%)** |

Per account: `theelitescense` 0/12 · `darknightjoe` 0/12 · `cinemaelevate` 3/12 · `movies.avengers` 1/12.

This is exactly **TRAP 2 from `clip_library.py`'s own docstring** — *"PRESENT != POPULATED"* — recorded there for the engagement panel and now recurring for subtitles. A field-presence sweep reports 12/12 and means nothing about whether a value is there.

### Worse: where it exists, it is the wrong text

Fetched a real track from `cinemaelevate` (`instagram.com/reel/DaDKVIBpKm6/`, locale `en_US`) and ran OCR on frames from the same clip:

| source | content |
|---|---|
| **subtitle track** | **7 characters — "Up. On."** |
| **OCR (8 frames)** | "can lift upto 2000kg … Lift upto 50 times of their own body weight … Lift over 850 times it's body weight" |

| metric | value |
|---|---:|
| subtitle words >3 chars | **0** |
| OCR words >3 chars | 16 |
| **shared words** | **0** |
| **overlap** | **0%** |

**The track is an auto-generated transcript of the spoken audio, not the burned-in overlay text.** On a text-overlay meme page — precisely the content this library is built from — the speech is near-silent while the overlay carries the entire message. The two do not substitute for one another; on this clip they do not intersect at all.

Timing, for completeness: subtitle fetch 0.66s vs OCR 6.3s for 8 frames — about **10×**, not 500×, and on 8% of clips, for text that answers a different question.

**Recommendation: keep capturing it — it is free — but do not plan an OCR bypass around it.** `subtitles_available` is now stored so the real rate is measurable going forward instead of assumed. `subtitle_text` exists and is populated only when a caller opts in.

## Limits

- **One clip retrieved end to end**, not a batch. The path is proven, not load-tested.
- **The subtitle finding rests on 48 clips across 4 accounts**, and the text comparison on **one** clip. The 8.3% populated rate is solid; the "speech not overlay" conclusion is one well-documented instance and should be re-checked on the next populated track before it is treated as universal.
- **OCR measured at 0.8s/frame, 6.3s for 8 frames**, against the ~16s/clip the brief cites. The gap is frame count and configuration, not a contradiction — I did not reproduce the 16s figure's setup.
- **`subtitle_text` is wired but never populated by the walk.** It requires an explicit `fetch_subtitles()` call, deliberately, to keep the runner's free-stages-only contract intact.
- **No `by-pk` endpoint exists**, so single-clip retrieval is bounded by paging. `max_pages` defaults to 1: a clip that has fallen off page 1 returns a clean "not found" rather than silently spending calls.
- **AV1 appeared where BL-787 saw VP9.** Rendition selection is by bandwidth and height, so this does not matter today, but a consumer assuming VP9 will be wrong.
