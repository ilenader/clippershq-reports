# BL-684 — is the posting-freshness rule enforced at all?

## THE RULE EXISTS AND IS REAL CODE, but it is only alive on TWO of the three platforms. TikTok and YouTube are enforced and working. INSTAGRAM HAS HAD NO FRESHNESS CHECK AT ALL SINCE 2026-07-22, because the freshness fetch is deliberately routed into the Apify chain that died that day, so it returns nothing, and the code then treats "no timestamp" as a transient failure and ACCEPTS the clip. This is not a permission bug: the owner's account bypasses nothing, and the batch path is not weaker than the single path on freshness. Measured live this round, an ORDINARY clipper submitted six Instagram clips today that were posted between 4.5 and 5.5 hours earlier, and every one was accepted.

## PART 0 — the rule exists, and here is exactly where

**It is enforced at `src/lib/clipper-submit-core.ts:150`**, inside RULE 2, on the shared clipper core that BOTH submit paths call:

```ts
// RULE 2 — freshness (30-min window). Lenient on transient provider failure.
const result = await fetchClipFreshnessWithRetry(clipUrl, platform);       // :138
if (!result.stats) { ... transient = true; }                               // :139-145  ACCEPTS
else {
  if (stats.createdAt) {
    const diffMs = Date.now() - new Date(stats.createdAt).getTime();       // :149
    if (diffMs > MAX_CLIP_AGE_MS) return fail(`This ... clip was posted more than
      ${MAX_CLIP_AGE_LABEL} ago and cannot be submitted.`);                // :150-152  REFUSES
  } else if (platform === "instagram" || platform === "youtube") {
    transient = true;                                                      // :154-156  ACCEPTS
  }
}
```

`MAX_CLIP_AGE_MS = 30 * 60 * 1000` and `MAX_CLIP_AGE_LABEL = "30 minutes"` live in `src/lib/clip-config.ts`. **So the answer to "does the rule exist in code" is YES, unambiguously.** The marketplace post path enforces the same constant separately at `src/app/api/marketplace/submissions/[id]/post/route.ts:89` and `:121`.

**One dead import worth noting:** `src/app/api/clips/route.ts:21` imports `MAX_CLIP_AGE_MS` and `MAX_CLIP_AGE_LABEL` and never uses either (the only match in that file is the import line). The single route delegates entirely to the core, so this is cosmetic, but it makes the route look like it enforces something it does not.

### The leading hypothesis was HALF right, and the half that is wrong matters more

**Confirmed: the post timestamp is essentially never STORED.** Live count:

| clips (not deleted) | with `Clip.postedAt` | without | percent with |
| --- | --- | --- | --- |
| 4349 | 100 | 4249 | **2.30%** |

BL-662's finding holds. The clipper core's `clip.create` (`clipper-submit-core.ts:182-186`) writes no `postedAt` at all, so an organic clipper submission NEVER records when the video was posted. The 100 that do have one come from the owner-submit path (`owner-submit-core.ts`, 20 references to `postedAt`), which backdates it deliberately.

**But refuted: a missing STORED timestamp does not make enforcement impossible.** The check at `:149` reads the timestamp from the LIVE provider response at submit time (`stats.createdAt`), not from the database. It never needed `Clip.postedAt`. **So the storage gap explains why nothing can be AUDITED after the fact; it does not explain why the rule fails.** The real cause is per-platform and is in PART 4.

### Yes, it is also unenforced PROSE, in most campaigns

Of 13 non-archived campaigns, **9 carry a 30-minute rule in `requirements` prose** and **8 phrase it as a window**. Redacted, the literal lines are:

Submit the video link within 30 minutes of posting.

**Zero campaigns configure it as a machine rule:** `rulesJson ILIKE '%POSTING_WINDOW%'` matches **0 of 13**, even though all 13 have a `rulesJson`. And `src/lib/campaign-rules.ts` declares the type but deliberately does not evaluate it, on an assumption that is now only two thirds true:

**The reviewer note therefore stays silent about posting window on every platform, on the stated ground that submit already handles it. For Instagram, submit does not.**

## PART 4 — what enforcement would take, per platform

### Where the timestamp comes from today

`fetchClipFreshnessWithRetry` (`src/lib/apify.ts:2501`) is the only source RULE 2 reads.

| platform | source at submit today | timestamp | status |
| --- | --- | --- | --- |
| **YouTube** | `getYouTubeVideoDetails` → `publishedAt` (`apify.ts:2522-2540`) | **PRESENT**, free Data API, no Apify | **ENFORCED** |
| **TikTok** | `fetchClipStats` → LamaTok, which maps `createTime` to ISO at `lamatok.ts:300-306` | **PRESENT** | **ENFORCED**, proven above |
| **Instagram** | `fetchClipStats(url, { skipHikerOverlay: true })` (`apify.ts:2566`) → **Apify only** | **ABSENT since 2026-07-22** | **NOT ENFORCED** |

### The Instagram cause, and the irony in it

`skipHikerOverlay: true` was added by **BL-137 specifically so the freshness gate WOULD be enforced**. Its comment at `apify.ts:2554-2560` says so: Hiker returns `createdAt: null`, which would make every hit look transient, so the flag routes Instagram to Apify *"→ freshness gate enforced"*. **When Apify died on 2026-07-22 that reasoning inverted: the flag that existed to guarantee enforcement now guarantees the opposite.** Apify returns nothing, `result.stats` is null, and `clipper-submit-core.ts:139-145` sets `transient = true` and accepts.

**And the premise is no longer true either.** HikerAPI's v2 media response **does** carry the post time: my probe read `taken_at` as a unix integer on all six posts, HTTP 200 every time. It is the parser that discards it. `src/lib/scraper-providers/hikerapi.ts:823` and `:884` hardcode `createdAt: null`, with a comment at `:649-651` asserting *"Hiker doesn't [expose it]"*. **That comment is demonstrably wrong, and it is the same class of error BL-670 made about the cover image and BL-673 corrected: the field is in `rawBody`, and only the summary parser drops it.**

### So enforcement per platform requires

* **YouTube: nothing.** Already works, free.
* **TikTok: nothing.** Already works.
* **Instagram: one field.** Map `taken_at` into `HikerResult.createdAt` at `hikerapi.ts:823` and `:884`, then stop forcing `skipHikerOverlay: true` for Instagram at `apify.ts:2566`. **No new vendor call is needed if this rides the Hiker call the path would make anyway; the marginal cost is at most one HikerAPI media call at about $0.001 per submission.** No storage change, no schema change.

### The risks, honestly, because this would REFUSE real clippers

* **Missing timestamp must FAIL OPEN.** This is non-negotiable. Today's code already does the right thing at `:139-145` and `:154-156`; any change must preserve it. A clipper refused because a provider was slow is far worse than a late clip accepted, and BL-664's human overturn baseline of **0.77%** is the bar an automated refusal has to beat.
* **One asymmetry to fix while you are there.** At `:154-156` the "timestamp absent" leniency covers only `instagram` and `youtube`. If a TikTok fetch ever succeeds with a null `createdAt`, **neither branch fires**: no age check and no `transient` flag, so the clip is accepted silently and the rate-limit slot is not refunded. Harmless today because LamaTok always supplies `createTime`, latent if that ever changes.
* **Clock skew and timezone.** The comparison at `:149` is `Date.now()` against a provider ISO string, both in UTC, so it is correct in principle. The exposure is server clock drift: a server five minutes fast turns a 26-minute-old clip into a refusal. A tolerance margin, refusing only past roughly 35 minutes while telling the clipper 30, absorbs that. This round explicitly avoided the trap by casting every database timestamp to `::text` and anchoring on DB `now()`; a local `+02:00` offset has faked a discrepancy on this platform before.
* **Provider lag and coarse timestamps.** Instagram `taken_at` is whole seconds and appeared immediately on posts minutes old, so granularity is not a problem here. The real risk is a provider that has not yet indexed a brand-new post: that returns not-found, which is the fail-open path, not a refusal. **Verify that before shipping, because a brand-new post is exactly the case the rule is meant to allow.**
* **The clipper on a slow connection.** A 30-minute window is generous against upload and copy-paste latency, but a hard refusal has no appeal route today. That argues for the recommendation below.

## PART 5 — verdict and ranked fix spec

### ONE LINE

**The freshness rule is real code at `clipper-submit-core.ts:150` and is enforced on TikTok and YouTube but has been completely dead on Instagram since 2026-07-22 because its only timestamp source was Apify, so the owner's submissions were not a bypass of any kind but the same unenforced behaviour every Instagram clipper has had for a week.**

### Ranked

**1. Restore Instagram's timestamp. `hikerapi.ts:823` and `:884`, then `apify.ts:2566`.** Map `taken_at` (and its `taken_at_timestamp` sibling) into `createdAt`, then drop the Instagram `skipHikerOverlay` forcing so the freshness path can see it. **Must be proven:** a live Instagram submission older than 30 minutes is refused; one under 30 minutes is accepted; a deleted or unresolvable post still FAILS OPEN and is accepted with `transient` set; TikTok and YouTube results are unchanged; the 6 money files and `tracking.ts` stay byte-identical by blob OID. **Rollback:** revert the commit; behaviour returns to accepting everything, which is today's state, so the rollback is strictly no worse than now. **This one change restores the rule the owner thought he had.**

**2. Decide the enforcement mode, and this is the owner's call, not the code's.** Given the platform's standing rule that only machine-certain violations may auto-reject:

* **HARD REFUSE is defensible here and I recommend it, narrowly.** A post timestamp read directly from the platform's own API is about as machine-certain as this platform ever gets: it is not a judgement call, not OCR, not a caption token, and it is the same class of certainty that already refuses TikTok and YouTube clips today without complaint. Refusing Instagram too restores consistency rather than creating a new risk. **But only with all three of: fail open on any missing or unresolvable timestamp, a tolerance margin above the advertised 30 minutes to absorb clock skew, and the refusal message naming the measured age so the clipper can see why.**
* **FLAG-FOR-REVIEWER is the safer half-step if the owner wants evidence first.** Set `POSTING_WINDOW` to produce a real verdict in `campaign-rules.ts:312-315` instead of `cannot_evaluate`, and let the reviewer note carry it. That collects a real false-positive rate before anything is refused, which is exactly the discipline BL-659 and BL-666 established. **Cost: the window stays unenforced on Instagram while it runs.**
* **Not recommended: enforcing via `rulesJson`.** Zero of 13 campaigns configure `POSTING_WINDOW`, and this is a platform-wide rule in 9 of 13 requirement texts, so it belongs at submit, not per campaign.

**3. Give the batch path the shadow evaluation the single path has.** `batch/route.ts` has 0 references against 5 in `clips/route.ts`, so batched clips get no reviewer note and record no `postedAt`. Fixing this is what would make freshness auditable after the fact instead of only measurable by paying a provider, as this round had to.

**4. Close the TikTok null-timestamp gap at `clipper-submit-core.ts:154`.** Add `tiktok` to the leniency branch so a null timestamp is explicitly transient on every platform rather than silently skipped on one. Latent today, one line.

**5. Remove the unused import at `clips/route.ts:21`.** Cosmetic only, and worth doing purely so the route stops looking like it enforces a rule it delegates.

**Not recommended: storing `Clip.postedAt` on the clipper path as the fix.** It would make future audits possible, which is genuinely useful, but it does nothing for enforcement, since RULE 2 reads the live provider response and never touches the column. Do it for observability if you want it, not as the answer to this question.
