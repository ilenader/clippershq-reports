# BL-684: The sound library is a separate artifact — enumeration is NO, the Spotify bridge is 65% (80% with a retry), and a 200 OK can carry a zero that isn't zero

**Date:** 2026-07-29
**Builds on:** [BL-678](BL-678.md) (routing rule, count passthrough) and [BL-680](BL-680.md) (schema correction, original-sounds majority).
**Spend:** **$0.0252** of a $0.03 budget — 42 billed calls at $0.0006 (20 + 20 + 2), metered as `probe:soundlib`, `probe:soundlib2`, `probe:soundlib_retest`; ledger `total_spent_usd` 2.8792 → 2.9044, a delta of exactly $0.0252. One further track (ABBA) was reused from BL-678's saved payload at $0.
**Scope:** design + probe only. No pipeline code changed. All 23 payloads saved to `_probe_samples/soundlib_tracks/` so none of this needs buying twice.

---

## The reframe this report acts on

Two-thirds of clips are `original_sounds` with no title, artist or hook; all track metadata lives on the licensed third. So the **clip library and the sound library are separate artifacts**, joined at edit time. This report designs the sound side and measures the three things that decide whether it is buildable.

---

## Q1 — Can `/v2/track/by/id` enumerate trending sounds? **No.**

**Evidence, and a token gotcha that cost a call to find.**

The first pagination attempt passed `page_id = response.paging_info.max_id`. It returned **the same 12 reels** (12/12 overlapping pks) with `more_available: true` — a silent no-op that looks exactly like a successful page turn. The provider wants the **envelope-level `next_page_id`**, which is a different token living outside `response`.

With the correct token:

| metric | page 1 → page 2 |
|---|---|
| items | 12 → 12 |
| overlapping pks | **0** |
| new pks | **12** |
| distinct `audio_cluster_id` on page 2 | **1** — and it is the id queried |
| distinct `audio_asset_id` on page 2 | 1 |
| distinct creators on page 2 | 11 |
| `more_available` | true |

**So paging yields more CLIPS of the same sound, never a new sound.** A scan of every audio-ish key in both saved responses confirms it: the licensed page references exactly one `audio_cluster_id` (the queried one) and no other, and carries no "related sounds" pointer anywhere in its 15 top-level keys.

**Conclusion:** the endpoint is a **clip/creator discovery surface for a known sound**, not a crawl frontier over sounds. Sound discovery has to come from crawling clips — each clip names its own audio — and the track endpoint is what you call *after* you have an id.

One asymmetry worth recording: on the **original-sound** page, the 12 items share one `best_audio_cluster_id` but carry **11 distinct `audio_asset_id`** and 12 distinct `music_canonical_id`. An original-sound "cluster" is a *family* of derived audio assets, not one file. Its `clips_count` therefore aggregates reuses across assets — which is what you want for a popularity signal, but it is not "this exact audio file".

## Q3 — Spotify bridge: 65% per pass, 80% across two, and it is not stable

20 licensed `audio_cluster_id`s from the corpus, resolved twice (the second pass also fixed a field-path bug of mine, below).

| pass | `spotify_track_id` present |
|---|---|
| pass 1 | 13/20 (65%) |
| pass 2 | 13/20 (65%) |
| **union** | **16/20 (80%)** |
| identical id where both passes had one | 10/10 |
| **flips** (present↔absent between identical calls) | **6/20** |

The headline number is stable at 65%, **but the membership is not** — six ids flipped between two identical calls minutes apart. Where both passes returned an id, the id was always the same (10/10), so the field is never *wrong*, only sometimes *missing*.

**Consequences for the schema:**
- `spotify_track_id` is a property of the **call**, not of the track. Store it as **last-known-good with a `_last_seen` timestamp**; a null must never overwrite a previously-good id.
- A single retry on null buys roughly **+15 percentage points for $0.0006**.
- Where it exists it is an **exact** join — no namesake risk, which matters because name-matching measured **53% wrong** in an earlier round. 80% exact-join coverage of the licensed third beats a fuzzy match on 100% of it.

## The new trap: `is_music_page_restricted` — a 200 OK carrying a plausible zero

Two ids returned **241,254** and **637,435** clips on pass 1, then on pass 2 *and* a confirming retest returned this:

```
status: "ok"          status_code: "200"        is_music_page_restricted: true
media_count: {"clips_count": 0, "photos_count": 0}
items: []             metadata.music_info: null
formatted_media_count: ""     paging_info: {"more_available": false}
+ music_page_restricted_context      (present ONLY on restricted responses)
- available_tabs, spotify_track_metadata   (absent)
```

This is the **same failure class BL-678 identified — present, plausible, wrong — with a different cause.** It is not a missing count; it is a successful call reporting zero for a track that had 637,435 reels ten minutes earlier. Restriction is **dynamic**: the same id served full data on the earlier pass.

Note `formatted_media_count` is `""` here — an empty string that a regex would happily coerce to 0. That is a second, independent reason never to parse the display strings.

**Rule:** `is_music_page_restricted == true` → the entire read is **UNKNOWN**. Do not persist the count, do not overwrite a known title with null, and **do not record a velocity point** — a restricted read looks like a −637,435 collapse and would make any "fastest falling sound" alert fire on rights restrictions instead of reality.

## Q5 — The routing rule, confirmed and made structural

```
audio_type == "licensed_music"  -> track_id = music_info.music_asset_info.audio_cluster_id
audio_type == "original_sounds" -> track_id = audio_ranking_info.best_audio_cluster_id
anything else                   -> UNROUTABLE — refuse to build a record
```

`track_id_source` is a **mandatory field on every sound record**, written by the router, not inferred later.

**The rule is never implemented by comparing the two ids**, and this round supplies the sharpest evidence yet for why. Divergence rate by dataset:

| dataset | licensed clips where `best` ≠ `asset` |
|---|---|
| pop corpus (BL-678) | 7 / 20 |
| this clip corpus (BL-680) | 0 / 59 |
| **inside the ABBA track feed (this round)** | **12 / 12** |

Zero percent, thirty-five percent, and one hundred percent — on the same question, from three datasets. An equality check would have reached a different conclusion on each. The bug is invisible in exactly the data you would validate against.

## Q2 / Q4 — The sound record, and why counts must be a series

```jsonc
{
  "track_id": "1825128190912080",
  "track_id_source": "licensed:music_asset_info.audio_cluster_id",
  "audio_type": "licensed_music",
  "audio_asset_id": "1389822245773253",
  "title": "The Winner Takes It All",
  "display_artist": "ABBA",
  "duration_in_ms": 297386,
  "spotify_track_id": "3oEkrIfXfSh9zGnE7eBzSV",
  "spotify_track_id_last_seen": "2026-07-29T13:46:00Z",
  "is_trending_in_clips": true,
  "highlight_start_times_in_ms": [124000, 249000, 109000],
  "counts": [
    {"ts": "2026-07-29T13:18:30Z", "clips_count": 837493, "restricted": false},
    {"ts": "2026-07-29T13:47:10Z", "clips_count": 837637, "restricted": false}
  ],
  "restricted_reads": 0,
  "first_seen": "2026-07-29T13:18:30Z",
  "last_checked": "2026-07-29T13:47:10Z"
}
```

**`counts` is append-only and never collapses to a scalar.** A single `clips_count` cannot express a rate and destroys the history that makes the rate meaningful.

**Velocity needs days, not minutes — measured.** Counts moved on **11 of 20 ids within ~10 minutes, 7 up and 4 down** (O Sanam −401, Let Him Cook −13, ABBA +144, Where Is My Mind +26). A count that moves *down* over ten minutes is a noise floor, not a trend. Therefore:

- sample **daily**, compute the rate from the **first and last clean points**, require ≥2 days;
- expose `n_points` so a 2-point rate is distinguishable from a 30-point one;
- discard restricted reads entirely rather than recording a zero;
- cost is **1 call per sound per day = $0.0006** → 500 tracked sounds ≈ **$0.30/day**.

**`is_trending_in_clips` is a genuine discriminator, not a restatement of size:** true on **3/20**, and independent of magnitude — ABBA at 837K is `true`, O Sanam at 1.07M is `false`. Free on every licensed read.

**`highlight_start_times_in_ms` was present on 18/20 track responses**, against 27% of *clips* (BL-680) — the track endpoint is by far the better source. It ships with four standing warnings: song time not reel time; licensed only; ranked not chronological (`[0]` ≠ best, unproven); and it marks a chorus/hook, not a drop.

## What one paid call actually buys (capture list)

Besides the count: **12 full media objects** (`play_count` 126,734 – 6,172,126 observed on the ABBA page, plus `like_count`, `comment_count`, `reshare_count`, full `clips_metadata`, `user`), `paging_info.max_id`, envelope `next_page_id`, and on licensed pages `spotify_track_metadata`, `available_tabs`, `audio_page_segments`. Treating this as a scalar lookup discards a page of proven high-performing reels and their creators.

## Method and honesty notes

- Two probe passes rather than one because pass 1 contained **two mistakes of mine**: it read `is_trending_in_clips` at `metadata.music_consumption_info` (the real path is `metadata.music_info.music_consumption_info`, so it scored a false 0/20), and it **did not persist the 19 responses**, making offline recomputation impossible. Pass 2 fixed both and saved every payload. The wasted spend was $0.012 — recorded here rather than quietly absorbed.
- The corpus for id selection was 90 unique clips across 4 saved chunk files: **70 original_sounds / 20 licensed_music**, yielding exactly 20 distinct licensed cluster ids.
- `spotify_track_metadata` is **null on all clip payloads** and only ever appears on the *track* response — consistent with BL-680.
- ABBA was reused from BL-678's saved response rather than re-bought.

## Open

1. **Original-sound clusters still have no name.** `best_audio_cluster_id` is confirmed correct for them and yields a count, never a title. Unchanged from prior rounds.
2. **Restriction scope unknown** — whether `is_music_page_restricted` is regional, rights-based, or transient was not determined; only that it flipped within ten minutes and then persisted across two consecutive reads.
3. **Retry-on-null for `spotify_track_id` is measured over 2 passes only** (65% → 80%). Whether a third pass keeps climbing is untested.
4. **Daily velocity is designed but not yet observed** — this round measured only the ten-minute noise floor, which is what proves the daily cadence is necessary.
