## 1. The one that matters — and a correction to my own BL-808

**BL-808 said `outcomes.py` had no specification. That was wrong.** I searched only the BL-80x reports; the specification is in **BL-797**, a 79x. I own that — it is the difference between "unrecoverable" and "fully documented", and it was the most important claim in that report.

BL-797 reported *shipping* three things to `outcomes.py`. Measured today:

| BL-797 shipped | present now |
|---|---|
| `mark_sent_from_csv()` | **0 occurrences** |
| `SEND_TRACKING_COLUMNS` | **0** |
| `RECORDABLE_COLUMNS = OUTCOME_COLUMNS + SEND_TRACKING_COLUMNS` | **0** |
| 9 permanent checks in the test suite | **0** — `test_outcomes.py` has no `touch_number` test |
| menu entry "Mark a whole sent list" | **0** in `control.py` |

**But the half that was committed survived:**

| | |
|---|---|
| `writer.FULL_COLUMNS` | **70 columns** — exactly BL-797's claimed 68 → 70 |
| `master_leads.csv` header | **`touch_number` at 69, `message_variant` at 70** |

**This is a half-shipped state, which is worse than either extreme.** The schema advertises two columns and the master file carries them, but nothing in the codebase can write either, and the menu entry that would has gone. Anyone reading `writer.FULL_COLUMNS` would reasonably conclude the feature exists.

### That harm is not hypothetical — it already happened, one report ago

**BL-810 documents the bulk marker as a live feature.** It lists the `[o]` menu as offering *"record + stats + **[4] mark a sent list**"*, and describes its behaviour in the present tense: *"the marker instead gates on a dry run whose confirm defaults to NO."*

The `[o]` menu, measured today at `control.py:3049-3052`, offers exactly three options:

```
("1", "Record what happened to a lead — paste a handle/email, mark the result"),
("2", "See what converts — reply & conversion rates by funnel / email / size / country"),
("3", "Export the numbers to a spreadsheet (CSV)"),
```

**There is no [4].** A careful agent doing a UI audit read BL-797, or the surviving 70-column schema, and documented a feature that no longer exists. It cost that round its accuracy, and the published record now describes an interface the user does not have. **This is the strongest argument for redoing it: the gap is already generating false documentation, and it will keep doing so until either the code returns or someone writes down that it is gone.**

BL-811's dependency is fine, for contrast — it uses `outcomes.match_indices()`, which survived and is live at `control.py:2940`.

### It also explains the missing checks

BL-808 noted the suite fell from 2,275 to 2,266 and said it had not identified why. **BL-797 states it added exactly 9 permanent checks.** 2,275 − 2,266 = **9**. The arithmetic closes: the lost 9 checks are BL-797's, destroyed with the code they tested.

### What redoing it needs — all from BL-797, none from me

```
mark_sent_from_csv(csv_path, date_sent, sent_channel, touch_number,
                   message_variant, dry_run=False)
```

- builds a normalised index **once inside the lock**, then dict-lookups every key
- returns matched/unmatched **key lists, never counts alone**
- `dry_run=True` returns identical output and writes nothing; the menu **always runs dry first**
- `touch_number` rejects 0 and negatives — *"there is no zeroth contact, and a stored 0 would read as 'not sent'"*
- `message_variant` free-form, capped at 40 chars, no controlled vocabulary
- both columns appended last, so byte positions of existing fields are preserved
- measured on live files: **2,781 of 2,787 keys stamped in 0.18 s**, 6 ambiguous refused rather than fabricated

**Why it is worth redoing above everything else:** nothing else in the system records that a send happened. `date_sent` is blank on all 58,000 rows, so every suppression rule that depends on "already emailed" is inert, and there is no way to measure reply rate. 2,787 keys are sitting in the export waiting for it.

## 4. What the logs revealed — nothing, and I had to correct my own method twice

First pass flagged 5 log shapes as unproducible by current source. **All five were false positives, from two different mistakes of mine:**

- **Wrapped string literals.** `"NON-EMPTY HikerAPI response but ZERO "` is split across two source lines in `ig_discovery.py:398`, so a single-line grep missed it. Fixed by joining implicit concatenation before matching.
- **Constructed messages.** `"migrated cache_hashtags.json into resolved_hashtags"` is assembled from a constant, so the literal never appears in source — but the logic is alive at `state.py:316`.

After both corrections: **every logged behaviour in the window is still producible by HEAD. No log-visible behaviour was lost.**

**And the logs answer a better question.** The lost edits were authored between the last commit (16:55) and the reset (20:27). Log volume in that window:

```
17:00  123    19:00  3    20:00  1
```

**Essentially nothing ran.** The lost work was being written, not executed. That is consistent with mid-authoring rather than finished-and-verified work — which is why there is no runtime trace, and why for four of the seven there is nothing to reconstruct from.

## Limits

- **"No trace" is not "nothing was lost."** For four modules I can only show that no evidence survives — the edits may have been substantial. Absence of a fingerprint is not absence of work.
- **My log-forensics method produced 5 false positives before I corrected it twice.** I would not trust its negative result as strongly as its positives; a third failure mode I have not thought of would look exactly like a clean pass.
- **The 9-check arithmetic is consistent, not proven.** 2,275 → 2,266 matches BL-797's stated 9, but several agents changed suites that day and I did not have per-suite baselines to confirm the attribution.
- **I did not read BL-797's actual diff** — it was never committed. Everything in §1 comes from the report's prose, which is a description of code, not the code.
- **I did not attempt OneDrive Version History**, which remains the only real recovery route for items 5–7.
- **Nothing was implemented, and I did not redo `outcomes.py`** — the brief scoped this round to the list. I also did not correct BL-810's `[4]` claim in that report; it is published and I only note it here.
- **I did not verify that BL-810's `[4]` line came from BL-797** rather than from an independent mistake. Either way the menu entry does not exist, but the causal story in §1 is my inference.
