## 1. The five stale headers — corrected, with a test

`MEMEBOT-009`, `-021`, `-025`, `-027`, `-033` each opened with a variant of:

> `# !! THIS MANIFEST CANNOT PASS verify_claims.py … .gitignore:137 ignores memebot/ entirely`

**Wrong twice over**, and three of them are mine:

- **MECHANISM.** `memebot/` is a **nested git repository**, not merely an ignored directory. Its files could never be blobs in the parent whatever `.gitignore` said — `git add` stores a gitlink. BL-859's proposed `!memebot/**/*.py` is a **no-op**: git does not descend into an excluded directory, so the negation is never considered. The ignore rule was never the cause.
- **STATUS.** `verify_claims` resolves HEAD against the owning repo now, so those claims verify. **VERIFIED: 193 claims across 16 manifests, 0 stale.**

All five now carry a correction naming both halves.

### The test, and the trap it fell into first

`tests/test_claims_manifest.py::ManifestHeaders`, two checks: no manifest may deny it can be verified while its claims verify, and none may blame `.gitignore` without naming the nested repo.

**My first version flagged all five headers it had just fixed** — because a correction *quotes* the claim it disowns. A guard that cannot tell an assertion from a quotation of a retracted assertion punishes the fix. It now skips a header carrying an explicit correction marker, and that exemption is scoped: planting a bare denial on a **clean** manifest (`BL-820`) fires **both** checks; restoring it returns the suite to green.

**Headers are checked on disk, claims at HEAD**, and the asymmetry is deliberate. A claim is a promise about code that must survive a reset (BL-797). A header is documentation about the manifest a person is reading, and disk is what they read — checking it at HEAD would leave a corrected caveat reported as a lie until somebody commits, inverting BL-874's rule that a manifest waits for the code and never the reverse.

## Found, not fixed: a false positive in `claim.py`'s staleness flag

`brief` reported **MEMEBOT-041 at 1 minute old as `POSSIBLY STALE: any declared file untouched for 81 min`.** That is wrong. The claim was seconds old; its declared files are pre-existing test files last edited 81 minutes ago, and a round that has just started has necessarily not written anything yet.

The rule I wrote in MEMEBOT-033 is `quiet > threshold and quiet > age * 0.75`. For a very young claim the second clause is trivially satisfied, so file age leaks in where it means nothing. **The fix is one condition — require `age > stale_after_min` as well** — so a claim cannot be called stale before it has had time to become so.

`tools/claim.py` is held by **BL-889**. Not fixed here. The flag is advisory and says "ask the owner", so a false positive costs a question, not a decision — but it is exactly the kind of noise that gets a guard ignored.
