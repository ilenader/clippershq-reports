## 2. THE DIAGNOSIS, BY TEST — there are TWO defects and every previous fix addressed neither

Instrument: `scratch/bl1255_keyshape.py` (selftest **18/18**). It reports **shape only** and
imports `redact` / `looks_like_credential` / `assert_credential_header_safe` from
`clippershq/secrets_guard.py` — never a copy.

### The byte-level shape, no value printed

| | |
|---|---|
| length | **109 chars** (109 bytes — pure ASCII) |
| after strip | **108** |
| trailing byte ordinals | `[65, 65, 10]` — **a bare LF**, not CRLF |
| ends with LF / CRLF | **True / False** |
| leading whitespace | none |
| prefix shape | `sk-ant-` ✓ |
| charset | alpha 86, digit 17, dash 4, underscore 1, other 0 |
| sha256[:6] of the stripped value | `b677ef` (a fingerprint, so two sources can be compared without either being shown) |

### The two candidate causes, separated by running them

| what was sent | result |
|---|---|
| **STRIPPED** (108 bytes) | **HTTP 401 `authentication_error: "API key is invalid."`** |
| **RAW as stored** (109, trailing LF) | **`ValueError: Invalid header value b'<REDACTED>\n'`** — raised *client-side*; the request never left the machine |

**Both defects are real and independent:**

- **A — the trailing newline.** Every HTTP client refuses the header before sending. The
  exception is raised in the transport layer, so it *reads as a network error* — which is why
  this has been misdiagnosed three times.
- **B — the key itself is invalid.** Stripped, it gets a clean 401 from the server. This is not
  a balance problem: a 401 `authentication_error` is not a 402, and the operator is right that
  the account has credit.

**Fixing only A yields a clean 401. Fixing only B still yields a transport error.** Every
previous "re-set" evidently fixed neither — which §3 explains.

**The other candidates the brief named are ruled out by test, not assumption:** no `.env` file
exists anywhere (four paths checked); `config.json` has no `anthropic` or `claude` block; no
`.bat`/`.ps1`/`.cmd` in the repo sets the variable; **no alternative name is set**
(`ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_KEY`, `CLAUDE_API_KEY`, and two misspellings all unset), so
nothing is shadowing it; and there is no BOM or CRLF file involved because there is no file.

## 3. WHY IT KEEPS COMING BACK: the store is outside the repo

```
HKCU\Environment  ANTHROPIC_API_KEY   len=109  strip_len=108  ends_LF=True
Machine scope                          UNSET
Process scope     inherited from User  len=109  ends_LF=True
```

**It is a Windows USER environment variable, and the trailing newline is baked into the registry
value.** No file in this repository is involved. Any "fix" that edited a repo file, a `.env`, or
`config.json` changed nothing at all — the source was never touched, so the newline returned the
next time a shell was opened. That is the cause the three previous reports missed.

### The guard that would have caught it already exists and nothing calls it

`clippershq/secrets_guard.assert_credential_header_safe` — written for the BL-1093/BL-1107 leak
— refuses this exact value and names the true cause:

```
ANTHROPIC_API_KEY: the credential has leading or trailing whitespace;
requests refuses such a header value.
```

…and refuses `\r`, `\n`, `\x00` separately as control characters, and a dict (the BL-1093 case)
by naming its type and length only. Its contract is that **the message names the parameter and
never the value**. Verified: stripped → safe; as stored → refused with that sentence and no key
material in it.

**The leak vector is confirmed live, not hypothetical.** The raw `ValueError` above contains the
whole key; only redaction at the write point kept it out of this round's artefacts. This is the
~18th instance in this project of a failure that reads as something else entirely.

`tests/test_bl1255_credentials.py` (**18 tests**) pins all of it, including a negative control
that fails if anyone re-implements `looks_like_credential`, `redact` or the header assert
locally instead of importing them.

## 4. THE TWO CARRY-OVERS, FIXED

### String timings — 553 rows, both recorders

`--elapsed-s` was declared to argparse with **no `type=`**, so both judge recorders wrote
`"elapsed_s": "42"` on every row they ever produced:

| file | rows | `elapsed_s` type before |
|---|---:|---|
| `bl1240_iter{1,2,3}.jsonl`, `bl1240_volume.jsonl` | 213 | `str` on all |
| `bl1242_iter{4,5}.jsonl`, `bl1242_rejudge874.jsonl` | 340 | `str` on all |

**`type=float` added to both** (`bl1240_record.py:136`, `bl1242_record.py:161`). Verified: both
now write `42.0` as a `float`, and both now **refuse** a non-numeric duration loudly instead of
storing it silently.

**The 553 existing rows are NOT rewritten.** They belong to two finished rounds, and rewriting
another round's committed artefacts is a bigger risk than the defect. Read them through a
coercing accessor — `scratch/bl1243_tokens.py:as_number` already exists and has the string case
in its selftest.

### A stalled run now says where it stopped

`bl1242_rejudge874.jsonl` stopped at 240 of 874 and nothing recorded where or why. Two changes:

- **`<out>.progress.json`, rewritten after EVERY verdict**, atomically. Not at the end: a
  Windows hard kill exits `0xC000013A`, so no `finally` and no `atexit` runs — a marker written
  only on completion is one that exists only when it was not needed. It carries
  `rows_written`, `last_handle` and `last_write_at`, because a count alone cannot tell a resume
  where to start.
- **`done --queue` now reports what is LEFT**, and says which key it compared against.

Asked about the real stalled run:

```
rows written : 240
queue key    : REJUDGE_874_ALL
total / done / remaining : 874 / 239 / 635
resume from  : memes, mazitundeednut, horoscoptic, florencebymills
```

**635 remaining, and a resume point.** One of the 240 rows is not in the queue list — 240 rows
against 239 matched — consistent with BL-1242's salvaged off-list row.

A defect found while building it: the queue has **no `handles` key** and carries several lists
(`REJUDGE_874_ALL` 874, `REJUDGE_874_TODO` 807, `D`, `E`, …). Guessing `handles` returned an
empty list and reported **"0 remaining" for a run with 635 left** — worse than refusing. It now
prefers the named set, then `handles`, then the longest list, and always publishes `key_used`.
