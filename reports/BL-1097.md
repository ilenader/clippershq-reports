### The cap, and why it is shaped this way

* **It charges ATTEMPTS, not successes.** A failed fetch costs the same page as a good one.
* **It reserves the next call BEFORE making it** — `Cap.reserve()` debits the worst case and
  returns `False` to stop. A refund is impossible; an overspend is.
* **It is written against paid legs generally**, so adding a leg later cannot escape it.

## WHAT I GOT WRONG

**Three format errors in my own harness, all of the same family — a join or shape I assumed
instead of checking — and every one produced a clean, plausible number.**

1. **I looked for media in directories that do not exist** (`clip_media/`, `media/`) and
   reported **0 clips with local media**. There is no canonical media directory; 354 clips
   have pixels sitting in `output/bl1081/` and eight scratch directories. Uncorrected, this
   round would have PAID to re-fetch frames already on the disk.
2. **I joined on the wrong key.** A library `clip_id` is `<media_id>_<user_id>`; a file is
   named `<media_id>…`. Comparing the composite against the stem meant the sets **could not
   intersect**, and it again reported 0 free clips. The correct join found **68**.
3. **I read the ground-truth files as flat maps** when they are metadata-wrapped
   (`_what`, `_verdicts`, `_limits`). My "10 hand-labelled clips" were wrapper key names, and
   "0 present in the library" was an artefact. The real set is 28 and all 28 *are* present —
   which is how I found the genuine zero in §4 rather than a fake one.

**And a patch that reported success while changing nothing.** My first attempt to add the
paid leg printed `patched` unconditionally without verifying the replacement matched. It had
not matched; the sweep then ran the old code path and spent **$0.00** while looking like it
had worked. That is precisely the family this brief warns about — *"a prior backfill logged 45
writes and changed zero values"*. Fixed by using an editor that fails loudly on a non-match.
