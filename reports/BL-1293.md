## 2. Both render bugs fixed, verified from the pixels

**Before touching `edit.py` I removed two copies of `BL921_WORKING_TREE_ONLY_MARKER` from its
tail.** That is test residue — `tests/test_verify_claims.py:59` appends it and restores it in

### Clip 41 — `--override-text` was cleaned before `--label-verbatim` was read

The flag's own help says *"no headline cut, no emoji strip, no leading-punctuation strip, **no
max_chars truncation**"*. But `label_verbatim` is not read until `apply_template`, a thousand
lines below the 120-char trim, so every verbatim caller was put through `caption_hook` first —
which cuts at a sentence boundary and appends an ellipsis. **`clip_pipeline.render_one` always
passes `--label-verbatim`, so this hit both entry points, not just the paste path.**

Fix: the trim is now `len(...) > MAX_CAPTION_LEN and not args.label_verbatim`. It still runs
for every non-verbatim caller, which is right — MEMEBOT-064 put the trim on this side of the
boundary deliberately.

**OCR of the label strip, shipped render vs re-render:**

| | drawn line | ellipsis | his words present |
|---|---|---|---|
| **BEFORE** (shipped) | `In The Hobbit (2014)...` | **yes** | **2 of 11** |
| **AFTER** (re-render) | the whole 126-character sentence | **no** | **11 of 11** |

### Clip 9 — the type reservation was dead by TWO routes, not one

The reported defect is real: the paste path called `label_strip_from_card(card, cover_band)`
and never passed `src_line`/`src_type_px`, while `clip_pipeline` passes both. Both values were
already in scope, read 46 lines above. Fixed.

**But that fix alone would not have moved clip 9, and finding out why is the finding.**
`measure_label_card` returns **None** on that clip, so `label_strip_from_card` returns None on
both arms and the box comes from the *no-card fallback* — which fits the strip to **his** ink
and knows nothing about the type **we** are about to draw. And `fit_label_px` only ever checks
**width**: it has no notion of how many lines the text wraps to or how tall the block becomes.

Measured with the fitter's own function, `type_block_height_px`:

| | |
|---|---|
| his line | 105 characters at 46 px |
| block the text actually needs | **335 px** (5 lines × 51 px) |
| strip it was given | **230 px** |
| **overflow onto the picture** | **105 px** |

So the fallback now reserves the same number the card path reserves. **The strip only ever
grows DOWNWARD** — `label_box[1]` is untouched, because the top edge is what covers his line
and moving it would uncover his words (BL-1130).

**From the pixels, shipped vs re-render at the corrected box:**

| | white strip | ink on its FIRST row | ink on its LAST row |
|---|---|---|---|
| **BEFORE** | y 220–449 (230 px) | **50%** | 15% |
| **AFTER** | y 220–554 (335 px) | **0%** | **0%** |

The block now sits fully inside the strip with clear margins at both edges.

### It applies everywhere he might paste

There are exactly **two** call sites of `label_strip_from_card` in the tree, and **both now
pass the reservation**: `clip_pipeline.py:4468` always did, `paste_batch.py:1674` now does,
plus the fallback beneath it. `parse_links` handles a single link and a list of links through
the same `run()`; an account goes through `harvest_accounts`, which harvests and scores but
does not render — its clips reach one of those same two paths.

## 3. Two hundred pages to mark, with the field the old file never had

**Why this matters more than it looks.** The marks file stores the JUDGE'S OWN VERDICT plus
your GOOD/BAD on it, and carries no reason column. So agreement is
`97 − broke(GOOD) + fixed(BAD)` — **a judge that changes nothing scores 97 by construction.**
That is an identity, not a measurement. These sheets take your verdict *independently* of the
judge's and your reason alongside it, so the next score is something the judge can fail.

|---|---|---|
| pages | **100** | **100** |

| external requests | **0** | **0** |

**Links were verified by re-reading the saved `index.html` from disk**, not from the builder's
in-memory model — the check can therefore catch a bad write, which a check on the model cannot.

### The marks cannot be lost quietly

Tested by running the sheet's **real script** under node v24 against a DOM and `localStorage`
stub — not by reading it:

| step | counter |
|---|---|
| start | 0 saved · 0 waiting |
| mark, type a reason, mark again | 2 · 2 |
| **download** | 2 · **0** |
| type a reason **after** the download | 2 · **1** |
| reload from a seeded store | 2 · 2, button restored, reason text restored |

Verdicts and reasons both persist. And **when `localStorage` throws, the white-on-red overlay
covers the page** (`display: block`, confirmed) telling him to download now and stop marking —
it does not let him type into a void.

This is the third appearance of the same hazard and it is why the counter uses a **monotonic
sequence, never `Date.now()`**: he lost 50 marks once to a save that failed silently in green,
and BL-1289 rebuilt that exact false green in a new place, where a mark made in the same
millisecond as a download read as already-downloaded.
