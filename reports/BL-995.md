## 1. Why the front half did not run

BL-979 is a live round growing the clip library. Its claim covers `clip_library`,
`clip_seen.json`, `repost_seen.json` and twelve more paths; it had completed stages A/B/C
(+658 clips) and was executing stage D — vision labelling of the 659 unlabelled clips —
when I started. `clip_library` had been written **13 seconds** before my first command.

Stages 1–3 of this brief write exactly those files. Running them would have interleaved two
rounds' appends into one library and corrupted both measurements, so I did not.

What I did instead: froze a snapshot of the library (2,661 clips) so my corpus could not
move under me, pinned `memebot` at HEAD in a detached worktree so another round's
uncommitted `duck.py` could not contaminate a comparison, and verified the front half's
boundaries read-only.

**This is itself a rehearsal finding.** The operator's first real day will hit the same
wall the moment anything else is running. The runbook now opens the front half with a
`claim.py brief` / `claims_read.py --holders clip_library` check and says plainly: reading
the library while another round appends is safe, writing it is not.


No stage was silent and nothing was unaccounted for, in any of the four runs. Every drop
carries a reason and a count. The same data reaches `dashboard/static/runs.json` with
credentials, emails and handles redacted at record time.

Two behaviours worth knowing, both surprising, neither a fault:

- **`--cap` is required.** Omitted, the run refuses to start. Correct: headless has no
  human, so the cap is the gate, and a forgotten cap must mean no run.
- **Omit `--target` and you get exactly one video** — the headless prompt answers with its
  default of 1. The funnel table lists `target_key: None`, but `--target` does reach the
  render batch.

## 3. The cap binds, and it printed as $0.00 while doing it

Deliberately under-capped at $0.0018 against a target of 20:

```
STOPPED ON THE CAP: $0.0012 spent, the next clip could cost $0.0012, cap is $0.0018.
1 video(s) made, 59 candidate(s) not attempted.
        59  not attempted: stopped early (budget)
```

**The firing check** is `run_batch`'s pre-flight comparison of *next clip cost* against
*remaining cap*, and the observable is that named drop — the 59 unattempted candidates are
counted into the log, so stopping on the cap leaves nothing unaccounted for.

But the summary line read:

```
produced 1   spend $0.0012 of $0.00 cap   wall 36.7s
```

`decision_log.py` formatted spend at `%.4f` and the cap beside it at `%.2f`, so **any cap
below half a cent printed as `$0.00`** — at the one moment the number matters, reading as
"the cap was zero" rather than "the cap bound". Small caps are exactly the caps that bind,
so the defect could only ever appear when it was most confusing.

Both amounts now print at `%.4f`; the same run now reads `spend $0.0012 of $0.0018 cap`.
An existing test pinned the old format (`"of $0.50 cap"`) and moved with the fix, plus
three new ones — including that the two dollar amounts on that line must agree on
precision, since two precisions for two amounts on one line is never right.

## 6. What I got wrong

Three findings died before publication, all the same shape — **I guessed a schema instead
of reading it**:

1. **"Treatment vocabulary mismatch."** The ledger says `mute-and-replace`, `duck.TREATMENTS`
   says `mute`. I nearly reported MEMEBOT-027 reopened. They are two deliberately separate
   vocabularies — one descriptive for the feedback loop, one the renderer's CLI — and
   nothing carries one into the other, because `render_one` passes `--audio-class`, never
   `--treatment`. The check now compares each against its own producer.

2. **"12 videos came from 6 clips."** Two ledger rows are written per render (one at start,
   one at finish), so counting raw lines double-counts. `read_records()` collapses 486 lines
   to 217 last-wins. I also first read `finished_at` as local time when it is stamped in UTC
   — so my own runs appeared to have written nothing at all.

3. **"The dashboard artifact has no stage names."** The keys are `kind` and `stage`, not
   `run_kind` and `name`. The artifact was complete the whole time.

Each was caught by looking at the data one level deeper. None would have been caught by a
test, and the second is the one this repo has shipped before — it is the documented
`videos_by_day` counted LINES gotcha, rediscovered from the other side.

## 7. The cost, and a warning about how it is measured

MEASURED, this run: **$0.00075 and 24.9s per video** for the render leg (1.25 re-fetches
per video).

All-in for one finished video, **two legs derived and labelled, one measured**:

| leg | per video | source |
|---|---|---|
| walk | ~$0.000406 | BL-979 measured (+600 clips for $0.2436) |
| vision label | ~$0.000990 | derived: `vision_spent_usd` $2.1438 ÷ 2,165 labelled, whole history |
| render | **$0.00075** | BL-995 measured |
| **all-in** | **≈$0.0022** | |

The previous figure, $0.0504/video from cold against a 50-clip library, is not wrong — it
is a different situation. The walk amortises across everything it catalogues, so the
per-video cost falls as the library grows. $0.0022 must not be quoted as a cold-start cost.

**And the ledger cannot attribute it.** Across my run window `spend.json` moved **+$0.6150**
while my four runs reported **$0.0120** between them; the difference was another round's
retrieval (`ig_spent_usd` +$0.6030, `vision_spent_usd` +$0.000041). A before-and-after
ledger delta answers "what did the machine spend", never "what did I spend". The
`Spend this run` line is the attributable figure because it meters the calls that went
through that run's own client. This is now in the runbook.
