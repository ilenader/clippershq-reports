## What was wrong, in one paragraph
BL-602 shipped the structured-rule auto-reject in shadow, but the shadow was a `console.log` line to Railway's ephemeral log stream (`clips/route.ts`), and the clips table stores no caption. BL-656 proved the consequence: the false-rejection rate, the one number that decides whether auto-reject is ever safe to enable, **could not be computed at all**, because neither the machine's decision nor the caption it judged was kept anywhere durable. This round fixes the measurement and changes nothing about any clip.

## PART 1 — the shadow decision is now persisted

A new **standalone, additive** table `rule_shadow_decisions` (Prisma model `RuleShadowDecision`) records every shadow evaluation. It follows the exact decoupled pattern of the existing `ScraperShadowSample`: `clipId` is a **plain indexed String**, a join key to `Clip.id`, **not a Prisma relation**, so the `Clip` model is untouched and this is a pure ADD. Applied to production with **`CREATE TABLE IF NOT EXISTS`** through the sanctioned `scripts/run-schema-sql.js` (never `prisma migrate`); the client was refreshed with `npx prisma generate` only.

Each row holds what PART 1 asked for:

| Column | Meaning |
|---|---|
| `clipId`, `campaignId`, `platform` | which clip, campaign, platform |
| `wouldReject` | the machine's would-be verdict (true only when a machine-CERTAIN auto_reject rule fired) |
| `wouldRejectRuleIds`, `rankRuleIds` | which rules fired, and which would rank for a human |
| `results` (JSONB) | full per-rule evidence: verdict + reason, e.g. "token(s) literally absent: @handle" or "sound id mismatch (got X, want Y)" |
| `evaluated`, `failedOpen` | fail-open sanity counts |
| `autoRejectLive` | the state of the live switch at decision time, always false this round |
| `createdAt` | timestamp |

The write is inside the existing `after()` callback, wrapped in its own try/catch, so a persistence miss (for example the table not yet present in an environment) fails open exactly like the old log line and never touches the clip. The `console.log` line is kept for live Railway tailing; the table is what makes the rate measurable.

## PART 2 — what the decision was based on is now stored

The row stores the **caption text** and the **sound id** the evaluator actually saw (`caption`, `soundId`, plus `captionPresent` / `soundIdPresent` booleans). These come from the provider payload **already fetched at submit** for views and freshness (BL-552), so storing them costs **no new vendor call**.

**Privacy.** The caption is the clipper's own public post text. It is retained only for as long as needed to validate the rule engine before auto-reject could ever be enabled, and a later round that drops or enables auto-reject should also decide the retention window and prune old captions. **It is redacted in this report and every public output** (the proof below prints only its length and a present flag, never its content).

## PART 3 — the false-rejection rate is now a single query

The measurement that decides everything, of the clips the machine WOULD have rejected, how many a HUMAN approved, is now one JOIN. Run it directly:

```sql
SELECT
  count(*) FILTER (WHERE d."wouldReject")                                       AS would_reject_total,
  count(*) FILTER (WHERE d."wouldReject" AND c.status = 'APPROVED')             AS false_rejections,
  count(*) FILTER (WHERE d."wouldReject" AND c.status = 'REJECTED')             AS agreed_rejections,
  round(100.0 * count(*) FILTER (WHERE d."wouldReject" AND c.status = 'APPROVED')
        / NULLIF(count(*) FILTER (WHERE d."wouldReject" AND c.status IN ('APPROVED','REJECTED')), 0), 2)
                                                                                AS false_reject_pct
FROM rule_shadow_decisions d
JOIN clips c ON c.id = d."clipId"
WHERE c.status IN ('APPROVED','REJECTED');
```

`false_rejections` counts clips a human APPROVED that the machine would have REJECTED, each an honest clipper the machine would have wrongly punished. `false_reject_pct` is the rate to compare against R-2's rejected 11.05 percent. It reads `NULL` until enough decided clips accumulate, which is honest rather than a fake zero.

## PART 4 — how long until it can be judged

Measured now: **6 campaigns** carry an auto_reject caption rule, and about **59 clips hit them in the last 7 days** (26 in the last 4, matching BL-656), so roughly 8 to 9 caption-rule clips a day. But only the **would_reject subset** feeds the rate, and most captions do contain their tokens, so would_reject decisions will arrive at perhaps one or two a day. A stable rate needs on the order of a hundred decided would-reject cases before it is more than noise, which at this pace is realistically **two to three months**.

**Broadening gathers data faster.** BL-596 noted the structured-rules backfill covered 11 campaigns and 86 lines, but only these 6 currently carry an auto_reject caption rule. If more active campaigns adopted a `REQUIRED_CAPTION_TOKENS` auto_reject rule, the would-reject sample would grow proportionally and the rate could be judged in weeks rather than months. That is a product choice for the owner, not something this round changes.

## PART 5 — the missing flag now exists, and still enables nothing

BL-602 described switch-on as one env flag, `RULES_AUTO_REJECT_LIVE`; BL-656 found no such flag in the code. It now exists as a real, greppable, off-by-default helper, `isAutoRejectLive()` in `src/lib/auto-reject-flag.ts`, returning `process.env.RULES_AUTO_REJECT_LIVE === "true"`.

It **gates nothing today**, deliberately, because there is no code path that rejects, flags or status-changes a clip from a rule verdict (building one is out of scope, and forbidden this round). Its only use here is to stamp each shadow row with `autoRejectLive` (always false), which is per-row proof the machine changed nothing. **Enabling auto-reject in a future round needs two things, not one: a measured, owner-accepted false-rejection rate, AND a new reject path built behind this gate.** Setting the env var alone is inert by design, so a stray env edit cannot silently start rejecting clips.

This demonstrates every requirement: a shadow decision was written to the database **with its rule, verdict, evidence, caption and sound**; the target clip's status was **unchanged** (PENDING before and after), so nothing was rejected or status-changed; nothing is exposed to any clipper (the table has no clipper-facing route); the **false-rejection query ran** and returned a result even on a one-row sample; and `autoRejectLive` is false, so **auto-reject remains off**. The test row was then deleted, so the production table starts **empty** and will fill only with genuine decisions from live submits after deploy.
