## The answer in one sentence

**Both Windows stores are clean, so his `REG delete` did exactly what it claimed — but the value
is still live in this process and every other terminal opened before the delete, and six
plain-text copies of the key are sitting on disk untouched by any registry operation.**

## 1. Is it gone from Windows? — YES, both stores

Read directly, not inferred. `[Environment]::GetEnvironmentVariable(name, store)`:

| store | what it is | result |
|---|---|---|
| `HKCU\Environment` | the one he deleted | **ABSENT** |
| `HKLM\...\Session Manager\Environment` | machine-wide, **nobody had looked here** | **ABSENT** |

A user-scope delete does not touch a machine-scope value, so the second row was a real
possibility and had to be checked rather than assumed. It is clean too.

I also enumerated both stores for any **sibling name** doing the same job under a different
spelling — `ANTHROPIC*`, `CLAUDE_API*`, `CLAUDE_KEY*`. **User: none. Machine: none.**

## 2. Is it still in a live process? — YES. This is his actual question.

**It is present in the process running this round: 109 bytes, ends in a newline. A child process
spawned from here inherits it: `PRESENT 109`.**

Windows copies the environment block into a process **when the process is created**. Deleting the
registry value changes what *future* processes get; it does nothing to one already running. So
every terminal, editor and shell he opened before the delete is still carrying the key, and every
child they spawn inherits the stale copy.

**Closing and reopening every terminal is REQUIRED, not merely tidy.** That is a measurement —
the store says ABSENT and the same lookup in process scope says PRESENT, at the same moment.

**The 109 against the 108 in §3 is the BL-1244 bug, visible as a byte count.** The env var is one
byte longer than the file because it carries a **trailing newline**. That newline is what made a
key into an illegal HTTP header and produced BL-1244's `APIConnectionError`.
