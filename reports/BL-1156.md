## 2. THE PLACER: measured, and nothing shipped

### The baseline reproduces, and so does 2.02x

```
density-matched baseline    +/-1s  21.2%      +/-2s  33.6%
shipping placer             +/-1s  12/28 = 42.9%  =  2.02x
                            +/-2s  16/28 = 57.1%  =  1.70x
```

A baseline is not "one second out of the clip's length" — it is a second drawn uniformly
from **the set the placer may actually return**, which is what makes it 21.2% and not the
12.8% that produced the inherited 3.35x.

> **One correction to the brief.** It says the shipping placer "does not clear at ±2s". On
> this measurement it does, narrowly: 16/28, Wilson CI **[0.391, 0.735]** against a 0.336
> baseline. The lower bound clears by 5.5 points. I am not claiming the brief's number was
> wrong — a different clip subset would move this — only that I could not reproduce it and
> am reporting what I measured.

### Every candidate, same clips, same labels

| candidate | ±1s | ±2s |
|---|---|---|
| shipping (1 fps argmax) | 12/28 · 2.02x | 16/28 · 1.70x |
| dense argmax (4 fps) | **12/28 · 2.02x** | **16/28 · 1.70x** |
| dense + middle-weight 0.3 | 13/28 · 2.18x | 18/28 · 1.92x |
| dense + middle-weight 0.5 | 13/28 · 2.18x | 18/28 · 1.92x |
| dense + middle-weight 0.7 | 12/28 · 2.02x | 17/28 · 1.81x |
| **dense latest-big ("wait for it")** | **10/28 · 1.68x** | **11/28 · 1.17x** |

**Sampling four times more finely changed nothing.** Dense argmax picks the *identical
second* as the shipping scan on all 28 clips. Whatever the miss is, it is not resolution.

### His two hypotheses, tested — and this is the part worth reading

**"The payoff is usually nearer the middle, rarely in the first or last 20%."**
Directionally right, statistically not supported on 28 clips:

```
payoff in the middle 60%   23/28 = 82.1%   [64.4%, 92.1%]
expected there by chance   66.6%           -> lift 1.23x
```

The confidence interval's lower bound (64.4%) sits **below** chance (66.6%). Most of the
apparent effect is that the middle 60% is simply where most of a clip is. Two payoffs land
at 0.92 and 0.93 of the way through, and four land inside the first 20%.

**"Wait for it" clips put the payoff last.** This is the one that produced the visible
failure — a render placed at 1.0 s on the back of a head — so I built it as its own
candidate: take the *latest* second whose change is within 75% of the maximum. **It is the
worst candidate tested and the only one that fails to clear the baseline at either
tolerance** (10/28 and 11/28). The observed miss is real; *"the payoff is last"* is not the
rule that explains it.

### Why the middle-weight is not shipped

It gains **one** hit at ±1s and **two** at ±2s. Paired against the shipping placer clip by
clip:

```
+/-1s   middle-weight wins 3, shipping wins 2   (5 discordant of 28)
+/-2s   middle-weight wins 4, shipping wins 2   (6 discordant of 28)
```

That is noise. A candidate once scored 7/19 against 5/19 here and was correctly not shipped;
this is the same size of difference and gets the same answer. **`drop_placer.py` is
unchanged — `git status` reports it unmodified.**

### What the dense scan IS good for, since it is not accuracy

It is **cheaper**, because it does one ffmpeg call with an `fps` filter instead of one
process per second:

```
                    p50      p90      p99     samples/clip
dense (4 fps)      0.72s    2.81s    3.11s        73
shipping (1 fps)   2.12s    5.39s    5.39s        18

a batch of 40:  dense 29s typical / 124s worst   ·   shipping 85s typical / 216s worst
```

Four times the resolution for a third of the time. **Not adopted**, because the brief's gate
is accuracy and it buys none; it is measured, tested and sitting in
`scratch/bl1156_scan.py` if a future round wants the wall clock back.

## 3. The hook picker is gone

`paste_batch.resolve_song()` picked a window at **plan** time — before the clip was fetched,
so it could not know the clip's length or where its action was — and `drop_placer.plan()`
then overrode it at render time. Every batch record carries the evidence: `hook: 'h1'`
beside `placement_hook_id: 'h4'`.

BL-1155 measured this and handed the removal to BL-1154. **BL-1154 was mine and did not do
it.** It is done now: the `<select>` is gone, the page sends no hook, and in its place is a
line saying the placer chooses per clip, linking to the marking page.

Removing it needed care in one spot: `fillPasteSongs()` began `if (!sel || !hook) return;`,
so deleting the markup alone would have silently emptied the **song** dropdown too.

## 4. What I got wrong — and it cost 107 links

**Every render in this round's first two batches failed, and the cause was mine.**

```
✕ --only filter matched zero videos (platform=instagram, handle='cawncept')
```

The staged file was present, the handle matched, and `discover_videos()` finds it when
called directly. What was wrong was one word in the config:

```yaml
output_dir: outputs_bl1156_drop\bl1156p_...\_work\paste_...      # RELATIVE
```

`edit.py` resolves a relative `output_dir` against **its own** root — `memebot/scraper/` —
where nothing of the sort exists. I had passed `--out-root outputs_bl1156_drop` as a
relative path. `build_render_config`'s docstring asserts *"`output_dir` is absolute and
belongs to this run"*, and nothing checks it.

**107 links resolved, 0 rendered, before I diagnosed it.** The tell was there from the first
batch and I read it as a gate problem because 45 of 49 refusals really were speech.

**The robustness hole is real and is not mine:** `build_render_config` should absolutise, or
refuse a relative path by name. It is a one-line fix in `clip_pipeline.py`, which is FREE —
I am not taking it because this round's remaining time is committed and a change to the
render path deserves its own verification, not a patch at the end of a long round.

Other mistakes:
* **I sampled the link list uniformly from the clip library**, which is dominated by talking
  clips: 45 of 49 refused for speech. The second list filters on the library's own measured
  `speech_frac <= 0.10` and non-empty `ocr_gate_text` *before spending anything*.
* **My scan harness wrote its JSON only at the end**, so its own timeout killed it and lost
  all 28 dense scans — the same shape as a funnel that meters in a `finally`. It now saves
  each leg as it lands.
* **A test of mine asserted the wrong arithmetic** about the tail guard (`clip_len 5.0`
  allows second 4; I claimed it did not). The code was right.
