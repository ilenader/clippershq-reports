## The evidence, and its honest limit

**The database records WHEN and WHICH JOB, never WHO or HOW.** The heartbeat table `cron_runs` has exactly five columns (`id, kind, firedAt, tickMinute, isBatchTick`, `prisma/schema.prisma:1688-1697`). Every insert writes only `kind` + time. **There is no column for User-Agent, source IP, the `x-vercel-cron` header, or which auth branch succeeded.** So the caller's identity cannot be read from stored data, and I have no access to Vercel or Railway request logs. **The identity of the live caller is therefore INFERRED from the timing signature plus the code, not proven from a logged header.** That inference is strong (below), but this is the one thing that could not be proven directly, and I say so plainly rather than dress timing as proof.

## PART 1 — who invokes each cron

There are **12 cron routes**. Only **three kinds ever write a heartbeat**: `lifecycle`, `tracking`, `watchdog` (plus a defunct `tracking-timeout`, last seen 2026-06-15). The other nine leave no heartbeat, so their live status cannot be read here (flagged below).

### tracking (the money cron) — a SEPARATE Railway cron service, unaffected

BL-633 established, and the timing confirms, that tracking runs as its own Railway cron service whose start command is `tsx scripts/run-tracking-cron.ts`; that script calls `runDueTrackingJobs(...)` **in process** (not over HTTP). Live: it fired at `11:50:27`, `11:40:41`, `11:30:15`, `11:20:27`, `11:10:11` UTC, on scattered seconds and off-cadence minutes (e.g. minute 2, minute 11 seen earlier). That jitter is the signature of a per-tick worker, and it did **not** change at 09:30. Tracking is healthy and never touched Vercel. It is CRON_SECRET-bearer only (`tracking/route.ts:56-65`, no `x-vercel-cron`).

### lifecycle and watchdog — MIGRATED off Vercel today, timestamped

These two are the only routes that accept the `x-vercel-cron` header (`lifecycle/route.ts:31`, `watchdog/route.ts:74`, header checked FIRST, bearer second). Their firing timing shows a clean, two-stage regime change today:

| Window (UTC, 2026-07-24) | Seconds past the scheduled minute | Reading |
|---|---|---|
| through **09:30:00.718** | **0.28 to 0.92** (sub-second) | Vercel Cron signature (fires within ~1s of the minute) |
| 09:45 to 10:30 | **~21.5** (dead-consistent 21.50, 21.51, 21.52) | a new scheduler, first phase |
| 10:45 onward | **~9.27** lifecycle / **~9.5** watchdog (dead-consistent 9.27, 9.27, 9.28) | the same scheduler after a restart re-phased it |

The last sub-second fire was lifecycle `09:30:00.718`; the very next was `09:45:21.503`. **No fire was missed**: lifecycle stayed 4 per hour, watchdog 2 per hour, through the transition (so the watchdog never had to alarm about itself). The switch was deliberate and seamless.

**Why ~9.27 seconds, dead-consistent, is the Railway in-process scheduler and not Vercel.** `railway-cron-scheduler.ts:177` ticks on a `setInterval(..., 30_000)` started at process boot; it is not minute-aligned. A job due at `:45:00` fires on the first 30s tick at or after `:45:00`, which lands at a FIXED offset determined by the boot phase modulo 30s. Because 15 minutes is exactly 30 ticks, every `:00/:15/:30/:45` lifecycle fire inherits the same offset, which is why it is nailed to 9.27s. A process restart re-phases the tick, which is exactly the one-time jump from 21.5s to 9.27s. Vercel Cron, by contrast, fires sub-second every time; an external HTTP pinger fires near the minute with random jitter, not a fixed 9.27s. **Only the 30s-tick in-process scheduler produces this signature.**

**Is a live Vercel deployment still running these crons? No.** Two independent facts: (a) the sub-second Vercel signature ended at 09:30 and has not returned; (b) there is **exactly one lifecycle fire per 15-minute slot** (10:45, 11:00, 11:15, 11:30, 11:45 = one each), not two. If a Vercel project were still firing lifecycle alongside Railway, every slot would show a doubled heartbeat. It does not. So a single scheduler is live, and its signature is Railway's.

**What `vercel.json`'s presence actually means: nothing, on its own.** `vercel.json` still exists at the repo root (last committed `2026-07-12T23:58`, declaring 5 crons: `expire-deadlines */10`, `notifications-cleanup 0 4`, `watchdog 0,30`, `counter-recompute weekly`, `lifecycle */15`). A `vercel.json` in a git repo is a config file; it only runs crons if the repo is actually deployed to a Vercel project with cron enabled. The timing proves that whatever Vercel deployment was firing lifecycle and watchdog stopped doing so at 09:30 today. The file is now describing a scheduler that is no longer the live one.

**Is `RAILWAY_NATIVE_CRON` genuinely unset, and what does the scheduler do?** It was unset when BL-652 measured at 09:50 (its sub-second data is the Vercel era). The timing shift indicates it was **SET at ~09:30 to 09:45 today**, re-enabling the in-process scheduler. I cannot read the current production value directly (it is a Railway env var, not in the repo or the DB; it is absent from local `.env.local`, which is only the dev environment). But BL-593 records its historical value was literally `"lifecycle,watchdog"`, which is exactly the two jobs whose timing changed. At runtime, `instrumentation.ts:14-20` starts the scheduler only when the trimmed var is non-empty; when set, `startRailwayCronScheduler` ticks every 30s and `fireJob` (`railway-cron-scheduler.ts:129-144`) calls `http://127.0.0.1:PORT/api/cron/<path>` with `Authorization: Bearer ${CRON_SECRET}`.

**The critical possibility the brief raised, resolved: the owner is NOT currently depending on Vercel for crons.** No Vercel cron has fired since 09:30 (no sub-second fires, no doubled heartbeats). Whether a **dormant Vercel project still exists and still bills** is a Vercel-dashboard fact not visible from here; if one does, it is now idle for crons and worth deleting to stop any charge and to close the second ingress (see PART 4). But he is not relying on running Vercel infrastructure he forgot about; he successfully left it this morning.

## PART 3 — what breaks if the `x-vercel-cron` header auth is removed

**This INVERTS BL-652.** BL-652 concluded (correctly for the Vercel era) that deleting the header would 401 lifecycle and watchdog. Now that both fire via the Railway scheduler's bearer, **removing the `x-vercel-cron` branch would NOT break them** — they would still pass on the bearer. The header is now effectively removable dead code for the live path.

Only two routes even read the header, so only these two could be affected, and both would survive on the bearer:

| Job | If it stopped | How long unnoticed |
|---|---|---|
| lifecycle (growth engine, marketing email) | no lifecycle emails sent | days (owner would notice an engagement/send drop, not immediately) |
| watchdog (CRON_DOWN alarm) | outages stop being detected | indefinitely and silently, the worst case |
| tracking (views + earnings) | views and earnings freeze | hours (clippers and the owner notice money going stale) |
| retire-dead-clips | dead clips keep polling, cost creep | weeks |

**Does the watchdog catch its own death? No.** BL-566 established the watched set is built from the `RAILWAY_NATIVE_CRON` allowlist plus tracking. A watchdog cannot detect its own silence, and nothing else watches it, so if the watchdog stops there is no alarm. That gap is inherent and pre-existing; today's migration did not exercise it because no fire was missed.

**The caveat that keeps this safe:** the conclusion that the header is dead rests on the inference that the live caller uses the bearer. Confidence is high (30s-tick signature, no doubling, scheduler code, CRON_SECRET provably set), but it is not a logged header. So the header must be PROVEN dead before it is removed (PART 4), not assumed dead.
