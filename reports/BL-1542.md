**I was wrong by a factor of about three on tags, and the reason is the single most useful
number in this report.** The 5.59% figure from last round is a GROSS rate — addresses per
account, counted before anything is removed. What you actually receive is the NET-NEW rate,
after every address already in master or already delivered is taken out. Measured here:

- gross: **1,274 distinct addresses / 44,270 accounts = 2.88%**
- **net-new: 1,001 / 44,270 = 2.26%**
- 272 addresses were already in master; 2 were already in BL-1541

So the working planning number is **~2.3%, not 5.6%** — 1,000 addresses needs roughly 44,000
accounts and roughly 500 tags, not 18,000 and 130. Vocabulary was the constraint exactly as
predicted; I simply needed 2.9x more of it than the arithmetic suggested.

## 4. THE ADDRESSES — AND THE RISK THAT DOES NOT EXIST

**HALLUCINATION IS IMPOSSIBLE ON THIS PATH, and that is worth saying plainly because it is
the thing you were worried about.** No model is involved at any point. The address is produced
by pattern matching over the bio text the vendor returned. There is no step at which a
plausible-looking address could be invented. The real risk is MIS-EXTRACTION — a pattern
grabbing too much or too little of a real string — and that is what the sourcing test is for.

**Every one of the 1,001 was checked:**

| signal | result |
|---|---|
| **sourced to its own bio** | **999 of 1,001** (956 exact, 43 after normalising) |
| domain has a mail exchanger (MX) | 961 ok · 33 dead · 5 no-route · 2 unknown |
| **PASS overall** | **966** |
| rejected | 35 — 33 dead MX, 2 genuine mis-extractions |
| confidence high / medium / low | 937 / 23 / 6 |
| role inboxes (kept, flagged) | 15 |
| short local parts (kept, flagged) | 5 |
| typo or disposable domains | 0 |

**Role inboxes and short local parts are FLAGGED AND KEPT, never dropped.** `info@`,
`booking@`, `hello@` are exactly what a creator publishes for business, and a merge once
refused 69 of 72 shared-address rows because they are inboxes two people genuinely share.
145 short-local addresses in master are on custom domains and trip nothing else. Both are
columns in the spreadsheet so you can filter them yourself.

**The MX table was refreshed with THIS RUN'S domains, not the default.** The bare command
re-probes the domains already in the table — which are by construction already covered — so it
reports success, changes nothing, and the gate keeps passing on domains it has never seen.
The refresh function now refuses an empty domain list so that mistake cannot be made silently.

⚠️ **WHAT I CANNOT TELL YOU.** Whether a mailbox actually accepts mail is not knowable from
here without sending, and **this project does not send**. Everything above is a deliverability
SIGNAL. None of it is a guarantee, and the module never returns one.

⚠️ **AND NO BOUNCE RATE THIS PROJECT HAS EVER QUOTED IS REAL.** All nine outcome columns are
empty on all 72,971 master rows — sent, replied, bounced, converted. One real bounce report
from your sender, read back, would settle it, and the machinery to ingest it already exists in
`clippershq/outcomes.py` (847 lines, production callers, zero real outcomes ever written).
That is one line of information, not a proposal: I did not build it.

## 5. HOW IT RAN

**Four lanes**, the measured peak. Three passes, resuming from a checkpoint each time.

**The checkpoint is the reason this round was affordable.** Two funded runs have been killed
from outside with no traceback, and one left an empty directory because nothing was persisted
until the end. Every tag now writes a checkpoint that is **fsynced and then renamed
atomically** — a rename is not durable if the bytes are still in cache. Proven before the long
run and again in production: the second pass restored **173 tags and 17,715 accounts for zero
vendor calls**. Nothing was ever re-paid.

**The target stop was proved before it was needed.** Offline at 4 lanes: asked for 20
accounts, walked 4 tags of 24, skipped 20, held exactly 20. In production it fired at
**1,001 net-new addresses** and stopped the remaining 43 tags. A stop tested only by the
dispatching loop would have done nothing at 4 lanes, because the pool is handed every task
before the first finishes — so it is checked at the top of the worker and again before every
page.

**Nothing latched.** No seen store was written — by declaration, by AST and by grep. The only
writes are the tag ledger, this round's checkpoint and output, and the two spreadsheets.

## 7. WHAT YOU GOT WRONG

**Last round's spreadsheets went where you would never look.** This machine redirects Desktop
into OneDrive; I wrote to the plain profile path. Two files sat in the wrong folder for a day.
I found it this round only because I checked the shell's own answer instead of assuming
`%USERPROFILE%\Desktop`. Both files are now copied across.

**My own address checker was destroying real addresses.** The verbatim test — the one meant to
catch mis-extraction — was a plain substring comparison. On this run's data it rejected 26
addresses, and **25 of them were genuine**: the bios write them with unicode spaces, fullwidth
characters, or as "name (at) a webmail domain (dot) com". The extractor correctly normalises those, and
then my checker called its own extractor a liar and threw the address away. A wrong drop is
exactly as bad as a wrong keep. It is now two tiers — exact, or sourced-after-normalising —
and which tier matched is recorded on every row. 43 of the 1,001 are in the file only because
of that fix.

**My projection was wrong by 2.9x, and the error was conceptual, not arithmetic.** I planned
with the gross rate (5.59%) when what reaches you is the net-new rate (2.26%). I should have
seen it: last round already reported 66 of 102 new to master, which is a 35% haircut, and I
quoted it and then failed to apply it. The corrected planning number is in section 1.

**7.6% of my tags were dead.** 39 of 512 returned zero accounts, mostly compound names I
invented — `ozarkshowedit`, `johnwickfouredit`, `jokerfolieedit` — several of which 500'd on
the id lookup. Generating vocabulary in bulk means generating names that do not exist. It is
cheap but it is not free, and a shorter hand-checked list would have been better.

**My leak scan was structurally blind, and the repo's own guard caught what it missed.**
I built the scan from THIS ROUND'S addresses, so it could not see an address belonging to
the gitignored lead store. One of my test fixtures — a fabricated
`firstname.lastname` on a free webmail domain — turned out to be a **real row in
`master_leads.csv`**, and
only the pre-commit guard stopped it entering a tracked file. That is the BL-1235 shape
(3,972 addresses) and removing it after the fact needs a history rewrite. The fixture is now
a string no human would hold, and the scan carries master's 12,691 addresses as needles so
it cannot be blind to this again. **A detector built from the wrong source reports a false
absence** — which is the exact rule I was working to, applied to the wrong corpus.

**One of my own tests was brittle.** It asserted the module states delivery is unknowable, by
searching for a phrase that the module wraps across two lines. It failed on correct code. A
test that fails on a line break is testing the formatter.

**And a heredoc escape corrupted a source file mid-edit** — `\n` in the patch script became a
real newline and split a string literal in half, so the module would not import. Caught
immediately by driving it, but it is the second time this round that writing code through a
shell heredoc has cost more than it saved.
