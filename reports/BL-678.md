## Why two calls instead of one

BL-677 asked for one call. An offline pass over the corpus first — free, no network — found something that made a *controlled pair* worth the extra $0.0006:

> On licensed reels, `best_audio_cluster_id` and `music_info.music_asset_info.audio_cluster_id` are **not the same value on 7 of 20 licensed clips** (13 match, 7 differ).

That turns a single call into a genuine experiment. Pick one reel where the two ids differ, resolve **both**, and whichever comes back tells you what the endpoint actually keys on. The reel chosen carried a known licensed track — *The Winner Takes It All* by ABBA — so the response could be checked against ground truth rather than merely inspected.

| | value | source field |
|---|---|---|
| **A** | `834176079344037` | `clips_metadata.audio_ranking_info.best_audio_cluster_id` |
| **B** | `1825128190912080` | `clips_metadata.music_info.music_asset_info.audio_cluster_id` |

## Gap 1 — does the provider strip `media_count.clips_count`?

**No. It passes through as an exact integer.** Both calls returned it, unmodified, at `response.media_count`:

| call | `media_count` | `formatted_media_count` |
|---|---|---|
| A | `{"clips_count": 5584, "photos_count": 0}` | `"5.5K reels"` |
| B | `{"clips_count": 837493, "photos_count": 0}` | `"837K reels"` |

The assumption BL-677 could not verify locally is now verified live: the provider is a faithful passthrough for this field.

**The localisation trap is now demonstrated, not just cited.** Even in English the formatted string is lossy — `"5.5K reels"` against a true 5,584 is a 1.5% error, and `"837K reels"` discards 493. Parsing the display string would inject rounding error before any localisation issue arose. Read `media_count.clips_count`; never touch `formatted_media_count`.

Note the same lossy string is repeated inside the metadata block as `formatted_clips_media_count`, so there are **two** display-string traps in one response, not one.

## Gap 2 — does `best_audio_cluster_id` work as `track_id`?

**Syntactically yes — semantically no, and this is the finding that matters.**

Both ids resolved. Neither 404'd. So `best_audio_cluster_id` "works" in the narrow sense that it is an accepted `track_id`. But the two resolved to **different audio entities**, and the metadata proves which is which:

| call | resolved to | populated metadata branch | `clips_count` |
|---|---|---|---|
| **A** — `best_audio_cluster_id` | the reel's **original sound** (`original_audio_title: "Original audio"`, carries `audio_asset_id`, `original_media_id`) | `metadata.original_sound_info` | **5,584** |
| **B** — asset `audio_cluster_id` | the **licensed track** — `title: "The Winner Takes It All"`, `display_artist: "ABBA"` | `metadata.music_info.music_asset_info` | **837,493** |

**The licensed track has 150× more reels than the reel's own audio cluster.**

So on a licensed reel, `best_audio_cluster_id` does not identify the song. It identifies *that reel's own uploaded audio object*. Keying a popularity signal on it would understate a licensed track's reach by two orders of magnitude — and would do so silently, because the call succeeds and returns a plausible-looking integer.

**This also explains the 100% fill rate that BL-677 flagged as suspicious.** The suspicion was correct. `best_audio_cluster_id` is populated on every clip regardless of audio type precisely *because* it is not a track identifier — it is the reel's own audio cluster, which always exists. A field that is never missing is not evidence of good coverage; here it was evidence that the field answers a different question.

Confirming detail: the licensed track's own response reports `audio_ranking_info.best_audio_cluster_id = 834176079344037` — pointing back at the original-sound cluster. The field is a cross-reference/ranking pointer, not an identity.

### The routing rule this implies

```
audio_type == licensed_music  ->  track_id = music_info.music_asset_info.audio_cluster_id
audio_type == original_sounds ->  track_id = audio_ranking_info.best_audio_cluster_id
```

The licensed branch is only available on the ~⅓ of clips that carry `music_info`. For the original-sounds majority, `best_audio_cluster_id` is the correct and only key — and there it is genuinely the right answer, because the reel's audio cluster *is* the audio.

## Gap 3 — what else the response carries

This is not a track-metadata endpoint. **It is a reels-by-audio feed**, and that is materially more useful than the schema assumed.

`response` top-level keys (15 on the licensed call, 14 on the original-sound call):

```
audio_page_reporting_id      audio_page_segments        audio_ranking_info
auto_created_reels_preview_metadata               available_tabs
formatted_media_count        is_music_page_restricted   items
media_count                  metadata                   music_canonical_id
paging_info                  status                     status_code
spotify_track_metadata   <-- licensed call ONLY
```

Worth capturing in the clip-library schema:

- **`items` — 12 full media objects per page.** Real reels using the audio, each with `play_count` / `ig_play_count`, `like_count`, `comment_count`, `reshare_count`, `media_repost_count` and full `clips_metadata`. Observed play counts on the licensed page ranged from ~126K to ~6.17M. This makes the endpoint a **discovery surface**, not just a lookup: one call yields both the popularity integer and a page of high-performing reels that used the sound.
- **`paging_info` → `max_id` + `more_available`**, and an envelope-level `next_page_id`. The feed paginates.
- **`music_consumption_info.is_trending_in_clips` → `true`** on the ABBA track. A free trending flag, distinct from raw count.
- **`music_asset_info`** carries the full track record: `title`, `display_artist`, `artist_id`, `ig_username`, `duration_in_ms`, `is_explicit`, `has_lyrics`, cover artwork URIs, `highlight_start_times_in_ms` (`[124000, 249000, 109000]` here), and download URLs for the audio itself.
- **`original_sound_info`** (original-sound branch) carries `original_audio_title`, `audio_asset_id`, `original_media_id`, `ig_artist`, `duration_in_ms`, `should_mute_audio`, `progressive_download_url`.

### The unexpected find: a direct Instagram → Spotify bridge

The licensed response carries a populated `spotify_track_metadata`:

```json
{"spotify_track_id": "3oEkrIfXfSh9zGnE7eBzSV",
 "spotify_listen_uri": "https://open.spotify.com/track/3oEkrIfXfSh9zGnE7eBzSV?..."}
```

This is an **exact Spotify track ID**, not a fuzzy title match. It matters because an earlier research round established that Spotify's audio-features endpoint has been unavailable to new applications since late 2024, which pushed genre/mood enrichment toward matching on `title` + `artist` strings — lossy for remixes, live versions and re-releases. An exact ID removes that ambiguity for whichever catalogue is used downstream.

Caveat, stated plainly: **observed on one licensed track.** Fill rate across the licensed corpus is unmeasured, and the key is absent entirely from the original-sound response. Treat as a strong lead, not a guarantee.

## The three traps, as they now stand

| trap (BL-677) | status after this round |
|---|---|
| Never regex the formatted count — it is localised | **Demonstrated, and worse than described.** Even English is lossy (`"5.5K reels"` vs 5,584). There are **two** such strings per response. Read `media_count.clips_count`. |
| The provider bills 404s; only 5xx are free | **Not exercised** — both ids resolved, so no 404 was observed and no negative-cache behaviour was tested. The billing rule stands on the spec and remains the correct implementation constraint. |
| Degrade to UNKNOWN, never to zero | **Reinforced by a new failure mode.** The original risk was a *missing* count. This round found a worse one: a *present, plausible, and wrong-by-150×* count returned by a successful call. UNKNOWN-on-missing is necessary but not sufficient — the routing rule above is what prevents the silent error. |

---

## Implementation notes

1. **Route by `audio_type` before choosing the id.** Using `best_audio_cluster_id` unconditionally is the trap this round found.
2. **Negative-cache dead ids.** 404s bill. A retry loop over dead audio ids bills every attempt.
3. **A missing or unroutable count is UNKNOWN, never 0** — consistent with the pipeline's standing "UNKNOWN never cuts" policy.
4. **Do not parse either display string.** Two exist per response.
5. **Consider the feed, not just the count.** The same billed call returns 12 reels with full engagement metrics; treating it as a scalar lookup wastes most of what was paid for.
