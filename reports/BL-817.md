### The write log

The premise that "backup timestamps are the write log" is **half right, and the wrong half is load-bearing**: `shutil.copy2` **preserves the source mtime**, so a backup file's mtime is when master was last written *before* the backup — not when the backup was taken. Only the timestamp **embedded in the filename** is the write time. Reading mtimes here produces a badly wrong timeline.

## The real defect: it locked a file no other writer uses

`scratch/bl806_remove_dead.py:26`

```python
with filelock.file_lock(filelock.lock_path_for(MASTER), timeout=60):
```

`file_lock()` already appends `.lock` internally (`filelock.py:99`, `lp = lock_path_for(path)`). Passing it a path that is *already* the lock path appends `.lock` a second time:

```
lock_path_for(master)                        = master_leads.csv.lock
what file_lock(master) locks                 = master_leads.csv.lock        <- every other writer
what file_lock(lock_path_for(master)) locks  = master_leads.csv.lock.lock   <- this script, alone
```

**So the script held an exclusive lock on a file nothing else contends for, and rewrote 58k rows with the real master lock free.** The stray `master_leads.csv.lock.lock` sidecar, created 22:37:26, is the physical fingerprint.

This is worse than simply forgetting to lock, because it **reads as correct in review** — the import is there, `file_lock` is there, a timeout is there, and the docstring says *"Done UNDER THE CROSS-PROCESS LOCK"*. Only evaluating the argument reveals it.

It is the **only** instance in the tree:

```
$ grep -rnE "file_lock\(\s*(filelock\.)?lock_path_for" clippershq/ scratch/ tools/
scratch/bl806_remove_dead.py:26
```

**Nothing was corrupted by it.** It ran while no other writer was active, and its write was atomic (temp → `os.replace`). The exposure was real; the outcome was luck.

## Can two agents safely measure at the same time?

**Yes for correctness, no for a stable denominator — and those need different fixes.**

`crossdedup.append_leads` writes temp → `fsync` → `os.replace` (`crossdedup.py:389-399`). `os.replace` is atomic on the same filesystem, so **a reader never sees a half-written master**. It gets the old file or the new one, complete. The two deferred rounds were not at risk of reading corruption.

What they *were* at risk of is real: master changing **between** two reads inside one measurement, so a percentage gets a numerator from 58,325 rows and a denominator from 58,324.

**Cheapest fix: a read snapshot.** One line at the top of any measurement:

```python
shutil.copy2("master_leads.csv", snap)   # then read `snap` for the whole round
```

Ranked against the alternatives:

| option | cost | verdict |
|---|---|---|
| **read snapshot** | one line, no coordination, no lock held | **recommended** |
| lock-aware read helper | shared code + holds the lock during a slow read, blocking writers | heavier, and blocks the thing you did not need to block |
| documented quiet window | needs humans/agents to coordinate; two rounds already failed to | weakest — it is the thing that just did not work |

A snapshot also survives the `crawl_suggested.py` hazard, because it is immune to *how* the writer writes.

**Not recommended, and worth saying:** taking the master lock for reads. Reads are frequent and slow (58k rows, 24 MB); writes are rare and fast. Locking reads would make readers the contention point to solve a problem atomicity has already solved.

## What I did not do

I did not implement anything, per the brief. Three fixes are queued by this report and none were applied:

1. **`scratch/bl806_remove_dead.py:26`** — one-character-class fix, `file_lock(MASTER)`. The script has already run and is unlikely to run again, so this is low urgency but should not be copied as a pattern.
2. **`filelock.file_lock()` could refuse a path ending in `.lock`** — the defect is only detectable by argument inspection, and a two-line guard would make it impossible. This is the change with the best ratio.
3. **`crawl_suggested.py`** — route through `crossdedup.append_leads`, or take `file_lock`. Latent only while a config flag stays false.

## Honest limits

- **A live paid run (`bl806_grow.py`, PID 32932) was executing throughout this audit** and had not yet written. Master was byte-identical at the start and end of my measurements, so the findings are internally consistent — but the timeline stops at 23:03:57 and that process will append after it.
- **I reconstructed the write log from backup filenames and file mtimes, not from an audit log**, because none exists. A write that took no backup and left no lock artefact would be invisible to this method. The 22:38:05 event was only attributable because the wrong lock file happened to leave a fingerprint.
- **"Nothing was corrupted" is an inference, not a proof.** I verified the one write that happened produced exactly the intended one-row delta with an identical header. I did not checksum all 58,324 rows against an independent copy.
- The unlocked-writer sweep is static analysis over `clippershq/`, `scratch/` and `tools/`. A writer that builds the master path dynamically would be missed.
- I did not inspect the two `http.server` processes beyond their command lines; they serve an unrelated directory and were assumed irrelevant on that basis.
