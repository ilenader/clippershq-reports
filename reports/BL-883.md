## The tool: built, raced, and proven

`scratch/bl883_backfill.py`. It does not run, but it is finished and it is safe.

**Two phases, and the lock is only in the second.** Phase A runs the VAD on a read-only
snapshot — 35 minutes, no lock. Phase B takes the shard lock, **re-reads inside it**, merges
by `clip_id`, writes temp → fsync → `os.replace`, releases. Holding a cross-process lock for
35 minutes would block every other round's appends for 35 minutes: that is a denial of
service dressed as safety.

**Merge, never rewrite.** A backfill that writes back a snapshot deletes anything appended
between the read and the write — worse than a torn append, because it is silent. Merging by
key means a row BL-867 appends during phase A is present at merge time, keeps its own
values, and simply is not backfilled. It does not need to be: MEMEBOT-035 made new rows
carry these fields.

**The race, run for real** — a second thread taking the same lock and appending flat out
while merges run into it:

```
appends made by the concurrent writer : 34
merges run against it                 : 12
final rows in the shard               : 74
appended rows LOST                    : 0
original rows still present           : 40/40
corrupted/unparseable lines           : 0
```

### My first guard was decoration, and the test caught it

I wrote a guard comparing `len(after)` to `len(before)`. **`after` is built from `before`, so
they are equal by construction and it could never fire.** The planted-failure test showed it
writing anyway — which is the only reason I know. A guard that cannot fail reads as coverage
and is worse than none; I said exactly that about someone else's code in MEMEBOT-030.

The guard now counts the **bytes actually written**: the temp file is re-read and its lines
counted before anything is replaced. Planting a real serialisation loss — one record
serialising to whitespace, which the reader skips and which raises nothing anywhere:

```
refused: refusing to write clips-2026-01.jsonl: read 74 rows under the lock
         but the replacement holds 73. The original file is untouched.
original file unchanged after the refusal: True
```

**Derivation token: `80904b03`**, computed from `clip_speech`'s own thresholds
(`SPEECH_PRESENT_MIN`, `BED_PRESENT_DBFS`, `SILENT_DBFS`, `SR`). It is computed in the
backfill rather than added to `clip_library.DERIVED_FROM` because that dict versions only
`format` and lives in `clip_library.py`, **held by BL-849 and BL-867 for this entire round** —
and because BL-856's own note says a detector-derived field's token has to come from the
detector's module, not from the library's thresholds.

## 5. The branch fires — and my explanation of why it never did was wrong

```
BEFORE -- the real historical state: no audio_class on the record
   treatment='duck-under'    class=None                  why='class UNKNOWN -- defaulting to duck...'
AFTER  -- the field present, as the backfill would leave it
   treatment='keep-original' class='dialogue-over-music'  why='stored class (measured)'
```

**It fires, and it did not fire on the historical record.** Precedence is right too: a
measured class outranks the free declared one, so a real VAD run beats a payload flag.

**A correction this round owes to MEMEBOT-035.** That report said the missing declaration and
the missing write were "two failures hiding each other". For this consumer that is not true:
`clip_pipeline._f()` tries `clip_library.field()` and **falls back to a plain dict read**, by
design, so the module can also be handed raw dicts by its tests. `_f` would have read an
undeclared `audio_class` perfectly well.

**The branch was dead for exactly one reason: the field was never written.** The declaration
still had to be fixed — every consumer that calls `field()` directly needs it — but it was not
what kept this branch unreachable. I found this because my first attempt at proving item 5
un-declared the field and the branch fired anyway.

## 4. What the fallback was costing

The bed is placed under a basis: the voice when `speech_dbfs` exists, the clip **mean** when
it does not. The error is the gap, and the bed inherits it one-for-one.

**The mean has to be `edit.py`'s own probe.** `volumedetect` reads the muxed track;

## Limits

- **Nothing was backfilled.** Every fill number after the change is identical to before.
- **The race proof is synthetic** — a temp shard and a thread, not BL-867 and the real
  library. It exercises the same lock and the same merge, but at 40 rows, not 3,865.
- **The gap distribution is n=12 on the memebot corpus**, which is not the library and skews
  music-heavy (80.3% vs BL-853's ~51.9%).
- **The token is computed outside `clip_library.DERIVED_FROM`**, so `stale_fields()` will not
  see it. Wiring it there needs that file, which was held all round.
- **BL-853's class distribution is not re-measured** — that needs the backfill.
- **`clip_pipeline._f`'s fallback means declaration is not load-bearing for that module.**
  It is for others; I did not audit which.

## Method

Ran `claim.py brief` first and reported it verbatim. Established the blocker by reading a
real library row and intersecting 2,003 library shortcodes against 508 local media files —
zero overlap — rather than assuming either way. Costed the only remaining path from the real
account count. Built the merge, raced it against a live appender in a temp tree, and planted
a serialisation failure to check the guard could fail at all; it could not, which is why it
was rewritten. No paid call, no key read, no library row written.
