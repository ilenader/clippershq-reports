## What shipped

### 1. `tools/claim.py` — what a round STARTED

```
python tools/claim.py list                 # who else is working?
python tools/claim.py start BL-NNN --intent "..." --write path/a.py
python tools/claim.py end BL-NNN
```

`.claims/BL-NNN.json`, written at start, deleted at end. `will_write` holds real paths; `[]`
means read-only and needs nobody's attention — BL-818 established that contention on files you
will **write** is the only thing worth blocking on.

**Advisory by construction, not by convention.** `conflicts()` returns a list; nothing raises,
nothing waits, nothing holds a lock. The quiet-tree rule was blocking and reached 1/40 adoption,
so a blocking design was never on the table. **One file per round** — a shared registry would
reproduce, in miniature, the contention bug this prevents. Atomic write (`tmp` + `fsync` +
`os.replace`), so a concurrent reader never sees a half-written claim. A torn claim is skipped,
never fatal. Stale claims are harmless by design: they cost one glance, unlike a stale *lock*,
which blocks real work.

It pairs with `docs/CLAIMS.md` (BL-820) rather than overlapping it: that manifest verifies what
a round **finished**, at HEAD. This declares what a round **started**.

### 2. `docs/PRECONDITIONS.md` — the quiet-tree rule, formally retired

The standard, in order, with each step's measured adoption so a reader knows what is convention
and what is aspiration: **claim → back up (14/40) → per-file mtime guard (8/40) →
`git show HEAD` (2/40, newly added) → process check (5/40) → read snapshot → filelock**.

The `git show HEAD` step is the one nobody had: **mtime cannot distinguish *written* from
*survivable*.** BL-816 found four restored symbols present on disk and absent at HEAD — one
`git checkout` from destruction, which is precisely how they were lost the first time.

It also records what is **noise**, so rounds stop deferring work that was never at risk:
"modified on disk" warnings, another agent in a *different* file, master growing during a read,
another module's test going red, and building on someone's partial work — BL-815 did that
successfully. And the four genuinely-unsafe hazards: `reset --hard`, uncommitted work,
unlocked full-file rewrites, and a lock on the wrong path.

## Limits

- **Adoption is the open question, not correctness.** Every mechanism here is a convention a
  round can skip. Expect the mtime guard's curve (8/40, rising) rather than the quiet rule's
  (1/40). One other round is using it as of publication; that is one data point.
- **A claim describes intent, not reality.** A round that writes a file it never declared is
  invisible. `will_write` is a promise, and nothing audits it after the fact.
- **`conflicts()` compares normalised paths only.** Two rounds writing the same *function* in
  different files, or the same config key, will not collide.
- **Stale claims never expire.** Deliberate — a long round is not an abandoned one — but it
  means a crashed round outside the context manager leaves a claim until someone clears it. The
  CLI path (`start`/`end`) has no such protection; only `with claim(...)` self-clears.
- **The precondition doc's adoption figures come from BL-818**, which counted report *mentions*,
  not uses. A round that guarded without writing it down is uncounted, so those are floors.
- **`.claims/` is gitignored**, so claims are visible only to agents on this disk — correct for
  in-flight state, but a remote clone sees nothing.

## Method

Read BL-818 and BL-817 first, then **checked disk before writing** — which is how the four
already-done items were found. Established a per-file mtime guard on the paths I intended to
write (two did not exist, so contention was impossible; `.gitignore` was 176 minutes quiet) and
took timestamped backups of `config.json`, `spend.json` and `master_leads.csv` with the
timestamp in the **filename**, per the `MASTER_WRITES.md` mtime trap. Claimed the round through
the tool being built, exercised the conflict path against a simulated second claim, and cleared
it at the end. Staged five paths explicitly by name — never `git add -A` — and scanned the
staged diff against every `config.json` string value ≥12 chars; the single match was
`caption_seen.json`, a pre-existing `.gitignore` line adjacent to my addition, not a credential.
`git -C .` throughout; no `reset`, no amend. No key was read, printed or logged.
