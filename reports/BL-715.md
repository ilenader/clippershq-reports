## 1. Stop scraping pages that can never carry the answer

BL-701 measured the waste; this quantifies exactly what the fix removes. Counting **actual HTTP requests** (not log lines) in today's two Spotify runs, from 15:19:

| host | requests | why it was fetched 11 times per artist |
|---|---|---|
| en.wikipedia.org | 738 | a Wikipedia URL in an artist's Spotify `external_links` was chosen as "their own website" |
| static.assetlab.io | 163 | tag loader, scraped off a linktree page |
| ib.adnxs.com | 154 | ad exchange |
| connect.facebook.net | 140 | Facebook SDK loader — `_classify_social` only knew `facebook.com`, not `.net` |
| api.consentjs.datagrail.io | 94 | cookie-consent API |
| wikipedia.org / fr.wikipedia.org | 88 | as above |
| graphql.api.rye.com | 33 | commerce API |
| www.googleadservices.com | 19 | ad serving |
| **total** | **1,448 of 6,112 = 24%** | |

The mechanism was `SITE_PAGE_BUDGET = 11`: whatever host got picked was fetched at `/`, `/contact`, `/about`, `/imprint`, `/impressum`, `/kontakt`, `/booking`, `/legal`, `/terms`, `/privacy`. 738 ÷ 11 ≈ 67 artists sent down a Wikipedia hole.

**The fix is one predicate, `enrich_links.is_junk_scrape_host()`, used in two places** — the hop-2 chooser *and* `site_contacts` itself. Two call sites on purpose: `site_contacts` is a public entry point (Spotify, Twitch and YouTube all call it with a site they picked themselves), so a Wikipedia URL arriving directly from `external_links` never passes through the outbound chooser at all. It covers four families:

- CDN / analytics / ad-exchange / consent hosts — extended with every host measured above
- **reference and music databases** — new: wikipedia/wikimedia/wikidata, fandom, imdb, discogs, allmusic, last.fm, musicbrainz, genius, songkick, setlist.fm, bandsintown, rateyourmusic. These *do* publish contact addresses, which is exactly what makes them dangerous
- affiliate / brand / storefront / file hosts (already existed)
- **`bio_parser.PLATFORM_HOP_DOMAINS`** — the repo-wide platform list that was already policy everywhere else. Matched on exact domain or subdomain, never substring, so `discord.com` cannot swallow `notdiscord.community`

**Measured after:** `site_contacts("https://en.wikipedia.org/...")` performs **0 fetches, was 11**. A real artist site still walks its full 11 pages, verified against `lophiile.co`, `naffrecordings.com`, `unitedmasters.com` and a `.de` site with an `/impressum`.

### The page-size cap

`MAX_PARSE_CHARS = 250_000`, applied in `fetch_link` — a `Content-Length` pre-check plus a truncate on the decoded text (the truncate is what matters, since most replies are chunked or compressed and carry no usable length).

BL-701's cost curve was 0.31s at 88KB against 9.23s at 1.8MB for one 11-page `site_contacts` call. Re-measured here with the network stubbed out entirely, so this is pure CPU:

| page | uncapped | capped |
|---|---|---|
| 321 KB | 1.14s | 1.03s |
| **1.3 MB** | **5.33s** | **0.97s** |

**5.5× less GIL-held CPU on a large page**, and no effect on ordinary ones. An email that appears only past 250 KB of a single page is not worth 8 seconds of a shared core.

## 2. A lookup can no longer outlive its own watchdog

The pathology BL-701 named: watchdog 30s, worst-case lookup 37.8s = `(1.1 pace + 10 timeout + 1.5 backoff) + (1.1 + 10 + 3.0) + (1.1 + 10)`. The watchdog fired first, the worker was abandoned, the pool refilled, and the replacement blocked on a limiter the abandoned thread still held — for work that was then discarded.

**`musicbrainz.LOOKUP_BUDGET = 20.0`**, a hard total across pacing, every attempt and every backoff. Enforced three ways: the loop stops when the budget is spent; the socket timeout is clamped to what remains; and a backoff that *would* overrun is skipped rather than taken.

Deliberately **not** fixed by raising the watchdog — that lengthens every stall instead of ending it.

**Measured:** an opener that always times out now returns `('', 'failed')` in **20.0s**, against 37.8s before. A regression test asserts `LOOKUP_BUDGET < spotify_finder.DEFAULT_SPOTIFY_MAX_SECONDS_PER_ARTIST`, so if either constant ever moves the wrong way the suite fails rather than the funnel.

## 3. The lock no longer spans the sleeps

The rate limit exists to honour MusicBrainz's ~1 req/sec courtesy ask to a free CC0 service. That is correct and is preserved exactly. What changed is that it no longer serializes *waiting*.

**One lock became two, each held briefly:**

- `_state_lock` — guards the counters only. Microseconds, never across I/O or a sleep.
- `_inflight` — guarantees at most one request to MusicBrainz at a time. Held across `opener()` and a residual pace bounded by `min_interval`.

Callers now **reserve** a send slot under `_state_lock` (`t = max(now, next_at); next_at = t + min_interval`), then sleep to their own slot **outside every lock**, then send under `_inflight`. Slots are min_interval apart by construction, so N waiting threads wait *concurrently* instead of in series. All backoff sleeps are outside every lock.

One subtlety worth recording: the reservation alone is not sufficient. If a request overruns its slot, several callers can come due while it holds `_inflight` and would fire back-to-back the moment it releases. A residual re-check against the *actual* last send closes that, and it is bounded by 1.1s — not by a socket timeout. That re-check runs in a bounded 3-iteration loop because `time.sleep()` returns early on Windows: it undershot by ~7ms, which put one measured gap at 1.093s against a 1.100s floor. One extra pass makes the floor unconditional.

**Proof, matching the prior round's acceptance test — 40 calls across 8 threads:**

```
requests sent    : 40
max in flight    : 1          <- the one-at-a-time guarantee holds
min gap          : 1.1090s    floor 1.1000s
gaps < 1.1s      : 0          <- ZERO VIOLATIONS
elapsed          : 43.3s      (39 x 1.1 = 42.9s floor)
effective rate   : 0.924 req/s   (MusicBrainz asks <= 1.0)
```

Lock hold time falls from up to **37.8s** to at most **~11.1s** (one 10s request plus a ≤1.1s residual).

## 4. The limiter is visible — and it answered the open question on the first run

BL-701's main GAP: nobody could tell whether MusicBrainz was actually returning 429/5xx during the stalls, because this is the only network call in the funnel using stdlib `urllib`, which has no logger. A 470-second stall looked identical to a hung process.

`musicbrainz.py` now logs to the app's own `clippershq` logger, so it lands in `logs/run.log` beside everything else: lookup start, every retry **with the HTTP status**, circuit-breaker opening, budget exhaustion, and slot waits over 2s. Verified end-to-end through the real `main.setup_logging()` (into a temp dir, so the production log was not polluted).

**The GAP is closed. MusicBrainz is returning HTTP 503.** From the very first live re-measurement:

```
musicbrainz: transient HTTP 503 on attempt 1/3 for artist 41A9WSBy51jtVHKO6VCeN0
musicbrainz: transient HTTP 503 on attempt 1/3 for artist 2datC2OML2YxykP6vnDRmg
musicbrainz: transient HTTP 503 on attempt 1/3 for artist 6HL912h0I4WSdVWuArkUSc
   ... 13 of them in one 30-artist run
```

It is **bursty**: 13 occurrences in the first run, **1** in an identical second run minutes later. So the stalls were a real upstream degradation, not a local bug — and it is now self-reporting rather than silent. Nothing logged carries a URL or a credential; MusicBrainz needs none, and the only identifier emitted is a public Spotify artist id.

## 5. Concurrency, re-measured on the real thing

Commit `1503f80`'s 7.5× came from a 60-artist **offline fixture** — no MusicBrainz limiter, no site scraping, i.e. exactly the part that parallelizes and none of the parts that do not.

Re-measured **live**, same 30-artist seed pool for every setting, related-expansion off so the worklist is identical, handle-resolution off so the run costs **$0**:

| concurrency | run 1 | run 2 | speed-up vs 1 |
|---|---|---|---|
| 1 | 44.7s | 24.1s | 1.00× |
| **3** | **30.3s** | **22.7s** | 1.48× / 1.06× |
| 6 | 29.8s | 22.6s | 1.50× / 1.07× |

**6 buys 1.02× and 1.00× over 3 — nothing.** The binding constraint is one global 1 req/sec limiter that no amount of concurrency can widen: of the 30 artists, 21 cleared the listener floor and reached MusicBrainz, so ~23s of a ~23–30s run is that serial floor.

**Default lowered 6 → 3**, in `config.json` and in `control.py`'s fallback so a fresh clone gets it too. Extra workers past 3 only deepen the queue on the limiter and widen the abandoned-thread exposure BL-701 documented.

The between-run variance (44.7s vs 24.1s at the same setting) is the 503 bursts, not the pool — which is why the conclusion rests on the 6-vs-3 comparison *within* each run rather than on absolute times.

### Two process-level notes, both worth recording

**The tree was not quiet at the start, and log silence is not a safe quiet signal.** A Spotify run (`python clippershq\main.py`, PID 4024) was live. The first check watched `run.log` for silence and passed — wrongly, because log silence *is the symptom* BL-701 documented. The process was in fact burning **99.8% of one core** (7,984 ms CPU in 8,000 ms wall) across 29 threads with zero log output — a live reproduction of the GIL-bound parse plus limiter queue, and 29 threads against `concurrency=6` matches the abandoned-thread finding. Work started only after the process actually exited. **For this system, only process exit is a valid quiet signal.**

**`master_leads.csv` grew by 483 rows at 18:29:31, mid-round, and it was not this work.** The rows carry `source_hashtag=spotify_finder` and the note *"recovered from run.log (livelocked run 2026-07-29 15:19); handle paid+confirmed HTTP 200, no email"* — another agent salvaging already-billed IG handles from the killed run. The file still parses cleanly (60 columns, 56,656 rows, 0 malformed) and none of this round's files were touched by them, so ownership stayed disjoint. **Do not restore `backups/master_leads.csv.bak_20260729_182621` — it predates that salvage and would destroy all 483 recovered rows.**

## What was deliberately not done

- **`make_spotify_id_fn` still has the old single-lock shape.** It is the same bug, but it serves ListenBrainz discovery, which is off by default and runs single-threaded before the country-gated run, so the lock is never contended there. Fixing it means a second test surface for a latent issue; flagged rather than bundled.
- **The socket timeout stays at 10s.** The budget clamps it when little time remains, but the base value was not re-tuned — no measurement here justifies a number.
- **`SITE_PAGE_BUDGET` stays at 11.** The skip list removes the pathological *hosts*; whether 11 pages is the right depth for a genuine artist site is a separate question with its own yield/cost trade-off, unmeasured.
- **No before/after on a full production run.** The concurrency measurement ran with handle-resolution off and expansion off, so its seconds-per-artist is not comparable to BL-701's 4.1s. The honest claim is the component measurements above, not an end-to-end speed-up figure.
- **Whether 503s explain all of BL-701's 1,677s of silence** is still unquantified — now measurable, since the limiter reports them, but one clean production run is needed to attribute the split between the limiter and `site_contacts` CPU.
