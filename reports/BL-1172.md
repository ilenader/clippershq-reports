### Records, not rows — hand-verified three times

`scratch/bl1172_verify.py` recomputes every count by a second method that does not call
`exporters`:

```
1. CLIP LIBRARY    by hand: 9,741 rows -> 2,761 clips  (3.53x)   exporter: 2,761   MATCH
2. RENDER HISTORY  by hand: 1,429 lines = 1,381 render + 48 outcome
                            -> 801 records (1.78x)               exporter: 801     MATCH
3. LEADS           by hand: 134,702 LINES -> 60,241 CSV rows (2.24x)
                            60,241 rows  -> 60,231 PEOPLE (1.0002x) exporter: 60,231 MATCH
```

**The master figure is THREE levels, not two, and the brief's 2.24x belongs to the first
pair.** Lines→rows is 2.24x because a scraped bio containing a newline makes one person span
several lines — `wc -l` is not a row count. Rows→people is a different and far smaller fold:
measured today, **5 humans occupy 10 extra rows**. Attaching 2.24x to rows→people would
overstate the dedup by roughly 2,200x.

## 2. Runs that announce themselves

A **"Just finished"** card sits directly under "Running now", **outside every `<details>`** —
all the folds on this page are closed by default, so anything inside one is invisible, and
this block exists because he spent days watching cards and guessing.

Each announcement carries the headline, **what to do next**, leads, cost, duration, a
**download button for that run's own output**, and a link to its log. Live on the page:

```
spotify finished   2026-08-06 20:06:20   leads 1181 · cost $1.2888 · took 6668s
                   [Download spotify_20260806_200613.xlsx]  [Its log]
tiktok failed      ...                   It ran and then failed. The log says why.
```

**The four end-states are distinct, and the classification is not done in the panel.**
`run_status.cause_of` already derived them from evidence; this only renders them:

| state | what it means | what to do |
|---|---|---|
| **finished** | ran to the end | take the output |
| **hit its cap** | stopped *itself* at the dollar ceiling | raise the cap — nothing went wrong |
| **failed** | ran and raised | the log says why |
| **killed** | terminated from outside | its work is on disk; the next run resumes |

A run whose process the OS **cannot confirm** is never announced as finished, and
"never started" is excluded — it has no output to announce.

**Finding the output.** `out_path` is written to the spend-ledger marker, not to the
`run_status` record the panel reads, so it is usually absent. Rather than shrug,
`_finish_output` matches a spreadsheet in `output/` on **both** the funnel name **and** the
run's own time window — either alone picks the wrong file.

## 3. The three measured bugs

**Bug 1 — `app.js` rendered the send list from name/label/URL and never touched
`rows`, `built_at` or `stale`.** All three were being computed by
`all_bot_ready.send_list_staleness` in `/api/files` and thrown away. BL-888 built that check
*because* BL-879 caught a send list 20 hours behind master; it has been answering into
nothing ever since. Now on the page, verified in the DOM:

> **ALL_BOT_READY.csv** — 3513 people · built 2026-08-06 22:06:43
> *Current — nothing has been added to master since this was built.*

Three states for `stale`, not two: `null` renders as **"Freshness unknown — this is NOT the
same as current"**, styled as a warning, never as fresh. **And the `setHTML` signature now
carries all three** — it was `name + decoys.length`, and the primary always has the *same
filename*, so a list that went stale could never have repainted. Identical shape to the bug
that left the run log saying "reading…" forever.

**Bug 2 — `server.py` copied 15 keys off the marker and dropped `pid_created_at` and
`boot_epoch`.** Two lines. Measured before and after on a live pid:

```
WITHOUT the two keys   verdict=None   "in use by a Python but nothing recorded WHICH
                                       process it was — cannot be confirmed either way"
WITH them (fixed)      verdict=False  "pid 21728 has exited — that number has since been
                                       reused by another python"
```

BL-1150 recorded these fields and BL-1157 taught `run_status` to write them; this endpoint
declined to forward them, so the fix reached the disk and never reached the page. That is the
54-hour ghost card — the Clipboard Service shown as a live lead funnel — still armed, one
recycled pid from firing.

**Bug 3 — `_LIVENESS_SOURCES` was a hardcoded 5-file tuple.** It is now every `*.py` under
`dashboard/` and `clippershq/` — **the same set `dashboard_launcher._py_mtimes` watches**, and
a test asserts the two sets are equal so they cannot drift again. From 5 files to 100+.
`tests/test_server_freshness.py` is **green**.

Two deliberate choices: `*.py` only, because the server writes `dashboard/static/runs.json`
continuously inside a watched tree and counting it would make every server permanently
"stale"; and **static assets are now out** (`app.js` was in the old list) — a running server
does not *run* `app.js`, it re-reads it per request, so telling him to restart because a
script moved trains him to ignore the banner.

  the real DOM, not by reading the HTML.
- **0 console errors.**
- Smallest new font on the page: **13px** (the floor BL-1159 set).

**No sideways scroll — with a caveat I am stating rather than papering over.** The OS window
would not shrink below 1920px, so `resize_window` did not change the viewport and **the CSS
media query was not exercised**. I measured the same property a different way: the run panel
was clamped to 700px and its children measured — **0 cards overflow, no panel overflows**, and
the wide exports table scrolls **inside its own `.tablewrap`** (856px content in a 662px box,

**Properties kept:** zero external requests per screenshot pass; `money(null)` renders
"unknown", never `$0.000`; per-pid liveness (strengthened by bug 2); panels independent; no
credential on any endpoint; page reads never advance rotation. `/api/exports` is fetched
**once at load and on an explicit Recount button, deliberately not in the 5-second poll** —
counting folds every store, so polling it would put ~6 s of CPU behind every refresh.

**Safety on the new endpoints:** the key must match one the catalogue produced — no path
arithmetic, no filesystem read from user input (`/export/../../secrets.csv` → 404). CSV
carries a BOM so Excel does not mangle accented names, and a cell beginning `=`, `+`, `-` or
`@` is prefixed — master holds **scraped** bios, and one starting with `=` is a CSV-injection
payload aimed at whoever opens the sheet.

## What I got wrong

1. **My hand-verification of render history was wrong, not the exporter.** I used
   `render_id or clip_id` and got 793 against 801, then nearly reported a mismatch. The real
   rule falls back to `output` and finally to `clip_id@ts` — bare `clip_id` collapses every
   re-render of one clip. Re-derived from the documented rule; calling `ledger.key_of` would
   have made the check circular.
2. **`clip_library.list_shards` returns bare filenames, not paths.** My line count opened
   nothing 55 times and reported a confident **0 rows folding to 2,761 records** — impossible
   on its face, and exactly the silent zero this file exists to prevent.
3. **A cold catalogue took 23.3 s** because seven master-derived datasets each re-folded
   master, and `funnel_values()` re-parsed the 25 MB CSV on *every* `census` call — fourteen
   times per pass. Invisible, because each individual census looked correctly cached. Cold
   23.3 s → **7.3 s**, warm 9.7 s → **0.29 s**.
4. **My `<details>` check counted prose.** `count("<details")` also matches the `</details` in
   every closing tag; and after fixing that it still failed, because this file *explains* its
   folds in comments — including the one directly above the panel under test saying it is
   deliberately not in a fold. A structural check that reads documentation as structure fails
   hardest on the best-documented code.
5. **I hand-listed three vendor keys** in the spend export, dropping `tikhub_usd` and
   `link_usd`, so the `usd` column would not have reconciled against its own per-vendor
   columns. `test_vendor_sources` caught it.
6. **I named `memebot/runs.jsonl` in my own module** — twice — when `ledger` owns that path.
   `test_clip_pipeline` caught both.

Four of those six were caught by this repo's own guards, on code I had just written.
