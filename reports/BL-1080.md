## 1. merge_append could not correct, and its docstring said it could

### The no-op, reproduced

BL-1061 restated 58 values onto a new engine and got a **45-row silent no-op**: 45 rows
written, every one well-formed, every rev incremented, not one value changed. Reproduced in
a throwaway library (`scratch/bl1080_probe.py`), which is the whole defect in four lines:

```
after first write : caption='ORIGINAL' rev=1
gap fill          : account_user_id='12345' rev=2  -> WORKED
correction        : caption='ORIGINAL' rev=3  -> SILENT NO-OP
raw rows written  : 3   (all three caption='ORIGINAL')
```

### The mechanism was right all along

`append_many` merges with `incoming_wins=(want > prev_rev)` and `build_record` defaults
`rev=1`, so an incoming row can never outrank a stored one. **That is the correct default
under concurrency** — a round holding a stale copy must not clobber what another round just
wrote. Gap-filling is safe; overwriting is not.

It stayed invisible because every prior backfill wrote into **empty** fields, where
gap-filling and correcting look identical. The docstring was the only thing that was wrong,
and it had been wrong for as long as anyone had been reading it.

### The decision: an explicit correct path

The brief allowed either. I added the path, because the phantom below needed it and because
"this tool cannot do the thing its name implies" is a worse resting state than one keyword.

```python
rec = build_record(clip_id=clip_id, posted_at=existing.get("posted_at"), **fields)
if correct:
    rec["rev"] = int(existing.get("rev", 1)) + 1
return append(root, rec)
```

Asking for `stored+1` is the whole difference between filling a gap and changing a value.
`append_many` recomputes `max(want, prev_rev + 1)` under its own lock, so a row that arrives
after another writer still lands above whatever is stored *then* — this number only has to
beat what we read, not be final.

### Blast radius: asserted, not assumed

The brief called this out — "the blast radius is every writer in the tree". Three proofs,
all in `tests/test_merge_correct.py` (11 tests):

| check | result |
|---|---|
| `correct` is not in `CLIP_FIELDS`, so `**fields` cannot shadow a real field | PASS |
| no existing caller anywhere in `clippershq/ tools/ tests/ scratch/` passes `correct` | PASS |
| a missing clip still raises rather than being created | PASS |
| default still fills gaps and still refuses to overwrite | PASS |
| a correction survives a later gap fill; two corrections both land | PASS |

Plus the three suites that own the touched module: `test_clip_library` (50 checks),
`test_clip_library_rev` (8), `test_audio_decodable` — all green.

**GOTCHA worth recording.** The caller-sweep test first reported `clip_library.py` as its own
caller: the regex `merge_append\(([^)]*)\)` matched the **definition line**, which now carries
`correct=False`. A `(?<!def )` lookbehind fixes it. A blast-radius test that counts the fix as
a symptom of the bug is a familiar shape here.

### The @saprutd phantom, removed

```

BEFORE verdict: ('third_party_watermark', 'non_english_caption', 'no_burned_in_hook')

AFTER  rev=8 ocr=''
```

## 2. The unjoinable 18% — a recurrence, fixed at source

### It is the same defect, at the site the fix never reached

When the no-repeat rule was found discarding **60 of 60 real store matches**, the fix was to
require a corpus track that could actually *join* before diverting to one. That rule went in
at the **diversion branch** and nowhere else.

The **ordinary fallback** — reached when there is no store match at all — still pooled every
local file:

```python
pool = [t for t in corpus if t.get("file")]   # no store-membership check
```

Measured on the live store and corpus: **0 of the corpus tracks are in the 4-song store.**
So this pool did not *risk* an unjoinable record. It **guaranteed** one — which is precisely
the brief's point that a fallback guaranteeing an unjoinable record is worse than a repeat.

### The fix, and its limit

A **preference, not a filter**. When a joinable track exists the pool restricts to those.
When none does, a track is still used — silence is worse than a bed nothing can learn from —
and `matched_on` says so in the record instead of the record quietly having no song.

Also: `store` was bound **only inside the store-exists branch**, so the preference would have
been a `NameError` on exactly the runs that reach the fallback. It is now bound before the
branch. That one is pinned by its own test.

`tests/test_bed_joinable.py`, 6 tests, all green. The orphan is deliberately **first** in the
pool, so plain LRU order would have taken it — the test genuinely discriminates rather than
passing by luck.

### Fresh-batch evidence

Ledger, 305 `ok` renders: **joinable True 279, False 7, None 19**. The 7+19 all predate this
change; the fallback that produced them can no longer prefer an orphan when a store track is
available.

## 3. The 20s ceiling now binds

### Why it was a spike and not a limit

Two causes, one fix each.

1. **`plan_ceiling` aimed at exactly `ceiling_s`.** The one-frame disagreement between a
   container's duration and the sum of its frame durations then decided *which side of the
   line* the file landed on. That is why 65 of 100 landed within 1ms of 20.000s and why the
   three overruns are tiny.
2. **`assert_ceiling` borrowed `TOLERANCE_S` (0.05) as an overshoot allowance.** That
   constant is argued in `duration.py` as an **undershoot** rule for the **floor** — a file a
   frame short is not the 56.8s truncation it exists to catch. There is no matching argument
   upward. Reused that way it made the real ceiling **20.05**, and all three overruns
   (+0.005, +0.020, +0.022) fit under it.

A limit that permits its own violation is a suggestion.

### The fix

`CEILING_MARGIN_S = 0.034` (one frame at 30fps). The plan aims *under*; the assert binds at
**zero**. The margin absorbs the rounding **before** the encode instead of the tolerance
absorbing it **after**, so an overshoot that survives means the trim did not take effect —
which is exactly what the assert should refuse.

All three measured overruns land at 19.97–19.99 instead of failing.

### The test the brief asked for

`tests/test_ceiling_binds.py`, 12 tests: no planned output exceeds the ceiling across a
40-point grid of source lengths × speeds; each of the three measured overruns is now
**refused**; exactly 20.000s is still **allowed** (`>` not `>=`, or the 65 renders that land
there would all fail); the floor's `TOLERANCE_S` is asserted **unchanged**.

**Four existing tests in `memebot/scraper/tests/test_duration.py` asserted "trims to exactly
the ceiling" — they were pinning the defect.** They now assert both bounds, which is
*stricter* than what they replace, not looser.

## 4. The 59% concentration is supply, not rotation

Per-song distribution over 305 `ok` renders:

| song | N | share | distinct hook windows used |
|---|---:|---:|---:|
| sng_0004 | 173 | 56.7% | 5 |
| sng_0001 | 50 | 16.4% | 6 |
| sng_0003 | 49 | 16.1% | 5 |
| (none) | 12 | 3.9% | 0 |
| sng_0002 | 9 | 3.0% | 6 |
| 11 corpus tracks | 12 | 3.9% | 1 each |

### Rotation is already maximal — it cannot spread this

Inside `sng_0004`, the five hook windows split **35 / 35 / 35 / 34 / 34**. That is as even as
five windows over 173 renders can be. Rotation is not failing; it is saturated.

### It is a supply fact

Matching all 2,728 library clips against the store:

```
parked 2,268 of 2,728 (83.1%)
per-song MATCH supply, before rotation touches anything:
  sng_0004   289   62.8% of matched
  sng_0003    91   19.8%
  sng_0001    69   15.0%
  sng_0002    11    2.4%
```

**The matcher offers `sng_0004` on 62.8% of matched clips; the ledger shows 56.7%.** The
delivered share is *below* supply — rotation is already pulling it down, not letting it run.

So the answer is unambiguous: **rotation cannot spread the 59%.** The concentration is the
shape of a 4-song store against this library, with an 83.1% park rate. The lever is more
songs (or broader mood coverage), not more rotation. `sng_0002` carries 6 hook windows and
only 11 clips can reach it — capacity that supply, not rotation, is failing to use.

## 5. A causeless failure is now impossible

6 failures on the batch (5 render, 1 unretrievable) and **two recorded no cause at all**.

The reason is structural: **three write sites, three different cause fields** —
`render.error`, `reconciled`, `retrieval.reason` — and each with its own idea of when to fill
it. "Always say why" was a convention, and the two that did not follow it are what a
convention is worth.

The fix lives in **`append_record`**, the one function every record passes through, so a
fourth write site that does not exist yet cannot forget the rule.

- **It fills, it does not refuse.** A dropped failure record is a render that silently never
  happened — worse than a vague one. The stamp names the defect it stands for
  (`NO CAUSE RECORDED -- status is ... and none of ... carried a reason`), so it is a
  diagnosis of the *code*, not a fake diagnosis of the render.
- **`"no output"` does not count as a cause.** It is what the render path writes when ffmpeg
  printed nothing — the *absence* of a cause, spelled. Counting it is how a causeless failure
  looks answered.
- The stamp deep-copies, so a caller that appends and then inspects its own dict — the
  pipeline does exactly this — never sees a field it did not set.

`tests/test_no_causeless_failure.py`, 13 tests, including a sweep that writes **every**
`failed:*` status the pipeline produces bare and asserts each comes back with a cause.
