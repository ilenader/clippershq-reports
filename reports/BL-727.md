## 1. The blocker, fixed and confirmed on live data

`repost_finder.iter_medias` returned **0** on the stream_rows envelope — no `response`, no `sections`, no `items`, so every branch missed and the caller saw an empty page with nothing raised. It now delegates to `clip_walk.iter_stream_medias`.

## 2. The client call — and BL-710's open question, answered

`IgClient.user_clips_by_views(user_id, page_token)` plus `make_clip_fetch_page()`, the adapter `walk_account` wants.

**BL-710 asked which pagination token fires in production. Both halves now have an answer, and they agree.**

**Request side**, from the provider's own OpenAPI spec (`_probe_samples/ig_openapi_spec.json`):

| endpoint | cursor parameter |
|---|---|
| `/gql/user/clips` | **`max_id`**, plus `sort_by_views`, `flat` |
| `/v2/user/clips` | `page_id`, plus `safe_int` |

These are different surfaces with different cursor names. Sending `page_id` to the gql path would be silently ignored and page 2 would return page 1 — visible only as duplicate clips, which the library's id-dedup would then quietly absorb. The client sends `max_id` only.

**Response side**, measured across 4 live pages:

```
envelope_next_page_id      0 page(s)
stream_rows_max_id         4 page(s)
none                       0 page(s)
```

**`stream_rows[*].data.paging_info.max_id` fires; the envelope-level `next_page_id` never does** on this endpoint. `paging_token()` accepting both was the right hedge, and now we know which branch is live.

**A lead the spec turned up, not acted on:** `/gql/user/clips` also takes **`flat`**. If that returns a flat list instead of the doubled stream_rows envelope, the whole richest-copy problem disappears at source. Untested — changing the response shape mid-round would invalidate the engine's tests.

## 5–7. Three skips, and a cost shape the brief did not assume

**Master carries no `user_pk` column** — I checked all 60. So a handle must be resolved before its clips can be fetched:

> **per account = 1 × `user_by_username` + N × `user_clips_by_views`**

That is **2 paid calls for a single-page account, not 1**. `plan()` feeds `estimate()` a per-account figure built from that pattern and the config's real `cost_per_call`, rather than `clip_walk`'s placeholder default, so the Proceed gate shows the bill that actually lands. It did: estimated $0.0048, spent $0.0048.

**Three independent skips, all before spending on that unit:**

1. **crossdedup** — 30 `MEME_PAGE` rows resolved to 30 distinct humans via `PersonIndex`, the same mechanism every other funnel uses. Degrades to handle-uniqueness if crossdedup fails, never to "walk nothing".
2. **seen-cache** (`clip_seen.json`) — clips processed by an earlier run.
3. **library index** (`load_index`) — clips already stored.

2 and 3 overlap deliberately, and a test pins why: **the index only knows clips that were STORED.** A clip walked and rejected below the floor is invisible to it, so without the seen-cache it would be re-processed every run.

## What this round cost, including the part I wasted

| | calls | cost |
|---|---|---|

| **total** | **70** | **$0.0420** |

**The bug:** `clip_library.load_index()` returns `{clip_id: rev}`, a dict. I wrote `have.add(cid)` against it. The per-account `try/except` contained the crash, so the run degraded to "walk everything, store nothing" and burned 60 calls across 30 accounts before I stopped it. Fixed by taking the keys — `set(load_index(root))` — with a comment saying why, and the offline rehearsal now runs first.

Two things worth taking from that. The per-account exception handler did its job (one bad account cannot end a walk) but it also **converted a hard failure into an expensive silent one** — the same shape as the bugs these reports keep finding. And a $0.036 mistake is cheap only because the cap was $0.10; without it, 30 accounts × 10 pages would have been the bill.

## Limits

- **`flat=true` is untested.** It may remove the doubled-envelope problem entirely and make the richest-copy logic unnecessary.
- **Multi-page pagination is still unproven live.** All 4 accounts stopped on the view floor or ran out within one page, so `max_id` was read from the envelope but never actually submitted. The cursor's *name* is confirmed; its round-trip is not.
- **`layout`, `speech_frac`, `ocr` are not wired**, so their zero counts prove less than they appear to.
- **`keep_rate=0.5` remains a guess.** This run kept 20 of 29 (69%) across 4 accounts against a 20,000 floor — too small a sample to replace the default.
- **The estimate assumes one page per account.** Correct for these four; an account with a deep high-view catalogue would cost more than quoted, bounded by `clip_max_pages_per_account`.
- **30 confirmed pages is the whole supply.** At ~5 kept clips per account, the library tops out around 150 clips before the repost finder has to run again.
