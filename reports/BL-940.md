### Why it read as a missing mp3 for four rounds

When a clip **parks** there is no song, so `path` is `""`, and `os.path.join(os.getcwd(), "")`
is **the repo root**. `os.path.exists` is True for a directory, so the guard passed and the
repo root became the bed. `edit.py` refused, correctly:

```
ambient_bed.file='C:\...\clipper finder' was requested and does not exist
```

The message names a missing **FILE**, which is why four rounds read it as a missing mp3 rather
than a wrong predicate. `isfile` is the whole fix.

## 2. The guard, and proof it fires

`tests/test_bed_path.py` also existed **untracked** — the test for the fix was as unprotected
as the fix. It is thorough (both layers, a non-vacuous positive case, and a check that a
disabled bed carries no stale path), so I preserved it rather than rewriting it, and added the
one case it could not catch.

**Mutation proof — the guard has been seen to fire:**

```
revert isfile(bed) -> `if bed:`                    2 tests FAIL
swap  isfile(bed) -> endswith(('.mp3','.m4a'))     2 tests FAIL, including the new plant
```

The second mutation is the one that matters. **A directory literally named `bed.mp3`** passes
a name check and every other directory case in the suite (the repo root, cwd and a temp dir do
not end in `.mp3`). Only asking the filesystem *what the path is* survives it — and the
tempting cheap fix for this bug is exactly a name check. Both new tests plant a directory
named like a track, one at the boundary and one at the producer.

`clip_pipeline.py` was restored byte-identical after each mutation (`git diff` clean).

## 3. The batch: verified by measurement, not by exit code

**Rendering the full backlog is not free and I did not pretend otherwise.** 286 clips are
renderable; **only 18 have media on disk**. The other 268 need paid retrieval, which at the
ledger's measured $0.000600/call is about **$0.16** — over this round's $0.10 budget, and more
than one call each for older clips because `retrieve()` walks pages newest-first.

Of the 18, **4 sources are corrupt**: 5,000-byte fragments from an aborted retrieval,
`moov atom not found`. Feeding one to the renderer produces a failure that has nothing to do
with the render path, so they are reported separately rather than counted as render failures.

### Four checks per output, because exit code has lied twice

A render has reported FAILED at returncode 0, and another shipped a healthy-looking **silent**
file at exit 0. So every output is checked: an audio stream exists, `volumedetect` on the
**finished** file shows a sane mean level, the duration clears the 8-second floor, and the
record names the file that is actually on disk.

## 4. `audio_decodable` is recorded nowhere — a correction to the brief

The brief says *"audio_decodable is recorded and nothing consumes it yet."* The first half is
not true, and it changes what "route around it" means.

`clip_media.audio_decodable()` exists and works. It is called inside `retrieve()` and rides
out on the **retrieval result dict** — and nothing writes it to the clip library:

```
clips in library                     : 2003
clips carrying audio_decodable       : 0        (the field does not exist on any record)
grep across clip_library/*.jsonl     : no match
```

So it is not "recorded but unconsumed" — it is **computed in memory during a paid retrieval
and then discarded**. Any consumer that wants it must either re-derive it from local media (as
this batch does, calling the real function per source) or pay to retrieve again.

Every source in the batch came back `audio_decodable: False`. **Thirteen of the fourteen still
rendered** — because `mute-and-replace` discards the source audio entirely and takes its sound
from the bed, so an undecodable source never has to be decoded. The fourteenth routed to
`keep-original`, which must decode it, and failed. See the measured result below: that split
is the next ceiling.

**And a spelling trap worth recording.** `audio_treatment` returns `music_only`; `edit.py`'s
argparse accepts `music-only`. The underscore form is **dropped with a warning** and the clip
renders on the `keep` fallback with its original audio — the copyright-shaped failure
`duck.py` warns about, arrived at by a hyphen. The batch normalises it.

## 5. Two live instances of the exit-code trap, found while working

Both are the reason item 3 exists, and I hit them within ten minutes:

* **`--only` matched zero videos and edit.py exited 0.** `RESULT edit: rendered=0 skipped=0
  errors=0 status=no-match`, returncode **0**. Nothing rendered and the process reported
  success. Anything trusting the exit code would have counted it as a render.
* **`errors=1` with an empty stderr and no error line in stdout.** The render failed and
  said only `status=failed`. The cause was a corrupt source, discoverable only by probing the
  input.

`output_dir` must also be **absolute**: `render_one` runs `edit.py` with `cwd=memebot/scraper`,
so a relative `output_dir` resolves under the scraper directory and the staged clip is
invisible — which surfaces as the zero-match exit-0 above.

### The one failure is the next ceiling, and it is the one the brief predicted

`3927961155634644396_38098820331` — `audio_decodable: **False**`, treatment
**`keep-original`**. Re-run with its correct class `dialogue-over-music` explicitly passed: it
**still fails**, so this is not an artefact of the harness.

`keep-original` must **decode** the source audio. xHE-AAC cannot be decoded by ffmpeg 8.0. The
13 that succeeded were all `mute-and-replace`, which discards source audio and takes its sound
from the bed — which is why undecodable audio did not touch them.

**That intersection is large, and nothing currently routes around it:**

```
treatment across 2003 clips:   keep-original     1013  (50.6%)
                               mute-and-replace   990  (49.4%)
audio_decodable                False on every one of the 14 local sources
```

Half the library routes to a treatment that requires decodable audio, against a reported ~35.5%
xHE-AAC rate — and `audio_decodable` is computed during a paid retrieval and **persisted
nowhere**, so nothing can route on it without paying again. **That is the next fix, and it is
bigger than a rounding error: it is the difference between 93% and whatever fraction of
`keep-original` clips carry decodable audio.**

## A bug in my own harness, found and fixed mid-round

`audio_treatment()` returns a **tuple** `(treatment, audio_class, why)`. My batch tested
`isinstance(t, dict)` and so extracted **no class at all**, meaning `--audio-class` was never
passed and edit.py fell back — the eighth instance in this repo of a value computed correctly
and dropped at a boundary, committed by the harness built to measure that very class of bug.

It did not change the headline: the 13 successes were sources with no decodable audio, where
edit.py's own fallback forces mute anyway, and the single failure fails identically with the
class passed explicitly. Fixed, and stated because a harness defect that happens not to move
the number is still a defect in the instrument.
