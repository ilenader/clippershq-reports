**These are the reason the brief says read the messages rather than run a checker.**

1. **My audit flagged 3 of 20 greetings as merge artifacts.** All three were wrong.
   `_is_merge_artifact` is designed to run on a **display name**, to decide whether to fall
   back to the `@handle` form; I ran it on the greeting that fallback had already produced,

   correct.
2. **My audit flagged `500` as an untraceable number.** It is the film — *500 Days of
   Summer*. The raw cell is the slug `500daysofsummer`, in which `500` has no word boundary;
   the digits only appear once `fandom_prose()` renders the title.

And one **real** fidelity bug in my harness, caught only by reading a rendered message:
I fed the renderer raw integers, so it produced *"did 1700000 views… a 1018460 median"*.
The export abbreviates at **write** time (`writer._merge_cell` → `1.7M`, `8k`). `writer.py`'s
own comment names this exact sentence as the defect it was written to prevent. Fixed by
routing every pilot cell through `_merge_cell`; the spike ratio is still computed on the
**raw** cells, because a rounded number must not decide a 3.0× boundary.

### The one red, and why the suite cannot be run concurrently

It finished after 76 minutes of wall-clock (815.7s of actual work — the rest was
contention). **One suite red: `tests/test_suites_parse.py`.** It is not my change, and the
cause is worth more than the failure.

The red is an **orphaned fixture**: `tests/bl932_probe_67vrvaav.py`, 17 bytes, untracked,
unclaimed, mtime **23:54** — three minutes *before* my suite started at 23:57:10.
`test_it_detects_a_planted_unparseable_file` creates it with `mkstemp(prefix="bl932_probe_")`
to prove the parse check can actually fail (TESTING.md rule 1), unlinks it in a `finally`,
and then asserts nothing is left. A run killed between the write and the unlink leaves the
file behind **permanently**, and every subsequent suite run on this tree goes red on it.

But the deeper defect is the last assertion itself:

```python
self.assertEqual([b for b in _unparseable("tests") if "bl932_probe_" in b[0]], [])
```

It matches on the **prefix**, not on the `path` this test created. So a second concurrent
run of the suite — which plants its own `bl932_probe_*` in the same shared directory —
makes this one red, and vice versa. **Two concurrent `run_all` invocations are structurally
guaranteed to fail each other here**, which is exactly the condition this session is in:
five rounds ran the full suite between 23:57 and 00:07.

That is a real bar on parallel work in this repository and it is invisible from the failure
message, which just names a stray file. The fix is one line — assert on `path`, not on the
prefix — plus tolerating other runs' probes in the detection step. `tests/` is not mine and
four suites were still running when I finished, so **I did not delete the orphan**: removing
a `bl932_probe_*` file while another round's test sits between its write and its assertion
would turn my cleanup into their red. Whoever holds `tests/` next should delete it on a
quiet tree and fix line 96.

**Nothing in this round's diff is implicated.** It changed no product code; its only
tracked, behaviour-bearing edit is one `.gitignore` pattern, and `test_tools_tracked.py` —
the suite that guards exactly that contract — is green.
