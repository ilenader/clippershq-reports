### The stdout guard was reporting a CORRECT pattern as a defect

`tests/run_all.py` failed it on a read that **is** checked: the drain runs in a nested
`_drain()` closure while `rc = proc.wait()` and `return rc == 0` sit in the enclosing
function, more than the guard's ±10-line **text window** away.

A correct pattern reported as a defect is how a standing red starts. So the guard now resolves
by **function scope** via AST — does any enclosing function consult the return code — with the
old text window kept as a fallback so nothing that used to be caught escapes. **Proved it
still fires** (TESTING.md rule 10 — refusal is not evidence):

```

CHECKED read    -> flagged: False
```

## 3. THE NUMBER: the joinable preference landed and **can never bind**

The brief asked whether the preference-not-filter fix landed and whether the rate dropped.

**It landed. The rate went UP: 4 of 40 (BL-1081) → 9 of 40 (now, 22.5%).** Lifetime: **36 of
369 finished renders (9.8%) are permanently unjoinable.**

The code is there and it is correct in form:

```python
_store_paths  = {ledger_song_path(s.get("path")) for s in store["songs"]}
_joinable_pool = [t for t in pool if ledger_song_path(t.get("file")) in _store_paths]
if _joinable_pool: pool = _joinable_pool
```

**The intersection is empty, always, by construction:**

```
store  (4 songs)  : memebot/scratch/song01.mp3 ... song04.mp3
corpus (19 tracks): track_1227570025460968.json ... (IG audio ids)
corpus tracks ALSO IN THE STORE: 0 of 19
```

So `_joinable_pool` is empty on every run, the `if` never takes, and the `else` branch — *"NONE
of 19 corpus tracks are in the song store — this record will not join"* — fires **every single
time**. The preference is a **no-op**, and the fallback still **guarantees** an unjoinable
record rather than risking one. The brief's own words: *worse than a repeat*.

**This is a supply problem, not a ranking one.** No preference over a pool disjoint from the
store can ever help; the corpus tracks have to be added to the store (`add_song.py`) or the
LRU fallback has to stop being reachable.

## Honest limits

- **I re-anchored citations rather than making them drift-proof.** They will drift again the
  next time those functions move; a line number in a document is a hostage to fortune and only
  the test catches it.
- **The stdout guard is now more permissive.** Any enclosing function that mentions
  `returncode`, `wait`, `poll` or `check=` satisfies it — a function that checks the code of a
  *different* process and reads this one's stdout unchecked would now pass. The old window had
  the opposite failure. I traded a false positive for a narrower false negative and it is a
  trade, not a strict improvement.
- **The out-of-repo guard covers `work_dir` only.** A caller that passes an in-repo `work_dir`
  and then moves the file, or a template writing elsewhere, still produces an out-of-repo
  record. It closes the path BL-1081 actually took, not the class.
- **The ceiling probe read the last 60 renders, not all 353.**
- **The unjoinable finding is diagnosis, not repair.** I measured why the preference cannot
  bind; I did not add the corpus tracks to the store, which is the operator's file.
- **The `9 of 40` is the last 40 by finish time**, which spans more than one round's batch, so
  it is not strictly comparable to BL-1081's own 40. The lifetime 9.8% is the sounder figure.
- **`clip_postable.py` shows as modified and is BL-1046's**, mid-edit. Not touched, not
  committed.
- **The `allow_outside_repo` flag is a hole I opened deliberately.** A future round could pass
  it and reproduce BL-1081 exactly. It is mitigated by being greppable, off by default,
  absent from every production caller, and announced on the run's progress when set — but it
  is a weaker guarantee than "impossible", and I chose it over rewriting two other rounds'
  tests to use in-repo paths.
- **Run 2 being green does not mean run 1's reds were noise.** Two were real and I fixed them
  between the runs; the third was another round's edit that they finished in the interval.
