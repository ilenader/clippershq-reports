## 2. The policy, and why 36 hours

A directory directly under `scratch/` is removable when **all three** hold:

1. no live claim covers it;
2. its newest file is older than **36 hours**;
3. **git tracks nothing under it** — a tracked file means committed evidence, not a workspace.

Measured against the claim-age distribution rather than chosen. Most rounds finish under 2.4 h, outliers at 17–27 h:

| N | frees | youngest directory it would remove |
|---|---|---|
| 24 h | 5.80 GB | **24.06 h** — reaches into the 17–27 h outlier band |
| **36 h** | **3.24 GB** | **38.5 h** |
| 48 h | 0.58 GB | 66.5 h — safe, and does not solve the problem |

36 clears the longest observed round by ~9 h, and on the day it landed the youngest thing it would have taken was 38.5 h old — not near the boundary in practice either.

### One command

```
python tools/scratch_gc.py            # DRY RUN — lists, frees nothing
python tools/scratch_gc.py --apply    # removes what qualifies, reports GB freed
python tools/scratch_gc.py --hours 72 # more conservative
```

**Dry run is the default**, because running this by accident is unrecoverable and a stale workspace costs a few GB.

## 3. It cannot reach real data — proven by planting

`PROTECTED` covers `master_leads.csv`, `clip_library/`, `scratch/songs.json`, `memebot/runs.jsonl`, `ground_truth/`, `output/`, `outputs_for_operator/`, `backups/`, `.claims/`, `spend.json`, `config.json`.

**Containment is checked in both directions.** A candidate that *contains* a protected path is refused whole rather than pruned around — that is precisely how `scratch/` gets allowed when the protected entry is `scratch/songs.json`, a protected **file inside the directory being cleaned**.

`tests/test_scratch_gc.py`, **14 tests**:

| | |
|---|---|
| a real file planted **inside every protected path** | refused |
| `scratch/songs.json` | protected |
| `scratch/` itself (contains a protected file) | refused |
| survey at `--hours 0` (maximally aggressive) | still refuses claimed and tracked |
| an **unreadable** claim | treated as covering everything |
| a pid that cannot be checked | treated as **alive** |
| **the removal path in a temp tree** | actually frees the directory |
| default run | removes nothing |

Both directions, because a gc that refuses everything passes every refusal test ever written and frees nothing — this project has already shipped a guard whose allow path crashed unnoticed for hours.

There is also a **re-check at the moment of deletion**: the survey may be seconds old and a round can start in that window, so the claim registry is consulted again before each `rmtree`.

## 4. Getting it out of OneDrive — reported, nothing moved

The project lives at `C:\Users\…\OneDrive\Desktop\clipper finder`, so every generated byte is uploaded and counted against the operator's quota.

**Blast radius of moving `scratch/`, measured:**

| | count |
|---|---|
| files that hard-code a `scratch/` path | **82** |
| of those, resolving it from the **repo root** | **29** |
| existing env override for the scratch root | **0 — none exists** |

Moving the directory means a junction (which OneDrive may follow and re-sync, defeating the point) or introducing a configurable root and threading it through 29 root-anchored call sites — each a chance to redirect a ledger write, which has already happened twice on this project and cost a manual recovery each time.

**Recommendation: OneDrive selective sync** (tray icon → Settings → Account → Choose folders; uncheck `scratch` and `backups`). Files stay on disk, stop being uploaded, and **no path changes, so nothing breaks**. A configurable scratch root is worth doing as its own round with its own tests.

## 5. `backups/` — redundant, and never a backup

1.92 GB, 252 files, inside the working tree, on the same disk, inside the same OneDrive folder as its subject. It dies in the same event as the thing it protects.

`tools/backup.py` already writes off-device archives and **refuses** same-volume writes, naming this directory as the anti-pattern in its own error text:

> *REFUSING: … is on the SAME VOLUME as the repo. A copy on the same disk dies in the same event — that is exactly what `backups/` already is: 252 files, 1.8 GB, same tree, same disk.*

**Verdict: no remaining purpose.** Its contents are dated `config.json` / `spend.json` snapshots predating `backup.py`. Safe retirement: archive off-device with `backup.py`, verify, then remove. **Not removed here**, and `scratch_gc` treats it as protected so no cleanup can take it by accident.
