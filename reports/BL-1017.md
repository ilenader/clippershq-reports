## 1–2. THE MECHANISM: A LIVE-LEAD JOIN THAT RUNS UNDER BOTH PROFILES

The real gap has a name and it is not a whitelist. `--profile private` switches the email rule
**off** — deliberately and correctly, because the private repo's entire purpose is storing
those addresses (BL-974 got `FAIL: 81 email addresses`, every one a legitimate lead row). That
leaves exactly the hole the brief describes: **a real address used as a documentation example
passes every check the private profile runs.**

`scratch/scan_report_for_secrets.py` now joins every address it finds against the live lead
list, under **both** profiles:

| property | why |
|---|---|
| runs under **public and private** | the public profile already refuses every address; the private one is where a real address can walk through, and this is the only check that stops it |
| an **invented** address still passes privately | otherwise it is just the email rule again, and every private report needing an example becomes unpublishable |
| compares **SHA-256 digests** | the join cannot leak through a log line or a traceback |
| refuses by **fingerprint** | enough to find the row, not enough to contact anyone |
| **no exemption exists** | a live address has no legitimate use in any document, so there is nothing for an allowlist to be for — and a test asserts no email/domain allowlist ever appears |
| an **unreadable** lead list refuses | *"I could not look"* is not *"there is nothing there"* |

**The lead-list paths are redirectable** (`CLIPPERSHQ_LEAD_LISTS`), because a check that cannot
be pointed at a fixture cannot be tested — `docs/TESTING.md` rule 3. That is how the suite
exercises it without a real address existing anywhere in the tests.

`tests/test_pii_live_join.py` — **7 checks, green**, including the one that matters: a real
address is refused under `--profile private`, and neither the address nor its local part
appears in the scanner's output.

**One defect of my own, found by that suite.** My first version skipped any lead-list path that
was not a file — so pointing it at a directory filed *"I cannot read this"* under *"there is
nothing here"*, the exact failure the check exists to prevent, one level up. Absent and
unreadable are now distinguished.

## Method / limits

**The redaction does not undo the disclosure.** The addresses were public for as long as those
two reports have been, and they remain in the reports repo's git history. What is fixed is that
they are no longer served at the URLs anyone reads, and that a new one cannot be published.

**The sweep only knows the lead list it can see.** 4,772 addresses across `master_leads.csv`
and the bot-ready export. An address belonging to a real person who is not in either file
reads as invented, and this cannot detect it.

**A live address was hard-coded in the scanner's OWN test.** `test_secret_scanner.py`'s
BL-980 fixture — the one asserting lead data must not block the private repo — used a real
lead. The new join refused it, which is the join working rather than the profile breaking, and
it is the same defect one layer further in: the test guarding the PII gate was itself carrying
PII. Replaced with an invented address, which demonstrates BL-980's property just as well.

**Two of the six `outcomes.py` addresses are not in the live list.** They were replaced anyway;
if they were invented, nothing is lost, and the file no longer teaches the next reader that a
real-looking address is an acceptable docstring example.
