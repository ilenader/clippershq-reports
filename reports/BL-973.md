# BL-973: a worktree used to answer "no rounds in flight" to ten live rounds — it now answers 13, and reads the same money ledger

**Date:** 2026-08-02 · **Type:** Governance plumbing, measured against real worktrees and a real clone · **Spend:** **$0.00 · 0 paid calls**
Claim filed with **repeated `--write` flags** (14 paths, each its own element). `tools/claims_read.py --holders` — **not** `claim.py` — run on every target before writing; all FREE. `git status --porcelain` read with the columns kept apart: **the index was clean** (`M ` empty) and 19 files were ` M` across five other rounds. `config.json` unmodified (`sha256 5fb1a8a2…`, 161 keys, 5 campaigns unchanged). No network, no paid call.

**BL-966 named one blocker; there were two, and they fail in opposite directions.** Both are closed.

## 1. Two wrong anchors, not one

```
CLAIM_DIR = ".claims"                              # relative to the CWD
REPO_ROOT = dirname(dirname(abspath(__file__)))    # relative to the CODE
```

Both are correct in the main checkout. In a `git worktree` they are wrong in **opposite** directions, which is why fixing either one does not cover the other:

| anchor | follows | ignores | what fragments |
|---|---|---|---|
| CWD-relative | the operator | the code | **the registry** — every worktree gets its own empty `.claims` |
| `__file__` | the code | the checkout | **the ledger** — every worktree gets its own empty `spend.json` |

`__file__` is the more dangerous of the two because a worktree *shares the code*: the file is byte-identical, so nothing looks wrong. And neither failure raises — both produce a **plausible number**. `claim.py list` said *"no rounds in flight"*. `total_spent_usd` would have said `0`, and the binding cap is `min(per-run, lifetime − total_spent)`, so with zero there the lifetime half never binds and **every `--cap` becomes advisory**. That is the shape BL-914 already paid for once, arriving by a different road.

## 2. The resolver: the git COMMON dir

`tools/repo_paths.py` resolves both from `git rev-parse --git-common-dir` — the `.git` shared by the main checkout **and every worktree hanging off it**. Measured on git 2.50.1 rather than read out of documentation, because the output shape is **not uniform**:

```
from the main checkout root   ->  .git            RELATIVE to the CWD
from a subdirectory of it     ->  ../.git         RELATIVE to the CWD
from inside a worktree        ->  <main>/.git     ABSOLUTE
```

so `dirname(abspath(common_dir))` is correct in all three. `--git-dir` is a **different question** with different answers — absolute from a subdirectory, and pointing *into* `.git/worktrees/<name>` from a worktree — and reaching for it would have produced exactly the fragmentation being fixed.

**Nothing moves and nothing migrates.** In the main checkout the registry is still `.claims` and the ledger still `spend.json`, byte-identical answers; outside a repository the resolver returns `None` and every caller keeps the fallback it had (a tarball export, a bare temp directory, a fresh clone). The no-op case is **asserted**, not assumed:

```python
def test_in_the_MAIN_checkout_the_answer_is_UNCHANGED(self):
    self.assertEqual(realpath(M.repo_path("spend.json")),
                     realpath(os.path.join(M.REPO_ROOT, "spend.json")))
```

**One thing that had to be asserted separately: that the fix is not inert.** `repo_paths` is not on `sys.path` for a `clippershq/` import, so `main.repo_path`'s `except` would have swallowed the ImportError and returned the old answer *forever*, looking fixed. A test checks `repo_paths` is actually in `sys.modules` afterwards.

A worktree is only ever as fixed as the last commit. The harness now asserts `tools/repo_paths.py` is present at HEAD as its first check, so this cannot be mistaken for a code fault again.

## 4. The commit guard, verified from a fresh clone

`core.hooksPath` is local config and is **not cloned**, so a fresh clone has no protection until somebody installs it. That gap is documented in every hook header and had never been exercised end to end.

**Refusal alone is not evidence** — a guard that refuses everything passes a refusal-only test. So every scenario is a **pair**, and each result records **which check fired**, read from the guard's own words rather than inferred from the exit code (three different checks all exit 1):

```
A. FRESH CLONE, HOOKS NOT INSTALLED
     core.hooksPath = ''
  [OK ] uninstalled: cross-round commit        accepted   check: (none matched)

B. AFTER `git config core.hooksPath tools/githooks`
  [OK ] installed: cross-round commit          REFUSED    check: commit-msg / foreign-claim
  [OK ] installed: own file, pathspec          accepted   check: ACCEPTED
  [OK ] installed: theirs.py survived          A  theirs.py
  [OK ] installed: Claim-Override accepted     accepted   check: ACCEPTED
  [OK ] installed: bare commit, unclaimed path REFUSED    check: commit-msg / bare-commit
  [OK ] installed: same file, pathspec form    accepted   check: ACCEPTED
  [OK ] clone reads its OWN registry           <clone>/.claims

  8 scenario(s), 0 BAD
```

Two named checks fired — `commit-msg / foreign-claim` on the BL-958 shape, `commit-msg / bare-commit` on the shared-index shape — and **four commits went through**, including the same file the bare form was refused for, via the pathspec form. The last row matters for this round specifically: the git-common-dir resolution scopes a **clone** to its own registry, not to the repository it was cloned from.

## 5. The `__file__` bug BL-966 hit twice — pinned against a real worktree

`tests/test_claim_location.py::ADirtyWorktreeIsNotClean` is that test, kept and pointed at an actual worktree rather than a temp directory:

* dirt in the worktree **is** seen from the worktree — anchor `dirty_declared` to `__file__` and a worktree full of uncommitted work reports **CLEAN**, and `claim.py end` releases over it. That is how BL-937 orphaned 169 lines and cost BL-875 its deliverable.
* a **clean** worktree still releases — the other half, because a guard that refuses everything proves nothing.
* the main tree and the worktree do **not** see each other's dirt. Correct, and the reason this is not simply "use the shared root for everything": **the registry is shared, the working tree is not.**

19 checks, all against a real repository with a real worktree created and removed per test.

## 6. Off-brief

* **`claims_read.py`'s contract had to be protected, not just extended.** It exists so a round can still get an answer when `claim.py` is mid-save, and it imports nothing but stdlib on purpose. It now imports `repo_paths` — stdlib-only, one `git rev-parse`, not a file rounds edit — but **never fatally**: if that import fails for any reason it degrades to the old CWD-relative name rather than raising. A degraded answer beats none. Pinned by a test that forces the import to fail.
* **The resolver caches per directory and the cache must be clearable.** `claim._path()` is called in loops and must not fork a `git` per call. But a test process chdirs between repositories constantly, and a cached answer from the previous repo would make a test pass for the wrong reason — so `clear_cache()` exists and every test in the new suite calls it.
* **`tools/claim.py` was momentarily co-claimed by MEMEBOT-078** during this round; by the time I re-checked, `--holders` showed only BL-973. Recorded because a transient overlap is exactly what the registry is for, and I did not have to stand off.

## 7. What I got wrong

* **My first worktree re-test reported the ledger still broken.** It was a stale worktree predating the commit, not a code fault — §3. I diagnosed it from the harness, but only after writing down a wrong conclusion first.
* **My clone harness produced a REFUSED that was not the guard.** `git commit -- mine.py` on an **untracked** file fails with `pathspec ... did not match any file(s) known to git` — BL-966 had already recorded that pathspec commits cannot introduce untracked files, and I wrote the harness anyway. **It was caught by recording which check fired**: the transcript matched *none* of the guard's refusal patterns. An exit-code-only harness would have scored it as a pass and I would have published a fabricated proof.

## 8. Still broken, and whose file

* **Config-path resolution — `clippershq/main.py` and `config.json`.** `clip_library_dir` and friends are CWD-relative strings *inside* the config; until they resolve against the shared root the way `spend.json` now does, a worktree round cannot run a funnel. Its own round: it touches every funnel's path handling.
* **`scratch/` cross-round sharing** — 844 untracked entries do not cross into a worktree. No owner; it is a consequence of `scratch/` being half-tracked.
* **One branch, one checkout** — git's, not ours. Needs a branch-per-round convention before worktrees are adopted broadly.
* **NOTED, NOT ACTED ON, as instructed:** the 29 bundled commits stay recorded in `docs/CORRECTIONS.md` rather than re-attributed — rewriting history was correctly out of scope. And **BL-899's claim on `clippershq/clip_pipeline.py` is now ~17.5 hours old** with nothing written under it; a third round had it staged in the shared index during BL-966. I did not touch it, and the commit guard now means nobody can sweep it up by accident.
