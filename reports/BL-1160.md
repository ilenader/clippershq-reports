**2026-08-06.** Every number below was produced by `.venv\Scripts\python.exe` (**Python

## Part 1 — Why runs kept dying

### The mechanism, measured rather than assumed

When a console window closes, Windows sends `CTRL_CLOSE_EVENT` to **every process attached to
that console**, waits ~5 seconds, and terminates them. `dashboard/server.py` spawned funnels
with `subprocess.Popen(...)` and no `creationflags`, so a funnel **inherited the dashboard's
console** and was on that list.

`scratch/bl1160_survive_probe.py` reads the console's own process list via
`GetConsoleProcessList` — the OS's answer to "who gets the event":

| case | shares the operator's console | killable by closing his window |
|---|---|---|
| **A. spawned as today** (no flags) | **yes** — 7 pids, including the parent | **YES** |
| B. spawned with `DETACHED_PROCESS` | no — its own private console, no window | no |
| **C. child calls `FreeConsole()` itself** | starts shared, **ends on no console at all** | **no** |

My first version of this probe opened a real console, closed it with `taskkill /T`, and
checked survival. It reported that the **control survived too** — it had not delivered a
console-close at all. It measured a race, so I deleted it rather than tuning it. A proof that
can pass for the wrong reason is worse than no proof.

A second measurement (`scratch/bl1160_hwnd_probe.py`) corrected me again: `DETACHED_PROCESS`
does **not** leave the child with no console on this machine — it gives it its **own**
(hwnd `56102286` vs the parent's `1050140`). Harmless, since no window exists for anyone to
click, but my first verdict field said "still reachable" and was wrong. The metric is now
*shares the console he can close*.

### What shipped

**Case C is the one the funnels use**, in `clippershq/run.py` via the new
`clippershq/proc_detach.py`. The child detaches **itself**, which is stronger than fixing the
spawner: it protects a funnel started by hand from a terminal the operator then closes, and it
did not require `dashboard/server.py`, which another round holds today (see *Not done*).

It refuses while `stdout` or `stderr` is still a terminal, so an operator watching a run in his
own console keeps his output and his Ctrl+C. Every live run since prints its own status:

```
SURVIVES: this run has left its console and will outlive the window that started it
```

**The dashboard itself** (`tools/dashboard_launcher.py`) had `CREATE_NEW_PROCESS_GROUP` alone,
with a comment claiming "closing the launcher window does not take the server with it". That
comment was **wrong** — that flag only stops Ctrl+C propagating — and it is why he has lost the
dashboard twice. It now spawns with `DETACHED_PROCESS` too. `START_DASHBOARD.bat` no longer
runs the server in the foreground of its own window ("Close it, or press Ctrl+C, to stop the
server" was an instruction to remember forever); it hands over to the launcher.

### The icon: resolved by capability, not by name

`OPEN_DASHBOARD.bat` used `where python`. Two independent reasons that printed
"PYTHON WAS NOT FOUND" while a terminal worked:

1. **PATH is not the same everywhere.** Explorer hands a shortcut the environment it cached
   when Explorer started.
2. **The name moved.** Measured today, in order:
   `Python313\python.exe` (3.13.14) → `Python311\python.exe` (3.11.9) →
   `WindowsApps\python.exe` (the Store stub, whose entire behaviour is to print
   *"Python was not found"* — so one way that message appeared was **Windows** printing it).

Both `.bat` files now try **absolute paths we control first** and **run each candidate**
before believing it. The launcher then picks on real capability:

```
.venv\Scripts\python.exe                  missing = []            <- PICKED
...\Python313\python.exe   missing = ['fastapi','uvicorn','tenacity','openpyxl','rich']
...\Python311\python.exe                  missing = []
```

**A bug found while proving this:** `missing_for()` probed with `import importlib` and then
called `importlib.util.find_spec`. The submodule is not bound by the bare import, so the probe
**crashed on some interpreters and not others**, the non-zero exit was read as "cannot even
run", and `pick_python` **silently discarded them**. Before the fix, the repo's own `.venv` —
which has every package — scored `None` and was dropped. A "cannot look" standing in for
"cannot run", inside the function whose only job is telling working interpreters from broken
ones.

### The relationship, on the page

`dashboard/static/runlog.html` now leads with it, both directions, plus the recovery line —
and so do all three `.bat` files and the launcher's own failure message:

> **Closing the dashboard does not stop a run.** … **Stopping a run does not stop the
> dashboard.** … **If your browser says "This site can't be reached":** the dashboard is not
> running — double-click **ClippersHQ Dashboard**. **Any run you started is unaffected and
> still going.**

### Attribution across a restart

I did **not** restart his server: another round holds `dashboard/server.py` and depends on it.
I did not need to. A run's identity lives on disk, and a restarted dashboard learns what is
running by reading those files with no prior knowledge — which is exactly what a fresh process
does. `scratch/bl1160_identity_proof.py`, run against the **live** run:

| case | verdict |
|---|---|
| the live run, read by a process that had never seen it | **alive, correctly attributed** |
| same pid, creation time altered by an hour (a recycled slot) | **rejected** |
| a real live foreign pid wearing our record | **rejected** |
| our own live pid with no identity recorded | **UNKNOWN** — not a guess either way |

**A false sentence found and fixed while proving this.** The recycled-slot case said
*"pid 9228 has exited"* about a pid that was **alive and running my funnel**. BL-1157 removed
that lie for conhost/svchost/Discord and left it in place for the case where the impostor is
another **Python** — which, on a machine running ~10 agent rounds plus the dashboard plus every
funnel, is the *likely* recycle, not the exotic one. `clippershq/proc_identity.py` now says
"that number has since been reused by another python".

**A hazard I did not fix, because it is in a file I do not hold.** `.venv\Scripts\python.exe`
is a redirector: it re-execs `Python311\python.exe`. Measured — Popen returned pid **18700**,
the run recorded pid **9228**, parent/child, 122 ms apart. So `/api/start` returns the *stub's*
pid while `run_status` records the *real* one. The live panel reads `run_status`, so its
attribution is right; anything comparing against the API's returned pid is comparing two
different processes.

## Part 2 — What survived, and the resume

### What survived of his run: the leads did not

| | |
|---|---|
| artists checked | **298** of 1,000 (log ends `[298/1000]`) |
| elapsed / heartbeats | 616.8 s, **382 ticks** |
| **leads written** | **0** |
| spreadsheet | **none** — no `output/spotify_2026-08-06*.xlsx` existed |
| `master_leads.csv` | **untouched** |
| spend recorded | **$0.009000** (15 receipt-counted requests) |

**Leads were NOT written as they were found — I checked rather than assumed.**
`control._find_spotify` calls `write_output_xlsx` and `append_found_to_master` **after**
`sp.run(...)` returns. The comment above them says they "run even on a mid-run interrupt" —
true for `KeyboardInterrupt`, which is caught, and **false for what actually happens**, which
is Windows terminating the process with no exception at all. The run's entire output sat in a
Python list in RAM for ten minutes.

**The ledger is understated for that run.** Its last heartbeat recorded **15 further billed
requests unflushed**, and no `scratch/ig_unflushed.json` marker exists to reconcile them. True
cost is **$0.0090–$0.0180**; only $0.0090 is on the books.

### Resuming his 298 was genuinely impossible — and I am saying so plainly

The killed run left **nothing resumable**. Its checkpoint, its resolve-cache write and its
master append all happened after a return that never came. The mechanism that would have made
it resumable **is what this round built**. Re-running those 298 was the only option, and it
cost **~$0.018** — that is the price of the kill, and it is now paid.

I also decided **not** to seed a skip-set from the old log by artist name. Every decision in it
(*too small*, *already had them*, *wrong language*, *no IG/TikTok*) is **free** to re-make, so
name-matching would have risked mis-skipping a real artist to save no money at all.

### What shipped: `clippershq/run_resume.py`

Append-only JSONL, **flushed and fsynced per line** (~0.4 ms against a 3–5 s per-artist
network cost). Written in `_tally` — the one place every artist result passes through exactly
once — **before** the counters, because a result on disk that was not counted costs a recount,
while a result counted and not on disk is what lost 298 artists.

On the next run, recorded artists are **replayed through `_tally`** (no network, no spend) so
counters, sheet and master append are exactly what an uninterrupted run would have produced.
Torn tails are **counted, not swallowed**. A finished run's checkpoint is **retired**, or the
next run would skip everything and report success having done nothing.

Three things I had to fix while building it, each caught by its own test:

- `seen_ids` had to be seeded with replayed ids, or **related-expansion re-queued and re-paid
  for an artist already recorded**.
- An unreadable checkpoint **raises** rather than returning `{}` — that downgrade turns a
  resume into a silent full re-run and re-pays for everything in it.
- `redo_keys` is deliberately **asymmetric**: skipping a recorded unit is right when the record
  *is* the deliverable, and wrong when the money bought something the record did not keep.

### Proof, on his real data

`scratch/bl1160_live_resume_proof.py` copies the **live** checkpoint and replays it with every
network function replaced by a **landmine that raises if called**:

```
live checkpoint : 1049 lines -> 1049 records, 0 torn, 32 with an email, 582 passed filter
resume          : 1049 offered -> 1049 replayed at zero cost, 0 left
delivered       : 582 results, 32 emails       checkpoint did not double: true
```

Reaching the end at all is the proof: nothing was re-fetched and nothing was re-paid.

## Part 3 — A dead run names its cause

`run_status.cause_of()` returns **five** facts and **never guesses** — it returns `None` with a
sentence when the evidence does not settle it:

| cause | evidence |
|---|---|
| **finished** / **capped** / **failed** | the run recorded its own ending |
| **killed** | says `running`, process gone, **`ticks` > 0** |
| **never started** | says `running`, process gone, **`ticks` == 0** |
| *(none)* | the OS could not confirm — unknown, **not** dead |

On his actual files, before I touched anything:

```
scratch/runs/spotify-20260806-135653-15824.json  ->  KILLED        (382 ticks, process gone)
scratch/runs/t.json                              ->  NEVER STARTED (0 ticks)
```

Two different facts that both used to render as *"not running — stale marker"*.

**`HALTED_CAP` existed since BL-1055 and was set by nothing.** `run.py` calls the funnel and
discards its return value, so a run that stopped itself at the cap recorded `completed` —
"it stopped itself, raise the cap" was indistinguishable from "it finished the job".
`control._LAST_FUNNEL_OUTCOME` now carries that fact up.

**The Spotify funnel never recorded an ending at all.** It wrote `status: running` at start and
*nothing* ever wrote the other half — which is why `spotify_finder.status.json` still said
`running` about pid 15824, a process that exited at 14:07. **Every completed Spotify run in
this project's history was, on disk, indistinguishable from a killed one.** It now writes a
terminal marker with counts and `halted`, and the sweep reads a thin marker's
`scratch/runs/*` sibling (matched on pid **and** `pid_created_at`) for the heartbeat count it
does not carry itself:

```
scratch/spotify_finder.status.json   running  died  WOULD SWEEP
   WHY: it was KILLED from outside — a closed window, a taskkill or a reboot.
        (read from its live-status sibling …-15824.json, which carries the heartbeat count)
   -> its work is in scratch/resume/ — the next run picks up where this one stopped.
```

## What I got wrong

1. **My first survival probe measured a race**, and reported the control as surviving too. Deleted, not tuned.
2. **I asserted `DETACHED_PROCESS` leaves a child with no console.** It gives it a private one. Caught by a second measurement; the metric was wrong, not just the wording.
3. **I blamed the wrong function for the wedge** (below) — `enrich_links`'s regexes, which are all linear. `py-spy` named the real one.
4. **My first `_code_only` helper blanked every string literal**, which would have gutted the guard it was fixing: a real `open("runs.jsonl")` would have stopped tripping it. A guard relaxed until it cannot fail is worse than the false positive.
5. **Three of my first test assertions were wrong, not the product** — a directory is legitimately "no checkpoint"; `where python` appears in a *comment* explaining why it is wrong; and I pinned a sentence the .bat had reworded.

## Still broken — and whose

**1. `bio_parser._EMAIL_CANDIDATE_RE` can wedge an entire run. Not mine to fix; it needs its own round.**

My first resumed run **stalled for 14 minutes** burning 68% of a core with a frozen heartbeat.
`py-spy` (`scratch/bl1160_wedge_stack.txt`) named it exactly:

```
Thread 2384 (active+gil):  extract_emails (bio_parser.py:444)
                           extract_from_html (enrich_links.py:232)
MainThread        (idle)   <- waiting for the GIL
"run-heartbeat"   (idle)   <- waiting for the GIL
3x pool workers   (idle)   <- waiting for the GIL
```

The pattern ends `(?:\s*(?:\(|\[|\{)?\s*(?:dot|\.)\s*(?:\)|\]|\})?\s*[A-Za-z0-9\-]+)+` — a `+`
over a group with several nullable subpatterns. Reproduced in isolation on text with no `@`
(so the match must fail after trying everything):

| input | time |
|---|---|
| 1,000 chars | 0.099 s |
| 2,000 chars | 0.538 s |
| 4,000 chars | 1.769 s |
| 8,000 chars | **8.703 s** |

Quadratic. `enrich_links` truncates to **250,000** chars, which extrapolates to **~2.4 hours on
a single page** — matching the observed wedge.

Two consequences worth stating separately:

- **The per-artist watchdog cannot save it.** It frees the pool slot, but the abandoned daemon
  keeps holding the GIL forever.
- **The BL-1154 heartbeat cannot report it.** `re` does not release the GIL, so the clock that
  exists to prove a run is alive is the first thing silenced. **Liveness is not progress**, and
  the panel currently cannot tell "working" from "wedged". The evidence already exists —
  `ticks` and the published `tick_interval_s` — so the check is *"is this run's last heartbeat
  older than it is allowed to be"*. That belongs with whoever holds `dashboard/server.py`.

**2. Two `.bat` files still cannot be reached by any test that runs them.** The assertions are
text-shape only. A real double-click test needs a clean machine, which this one is not.

**3. `dashboard/server.py` still spawns funnels attached to its console.** Held by BL-1159 all
afternoon. The child-side detach in `run.py` covers every funnel started through it today, so
this is belt-and-braces rather than an open hole — but the one-line change is
`**proc_detach.spawn_kwargs()` on the `Popen` at `dashboard/server.py:1757`, and the same at
`:3739`.
