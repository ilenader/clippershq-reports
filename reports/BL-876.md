## The third category, landed

**`record_failure()` now classifies three ways:**

| reason | kind | attempts | `vision_tooling_gen` |
|---|---|---:|---:|
| `unparseable response` | **tooling** | +1 | **2** |
| `truncated at max_tokens` | **tooling** | +1 | **2** |
| `openrouter HTTP 502` | transport | **+0** | — |
| `download failed: URLError` | transport | **+0** | — |
| `no video_dash_manifest` | content | +1 | — |
| `clip not found in 12 page(s)` | content | +1 | — |
| *something nobody has seen before* | content | +1 | — |

**A tooling failure still costs an attempt.** The call spent money and `vision_attempts` is the record of that; zeroing it would erase cost history. The re-open lives in the **skip decision**, not in a reset counter:

```python
if attempts_of(clip) >= MAX_ATTEMPTS and not tooling_gen_is_stale(clip):
    return True, SKIP_FAILED
```

**`PARSER_GEN = 2` is the whole mechanism.** Bump it and every clip retired under an older generation becomes selectable again — no sweep, no scratch runner, no list of clip_ids to remember. It is the same idea as a derivation token on a derived field: stamp what produced the value so a later change knows exactly what it invalidates.

> gen 1 — every runner carried its own `re.search(r"\{.*\}")`, `max_tokens=2000`
> gen 2 — BL-889's shared `parse_vision_json` (8/11 → 11/11), BL-904's `max_tokens=5000`

Both of those landed *after* clips had been retired by gen 1, and nothing re-opened them, because the ceiling had no memory of which generation failed them. **That is the memory.**

### The legacy-row trap, which nearly made this useless

Every retirement written before today carries `vision_last_error_kind = "content"` — the two-way rule had nowhere else to put an unparseable reply. **Keying the re-open on `kind` alone would have stranded precisely the rows this exists to rescue**, including the clip BL-875 caught.

So `tooling_gen_is_stale()` falls back to the **reason string**, which is ground truth; `kind` is a cache of a decision made by whichever version of the module happened to be running. A row with no `vision_tooling_gen` is treated as generation 0 — the oldest — and re-opens.

Verified on the live library, and it is exactly right:

| | clips |
|---|---:|
| **re-opened** | **1** — `3950256644352314564_36488443501`, `hollywood_jan07`, **67,366 plays** |
| stay retired | 16 — 12 no DASH manifest, 1 oversize, 3 deleted |

**That is item 3's clip, and it re-opened itself.** No data was rewritten, no `vision_attempts` reset, no audited re-open row appended — the mechanism made it selectable the moment `select()` next runs, and its full failure and cost history is intact. That is a better outcome than BL-928's manual append: **the sweep is not needed, because the rule now does what the sweep did.**

## Item 5 — the shared-index problem, and the half already solved

BL-875 could not land 20 lines without landing someone else's 169. Two distinct failures hide under that sentence, and only one is about the index:

**(a) A commit spanning two rounds' paths — ALREADY SOLVED.** `tools/claim.py staged` refuses it, wired as a real pre-commit hook via `core.hooksPath = tools/githooks`. It fired on this round's commit:

```
staged paths belong to one round: BL-946
```

With **11 other files dirty from other rounds** at that moment, that guard is doing real work. Item 5's proposed "commit helper that stages only a claim's declared paths" substantially exists already.

**(b) One FILE holding two rounds' uncommitted lines — NOT SOLVED, and no path-level check can solve it.** `clip_vision.py` was a single path containing BL-937's work and would have contained mine. Granularity is the whole problem.

**The smallest fix is not worktrees — it is closing the door that creates orphans.** `claim.py end()` deletes the claim file with **zero** awareness of the working tree; `porcelain` and `dirty` appear **0 times** in the entire module. A round can therefore release while leaving its declared paths dirty, which is exactly what BL-937 did and what cost two rounds their deliverable.

> **Proposal — ~10 lines in `claim.py end()`:** before releasing, run `git status --porcelain` over the claim's declared `--write` paths. If any are dirty, refuse and name them: *"BL-NNN declared these paths and is leaving them uncommitted — commit or revert first."* Orphaned work then cannot be produced by an orderly release, only by a crash, which is a much smaller and far more visible failure mode.

Per-round worktrees are the stronger fix and the right long-term answer, but they are a workflow change for every round; this is one function and it addresses the observed cause. **I did not implement it — `tools/claim.py` is another round's declared path and this round did not claim it.**

## Limits

- **The re-opened clip has not been re-labelled.** This round was specified as no-paid-calls, so it is selectable and untried. On BL-867's base rate (3 of 4) it is likely recoverable, but that remains an inference from n=4, not a measurement of this clip.
- **`PARSER_GEN` must be bumped by hand.** Nothing detects that the parser changed — BL-889 and BL-904 would each have needed a deliberate bump. A future round that fixes the parser and forgets the constant recreates exactly this bug, silently. A test asserting the constant moves whenever `parse_vision_json` does would close that, and is not written.
- **The tooling marker list is substring-based on a free-text reason string.** It matches what the runners happen to write today. A runner that words a parse failure differently is classed `content` and retires normally — the conservative direction, but coverage depends on phrasing that nothing enforces.
- **Item 5's fix is proposed, not implemented**, because `tools/claim.py` belongs to another live round. That is the same contention pattern this report is about, one level up.
- **`git status` showed 11 other modified files throughout.** This round's commit contains exactly two paths, verified before committing, but the tree remains a shared index and the next round faces the same hazard.
