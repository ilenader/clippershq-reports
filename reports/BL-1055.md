**Brief:** make every long run resumable, write incrementally, never re-pay, fail safely on

**Scope cut at the gate.** `clippershq/clip_pipeline.py` — the long-run driver items 1–4

**$0.05 declared, $0.00 spent.** Both deliverables are read-only.

## 5. The audit — 6 load-bearing blocks, 3 of them PAID

AST-based, not `grep`: a `finally` that closes a handle is free to skip because the OS
reclaims it; a `finally` that writes the ledger is money on the floor. The difference is
what the block *does*, so each is classified by the calls inside it.

**121 modules scanned · 44 `finally`/`atexit` blocks · 20 cheap · 18 unclassified ·
6 LOAD-BEARING.**

| file | kind | line | class | what it does |
|---|---|---:|---|---|
| `clippershq/control.py` | finally | 2948 | **PAID** | `flush_spend` |
| `clippershq/editor_brief.py` | finally | 1011 | **PAID** | `flush_spend` |
| `clippershq/main.py` | finally | 5149 | **PAID** | `_sync_meters`, `_metered_already` |
| `clippershq/ig_client.py` | atexit | 82 | **ATEXIT** | `_warn_unflushed` |
| `clippershq/twitch_finder.py` | finally | 1594 | PERSISTS | `cancel_dump_traceback_later` |
| `memebot/scraper/edit.py` | atexit | 53 | ATEXIT | `_cleanup_temp_caption_files` |

**A hard kill (0xC000013A) skips all six.** The question the brief asks is whether each is
*also* reachable another way, and the answers differ:

- **The three PAID ones are backed.** `spend_ledger` carries `self._clock` and a
  `time_flushes` counter — writes triggered by the **clock**, not the count. This is the
  30-second bound the brief credits with saving a real kill, and it is present in the code,
  not just in the report that described it. The `finally` is a belt over a working brace.
- **`memebot/scraper/edit.py`'s temp cleanup** is genuinely skippable — orphaned temp files
  cost disk, not correctness.
- **`ig_client.py:82` `_warn_unflushed` has NO backstop, and that is the finding.** Its own
  docstring says it exists because "a counter that is silently discarded looks identical to
  a counter that is zero". It is registered with `atexit` — so **the warning that makes
  silent loss visible is itself skipped by the exact failure it warns about.** On a hard
  kill the client dies owing requests to the ledger and says nothing, which is the BL-876
  retrieval leak's precise shape returning through the one door left open.

## 6. One command — and it found something on its first run

`python tools/run_status.py`. Read-only; starts nothing, resumes nothing, pays nothing.

```
SPEND
   688 rows, $11.3381 lifetime
   last row : 2026-08-03 14:35:40  memebot  ($0.0018)

RECORDS WRITTEN
   805 records: ok 307, failed 82, PENDING 357, no status 59

DID THE LAST RUN FINISH?
   DID NOT FINISH
   357 render record(s) are still `pending` — written at start and never resolved.
   A hard kill leaves exactly this: the row exists, the outcome does not.
```

**357 of 805 records (44%) are `pending`.** Written at start, never resolved — the signature
of repeated kills, sitting on disk unnoticed because nothing asked the question.

Three rules it follows, each pinned by a test:

1. **An unreadable file RAISES; it is never downgraded to empty.** A ledger that returns
   `0.0` when it cannot be read arms a cap against a spend it cannot see — measured here at
   **$5.00 armed against a true $0.10**.
2. **Absent is reported as absent**, which is a different fact from unreadable.
3. **No-pending is NOT reported as "it finished."** A run killed before writing its first
   record leaves nothing to find, so the absence of evidence is stated as exactly that.

`test_run_status`: **5 tests, OK.**

## What was NOT done, and why

**Items 1–4 are untouched: resumability, incremental-write proof, the ledger delta across a
kill, and the disk pre-check.** All four live in `clip_pipeline.py`, held by live BL-1050,
and all four require killing a *real* metered run — which the brief rightly insists on
("not by simulating").

I want to be exact about the one that would have been easiest to fake: **I did not verify
that a resume avoids re-paying.** Reading the driver would show what it intends; only a
kill-and-resume with a ledger delta shows what it *spends*. This repo's own history is that
the intent was right while a branch that wrote nothing was re-paid on every pass at $2.16
per 1,000. That question is answered by a metered run or not at all — so `run_status` says
so out loud rather than implying it checked:

> *"Confirm the driver skips by id before resuming — this command cannot confirm it for you."*
