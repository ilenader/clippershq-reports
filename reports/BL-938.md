## 1. youtube — a working governor pointed at the wrong number

```python
max_run_usd = float(max_run_usd if max_run_usd is not None
                    else fcfg.get("max_run_usd", DEFAULT_MAX_RUN_USD))   # nested key, $5.00
```

`run.py --cap` writes the **top-level** `youtube_finder_max_run_usd`; the funnel read the **nested** `youtube_finder.max_run_usd` and fell back to its own **$5.00**. This is worse than tiktok's missing cap, and the reason is worth stating: tiktok had no governor to find, so looking for one failed loudly. Here a governor exists, halts correctly, and reports itself — every inspection finds a cap and every inspection is reassured. The number it was reading was simply never the operator's.

Now all four ceilings are collected and the **smallest binds** — BL-930's shape, applied to one more source than tiktok needed:

```
Run cap : $0.0100  (smallest of $0.0100, $0.0100, $5.0000, $50.0000)
                    --cap ──┘         │          │          └── lifetime
                    explicit arg ─────┘          └── the nested knob it used to obey
```

### Proved on three real runs, same funnel, same source

| `--cap` | paid resolves | spend |
|---:|---:|---:|
| $0.0100 | **2** | $0.0048 |
| $0.0020 | **1** | $0.0018 |
| $0.0006 | **0** | $0.0000 |

The paid-resolve count falls monotonically with the cap. Before this change all three ran at $5.00 and would have made every resolve they wanted.

**Being precise about what these runs show.** At $0.01 and $0.002 the run also hit "source ran dry" (18–20 contactable from a 200 target), so the cap and the source were both in play. At **$0.0006 — below the price of a single call — the run made zero paid resolves**, which is the governor refusing the first call rather than the source running out. That is the cap binding, and the descending series is the evidence that it governs rather than coincides.

## 2. google_play — a governor where there was none, over the one counter that can cost

Its own docstring said it plainly: *"There is no dollar cap (Google Play is free)"*. That is true of the listing scrape, and it is why the funnel had nothing to which a cap could be passed. It is not true in principle: `link_calls` — the website fallback when a listing carries no email — is the counter that carries cost the moment those run through a priced proxy.

So the governor bounds `link_calls × link_cost_per_call`, and at the shipped price of **$0.00/call it cannot fire** — which is the honest behaviour. A cap on a funnel that spends nothing should not invent a limit.

### The live run could not demonstrate it, and that is the result

```
Niche search terms (from config['google_play']['terms']): habit tracker
23 emails from the app listing · 0 from a website scrape
google_play: completed  leads=1  spend=$0.0000  51s
```

Play mandates a public developer email, so **23 of 23** came from the listing, `link_calls` stayed **0**, and a governor over a counter that never moves cannot fire. Reporting that as "the cap didn't bind" would be true and useless.

**So the governor is driven directly instead** — same function, real execution, with a price set and a fallback that is actually used:

```
gpf.run(40 apps, listings with NO email, link_fn, max_run_usd=0.05, link_cost_per_call=0.01)
  -> stop_reason = "dollar_cap", halted = "max_run_usd", link_calls <= 6
```

Three cases are asserted: it halts with a price and a cap; it does **not** halt at a zero price; it does **not** halt with no cap set.

### google_play could not run headless at all before this

BL-891 made it refuse loudly with *"pass terms= or set config['google_play']['terms']"* — and **nothing read that key**, so the advice was unfollowable. It now reads it, which is what made the run above possible. Every other funnel already had a configured fallback (spotify `seeds`, twitch `categories`, tiktok `default_hashtags`); this is that.

## 3. Meters: the clock bound now reaches every funnel

BL-923 gave `IncrementalMeter` both bounds, but only `main._sync_meters` called `tick()`. `metered_spend_fn` — the wrapper every *other* funnel meters through — called `sync()`, which reaches the staleness check only when the counter **moved**. A run whose expensive phase makes no new billed call held its batch indefinitely while still calling `spent()` for the cap. One line closes it for all of them.

**The evidence is in this round's own ledger rows:**

```
23:29:18  youtube_finder  calls=5  $0.0030
23:29:39  youtube_finder  calls=3  $0.0018
23:30:38  youtube_finder  calls=1  $0.0006
23:30:58  youtube_finder  calls=2  $0.0012
                                   $0.0066
```

Batches of 5, 3, 1 and 2 against a 25-call quota: **every one is a clock flush**. A count bound would have written nothing at all, and a kill would have lost all eleven calls.
