## PART 1 — every caller that reads media from the flipped endpoint

`ig_client.user_medias()` (`ig_client.py:232-248`) posts to `self._medias_path`, which is `ig_api.medias_endpoint` — **confirmed `/v2/user/clips` in the live config**. Two call sites, and one of them fans out to two more consumers:

| # | caller | file:line | extractor used | status |
|---|---|---|---|---|
| 1 | `ig_discovery.fetch_recent_posts` | `ig_discovery.py:319` → `:323` | `extract_ig_media` | **SAFE** |
| 1a | ↳ main deep-check | `main.py:3172` wired at `main.py:3266` (`deep_fn=_ig_deep`) | via #1 | **SAFE** |
| 1b | ↳ suggested-crawl deep-vet | `crawl_suggested.py:1038` → consumed `crawl_suggested.py:620` | via #1 | **SAFE** |
| 2 | `repost_finder` account gate | `repost_finder.py:611` → `:613` | `iter_medias` | **WAS BROKEN — fixed by BL-695** |
| 3 | `repost_finder` tag discovery | `repost_finder.py:546` → `:551` | `iter_medias` (sections branch) | **SAFE** — reads `/v2/hashtag/medias/clips`, not the flipped path |
| 4 | `ig_client._is_empty_media` | `ig_client.py:184` | `extract_ig_media` | safe today, **see PART 4** |

**Why #1 survived, and it is not because anyone designed it to.** `extract_ig_media` (`ig_discovery.py:208-215`) tries the explicit sections path, then falls back to `_iter_media_dicts` (`ig_discovery.py:150-164`), which recurses into every dict value looking for a dict carrying an author *and* an id. A `{"media": {…}}` wrapper has neither, so the walk descends into it and yields the inner media dict. **The unwrap is a side effect of a tolerant structural search, not an intentional handler.** That is worth knowing before anyone "simplifies" that function.

**Verified independently of BL-695's own claim:** replaying `/v2/user/clips` payloads through `repost_finder.normalize_media` today gives **12/12 gate-usable** (username *and* thumb_url present) on `decibeldrops`, and `iter_medias` reaches 12/12 on all three account payloads. The fix works.

Nothing else in the repo parses an IG media envelope. A repo-wide grep for `get("response")` / `get("items")` / `get("medias")` / `get("sections")` returns exactly three modules: `ig_discovery.py:177-196`, `repost_finder.py:184-206`, and `track_id.py:183` (the last reads a track payload, not media, and is correct on all four of its saved captures).

## PART 2 — where the two extractors disagree, measured on all 34 payloads

Both extractors were run over every saved payload. Disagreement means one caller silently receives less than another caller from **identical bytes**.

| payload shape | envelope | `extract_ig_media` | `iter_medias` | verdict |
|---|---|---|---|---|
| `/v2/user/clips` ×7 | `{next_page_id, response}` | 12 | 12 | agree |
| `/v2/hashtag/medias/clips` | `{next_page_id, response}` | 30 | 30 | agree |
| `/v2/hashtag/medias/top` | `{next_page_id, response}` | 33 | 33 | agree |
| `/v2/track/by/id` ×4 | `{next_page_id, response}` | 12 | 12 | agree |
| `/v2/user/medias` (pre-flip) | `{next_page_id, response}` | 12 | 12 | agree |
| **`/v1/hashtag/medias/clips/chunk`** ×3 | **`LIST[list, str]`** | **30** | **0** | **DISAGREE** |
| **`/gql/user/clips?sort_by_views`** ×3 | **`{stream_rows}`** | **12** | **0** | **DISAGREE** |
| TikTok `hashtag_medias.json` | `{cursor, extra, hasMore…}` | **5** | 0 | DISAGREE (see below) |

**7 of 34 payloads diverge.** Three distinct classes:

**(a) The chunk list envelope — `repost_finder.py:180-181`.**
```python
if isinstance(payload, list):
    return [m for m in payload if isinstance(m, dict)]
```
`/v1/.../clips/chunk` returns `[items[30], cursor_str]` — a two-element list whose members are a **list** and a **string**, neither a dict. The comprehension returns `[]`. `extract_ig_media` recurses through the list and reaches all 30.

**(b) The GraphQL `stream_rows` envelope.** `/gql/user/clips` wraps media in a streamed row structure with no `response`, no `sections`, no `items`. `iter_medias` has no branch for it and returns `[]`; the structural walk finds all 12.

**(c) Over-tolerance, the opposite failure.** `hashtag_medias.json` is a **TikTok** payload. `extract_ig_media` still "finds" 5 media dicts in it, because the structural walk only asks for author+id and TikTok items satisfy that. Not a live bug — nothing feeds TikTok payloads to the IG extractor — but it means `extract_ig_media` returning a non-empty list is **not** evidence that the payload was the shape you thought. That is the same "looks valid and isn't" property, pointed the other way.

## PART 3 — the chunk migration breaks the repost gate in TWO places, and the envelope is only the first

This is the finding that matters, because BL-676 recommended `/v1/hashtag/medias/clips/chunk` as the hashtag-discovery replacement (the current `/v2/hashtag/medias/clips` is flagged deprecated in the provider's own spec). **Fixing the envelope would not be enough.** Measured on `chunk_series_p1` (30 items reachable):

| # | breakage | file:line | measured |
|---|---|---|---|
| 1 | `iter_medias` cannot read the list envelope | `repost_finder.py:180-181` | reaches **0 / 30** |
| 2 | `best_thumb` reads only `image_versions2.candidates` | `repost_finder.py:215` | **0 / 30** non-empty — `image_versions2` present on **0**, flat `thumbnail_url` present on **30** |
| — | `caption_of` | `repost_finder.py:235-243` | **NOT broken — 30/30.** It already falls back to flat `caption_text` |
| — | `username` | `repost_finder.py:252` | not broken — 30/30 |

**End-to-end: 0 / 30 gate-usable items.** The gate requires *both* `username` and `thumb_url`; `username` is fine on all 30, `thumb_url` is empty on all 30. So even after fixing #1, `repost_finder.py:556` (`if not r["username"] or not r["thumb_url"]: continue`) discards every item. The same payload through `/v2/user/clips` scores **12/12**, so this is purely a shape difference.

**The codebase already learned this exact lesson once — for captions.** `caption_of` carries a comment saying *"some payloads set [caption] to null and put the text in a flat `caption_text` instead… Reading only the first shape silently yields '' on the second"*, and it handles both. `best_thumb` two dozen lines away has the identical dual-shape problem — nested `image_versions2.candidates` versus flat `thumbnail_url` — and handles only the nested one. The fix pattern is already in the file; it was just never applied to the thumbnail.

`ig_discovery` is only partly exposed here: its field map lists `thumbnail_url` first (`ig_discovery.py:93`) and `caption_text` as a fallback (`:78`), so it survives #2 and #3 — but its `taken_at` chain (`:77`) resolves the flat ISO string `"2026-07-28T20:12:43Z"` before `taken_at_ts`, and `_to_int` returns `None` on it, so post timestamps go silently null (documented in BL-676, unchanged).

## PART 4 — the emptiness guard and the consumer disagree by construction

`ig_client.hashtag_medias_clips` falls back to `/top` when the clips surface returns a 200 carrying no media, and it decides "no media" with `_is_empty_media` (`ig_client.py:174-186`), which calls **`ig_discovery.extract_ig_media`**. Its docstring says this is deliberate — *"the same function the callers use, so this can never disagree with them about what 'empty' means."*

That is true of one caller. The repost finder consumes the very same response with `iter_medias`. On any shape where the two diverge — chunk, `stream_rows` — the guard sees items, declares the page non-empty, **suppresses the `/top` fallback**, and hands the repost finder a payload it reads as zero. The one mechanism built to catch a silent zero would actively prevent the recovery. Not live today (the guard only runs on the hashtag path, which is still v2), but it is wired to the wrong extractor for a module that has its own.

## PART 5 — user-visible symptom, per breakage

| breakage | what the operator sees | why it is dangerous |
|---|---|---|
| `repost_finder` account gate (fixed) | candidates found, one paid call each, all filed **THIN — "not enough to judge"**; sheet delivers nothing | reads as *"the accounts were weak today"*. Money already spent. No error, no warning, exit code 0 |
| chunk migration, #1 + #2 | `#tag page 1: 0 clips` for **every** tag, every page | reads as *"the tag is dead"* or a bad tag list. Indistinguishable from a genuinely empty surface — this is the exact failure BL-695 already paid for once |
| `stream_rows` if ever consumed | same zero-yield, plus **double counting** if it were half-parsed: each media appears twice in the stream envelope (12 unique across 15 rows) | a silent 2× inflation of any per-account count |
| `_is_empty_media` divergence | the `/top` fallback silently does **not** fire; run reports normal page counts | removes the safety net *and* the log line that would have said the surface was degraded |
| `extract_ig_media` over-tolerance | a wrong-platform payload returns 5 plausible items | a non-empty result is not proof of correct shape |

**Every one of these is a silent zero or a silent wrong number. Not one raises, logs an error, or changes an exit code.**
