## 3. The outcome loop end to end — and it found a real bug in my own BL-972 work

Every prior proof of this path was synthetic. `scratch/bl984_roundtrip.py` copies the **real** `memebot/runs.jsonl`, works only on the copy, and asserts the live file is byte-identical afterwards (**947,404 → 947,404**).

```
export 133 · fill A (full + url) · B (views only, NO url) · C (blank) · import
  2 lines written -- the blank row wrote NOTHING; exactly 2 appended
  A views 12,431 -> 12431 · saves 61 · shares 7 · post_url set · posted_at is the DATE I
    TYPED, not an epoch · and A still carries its render context, so the join holds
  B recorded WITHOUT a url; its unfilled metrics are ABSENT, not 0
  C recorded nothing; C.views is None, never 0
  re-export is 2 shorter · bias_map {} at n=2 · should_bias refuses at n=1/arm
```

### CORRECTION — a correction erased the field it exists to protect

The first run failed on step 6, and this is the finding of the round:

```
rev 1   views 12431, likes 288, post_url .../reel/DAbc123/, posted_at 2026-08-02, note ...
rev 2   views 15980
resolved BEFORE:  views 15980, likes None, post_url None, posted_at None, note None
```

`resolve()` took the **highest-rev outcome line whole**. `append_outcome(path, rid, views=…)` is the documented way to fill a number in later, and it is what `import_csv` emits when the operator updates one cell. **So the ordinary act of refreshing a view count deleted the url — and BL-972 added `post_url` precisely so a post could be found again and its views refreshed. The feature and the thing that destroys it were the same keystroke.**

**And my own test said the opposite.** BL-972 asserted *"the correction did not have to re-state the url to keep it"* by reading the **rev-1 line off disk**. Of course it was there — the file is append-only, that line is guaranteed. It never asked `resolve()`. **A test that checks the wrong object passes for a reason unrelated to the claim it makes, and retires the question.** That is worse than no test.

**FIXED.** `resolve()` folds every revision for a record **in rev order, key by key** — the rule `clip_library.merge_over` has always used: *"a field the incoming row does not carry is KEPT."* Two append-only stores in one repo with opposite merge semantics was the actual defect. An explicit `None` still clears, because *"I looked and there is nothing"* is a different statement from not mentioning the key.

Three regression tests, plus the corrected BL-972 assertion re-pointed at `resolve()`:

- a correction keeps `post_url`, `likes`, `posted_to`, `posted_at`, `note`
- an explicit `None` **does** clear
- **revisions fold in REV order, not file order** — a resumed run can append a lower rev after a higher one, and arrival order would let the stale line win

## 5. Fill is not rate

`vision_control_declined` is **99.1% populated**. BL-967 — mine — ranked it the third most valuable gap in the system on that number and never measured the rate. It is **1,982 True / 3 False / 18 None**. **It fires on three clips of 2,003.**

**FILL says how often a field is PRESENT. RATE says how often it says anything a consumer would act on.** For a boolean those are nearly unrelated: a flag that is False on nothing is 100% filled and worth nothing; a flag on 5% of rows that is True on all of them is worth more than both. Fill bounds rate from above and is otherwise not evidence about it.

Recorded in `clip_library.py`'s own `CLIP_FIELDS` comment for that field — **`docs/TESTING.md` is held by three rounds**, and the next person to reason about this field will read it there rather than in a doc. The note also flags that every other percentage in that file is a fill figure and inherits the caveat.
