# BL-1183 — one unwrapper, an empty that is not a zero, and a killed run that lost 6 paid calls

**A hard kill at 22 seconds cost 6 paid calls and the ledger recorded $0.000000.** Not a
hypothetical — measured live in this round, twice, against HikerAPI's own balance. That is the
headline, and the fix for it is **not** shipped: I built one, could not verify it, and reverted
it rather than put an unproven change on the money path. It is recorded as a failing test.

What did ship: `clippershq/envelope.py`, one unwrapper that reads every nesting shape this
project has seen — verified against all 74 saved payloads — with five distinct states so that
"the vendor returned nothing" and "we could not read what it returned" are different values.
Plus a guard test that fails when a new depth-blind reader appears.

**Spend: 21 billed calls, well inside the $1.00 cap.** Every figure below is from
`Python311\python.exe` (3.11.9); bare `python` here is 3.13.14 and lacks the packages.

## 1. THE WRAPPER BUG — ONE UNWRAPPER, AND THE FOURTH SHAPE WAS ALREADY WAITING

`clippershq/envelope.py`. Run against **all 74 payloads in `_probe_samples/`** — real responses
this project has already paid for:

| state | n | meaning |
|---|---|---|
| `ok` | 38 | items found; the path they were found at is reported |
| `single` | 24 | the payload IS one object (`balance`, `user_by_username`, `spotify_artist`) |
| `empty` | 4 | a well-formed container with zero items — **a real zero** |
| `vendor_error` | 1 | the MusicBrainz 404, surfaced with the vendor's own words |
| **`unreadable`** | **0** | |

The container lives at `response.items` (17), `response.sections` (8), `stream_rows` (3),
`data.aweme_list`, `itemList`, the bare list (6) — **and at `raw.response.userList`, three
levels down, in 4 of them.** Any reader with a hard-coded depth is one vendor change from being
the fourth incident; this one walks to depth 4.

### The cry-wolf fix that mattered more than the feature

The first cut classified all 24 single-object payloads as `UNREADABLE`. **A warning that fires
on a third of all healthy responses is a warning nobody reads**, and this repo has lost a guard
exactly that way. The split that keeps `UNREADABLE` meaningful: a payload carrying a *wrapper*
key promised a container and failed to deliver one — that is the bug. A payload with no wrapper
was never a collection.

### Structural, and deliberately not a rewrite

I did **not** rewrite the five existing hand-rolled unwrappers. Each is correct for the shapes
it has seen, each carries its own tests, and `repost_finder.iter_medias` already delegates
`stream_rows` to `clip_walk` for a measured reason. A rewrite is risk with no measured payoff.

What actually stops a fourth incident is `NoNewDepthBlindReaders` in `tests/test_envelope.py`:
it walks `clippershq/`, and **fails when a function that calls a billed client (or takes an
envelope-shaped parameter) reads a container key without handling a wrapper**. The eleven
current ones are allowlisted with a one-line reason each, and a second test fails if an
allowlist entry goes stale.

### The instrument was wrong twice before it was right — both wrong numbers are in the script

- First cut: **73 depth-blind readers.** False. It was counting `stats["results"]` on local
  dicts. A report built on 73 would have sent you hunting through code never on a paid path.
- Second cut: **19.** Still false — the client-method list had swept in `wait`, `flush_spend`,
  `balance`, colliding with `concurrent.futures.wait`.
- Final: **11**, after defining a billed call as *a client method whose body issues HTTP*. All
  11 hand-verified; 4 are `_tally(r)` on local dicts, the rest are safe for stated reasons.

## 2. EMPTY IS NOT ZERO

Six states, of which `is_failure` is **False** only for `ok`, `empty` and `single`:

```
OK · EMPTY (a real zero) · SINGLE · UNREADABLE · NO_RESPONSE · VENDOR_ERROR
```

`items_of()` survives as a back-compat shim that still returns `[]` for both zeroes — flagged
in its own docstring as the one place that still conflates them, so new code uses `read()`.

## 3. RECONCILING SPEND TO THE VENDOR — TWO DEFECTS, BOTH MEASURED

`/sys/balance` returns HikerAPI's own `{"requests", "amount"}`. Reading it before and after is
the only figure that is an invoice rather than an assumption.

**DEFECT A — `/sys/balance` is FREE, and we bill ourselves for it.** Three consecutive balance
reads moved the vendor's counter by **0**, while our client counted **3** billed requests. Every
balance read overstates spend.

**DEFECT B — the vendor charged 7 for 6 receipt-counted calls.** In the kill test the vendor's
`requests` fell by 7 (balance reads being free), and the client's x-hiker-info receipt counter
recorded 6. One paid call we never counted. I did not isolate the cause inside budget; a retry
inside `_get` billing twice is the obvious candidate and is **not proven**.

**A LIMIT ON THIS WHOLE METHOD, and it bit me.** The balance is **account-wide**. Seven rounds
were in flight; between two of my own reads the counter fell 25 with none of it mine. Account-
level reconciliation is only valid when nothing else is running — otherwise it must be
per-client via `x-hiker-info`, which is what `_reqs_from` already does.

## 4. THE KILLED RUN — THE HEADLINE, AND IT IS BAD

`scratch/bl1183_kill.py` starts a child that spends, then `taskkill /F /T` — the same shape as
an OOM kill, a power cut, or you closing the console.

```
child attempted             : 6 calls
child receipt-counted       : 6
unflushed at last heartbeat : 6
LEDGER caught               : 0 calls   $0.000000
```

**Six paid calls, nothing on the ledger.** Both existing clocks missed:

- `configure_autoflush(every=25, max_seconds=8.0)` — the count bound could not fire (6 < 25),
  and **the time bound could not fire either**, because `_maybe_autoflush` is only ever reached
  from `_bill`. The clock only ticks when *another call completes*. The child made 6 calls in
  7.1s, then blocked inside a slow request until it was killed at 22s. Fourteen seconds past
  its 8-second window, and nothing was watching.
- BL-1058's independent `_unflushed_watch` daemon **does** tick on a real clock — at
  `UNFLUSHED_WATCH_SECONDS = 30.0`. The child died at 22s. **No marker was written either.**
  The watchdog period is longer than the life of a short run.

### The fix I built, could not verify, and reverted

A daemon thread calling `_maybe_autoflush` on its own clock. The thread started, stayed alive,
and was a daemon — and the flush inside its loop silently did nothing, while an identical
flush from any other thread worked instantly. I did not find the cause within budget.

**Reverted.** An unverified change to the money path is worse than a measured defect, and
`git diff clippershq/ig_client.py` is empty. The measurement is preserved as
`@unittest.expectedFailure` in `TheFlushClockDoesNotTickWithoutACall` — it turns the suite RED
the day someone fixes it, which is the notification.

## 6. CAP KEYS, PER FUNNEL

All 12 paid funnels declare a `cap_key` in `run.py:FUNNELS`, and all 12 are read (by
`control.py` or `run.py` — **not** inside the finder modules, which is why my first per-module
audit produced false "nothing reads it" claims and why that number is not in this report).

**The structural finding: only `youtube_finder` resolves the MIN of all four cap sources** —
explicit argument, the flat key `--cap` writes, the nested knob, and the lifetime ceiling. That
is the BL-930/933 fix, and it was applied to **one** funnel and never generalised. The other
seven read a single source, so a second ceiling set elsewhere does not bind.

Worth your eye: `repost_finder` has **both** `repost_finder_max_run_usd` (flat, 2.0) and
`repost_finder.max_run_usd` (nested, 2.0). They agree today. Nothing makes them agree tomorrow,
and with a single-source read only one of them binds — and nothing says which.
