## 1–3. Classification: the premise was false, and here is the evidence

`runs.jsonl` is **append-only with a `rev`**. A render writes a `pending` line when it
STARTS and a resolving line when it ENDS. So a *completed* render leaves **two** lines — and
a counter that counts lines reports the finished half as still running.

```
812 lines  ->  390 RECORDS   (last-wins by rev, ties by file order)
                 ok               305
                 failed:render     60
                 failed:unretrievable 22
                 unset              3
                 pending            0
the 360 render_ids that ever had a `pending` line:
                 ok  300   failed:render  60   unresolved  0
```

**Nothing to resolve, so nothing was appended.** `runs.jsonl` shows 416 insertions in the
working tree — those are another round's appends; it was already `M` when I started and my
classification was read-only. Item 2's append-only discipline was honoured by not needing
it, which is the better outcome than exercising it.

**Nothing to mark unknown either.** Zero records are in the "could not determine" state, so
item 3's distinction — *could-not-determine ≠ failed* — had no instances to apply. Saying
that is different from saying it was checked and found clean, and it was checked.

### The bug, precisely, and why I should have caught it

This project already has the lesson written down, for a store with the identical shape:

> *"Clip library rows are NOT records — append-only + rev, `read_all` is LAST-WINS.
> NOTHING should dedup it."*

I applied that to `clip_library` and not to `runs.jsonl`. **Same store shape, same trap, one
file over.** `read_renders()` now folds by `(rev, position)` before counting, and the
output states the distinction rather than assuming the reader knows it:

```
812 lines -> 390 RECORDS (append-only + rev; a line is not a record)
ok 305, failed 82, PENDING 0, no status 3
```

**A headline number in a published report was wrong for a day.** BL-1055 said *"the
signature of repeated hard kills, sitting on disk unnoticed"* — a confident causal story
built on an artifact of my own counting.

## 4. The cause — there was no leak to fix

A record written at start and resolved at end *is* lost by a kill, and the brief is right
that it would be. But the resolving line is being written: 360 of 360 got one. The
self-healing sweep item 4 proposes would have had **nothing to heal**, so building it now
would be a mechanism with no measured failure behind it. Recorded rather than built.

## 5. `ig_client.py`'s gap — closed, and proven against a real kill

This one was real. `_warn_unflushed` is registered with `atexit`; a hard kill exits
0xC000013A and runs no `atexit`, so **the warning that exists to make silent loss visible
was itself silent on the one failure mode that strands money.**

The fix is the one `spend_ledger` already proved — **a clock, at the same 30 seconds**:

- a daemon thread writes owed requests to `scratch/ig_unflushed.json` on an interval, so the
  fact is on disk **before** the kill rather than emitted after it;
- **a file, not stderr** — at kill time there is no shutdown to print during, and the marker
  is an artefact `run_status` can read afterwards;
- `os.replace`, so a kill mid-write never leaves a half-written marker;
- returns `-1` instead of raising — a backstop that crashes is worse than none;
- removes the marker when nothing is owed, because a false alarm that repeats is how a real
  one stops being read.

**Proven by killing a real process, not by simulating one.** A process holding a client
owing 7 requests was hard-killed; `atexit` wrote nothing; the marker was on disk:

```json
{ "pid": 25784, "total_unflushed_requests": 7,
  "why": "written on a clock, NOT at exit: a hard kill (0xC000013A) skips atexit, so the
          warning that exists to make silent loss visible would itself be silent" }
```

And `run_status` now surfaces it, so the operator's one command reports stranded money:

```
*** UNFLUSHED SPEND MARKER PRESENT ***
   7 billed request(s) were never written to spend.json (pid 25784).
   Written on a clock, so this SURVIVED whatever ended the run.
```

`test_ig_client_flush`: **6 OK.** `test_run_status`: **5 OK.**
