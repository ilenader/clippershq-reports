## 1. The picker was already vestigial

`paste_batch.resolve_song()` picks a window at PLAN time — before the clip is fetched — so it
cannot know the clip's length or where its action is, and returns `hooks[0]`. Then at render
time, once `real_len` is known, `drop_placer.plan()` runs over **all** the song's windows and
overrides it. That override is on disk in every batch record:

```
hook               'h1'    <- what the batch nominally carried
placement_hook_id  'h4'    <- what the placer actually chose
place_at_s          3.0
placement_ok        True
placement_strict_ok False   + placement_strict_reason
```

So the honest finding is not "selection needed building" — it is **he was being asked for
input that was thrown away.** Removing the question from his path is a UI change in
`dashboard/static/index.html`, which **BL-1154 holds**; the backend already ignores it and
`paste_routes` only forwards `--hook` when one is supplied. That handover is stated rather
than done, because the file is claimed and clean.

## 2. The placeable fraction, measured — and the recommendation

Re-measured over his 21 windows at the 20.0 s ceiling (`scratch/bl1155_windows.py`):

| rule | placeable | songs with any |
|---|---|---|
| `place_at_detail` (hook plays ONCE IN FULL: `clip_len >= 2*hook_len`) | **4 of 21 (19%)** | **1 of 4** |
| align-and-loop (only the drop INSTANT must land) | **21 of 21** | 4 of 4 |

Exactly BL-1146's number. Under the strict rule **three of his four songs could never have a
drop placed at all** — that is a supply problem, not a selection problem.

**Recommendation, and it is already what ships:** keep align-and-loop. It needs no re-marking
and no change to `place_at_detail`, which is untouched and still answers its own question.
Every placement carries the strict verdict alongside, so neither number is hidden. Nothing
is placed at 0.0 and called done.

## 3. "Could not place" is None, never 0.0

`Placement.place_at_s` is **None** on refusal. A refusal returning a valid-looking number is
indistinguishable from a success — the shape that produced a false 588-of-588 here — and a
plan of 0.00 also trivially matches a measured lag of 0.00, so the verifier would score it
correct for free. `tests/test_hook_select.py` pins this from both directions.

## 4. The assumption he should check by ear — and the fix that did not exist

**The system takes each marked window's drop to be at its START.** If a window's drop is
really N seconds in, every placement using it is N seconds late.

**His own notes already contradict it:**

```
sng_0004 h2   "this is the beat drop at the beg[inning]"   <- offset 0, consistent
sng_0004 h4   "second sec is the beat drop him ..."        <- the drop is ~2 s IN
```

The docs said the fix was "one number per window in his own file". **Nothing read that
number.** `drop_offset_s` is now honoured by `plan()`: it shifts which instant of the *track*
is aligned, while the drop still lands on the action.

```
offset absent   place_at=6.0   track position 66.70   (unchanged behaviour)
offset 2.0s     place_at=6.0   track position 68.70
```

One line in `scratch/songs.json` and no code change. h4 was used on one of the shipped pairs,
so that pair is probably 2 s late — the README tells him so.
