# BL-913: adopted — and another round had already built half of it, with a better idea than mine. `stillness.py` now delegates to `claims_read.py` instead of duplicating it

## The finding I did not expect: I was about to build a duplicate

Sweeping for hand-rolled stillness checks turned up **`tools/claims_read.py`** — written by BL-906 while BL-905 was writing `stillness.py`. Same diagnosis, same session, same fix: read `.claims/*.json` directly, stdlib only, no code path through `claim.py`.

**And it had an idea mine lacked**, stated in its own docstring better than I had stated it:

> `unavailable()` distinguishes "no rounds in flight" from "could not read the registry". Those are the same integer and must never be the same answer.

That is BL-903's failure expressed as a rule. My module counted claims correctly but had no way to say *"the registry is unreadable right now"* — it would have reported a clean zero from a directory it could not parse.

**So this round adopts rather than duplicates.** `stillness.registry_unavailable()` delegates to `claims_read.unavailable()`, and an unreadable registry now **blocks** stillness instead of passing as zero rounds.

The import is **defensive on purpose**, and a test pins it:

```python
def test_it_survives_claims_read_being_unimportable(self):
    """tools/claims_read.py is itself a live edit target. If importing it raises,
    stillness must fall back rather than die — that would be the very failure this
    module exists to prevent."""
```

A helper that is itself somebody's edit target cannot be a hard dependency of the check that exists because helpers get edited. On any import failure it falls back to reading the directory itself.

```
  verdict STILL?         -> False
     - 13 round(s) in flight: BL-849, BL-895, BL-897, BL-899, BL-900, BL-906
     - tree quiet for 0s, need 600s

  tool unparseable, count still 13 -> UNAFFECTED
```

And a **torn claim file carries both facts** — it is counted *and* reported:

```
  claims_in_flight     -> 14 (torn file still COUNTS)
  registry_unavailable -> 1 claim file(s) unreadable (being written right now): BL-TORN.json
```

Counted because it is evidence a round exists. Reported because the registry cannot be trusted at that instant. Those are different facts and conflating them is how BL-903 happened.

## Honest limits

- **Two modules still do overlapping work.** `stillness.py` now delegates for the registry read, but `claims_read.py` also has `count()`, `holders_of()` and a CLI of its own. Consolidating them is a real change to a file BL-906 holds, so I wired them together rather than merging them. Someone should merge them.
- **`run_checked()` still has no production caller.** Rank 1 was fixed with an inline `returncode` check rather than by importing `stillness.run_checked` into a test module, because `tests/` importing from `clippershq/` for a three-line guard buys a dependency it does not need. The rule is adopted; the function is still unused.
- **Rank 2 is unfixed** and will stay that way until MEMEBOT-047 releases `test_clip_media_audio.py`.
- **`--poll` is untested against a genuinely still tree**, because there has not been one. Its verdict logic is covered by unit tests with synthetic samples; the loop itself has only ever been exercised against a moving tree.
- **The fingerprint uses mtime and size, not content.** A rewrite that restores a file byte-for-byte reads as a change. Conservative direction: it can say "not still" when the tree is fine, never the reverse. I hit this myself this round — `git status` called `stillness.py` modified when the diff was empty.
- **I did not run the full suite.** 13 rounds are in flight; BL-884, BL-891 and BL-903 all established that an aggregate number under those conditions cannot be interpreted. The six suites this round touches were run individually and pass.
