## 1. The amplifier — recommendation, then the fix

**Two options were on the table.** Bring `main` current, or make the topology explicit so `main` cannot be mistaken for current.

**I recommend bringing `main` current, and did that.** Three reasons, in order of weight:

1. **It removes the hazard at the source rather than documenting it.** After the fix, the dangerous command is not merely discouraged — it does nothing. Option (b) leaves a live trap for every tool, script and agent that reasonably defaults to `main`.
2. **It was provably lossless.** `git merge-base --is-ancestor origin/main HEAD` succeeded, so this is a fast-forward: no merge, no history rewrite, no force push. The 7 files `git diff` showed as deleted are the pre-repackage flat-layout copies (`control.py`, `writer.py` at root) that moved into `clippershq/` — recorded as delete+add, not lost.
3. **It fixed a second, live bug nobody had noticed** — see below.

```
git -C . merge-base --is-ancestor origin/main HEAD   # YES: fast-forward is safe
git -C . branch -f main HEAD
git -C . push origin main                            # 8aa60d8..39eb365, no --force
```

### The second bug: a real `git clone` was broken, and BL-759 could not have caught it

`origin/HEAD` points at `main`. With `main` stuck at the initial commit, **a fresh clone produced a project with zero `clippershq/` files and zero `tests/` files** — 47 files of pre-repackage layout.

| a fresh `git clone` gets | before | after |
|---|---|---|
| `clippershq/*.py` | **0** | **63** |
| `tests/*.py` | **0** | **52** |
| `tools/*.py` | 0 | 2 |

[BL-759](BL-759.md)'s disaster-recovery audit reported "a fresh clone imports cleanly but fails 6 of 48 suites". That was measured with `git archive HEAD` **on the checkpoint branch** — so it never touched `main` and could not see this. The real recovery posture was worse than reported: a clone did not give you a broken build, it gave you a different project.

## 2. The guard — and an honest statement of what it cannot do

`tools/repo_guard.py`, one tool with subcommands so there is one thing to remember.

**What it cannot do, stated first because the brief asked for honesty over reassurance: git has no `pre-reset`, `pre-checkout-force` or `pre-clean` hook. Nothing can intercept a raw `git reset --hard` typed into a shell.** Any tool claiming otherwise is lying. The hook covers `pre-push` only, and `.git/hooks` is neither cloned nor versioned — a fresh clone has zero protection until `--install-hooks` is run again. That limitation is printed by the installer itself, not buried here.

So the guard narrows the blast radius; it does not close the hole. The things that actually close it are, in order: the amplifier fix (§1), WIP commits (§3), and `RECOVERY.md` (§7).

| subcommand | what it does | proven |
|---|---|---|
| `check-reset <ref>` | tells you what a reset would destroy **before** you run it | blocked the real command at 49 commits / 135 files |
| `check-untracked` | fails when a load-bearing file is untracked | **failed, then passed** — §4 |
| `verify-remote` | every commit reachable from HEAD is on a remote | 52 commits, **0 local-only** |
| `sweep` | finds the BL-807 shape in the whole tree, `scratch/` included | §6 |
| `pre-push-hook` | refuses a push whose HEAD is far behind upstream | blocked a synthetic 10-behind push |
| `preflight` | all of the above in one call | **PREFLIGHT CLEAN (0 of 4 failed)** |

**Pre-push hook, demonstrated in a disposable clone** (not the real repo):

```
  HEAD 10 commits BEHIND origin/main
  BLOCKED by repo_guard pre-push: HEAD is 10 commits BEHIND origin/main.
  exit=1
```

### A correction to the folklore in BL-807

BL-807 says "`set -e` did NOT abort on the failed `cd`". **Stated that generally, it is false** — `set -e` *does* abort on a standalone `cd` that fails. It is suppressed when the command sits in a condition, in an `&&`/`||` chain, in a subshell whose status is discarded, or when `set -e` was never in effect in that shell. I could not determine which applied, and it does not matter: the fix is the same either way, which is why `repo_guard.py` documents it precisely rather than repeating the folklore.

## 3. WIP auto-commit — the cheapest thing here, and the one that would have saved BL-807

`tools/wip_commit.py`, plus menu action **`w` — "Save my work now"**.

**The entire cost of BL-807 was uncommitted work.** Tracked files returned in one reflog command; seven modules of in-flight edits never returned, because an edit that is never `git add`-ed creates no git object. This converts that worst case into "one commit back".

Deliberately conservative: source only, never pushes, never touches data files, and **refuses any file containing a credential-shaped literal**. That guard fired on its first run:

```
  SKIPPED : scratch/twitch_helix_probe.py   contains a credential-shaped literal
```

**Two bugs the first dry-run exposed, both fixed:**

- **It wanted to commit 481 paths** — the whole clip library, `output/`, `backups/`, `.claude/`. A safety net that makes 400-file commits is one nobody uses. Now scoped to `clippershq/ tests/ tools/ docs/` plus root docs: **482 paths in tree → 480 out of scope → 2 committed.**
- **Path parsing silently ate the first character** — `run.sh` came through as `un.sh`. `git status --porcelain` emits `XY<space>PATH`, but a single status char shifts it; slicing `[3:]` was wrong. Fixed and verified.

Proven end to end by invoking the menu handler itself, not the script:

```
$ python -c "import control; control._save_work_now()"
  Saving a snapshot of any half-finished work...
  will commit : 2
  committed 376dae0 — 2 file(s) are now recoverable.
  Done. Anything half-finished is now recoverable.
```

The handler also caught a real defect during wiring: `control.py` does not import `sys`, so `sys.executable` would have raised `NameError` on first use. Now a local `import sys as _sys`.

## 6. The sweep — one true positive, and a correction to BL-808

BL-808 reported "no destructive patterns found in tracked scripts". **That holds for destructive git commands — there are none, and there were none.** But the sweep found one instance of the *trigger* shape in committed code:

```
run.sh:8   cd "$(dirname "$0")"        # under set -e, no || exit
```

Hardened to `cd "$(dirname "$0")" || exit 1`. **Severity: low** — `dirname "$0"` essentially always resolves, and what follows is `pip install`, not a git command. It is the same shape, not the same danger, and I have not inflated it.

That distinction is now built into the tool. Conflating "unguarded `cd`" with "destructive command" makes a checker cry wolf and get switched off, so the sweep has **two severities**: `BLOCK` (reset --hard, clean -fd, checkout -f, push --force) and `ADVISE` (unguarded `cd`). Only `BLOCK` fails the build.

**Two precision bugs found and fixed while proving it:**

- It flagged the *guarded* `cd` after I fixed it — the regex ignored the `|| exit`. A tool that flags its own fix is worse than no tool.
- It flagged **its own docstrings and `control.py`'s**, which name `git reset --hard` while explaining why they exist. Now skips triple-quoted blocks in `.py` files and backtick-quoted spans everywhere.

Verified precise in both directions — silent on the clean tree, loud on a planted hazard:

```
$ printf '#!/bin/sh\ncd "$REPO"\ngit reset --hard origin/main\n' > scratch/_probe.sh
  ADVISORY : scratch/_probe.sh:2  cd "$REPO"
  BLOCKED  : scratch/_probe.sh:3  reset --hard
  exit=1
```

## Honest limits

- **Nothing can stop a raw `git reset --hard`.** Git provides no hook for it. The amplifier fix means that specific command is now harmless *here*, but a reset to any other ref still bypasses everything. `check-reset` only helps someone who chooses to run it.
- **`.git/hooks` is not cloned and not versioned.** Every fresh clone starts unprotected until `--install-hooks` is run. The standalone subcommands exist because of this, not as a convenience.
- **The seven modules from BL-807 are still gone.** Nothing here recovers them; this only makes the next occurrence cheap.
- **`LOAD_BEARING` is a hand-maintained list of 9 files.** A new critical file is unprotected until someone adds it — the check cannot infer importance.
- **The reflog and all backups remain on one disk**, and `OneDrive.exe` was not running as of BL-759. This round did not change the offsite position at all.
- **I did not test the pre-push hook via an actual `git push`**, only by invoking its logic directly against a synthetic 10-commits-behind branch in a disposable clone.
- The two WIP commits in the history were left as-is rather than squashed: `39eb365` was already on the remote, and rewriting pushed history is exactly the class of operation this work exists to prevent.
