# BL-745 — Spec: what a downstream editing bot needs to recreate a clip. 29 of 39 fields already ship; the one that matters most is the one nobody has measured

**Date:** 2026-07-31 · **Type:** Specification (new files only) · **Spend:** **$0.00** — no API call was made
**No existing module was edited. `config.json` was not written.** Three new files under `scratch/`, nothing else.

Deliverables: **`scratch/bl745_edit_spec.md`** (the schema) and **`scratch/bl745_example_record.json`** (one real filled record), plus `scratch/bl745_frame_features.json` as the geometry evidence.

---

## Headline

A bot can already be told **who posted a clip, where to find it, what the caption said, and what the frame looks like geometrically** — that is 29 of 39 fields, and every one of them is free. What it cannot yet be told is **what the overlay text actually said**, which is the single field the whole exercise turns on.

The gap is not that overlay text is missing. `frame_features()` produces `ocr_text` today. The gap is that it is produced in a form that has been optimised for a *classifier* and is lossy for a *transcriber* — space-joined, truncated at 400 characters, and read at a resolution chosen because it does not change any classification decision.

**Ten fields are absent, and all ten are honest absences** rather than fields I filled with plausible defaults.

---

## The correction that matters most

**I nearly recommended a change that would have regressed a measured decision, and I want that on the record rather than quietly fixed.**

My first draft said: BL-733 measured 82% usable transcription with the downscale removed, the library path still downscales, therefore port the fix. That reasoning is wrong, and [BL-736](BL-736.md) — which landed *while this spec was being written* — is why.

BL-736 drove the real shipped path at both resolutions and found removing the 640 downscale produces **zero tier changes and zero hit changes** for **2.9×** the CPU, and makes `text_in_band` *noisier* (`A19` 1.000 → 0.399), because full resolution finds more text outside the bar and dilutes the ratio. On a run BL-732 clocked at 31.9 s/candidate already OCR-dominated, raising it would push 2.7 hours toward 8 and buy nothing. **`OCR_MAX_SIDE = 640` should stay.**

The two questions come apart:

| | resolution | repair pass | consumer | quality evidence |
|---|---|---|---|---|
| `ocr_features.ocr_one` | full (BL-736, today) | yes | account gate | 81.8% usable, CER 0.020 |
| `repost_layout.frame_features` | 640 | no | repost classifier | decision-neutral (BL-736) |
| **`overlay_text` (this spec)** | — | — | **transcription** | **nobody has measured this** |

BL-736 measured whether 640 changes a **classification**. `overlay_text` needs to know whether it changes a **transcription**. BL-736's own numbers show full resolution "nearly doubles boxes and characters" — for a classifier that extra text is noise it correctly ignores; for a bot reproducing a caption it is exactly the thing being lost.

**So the recommendation is a second, separate read** — OCR the cover at full resolution only for clips entering the library, leaving the classifier's cheap pass alone. That spends the 2.9× where it earns something. It should be measured before it is built.

**The honest status of `overlay_text` quality is *unmeasured*, not *bad*.** Quoting BL-733's 82% for this field would be quoting a number across a gap it does not cross.

### A second consequence of BL-736

It added `repair_ocr_text()`, which rewrites `;`→`,` and restores apostrophes. A net win for the account gate — and a problem for the word *verbatim*. Repaired text is no longer what was on the pixels. If `overlay_text` is ever sourced through that path, **the raw read must be kept beside it and the repaired field's provenance must be `derived`, not `measured`.** The ladder already has the right word for it.

## The six items

### 1. Overlay text, verbatim — BUILD

`ocr_boxes()` already returns per-box `{text, conf, x0, y0, x1, y1}`. `frame_features` then destroys it:

```python
feat["ocr_text"] = " ".join(str(b["text"]) for b in boxes
                            if b.get("conf", 0) >= OCR_MIN_CONF)[:400]
```

Line breaks gone, casing kept but position lost, long captions cut. Specified instead: `overlay_text` (newlines preserved), `overlay_lines` (per-line text + conf + band), `overlay_band`, `overlay_conf_min`, `overlay_script`. Line grouping sorts by `y0` and breaks when the next box clears the current line's `y1` — EasyOCR returns *reader* order, which is not visual order once there are two columns.

Shown rather than asserted, from a real `frame_features()` run on a committed golden frame:

```
ocr_text : 'No CCI  Just Ryan bcing HIM:'     ocr_max_conf 0.5287
```

"No CGI" → `No CCI`, "being" → `bcing`.

**Non-Latin is unusable at any resolution** — BL-733 measured 0 of 10 across Arabic, Cyrillic, Devanagari, Gujarati, Hangul, Malayalam. `overlay_script` exists so the bot refuses rather than reproduces nonsense.

### 2. Emoji with codepoints — BUILD

The BL-694 trap reproduces in three lines:

```
naive positive set = set("😂❤️✨")  -> 4 members, not 3
naive negative set = set("😢☹️💔")  -> 4 members, not 3
OVERLAP: ['U+FE0F']  VARIATION SELECTOR-16
```

`❤️` is `U+2764 U+FE0F` and `☹️` is `U+2639 U+FE0F`, so a bare variation selector landed in **both** sets and set membership decided sentiment.

Fields carry the **full sequence** — `"U+2764+U+FE0F"`, not the base — because a bot writing `U+2764` alone renders a black heart, not a red one. Cluster extraction keeps trailing `U+FE0F`/`U+FE0E`/`U+200D`/skin-tone `U+1F3FB–U+1F3FF`; a modifier never starts a cluster. Verified to round-trip byte-identically.

**Do not reuse `caption_parser`'s emoji sets here** — those score `😭` as zero deliberately, because BL-694 measured it in both registers. Reproduction needs every emoji, unweighted.

### 3. Layout geometry — 11 of 12 SHIP

Names copied out of `repost_layout`'s return dict, not retyped. **Two corrections to the brief:**

- It is **`bar_top_color`**, not `bar_color`.
- **There is no `bar_bot_color`.** Only the top bar's colour is computed. A bot rebuilding a bottom bar has no colour to copy, and inventing one would be a fabricated field.

The one field to build is **`free_bands`** — where new text fits without covering imagery. `bar_runs` already carries the occupied spans, so it is the arithmetic complement, not new detection. It is also the field an editing bot most needs.

### 4. Source clip — permalink only

`width` / `height` / `aspect_ratio` need building and are **free**: a real media object carries `original_width` 720, `original_height` 1280, `video_duration` 58.676.

**`duration_s` has a real bug.** `clip_runner.clip_record()` sources it from `clips_metadata.original_sound_info.duration_in_ms` — the **audio track's** length, not the video's — and on `licensed_music` clips `original_sound_info` is absent entirely. That is why the example record shows `duration_s: absent` on a clip whose payload plainly carries `video_duration`. One field name.

**Never the CDN url** (BL-690, ~33-hour expiry). `clip_library` already tests a serialised record for `cdninstagram` / `scontent` / `oe=` / `_nc_ohc` — keep it.

### 5. Audio — declared ships, measured is blocked

`track_title`, `track_artist`, `audio_type` ship today (~23% declared). `has_music`, `genre`, `energy`, `vocals` are **blocked at [BL-737](BL-737.md)** — $0 balance against a flat $0.50 audio minimum.

**`has_music` is read off the model, not inferred**, as asked. The enum already defines `genre: "none"` as *no music at all*, so `has_music = (genre != "none")`. Deriving it from `audio_type` would be wrong — `original_sound` covers both a silent talking-head and a creator's own music bed.

Until the credit lands these are `absent` — **not `false`, not `"unknown"`**.

### 6. Provenance on every field

`declared` / `measured` / `derived` / `absent`, with `READABLE = (declared, derived, measured)`. **A field with no provenance entry reads as null**, which is what makes a zero-error subset filterable. Machine-checked on the example record:

```
every data field has provenance : OK
no orphan provenance entries    : OK
absent fields all read as null  : OK      <- the consumer rule
readable fields all carry value : OK
```

**One asymmetry worth knowing:** `caption_parser.field()` does not know `measured` and returns `None` for it. Consumers must go through `clip_library.field()` or every geometry field silently disappears.

## Ships vs build

| group | ships today | needs building |
|---|---|---|
| provenance ladder | ladder + `field()` enforcement | — |
| clip identity | `clip_id`, `permalink`, `account`, `play_count`, `posted_at`, `caption` | — |
| dimensions | — | `width`, `height`, `aspect_ratio` (free on the payload) |
| duration | `duration_s` (wrong source) | repoint to `video_duration` |
| geometry | 11 of 12, verbatim names | `free_bands` |
| overlay text | `ocr_text` (space-joined, 400-cap) + position stats | `overlay_text`, `overlay_lines`, `overlay_band`, `overlay_conf_min`, `overlay_script` |
| emoji | — | all of it |
| audio, declared | `track_title`, `track_artist`, `audio_type` | — |
| audio, measured | — | `has_music`, `genre`, `energy`, `vocals` (blocked) |

**Nothing in this spec needs a new paid call.** The cover frame, the dimensions and the caption all ride on responses the funnel already buys. The only spend anywhere is the audio model.

## The example record

Real clip from `scratch/bl725_library`:

```
account    loste1980
clip_id    3941210953483232160_227282247
permalink  https://www.instagram.com/reel/Dax_nsTPyOg/
play_count 1,385,002
track      "Mother Nature" / Apollo Keys   (licensed_music, declared)
39 fields · 29 readable · 10 absent
```

**One honesty note, stated rather than blended.** This clip's own cover frame was not retained, so the geometry block comes from a real frame in the committed calibration set (`002.jpg`: `bar_top_frac` 0.3969, `bar_top_color` "B", `text_in_band` 1.0, `n_bar_runs` 2). Those are genuine `frame_features()` outputs, not invented — but they are **not this clip's own geometry**, and the record says so in a `_sources` block rather than presenting a seamless row.

The emoji field is a real find: the caption carries `🧠📺⭐🎭📝🔥🏆🎬📅`, the cluster-A farm template from BL-695 — `emoji_order` preserves the repeats (📺 three times), `emoji` dedupes with counts.

## Limits

- **This is a specification. No code was written and nothing was measured end to end.** Field shapes are proposals; only the values quoted from real runs are evidence.
- **`overlay_text` — the field the brief cares most about — has no quality number on the path that would produce it.** I can say what is wrong with the current aggregation and what the fix probably is; I cannot say how good the result would be.
- **Multi-line grouping is unvalidated.** The y-band rule is reasonable and untested — BL-733's corpus was single-line captions.
- **`free_bands` has no consumer yet**, so its shape is a guess at what an editing bot wants.
- **Emoji from OCR and from caption may disagree** and no reconciliation rule is specified; `emoji_source` records the surface rather than merging.
- **The audio half of item 5 is specified but unproven** — four rounds outstanding on that benchmark now.
