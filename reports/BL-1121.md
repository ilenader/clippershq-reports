## 2. WHAT I SHIPPED: `tools/verdicts_merge.py`

The brief's item 1 has two halves. The merge itself was blocked; **the half that stops it
recurring was not**, and it needed only a new file nobody holds.

`clip_verdicts.json` is **whole-file JSON**. Every writer reads all rows, appends, and writes
all back. With ten live rounds that is a lost-update race: two rounds read 307 rows, each
adds its own, each writes back, and **the second silently destroys the first's labels**.
Nothing errors and nothing looks missing.

**Two consecutive rounds have now routed around it rather than risk that** — BL-1115 wrote to
a sibling, and this round could not merge that sibling for the same reason. A format that
makes two rounds in a row work around it is a defect in the format.

### Five guarantees, each pinned by a test (11/11 green)

| | |
|---|---|
| **1. No prior row is ever dropped or altered** | existing rows are copied first and never rewritten — asserted byte-for-byte including keys the helper has never heard of |
| **2. Idempotent** | re-merging adds nothing. **The same clip judged by two judges stays two rows** — collapsing on `clip_id` would erase the disagreement this file exists to record (kappa 0.378, and 0.118 in the newest pair) |
| **3. Refuses rather than guesses** | a row without `clip_id` or `judge` raises, and **a refusal leaves the target untouched** |
| **4. Atomic and locked** | temp file in the same directory, fsynced, `os.replace`d, under the project's own cross-process lock |
| **5. It reports what it did** | counts in, added, skipped, total — a silent merge is indistinguishable from a no-op, which is exactly what `merge_append` was found doing (45 rows written, zero values changed) |

### The merge is PROVEN, not performed

```
DRY RUN — ground_truth/clip_verdicts.json
  existing rows      : 307
  from clip_verdicts_bl1115.json    60 row(s), 60 new
  added              : 60      skipped duplicates : 0
  TOTAL after        : 367     (nothing written)
```

And a test performs the **real** merge into a **copy**, asserting every prior row survives
byte for byte and that the original on disk is unchanged. So when BL-1085 releases, the merge
is one command with a known outcome.

## WHAT I GOT WRONG

**I guessed `filelock`'s API and the guess announced itself as a feature.** I wrote
`filelock.FileLock(path + ".lock")` — a class this module does not have, on a path it
*explicitly rejects* (`LockPathMisuse`, BL-817: pass the data file, never the lock file). The
`except Exception` around it swallowed the `AttributeError` and printed *"no advisory lock
available; merging anyway"*, so **every merge ran unlocked while announcing a degraded mode
that was really a bug**. The tests passed throughout, because they tested the merge, not the
lock.

It now uses `file_lock(path)` on the data file, per its own docstring, and the degraded-mode
message fires only on a genuine import failure. Guessing an API and catching the consequence
is how a guarantee turns into a comment.
