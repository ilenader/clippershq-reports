## WHAT THE PRECONDITION CHECK ACTUALLY FOUND

`git status --porcelain` returned one dirty target: **` M scratch/songs.json`** — his file.
The brief says stop and report on a dirty target, and the dirt turned out to be the whole
story.

**His 21 drop offsets existed in exactly two places, and neither was safe.**

### 1. The live file is tracked — but the marks were not in it

```
HEAD          21 windows,  0 with drop_offset_s
working tree  21 windows, 21 with drop_offset_s
```

Every mark he made by ear was **uncommitted**. `git checkout -- scratch/songs.json`, a hard
reset, or a stash applied in the wrong order erases all 21, and `drop_placer` honours every
one of them.

### 2. The backups were a cleanup candidate, eight hours out

`scratch/songs_backups/` — the timestamped copies every writer of that file takes precisely
so a bad write can be undone — is **untracked and unclaimed**. `scratch_gc`'s own survey, run
against the live tree:

```
songs_backups   2.414 MB  age=27.7h  KEEP   only 27.7h old (< 36h)
```

**Age was the only thing keeping it.** At 36 h it becomes `REMOVE`, and the next round that
hits disk pressure and runs `scratch_gc.py --apply` takes it. That is not hypothetical: the
tool exists because the disk hit 100% on 2026-08-03, `docs/DISK.md` documents `--apply` as
the operator's move, and BL-1174 already recovered 810 already-paid leads from a checkpoint
this same tool was free to delete.

### Why the existing guard did not cover it

`scratch/songs.json` **is** in `PROTECTED`. `scratch/songs_backups` is its **sibling**, and
`protected_conflict` asks only about equality and containment — neither holds between
siblings. The `backups` entry in the same tuple is the **repo-root** `backups/`, a different
path again. Nothing in the list reached it.

> **Protecting a file does not protect its backups.**

The print filter is why nobody saw it: `scratch_gc` only prints `KEEP` rows over 50 MB or
explicitly protected, and this directory is 2.4 MB. It was surveyed every time and displayed
never. My first grep for it came back empty and I nearly reported that as "not a candidate" —
the absence proved nothing, and the verdict had to be queried from `survey()` directly.

## THE FIX — TWO HALVES, BOTH NEEDED

**His marks are committed.** The live file is now recoverable from git.

**`scratch/songs_backups` is in `PROTECTED`.** The copies that exist to undo a bad write can
no longer be swept by the tool that cleans the directory they live in.

Either half alone leaves a single point of failure: committing without protecting leaves the
undo history sweepable, and protecting without committing leaves every mark one `git checkout`
from gone.

### Committing his file was checked, not eyeballed

Roughly seven rounds share this working tree, so committing someone else's dirty file means
committing whatever else is sitting in it. `scratch/bl1231/diff_songs.py` enumerates every
**leaf** that differs between `HEAD` and the working tree, comparing parsed objects rather
than text — a text diff cannot tell *a mark was added* from *a window was rewritten*:

```
leaves: HEAD 1014, working tree 1035
  added   21      <- every one of them a .drop_offset_s
  removed  0
  changed  0
VERDICT: the ONLY difference is his drop marks -- safe to commit
```

It exits non-zero on anything else, so the commit is gated on the check rather than on my
reading of a diff.

**Eight of the 21 are `0.0`, and that is a fact, not a gap.** "Marked at 0.0" and "not marked"
are different states — the key is present with value `0.0` in the first and absent in the
second — and the commit preserves the distinction the brief asked to keep visible.

### The tests
