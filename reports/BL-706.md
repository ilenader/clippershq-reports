## 1. What was built

`clippershq/artist_genre_map.py` — keyed on `clips_metadata.music_info.music_asset_info.display_artist`.

```python
lookup(credit, require_confirmed=False) -> record   # full record + provenance
field(record, name)                                 # the consumer rule
genre_for(credit)                                   # convenience, goes through field()
is_mapped(credit)
split_credit(credit)                                # whole credit first, then components
normalise(name)                                     # the lookup key
unmapped_artists(counts) -> [{artist, clips, variants}, ...]   # ranked extension queue
coverage(counts) -> {clips_total, clips_mapped, pct}           # clip-weighted
unconfirmed_entries() / mapped_artists()
```

It is on a **different axis** from `content_genre.py`. That module answers "what is this clip about" (action, sitcom, superhero) from the hashtag and caption. This one answers "what kind of music is the licensed track". The two are never merged.

No config file, no network, deterministic — importable for offline batch work, same contract as `caption_parser`.

## 3. Case normalisation runs before lookup — BL-704's 10+4 split is the reason

BL-704 found `kowlys` and `Kowlys` counted as two artists in the raw table, splitting one 14-clip artist into a 10 and a 4. That is not cosmetic: it is the difference between the head being ranked correctly and being ranked wrong.

`normalise()` does NFKC → curly-apostrophe fold → trailing `feat.` strip → connector-punctuation trim → whitespace collapse → casefold. It deliberately does **not** strip internal periods or apostrophes, because `mc k3` and `i'll take you there choir` are real keys.

`unmapped_artists()` folds case variants into one row with the **summed** count and lists the raw spellings in `variants`, so a surprising fold is visible rather than silent.

A guard runs at import: `_selfcheck_keys()` raises if any key in `_CURATED` is not already in normal form. Without it, a key written as `"Apollo Keys"` could never be hit and the map would look bigger than it is — the miss would surface later as a genre that "just doesn't work sometimes".

## 4. Multi-artist credits — and the ampersand trap

The corpus carries comma-joined credits that match no single-artist key: `Kendrick Lamar, SZA`, `tienanh109, HDN, MC K3`, `Alok, Alan Walker`, `Raghav Kaushik, Rekha Bhardwaj, Amrita Saluja`. `split_credit()` splits on `,` `&` `/` `+` `x` `×` `and` `vs`.

**But splitting on `&` is a trap, and the same corpus proves it.** It also holds `She & Him` and `Vishal & Shekhar` — single acts whose *name* contains an ampersand. Splitting those yields four artists that do not exist.

So the resolution order is **whole credit first, components second**. `split_credit()` always returns the full normalised credit as element 0. A future `"she & him"` entry therefore beats the splitter automatically, with no special-casing — and the test pins that behaviour by planting a deliberately wrong `"him"` entry and asserting it never wins.

`matched_artist` on the returned record names the component that actually hit, so a multi-artist resolution is auditable instead of mysterious.

## 5. Provenance: `declared`, and never `derived`

Follows the existing `caption_parser` ladder — `declared` / `derived` / `absent`, with `field()` returning None for anything not attributable.

A curated-map hit is **`declared`**: a human wrote it down. This module never infers at lookup time, so it **never emits `derived`** — a miss is `absent`, never a guess. A test asserts no lookup on any input can produce `derived`.

## 6. Licence hygiene — and one thing I did NOT do

Not one genre string is copied from MusicBrainz (CC BY-NC-SA), Last.fm or Deezer (non-commercial), Discogs (genre appears to be Restricted Data), or the iTunes Search API (terms uncleared per BL-704 §4).

That last one was a live temptation worth naming: `scratch/bl703_itunes_results.json` **already contains** iTunes genres for these exact artists — Apollo Keys → "Classical Crossover" (flagged `ambiguous: true`), Trikstar → "Pop", kowlys → "Electronic". Pasting those in would have been the fastest route to a filled map and would have silently imported the exact licence risk BL-704 was written to avoid. A test enforces the abstention: it asserts that none of the seven iTunes strings appears as a genre value.

The head labels are instead read off **your own corpus** — the track titles already in the saved payloads:

| Apollo Keys | Hope of the Heart · The Fountain · It Snows Silently · Mother Nature · **Piano Craft** · The Dark Forest | `cinematic-instrumental` |

### The seed labels are proposals, not your declarations — and they are flagged as such

You asked for *your own* labels for artists *you* have seen. I do not have those, so I did not pretend to. Every seed ships `confirmed=False` with a `basis` string recording exactly what evidence produced it. `unconfirmed_entries()` lists all twelve, and `lookup(..., require_confirmed=True)` returns nothing until you sign them off — with that flag set, coverage is 0% by design.

Confirming one is a one-character edit. This is the only part of the deliverable that needs you rather than the data: **the mechanism is proven either way, but the three head labels are my reading of your track titles and should get your eye before anything downstream trusts them.**

## 7. The extension point

Adding an artist is one line:

```python
"new artist name": _E("genre-slug", "why you know this"),
```

`unmapped_artists(counts)` is the maintenance loop, not a one-off audit — it returns every unmapped artist **sorted by clip count descending**, ties broken by name for a stable diff, with case variants already folded. Run it after each corpus refresh.

On the corpus as it stands today it returns 38 rows, **all of them singletons** — which is BL-704's "mostly tail" finding restated as a work queue, and confirms there is no cheap win left to take.

## 10. What this does not fix

- **The tail still does not saturate.** 38.8% of licensed clips remain unmapped and every one is a singleton. Per BL-704 the answer there is Wikidata (30% clip-weighted, CC0, clean), not more curation.
- **Only 23.5% of clips carry a title+artist at all.** This map operates on that slice; the other 76.5% are `original_sounds` with no music metadata to key on (BL-702).
- **The three head labels are unconfirmed** until you sign them off, as above.
- **Genre granularity is untested.** Whether `cinematic-instrumental` is the right grain for a downstream editing bot, or whether it wants `piano` / `orchestral` split out, is a product question no measurement here answers.
