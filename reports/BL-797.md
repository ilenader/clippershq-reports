## 1. The two columns

Added to `writer.FULL_COLUMNS` (68 → **70**), appended last so every existing column keeps its byte position and an older master auto-migrates by field NAME.

| column | meaning | validation |
|---|---|---|
| `touch_number` | which contact in the sequence — 1 = first approach, 2 = first follow-up | positive integer; **0 and negatives rejected** |
| `message_variant` | which template — `A`, `B`, `short-v2` | free-form, capped at 40 chars |

`touch_number` rejects `0` deliberately: there is no zeroth contact, and a stored `0` would read as "not sent" to anything treating the column as a count.

### The one design decision worth explaining

They are **not** in `outcomes.OUTCOME_COLUMNS`. That block is asserted by `test_outcomes` to sit **contiguously** inside `FULL_COLUMNS`, and that guard was deliberately narrowed on 2026-07-30 so later blocks could be appended last rather than inserted mid-header. Adding two entries to it would have forced a choice between breaking the guard and shifting the outcome block — the exact movement the guard exists to catch.

So they live in a new `SEND_TRACKING_COLUMNS`, with `RECORDABLE_COLUMNS = OUTCOME_COLUMNS + SEND_TRACKING_COLUMNS` as what validation and the output header use. Both invariants hold, unchanged.

## 2. The bulk marker — built the way you specified

`outcomes.mark_sent_from_csv()`. The index is built **once, inside the lock**, and every key is then a dict lookup.

### Measured on the live files — 2,787 keys, 58,065 master rows

| approach | time |
|---|---:|
| **build index once + 2,787 lookups** | **0.178 s** (0.176 build + 0.002 lookup) |
| looped `match_indices` (measured on 40 keys, projected) | **121.6 s** |
| **speedup** | **681×** |

The brief's 1,784× was measured at 1,618 keys against a 57,386-row master; at today's larger sizes I measure **681×**, and the earlier index-only run measured 1,185×. The ratio moves with the sample; **the shape is what matters — one pass instead of one pass per key.**

Full dry run against the real export, including reading the 24 MB master: **0.8 s**.

**Correctness is not traded for speed:** on 60 randomly sampled keys the index and `match_indices` returned **identical row sets, 0 disagreements**. That equivalence is now a permanent test.

Everything validated is reused — `normalize_outcome` / `apply_outcome`, `filelock.file_lock`, the timestamped backup, the atomic `os.replace` + `fsync`. The only thing deliberately *not* reused is `match_indices` in a loop.

## 3. dry_run, and why the unmatched list is the point

`dry_run=True` returns the same report and writes nothing — asserted byte-identical in the tests. Unmatched and ambiguous keys are returned as **lists of keys**, never counts alone.

### What the live dry run actually reports now

```
  DRY RUN — nothing written
    keys in file : 2787
    matched      : 2781
    updated      : 0
    took         : 0.782s
    AMBIGUOUS    : 6 — each matches 2+ master rows; NOT stamped.
        bo..@nexaecho.com#54203a
        ja..@fullcircle-mgmt.com#793226
        ar..@spiresagency.com#75e583
        br..@good-direction.agency#5fd43d
        lu..@nge-booking.com#233172
        to..@unitedtalent.com#2317bb
```

**Zero unmatched.** The 6 ambiguous are real and correctly refused: shared agency inboxes where one address represents several artists (United Talent, nexaecho, Spires). Guessing which artist was emailed would put a wrong send date on a real person, so the marker refuses — the same contract `record_outcome` already had.

### The ghost correction, in detail

Before the fix the same run reported 8 unmatched. I checked whether those rows had actually left the master. They had not — **all 8 are still there**:

| master cell (raw) | export writes | why it missed |
|---|---|---|
| `'-…@gmail.com` (×5) | `…@gmail.com` | CSV-injection sanitizer prefix not stripped by `normalize_email` |
| `www.…@gmail.com` | `…@gmail.com` | `www.` prefix |
| `…be.......@gmail.com` | `…be@gmail.com` | seven consecutive dots collapsed by the cleaner |

`build_key_index` now indexes **both** forms — the raw cell and the cleaned address `bio_parser.rank_emails` produces. The invariant it enforces: **anything the exporter can emit, the marker must be able to stamp.** A permanent test locks it.

This also means **there are currently no ghosts at all** in the live export — a claim BL-768 and BL-788 both carried forward, now retired.

## Limits

- **The 681× figure is a projection** for the looped path: I measured `match_indices` on 40 real keys and scaled. Running all 2,787 for real would take ~2 minutes to prove a number nobody disputes.
- **The live master has never been stamped**, so `outcome_stats` is still empty and the pilot's actual reply-by-touch and reply-by-variant numbers do not exist yet. This round makes them recordable, not recorded.
- **`message_variant` is unvalidated beyond length.** Two spellings of the same template (`A` and `a`) will split the stats. A controlled vocabulary would need the sender to declare their variants up front, which seemed worse than letting them name their own.
- **Ambiguous keys are reported, not resolved.** The 6 shared agency inboxes will need a per-row decision — probably by handle rather than email — before those leads can carry a send date.
- **The menu's file picker lists the first 9 CSVs in `output/`**, which today includes the stale historical exports BL-786 flagged. It shows the path so the choice is visible, but it does not warn that a file is two weeks old.
