# BL-771 — Duplicate humans: master is clean (5, all Google Play). But the send path **would double-send 1,395 people** — because dedup is perfect *within* each export file and absent *between* them.

**Date:** 2026-07-31 · **Type:** Audit, read-only · **Spend:** $0.00 · **API calls:** 0

Master opened read-only. Exports run against a **disposable copy** outside the repo. Nothing in
the repo was written. Email local-parts redacted.

## The two numbers you asked for first

**Duplicate humans in master: 5** (10 extra rows). All five are Google Play. **Zero** are
found by more than one source. After the earlier cleanup and the crawl-append fix, master is
effectively clean — 5 duplicate humans in 57,386 rows is 0.009%.

**Would the send path double-send? YES — to 1,395 people, if you use more than one export
file.**

```
ALL_BOT_READY.csv   1,620 addresses   within-file duplicate humans: 0
SEND (2 campaigns)  1,398 addresses   within-file duplicate humans: 0
                    ------------------------------
in BOTH files       1,395            <- every one a second send
union                1,623
SEND-only                3
```

`crossdedup` works. It is applied **inside** `bot_ready_rows` and **inside** `send_list.build`,
and both files come out with **zero** duplicate humans — verified by exact address *and* by
cross-identity person key. What nothing does is dedup **across** the two files, because nothing
in the codebase ever sees both at once. **99.8% of the SEND list is a subset of
ALL_BOT_READY.**

**Send from one file. Not two.** If you send `ALL_BOT_READY.csv` you reach 1,620 people, which
is every address in the SEND files except 3. That is the whole fix, and it costs nothing.

### Evaluating option (c): keep the merge, carry the absorbed handle onto the survivor

**Verdict: it fixes the silent data loss, it does NOT recover the lead for outreach, and as
literally worded it changes the merge behaviour it promises to leave alone.**

**Where it wins.** It is purely additive — it does not touch `_is_mergeable_email`, so
`_selftest` case 1 (`<redacted>@studio.io` shared by `artistx` and `diffhandle` → one person) stays
green and the 7 checks that killed the earlier attempt are never contradicted. That is a real
advantage over option (b), which requires re-litigating a documented, tested contract across
all five funnels.

**Where it breaks, and this is the part to catch before building it.** `row_person_keys` adds
an `h:` identity key for **every** handle in the `instagram` cell:

```python
for h in _handles(row.get("instagram")):
    keys.add("h:" + h)
```

So writing the absorbed handle into `instagram` — the obvious carrier, it is already a
`;`-joined multi-handle field — **makes that handle a permanent identity key on the survivor.**
Next run, any row for Saya Gray merges into `dexterinthenewsagent` on the *handle* as well as
the email. Option (c) as worded would make crossdedup **strictly more aggressive**, which is the
opposite of its stated intent.

**The carrier has to be a field crossdedup does not read.** `extra_socials` qualifies —
crossdedup never touches it, and it already survives into the DM export. But `_dm_extra_contact`
filters to `telegram:` / `discord:` prefixes only, so a `spotify:sayagray` entry would be stored
and **never displayed**. Inert.

**The deeper limit: every exporter emits one contact per row.** `bot_ready_rows` writes one
email, `dm_list_rows` and `ig_dm_list` write one handle. A carried-along handle sitting in a
column changes nothing about who gets contacted — the survivor's manager still receives the one
email, and the absorbed artist is still never reached. Option (c) converts a **silent** loss
into a **recorded** one. That is a genuine improvement — you could audit it, and later mine it —
but it does not put Saya Gray back in the send list.

**If the goal is to stop losing leads, (c) is not sufficient on its own.** It needs either an
exporter that emits per-carried-handle, or option (b). If the goal is to stop losing leads
*silently*, (c) is the cheapest thing that works, provided the carrier column is one crossdedup
does not key on.

## 3. Does the send path honour dedup?

**Within each file: yes, completely.** Verified two ways — exact address, and cross-identity
person key resolved through `crossdedup.PersonIndex` against the master row behind each address:

| file | rows | exact-address dupes | **same-person dupes** |
|---|---:|---:|---:|
| `ALL_BOT_READY.csv` | 1,620 | **0** | **0** |
| SEND (both campaigns) | 1,398 | **0** | **0** |

Both call `crossdedup.collapse_records` internally, and it is doing its job — including the
harder case of one human under two different addresses.

**Across files: no dedup exists at all.** 1,395 addresses appear in both. Of the 1,398 SEND
rows, 1,395 are already in `ALL_BOT_READY`; only 3 are unique to SEND.

BL-765's "union of 1,623 from 1,620" is confirmed and explained: the SEND files are a
**re-derived subset**, not a distinct population. `send_list.build` reads master independently
and re-applies its own gates (ALIVE + campaign attribution), landing on almost exactly the
subset `all_bot_ready` already emitted.

**Cross-file duplicates by different address: 0.** Every one of the 1,395 is an exact address
match, so even a naive exact-match dedup at send time would catch all of them. That is a
smaller problem than it could have been.

## 5. `crawl_suggested.py` — confirmed latent, and it is the more dangerous of the two hazards

**`ig_crawl_enabled = False`.** Confirmed in live config. The path is dead today.

**Confirmed: neither import is present.** `grep -c` returns **0** for `filelock` and **0** for
`crossdedup`. Its imports are `bio_parser, enrich_links, writer, recover_ig_emails,
cluster_detect, resolve_cache, dedup.DedupIndex`.

The write, at `crawl_suggested.py:807-818`:

```python
bak = f"{master_csv}.{now:%Y%m%d_%H%M%S}.crawl.bak"
shutil.copyfile(master_csv, bak)
tmp = master_csv + ".tmp"
with open(tmp, "w", ...) as fh:
    for r in rows:       w.writerow(...)   # every pre-existing row, from a STALE snapshot
    for r in new_rows:   w.writerow(...)
os.replace(tmp, master_csv)
```

**An unlocked full rewrite of all 57,386 rows from a snapshot read earlier.** The atomic
`os.replace` guarantees no torn file — it does not guarantee no lost rows.

### What would happen if it were switched on right now

Two distinct failures, both live given the concurrent-agent activity in this repo:

**(a) Silent row loss — last writer wins.** `crawl_suggested` reads master, spends minutes on
paid IG work, then rewrites every row from its stale copy. Any row appended by another writer
in that window is **erased**. There is no error, no warning; master simply gets smaller. The
timestamped `.crawl.bak` would hold the pre-crawl state, so recovery is possible — but only if
someone notices, and nothing detects it.

`crossdedup.append_leads` documents this exact hazard and defends against it:

> *"CONCURRENCY: the whole read->reconcile->rewrite runs under a cross-process lock on the
> master (filelock.file_lock). Two funnels/agents rewriting the 55k-row master at once would
> otherwise LOSE the first's rows (each reads a snapshot, both rewrite, last rename wins). The
> READ is done INSIDE the lock... The main IG run's per-row append (`writer._append_master`)
> takes the SAME lock, so an append can never be clobbered by a rewrite."*

**`crawl_suggested` is the one writer that does not take that lock** — so it can clobber
appends that the lock was specifically built to protect, and it can be clobbered in turn.

**(b) Duplicate humans re-enter master.** Without `crossdedup`, new leads are checked only by
`dedup.DedupIndex`, which is **handle-level**. A crawled lead whose handle is new but whose
email or IG matches an existing row is appended as a **new row** — creating exactly the
duplicate humans this audit found to be at 5. Every one of those would be a genuine person, and
the crawl is the highest-volume funnel — so this would not stay at 5.

**Which matters more:** (a) is worse. Duplicates are visible and fixable; a full rewrite from a
stale snapshot destroys other funnels' work with no trace beyond a backup nobody is watching.

**This is latent only because of a config flag.** Nothing structural stops it — flipping
`ig_crawl_enabled` to true is a one-line config change, available from the Control Panel, and
this repo currently has multiple agents writing concurrently.

## Limits

- **Absorbed rows leave no artifact**, so §2's "how many were absorbed" cannot be answered from
  master by me or anyone else. 297 magnets and 20.4% of Spotify rows are the *exposure*, not a
  loss count.
- **`reaches_person_directly` is a heuristic.** The 297 are its verdict, not a hand-checked
  list. Some will be legitimate personal addresses on a custom domain.
- **Cross-funnel duplication is measured on funnels that have barely run.** 0 today is real but
  weakly evidenced — 953 rows across four funnels, none exportable.
- **The 1,398 SEND figure depends on the live `config.json` tag pools.** Changing campaign tags
  changes it; the 1,623 union does not change.
- **Counts are a snapshot.** Other agents are appending to master during this audit; figures
  are from a copy taken at run time.
- **`--report` output is the shipping function**, not a re-implementation, but it keys only on
  email/handle/platform-identity. A duplicate human sharing none of those is invisible to it and
  to me.

## Method

Ran `crossdedup.py --report` against the live master (read-only). Group membership, merge keys
and the mergeable-email decisions were reproduced by calling the module's own functions —
`row_person_keys`, `_is_mergeable_email`, `PersonIndex`, `_emails` — plus
`role_policy.kind/reaches_person_directly`, `email_finder._looks_third_party`,
`bio_parser.is_free_provider` and `writer._first_email`, over all 57,386 rows, so every count
comes from shipping code.

`master_leads.csv` was **copied** to a scratch directory outside the repo; `all_bot_ready.build`,
`send_list.build` and `ig_dm_list.build_rows` were run against the copy with output written
there. Cross-file overlap was computed both by exact address and by resolving each exported
address back to its master row and through `crossdedup.PersonIndex`. `crawl_suggested.py` was
read statically and its imports verified by `grep -c`; `ig_crawl_enabled` was read from live
config. Zero API calls, $0 spent, no repo writes, no credential read or printed.
