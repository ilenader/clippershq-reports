## 3. The three things that had just landed, and what each was worth

### 8 lanes — and the pool did not exist yet

**`tiktok_finder.py` was still serial.** BL-1325 recommended the lane pool and BL-1326 landed
the recency gate and lane *seeds* instead, so the per-author loop was still a plain `for`. This
round built it: `discover(..., lanes=1)`, the body extracted to `_process`, every shared write
under a lock, and **`lanes` defaults to 1** so no existing caller changed behaviour.

**Result: 256 pages in 8.8 minutes — 29.1 pages/min against the standing 5.05, a 5.8×.**

Not the 39× of the bare endpoint, and the gap is honest: a page here costs ~2.87 billed calls
plus a contact sheet built from **12 cover fetches over plain HTTP**. 2,455 tiles were fetched.
The vendor stage is no longer the limit; the cover fetches are.

**Parallelising exposed a real latent bug, and the test pins it.** The serial code built each
row's `sheet` field from `result["sheets"][-1]` — the last element of a shared list. Under N
lanes that is *whichever lane appended most recently*, i.e. **another page's contact sheet
attached to this page's row**. That is exactly the defect that once put the wrong account's
posts in a grid. The sheet is now held in a local and never re-read off the list.
`tests/test_bl1327_lane_pool.py` asserts it directly, plus: the default is still serial, 8 lanes
return the same rows in the same order as 1, counters survive concurrent increment, and the cap
is atomic. **8 tests, all green.**

Applied at step 3a, **after the free handle call and before `profile_of`**, so a dropped page
never costs a profile, a sheet, or a judge. **21 pages dropped, 0 undated.**

### The SigLIP probe as ordering — 46 fewer pages judged, and an honest correction

Used as **ordering only**. `allow_drop=False`, nothing dropped, every page reached a judge.
256 sheets embedded in 47.1 min (11.03 s/page, CPU, 0 errors).

| to reach | capture order | **probe order** | pages saved | judge share |
|---|---:|---:|---:|---|
| 50 wanted | 109 | **75** | 34 | 42.6% → **29.3%** |
| **100 wanted** | **211** | **165** | **46** | **82.4% → 64.4%** |
| 125 wanted | 256 | 241 | 15 | 100% → 94.1% |

**Top-25 precision: 84% under the probe against 36% in capture order — 2.3×.**

**The correction he should have.** The headline **AUC 0.9695** was measured on *Instagram*
grids against *his own marks*. Against **this run's TikTok verdicts it is 0.7096** (n = 125
want / 131 reject). Two things changed at once — the platform (a TikTok sheet is 465×992, the
probe was fitted on 934×934) and the target (a judge's verdict, not his mark). **It is still
clearly worth running** — 46 fewer judge calls and 2.3× top-of-list precision — but 0.9695 is
not the number to plan with on TikTok. This is precisely why it ships as ordering: at AUC 0.71
a gate would have thrown away real pages.

### OCR — off, and it is a proof rather than a preference

`config.json` ships `read_on_screen = true`, a measured **32.9 s/page**. It was **not needed**,
and not as a judgement call:

* `judge_author` consumes `on_screen` through **exactly one rule** (`tiktok_finder.py:521`):
  `if not has_text and talking: ok = False`.
* `talking` is False unless `speech_fracs` is passed.
* **`speech_fracs` has no call site anywhere in the module** — it appears only in
  `judge_author`'s own signature and body, and `discover()` does not pass it.

**So the rule can never fire, and OCR changes zero verdicts on this path while costing 32.9
s/page.** On 256 pages that is **2.3 hours saved for nothing given up.** What reads the drawn
text is the contact-sheet grid, which the judge looks at directly.

## 5. Two things worth a follow-up round

**1. The cap counts logical calls, not attempts — so a retry storm can spend past it.**
`api_client.py:307` says it plainly: `http_requests` increments per HTTP attempt "so a 429/5xx
retry storm isn't under-metered". But `run_funnel`'s `reserve()` is driven by `on_call`, which
fires **once per logical call**; the client's internal retries are invisible to it. The ceiling
is therefore enforced on a number smaller than the one the vendor bills. My own top-up pass saw
271 attempts for 256 logical calls (**5.9% retries**) on a quiet minute; the 502 bursts this
project has recorded are far worse than that. **This is a code fact, read not inferred, and it
is the one thing here that can cost real money unexpectedly.** The fix is one line — drive
`reserve` off the client's attempt counter.

**2. A repo module shadows a third-party package and produces a completely false error.**
`clippershq/filelock.py` shadows `filelock`. With `clippershq/` first on `sys.path`,
`huggingface_hub` cannot import `BaseFileLock`, and open_clip re-reports it as:

> `Failed to download weights for tag 'webli': Hugging Face hub model specified but package not
> installed. Run 'pip install huggingface_hub'.`

**Every word of that is wrong** — huggingface_hub 1.21.0 is installed, `hf_hub_download` imports
fine, `_has_hf_hub` is True, and the weights were already cached. Following the message
installs a package that is already there and nothing changes. It cost three failed runs here.
Appending `clippershq/` instead of inserting it fixes it.
