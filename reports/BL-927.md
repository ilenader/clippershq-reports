## 1. The number: the master finalise did not land

`writer.migrate_master_csv()` rewrites all 58,000 rows of `master_leads.csv` to a temp file and then calls a bare `os.replace` (`writer.py:839`). BL-914 predicted this was exposed. It is much worse than predicted.

**VERIFIED against the real function** — not a mock — under one concurrent reader, 40 migrations per row:

| reader shape | duty | landed | **FAILED** | rate |
|---|---|---|---|---|
| tight loop, no gap | 100% | 13 | 27 | **67.5%** |
| 1 ms hold, no gap | 100% | 6 | 34 | **85.0%** |
| 1 ms hold, 20 ms gap | 5% | 40 | 0 | 0.0% |
| 5 ms hold, 100 ms gap | 5% | 37 | 3 | 7.5% |
| 20 ms hold, 500 ms gap | 4% | 39 | 1 | 2.5% |

An earlier run of the same harness, before it modelled a gap at all, recorded **100.0% — 40 of 40 migrations failing, not one landing.**

**What a failure means here is the part worth sitting with.** The migration read every row, mapped every field, wrote a complete and correct temp file, and then **did not install it**. The work was done and thrown away. The caller sees a `PermissionError` — so this is not silent corruption, it is a loud failure *provided somebody is catching it*, and `migrate_master_csv` is called from a startup banner path that recommends running it.

`docs/PRECONDITIONS.md` lists a growing `master_leads.csv` under **NOISE**, on the grounds that "`os.replace` is atomic — you get the old file or the new one, complete, never a torn row." **That sentence is true and it is not the whole story.** Atomic describes what a reader sees. It says nothing about whether the writer succeeded. BL-914 annotated that row; this round measured what the gap costs.

## 3. VERIFIED after — and the LIMIT, stated plainly

Same harness, same shapes, after the change:

| reader shape | duty | before | **after** |
|---|---|---|---|
| tight loop, no gap | 100% | 67.5% | **0.0%** |
| 1 ms hold, no gap | 100% | 85.0% | **50.0%** |
| 1 ms hold, 20 ms gap | 5% | 0.0% | **0.0%** |
| 5 ms hold, 100 ms gap | 5% | 7.5% | **0.0%** |
| 20 ms hold, 500 ms gap | 4% | 2.5% | **0.0%** |

**Every realistic reader shape goes to zero.** That is the result.

**The 50% row is the honest limit and I am not going to bury it.** A retry can only ever succeed in a gap. A reader that reopens the instant it closes — 100% duty cycle — never offers one, and no retry budget fixes that; it is a lock wearing a reader's clothes. My first version of this harness had *no gap parameter at all*, so it measured only that pathological case and made the guard look far weaker than it is. Reporting that number without the duty-cycle column would have been measuring the harness, not the fix. The two 100%-duty rows are the retry's limit, not its performance.

If a real reader ever holds `master_leads.csv` for more than 1.2 s, the guard raises — loudly, deliberately, because a caller that could not install its file must never be told that it did.

## Honest limits

- **The suite is fully green and this is the first time I can say that without a caveat.** 110/110, 4,226 checks. It has grown 96 -> 98 -> 101 -> 104 -> **110** across five rounds today, so the denominator is not comparable with any earlier figure.
- **`clippershq/main.py:124` is still bare.** One site, held by BL-923 all round. Exempted by name, with its owner, so the debt is visible rather than skipped.
- **The 50% pathological-reader failure is real and unfixed.** Retrying cannot beat a reader that never closes the file. If that shape ever appears in production the answer is a lock or a reader that lets go, not a longer budget.
- **I measured 2,000 rows, not 58,000.** The race is on the `replace`, not the write, so a smaller file yields more replaces per second and therefore more samples. A 58,000-row file spends longer writing and would be hit *less* often per call — the rate I report is not the production rate, it is the rate at which the exposed operation loses.
- **`ig_client.py` and `repost_finder.py` were ` M` when I edited them** — released, but carrying another round's uncommitted work. Edited surgically, same disclosure BL-914 made about `claim.py`.
- **`docs/CORRECTIONS.md` entry is outstanding**, held by MEMEBOT-055.
- **I changed no caller.** Every guarded site now raises after 1.2 s instead of immediately; nothing was audited for whether its caller handles that better than it handled the instant failure. The failure got rarer, not better-handled.
- **Threads, not processes.** Both harnesses use a reader thread. Windows sharing violations are per-handle, not per-process, so the mechanism is identical — but a separate process is the true production condition and I did not test it.
- **These rates vary run to run and I am quoting single runs.** The pathological rows moved between 67.5% and 100% across three executions of the same harness on the same code; the tree has a dozen rounds competing for disk. Treat the realistic-shape figures (0% after, across three shapes) as the load-bearing result and the 100%-duty rows as an order of magnitude, not a constant. This is the same caveat `run_all.py` now prints about suite counts: a measurement taken while the tree moves is a moment, not a property.

## Say it plainly

The pattern was right and the call was failing. Every shared file in this project is written the same careful way — temp file, `fsync`, atomic replace — and on Windows that last step simply does not happen while anyone is reading. For `master_leads.csv` that meant a full 58,000-row migration could complete perfectly and install nothing, up to 85% of the time, with no counter anywhere recording that the file it produced was discarded.

It is the same failure this session keeps finding, one layer further down: a dead `claim.py` returned zero rounds, a piped scanner returned success, a `;`-chain returned `echo`'s status, and now an `os.replace` that raised was treated by twenty-three call sites as an atomic write that happened. Each time the code could not tell *"it did not work"* from *"it worked"*. The fix is never more care — it is making the failure representable, and then making a test go red when someone writes the old shape again.
