## 1. What is new, counted two ways, and reconciled

### The counts, and the arithmetic that has to close

Both files are ~136,000 **physical lines** for ~62,000 **records**, because 74,460 newlines sit
inside quoted bio fields. `wc -l` answers a different question. So each file was counted by the
app's own reader **and** by a byte-level quote-parity scanner that shares no code with it
(`scratch/bl1301_diff.py`).

| | handover | today |
|---|---:|---:|
| **WAY A** — `csv.DictReader` | **62,092** | **62,675** |
| **WAY B** — byte-level quote parity | **62,092** | **62,675** |
| agree | ✔ | ✔ |
| physical lines | 136,553 | 137,136 |
| newlines inside quoted bios | 74,460 | 74,460 |
| arithmetic | 62,093 + 74,460 = **136,553** ✔ | 62,676 + 74,460 = **137,136** ✔ |
| CRLF record boundaries | 62,093 | 62,676 |
| columns | 72 | 72 (identical) |

The embedded-newline count is **identical in both** — 74,460 — which is its own check: the 583
new rows added no bios containing newlines, and nothing rewrote an old one.

### The diff is by identity, not by row position

A positional diff would have called the one modified row "new". Identity is the key the writer
and `crossdedup` use: normalised handle + platform, falling back to normalised email.

**583 new · 0 removed · 1 modified** (`source_hashtag`, a funnel tag accumulating on a row that
already existed — exactly what BL-1288 measured from the other direction).

### Reconciling against the run's own figures

BL-1288 reported **362 emails found, 360 distinct, 351 new rows with an address, 9 merged, 302
in the send file**. The diff says **583 new records, 352 of them with an email**. 351 against
352 is a real disagreement and "pick a number" is not an answer, so
`scratch/bl1301_reconcile.py` resolved it from both independent sources — the checkpoints (what
was paid for) and the master (what was written):

| | |
|---|---:|
| distinct addresses in the checkpoints | **360** |
| landed on a **new** row | **351** |
| **merged** onto a pre-existing person | **9** |
| found but absent from master | **0** |
| on a stamped row but absent from the checkpoints | **0** |
| **351 + 9** | **360** ✔ |

**So where does 352 come from? Two of the 583 new rows carry the same address.** 352 rows,
351 distinct addresses. BL-1288's "351" was a distinct-address count and the row count is 352;
both are right, and they are not the same quantity. Everything closes:

```
583 new records  =  352 with an email  +  231 handle-only
352 rows with an email  =  351 distinct addresses  (two rows share one)
351 new  +  9 merged  =  360 distinct addresses found   ✔ the run's own figure
352 rows  −  40 role inboxes  −  9 partition collisions  −  1 in-run duplicate  =  302 shipped ✔
```

**And one thing the run could not have known: 10 of the 351 addresses are already in his
copy**, attached to a different artist — management and agency addresses covering more than one
act. They are new *rows* to master but not new *people* to him, and the merge script's identity
check catches them on his side rather than mine.

**What it does not ship, and why:**

* **not `master_leads.csv`.** Replacing his file would destroy every lead he has found since
  the handover. Only he knows what is on his side.
* **not `resolve_cache.json`.** BL-1279 set this principle and it still holds — overwriting his
  cache re-opens every resolve he has already paid for. **Ship only what he lacks.**

**The merge script's five safety properties**, each verified in §4:

1. **Identity, not row position.** Handle + platform normalised, else email.
2. **Refuses to run twice** — a receipt beside his database records the update id.
3. **Backs up first** — `master_leads.csv.before_update_<stamp>.bak`, before a byte is written.
4. **Temp file + `os.replace`** — an interruption cannot leave half a file.
5. **Refuses a column mismatch** rather than writing a misaligned row, and says which columns.

### Two corrections I made to my own work here

**The identity rule was wrong for Google Play rows.** `crossdedup` excludes `google_play` from
handle keys because that column holds a **developer name**, not an account — "Garena
International I" is a company, and two apps by one publisher are two rows. My first identity
collapsed them, which showed up as **15 duplicate identities already present in his baseline**.
Corrected to match `crossdedup`, that falls to **8** (rows with neither handle nor email, keyed
on display name) — and both figures are **pre-existing in his copy, unchanged by the merge**.
The delta itself is 583 either way: every new row is `platform=instagram`, so the rule never
bites on today's data. It was still worth fixing, because the script will be run again.

**I wrote a hidden file.** The receipt was `.leads_update_receipt.json` — a leading dot, which
is invisible to every glob and is the exact hazard flagged for handles (2.08% of them start
with one, and it has hidden data twice). A receipt he cannot see is a receipt he will not find.
Renamed to **`leads_update_receipt.json`** and the off-tree proof re-run from a clean copy.

**Of the 583 new records, 0 have a leading-dot handle** — checked, not assumed.
