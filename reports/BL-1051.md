## 0. THE CAP, PROVEN TO BIND BEFORE ANY MONEY MOVED

The brief's condition was that an unbindable cap means no paid run. Three facts were
established **before the first candidate was looked at**, and the script exits 2 without
spending if any fails:

| check | result |
|---|---|
| `resolve_budget` returns exactly the declared ceiling | **$0.20** = min(per-run 0.20, lifetime room 38.66 against a 50.00 lifetime cap on 11.3381 spent) |
| the cap governs **every** paid leg | `PAID_VENDORS == ('ig',)` — retrieval is the only billed leg, so this is a claim about the whole set |
| an uncapped run is **refused**, demonstrated not read | `UncappedRun`: *"REFUSED: this batch would write real dollars to spend.json with no ceiling on them."* |

The cap is checked **before** each candidate on the **worst case** (`max_pages × cost_per_call`),
not after — a cap checked afterwards is always exceeded by exactly the call that broke it.

**A projection I got wrong, and the correction.** I predicted **$0.1969** for 100 by scaling
MEMEBOT-115's $0.00197/clip, and wrote in the claim that the cap would nearly bind. Actual:
**$0.0690**, 2.9× lower. The reason is retrieval pages per clip, not price: this run metered
**115 pages across 106 attempts = 1.09 pages/clip**, where 115's mix cost roughly three. The
per-clip cost of this pipeline is **not a stable constant** to extrapolate from — it is a
function of how many rendition pages each clip needs.

## 2. VERIFIED MECHANICALLY — from the files, never from an exit code

`RESULT edit: status=ok` is the renderer's opinion of itself; the first live batch produced a
5-second video from a 61.8-second clip and ffprobe called it healthy. Every number below is
re-derived from the file.

| check | result |
|---|---:|
| file exists | **100 / 100** |
| video stream (ffprobe) | **100** |
| audio stream (ffprobe) | **100** |
| not silent (mean volume > −60 dBFS) | **100** |
| duration inside [8.0, 20.0] | **97** ⚠️ |
| configured track beats **every other store track** | **81 of 82 testable** |
| joinable ledger record | **82** ⚠️ |
| ceiling provenance present | **100** |

**The track test, and why each piece of it is there.** Signed 40–250 Hz envelope correlation
against the **APPLIED** window (`applied_start_sec`/`applied_end_sec`) — *not* the marked
hook, because `fit_window` widens it: on the first record the hook is `7.828–22.714` and the
applied window is `7.83–35.03`, so correlating against the hook compares the render to audio
it never used. **Signed**, because an inverted match is not a match. **Bounded lag** (±2 s),
because an unbounded search finds a peak in noise. And **every other store track as the
null**, so the claim is "this track beats the alternatives", not "this number looks big". It
separates cleanly: a typical render scores **0.9904** against its own track and 0.07–0.16
against the other three.

**One genuine miss (1 of 82):** `3953565260068939452` scored **0.0964** for its own track
against **0.1522** for the best other — margin **−0.056**, both low. Reported as a miss rather
than explained away.

## 4. THE RARE FAILURES — 6 of 106 attempts = **5.66%**

| status | n | cause |
|---|---:|---|
| `failed:render` | **5** | 3 carry `join_reason: "song is not in the store at all"`; **2 record no reason at all** |
| `failed:unretrievable` | **1** | retrieval exhausted its pages |

**At n=1,000 that is ~57 failed attempts**, and **~19 of them would carry no recorded cause** —
the two unexplained render failures are 1.9% on their own. Nothing retried; no silent file
(all 100 have audio above the floor); no duplicate.

### THE 18% DEFECT — a bed that is not in the store

**18 of 100 successful renders use `scratch/bl691_audio/*.m4a`, not the curated store.** The
pipeline is not confused about this — it stamps every one of them:

```
join_reason : "song is not in the store at all"
joinable    : false          hook_id : null          confidence : "none"
```

The **not-joinable set and the track-untestable set are exactly the same 18 clips** (asserted,
not assumed). So 18% of the batch ships with an **uncurated bed, no hook window, and a ledger
record that cannot be joined** — and the *same condition* causes 3 of the 5 render failures.
**At n=1,000 that is 180 videos** the outcome loop cannot attribute.
