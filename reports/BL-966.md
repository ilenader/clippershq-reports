# BL-966: the git index is shared, so `git commit` is a race — it now refuses, and 29 commits already admit they lost that race

**Date:** 2026-08-02 · **Type:** Governance, enforced and proved end to end · **Spend:** **$0.00 · 0 paid calls**
Claim filed with **repeated `--write` flags** (12 paths, each its own element). `tools/claims_read.py --holders` — **not** `claim.py` — run on every target before writing; all FREE. `git status --porcelain` read with the columns kept apart: `M ` staged, ` M` unstaged. `config.json` unmodified (`sha256 5fb1a8a2…`, 161 keys, 5 campaigns unchanged). No paid call, no network.

**The headline is not the fix, it is the count.** `git add` + `git commit` is a read-then-write on a file ten rounds share. **29 commits in this repo's log already say so in their own messages** — "NOT ALL MINE", "not my work", "wip: snapshot eleven in-flight files from six concurrent rounds", "staging race". Every one is a commit where the mechanism forced a choice between **losing** somebody's work and **misattributing** it.

## 1. The mechanism, measured rather than reasoned about

A probe repository with a hook that only records what git showed it. Two files staged, one commit at a time:

| form | `GIT_INDEX_FILE` the hook sees | what the hook sees staged |
|---|---|---|
| `git commit` | `.git/index` | **both files** — the shared index |
| `git commit -a` | `.git/index.lock` | **both**, plus unstaged worktree edits |
| `git commit -- mine.txt` | `.git/next-index-<pid>.lock` | **only `mine.txt`**; `theirs.txt` survives staged |
| `git commit --amend` (message only) | `.git/index` | nothing |

**`git commit -- <paths>` is immune by construction:** git snapshots the pathspec into a *temporary* index and commits that, leaving the shared one untouched. That is git's behaviour, not our carefulness, and it is the whole fix. `-a` is the worst form and is distinguishable — `index.lock`, not `next-index-*`.

This is re-measured against real git by `tests/test_commit_guard.py::GitGivesUsAScopedIndexForAPathspecCommit`, because if it were false every other test here would be theatre.

## 2. What the existing check could not do, and why

`claim.py staged` asks one question: *do the staged paths span two live rounds?* It is a good question and **it is not the one that failed**. BL-958 ran it and was told:

```
staged paths belong to one round: BL-961
```

**True. Correct.** And BL-958 committed BL-961's nine files under a BL-958 subject anyway, because nothing compared the round that *owns* the paths to the round whose *name* is on the commit. That name exists in exactly one place — the message — and **`pre-commit` is never given the message**.

So the new enforcement is a **`commit-msg`** hook. `pre-commit` keeps its two checks and now carries a comment saying precisely which half it cannot do.

### The two rules

1. **Foreign paths — every form.** A path whose most-specific live claimant is a round other than the one in the **subject line** → refused. The `b6abeee` and BL-958 shape. Applies to pathspec commits too: scoping fixes the *race*, not the *authorship*.
2. **Unscoped commits — only while other rounds are live.** A bare `git commit` may carry only paths the committing round declared. In a tree with **no** other live round the index is not shared and this does not apply — a guard that fires where it cannot be right is a guard people switch off.

### The escapes are trailers, not flags

```
Claim-Override: BL-899        # committing BL-899's path, deliberately
Index-Override: <reason>      # making an unscoped commit, deliberately
```

Both land **in the commit**. That is the entire difference from `--no-verify`: a year later the record says an override happened and why. `--no-verify` leaves nothing.

## 4. `git worktree`: tested, and NOT adopted

Per-round worktrees would remove this class outright. I created a real worktree from this repo, measured it, and removed it.

**It works mechanically.** `.git/worktrees/<name>/index` is genuinely separate, and `core.hooksPath` is inherited so the hooks still run.

**And every piece of shared runtime state is gitignored, therefore absent:**

| absent | consequence |
|---|---|
| `spend.json` | **the money ledger.** A worktree round creates a second one and computes its cap against an empty ledger. Every `--cap` becomes advisory. |
| `.claims/` | **the registry.** Measured: `claim.py list` inside the worktree printed **`no rounds in flight`** — the one tool whose job is to say who else is here would answer *nobody* to all ten rounds. |
| `config.json` | no campaigns, no keys, no knobs |
| `master_leads.csv` · `clip_library/` · `memebot/` · `state.json` · `output/` · `logs/` | the leads, the 2,003 clips, the renderer, the wells, the send files |

**And one branch cannot be checked out twice.** Measured:
```
fatal: 'checkpoint/session-2026-07-23-full-day' is already used by worktree at '<main>'
```
Ten rounds would need ten branches and ten merges per session on the same files, which **moves** the commingling from the index into merge conflicts rather than removing it.

**Verdict: not now, and the blocker is not git.** The load-bearing prerequisite is that `.claims/` becomes location-independent — it is `CLAIM_DIR = ".claims"`, relative to the CWD, with no override. Until that exists a worktree is a strictly worse trade: it fixes an attribution fault that now refuses at commit time, and silently breaks money accounting and round coordination in exchange. `spend.json` already has its indirection (`$CLIPPERSHQ_SPEND_FILE`), but nothing *enforces* it and an unset one is a silent second ledger. Full assessment and the adoption order in `docs/GIT_INDEX.md`.

## 6. Off-brief: two bugs the tests found in my own guard

* **`claim.dirty_declared()` read the claim from one repository and `git status` from another.** `CLAIM_DIR` is `.claims` relative to the CWD; my first version defaulted `repo` to `__file__`'s parent. Under a worktree — the very setup item 3 evaluates — it would have reported a **dirty tree as clean**. Caught by the test chdir'ing into a throwaway repo and getting `[]` for a file it had just created. Both `tools/commit.py` and `tools/commit_guard.py` now resolve the repository with `git rev-parse --show-toplevel`, never from `__file__`.
* **"no repository" was being treated as "cannot see".** The first fix raised `RuntimeError` whenever `rev-parse` failed, which broke `tests/test_claim.py` (it drives the registry in a bare temp dir) and would have made `claim.py end` unusable outside a checkout. *No repo* means there is no such thing as uncommitted work; *`git status` failed inside a repo* means blindness. Only the second refuses now.

**A design note I want on the record:** the guard **fails closed on blindness and open on a bug.** If the commit contents cannot be read it refuses. If the guard itself raises, it prints an unmissable banner and lets the commit through — because a hook that runs for ten rounds and can brick the repository is a hook somebody disables permanently within the hour, and then there is no guard at all.
