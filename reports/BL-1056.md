# BL-1056 — the run explains itself now, and the proof caught six things on the way

The operator is about to run this for real and expects it to fail somewhere. The question
was whether he could then read **exactly what happened, without guessing and without
reading code**. He can now, per clip, with the number that decided it.

The more useful half of this round is that **the harness written to prove it passed 5 of 5
on its first run while three of the five plants never executed** — a scanner printing PASS
after reading zero files, committed inside the round whose subject is that exact defect.

**Three kinds of silence are now distinguished**, and the second and third could not be
expressed before:

| | meaning | how it was invisible |
|---|---|---|
| `SILENT` | ran, produced nothing | already existed |
| `NEVER RAN` | the run returned before reaching it | **it was simply not a row** — a run that stopped before retrieval looked identical to one that retrieved nothing |
| `DEGRADED` | succeeded, and the output is wrong anyway | every count balanced, so nothing could fire |

`DEGRADED` is what a song falling through to the local corpus is: a **finished** video that
can never earn rotation, and nothing downstream will ever complain about it.

## 2. The value, not just the verdict — and it was already being computed

`gate()` built the string `"duration 7.4s outside [7.626, 20]"`. `run_batch` then ran

```python
_primary = re.sub(r"[-+]?\d[\d.,]*", "N", _bad[0])
```

so reasons would **group** — which is correct, and which also destroyed the only copy of
the number. The operator was shown `duration Ns outside [N N]`: a reason with the digits
deliberately removed. **The measurement existed and was deleted one line before it was
logged.**

So the numbers now travel *beside* the reason instead of inside it. `gate_detail()` returns
`{reason: (measured, threshold, op, unit)}`, the reason stays the grouping key, and the log
aggregates to a **range** per reason (`3.1s–7.41s < 7.626s`) while keeping the exact value
per clip. It also names **which side** of a range was missed, because 7.41 and 41.0 are
different problems with the same "outside [7.626, 20]".

`gate()` itself is unchanged — 2-tuple, three callers, no churn.

## 3. Five plants, and the harness that lied about them

`scratch/bl1056_plants.py` plants five failures across four stages, runs the real
`run_batch` with **both fetchers injected** (no network, no paid calls, `$0.00`), and then
reads the result **as text** — the terminal summary plus the written record. It never asks
the objects, because that would prove the data exists rather than that a human can find it.

| plant | stage | explained by the log alone | answerable by `--clip` |
|---|---|---|---|
| missing audio class | gating | yes | yes |
| under the duration floor | gating | yes — **`7.41s < 7.626s`** | yes |
| unreachable clip | retrieval | yes — 404, named | yes |
| song with no match | song | yes — **DEGRADED**, then rendered | yes |
| vendor 502 | retrieval | yes — **`502 Bad Gateway`** | yes |

### It passed 5 of 5 before any of that was true

The first run printed all five EXPLAINED with `injected http calls 0`. The fixture set
`audio_class="music"` — **not a member of `RENDER_AUDIO_CLASSES`** — so all seven clips
were refused at the gate, three plants never reached the stage they were testing, and the
word-match scored them anyway because it searched the whole run blob rather than the clip's
own explanation.

Three fixes, and each is the same lesson: **the fixture read the live constant**
(`CP.RENDER_AUDIO_CLASSES[0]`), the check was scoped **per clip**, and a plant must be shown
to have **reached its stage** before it can score.

### And the marker was hiding inside the id

The 502 plant required the word `"502"` — and was named `p5_vendor502`. It passed on its
own id while the vendor's actual answer was being discarded upstream. Renamed
`p5_vendorbad`, required words `502` **and** `Bad Gateway`, and only then did the real
defect below surface.

## 4. Six defects, three of them in shipped code

| # | where | what |
|---|---|---|
| 1 | **my harness** | fixture used a non-existent audio class; 3 of 5 plants never ran and it still passed |
| 2 | **my harness** | the required marker was a substring of the fixture's own id |
| 3 | `decision_log.explain_clip` | answered *"what happened to this clip"* **without ever naming the clip** |
| 4 | `decision_log._load_runs` | returned the wrapper `{"runs": [...]}`, so `--clip` crashed with `'str' object has no attribute 'get'` **the first time it was pointed at a real file** — the plant harness passes the record in directly and never touched that path |
| 5 | `clip_media.retrieve` | kept `type(exc).__name__` and threw the message away, so a `502 Bad Gateway` reached the log as `download failed: OSError` |
| 6 | `decision_log._HANDLE` | **a real lead-data leak** — see below |

### The leak

`_HANDLE` was `(?<![A-Za-z0-9_])@[A-Za-z0-9._]{2,30}`. The `_` in the lookbehind means a
handle preceded by an underscore does not match — and **a clip id is `<pk>_<user_id>`**, with
the walk building ids from account handles. So `123_@a_real_creator_handle` scrubbed clean
standalone and survived **unchanged into the terminal summary, the written `runs.json`, the
`--clip` answer and `as_dict()`**.

The lookbehind exists so an email's local part is not re-matched as a handle; `_EMAIL` runs
**first** and has already replaced any real address, and an alphanumeric before the `@` still
blocks the match. Dropping `_` only widens what counts as the *start* of a handle — the safe
direction. All five surfaces are clean now, and the repository's own scanner passes over the
written artefact under its **private** profile.

## 5. Redaction, checked on the artefact and not only the report

BL-1038 verified the fields that existed then. This round adds **five more places** a
caller-supplied string lands, and a redaction proof only ever covers the fields it was
written for: the trace **key** (`clip_id` — a dict key, so scrubbing later is too late), the
trace reason, arbitrary `**extra` (key *and* value), `warn()` text, and `expect` stage names.

`scratch/bl1056_redaction.py` puts a credential-shaped token, an email and a handle through
all of them and checks **five surfaces**: terminal, written `runs.json`, `--clip`,
`trace_lines()`, `as_dict()`. All clean. The needles are asserted **detectable** first, so a
green result cannot mean the fixture was inert, and the run's artefact is passed to
`scan_report_for_secrets.py --profile private` — an independent rule, because two components
disagreeing about what a secret is was the BL-1029 shape.

### What I got wrong

Beyond the two harness defects above: I wrote the trace, the CLI and the tests before
pointing the CLI at a file on disk, and the tests passed because they used the same in-memory
object the writer produced. **The read-back path was the last thing I exercised and the first
thing that was broken.** `test_decision_log_trace.py` now has a class that writes a record
and reads it back through the file, which is the path the operator uses and the only one that
would have caught it.
