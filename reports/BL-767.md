# BL-767 — SPEC: the two gates protect nothing on client funnels, there is a third gate nobody has counted, and the fix is one declared field — not a verdict default

**Date:** 2026-07-31 · **Type:** Spec, READ-ONLY · **Spend:** $0.00 · **API calls:** 0
**Nothing implemented.** Pipeline code read-only; predicates imported and run, rows copied in memory. All output in `scratch/`.

Follows [BL-765](BL-765.md) (888 stranded) and [BL-764](BL-764.md) (the verdict gate).

---

## Answer first: are the gates protecting anything?

**The verdict gate: YES on the funnel it was built for, NO — nothing at all — on client funnels.**

A gate can only protect if the field it reads *varies*. It does not:

| funnel | rows | distinct verdicts | distribution |
|---|---:|---:|---|
| hashtag crawl (TikTok+IG) | 55,349 | **4** | EDITOR 34,971 · LIKELY 9,348 · UNSURE 7,795 · CREATOR? 3,225 |
| spotify_finder | 1,233 | **0** | empty ×1,233 |
| twitch_finder | 534 | **0** | empty ×534 |
| google_play | 131 | **0** | empty ×131 |
| kick_finder | 37 | **0** | empty ×37 |
| email_finder | 60 | **0** | empty ×60 |
| repost_finder | 42 | **1** | `MEME_PAGE` ×42 |

On the hashtag crawl the gate blocks **1,211 emailable rows** — 619 `UNSURE`, 592 `CREATOR?`. Those are people the crawl found and judged *not to be editors*. On a funnel whose purpose is to **hire** a clipper, refusing to email a non-editor is a genuine protection, and it should stay.

On the four client funnels the field has **zero variance**. The gate is not filtering — it is a **constant-false predicate**. It cannot distinguish a good Spotify artist from a bad one because it has never been told anything about either. It excludes 100% of them **by accident**, which is the definition of a gate that protects nothing.

**The liveness gate: NO, and it is structurally impossible, not merely unpopulated.**

| funnel | rows | `date_source == deep` | `last_post_date` | can ever be ALIVE |
|---|---:|---:|---:|---:|
| hashtag crawl | 55,349 | 2,118 | 55,312 | 1,952 |
| **all four client funnels** | **1,935** | **0** | **0** | **0** |

`writer._activity_of` returns `ALIVE` only when `date_source == "deep"`. No client funnel writes either field, and none ever will through the current path — there is no "deep post check" for a Spotify artist. `send_list.build` then cuts on `activity != "ALIVE"`. **Client rows resolve to UNKNOWN and are cut, permanently, by construction.**

The concept is also wrong on its own terms. `ALIVE` asks *"is this account still posting?"* — the right question for a clipper you want to hire, and the wrong one for a musician you want to sell to. A musician who has not posted a TikTok in a year may have just released an album. Their liveness signal exists (`latest_release_date`, last stream, last app update) and **is not persisted** — `spotify_finder.find_contact` computes `latest_release_date` and the write path drops it.

## The gate cuts UNKNOWN while its own comment forbids exactly that

This is not an oversight in a corner; it is a contradiction inside one file.

```python
# send_list.py, line ~56
# ALIVE first. UNKNOWN is "we could not check", never "bad" — it sorts BETWEEN alive and
# dormant rather than being treated as dead (the never-cut rule).
_ACT_RANK = {"ALIVE": 0, "UNKNOWN": 1, "DORMANT": 2}

# send_list.py, line ~233
if activity != "ALIVE":
    continue                       # <-- cuts every UNKNOWN
```

`writer._activity_of`'s docstring says the same thing: *"unknown is 'we could not check', never 'bad'."*

**2,678 rows carrying an email resolve to UNKNOWN and are cut. 1,293 of them are client-funnel rows.** The sort key even reserves a middle rank for UNKNOWN that nothing can ever occupy, and the comment at line 268 anticipates the widening — *"all ALIVE here, but the key keeps the contract explicit if the filter ever widens."* The design intent is already written down. Only the filter disagrees with it.

## A third gate nobody has counted

BL-765 identified two blockers. There are **three**. Even with a verdict *and* a liveness signal, client rows would still not reach a send list:

```python
# send_list.build
name = attribute(r, pools)      # campaign attribution by source_hashtag
if name not in out:
    continue                    # AMBIGUOUS / UNATTRIBUTED -> not sendable
```

Measured against the live config (`ZHUS`, `PANICBABY`, `STRAENGE`, `DAYLIGHT`, `ANIME15K`):

| funnel | attribution |
|---|---|
| hashtag crawl | `PANICBABY` (400/400 sampled) |
| **spotify_finder** | **UNATTRIBUTED 400/400** |
| **twitch_finder** | **UNATTRIBUTED 400/400** |
| **google_play** | **UNATTRIBUTED 131/131** |
| **kick_finder** | **UNATTRIBUTED 37/37** |
| repost_finder | UNATTRIBUTED 42/42 |

Campaigns are defined by **hashtag pools**. A client row's `source_hashtag` is the literal string `spotify_finder`, which matches no pool. **Any fix that addresses only verdict and liveness will unstrand nothing on the `send_list` path.** This is the gate that would have made a two-part fix silently fail.

## The recommendation: declare the lead's KIND; make the gates kind-aware

**Not** a per-funnel verdict default, and **not** a fifth exporter.

### Why not a verdict default

Writing `verdict = "EDITOR"` (or `"CLIENT"`) on Spotify rows unlocks `BOT_READY` in one line, and it is the wrong fix:

- It **overloads a field with a meaning it does not have.** `verdict` answers "is this person an editor". A Spotify artist is not an editor and is not *failing* to be one — the question does not apply. Writing a value makes the column lie for every future reader, including the next audit.
- It **does not fix `send_list`** — liveness and attribution still cut. It buys `ALL_BOT_READY` only, which BL-765 shows is not the file n8n watches.
- It **encodes the bug as data**, so the next person to look at `verdict` cannot tell a real editor judgement from a placeholder.

### Why not a separate client exporter

BL-765 already found **four exporters with four different gate stacks**, two of which disagree on quality. A fifth path means the suppression list, the dedup, and the bounce rules must be maintained in five places. The divergence is already the problem; adding to it is not the fix.

### The spec

**1. One new declared column: `lead_kind` ∈ {`clipper`, `client`}.**

Written by every funnel at append time. `clipper` = we want to hire them (hashtag crawl, repost finder). `client` = we want to sell to them (Spotify, Twitch, Google Play, Kick, and the email finder when list-driven).

**A missing `lead_kind` is `unroutable` — never a default of either kind.** Unroutable rows are counted and reported loudly at export, never silently dropped and never silently sent. This is the point that satisfies item 4: routing is **declared per row**, never inferred from a field happening to be empty or a filter happening to remove the exceptions.

**2. Make each gate state which kind it applies to.**

| gate | `clipper` | `client` |
|---|---|---|
| editor verdict ∈ {EDITOR, LIKELY} | **applies** — keeps blocking 1,211 non-editors | **does not apply** — no such judgement exists |
| liveness `ALIVE` | applies (deep date) | applies against a **kind-appropriate** date (see 3) |
| campaign attribution | applies (hashtag pools) | attribute to a client campaign, else `DIRECT` — never `UNATTRIBUTED` |
| curation-page, bio-link quarantine, dedup, suppression | **apply to both** | **apply to both** |

The gate that replaces the verdict for a `client` row is **the funnel's own qualifying criteria**, which already ran before the row was written: Spotify's listener floor + country + language gates, Google Play's install floor + monetisation, Twitch's viewer floor. Record it as `qualified_by` (e.g. `spotify:listeners>=50k,country=GB,lang=en`) so the bar is auditable per row rather than implied by funnel membership.

**3. Generalise liveness instead of special-casing it.**

Replace the read of `last_post_date`/`date_source` with a kind-neutral pair — `last_activity_date` + `activity_source` — where each funnel writes its own meaningful recency: deep post date for a clipper, latest release for a Spotify artist, last stream for Twitch, last app update for Google Play. `_activity_of`'s existing three-state logic then works unchanged for everyone.

**And restore the never-cut rule in `send_list.build`:** rank by `_ACT_RANK` (which already has a slot for UNKNOWN) instead of cutting on it. That is what both comments already say the code does.

## What could go wrong

1. **Unstranding before suppression is fixed multiplies the damage.** BL-765 found *nothing* is suppressed today — 20 dead-domain rows, 44 role inboxes, 26 agency addresses, 109 dormant and 101 over-180-day rows all ship. Adding 888 addresses to a path that cannot suppress anything makes the blast radius bigger, not the outcome better. **Sequence: suppression first, then unstranding.** This is the single most important line in this spec.
2. **The existing 1,935 client rows carry no quality context at all.** Measured: `country` 0/1,935, `email_quality` 0/1,935, `spotify_monthly_listeners` 0/1,935, `display_name` 0/1,935. BL-761 added those columns and the write path, but **only future runs populate them.** So unstranding today sends to rows qualified solely by funnel membership, with no per-row evidence and no `qualified_by`. Either backfill or accept that explicitly — do not let a future reader assume the context was checked.
3. **A default-on `lead_kind` would make 57,386 legacy rows instantly sendable.** Hence unroutable-by-default. The migration must not guess a kind for a row whose funnel cannot be determined.
4. **The weaker path writes the real files.** `send_list.build` has no verdict gate and no curation gate; today nothing exploits that only because ALIVE removes every non-editor emailable row. Kind-aware gating must add the curation and quality gates to `send_list` at the same time, or widening liveness will expose exactly the hole BL-765 warned about — the data luck becomes a live defect the moment the filter widens.
5. **`date_sent` is empty on all 57,386 rows.** There is no send history, so nothing prevents re-sending to a newly-unstranded lead on the next run. Unstranding raises the cost of that gap.
6. **`qualified_by` can rot.** If a funnel loosens its own gates, `client` rows silently drop in quality with no downstream check. The string must record the actual thresholds used, not the funnel name.

## What else is stranded, and what arrives stranded

**`repost_finder` — 42 rows, and it should not export through these paths.** Verdict `MEME_PAGE` on all 42, **0 emails, 0 profile URLs**. Under this spec it is `clipper`-kind but has no contact of any sort; it stores pages, not people. It will not export and that is correct. If those pages are ever meant to be contacted, the funnel must first write a handle or an address — the gates are not what is stopping it.

**My own BL-761 fix is already stranded.** That round made Spotify save handle-only DM leads instead of discarding 52% of every run. **642 client-funnel handle-only rows now sit in master** — and `writer.dm_list_rows` gates on verdict exactly as `bot_ready_rows` does, so every one of them is unreachable. The leads were rescued from being dropped at the door and are now stuck in the hallway. Until `lead_kind` lands, BL-761 converted an invisible loss into a visible one; it did not deliver a sendable lead.

**Every future funnel arrives stranded by default.** The pattern is now clear: the hashtag crawl wrote `verdict`, `last_post_date` and a campaign-matching `source_hashtag` because the exporters were built around it. Every funnel built afterwards — five so far — writes none of the three and is silently excluded. **A sixth will be too.** That is the argument for declaring kind and gate-applicability explicitly rather than fixing five funnels one at a time.

## Honest limits

- This is a spec. Nothing was implemented and no number here is a post-fix measurement; the +1,232 is BL-764's simulation of the real predicates, which shows what the code *would emit*, not what would reply.
- I did not cost the migration. Adding `lead_kind`, `qualified_by`, `last_activity_date` and `activity_source` is four columns and a touch of every funnel's append path — larger than the one-line verdict default it replaces, and that trade is the owner's call.
- `attribute()` was sampled on the first 400 rows per funnel, not all 57,386; the client funnels returned UNATTRIBUTED unanimously, so the conclusion is not sensitive to the sample.
- Whether `email_finder` is `clipper` or `client` depends on what is fed to it — it is list-driven. That row cannot be classified by the funnel alone and needs the caller to declare it, which is an argument for the field, not against it.
