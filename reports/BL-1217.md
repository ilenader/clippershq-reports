# BL-1217 — the bioLink field is real at 30.0%, and the thing worth reading in it is not the link

**The stale sample was stale.** TikTok returns `bioLink` on **18 of 60** profiled authors —
**30.0%** — measured live, on a call the pipeline was already paying for. The sample claiming
otherwise is dated 2026-06-30 and predates the field.

**But following the link is not where the value is.** Scraping the six link-in-bio
aggregator pages behind those links yielded **zero addresses**. What the field actually
carried was an Instagram handle four times and a bare email address once.

Every figure came from **`.venv\Scripts\python.exe`, Python 3.11.9**. Bare `python` is 3.13
and lacks the packages. **Vendor receipt: 60 calls, $0.0360** against a $2.00 cap.

---

## 1. bioLink, read and sized

The field was being thrown away by exactly one of the two functions that parse the same
payload:

| function | reads `bioLink`? | used by |
|---|---|---|
| `email_finder.make_tt_profile_fn` | **yes** | `control.py` ×3, `youtube_finder.py` |
| `tiktok_finder.profile_of` | **no — `signature` only** | the discovery path |

So `enrich_links.py`, which exists precisely to follow a link-in-bio page and pull an
address off it, was never handed a URL to follow for a discovered TikTok lead.

**What 60 live profiles found** (60 billed calls, $0.0360):

| | n | share |
|---|---|---|
| authors profiled | 60 | |
| **carrying a `bioLink`** | **18** | **30.0%** |
| addresses in the bio text | 1 | |
| addresses behind the link, scraped | **0** | |

And what those 18 links actually were:

| the link was | n | share of links |
|---|---|---|
| a link-in-bio aggregator (linktr.ee, solo.to, guns.lol…) | 6 | 33.3% |
| **an Instagram URL** | 4 | 22.2% |
| unreachable | 2 | 11.1% |
| **a bare email address in the link slot** | 1 | 5.6% |
| telegram | 1 | 5.6% |
| other (straw.page, tr.ee…) | 4 | 22.2% |

**Six aggregator pages scraped, zero addresses.** That is the honest headline and it is the
opposite of what "read the bioLink and follow it" promises.

**Two free things were being discarded, and both now land:**

1. **An address in the link slot.** One of the 18 was literally `<name>@gmail.com`. Parsed
   now with the same extractor as the bio, so it is held to the same standard.
2. **An Instagram handle arriving structurally.** Four of 18. This is the cross-link (§2)
   delivered as a field rather than inferred by regexing `@name` out of prose — which is how
   a previous round over-counted the cross-link at 30%.

**Cost per new email from the link field so far: $0.0360 for one address** — one profile
call each on 60 authors, of which the field yielded exactly one address directly. That is
not a good rate on its own; the four Instagram handles are where the rest of the value is,
and they feed a pipeline that already works.

**One reader, not two.** The parse now lives in `email_finder.bio_link_of` and both call
sites delegate to it. The tests assert the delegation, because a third copy of this parse is
the defect coming back.

## 2. The Instagram cross-link, honestly sized

**I could not measure the base rate this round and I am not going to quote one.**

The obvious corpus, `output/tt_xlink_resolve_run.jsonl`, has 250 rows and **100.0% of them
name an Instagram** — because that file *is* a resolved cross-link run. It is a
post-selection population. Reporting 100% would be the same error as the round that reported
30%, just louder. The honest carry-forward remains the previously measured **4.6% floor
across 49,810 bios and 10.3% [4.8, 20.8] live at n=58** — not "most".

What this round adds is a **better mechanism at that share**: 4 of 18 links (22.2%) were an
Instagram URL in a structured field. A handle read from a URL field cannot be confused with
a mention of a friend, which is what regexing bio prose does.

**Why TikTok lags, said plainly.** TikTok reads 10.9% against Instagram's 16.9% and it is
**not a filter-quality problem**. Instagram's payload carries two things TikTok's does not:

| | Instagram | TikTok |
|---|---|---|
| business e-mail field | **40 hits** | does not exist |
| contact button | **31 addresses — 51% of all yield** | does not exist |

Half of Instagram's yield comes from a surface TikTok does not have. Chasing a filter fix
for that gap is chasing a platform difference. The route that remains is the cross-link:
TikTok bio or bioLink names an Instagram → follow it → read the business field and contact
button *there*, on the platform that has them.

**A TikTok page and its Instagram are the same lead** — his words — so the cross-link must
deduplicate into one master row, never two.

## 3. Sherlock

**REFUSE.** Tested on **12 real TikTok handles** from `master_leads.csv` (the Instagram
corpora were the wrong file), MIT licence, sherlock-project 0.16.0, isolated venv built from
`.venv\Scripts\python.exe` (3.11.9).

**The finding that ends it: a control run on two impossible usernames returned exactly 3
hits each — the same 3 — and one of them was TikTok.** That floor is unconditional. Its
TikTok detector is 100% false positive, on the one platform this project cares about.

| | |
|---|---|
| wall clock | **75.8 s per handle** (61.8–87.5), 15.5 min for 12 |
| raw hits | 83 → 49 above the floor → **~20 survive actually fetching the URL** |
| plausibly the same person | 4 (only **1** proven) |
| **demonstrated different humans** | **5** |
| returned nothing but the floor | 3 of 12 |
| emails obtained | **1** — and not incremental |
| disk | 406 M installed, **406 M reclaimed**, install verified `GONE` |

It reports 404s, Cloudflare 403 challenges, SSL failures, search-URL echoes and the bare
string `https://discord.com` as `[+]` hits. The namesakes are concrete: `zackdfilms92` → a
Snapchat "Zdak" and a YouTube *fanpage*; `panteravfx` → a Pinterest "seden"; two
dot-stripped matches to a different "Neval".

The single address it found, `pa…@gmail.com (85c778)`, came off `linktr.ee/panteravfx` —
and **`clippershq/enrich_links.py` already scrapes linktr.ee**. The only other addresses were
`su…@discord.com (11ae1f)` and Patreon's `no-reply@` / `guidelines@` / `merch@`: precisely the
transit-authority-stranger failure that was measured here before at 0 for 6.

Against a **0.81%** bounce rate, sherlock hands back the five wrong humans and the four right
ones in one undifferentiated list. A wrong address bounces and damages sender reputation
permanently. **The cheap upside is already ours; the downside is not recoverable.**

**The one thing worth taking from it:** guess `linktr.ee/<handle>` in the existing enricher —
one request, not four hundred.

Full detail: `scratch/bl1217/sherlock.md`.

**And no email-finder service.** Already measured and refused: those services take a name
plus a **company domain** and permute; Hunter's own documentation says it cannot work with
personal addresses. These are creators on gmail. Not proposed, not revisited.

## 4-5. His account rules, and the supply that has to come first

**NOT IMPLEMENTED THIS ROUND, and I want to be exact about why rather than ship a verdict
that cannot be trusted.**

The brief itself names the blocker: **discovery yields 1.15 videos per author**, the live run
quietly used `min_videos=1`, and the filter passed 117 of 119. Three of his seven rules —
~3,000 average views on recent videos, on-screen text English only, and no creator who talks
— are judgements about a *body of work*. Asked of a single video they are not measurements,
they are coin flips with a threshold attached. `average_views` already says so in its own
docstring: requiring 3 videos leaves **3.2% of authors judgeable**.

So implementing the seven rules on today's supply would produce a filter whose verdicts
looked precise and meant nothing — the exact shape BL-1210 spent a round unpicking. The
supply fix (group `/v2/search` and `/v1/hashtag/medias` results by author until each has
enough videos to judge) has to land first, and it did not fit this round alongside the
bioLink work.

**What I did confirm, cheaply:** `clippershq/frame_text.py` is still **not imported anywhere
in the TikTok path** — OCR has never run on a TikTok frame, exactly as the brief states. And
the vendor constraint stands: there is no endpoint listing a named account's videos, so
video-first discovery is the only shape available.

**The recent-post rules (under 30 videos → posted in the last week; 30+ → posted in the last
two months) are the two that need no supply at all** — they read one timestamp. They are the
right first thing for the next round to land.

`scratch/bl1217/dashboard_audit.md`. Verdicts against his seven asks:

| # | ask | verdict |
|---|---|---|
| 1 | one launcher, one icon, one URL | **PARTIAL** |
| 2 | survives the window closing | **WORKS** |
| 3 | a run survives the dashboard dying, shown correctly | **WORKS** — all three identity components present |
| 4 | **clear a finished run** | **MISSING** |
| 5 | freshness banner | **WORKS** |
| 6 | every dataset as .xlsx + .csv with row count and build time | **PARTIAL** |
| 7 | batches sorted by `started_at` | **WORKS** — BL-1212 fixed it |

The findings worth his attention:

- **Point 4 is the only outright hole.** No clear endpoint exists anywhere; `/api/stop`
  explicitly refuses a dead pid (`server.py:3835`) and `app.js:419` renders a button only
  when `withStop && live && r.pid`, so a finished run has no control at all.
- **Two icons are deliberate.** `tools/make_shortcut.ps1` creates both by name. Three `.bat`
  files can start the same dashboard.
- **A real reuse bug:** the start path scans **10** ports (`dashboard_launcher.py:331`) while
  the stop path scans **30** (`:353`), so a dashboard recorded on :8799 is invisible to start
  and a second server gets launched.
- **A deletion hazard:** `server.py:2333` spawns runs with **no** creationflags — survival
  actually comes from the child self-detaching at `clippershq/run.py:848`. The comment at
  `dashboard_launcher.py:551` claiming runs are spawned detached is false, and anyone
  trusting it could remove the thing that actually works.
- Identity does use pid **and** creation time **and** boot epoch
  (`proc_identity.alive()`), so the 54-hour Clipboard-Service failure is genuinely closed.

## 7. The send list

**No new addresses reached a send file this round**, so no MX refresh and no re-verification
were run — there was nothing to suppress. Running them over an empty delta would produce a
green tick that means nothing, which is the "vacuous suppression" this project has already
been caught by once (9 of 13 domains unprobed on one file).

The one address the bioLink field yielded is in `scratch/bl1217/biolink.json` and is
**deliberately not promoted**: a single address is not worth a send-file migration, and the
rule that TikTok pages get their own file with no address in two files is easier to honour
when the first write is a batch rather than a trickle.

**What a week produces, from this round's only real rate:** at 30.0% bioLink presence and
~1 direct address per 60 profiles, the link field alone is roughly **1 address per $0.036**.
The cross-link is the multiplier, and its yield depends on the Instagram pipeline that
already works — but the 4.6–10.3% share means ~3–6 Instagram handles per 60 TikTok profiles,
not 18.
