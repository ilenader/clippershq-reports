# BL-1192 — "save FAILED" in green: the cause, the recovery, and a sheet that can no longer lose a mark

**Your ~50 marks from the failing session are NOT on disk — and they are almost certainly
still recoverable from the browser tab, if it is still open.** Read §2 first and do that
before anything else. Everything below is fixed, but nothing below gets those 50 back.

Every number here came from `.venv\Scripts\python.exe` (3.11.9). Bare `python` on this box is
3.13.14 and lacks the packages; it was not used. **Spend: $0.00** — no paid call was made.

---

## 1. THE CAUSE, REPRODUCED

Two independent defects that only bite together, plus a third that hid the damage.

**a. The server dies when you close the window.** `OPEN_REVIEW_SHEET.bat` ran the server in
the *foreground* of the cmd window it opened. Closing that window kills it.

**b. The page never notices.** It decided once, at load:

```js
fetch('ping').then(function(r){live=r.ok;})     // and never again
```

`live` was latched. A server that died after load left the page confidently POSTing into a
closed socket for the rest of the session.

**c. The failure was painted the colour of success.** The `.catch` wrote `'save FAILED'` into
`<span class="saved">`, and that span's only rule was `.saved{font-size:12px;color:var(--ok)}`
— **green, 12px, beside the button**. Nothing stopped you marking the next row, or the next
fifty.

Reproduced end to end in `scratch/bl1192_repro.py` — server up, mark saved, server killed the
way a closed window kills it, mark attempted again:

| step | result |
|---|---|
| ping, server up | `200 ok` (1.0 ms) |
| POST /mark, server up | `200 ok` (3.0 ms) — appended |
| *server killed* | |
| ping, server down | `URLError` — **WinError 10061, "actively refused it"** |
| POST /mark, server down | `URLError` — **WinError 10061** |

That rejection is precisely what the browser's `fetch` throws, and precisely what the old
`.catch` turned into green text.

## 2. WHAT IS ON DISK, AND HOW TO GET THE REST BACK

`ground_truth/review_marks.jsonl` holds **103 marks across 100 distinct rows** (65 GOOD,
38 BAD), all timestamped between **13:58:51Z and 14:51:40Z today**. Rows 1–100 are complete
with no gaps; three rows carry a second mark from a rapid double-click.

**Nothing has been written since 14:51:40Z.** The failing session produced **0 marks on
disk**. Resume from where that earlier hundred ended — not from the beginning.

### The 50 are very likely still in the browser, and closing the tab loses them

The old code called `store(rec)` **before** the network, unconditionally, so every mark went
into `localStorage` under the key `bl1186_marks`. The Download button that would have got them
out was rendered *only* in the `!live` branch — so a session that began with a live server held
the data and had no door to it. That is why the marks vanished from view but not from memory.

**If that tab is still open, do this before touching anything else:** open DevTools on the
sheet (F12), Console, and run:

```js
copy(JSON.parse(localStorage.getItem('bl1186_marks')||'[]')
       .map(r=>JSON.stringify(r)).join('\n'))
```

That puts one JSON object per line on the clipboard. Paste it onto the end of
`ground_truth/review_marks.jsonl`. The file is append-only and the reader takes the newest
mark per row, so appending is always safe and duplicates are harmless.

With the fixed sheet you will never need this again — the new page keeps a **Download the N
unsaved** button on screen the whole time the server is down.

## 3. WHAT THE SHEET DOES NOW

- **Liveness is a question, not a fact.** `ping` is re-asked every 5 s whenever the server is
  down or anything is pending, and on the browser's `online` event. Nothing is ever latched.
- **A mark is written down before it goes near the network.** The submit handler *only*
  queues (`localStorage`, two lists) and hands off. A test asserts the handler contains no
  `fetch(` at all, so nothing can be lost between the click and the socket.
- **A record leaves the queue only on a `200`.** A dead server, a 500, a refused connection —
  all leave it queued, and the drain loop retries in order, so the file keeps its append order.
- **Failure is unmistakable and blocking.** The failed state is a *class*, not just text:
  white on red, 14px, bold-800, boxed, prefixed `⚠ NOT SAVED —`, with `role="alert"`. The
  banner turns into a sticky red bar, rows grey out, and `pointer-events:none` stops further
  marking until saving works. Not colour alone — it survives a colour-blind reader.
- **A permanent counter**, bottom-right, always reading `N saved · M waiting to save`.
- **Leaving with unsaved marks warns** via `beforeunload`.
- Recovery is automatic: relaunch the .bat and the page notices within 5 s and sends
  everything it was holding, without you doing anything.

## 4. THE LAG

Measured by building the sheet from the committed version and from the new one, in the same
process (`scratch/bl1192_measure.py`):

| | before | after |
|---|---|---|
| page weight | 831.1 KB | 853.8 KB |
| `<img>` elements | 972 | 972 |
| with `loading="lazy"` | 972 | 972 |
| with `decoding="async"` | 0 | **972** |
| elements in document | 16,190 | 16,192 |
| **layout units on first paint** | **16,190** | **160** |

**101× fewer.** The page is 22.7 KB *heavier* — that is the new CSS and JS, and it is an honest
cost. `loading="lazy"` was already present and was never the problem: the browser still had to
lay out ~16,000 elements before it could show anything. `content-visibility:auto` with
`contain-intrinsic-size` on each row lets it skip layout and paint for every row not near the
viewport, and `decoding="async"` moves 972 image decodes off the main thread.

**On "time to interactive": I did not measure milliseconds and will not quote any.** A real TTI
needs a browser on your machine with your cache and your CPU. What is above is the count of
layout units the engine must resolve before first paint — a proxy, labelled as one. Quoting a
fabricated ms figure is exactly the kind of number this project keeps having to retract.

## 5. THE SERVER

`start ""` in the .bat launches the server in its own process, so **closing the window no
longer kills it**. The .bat also refuses to run at all if `.venv\Scripts\python.exe` is missing,
rather than starting nothing and leaving you marking into a void.

Re-running the .bat is now the normal recovery, and it is safe: `serve()` asks its own `/ping`
first and re-uses a live server instead of fighting for the port. **This was demonstrated
accidentally during testing** — a second launch found the first still listening and re-used it.
Port-walking (8 tries), `allow_reuse_address` and `daemon_threads` were already there and are
unchanged. `--no-browser` is new, so tests and probes stop throwing tabs at you.

## 6. WHAT I GOT WRONG, AND WHAT IS STILL OPEN

- **I put fake marks into your ground-truth file twice** — a probe row, then three drain-test
  rows — and removed both, restoring the file to exactly 103 marks / 100 rows / 65 GOOD /
  38 BAD. Backups at `scratch/bl1192_marks_backup.jsonl` and `…_backup2.jsonl`. The second
  time happened because `append_mark(rec, path=MARKS)` bound the path as a **default argument
  at def time**, so redirecting `review_sheet.MARKS` to a scratch file was silently ignored.
  That footgun is now fixed (`path=None`, resolved at call time), which is also what makes the
  module testable without touching real data.
- **The end-to-end browser proof did not land.** Chrome in this environment cannot reach the
  local server at all — `ERR_CONNECTION_REFUSED` on both `127.0.0.1` and `localhost`, while
  `curl` and Python got `200` against a socket `netstat` showed `LISTENING`. That is a proxy
  policy on this automation profile, not something your machine shares — your sheet plainly
  loads and runs JS, which is how you saw "save FAILED". So the buffer-and-retry behaviour is
  proven by **contract tests on the generated page** plus the HTTP-level reproduction, not by
  a recorded browser session. Named, not hidden.
- **Two suites fail and neither is mine**: `memebot/meme/tests/test_render.py` and
  `memebot/meme/tests/test_ocr.py`, both in the nested `memebot/` repo.
- **A first draft of one test was wrong** and I fixed it rather than the code: it compared
  source positions of `wr(PK,q)` and `fetch('mark'` across the whole script and failed because
  `drain()` is merely *defined* earlier. It was asserting text order where the claim is about
  execution order; it is now scoped to the submit handler.
