## 2. The 429 question — retired rather than answered

BL-857 flagged its 429 rule as inference. I set out to measure it and **failed to provoke a 429 in 22 rapid calls**, so the specific case remains unobserved.

**The probe found something better.** HikerAPI states its own billing on every single response:

```
x-hiker-info: {"reqs":1}
```

That is the provider's own count of billable requests, and it makes the inference unnecessary. `_bill_from()` now reads the receipt and falls back to the status-code rule only when the header is absent. **If a 429 ever arrives carrying `reqs:1`, it bills; carrying `reqs:0` or nothing, it does not.** Nobody has to guess again, and no further paid probe is needed to settle it.

Pinned by six tests, including the previously-unanswerable case: a 429 with `reqs:1` bills 1 and is still counted as throttling.

## 5. The duplicate first-writes: 27, not 1, and the mechanism is concurrency

BL-857 reported one clip with two rev-1 rows. There are **27**.

| | clips |
|---|---:|
| byte-**identical** duplicates — same data written twice | **3** |
| genuinely **different** first writes — two separate fetches | **24** |
| of those, differing on immutable `posted_at` | 1 |

Fields that differ across the 24 are exactly the ones that legitimately move between two fetches at different times: `media_renditions` 19, `play_count` 14, `save_count` 11, `follower_count` 7, `like_count` 5.

**The mechanism.** `clip_library.append()` is deliberately blind — it never checks whether a `clip_id` exists, because the log is append-only and last-wins-by-rev on read. Dedup therefore lives entirely in the writer: `clip_runner.run()` does

```python
have = set(clip_library.load_index(root))   # ONCE, at run start
```

and never re-checks at write time. **Two walks overlapping in time both load `have` before either writes, both see the clip as absent, and both write `rev=1`.** With three or four rounds appending to `clip_library/` simultaneously — which is today's normal — this is expected rather than exotic.

It is paid waste: 24 clips were retrieved twice. Small in absolute terms, and it scales with concurrency, which is increasing.

**It is not the shard boundary.** I checked that first: both rows of the `posted_at` case land in `clips-2026-04.jsonl`, because 13.9 days apart is still the same month. `shard_for(posted_at)` would split a pair straddling a month end, but that is not what happened here.

**The `posted_at` case is still unexplained.** Every other differing field has a benign reason; that one does not, and 1 in 2,003 is too thin to diagnose. It now has a named mechanism — two independent fetches — rather than being a mystery, and `scratch/bl861_note_for_bl855.md` carries the detail.

## 6. Both asymmetries kept, and the reason is now in the code

- `estimated_pages()` **under-excludes**: rank is computed over clips we hold, so true depth is worse and the estimate errs toward including. Excluding a reachable clip costs a video; including an unreachable one costs $0.0012.
- An **unknown-but-served status still bills**: under-counting spend is the dangerous direction, because the cap is what stops a run.

Both are comments at the point of decision, not in a doc.
