# BL-1152 — the panel was showing the Windows Clipboard Service as a running lead funnel

**One sentence:** clip_render never died — it **completed**, in seconds, with nothing to do,
and "finished instantly" and "vanished" render identically; the runs that *did* die left no
trace because the capture was thrown away the moment a run survived six seconds; and the
"running" cards were a `svchost.exe`, a `conhost.exe` and **Discord**, holding recycled pids.

**Spend: $0.0000 of a $0.30 hard cap.** Every paid leg was reserved before it was attempted.
Ledger folded by record: `spend.json` holds **1,009 rows** but **1,003 distinct records** —
the row count is not the run count. Zero rows are attributable to this round's runs; the
Spotify discovery phase is free and every run was stopped before the paid phase.

## 1. What the captured output actually said — and why item 1's premise was false

**There was nothing on disk to read.** BL-1149's capture is:

```python
proc = Popen(argv, stdout=PIPE, stderr=STDOUT)
try:
    out = proc.communicate(timeout=6.0)[0]   # a start-up death: captured perfectly
    died = True
except TimeoutExpired:
    out, died = "", False                    # survived the probe -> the output is DROPPED
```

A run that dies inside six seconds has its output returned in the HTTP response — shown once,
in red, then gone. A run that survives has its output read into memory by `communicate`'s
reader threads and **discarded**. Nothing is ever written to a file. `logs/run.log` confirms
it: 4,918 lines, and in the last six hours only 11, all `enrich_links` chatter from an
unrelated funnel.

**So I read the run markers instead**, which do persist. Per run, in the last hours:

| funnel | outcome | the actual reason |
|---|---|---|
| **clip_render** ×11 | **completed**, 0 leads | it did not die. It ran and exited cleanly with nothing to do |
| **spotify** ×4 | **failed** in **0.9 s** | `"Spotify finder run failed"` — a wrapper that swallowed the real exception |
| **tiktok** ×4 | failed | `headless: cannot choose a campaign… Set config['headless_campaign'] to one of ZHUS, PANICBABY…` |
| **google_play** ×3 | failed | `no search terms. Nothing in config['google_play'] supplies them` |
| email_finder, ig_crawl | completed, 0 leads | nothing to process |
| clip_walk ×1 | failed | `clip_runner: walk failed for <account>` |

**tiktok and google_play are not broken — they are unconfigured**, and they say so precisely.

### The fix: to a file, not a pipe

`api_start` now writes the child's stdout+stderr to `logs/runs/<ts>-<funnel>-<pid>.log` and
watches for a start-up death by polling. **Every response now names its log file**, including
the success path — so a run that dies at minute four has an address.

> I also predicted the abandoned pipe would *deadlock* the child on a full 64 KB buffer.
> **Measured at 8 KB and 256 KB: it does not.** `communicate` leaves its reader threads
> running after `TimeoutExpired`, so the pipe keeps draining. The hypothesis was wrong and
> `scratch/bl1152_readlog.py` records the refutation.

## 2. The ghosts: not stale files — recycled pids belonging to real, unrelated processes

```
this machine booted        2026-08-05 10:13:59
repost_finder card         pid 10120, "running", started 2026-08-03 12:03:54  (46 h before boot)
pid 10120 IS              svchost.exe -k ClipboardSvcGroup   created 10:14:21 (22 s after boot)
a youtube card's pid      conhost.exe
another youtube card's    Discord
```

The rule "a pid that no longer exists leaves the panel" is sound and **never fired, because
the pid exists**. `OpenProcess(10120)` returns ALIVE and always will.

`tools/sweep_stale_markers.py` retires them using BL-1150's identity check — **rewritten in
place as `status: died` with the reason and what the pid turned out to be, never deleted**,
because a panel that silently empties is the same class of failure as one that silently lies.

```
110 markers read -> 36 dead, swept.  Immediate re-run: 0 dead, 110 kept.
```

**And the panel needed wiring, not just the markers.** `/api/now` used bare `_pid_alive` at
two sites; both now use `spend_ledger.marker_state()`. Before: **3 running cards** with
nothing running. After: **0**.

`died` also had to become a terminal status — without that the sweep rewrote a marker and
then re-judged it dead forever, reporting 36 swept and 35 still to sweep. **A sweep that
never converges is indistinguishable from one that never worked.**

## 7. What I got wrong

* **The deadlock hypothesis.** I predicted the abandoned pipe froze the child. Measured at
  8 KB and 256 KB — it does not. Tested before reporting; the refutation is on disk.
* **My sweep was not idempotent** — `died` was not in `TERMINAL_STATUSES`, so it re-swept
  forever.
* **The repo's own guards caught three violations in my code**: an unchecked subprocess stdout
  read in `proc_identity.process_name` and in the sweeper (a failed probe would have read as
  "not one of ours" and cleared a *live* run); a bare `os.replace` in the sweeper; and a
  silent-zero at the new log read, where "could not read the log" produced the same empty
  string as "the funnel printed nothing" — **which then becomes the operator's explanation.**
  That last one is the exact failure-reads-as-success shape this round exists to fix, written
  by me, while fixing it.
* **I broke two of BL-1149's tests**, and one was fair: their `test_run_from_page` pinned
  `communicate(timeout=` — the *mechanism* — which I deliberately replaced. I changed it to
  assert the *property* (that the process is watched), and replaced an 8000-byte source slice
  with a parse to the next top-level `def`. Their own comment already said that slice was
  "measuring the comments above the code"; it had been raised from 6000 once before.
