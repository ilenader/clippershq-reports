# BL-1036 — the shared-index window, closed on the case nobody could see

**The defect was not the one in the brief, and it was worse.**

`pre-commit` has called `claim.py staged` and refused on its exit code since MEMEBOT-059,
so "nothing refuses" was already stale. What actually failed is narrower and nastier:

> `rounds_owning` derived ownership **only from live claims**, and
> `check_staged_single_round` documented an unclaimed path as *not an error*. Both halves
> were defensible. Together they made a **departed** round's staged work completely
> invisible.

Run against the live index at 11:48, with 13 files staged:

```
$ python tools/claim.py staged
  staged paths belong to one round: MEMEBOT-116
$ echo $?
0
```

MEMEBOT-116 owned **one** of the fourteen staged paths — its own claims manifest. The other
thirteen belonged to **BL-1002** and **MEMEBOT-115**, both finished and released. Every
guard passed. Any bare `git commit` would have landed two departed rounds' work under a
third round's name, and the tool that exists to prevent exactly that would have said it was
fine.

**This is the worst case, not an edge case.** A live round can be asked to resolve its own
staging. A departed one cannot — nobody is coming back for those files.

---

## 1. The fix: the path names its own round

`claim.round_of_path()` reads the round id out of the filename and is used **only as a
fallback**, for paths no live claim covers. A live claim always wins, so the
most-specific-claimant rule and every existing caller are unchanged.

**Measured before it was trusted** (`scratch/bl1036_extract_probe.py`, 75,844 files):

| | |
|---|---|
| files mapping to a round | **2,215**, across **360** distinct rounds |
| files under `clippershq/`, `tools/`, `tests/` that map | **0 of 62,529** |

The convention is real where round-owned working files live, and **cannot misfire on
product code** — which is the property that makes it safe to act on. A false positive here
would refuse an honest commit, and a guard that does that is one people disable.

```
$ python tools/claim.py staged
  STAGED PATHS SPAN 2 ROUNDS -- commit them separately:
     BL-1002        [DEPARTED - cannot resolve its own staging]
     MEMEBOT-115    [DEPARTED - cannot resolve its own staging]
  A DEPARTED round's files will not resolve themselves. Commit them
  under their OWN round id, which keeps the attribution honest:
      python tools/commit.py <THEIR-ROUND> -m "..." -- <their paths>
$ echo $?
1
```

### The half the brief did not ask about, and which mattered more

`pre-commit` only sees the shared index on a **bare** commit. For a pathspec commit git
builds a `next-index`, so `claim.py staged` sees just the pathspec and passes — correctly.
That means the bare-commit path was never the only hole:

> **`tools/commit.py BL-XXXX -- <a departed round's file>` sailed through both rules.**
> Rule 2 is skipped for scoped commits, and before the fallback the path had **no live
> claimant, so it was foreign to nobody**.

Rule 1 in `commit_guard.py` applies to every commit form, so teaching `rounds_owning` about
departed rounds closes the scoped path too. Both are proved below, and they fire in
different places.

## 2. Proved both directions, in throwaway repos, naming which check fired

`scratch/bl1036_proof.py` creates a real git repository under `tempfile` for each case,
copies this tree's `tools/` and hooks in, runs a **real `git commit`**, and asserts the exit
code **and** text unique to the branch that fired. Never the live tree.

| case | expected | which check fired |
|---|---|---|
| cross-round, BARE commit, two departed rounds | REFUSE | `pre-commit → claim.py staged` |
| **cross-round, SCOPED commit of a departed round's file** | REFUSE | **`commit-msg → commit_guard.py`** |
| two LIVE rounds in one staged set | REFUSE | `pre-commit → claim.py staged` |
| BARE commit beside two departed rounds' orphans | REFUSE | `pre-commit → claim.py staged` |
| **SCOPED commit of own file beside foreign orphans** | **ACCEPT** | — |
| single round, scoped, own file | ACCEPT | — |
| single round, bare, no other round live | ACCEPT | — |
| departed round's files, committed under THEIR id | ACCEPT | — |
| `Claim-Override` acknowledged in the message | ACCEPT | — |
| unclaimed, unnamed file is not an error | ACCEPT | — |

**10 of 10.** Both refusals name both round ids and label each owner `live` or `DEPARTED`,
because the two need different instructions.

### The ACCEPT cases earned their keep on the first run

The brief warns that a refusal-only test stays green through an outage. It happened here,
by accident, immediately: the first probe copied only `claim.py` and `commit_guard.py`, but
`pre-commit` runs `verify_claims.py` **first**, and a missing script exits non-zero. Every
ACCEPT case failed; **all three REFUSE cases were green throughout.** A refusal-only proof
would have shipped a guard that refused everything, and the summary would have read
`3/3 OK`.

### The case that decided whether this was safe to ship

`SCOPED commit of own file beside foreign orphans` reproduces the live tree — 13 foreign
files in the shared index — and commits one's own file via `commit.py`'s exact form
(`git add -- <paths>` then `git commit -F msg -- <paths>`). **It must ACCEPT**, or the
change bricks the repository for all 17 live rounds. It accepts, and that is measured
rather than reasoned: git snapshots a pathspec commit into its own index, so both hooks see
the pathspec.

All 13 are `A ` — **new work not in HEAD**. Neither round holds a live claim.

### What this now means for the other 16 rounds — say it plainly

* **`tools/commit.py` still works.** It uses the pathspec form, which is scoped; proved
  above beside these exact orphans.
* **A bare `git commit` is now REFUSED for everyone**, until these 13 are resolved. That is
  the intended effect — a bare commit in this state lands two departed rounds' work under
  whoever typed it — but it is a real change to what works today, and you will hit it
  without warning if you were relying on bare commits.
* **The fix is not to unstage them.** Commit them under their own ids, which keeps the
  attribution honest and is what the refusal text tells you to do:
  `python tools/commit.py BL-1002 -m "..." -- scratch/bl1002_*`

I did not do this myself: they are two other rounds' measurements, and committing seven
files of BL-1002's work under a message I would have to invent is the mis-attribution this
round exists to stop. `Claim-Override` exists for a round that decides otherwise.

## 4. Reachability — the guard is only armed by uncommitted local config

Hooks run **only** because `core.hooksPath` points at `tools/githooks`, and that lives in
`.git/config`, which no clone copies. The scripts travel; the thing that arms them does not.

`tools/repo_guard.py::check_hooks()` already makes this loud, and it is the answer to
"confirm the guard is reachable and its absence is LOUD":

```
== hooks are armed in THIS checkout ==
  core.hooksPath    : tools/githooks
  OK: hooks installed and present.
```

Absent, it prints `the hooks are NOT installed here — every commit guard is INERT` and exits
non-zero. Verified present and firing: both refusal paths above ran through real hooks.

## 5. `LedgerUnreadable` is now one class

`clip_pipeline.py:2286` and `spend_ledger.py:305` each defined a `LedgerUnreadable(
RuntimeError)` with an identical contract. **Two same-named classes are a trap that springs
once:** `except LedgerUnreadable` reads as exhaustive, catches exactly one of them, and the
day the other crosses that boundary the handler is skipped and the budget fails open — the
precise defect both classes exist to prevent, reintroduced by the fix's own duplication.

`spend_ledger` is canonical because the dependency runs that way (`clip_pipeline` imports it;
`spend_ledger` is stdlib-only, so no cycle). Its own docstring recorded the handover "when
whoever holds that file next can make the change" — BL-1028 ended BL-899's 37.6-hour claim,
so this round is that holder. `clip_pipeline.LedgerUnreadable` is now a re-export:

    clip_pipeline.LedgerUnreadable is spend_ledger.LedgerUnreadable   -> True
    each module's `except` catches the other's `raise`                -> True
    still not caught by (TypeError, ValueError)                       -> True

`spend_ledger.py` itself is held by **BL-1042**, so its now-stale "should become an alias"
note is left for its owner rather than edited under them.

## 6. The two corrections, recorded

Both appended to `docs/CORRECTIONS.md` so no future brief repeats them.

**"Assert the returned set is identical" is FALSE BY DESIGN after interleaving.**
`rank_candidates` truncates to `want × over_provision`, so reordering changes who survives
the cut — 65 displaced, and that displacement *is* the feature. The only ways to make the
literal assertion pass are to stop interleaving or interleave after the cut, which restores
the concentration being fixed. Assert instead that the interleaver is a **multiset
permutation of its input**, and that `rank_candidates` is set-identical **only when the cut
does not bind**.

**A $0.001 cap and "every record carries provenance" cannot both hold.** At that cap the
budget binds before the first retrieval — `retrieval 30 in / 0 out, "stopped early
(budget)"` — so the run writes no records and the claim is vacuously true of an empty set.
Check a quoted cap against the measured ~$0.0011 per video before writing it into a brief.

## 7. What I got wrong, caught by the suite

**The fallback swallowed the claim registry, and a round could never finish.**
`dirty_declared` routes through `rounds_owning`, so `.claims/BL-966.json` — which has a
round id in its name — became BL-966's own uncommitted work, and `claim.py end` refused to
release it. *The act of claiming created the dirt that blocked the release.*
`tests/test_commit_guard.py` said so within minutes. `round_of_path` now excludes the
registry **directory** — `docs/claims/*.claims` is committed output and still maps, which is
why the exclusion names the directory and not the word.

**I recorded a removal that did not happen.** BL-1013's manifest claimed
`clip_pipeline::LedgerUnreadable` as a `func:`, and `verify_claims` resolves those by AST —
an import is not a definition — so that manifest went red the moment the alias landed. I
wrote it as `superseded:` and the tool refused, with the better diagnosis:

> `LedgerUnreadable` is absent from its own path but **ALIVE at HEAD** in
> `clippershq/spend_ledger.py` — this was **MOVED, not removed**. A move is a re-point: aim
> the claim at its new home rather than recording a removal that did not happen.

`superseded:` asserts a thing is *gone*. It is one module over. A superseded line would
have asserted something false and passed forever while the type it guards was live
elsewhere — a manifest entry that cannot go red is the failure manifests exist to stop. The
claim now points at `spend_ledger.py::LedgerUnreadable`.

**I pinned a test to my own old wording.** `test_silent_zero_fixes.py` asserted the literal
string *"claimed by another live round"*. Ownership is no longer live-only, so that sentence
is now false on exactly the case this round exists for. Re-pinned on the behaviour — it
refuses, it names the round, it says which kind of owner — not on one sentence.
