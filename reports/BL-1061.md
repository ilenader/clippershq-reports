## What I got wrong

**I tried to restate the 58 EasyOCR values onto the new engine and it was a 45-row silent
no-op.** The log recorded 45 writes; the values changed **zero** times.

`merge_append`'s docstring says *"Add or **correct** FIELDS on an existing clip"*. It cannot
correct. It calls `build_record(...)`, which defaults to `rev=1`, and `append_many` treats the
caller's rev as a **staleness signal**:

> *"If N is no higher than what is already stored, the caller read before someone else wrote
> and its CONFLICTING values are the old ones — so it **fills gaps only**."*

Stored rev was 5; incoming rev 1 never wins. **The merge semantics are correct and
deliberate** — that rule is what makes concurrent appends safe. The defect is narrower and
real: **a function documented as correcting a field structurally cannot, and reports success
while doing nothing.** That is this project's most familiar shape, in a core function every
backfill uses.

It has been invisible until now because BL-1016's `motion` and BL-1027's `ocr_gate_text`
backfills only ever wrote into **empty** fields, where gap-filling and correcting look
identical.

**No data was harmed:** 45 extra revs, 0 values altered, 0 accounts blanked, 0 hidden values.
I did not change `clip_library.py` — the blast radius is every writer in the tree, and the
right fix (let a caller pass a rev above the stored one, or rename the function) is a decision
for whoever owns that file, not a thing to slip into an OCR round.
