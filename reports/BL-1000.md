## 2. The decision log — the walk was dark, and now is not

BL-999 named the gap: *"walk and labelling stages are absent from DecisionLog, making the
costs invisible without manual log reading."* Confirmed at HEAD — `DecisionLog` was imported
by `clip_pipeline.py` and nothing else, so the **render** half printed
`no silent stages, nothing unaccounted for` and the **front** half printed nothing.

The brief says a dark stage is itself a finding: *instrument or report*. `clip_runner.py` was
FREE and clean, so I instrumented it. **Live output from stage 2:**

```
stage                            in      out   dropped  seconds
accounts                        249      128       121
         121  not reached before target/cap
view floor                     1875     1695       180
         180  below the view floor
dedup                          3323     1695      1628
        1627  already in the library
           1  seen in an earlier run
store                            67       67         0
produced 67   spend $0.1500 of $0.1500 cap
no silent stages, nothing unaccounted for.
```

Deliberately **derived from the final stats dict**, not threaded through the walk loop: every
number was already counted there, so the log adds no second bookkeeping that could drift, and
it cannot change what the walk does — which matters in a module three other rounds read. It
is wrapped so a reporting failure can never lose a walk that has already been paid for.
12 new tests hold the property that makes it worth reading: **the books balance by
construction**, so a row cannot leave a stage without a named reason.

**`repost` and the labeller still do not emit one.** Their numbers are complete in their own
summary blocks; they are simply not in `runs.json`. Reported, not silently left.

### FINDING 1 — `runs.json` is an unlocked read-modify-write and loses entries

The walk's log **printed correctly and never reached the file.** `decision_log.write()` reads
`runs.json`, appends, and writes tmp+replace with **no lock**. Thirteen concurrent
`clip_render` runs were writing the same file; one of them read the pre-write version and
wrote back after mine, and my entry was gone. Writing the same record by hand afterwards
worked first time, which is what isolates the cause to concurrency rather than to the code.

This is the same shape as the clip-library race BL-863 measured — and there the fix was to do
the check inside the lock `append_many` already takes. `runs.json` has no lock at all.
**Under several rounds, treat the terminal summary as the record and `runs.json` as
best-effort.**

### FINDING 2 — a walk reports two different spends

The first live log read **`spend $0.2094 of $0.1500 cap`** — a run apparently 40% over a
ceiling it had just correctly stopped on. Both numbers are real and they count different
things:

- `st["spend_usd"]` = `paid_calls × cost_per_call` — the walk's own arithmetic, and
  `paid_calls` is only completed **after** the loop, when per-account page counts are summed;
- the **cap** is enforced against `spent_fn()`, the incremental meter reading the HTTP
  client's billed-request counter — which reported $0.1500.

Only the metered figure is what the ledger will show. The log now prefers it and notes the
difference when they diverge by more than half a cent.

Each of these has silently failed in this project before, so each is asserted against the
**live library**, not read out of the code.

| boundary | result |

**Two "failures" were mine, and checking them was the point.**

- **`MATCHER_FIELDS` lists `clip_duration_s`, which is empty on every clip.** Not a defect:
  `song_library.py:1026` reads `clip.get("duration_s") or clip.get("clip_duration_s")`, so
  the real name is `duration_s` (1,842 filled) and this is a fallback alias the walk has
  never populated. The `or` is what has been saving it. **Worth naming as a trap** — a
  constant advertising a permanently-empty field will mislead the next reader.
- **"0 moods in the store"** was my check reading `.get("mood")` off a value that is a
  **list**, on a store whose first key is `_readme`. The matcher demonstrably works.

One residual anomaly, reported rather than dressed up: **3 clips of 1,668 carry a positive
`bed_dbfs`** (0.1, 0.2, 1.3), which is impossible for dBFS. It is **not** the LUFS-into-dBFS
wiring MEMEBOT-046 warns about — a LUFS value would be near −14, still negative — and
`speech_dbfs` is positive on the same rows. A measurement artifact at 0.18%, named and left.

## 4. Caps bind mid-run, and the meter records through them — 10 of 10

Not "the run refuses to start without a cap" — BL-995 proved that, and it is a different
guard. The claim here is that a run **already in flight** stops.

| property | result |
|---|---|
| meter flushes every 25 calls | 60 calls → ledger `[25, 25]`, 10 pending |
| the final flush is a REMAINDER | `[25, 25, 10]` — not a re-write of all 60 |
| no double counting | sum = 60 of 60 |
| the CLOCK bound flushes a stalled run | 5 calls, +31 s → ledger `[6]` |
| the cap HALTED a synthetic run mid-flight | halted after 11 of 40 accounts |
| spend recorded at the halt | $0.0132 on 22 calls |
| the halt appears in the DECISION LOG | `halted on max_run_usd` |
| the capped run's books still balance | 0 unaccounted |

**And it bound on the live run too:** stage 2 stopped on `! STOPPED at your run spending
limit` at exactly $0.1500.

### FINDING 3 — the labeller's cap covers the model leg and NOT the retrieval leg

This is the overspend, and it is a real hole rather than a mistake in my arithmetic.

```
declared stage 3 cap : $0.25          (BL867_BUDGET)
model leg            : $0.1831  <- OBEYED the cap and stopped under it
retrieval leg        : $0.4200  <- 700 calls, NO CAP CHECKED AT ALL
stage 3 actual       : $0.6031        = 2.4x the declared ceiling
round total          : $0.7573 of a $0.60 budget = +26%
```

`bl867_deep_label.py` accumulates `spent` from the **OpenRouter response cost** and breaks
when `spent >= BUDGET`. The IG retrieval that precedes every model call is metered — it
flushes correctly, which is why the number above exists — but **nothing compares it to a
ceiling**. At 25.8% retrieval success, three of every four paid retrievals buy no label at
all, so the uncapped leg is also the leg with the worst yield.

**The cap did not fail; it was never asked.** A budget knob that governs one leg of a
two-leg stage will under-report by exactly the ratio of the legs — here 3.3×. Any future
run of this driver should treat `BL867_BUDGET` as a model-spend knob and cap the retrieval
leg separately, or the declared figure is fiction.

The clock bound exists because **a count bounds dollars and only a clock bounds a stall**:
BL-914's tiktok run was killed on a timeout and wrote $0.0000 against a vendor-measured
$0.0668, and a hard kill on Windows runs neither `finally` nor `atexit`.

**A third thing worth knowing, found the hard way:** `flush()` calls `record_fn` by
**keyword** and catches *every* exception, so a `record_fn` with the wrong signature fails
**silently** and the meter simply never writes. My first stub did exactly that and read as
"the meter is broken". In production the same swallow turns a bad `record_fn` into
permanently unmetered spend.

cost depends entirely on how much unwalked supply is left, and quoting either as *the* number
without that condition is how the $0.0504 figure went stale.

## 7. What I got wrong

1. **My cap/meter stub had the wrong `record_fn` signature**, and `flush()` swallowed the
   `TypeError` by design — so 4 of 10 properties read as failures of the meter rather than of
   my test. Corrected, and the swallow is now documented as a production hazard.
2. **Two of my eight boundary checks were wrong, not the pipeline** — `clip_duration_s` is a
   fallback alias, and the song store's values are lists behind a `_readme` key. Both were
   investigated before being reported as defects.
3. **My first read of `runs.json` used the key `run_kind`; the field is `kind`.** It gave the
   right answer (zero walk entries) for the wrong reason, and I checked before concluding.
4. **I declared a $0.25 cap for stage 3 and spent $0.6031.** I read `BL867_BUDGET` as a stage
   ceiling; it is a model-leg ceiling. The budget was declared before spending, as the brief
   requires, but it was declared against the wrong quantity — and the run had no second gate
   to catch it. The round is 26% over as a direct result.
