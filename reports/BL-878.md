# BL-878 — the two silent defects fixed, and the automation that has never once fired on its own

Acts on BL-874, which found both defects and correctly left them for a round that holds the
files. Tooling and docs only — no module edited, no paid calls.

**The finding that matters most is not one of the two.** `ff_main` — BL-874's automatic
`main` advance — **has never fired automatically.** Nothing schedules `wip_commit`, and every
round pushes with plain `git push`, which never reaches it. Every advance so far, in three
rounds, was a human typing `python tools/ff_main.py`. `main`'s gap reads zero because it is
being maintained by hand, which is precisely the state BL-874 set out to end.

---

## 1. wip_commit COMMITTED A WRITE IN PROGRESS — fixed

`clippershq/song_library.py.tmp.10364.377f7df1be70` passed every filter: under `clippershq/`
so `INCLUDE_DIRS` admitted it, absent from `NEVER`, and unclaimed — **because a writer never
declares its own temp file**, so the claim registry can never help here.

What that file *is*: the middle of an atomic `write temp → fsync → os.replace`. Every locked
writer in this repo uses that sequence, so whenever one is running there is a sidecar on disk
holding a **truncated module**. A human triaging reads the name and skips it. **A timer does
not read names**, and this tool runs unattended.

Matched by **shape**, since the pid and random suffix differ every time — no literal allowlist
could work:

```
NAME.tmp.<pid>.<rand>   NAME.tmp / .temp   NAME.lock   .swp/.swo
NAME.orig / .rej        NAME.part          .#emacs     NAME~
```

Reported under `SKIPPED` rather than dropped, so an unattended run leaves evidence a writer
was mid-flight.

### What else in the tree matches that shape

Measured across the whole tree: **64 transient sidecars, all `.lock`.** Only **2** sit inside
this tool's commit scope:

| Path | In scope | Also gitignored? |
|---|---|---|
| `clippershq/resolve_cache.json.lock` | yes | **yes** — `*.lock` |
| `clippershq/spend.json.lock` | yes | **yes** — `*.lock` |
| the other 62 | no — `clip_library/`, `scratch/`, `output/` | — |

So those two had a second line of defence. **The `.tmp` shape does not.** `.gitignore` lists
only `config.json.tmp` and `state.json.tmp` — never the atomic-write form. Planting one and
asking git directly:

```
clippershq/<module>.py.tmp.<pid>.<rand>   ignored: NO   <-- git WOULD have committed it
```

**For the exact file BL-874 found, this pattern filter is the only thing standing in the way.**

`tests/test_wip_commit.py` — 5 tests, **green**: the literal filename BL-874 saw, every
sidecar shape, an end-to-end `--dry-run` against a planted temp file, case-insensitivity, and
— the failure that would matter more — that `template.py`, `tmp_helper.py` and
`contemporary.py` are **not** excluded.

Both directions, asserting on exit codes, never printing a value:

| Planted | Result |
|---|---|

| …reported as a SECRET BLOCK hit (config path only) | **yes** |

| an unreadable path | **FAILS**, exit 1, *"ZERO readable"* |
| **CRLF-tainted paths** — the original bug | **FAILS**, exit 1 |
| …the same paths with the CR stripped | exit 0 — proves the failure is the CR, not the paths |
| an empty list | does not claim a clean scan |

**My first CRLF fixture was wrong and reported a false FAIL.** It wrote a CRLF file and read
it back — but Python's universal-newline translation strips `\r` on read, so the round-trip
could not reproduce the bug at all. The fixture now builds the tainted path with a literal
trailing `\r`. Worth recording: a test that cannot reproduce the bug it guards is the same
class of defect as the guard it is testing.

## 3. THE GUARD SWEEP — 9 was optimistic in one direction and pessimistic in another

`scratch/bl878_guard_sweep.py` looks for four shapes: empty-input success, swallowed
exception, piped exit code, and unfireable guard.

**First pass: 14 findings. Real: 1.** The honest breakdown matters more than the number.

- **10 were the same 4 files**, triplicated by git worktree copies under `scratch/mb029/`,
  `scratch/mb034/`. Excluded.
- **2 were false positives I verified by hand and then designed out:**
  - `quality_gate.detect_hashtag_language()` returns `None` for *no marker found* — the
    documented contract, and the whole language policy rests on unknown never penalising.
    `None` means **unknown**, not **pass**; it is no longer treated as a success constant.
  - `thumbnail_vision._ensure_heif()` has a bare `except: pass` and says why in its own
    docstring — it registers an **optional** decoder and is not a guard at all. It matched
    only because the name regex matches "ensure".

**Category C — piped exit code — found zero in committed code, and that zero is real.** I
validated the regex against known-bad forms before trusting it (`scanner.py … | tail`,
`verify_claims.py … | grep` both hit; `echo hello | tail` correctly missed). `PUBLISHING.md`
warned about this shape and committed code has heeded it. *I* violated it twice in BL-865 —
interactively, in shell, not in a committed file.

**The one real finding is category D, and it is the round's headline** — see §4.

## 4. ff_main HAS NEVER FIRED AUTOMATICALLY

BL-874 asked: *report main's gap — if it is anything other than zero, the automation is not
firing.* The gap is zero. **The test was too weak, and the conclusion it invites is wrong.**

What I found looking for the trigger rather than the symptom:

- **Nothing schedules `wip_commit`.** No cron, no scheduled task, no timer. The "auto-commit
  on a timer" described in earlier rounds does not exist as a running thing.
- **The only installed hook is `pre-push`**, which delegates to `repo_guard.py` and has no
  knowledge of `ff_main`.
- **Rounds push with plain `git push`.** `ff_main` fires only on `wip_commit --push`, a
  command no round runs.
- **`origin/main`'s reflog shows 6 updates**, all inside the three rounds where I ran the
  advance by hand.

Measured live during this round, before I advanced anything: **`main` was 5 commits behind
local HEAD** — four of them other rounds' work. It read zero against *pushed* state only
because I had advanced it manually at the end of BL-874.

> A guard wired to an entry point nobody invokes is the same defect as a scan that reads zero
> files: it reports nothing, and its silence reads as health.

**The fix, not taken here:** move the advance into the `pre-push` hook — the one path every
round already uses — via `repo_guard.py`'s `pre-push-hook`. That file is **outside this
round's claim**, and BL-874's discipline of leaving a defect to a round that holds the file is
exactly what made this round possible. Recommended as the next round's work, with the
ancestry gate and `..` assertion already built and tested in `ff_main`.

## 5. THE MANIFEST RULE, IN docs/CLAIMS.md

Written into the *Workflow* section, where rounds already read the format:

> **A manifest is only committable once the things it CITES are committed. The manifest waits
> for the code. Never the reverse.**

The tempting fix is named explicitly: when a manifest cites a symbol present in the working
copy but not at HEAD, committing that file turns the suite green immediately — and snapshots
**another round's half-finished module** to do it. A four-row table gives each case; the
in-flight case resolves to `git rm --cached`, leaving the manifest on disk to become
committable when its owner lands.

### It was exercised within the hour, by a case the table already covers

The suite went red on `MEMEBOT-022`, which claims `const song_library.py::TIER_TITLE`.
**Not a regression from this round, and not mine to fix:**

- It verified **10/10** when BL-874 committed it (`7879644`).
- `TIER_TITLE` was **deleted afterwards** in `5c559a1`, by MEMEBOT-032's matcher work —
  a correct deletion, made on measurement.
- **BL-881 filed a claim for it 0.4 minutes before I found it**, holds
  `docs/claims/MEMEBOT-022.claims`, `tools/verify_claims.py` and `tests/test_claims_manifest.py`,
  and explicitly recorded that `docs/CLAIMS.md` is held by BL-878. A clean split; I did not
  touch its files.

BL-881's approach — *drop the claim with a reason, do not re-add the constant* — is the same
rule from the other side: re-adding a deliberately-deleted constant to satisfy a checker is
the identical mistake as committing an in-flight file. It also proposes a `SUPERSEDED` marker
so a correctly-undone claim can say so without lying or failing, which is a genuine gap in
what I wrote: my table's fourth row says *"fix the manifest — the claim is now false"*, and
"false" is the wrong word for a claim that was true and was then correctly undone.

### Method / limits

- Claim filed with **seven repeated `--write` flags**; `claim.py` confirmed all seven
  registered individually.
- Both fixes are proven by **planting** the artefact — a temp file in the tree, a real
  credential in a scanned file — because both defects were things that looked fine. Reading
  the code would not have caught either.
- The credential fixture is read from the live config, written to a temp file, asserted on by
  exit code only, and deleted in a `finally`. No value is printed anywhere.
- The guard sweep is static. It cannot see a guard that fails at runtime for a reason the AST
  does not show, and category D is hand-seeded rather than inferred — it found `ff_main`
  because I went looking for the trigger, not because the sweep is clever.
- `repo_guard.py` (the `pre-push` fix for §4) and `MEMEBOT-022.claims` (§5) were both left
  alone: outside this round's claim, and the second is actively held by BL-881.
