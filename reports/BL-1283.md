## 1. `envelope.items_of` — a GROUP is not a RESULT

`sections` was in `CONTAINER_KEYS`. It should never have been. A section is a *container of*
results; the medias live one level further down at
`response.sections[].layout_content.{medias,fill_items,one_by_two_item.*.items}[]`.

Measured on the live payload saved at `_probe_samples/ig_hashtag_medias.json`:

| reader | items |
|---|---:|
| `envelope.read()` **before** — `state=ok`, `path=response.sections` | **9** |
| `ig_discovery._section_medias` — the shipped parser | **33** |
| `envelope.read()` **after** | **33** |

**It read 9 of 33 — 27% — and returned `state=ok`.** That is worse than the `UNREADABLE` case
this module exists to catch. `is_failure` was False, `__bool__` was True, and `describe()`
said *"9 item(s) at response.sections"*. An undercount that reports success cannot be noticed,
which is why three separate rounds (BL-1276, BL-1280, and this one) found it independently.

### It was never one payload

Re-run across **all 134 readable payloads** in `_probe_samples/`, comparing `read()` against
`read()` with the expansion disabled — the same function, not a reimplementation of the old
one, which matters: the first cut of the sweep used a hand-rolled baseline and produced 30
spurious "0 → 1 improvements" because it modelled the `SINGLE` state wrong.

| | files |
|---|---:|
| unchanged | **126** |
| undercounted before the fix | **8** |
| **lowered by the fix** | **0** |

Every one of the eight is an Instagram sections feed and every one was short by ~3x:
9→27, 9→27, 9→33, and 10→30 five times. The **9→27** on
`ig_v2_hashtag_clips_memereels_p2.json` reproduces BL-1276's live figure — *"9 of 27, on two
independent calls"* — exactly, from a saved payload, at no cost.

### The fix is fail-safe by construction

`_explode_groups` replaces the list it was given **only when the expansion yields something**.
A section layout it does not recognise degrades to the old undercount, never to zero. There is
no input on which this can return fewer items than before — which the 134-file sweep confirms
empirically, and which is the property that makes a change to this module safe at all.

`path` was deliberately left reporting `response.sections`, and the items' origin is recorded
in a **new `group_path` field**. `path` has always meant "where the container was found", and
`tests/test_envelope.py` asserts on exactly that. Overloading it would have cost a real
diagnostic to buy nothing. `test_envelope.py`: **24 tests, OK.**

## 2. The TikTok send file — wired, and matching master

`tiktok_send_list.build()` had no caller anywhere in shipping code. The only three mentions
were prose: two comments in `tiktok_finder.py` and a *"run it by hand"* note in
`exporters.py:273`. **`meme_send_list.build()` had no caller either** — and that is not scope
creep, it is a precondition: the tiktok file excludes every address already in the meme file,
so building 3 against a stale 2 partitions against a set that no longer exists.

`control._build_send_files` — the operator's `[b] BUILD MY SEND LIST` — now builds all three
in partition order, each in its own `try` so a partner list cannot take down the editor list.

Driven for real against the real master:

| | |
|---|---:|
| master rows | 62,092 |
| tiktok-tagged in master | **124** |
| kept after the send gates | **123** (1 excluded: already in another send file) |
| rows in `TIKTOK_PAGES_BOT_READY.csv` | **123** |
| file set == builder set | **true**, both directions empty |
| MX coverage of this file's domains | **100.0%** |

The set equality is recomputed independently from master rather than trusted from the
builder's own `stats` — both difference sets are empty, in both directions.

**On the "115 → 123" figure, precisely:** 115 is what the brief states and what
`tiktok_send_list.py`'s own docstring records ("all 115 rows raised"). **This round did not
measure it.** The first build overwrote `TIKTOK_PAGES_BOT_READY.csv` before its prior row
count was recorded, `output/` is gitignored so there is no history, and no backup exists. What
is measured here is **123 written against 124 tagged in master**, with the single exclusion
accounted for (already present in another send file). If 115 was accurate, eight paid
addresses have now reached the file for the first time; that arithmetic is inherited, not
independently confirmed.

The three-way partition, measured on the written files:

| | editors | meme | tiktok |
|---|---:|---:|---:|
| rows | 3,978 | 874 | 123 |
| pairwise overlap | 0 | 0 | 0 |

### Two defects the wiring exposed on its first run

Both were found by running it, not by reading it:

* **`assert_clean` contradicted the build it was re-checking.** Both partner files KEEP role
  inboxes by the operator's standing decision (BL-1186), but `assert_clean` defaults to
  `exclude_role=True` and meme's raises `AssertionError` on every role address it finds. Called
  with the default it aborted the meme build on its own 151 kept addresses. Now called with the
  module's own `*_KEEP_ROLE_INBOXES` flag.
* **The two modules return different shapes for "nothing wrong".** tiktok's `assert_clean`
  filters zeroes and returns `{}`; meme's returns `{'dead_mx': 0, 'role': 0, …}` — non-empty,
  therefore truthy. A bare `if problems` reports a perfectly clean meme file as a problem. The
  emit now reduces to what is actually non-zero rather than reconciling two modules another
  round holds.

The build line also now says **what the check did not check**: with role inboxes kept the role
test is *skipped*, and "CLEAN" would otherwise read as "there are none" when there are 151.

### A third defect, and it is the one worth reading: [b] desynchronised the n8n target

`LATEST_BOT_READY.csv` is what the n8n automation watches. BL-787 deliberately made it
**byte-identical** to `ALL_BOT_READY.csv` so that whichever file an automation reads it gets
the complete, fully-flagged set — before that it held 2 rows for two weeks and a sender aimed
at it would have mailed 2 people out of thousands.

`all_bot_ready.main()` — the **command-line** path — refreshes the mirror from the same rows
immediately after writing the primary. **`control._build_send_files` does not call `main()`.**
It calls `build()` and writes the primary itself, so it rewrote one half of a pair that is
only correct as a pair.

**Pressing [b] has therefore desynchronised the mirror every time, and this predates BL-1283
entirely.** It went unnoticed because the test compares the two files by sha256 and they only
diverge once somebody uses the menu instead of the CLI — this round pressed [b] and
`test_send_superset::test_the_automation_mirror_is_still_byte_identical` went red immediately:

```
AssertionError: '685c8702…' != 'd551f837…'
  LATEST_BOT_READY.csv is NO LONGER byte-identical to ALL_BOT_READY.csv.
```

Fixed in the same function, in its own `try` — a stale mirror is bad, a build that dies after
writing the primary is worse. `test_send_superset`: **15 tests, OK.**

**This is the round's one accidental finding, and it was free.** It cost nothing to find
because wiring a menu action correctly meant actually running it, and running it is what the
send files had been missing for the whole time they had no caller.

## 3. `run.json` survives a killed run — demonstrated twice

The ledger write and the findings write had the identical defect and only one was fixed. Both
sat below `discover()`; `discover()` *is* the capture loop. The export now gets the ledger's
exact treatment: a checkpoint every `EXPORT_CHECKPOINT_PAGES = 10` judged pages via a new
`on_progress` hook, plus a flush in the same `finally` that already closes the ledger.

`EXPORT_CHECKPOINT_PAGES` is **smaller** than `SPEND_CHECKPOINT_CALLS = 25` on purpose: losing
25 requests of accounting costs $0.015 and is recoverable from the vendor's quota, while losing
10 judged pages costs the profile calls that bought them *and* the judgement, and nothing on
the vendor's side can return either.

### Arm A — the `finally` tail, against the real pre-fix module

The control is `git show HEAD:clippershq/tiktok_finder.py`, imported under its own name and
driven by the **same** stub client through the **same** entry point, killed at the **same**
call. Not one billed request: the client is a stub, and `$CLIPPERSHQ_SPEND_FILE` and
`master_csv` were redirected to temp paths so neither the real ledger nor the real lead file
was touched.

| | run.json | rows | profiles bought | billed calls |
|---|---|---:|---:|---:|
| **before** (HEAD) | **absent** | 0 | 0 | — |
| **after** | present | **14** | **14** | 30 |

`complete: false`, `export_reason: "interrupted"`. Fourteen pages' worth of purchased
evidence, kept instead of lost.

### Arm B — the checkpoint, under a kill that runs no `finally` at all

`os._exit(137)` from inside the client: no exception, no `finally`, no atexit, no flush. If
`run.json` exists afterwards, a **checkpoint** wrote it mid-loop.

| child exit | run.json | rows | `export_reason` | well-formed |
|---:|---|---:|---|---|
| 137 | present | **10** | `checkpoint` | yes |

The write is atomic (temp + `atomic_io.replace`), so a kill *during* a checkpoint leaves the
previous complete file rather than a truncated one — without that, the fix would be worse than
the bug on exactly the kill it exists to survive.

`complete` is set only by the `final` write. A partial file must say so: a checkpoint and a
finished run are the same shape, and a reader that cannot tell them apart reports a killed
run's counts as a complete one's.

## 4. The dotfile hazard — five sites, one sanitiser

`tiktok_finder.sheet_filename` has carried this fix since BL-1260 and was the **only** place
in the tree that had it. Four more sites derived a path from a handle with no sanitiser at all,
and three of them must agree or the pipeline stops finding its own files:

| site | what a dot-handle produced |
|---|---|
| `tiktok_finder.discover` | a hidden OCR work **directory** — every frame and intermediate |
| `clip_pipeline.stage_clip` | a hidden directory holding **every staged clip** for that page |
| `clip_pipeline.expected_output` | the path the renderer is told to write |
| `clip_pipeline.find_output` | the path the pipeline reads back |

All five now route through **`clippershq/safe_name.safe_component()`**, and `sheet_filename`
is a *name* for the shared rule rather than a second copy of it. Proved end to end on the real
handle `.boovkanio` — written to disk, then a recursive glob asked whether it can see it:

| site | component | glob sees it | any hidden component |
|---|---|---|---|
| `sheet_filename` | `_.boovkanio.png` | yes | no |
| OCR workdir | `_.boovkanio/frame.png` | yes | no |
| `stage_clip` | `tiktok/_.boovkanio/111_222.mp4` | yes | no |

`expected_output` == `find_output`: **true**. Collision-safe: `_` is prepended, never stripped,
so `.rzn1` and `rzn1` — two different real accounts — keep two different names. Stripping would
trade an invisible file for a lost one.

### The rate, with its denominator

Three rounds have quoted three figures and none said what over what:

| | measured | population |
|---|---|---|
| BL-1260 | 1.6% | 2 of 125 handles |
| BL-1279 | 2.08% | a larger population |
| **BL-1283** | **1.07%** | **4 of 374** in `tiktok_pages_seen.json` → `pages` |

`.jbpoppedyoshi`, `.rzn1`, `.infinitememes`, `.02_92`. They are not in conflict — different
populations. The honest reading is *order of one to two per hundred*, which at the 159-page run
that lost one page is one to three hidden deliverables per run, matching both incidents.

**Adjacent and deliberately NOT fixed:** a handle ending in a dot or a space is renamed by
Windows at write time — the same class of bug, a different mechanism, and outside the named
defect. Flagged, not silently folded in.

## 5. `test_repost_export` — real, fixed, and it will re-arm

**24 tests, OK.** The four-round red is closed.

It was never environmental and never a bad fixture. It is a *staleness tripwire*: it reads the
on-disk CSV and compares it to `build_rows()` computed now.

| | on disk | known |
|---|---:|---:|
| 2026-08-12 (BL-1235 rebuild) | 327 | 327 |
| the brief | 327 | 340 |
| this round, first measurement | 327 | **344** |
| this round, 40 minutes later | 327 | **374** |

**The gap widened by 30 inside one round**, because the sources it folds — 55 `clip_library`
shards, the render ledger, `repost_rejections.jsonl` — are appended to continuously. 47
accounts he could DM were missing from the file he downloads.

Two parts, and only the second is durable:

1. **The export was regenerated** — 374 accounts, union of 5 sources, 9,741 rows → 2,761
   records (3.53x), 2,091 ledger lines → 1,183 records (1.77x). This makes the tripwire green.
2. **`exporters.build_repost_accounts()` now REBUILDS** instead of `_read_csv`-ing the frozen
   file. `build_send_list` beside it solved the identical problem the identical way. 3.4s over
   55 shards; `build_send_list` rebuilds over 62,092 master records on every download.

**Stated plainly: part 1 will rot again.** The tripwire compares a snapshot to a live
computation, so it re-arms the moment the next walk appends. What part 2 fixes is the thing
that actually mattered — the operator's download is no longer a stale snapshot at all. Making
the *test* stop rotting means changing the test, which is in the held glob.

## 6. The "environmental pair" — the record, corrected and then acted on

BL-1273 already measured that both suites PASS under system 3.11 and diagnosed missing
*packages*. **Nobody installed them**, so five rounds kept calling the reds environmental.

Verified again under `.venv` before the fix:

```
C:\Program Files\Tesseract-OCR\tesseract.exe   present
C:\Windows\Fonts\seguiemj.ttf                  present (12,450,664 bytes)
```

**The binary and the font were both already installed.** What was missing was two pure-python
wheels, 14 kB and 2.4 MB. Installed through `clippershq/pipguard.py` (dry-run first: *"resolution
is CLEAN — no protected package moves backwards"*), then:

| suite | result |
|---|---|
| `memebot/meme/tests/test_ocr.py` | **154 checks, OK** |
| `memebot/meme/tests/test_render.py` | **91 checks, OK** |

Moved out of the OPTIONAL block, because *"optional at runtime"* and *"optional to the suite"*
are different claims and the file used to make only the first.

### Only one of the two could be pinned, and finding out why cost a red

Pinning both turned `tests/test_env_audit.py` red —
`test_optional_imports_are_not_pinned_as_required` carries a hard-coded list,
`("torch", "easyocr", "open_clip", "pytesseract")`, of guarded imports that must never appear
as a `==` pin. **The rule is right in general and wrong for this package.** It exists because
`essentia` has no Windows wheel and pinning it would make the file uninstallable on the machine
it is for; `pytesseract` is a 14 kB pure-python wheel that installed here in under a second.

`fonttools` is not in that list, so it **is** pinned. `pytesseract` is documented in the file
with the exact one-line install instead. The honest fix is to narrow that list to packages
that actually lack a wheel here — a test change, therefore blocked. It is item 6 in §7, and
`test_env_audit` is back to **24 tests, OK**.

**Stop calling these reds environmental.** They were an unpinned dependency for five rounds.
