## 1. What actually happened

**The file was there.** `output\fresh50\REVIEW_50_FRESH.html`, written 2026-08-10 13:09,
37,188 bytes. It was not swept — it lives under `output/`, and only `scratch/` ages out. He was
looking in `output/` at loose files; `fresh50` is a *folder*, and the thing he wanted was
inside it.

That is the smallest part of the answer. **The file could not be opened by any route he had**,
for three independent reasons, each measured rather than assumed.

### 1a. It held 34 pages, not 50 — and said so itself

Its own `<title>` read **`ClippersHQ — mark 34 pages`**. Its four row-chunks held 10, 10, 10 and
4 rows: **34**.

BL-1206 §8 is headed *"Fifty fresh pages he has never seen"* and its first line says
*"**34 judged of 50 attempted**, 17 passed … The other 16 were refused before he sees them:
9 no-videos, 7 unjudgeable."* The body was accurate. The heading, and the sentence that named
the path, were not — they promised fifty and pointed at a file holding thirty-four.

### 1b. Double-clicking it shows ZERO rows

The windowed sheet ships as **two documents that sort next to each other in a folder listing**,
and only one of them opens off a disk:

| document | rows when double-clicked | images |
|---|---:|---:|
| `REVIEW_50_FRESH.html` — the shell | **0** | 0 |
| `REVIEW_50_FRESH_offline.html` — rows inlined | 10 | 10 |

The shell holds no rows. It fetches `rows_000.json` at run time, and Chromium refuses that:

> `Fetch API cannot load file:///…/output/fresh50/rows_000.json. URL scheme "file" is not supported`

The shell sorts **first**. So the natural thing — open the folder, double-click the file whose
name matches the report — produces a page with a header, a counter reading `0 saved`, and
nothing else.

### 1c. Served, every thumbnail 404s

BL-1206 built the sheet with `thumb_dir="../review_50_fresh_thumbs"`. Relative to the HTML *on
disk* that is correct. But `serve()` roots its HTTP server at the folder holding the HTML, and
`SimpleHTTPRequestHandler` collapses `..` and **refuses to serve above its root**. Measured:

| request | status |
|---|---|
| `/REVIEW_50_FRESH.html` | 200 |
| `/rows_000.json` | 200 |
| `/../review_50_fresh_thumbs/DYO-vpehuA8.jpg` | **404** |

All 473 thumbnails. The rows, verdicts, buttons and marking would all have worked; only the
pictures would be missing. A sheet of empty 9:16 boxes reads as *"this is broken"*, not as
*"one path is wrong"*.

### 1d. No launcher ever pointed at it

`OPEN_REVIEW_SHEET.bat` serves `output\REVIEW_500.html` on port 8777, rooted at `output\`.
Nothing in the repo served `output\fresh50\`. There was no command he could run.

### The corroboration

**Not one mark in either file carries the sheet id `BL-1206-FRESH50`.** 904 marks say
`BL-1196-500`, 103 say `bl1186_pages`, 51 say `bl1190_pages`. He never marked that sheet —
consistent with never having had it open.

**Said plainly:** the report named a real file, at the right path, that was one-third short of
its promised size and could not be read by double-clicking, could not be served with its
pictures, and had no launcher. A report that names a file the operator cannot open is worse
than one that says the file was not made, and this was worse still — it was made, and every
way of reaching it failed.

## 5. The launcher

`OPEN_FRESH_50.bat` → `tools\serve_fresh50.py` → port **8790**, so it never collides with the
500-sheet's 8777 and both can be open at once.

* **Survives its window closing** — `start ""` gives the server its own process. This is the
  BL-1192 defect: the server used to run in the foreground of the .bat's window, so closing it
  killed the server while the open sheet kept POSTing marks into a closed socket and reported
  *"save FAILED"* in green. ~50 marks went that way.
* **Re-uses a live instance** — verified: a second launch printed
  *"the sheet is ALREADY being served at http://127.0.0.1:8790/REVIEW_50_FRESH.html — opening
  it."* rather than dying on a taken port.
* **Refuses loudly** if the sheet or the venv is missing, rather than opening an empty page.

**It is a serve-only entry point, and that is not tidiness.** `review_sheet.py --serve` builds
before it serves, and *neither* build path can rebuild this sheet: without `--windowed` it calls
the legacy renderer and would overwrite the windowed sheet with the one-document shape that
froze his browser; with `--windowed` it calls `build_windowed()` **without a `sheet=` argument**,
so the id falls back to `BL-1196-500` and every mark he made on these 50 would merge into the
425's under colliding row numbers. That failure would be invisible — the marks still save —
until the next round tried to read them.

Served end to end in Chromium at the real URL: 50 rows, 5 batches, 10 images decoded,
**0 HTTP errors**.
