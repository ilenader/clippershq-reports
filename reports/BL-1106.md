# BL-1106 — one global time control, and every panel honest about what it did

**Budget declared before spending: $0.00 hard cap. Actual spend $0.00.** No paid call, no
network call. The screenshot pass drives Playwright against a local uvicorn; the test client
runs the app in-process. **Zero external requests, asserted per width and per range.**

Preconditions cleared first: all four dashboard files **FREE and clean** — BL-1092 had landed,

## What shipped

**One control above the tabs — `7d / 30d / 60d / 90d / all / custom` — obeyed by every panel
and every chart.** It is a `radiogroup`: arrow keys move, the selected state carries a border
and a weight change as well as a tint, so it survives greyscale.

The range lives in **one object** in `app.js` and `get()` — which every panel already goes
through — appends it to every request. **No panel builds its own URL, so no panel can forget
to obey the range.** `/api/settings`, `/api/health` and the two write endpoints are explicitly
excluded: they describe the machine now, not a period.

Server side, `dashboard/range_filter.py` is a pure module — one window, one parser, one
`meta()` that every endpoint reports through. Twelve panels cannot drift into twelve slightly
different ideas of "last 7 days" because there is only one.

## The three traps, handled — not rediscovered

### Trap 1: `posted_at` is an epoch int

`stamp_epoch()` takes epoch ints, epoch floats, digit-strings and ISO alike. Pinned by seven
tests, including `test_the_LIBRARY_shape_filters_correctly`, which filters a row shaped
exactly as `clip_library` stores it.

Two edge cases the trap invites and the tests now hold shut: **`True` is an `int` in Python**
and would otherwise date a row to 1970, and a millisecond timestamp would otherwise land in
the year 55000.

### Trap 2: every range returns the same number

`meta()` carries `same_as_all`, and the panel says so in words:

> Filtered on **render time** — when the render finished (memebot/runs.jsonl,
> record.finished_at). **All 369** are inside the last 7 days — every range shows this same
> number.

It deliberately does **not** fire on all-time (keeping everything is not a coincidence worth
explaining) and does **not** fire on an empty population — 0 of 0 is "no data yet", never
"every range shows this number".

### Trap 3: rows are not records

Nothing counts lines. The verification prints the collapse every time:

```
library  raw lines 9,507  ->  distinct clips 2,731
ledger   raw lines   985  ->  records 463  ->  finished 369   (2.13x if you count lines)
```

## Item 2 — the clock, named per panel

**Seven distinct notes rendered on the live page**, captured from the DOM in the screenshot
pass:

| panel | note |
|---|---|
| Clips | Filtered on **the clip's own post date** — when the SOURCE CLIP was posted to Instagram (clip_library, posted_at) — **NOT when we did anything with it** |
| Recent videos | Filtered on **render time** — when the render finished (record.finished_at) |
| Money / ledger rows | Filtered on **spend time** — when the money was spent (spend.json, run.ts) |
| Video state | **NOT FILTERED BY DATE** — a walked file carries only its mtime |
| Hook window rotation | **NOT FILTERED BY DATE** — rotation state is cumulative |

**`lifetime`, `metered` and `estimated` are deliberately NOT filtered**, and the payload says
so. Silently making a field called `lifetime` mean "the last 7 days" would be the worst kind
of correct-looking wrong. The rows, the funnel split and a new `in_range_usd` do obey it.

Charts carry a clock **per series** in `range_by`, and a test asserts `videos_by_day` and
`clips_by_month` do not claim the same one.

## Item 4 — panels that cannot slice say so

- **Video state (the disk walk)** — the only date is the file mtime, which is when a file was
  *written or copied*. Filtering on it would put a confident, wrong "3 videos in the last 7
  days" under the control. The ledger half of that payload **is** sliced, on render time, and
  the note points at it.
- **Hook window rotation** — rotation state is *cumulative by definition*; it is the counter
  that drives least-used picking. Answering "windows used in the last 7 days" with it would
  make the picker look like it had forgotten everything older than the control. So the
  counter declares itself unsliced and an `in_range` block answers the range question beside
  it.

## Item 5 — hand-verified, two independent methods, three ranges, two sources

Method A is the real endpoint through the real range machinery. Method B reads the source
file directly and shares **no code** with A — not the parser, not the window, not the
collapse.

**Against a frozen snapshot, and that is not a convenience.** The first run disagreed by +4,
then by −7, while `clip_library` grew 9,212 → 9,507 lines underneath it. Ten rounds share this
tree and several render. Two methods reading a moving file cannot be compared, and "the counts
drifted" is indistinguishable from a real defect. Both methods now read one copy, taken once.

```
CLIPS -- clock: the SOURCE CLIP's own posted_at
  range   dashboard    by hand   verdict
  7d            330        330   MATCH
  30d          1308       1308   MATCH
  all          2731       2731   MATCH

RENDERS -- clock: OUR render time
  range   dashboard    by hand   verdict
  7d            369        369   MATCH
  30d           369        369   MATCH
  all           369        369   MATCH
```

### Three real disagreements came out of this, all method B's fault, all worth the trip

1. **`status == "ok"` is not the endpoint's definition of finished.** `_is_finished` also
   counts a record with no status but a real `output` — the 4 legacy rows BL-1096 flagged as
   invisible in an ok/failed split. Counting strictly was off by exactly those 4.
2. **A ledger row's identity is a three-tier fallback**, not `render_id`: `render_id` →
   `output` → `clip_id@ts`. Keying on the first tier alone collapsed the 59 id-less lines into
   one bucket, giving 460 records instead of 463. **This resolves the open caveat BL-1096
   raised and could not answer.**
3. **A render's date is a fallback chain too** — `finished_at` → `ts` → `started_at`.
   Demanding `finished_at` dropped the same 4 rows from every *bounded* range while keeping
   them in `all`: a filter losing rows its own population contains.

In all three the dashboard was right and the hand method was wrong. That is the value of a
second method that does not share code with the first.

The pass drives **the real control** — it clicks the button, not the query string, so it would
fail with the control unwired — and compares the two ranges **by number**, not by eye.

### The screenshot pass caught two real defects that the API tests could not

**1. The KPI cards showed the corpus under a dated control.** The note read "showing 330 of
2,731 in the last 7 days" while the card beside it still read **2,731**. The `in_range` block
was computed and returned; `renderLibrary` simply never used it. This was worse than an
ordinary mismatch because *the honest sentence was right there making the wrong number look
verified*. Cards now show 330 / 116 accounts / 78.5% vision / 62 renderable, each labelled
"in range" — and `songs enabled` stays whole with "the store has no date, never sliced".

**2. A chart kept its old picture during a refetch.** Changing to 7 days recomputes the series
server-side — **3.3 s, measured** — and until it landed the corpus chart displayed **eighteen
months under a "7 days" heading**. Stale pixels are worse than a quiet zero: a zero looks like
an answer nobody should trust; a full chart under the wrong heading looks verified. A chart
with nothing to draw is now **cleared** and says which of the two it is — "No clips were
POSTED in this range" or "Loading for this range…". Asserted by counting bars: **18 at
all-time, 1 at 7d**.

Neither was visible to an endpoint test. Both were visible in the first screenshot.

### Two of my own, caught and fixed

1. **`test_dashboard_panels`** — `TypeError: api_audit() missing 1 required positional
   argument`. That suite calls the endpoint functions **directly**, not through the app.
   Fixed by giving `request` a default; `_win(None)` already returned all-time.

   default is exactly what that test exists to prevent, and I introduced one while building a
   feature about not having silent defaults.** Fixed by moving `request` **last** on all four
   endpoints that take other parameters.

Both green.

## Finding the live dashboard

Ten servers listen at once, one per round. Match the **PID**, not the port:

```bash
netstat -ano -p tcp | grep -E "127.0.0.1:8[78][0-9][0-9]" | grep LISTENING
```

Guessing by port lands you on another round's server — which is how a screenshot pass
photographs someone else's page.
