# BL-676 — the view-count decoy: which field actually carries reach, per platform

## No live wrong-field read exists today, but the premise needs correcting and one gun is loaded. TikTok's `view_count` is not null — it is present 52/52 and every value is literally `0`, which is a materially different hazard because `0` survives every `is not None` guard in the pipeline and reads as a measured zero. No TikTok code path reads it. Instagram carries the identical decoy (`view_count = 0` on 30/30 items of the `/v1/hashtag/medias/clips/chunk` surface) and is protected only by field ordering: `play_count` is listed first and wins on 100% of clips items measured. Nothing downstream can tell a decoy `0` from a real measurement, so the day `play_count` is absent on an item, accounts get cut as "known-low" when the truth is "not measured" — a fail-CLOSED inversion of the documented `missing != bad` rule.

## PART 1 — the premise, corrected

The starting claim was "`view_count` appears 52 times and is non-null zero times". Measured against the saved payloads, the field is **non-null 52 out of 52 times**. What it is not, is non-zero:

| sample | field | present | non-null | non-zero |
| --- | --- | --- | --- | --- |
| `search_by_handle.json` | `play_count` | 65 | 65 | **65** |
| `search_by_handle.json` | `view_count` | 52 | **52** | **0** |
| `tikhub_zainvfx.json` | `play_count` | 10 | 10 | **10** |
| `tikhub_zainvfx.json` | `view_count` | 10 | **10** | **0** |
| `hashtag_medias.json` | `playCount` | 10 | 10 | 10 |
| `hashtag_info.json` | `viewCount` | 3 | 3 | 3 (hashtag-level, not per-post) |

This distinction is the entire bug class. A `None` is discarded by every `is not None` guard and lands in the protected UNKNOWN path, where the pipeline's hard rule is "missing != bad, keep and flag". A `0` passes all of those guards and is treated as a real measurement of zero reach. The two failure modes are opposites: null fails **open**, zero fails **closed**.

### Instagram — correct today, by ordering alone

`ig_discovery.py:76` defines the resolution chain:

```
"engagement": ["play_count", "ig_play_count", "view_count", "video_view_count"]
```

Consumed at `ig_discovery.py:242` and `ig_discovery.py:326` via `_to_int(_g(item, fmap["engagement"]))`.

Replaying the real `_g` + `_to_int` over every saved Instagram payload — which field actually wins, per surface:

| sample (n media) | play_count | ig_play_count | view_count | field that WON |
| --- | --- | --- | --- | --- |
| `user_clips` ×6 files (12 each) | real 12/12 | real 12/12 | null | `play_count` |
| `gql_user_clips` ×3 files (24 each) | real 24/24 | null | null | `play_count` |
| `hashtag_clips_chunk` ×3 files (30 each) | real 30/30 | null | **ZERO 30/30** | `play_count` |
| `hashtag_clips_v2_series` (30) | real 30/30 | real 30/30 | null | `play_count` |
| `hashtag_medias` (28, mixed feed+clips) | real 10, null 18 | real 10, null 18 | **real 7**, null 21 | play_count 10, **view_count 7**, NONE 11 |
| `user_medias` (12, all feed video) | null 12/12 | null 12/12 | null 12/12 | NONE → UNKNOWN |

Two things follow, and the second is easy to get wrong:

1. **`play_count` wins on 100% of clips-bearing items.** The ordering is doing real work and is currently sufficient.
2. **`view_count` is NOT globally a decoy — on the mixed `/top` hashtag surface it is the legitimate carrier for feed items** (7 real values that nothing else supplies). It must not be "cleaned up" out of the chain. The `user_medias` row resolving to NONE across the board is also correct behaviour, not a bug: those are feed videos, which structurally have no play count, and the account is flagged views-unknown rather than cut.

## PART 3 — the loaded gun: nothing downstream distinguishes a decoy `0`

The resolution chain is safe. Every consumer of its output is not. `0` is admitted as a genuine measurement at each of these points:

| location | code | effect of a `0` |
| --- | --- | --- |
| `ig_discovery.py:119-123` | `_g` returns first `v not in (None, "", [], {})` | `0` is **not** in that tuple → `0` is returned as a real value |
| `filters_free.py:161-163` | `v = _coerce_int(...)`; `if v is not None: samples.append(v)` | `0` admitted as a view sample |
| `filters_free.py:224` | `avg_views_sampled = sum(samples)/len(samples)` | becomes `0`, **not `None`** |
| `filters_free.py:274-278` | `avg_views_ok` | the `MISSING_KEEP` branch tests `avg is None` → a `0` **skips the protection** and returns "known-low → cut" |
| `main.py:1734` | `isinstance(_av,(int,float)) and _av < _ig_floor` | drops the lead as `known-low avg views 0` |
| `quality_gate.py:1311` | `isinstance(p.get("views"),(int,float))` | `0` enters the mean and the median |
| `quality_gate.py:2288-2298` | `_dmed` below `_median_floor` | reads as a KNOWN-below median → sink, or **cut** where `below_reach_floor="cut"` |

The comment at `quality_gate.py:2295-2296` states that cutting on a below-floor median is legitimate because "a KNOWN-below median IS evidence, so it never violates unknown-never-cuts". A decoy `0` violates that principle precisely while appearing to satisfy it: the value looks known, so every unknown-protection in the codebase is bypassed by construction.

**Trigger condition:** any single item where `play_count` is absent while `view_count` is present-and-zero. That is not hypothetical — it is the exact shape of `/v1/hashtag/medias/clips/chunk`, the surface currently under evaluation as the hashtag-discovery replacement (BL-674 probe): `view_count = 0` on 30 of 30 items, on both tags sampled. Today `play_count` is also present on 30/30 so the decoy never wins. The gap between "safe" and "silently cutting real editors" is one field-map reorder, or one upstream change that drops `play_count` from a single item.

This is the same class as the dead-knob failures: a field that exists, resolves to a value the code accepts, and moves a filter without ever raising.

## PART 4 — one dormant shape bug, same class, fails the other way

`discovery.py:192` accepts both envelope shapes:

```python
items = resp.get("itemList") or resp.get("aweme_list") or []
```

and hands the items to `normalize_item`, which parses **only** the camelCase web shape — `author.uniqueId` at `discovery.py:128`, `stats.playCount` at `discovery.py:137`. An `aweme_list` item carries `author.unique_id` and `statistics.play_count` instead. So `normalize_item` finds no handle and returns `None` at `discovery.py:130`, every post is skipped, `posts` comes back `[]`, and the caller reads deep **UNKNOWN**. No exception, no warning, no log line — it fails **open**, yielding no deep signal where real view data was available.

`tikhub_normalize.py:7-8` documents this exact incompatibility in its own module docstring, which is what makes the `or resp.get("aweme_list")` branch dead on arrival rather than merely untested.

**Currently dormant**, for two independent reasons: `tt_deep_check` defaults to `False` (`control.py:393`, annotated "TikTok user-videos endpoint dead -> off"), and the TikHub deep-check path is a different, correct implementation — `main.py:2908` routes through `tikhub_normalize.deep_posts`, which reads `statistics.play_count` properly. The bug is reachable only by enabling the LamaTok deep-check against an `aweme_list`-shaped response.

## PART 5 — what was deliberately left alone

Nothing was fixed. This was an audit and the scope was explicitly read-only. In particular:

* **The field-map ordering was not changed.** It is correct, and reordering it is how this bug goes live.
* **`view_count` was not removed from the chain.** It is the only view carrier for Instagram feed items on the mixed `/top` surface (7 of 28 items) and removing it would lose real data.
* **No `0`-vs-`None` guard was added.** The right fix is a design decision with blast radius across five call sites and both platforms — whether a resolved `0` should be coerced to UNKNOWN at the normalizer, or rejected per-field at each consumer — and it belongs in its own round with the owner's call on which semantics to adopt.
* **The dormant `aweme_list` branch was not touched.** It is unreachable at current config.
