Three findings, and two of them contradict the brief I was given.

1. **All five named suites are green**, and item 1 was already fixed by INFRA-023 before I
   arrived. This round is verification, not repair.
2. **The reds are not standing — they churn.** Two full working-tree runs 45 minutes apart
   produced **5 reds and 2 reds with ZERO OVERLAP**. Six of the seven were transient.
3. **A clean extract is 22 of 175 red — four times worse than the working tree**, which
   inverts the brief's premise that a clone has been greener. **A clone cannot run this
   suite at all**, and the reason is not the code.

## 1. The leaked fixture: already fixed, and the suite still flaps for a DIFFERENT reason

`tests/bl932_probe_67vrvaav.py` is **not on disk**, and the assertion is **already scoped**.
INFRA-023 (`9e9cd31`) did both:

```python
tmp = tempfile.mkdtemp(prefix="bl932_plant_")
self.addCleanup(shutil.rmtree, tmp, ignore_errors=True)
path = os.path.join(tmp, "bl932_probe_planted.py")
...
bad = _unparseable(tmp)                    # <- the temp dir, not the live tests/
```

The plant now lives where nothing else can write, and both assertions read `_unparseable(tmp)`
rather than sweeping `tests/`. Concurrent runs can no longer redden each other and a killed
run orphans nothing. **Nothing to fix and nothing to delete.**

**But the suite went red once during this round anyway, and the cause is different.** It
scans every `.py` in the tree, so a round mid-save on any file makes it fail — which is
what its own sibling test records: *"tools/claim.py raised SyntaxError mid-save twice in one
session."* INFRA-023 fixed the suite's **own litter**; what remains is the suite **reading a
tree that seventeen rounds are writing**. Those are two problems and only the first was ever
this suite's fault. It passed on every re-run.

### A clone cannot run this suite

The extract is `git archive HEAD` of **both** repos — parent `f97239e`, memebot `7a7cadc`,
885 + 48 Python files. It is what anybody else gets, and it is **22 of 175 red**.

The cause is not the code. Sampled by hand:

```
test_config_contract   FileNotFoundError: config.json
test_clip_wiring       FileNotFoundError: config.json
test_secret_scanner    FileNotFoundError: config.json
test_funnel            OK        <- passes in the extract, red in the run
test_filelock          OK        <- passes in the extract, red earlier in the tree
```

`config.json`, `master_leads.csv`, `spend.json`, `clip_library/` and `output/` are all
gitignored — correctly, they hold credentials and lead data — so a fresh clone has none of
them and every suite that needs one dies on `FileNotFoundError` rather than skipping loudly.

**This inverts the premise I was given.** A clone is not greener; it is four times redder,
and it always would have been. The working tree's greenness comes from data that is not in
the repository.

That is a real gap and it is nobody's round: there is no documented bootstrap that gets a
clone to a runnable state, and the suites that need private data do not say so — they crash.
`docs/TESTING.md` rule 6 says skip loudly, never silently; **crashing is neither.**

### What I got wrong

I ran the first extract with `tail -14`, which **truncated the headline count** — the
failure list was longer than the tail, so I had nine suite names and no total. I had to re-run
the whole extract to recover the number that is the point of the exercise. The second run
redirected to a file.

The two working-tree runs and the first extract run **overlapped on CPU**. I started the
extract while run 1 was still going because sequential execution of three ~40-minute runs was
not going to finish. Contention affects timing, and timing affects timing-sensitive suites, so
the *transient* counts above are if anything overstated — which cuts in the safe direction for
the conclusion, but it is a caveat on the numbers rather than a footnote.
