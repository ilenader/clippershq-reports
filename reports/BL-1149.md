## 2. Where it actually died — and it is two separate faults

### Fault A — the layer your symptom came from: **the browser never reached the server**

```js
}).catch(function () {                       // <- no argument. The error is discarded.
  msg.textContent = 'request failed';
});
```

`fetch().catch()` fires when the request **never completed** — a dead server, a wrong port, a
closed window. It is a *transport* failure and it printed the same words as every other
problem. The OFFLINE pill was the **same fact rendered twice**: `get('/api/health')` swallows
every failure and returns null, and the pill turned that null into one word.

So "Request failed" + OFFLINE together were never evidence about Spotify. They were one
sentence: *this tab is pointed at a port nothing is answering on*. There was a stale server
from an earlier session listening on **8897** while the launcher picks **8787** — ports move
when one is busy, and an old tab keeps asking the dead one.

### Fault B — the one that would have bitten you next: **queued ≠ alive**

```python
proc = subprocess.Popen(argv, stdout=DEVNULL, stderr=DEVNULL)   # every word discarded
return {"status": "queued", "pid": proc.pid}                    # never asks if it lived
```

And the chain that made it fatal — **three of the four links are mine, from BL-1147**:

1. The import is `spotify_scraper`; the **distribution is `spotifyscraper`** — no hyphen, no
   underscore. BL-1147's lookup tried `spotify-scraper`, got nothing, concluded "not
   installed", and **wrote in a report that the Spotify funnel could not run**. It was
   installed the whole time.
2. So `requirements.txt` never named it.
3. `START_DASHBOARD.bat` builds `.venv` from `requirements.txt` → the venv lacked it.
4. `/api/start` spawns `sys.executable`, which under that launcher **is** the venv.

Result: every Spotify run started from the page died on `ModuleNotFoundError`, and `DEVNULL`
meant nobody could ever see it. The funnel's own log said *"Details in logs/run.log"* — and
`logs/run.log` had nothing from that run at all. The cause was written **nowhere**.

**Fixed at each link:** the lookup now tries every separator spelling, `spotifyscraper==3.9.2`
is pinned, the venv has it (installed through `SAFE_PIP`/pipguard, which dry-ran it clean),
and `/api/start` now captures output, watches the process for 6 s, and refuses to call a
corpse "queued".

## 4. A sixth cap defect, found by running

The end-to-end run was `clip_walk`, cap **$0.0200**:

```
BEFORE lifetime $12.1051      AFTER $12.1273      delta $0.0222
SPEND <= CAP : *** NO ***     11% over, about 3.7 calls
```

`clip_runner.py:879` read:

```python
if max_usd and spent() >= max_usd:      # notices only AFTER the money is gone
```

That is the documented *cap-checked-after-the-fact* family. It now reserves the next pass's
worst case before taking it, exactly as `clip_pipeline._run_batch_inner` does. Re-measured:

```
cap $0.0200   spend $0.0210   overshoot $0.0022 -> $0.0010   (11% -> 5%)
```

**Still over, and I am not claiming otherwise.** The residual cause is measured and named:
`spent()` reads the metered ledger, and `spend_ledger.DEFAULT_FLUSH_EVERY = 25` — so between
flushes the number it checks against can lag reality by up to **25 × $0.0006 = $0.015**. The
cap is now reserved correctly against a baseline that is itself stale. Closing that means
reading `IgClient.unflushed_requests` inside the check, across `spend_ledger` and `ig_client`
— files this round does not hold.

### Reconciliation, and its honest limit

```
ledger delta        $0.0210     naive row-sum $0.0210   FOLDED BY RECORD $0.0210
run record          spend_usd 0.021, status completed
```

Ledger, folded ledger and the run's own record agree: **35 calls**. What **cannot** be
reconciled is the *price*: the vendor's receipt header (`x-hiker-info`) returns a **request
count**, not an invoice. `$0.0006` is a config constant, and the brief is right that such a
constant has been wrong by 2.7× before. **The count is verified; the unit price is not
verifiable from anything the vendor returns.**

Three states, not two: `live`, `no answer` (transport), `bad reply` (something answered, but

**And a pre-flight**, so the class cannot recur silently: before spawning anything,
`/api/start` asks the target interpreter whether it can import what the funnels need. On your
old 3.13 it names all seven; on the venv it returns `[]`. `None` means *could not check* and
is never treated as *nothing missing*.
