### Refresh is now a STEP, not a one-off

A snapshot cannot protect a file rebuilt daily. Three things now exist so the table's
staleness is impossible to not notice:

- **`python tools/refresh_mx.py`** — documented as **step 0** in `docs/SENDING.md`, before
  the rebuild. ~5 s, free, no key. `--dry-run` and `--from-master` included.
- **`send_suppress.table_health()`** — coverage %, age in days, and any verdict the reader
  does not understand.
- **`all_bot_ready.py` prints it on every build.** Silence from a suppression layer is
  indistinguishable from approval; this makes the silence audible.

Each of the three failure modes was **shown to fire**, because a guard nobody has seen fire
is not a guard:

```
partial coverage -> "MX TABLE COVERS 99.6% of this file's domains (561/563)."
stale table      -> "MX TABLE IS 30 DAYS OLD (limit 7). ... refresh takes ~3s"
unknown verdict  -> "'SOME-FUTURE-VERDICT' on 1 domain(s) - treated as UNKNOWN, so NEVER
                     suppressed. A CERTAIN bounce can ship this way."
```

## 2. The dnspython gap: removed, not installed

`scratch/bl763_dns.py` — the script that built the original table — did this:

```python
try:    import dns.resolver ; HAVE_DNS = True
except: HAVE_DNS = False ; print("(dnspython not available -- falling back ...)")
```

and then, with `HAVE_DNS` false, answered **"does the name resolve?"** while printing
verdicts in the vocabulary of **"does it have a mail route?"** — `ok - has MX`.

**dnspython is not installed on this machine and is not in `requirements.txt`.** So that was
not a rare path, it was *the* path, guarded by one notice line above a table of verdicts.

**I did not install it.** An optional import that changes what a verdict *means* is a hazard
whether or not it happens to be present: installing it fixes today and leaves the shape.
Instead `clippershq/mx_probe.py` speaks DNS directly over UDP — question encoding, answer
parsing, compression pointers, TCP fallback on truncation — in stdlib only. There is now no
dependency to be missing.

`scratch/bl763_dns.py` **refuses to run** rather than degrading:

```
REFUSING TO RUN: clippershq/mx_probe.py is unavailable.
  This script will NOT fall back to an A-record check. That fallback answered
  'does the name resolve?' while printing 'ok - has MX', and its output was
  written into the shipped suppress_mx.json.
  Use: python tools/refresh_mx.py
```

Verified: no live `dns.resolver` or `HAVE_DNS` reference survives anywhere — the only
remaining mentions are the comment explaining the removal.

## 3. What I got wrong: I shipped the same failure shape, mid-round

This is the finding worth reading.

The refreshed table introduced a fourth verdict, `null-MX` (RFC 7505 — a domain that has
declared in DNS that it accepts no mail). I wrote it into `suppress_mx.json` **before**
teaching `send_suppress` the value. Its `mx_status` matched three literals and returned
`"unknown"` for anything else:

```
cea.agency   table=null-MX  mx_status=unknown  excluded=False
mskd.com     table=null-MX  mx_status=unknown  excluded=False
```

**Two certain bounces, newly probed, correctly written down, and silently shipped** — by the
round whose entire purpose was to stop exactly that. The "absent means UNKNOWN, never dead"
rule is right, and it made an *unrecognised* value indistinguishable from an *absent* one.

Caught by checking the output rather than trusting the write. Three things came out of it:

1. `_MX_NULL` handled, mapping to the same treatment as `DEAD`.
2. **`send_suppress.KNOWN_TABLE_VALUES` + `unknown_table_values()`** — the reader can now
   *report* a verdict it does not understand instead of quietly ignoring it, and the build
   prints it.
3. **`test_every_table_value_is_one_send_suppress_understands`** — asserts every value
   `mx_probe` can write is one `send_suppress` knows. The next verdict cannot repeat this.

Both regression tests were **mutation-checked**: reverting the fix turns each red. A test
that passes with and without the fix protects nothing.

## 4. `bounced`, end to end

`bounced` was already a column, already in `_ALLOWED`, already counted by `outcome_stats`,
already reachable from the `[o]` menu — and empty on all 59,006 rows. Reading the source
suggested it worked. Driving it found two gaps.

**Gap 1 — no bulk path.** A bounce report is a *list* of twenty addresses; the only recorder
was one-lead-at-a-time and interactive. `mark_sent_from_csv` existed for the send side and
had no counterpart. Added **`outcomes.mark_bounced_from_csv`** and **`read_bounce_keys`**,
which take a CSV *or a plain text file you pasted the bounce notices into* — angle brackets,
trailing punctuation and the `'-` spreadsheet guard all stripped.

**Gap 2 — a bounce without `date_sent` was invisible.** `_was_sent` required `date_sent` or
`sent_channel`, so a programmatically-recorded bounce was dropped from `sent`, and therefore
from `bounced` **and from the bounce_rate denominator**. The interactive menu happens to
avoid it (it only offers "it bounced" underneath "have you contacted them yet?"). The
programmatic path — stamping a bounce report, i.e. precisely the case the operator is in —
did not. **A bounce is proof of a send, and now counts as one.**

Contract kept identical to the send side: **unmatched and ambiguous come back as KEYS, not
counts**, and **ambiguous keys are refused, never guessed** — a shared agency inbox stands
for several artists, and marking the wrong one bounced would suppress a real person from
every future send. A new field, `not_marked_sent`, records the bounce *and* reports that the
send stamping is incomplete.

**Proven end to end on a COPY** (`scratch/bl964_bounce_proof.py`; real master read-only):

```
1 COPY master                          300 rows, 150 stamped as sent
2 CSV report -> 4 keys                 plain TEXT log -> 1 key
3 DRY RUN                              file byte-identical, matched=3 updated=0
                                       unmatched listed by ADDRESS, not counted
4 FOR REAL                             updated=3, 3 rows carry bounced=yes IN THE FILE
5 bounce on an unstamped row           recorded anyway AND reported as incomplete
6 outcome_stats                        sent=151 bounced=4 bounce_rate=2.6
7 re-run                               still 4 — idempotent
8 by-dimension                         tiktok sent=119 bounced=4 rate=3.4
ALL GREEN
```

The smallest manual step, now in `docs/SENDING.md` as step 9:

```python
res = mark_bounced_from_csv("bounces.csv", master_csv="master_leads.csv", dry_run=True)
print("\n".join(format_mark_report(res)))     # read it, THEN drop dry_run
```

The atomic write was **extracted into `_rewrite_master()`** and shared with
`mark_sent_from_csv` rather than copied — a second hand-rolled backup+fsync+replace block is
how "one answer, three copies" starts. The extraction also picked up the retrying
`os.replace` that `docs/PRECONDITIONS.md` asks for and the original did not have.

## 5. `noMX-Aonly`: decided by measurement — exclusion KEPT, the claim corrected

RFC 5321 §5.1 makes an A record an implicit MX, so the strict reading says excluding these
is over-suppression. Both readings are arguable from the RFC. Neither is arguable from a
live server, so I opened port 25 on the A record of all five
(`scratch/bl964_implicit_mx.py`):

```
essosa.com     NO_MX_A_ONLY   reachable=False   TimeoutError
proxy.com      NO_MX_A_ONLY   reachable=False   TimeoutError
reydempto.tv   NO_MX_A_ONLY   reachable=False   TimeoutError
undrcntrl.com  NO_MX_A_ONLY   reachable=False   TimeoutError
vico.gg        NO_MX_A_ONLY   reachable=False   TimeoutError

0/5 reachable.  0/5 accepted a recipient.
```

From the same machine, in the same session, 551 `MX_OK` domains completed SMTP handshakes.
In practice these A records are web servers.

**DECISION: keep the exclusion, change the justification.** It is no longer "this cannot be
delivered" (unproven) but **"no reachable mail server was found, measured"**. A timeout is
weaker evidence than NXDOMAIN — it could be a firewall — so the docstring now states the
asymmetry plainly: 17 such rows across all of master, against a bounce cost that is
unrecoverable. `NO_MX_A_ONLY` is **not** in `mx_probe.CERTAIN_BOUNCE`, and a test asserts it
never becomes so, so the *policy* and the *certainty* can no longer be silently merged.

## 6. Yahoo: SHIP them

20 rows (0.67% of the file: 18 `yahoo.com`, 1 `yahoo.it`, 1 `yahoo.de`), split 10 clipper /
10 client. **All 20 resolve `ok-MX`.**

The `550 5.7.25 Forward-confirmed reverse DNS failed` that BL-962 hit is Yahoo refusing
*this machine* — a residential IP with no rDNS — at `MAIL FROM`, before any recipient is
named. It is not a fact about the addresses, and no amount of probing from here will change
it: rDNS is a property of the connecting IP.

**They ship.** Under the never-cut-on-unknown rule an unverifiable address is UNKNOWN, and
unknown is never a cut. Even if all 20 bounced that is 0.67%, below the 2% throttle line on
its own. The one thing worth doing is **not putting them in the day-1 batch of 20** — a
verified-clean opening batch is cheap, and they can go out in week 2 once reputation exists.
A real sender with rDNS and SPF can verify them properly at that point.

## 7. The measurement lesson, carried

BL-962's naive SMTP acceptance was **97.2% and meaningless**: catch-all domains accept every
recipient, so an accept there proves nothing. Only the non-catch-all, clean-answer subset is
informative — **44.1% of domains are catch-all but only 9.5% of rows**, because 243 catch-all
domains average 1.2 rows each while the mass sits on four providers that all discriminate.

That distinction is now **enforced in code, not just remembered**:
`mx_probe.CERTAIN_BOUNCE` excludes `NO_MX_A_ONLY`; `send_suppress` distinguishes *absent*
(unknown) from *unrecognised* (unknown **and reportable**); and `table_health` reports
coverage so a layer with no opinion cannot be read as a layer that approved.
