### Then what is 1001?

### The proof that it is not a target, and it is free

The counter has **run past it**. Live stage: `[1044/1001]`. Highest index in the log: **1049**.

### Where 1001 comes from, named, as the brief requires

### Is this the same family as the five cap defects? I checked. No.

`run.py:140-152` `_apply` handles both shapes correctly:

```python
if target is not None and spec["target_key"]:
    block, key = spec["target_key"]
```

Spotify's `target_key` is `("spotify_finder", "run_target")` — nested — and `_apply` writes
the nested key. There is **no nested-vs-top-level split here.** The cap family does not
recur.

One genuine trap worth naming, because it is how this looks like the cap family and isn't:
`spotify_finder.run(cap=…)` — the kwarg named **`cap` is the lead-count target**, while the
dollar cap is `max_run_usd`, one call away. Two meanings of "cap" in one signature.

Also verified: `config.json` on disk still reads `spotify_finder.run_target = 700` while the
run carries 2000. That is **correct** — `_apply` deep-copies (`json.loads(json.dumps(config))`)
and never writes back, so a per-run target leaves no residue. Worth knowing only because
anything that re-reads `config.json` mid-run sees 700.

### The finding the brief asked for

**47.6% of this seed pool was already known.** Real, and worth telling him — but "nearly
every line" overstates it. The larger loss is the **listener band: 28.4% too small + 6.5% too

**2.6%** became a new lead with an email. More Spotify runs against these seeds are not
worthless, but they are a ~2.6% yield, and the single biggest lever is the band, not the seeds.

### The part underneath, which is worse and is not what the brief assumed

`run.py:419`, inside the heartbeat:

```python
leads=_leads_now(master_csv) - leads0,
```

`_leads_now` counts **rows in the master CSV**. The master append happens only after
`run_fn` returns (`control.py:2470+` → `spotify_finder.py:1255+`). Nothing is appended while
a run is in flight.

**So `leads` is structurally 0 for the entire duration of every run, always.** It is not
"0 because they were all already known" — the 27 new emails found above are not in it either.
A run that found 2,000 leads would display `leads 0` until the second it finished.

He reads it as broken because it *is* broken. Showing a breakdown beside it is right, but
the counter itself is measuring the wrong thing at a time when that thing cannot have moved.

**Everything needed is already in memory and already correct.** `spotify_finder.py:754-772`
builds a stats dict carrying `qualified`, `new`, `existing`, `too_big_skipped`,
`filtered_out`, `filter_reasons`, `country_filtered`, `country_kept`, `country_unknown`.
The funnel already counts every category the brief asks to display. Nothing computes them
into the status file. This is a plumbing gap, not a measurement gap — which is why it is
cheap, and why I am sorry not to be able to close it (see §4).

## 3. THE PANEL IS STALE BECAUSE THE WRITER STOPPED. Polling was never the problem.

### The writer is frozen — measured on file mtimes, PowerShell, nothing running by me

Six samples, 5s apart, of `scratch\runs\spotify-resume-20260806-145616.json`:

```
...

```

A **2-second** heartbeat had not written for **five minutes**, and `ticks` and `elapsed_s`
were frozen with it. The log file froze in the same instant (age 258s at first read).

**This is the answer to "where do the minutes accrue".** It is the first of the brief's four
candidates — heartbeat not firing. The data the panel shows really is minutes old. No change
to polling, buffering or re-rendering can improve a number that is not being written.

### Why it stopped

The log's last lines, then silence:

```
15:22:33 enrich_links: www.whatsapp.com returned 252459 chars — parsing the first 250000
15:22:40 enrich_links: linktr.ee   returned 253793 chars — parsing the first 250000
15:22:40 enrich_links: open.spotify.com returned 251088 chars — parsing the first 250000
         (this one took a while — country lookup 174s)
```

Meanwhile pid 9228 burns **~100% of one core** (5.03 CPU-seconds per 5 wall-seconds) across
20 threads, with the system at only 34.2% of 12 cores — so the box is *not* saturated; one
process is spinning.

The run is stuck on quarter-megabyte pages and 174-second country lookups. The per-artist
watchdog abandons the worker but **cannot kill the thread** — `spotify_finder.py:727` and
`:922` say so in terms ("its abandoned daemon's spend is still metered via the http
counter"). Abandoned CPU-bound daemons accumulate and starve the pure-Python heartbeat thread.

### The latent hazard next to it, which did *not* fire here but will

`run_status.py:267-277`: a failed `os.replace` is caught and logged **at most once per run**
via `_save_warned`, then silent forever — the file freezes and nothing ever complains again.
And `run.py:431-436` wraps every `tick()` in `except Exception: pass`.

I searched the live log for that warning: **not present**. So the write is not failing here —
the thread simply is not being scheduled. But a status writer that can go permanently silent
after one line is the same shape as the defects this project keeps re-finding, and it is one
OneDrive lock away from firing.

### /api/now's cost — the brief's attribution is wrong by ~700x, and this matters

The brief says to fix `/api/now`'s ~110 file opens first, or harder polling makes it worse.
The instruction to fix cost before polling is right. **The cost is not in the files.**

| measurement | result |
|---|---|
| read all **113** JSON files in `scratch\runs` | **21.3 ms total (0.19 ms/file)**; warm 29.9 ms |
| `api_now()` called **in-process** (3 calls) | **49 / 41 / 65 ms** |
| `GET /api/now` over **HTTP** (3 calls) | **7,465 / 14,523 / 14,950 ms** |
| `GET /api/health` over HTTP, 136-byte reply | **2,136 / 2,877 / 3,211 ms** |
| OneDrive sync client | **not running** |

The same work costs 45 ms in-process and up to 15 s over the socket. Removing the file reads
entirely would buy 21 ms of a 14,000 ms problem.

Two things establish where it does live:

1. **`/api/health` — a 136-byte constant — takes 2.1 s.** It opens no run files. That is
   pure queueing, and it also corrects the brief's baseline: health is not 25 ms right now.
2. **Six established TCP connections to :8787.** Six pollers, each asking every 5 s for a
   response the server cannot produce in 5 s. The queue cannot drain.

`dashboard/server.py:333-339` documents this exact failure already, from `tasklist`:
*"/api/now took 40.2s … against 0.01s for every other endpoint. The page fetches all five
with `Promise.all`, so the WHOLE dashboard waited on it."* Same shape, new cause. The fix
that landed then — make the endpoint cheap — is already done; what is missing is that
**nothing bounds concurrent pollers**, so an endpoint that ever exceeds the poll interval
collapses.
