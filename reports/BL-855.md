## 1. The ranking — SHIPPED

`clippershq/clip_pipeline.py::rank_score`, before and after:

```python
# BEFORE — engagement_per_follower was the PRIMARY sort key, above play_count
return (0 if old else 1, epf if epf is not None else 0.0, pc), why

# AFTER
score = math.log10(pc) if pc > 0 else 0.0
if d is not None and d < SHORT_CLIP_S:            # 10.0
    score += SHORT_CLIP_BONUS                     # 0.15, PROVISIONAL

```

**What that changes in practice.** The old key meant a 30,000-view clip with a good ratio outranked a 9,000,000-view one. The test suite *asserted* that — `test_bonus_outranks_raw_views_when_present`. That assertion is now inverted and named `test_views_outrank_engagement_INVERTED_BY_BL850`, with the reason in the body.

**Removed, each with its measurement in a comment at the removal site:**

| term | why removed |
|---|---|
| `engagement_per_follower` | r = +0.593 only because its numerator contains views. The per-view ratios are flat: `saves_per_view` r = −0.001 (p = 0.99), `reshares_per_view` r = +0.069 (p = 0.27). |
| age demotion (`AGE_DEMOTE_DAYS`) | r = −0.008, q = 0.987 — the flattest of 40. The constant survives, reporting-only; age is still printed in `score_why`, never scored. |
| `like/comment/save/reshare_count`, `follower_count`, `valence_text`, `audio_type` | added to `_RANK_FORBIDDEN` |

**The provisional term is labelled where someone will actually read it** — at the constant, not only in a report:

```python
# PROVISIONAL, and the only clip feature in the score. BL-850: clips under 10 seconds sit
# +0.184 within-account rank percentile above their own account's other clips, q = 0.037
# after Benjamini-Hochberg over 40 hypotheses ... It rests on n = 24 clips across 10
# accounts ... Six of those accounts contribute exactly ONE short clip.
# Sized DELIBERATELY BELOW the measured effect (0.15 against 0.184 of a rank percentile, on
# a log10 scale where one decile of the library is ~0.35). RE-TEST BEFORE TRUSTING IT.
SHORT_CLIP_S = 10.0
SHORT_CLIP_BONUS = 0.15
```

**The second data-quality gate** is new: a cover frame that is one flat field of colour (`strip_frac ≥ 0.90 and bar_mid_frac ≥ 0.90`) is now gated out. **Stated plainly because it is a real cost:** BL-850 measured those 24 clips at mean within-account rank **0.555 — slightly above their accounts' median.** They are not weak. The gate is about downstream frame-readability only, it is named `_BLANK_STRIP_MIN`, and it is one line to delete.

**Verified live:**

```

epf forbidden      = True      follower forbidden = True
score(1M views, 50s) = 6.0000      score(1M views, 8s) = 6.1500
```

**The brief's premise needs one correction before the numbers.** "moviefacts was 67% of a recent round's yield while BL-732's old ranking had it absent from the top three." The 67% is true of BL-828 and **means nothing as a ranking**: that run stopped after 8 of 24 tags on a *page target*, tags are walked in bank order, and moviefacts sits near the front. BL-842 walked all 24 and moviefacts came out at **20/158 = 13%**. It is still the best tag. It is not two thirds of the funnel, and no tag ranking taken from a target-truncated run measures anything but list position. That is BL-842's finding, not this round's.

### The projection was right about money and wrong about time

**Cost: $0.0654 against a $0.50 budget** — projection $0.14 for 111 pages, actual $0.0654 for 16, i.e. **$0.0041 per confirmed page**, ~3× the $0.00126 the projection assumed. The depth lever costs more per page than a shallow pass because pages 3–6 surface more foreign-language and sub-threshold accounts, each of which is paid for at the gate and then rejected. **Time: badly underestimated.** I modelled 4.2 s per candidate from thumbnail fetches. The account gate runs EasyOCR over 12 thumbnails per candidate at ~1.34 s each — **~16 s of local CPU per candidate**, so the real figure is nearer 20 s. Run 1 took ~55 minutes to spend 1.5 cents.

> **This funnel is TIME-bound, not dollar-bound.** A $0.25 cap is not a meaningful constraint on it; wall-clock is. At the measured $0.0041 per page and ~2 hours per four tags, the remaining ~85 pages to 300 cost roughly **$0.35 and 10–12 hours**, and the useful knob is concurrency or `use_ocr`, not the budget.

**NOT DONE:** the pool is short of 300. Getting there is now a known, cheap, slow operation — the finding was that the old configuration could not have got there at any price.

**One caveat on the per-tag table this projection rests on.** It comes from BL-842's full-bank sweep. **BL-873 is in flight specifically to "correct + publish the tag ranking"** after BL-858 found faults in the repost gate. If it lands, the tag *ordering* used to pick these four tags may be superseded — the depth finding does not depend on it, but the choice of which tags to walk next does.

## 4. The `follower_count` artefact — SHIPPED into `clip_walk.py`

Recorded in the module whose traversal *causes* it, not in the module that was fooled by it, with the raw rows that make it obvious:

```
richardthedis6067    followers   play_count
  6198                           1,929,194   <- page 1, ranked descending
  ... (7 rows at 6198)
  6247                             567,624   <- page 2, follower count re-read
  ... (5 rows at 6247)
```

`follower_count` is re-read from every page response; the pages are ordered by view count; so every page boundary is also a view-rank boundary and the field steps down the ranking in lockstep. r = −0.566, p < 0.0001, and **circular**. Within an account it varies by a median of 1.1% across 2–3 distinct values, while on the same rows `posted_at` gives r = −0.056, p = 0.325.

It is also in `_RANK_FORBIDDEN`, so the AST guard fails the suite if anything reads it again. The note says explicitly that it **remains correct at account level** — the artefact is in its *within-account variation*, not the field.

## 7. UNASKED AND URGENT: a test suite was deleting live config keys

`tests/test_dashboard.py::test_put_writes_a_block_scoped_knob_into_its_block` PUTs to the live `/api/settings`, which writes the **real `config.json`**, restoring the old value in a `finally`. It hard-coded `twitch_finder.min_viewers` and restored with `int(before)`.

Diffed against this round's own timestamped backup:

```
twitch_finder.min_viewers    backup = 20     live = MISSING
```

**The failure is self-perpetuating.** When the key is absent, `before` is None, `int(None)` raises in the body — and raises *again* in the `finally`, so the restore never runs. The first crash removes the key; the missing key guarantees the next crash.

- **Restored** to 20 via `main.save_config` (own timestamped backup, validate, atomic replace).
- **Fixed** the test: pick a knob that is actually present and integer-valued, skip if none, and assert the live config is left as found.
- **Not reverted:** `spotify_finder.run_target` also differs from the backup (700 → 900). That is a plausible deliberate change by one of the rounds in flight and is not mine to undo. Reverting everything that moved would clobber other people's work, which is why the diff was inspected key by key.

## Post-publication corrections

This report was published, and then the background task that ran the depth discovery reported as **killed**. [A killed run is not a failed run](https://raw.githubusercontent.com/ilenader/clippershq-reports/main/reports/BL-822.md) — verifying it against `spend.json` and the data found that **two published figures were wrong**, in opposite directions, and both for the same reason.

**1. Spend: $0.1308 → $0.0654. The published figure was more than double the truth.**

I computed it as `spend.json.total_spent_usd` minus its value at round start. That delta is not this round's spend — **it is every round's spend**, and thirteen were in flight. The ledger's own labelled entries since 16:12:

```
16:23  CLIP_LIBRARY            $0.0150     18:13  BL858_AUDIT            $0.0180
16:26  memebot                 $0.0006     18:17  REPOST_FINDER          $0.0048  <- mine
16:41  memebot                 $0.0006     18:32  REPOST_FINDER          $0.0150  <- mine
16:56  REPOST_FINDER           $0.0150  <- mine    18:52  BL872_VISION    $0.0306
17:28  BL858_AUDIT             $0.0012     19:05  BL873_VERIFY           $0.0108
17:35  BL864_PROBE             $0.0150     19:24  REPOST_FINDER          $0.0006  <- mine
17:35  BL864_VISION            $0.0048     19:33  REPOST_FINDER          $0.0150  <- mine
18:09  REPOST_FINDER           $0.0150  <- mine    19:34  BL876_VISION    $0.1014
```

Total since 16:12: **$1.0842**. `REPOST_FINDER` only: **$0.0654**. The rest is other rounds. This is BL-818's moving-denominator failure wearing a different hat: I used `read_snapshot` to protect the *library* measurements and then read a shared ledger the naive way. **A ledger total is not a round's spend unless the round is alone in the tree.**

**2. Pages: +13 → +16, and the pool total is not the right measure at all.**

I counted `MEME PAGE` lines while the run was still working, then read the pool total as final. Two errors: the run was alive and went on to confirm 16, and **BL-873 was running paid repost discovery on the same funnel at the same time**, so the pool delta of +26 is a *shared* number.

The fix is to attribute by identity rather than by arithmetic: 16 handles printed by this run, 16 found in master. That figure is immune to whatever else is writing.

**3. The process check that caused it was broken and returned a confident wrong answer.** I checked "is the run finished?" with a PowerShell one-liner whose quoting was malformed; it errored and printed `NONE`, which read as *finished*. It was not. The reliable check was file growth — my run's output frozen at 5,078 bytes while `spend.json` kept moving, which is what revealed a *different* round was spending. A liveness probe that cannot fail loudly is worse than no probe.

**Nothing else in this report changes.** Every code claim, the dedup result, the declared-panel measurement, the artefact and the below-floor costing were measured against a frozen snapshot or the files themselves, not against shared totals. The corrected spend is still 13% of budget.
