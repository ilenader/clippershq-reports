## BROKEN 2 — dead-run identity degrades to pid-only, silently

Every run card reports `has_pid_created_at: false, has_boot_epoch: false, source: ["marker"]`.
But the marker file on disk **does carry both**:

```
scratch/runs/spotify-bl1166-20260806-181508.json
   pid              13576
   pid_created_at   1786032908.815363
   boot_epoch       1785917639.2152162
```

**The exact defect.** `dashboard/server.py:407-422` builds the marker row and copies 15 keys
— `funnel, status, progress, pages, target, leads, spend, elapsed, ts, epoch, pid, calls,
appended_incrementally, halted, out_path` — and **not** `pid_created_at` / `boot_epoch`.
`_liveness_evidence()` then reads `row.get("pid_created_at")` at line 702 and gets `None`.
The headless path at line 478 carries them; the marker path does not. That asymmetry is the
whole bug.

**Severity, measured** — `proc_identity.describe()` on a live pid using a dead run's start time:

```
WITHOUT identity (what the marker card passes today):
   verdict=None   "pid 10652 is in use by a Python but nothing recorded WHICH process
                   it was, so this cannot be confirmed either way"

WITH pid_created_at + boot_epoch (fields the marker file ALREADY HAS):
   verdict=False  "pid 10652 has exited -- that number has since been reused by another
                   python, which is why it still looks alive"
```

The fix turns an unresolvable "cannot confirm" into a definitive "this is a recycled pid".
`server.py`'s own comment calls the first state *"THE WEAK CASE, NAMED… what his three ghost
cards were standing on."* **This is the 54-hour Clipboard-Service bug, still live, with the
data to defeat it sitting unread in the file.** It is latent only because every pid currently
on screen has genuinely exited.

**Exact change** — `dashboard/server.py`, in the marker row dict ending line 422:

```python
             "out_path": rec.get("out_path"),
+            "pid_created_at": rec.get("pid_created_at"),
+            "boot_epoch": rec.get("boot_epoch"),
         }
```

`dashboard/server.py` is **held by BL-1159**. Handed over, not applied.

**What does work:** finished runs say finished. `repost_finder` and `spotify_finder` read
`completed`; `twitch_finder`, `youtube_finder`, `clip_library` read `died`; none read
"running". Each carries a plain-language basis — *"the operating system says this process is
gone — pid 18568 has exited"*. That is a real improvement over this morning, when two of
these markers still said `running`.

## THE HEADLINE — can he trust the numbers?

**Mostly yes, and the exceptions are specific.**

**Trust these.** Every counting panel I could hand-verify was right, and right in the hard
way — it counts *records*, not rows, in all four places I checked: Clips 2,761 from 9,741
rows; Video 35 from 55 files; the render ledger 801 from 1,429 lines with 455 finished; drop
marks 21 from 52 lines. The Money arithmetic is exact to four decimals. The accounts export's
double-entry closes to the unit. On the tenth rows-versus-records check, **the site passed.**

**Do not trust these three.**

1. **The send list.** It is four days old, holds none of today's leads, and the page shows no
   row count, no build date, and no stale flag — while the server has all three and has
   already computed `stale: True`. Until that lands, he cannot tell from the page whether the
   file he is told to send from is current. It is not.
2. **"Is this run alive?" on any marker card.** Identity has silently degraded to pid-only.
   Right now every pid on screen is genuinely dead so the answers are correct — but the
   mechanism that produced a 54-hour ghost card is intact and one recycled pid away.
3. **The freshness banner's silence.** It checks five files, not the code it runs, and its own
   guard is red. A silent banner is not evidence the server is current; check `started`
   against the tree.

The rest — the estimate, the refusals with their measured reasons, the required-field guards,
the zero-states, the drop-marking page, hot reload — works, and several of them work better
than they need to. The drop page's *"Somebody listened and confirmed it"* is the standard the
send list should be held to.

**One thing this round could not do:** certify that the 11 funnels start, count, tail, accrue,
stop and clear. The machinery was being rewritten underneath it by BL-1167 for the whole
session. That is the single largest hole and it needs a quiet tree.
