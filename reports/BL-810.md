### Labels that do not match behaviour

1. **`main.py [7] "See my leads & send lists"` — the worst offender.** It calls `show_status()`, which prints campaign totals and the last few runs. It does not show a send list, does not build one, and does not name one. A user reading that label reasonably expects the thing this system exists to produce.
2. **`main.py [r]` is a real funnel with no menu line.** It appears only in the error text `"pick 1-8 or R, or Q to quit."` — discoverable by typing something wrong.
3. **`[6] Find editors` contains a repost-page option** (`[d] CAPTION-FINGERPRINT repost pages`). Repost pages are not editors, and repost is separately reachable at `[r]`. Two doors, one room, different names.
4. **Money caps live in two places** — Control Panel `[5] Global settings — money caps` and `[f] Funnel filters — … + money caps`. Nothing says which wins.
5. **`[k] Build the clip library`** writes to `clip_library_dir` = `./clip_library`, which **does not exist** (BL-803). The label promises a library; the only live run landed in `scratch/`.

## 2. Is the cost always visible before spending?

**No path spends silently. Every paid funnel has a Proceed gate.** But the gates are not equal.

| path | itemised BEFORE-YOU-SPEND projection | Proceed prompt |
|---|---|---|
| Twitch, Spotify, Google Play, YouTube, email finder, repost | **yes** | yes |
| clip library | **yes** | yes |
| `_find_crawl`, `_find_editors_tiktok`, `_find_caption_repost` | **no itemised block** | **yes** |

The three crawl paths — which produced **54,521 of 58,325 leads**, the overwhelming majority of all spend — confirm before spending but do not print the itemised projection the client funnels do. They partly compensate with **inline prices in the submenu labels** (`~$1.20/1k`, `~$0.52-1.04/1k`), which is genuinely good UI and worth keeping.

**Verdict: no hole, one inconsistency.** The funnel you use most has the least detailed cost preview.

Non-spending paths (`[o]` outcomes, the bulk marker) correctly have no cost gate; the marker instead gates on a **dry run whose confirm defaults to NO**.

## 3. Is the output findable?

**No. This is the single clearest failure in the interface.**

A grep across `control.py` and `main.py` for `ALL_BOT_READY`, "safe to send" or "send from" returns **zero user-facing strings**. BL-786 established that `ALL_BOT_READY.csv` is the only file safe to send from — a strict superset of every other export, where using any second file is a pure double-send. **That conclusion exists only in a report.**

What the interface tells you after a run: `show_status()` prints qualified / candidates / tags used / calls / dollars. **No file path. No filename. No statement of which of the eight-plus CSVs in `output/` is the one to use.**

So the daily loop is: run a funnel → see a count → open `output/` → find ~50 CSVs including seven `EPICWAR_*` files from 4 July carrying 262 dead addresses (BL-786) → guess.

## 5. What would confuse you in a month

- **"See my leads & send lists"** — you will click it expecting a send list.
- **`[9] Find more editors like my best (Instagram)`** vs **`[6][a] Instagram — snowball off your best editors`** — the same crawl, two names, two menus.
- **`[f] Funnel filters` vs `[5] Global settings`** — both say "money caps".
- **`[d] CAPTION-FINGERPRINT repost pages`** — assumes you remember caption-fingerprinting is a distinct technique from `[r]`'s layout detection.
- **`[w] Save my work now — checkpoints any half-finished code`** — a developer action sitting in an operator's menu.
- **Units are mostly good.** `~$1.20/1k` states the denominator; `min_subscribers: 50000` is unambiguous. The gap is **rates without a base**: `deep_median_views` and `editor_pct` appear in output with no in-UI explanation of what they measure.

## 6. Error paths

**Input validation is genuinely good.** Every bad answer re-asks with a plain-language message and an example — `"! '{raw}' isn't a whole number. Try e.g. 1000."`, `"! Too high — must be at most {max}."` No stack traces reach the console (`_NoTracebackFormatter` strips them; the file log keeps them).

**What I could not confirm, and am not going to claim either way:** I sampled the `! `-prefixed messages and they are dominated by input validation. I did **not** trace an API failure, an exhausted YouTube quota, an empty 200, or a dead lock through to the console string a user would actually see. Prior rounds establish the machinery exists — partial runs are saved and metered on interrupt, `ApiShapeDriftError` fires loudly on a zero-result, YouTube `quotaExceeded` degrades to a partial — but **whether each message states "your leads were saved" and "you were charged $X" is unverified here.** That is the highest-value follow-up in this audit and it needs a live fault injection, not a grep.

## Limits

- **This is a static read of the dispatch tables and labels.** I walked the menus in source, not by running the panel interactively. A label rendered differently at runtime would not show here.
- **§6 is deliberately incomplete** and says so. I did not inject faults.
- **Cost-gate detection is keyword-based** (`estimate` / `Proceed` / `confirm_fn` / `_ask_yes_no` inside each function body). A gate implemented under another name would read as absent — which is exactly why I checked `_find_editors` by hand before reporting it, and found it was a router with inline prices rather than an ungated spender.
- **I did not re-verify BL-806's change.** I checked only whether a send-file builder is reachable from either menu today. It is not.
- **`output/` file count and the 262 dead addresses are carried from BL-786**, not re-measured.
