# BL-733 — OCR transcription accuracy, measured for the first time: production is throwing away half its accuracy on a `max_side=512` downscale

## THE EASY-CASE USABLE-MATCH RATE IS **36.4%** AS PRODUCTION IS CONFIGURED, AND **81.8%** IF YOU DELETE ONE ARGUMENT. `ocr_features.ocr_one()` shrinks a 540×960 cover to 288×512 *before* OCR; removing that downscale takes the easy case (solid bar, large, plain font, Latin) from **exact 27.3% → 45.5%, usable 36.4% → 81.8%, caption-correct 45.5% → 90.9%, CER 0.052 → 0.020**. So on the population you care about, character accuracy is already **98.0%** once the resize is gone, and the two residual misses are single trailing characters bled in from an adjacent emoji and a handle's underscore — not recognition failures. **99% on the easy case is close, but it is not true today, and it is not true at any resolution for non-Latin: 0 of 10 usable across Arabic, Cyrillic, Devanagari, Gujarati, Hangul and Malayalam.** Separately, the "OCR returned nothing" population turns out not to be OCR's fault at all: all 12 sampled cases have no overlay text whatsoever.

**2026-07-30 · MEASUREMENT. Read-only on pipeline code — imported, never modified. $0: every image was already on disk, no network, no paid call. Nothing installed (three candidate engines were dry-run through `pipguard --check-only` only).**
**Artifacts.** The transcriptions, raw OCR output, per-image scores, sample manifest and all three scripts are committed alongside this report in `reports/BL-733-assets/` — so every number here re-derives offline with `python bl709_score.py`.
**The 60 images themselves are deliberately NOT in this public repo.** They are Instagram thumbnails of identifiable private individuals (selfies, portraits), and publishing them here would distribute personal images the measurement does not require. They are retained in the private pipeline repo at `scratch/bl709/images/`, keyed by the same ids (`A00`…`D59`) as `sample.json`, which records each source filename — so the set is fully reconstructible by anyone with pipeline access. This is the one deviation from the brief's "save the images to the repo", and it is deliberate.

## PART 0 — the premise checks out: nobody had measured this

`_vision_dataset/ocr_bench.py` exists, and its own docstring states its question: *"does OCR + content-type fusion beat the SigLIP-only ~76% baseline on a HELD-OUT split?"* It reports AUC, precision and recall for a **classifier**. It caches OCR text (2,028 entries) and never once compares that text to the words on the image. **Whether OCR reads correctly had never been measured in this programme.**

---

## PART 1 — sample design, because the obvious sample would have inflated the number

The tempting sample is "images where OCR returned text". That measures only whether OCR got the words right *when it found words* — i.e. precision — and **structurally cannot see a total failure**, where text is plainly visible and OCR returned nothing.

So strata were defined by the **geometric** bar detector (`repost_layout.layout_features` — pure numpy, no OCR, no model) crossed with whether cached OCR was empty, over 1,413 candidate images from the movie/meme tags:

| stratum | definition | available | sampled |
| --- | --- | --- | --- |
| A | bar detected + OCR text | 591 | 26 |
| B | bar detected + **OCR EMPTY** | 254 | 12 |
| C | no bar + OCR text | 304 | 14 |
| D | no bar + OCR empty | 264 | 8 |

**Transcribed blind.** Every transcription was written before any OCR output for these 60 images was read — the OCR run was still executing in a background process while I transcribed. Fixed seed; the file list is committed, so the whole thing re-runs.

**Metric definitions, stated because "accuracy" is ambiguous:** *exact* = whitespace-normalised string equality, case and punctuation kept. *usable* = multiset of word tokens equal, lowercased, punctuation and emoji stripped, order-insensitive (OCR returns regions in reader order; that is not a transcription error). *CER* = character-level Levenshtein / length of truth. *caption-correct* = every word of the **primary** overlay caption present, ignoring watermarks and incidental scene text.

## PART 2 — the answer to the deciding question, first

**Easy case = solid caption bar + large text + plain font + Latin script. n=11.**

| variant | exact | **usable** | caption-correct | CER |
| --- | --- | --- | --- | --- |
| **production (`max_side=512`)** | 27.3% | **36.4%** | 45.5% | 0.052 |
| **no downscale** | 45.5% | **81.8%** | **90.9%** | **0.020** |
| crop to bar + 2× upscale | 45.5% | 81.8% | 90.9% | 0.021 |

**Yes — the residual error is overwhelmingly NOT in the easy case, but only once the downscale is removed.** As shipped, the easy case is *not* already at 95%; it is at 36% usable, and that is a pre-processing defect rather than an engine limit.

At full resolution the two remaining easy-case misses are trivial, and in both the caption itself is correct:

| id | truth | full-res output | cause |
| --- | --- | --- | --- |
| A10 | `Vo Meri Biwi Hai` | `Vo Meri Biwi Hait` | adjacent 😂 emoji bled one character into the text |
| A19 | `Picknic par nhi aaye ho …crate_` | `… crate 2` | the trailing `_` of a handle read as ` 2` |

**Easy-case CER at full resolution is 0.020 — 98.0% character accuracy.** The gap to 99% is emoji adjacency and trailing punctuation, not recognition.

**Honest caveat, stated plainly: n=11.** 9/11 = 81.8% carries a 95% Wilson CI of **[52.3%, 94.9%]**, and 10/11 caption-correct is **[62.3%, 98.4%]**. The direction and size of the downscale effect are unambiguous; the precise level is not pinned down at this n.

## PART 3 — the bug, and why it was invisible

`ocr_features.ocr_one(..., max_side=512)` downscales any image whose longest side exceeds 512 px before handing it to EasyOCR. The sampled covers are 540×960, so **production has been OCR-ing a 288×512 version of every thumbnail.** The docstring justifies it as a ~2× CPU saving on the dominant cost, and reasons that "overlay captions are large and stay legible."

**They do not stay legible enough.** Measured across all 29 Latin text-bearing images:

| variant | mean CER | mean WER | WER ≤ 0.10 |
| --- | --- | --- | --- |
| production 512 px | 0.195 | 0.314 | 24.1% |
| **no downscale** | **0.112** | **0.255** | **41.4%** |
| crop to bar + 2× | 0.219 | 0.444 | 48.3% |

This was invisible because every prior round asked whether OCR *helped a classifier*. A feature like `f_clickbait` fires on `"wait for end"` whether or not the neighbouring word is mangled, so a 20% CER barely moves an AUC — and the AUC was the only thing anyone looked at.

**Cropping to the detected bar is not the fix.** It matches full resolution on the easy case and is *worse* across all Latin images (CER 0.219 vs 0.112), because the crop occasionally clips glyph tops and discards on-video text outside the band. **Just stop downscaling.**

## PART 4 — errors by condition

### Latin vs non-Latin — the single largest split

| | n | usable | caption-correct | CER |
| --- | --- | --- | --- | --- |
| Latin | 29 | 24.1% | 34.5% | 0.195 |
| **any non-Latin** | **10** | **0.0%** | **0.0%** | **0.840** |

Per script, all zero: Arabic (CER 0.905), Cyrillic (0.966), Devanagari (0.647), Devanagari+Latin (0.824), Gujarati (1.000), Hangul (1.000), Malayalam+Latin (0.802). **BL-683 found CJK read 0/8 on the `en` pack; this extends that verdict to every non-Latin script in the corpus.** The 95% CI on 0/10 is [0%, 27.8%] — consistent with "hopeless", not merely "unmeasured".

One nuance worth keeping: **digits survive inside non-Latin text.** A Hindi astrologer banner recovered `91- 70786- 99082` exactly while every Devanagari word failed. The existing `_PHONE_RE` spam feature therefore still works on Hindi overlays.

### Bar vs no bar (Latin only, so script is not confounded)

| | n | usable | CER |
| --- | --- | --- | --- |
| in a solid caption bar | 15 | 33.3% | **0.089** |
| directly on video | 14 | 14.3% | **0.309** |

**The caption bar is worth ~3.5× on character error.** This is the strongest confirmation yet of the repost-funnel design premise: the format that makes a page identifiable also makes its text readable.

### Font and size (Latin only)

plain CER 0.145 · mixed 0.130 · decorative 0.157 · **stylised 0.385**. large CER 0.147 · medium 0.196 · **small 0.697**.

Stylised condensed caps are the worst font case (`MOVE ON BRO, IT'S JUST A MOVIE` → `MOVE ON BPo, MT$ JST 4 MOVE`). Small text is effectively unreadable, which is expected and mostly affects UI screenshots rather than captions.

### Systematic character confusions

Across the 29 Latin images: **apostrophe dropped 3×, comma → semicolon 3×, `@` → `G` 3×.** These barely move CER but they destroy exact and word-level match — `@` → `G` turns a handle into a different token. A three-rule post-processing pass would recover most word-match failures at zero cost.

## PART 5 — the finding that reframes "OCR returned nothing"

**All 12 sampled stratum-B images (bar detected, OCR empty) have no overlay text at all.** Hand-checked, every one: letterboxed film frames, dark scenes, a mosque at night, a selfie. One carries **only emoji** (🚬💀🔥); one carries only a CapCut watermark glyph. All 8 of stratum D likewise.

**OCR made zero errors on 21 of the 60 images, because there was nothing to read.** The 254-image "bar but no OCR text" population is a **geometric bar-detector** artifact — it fires on letterbox padding and dark bands — not an OCR failure population. Anyone reading the 30% empty rate as an OCR miss rate would be chasing the wrong component.

Hallucination is the real risk on blank frames, and it is small: production emitted text on **2/21** blank images (9.5%, CI [2.7%, 28.9%]), both short garbage strings. Removing the downscale slightly *increases* this to 3/21 — a real if minor cost of the fix.

**The bar detector also has a false negative**, found incidentally: C43 carries obvious solid black bars reading `Part 9 / Telugu, Romantic and Comedy` and was classified no-bar, while A08/A09 — the identical template — were caught.

## PART 6 — the cheapest fix, ranked. Nothing was installed.

| # | fix | cost | measured effect | risk |
| --- | --- | --- | --- | --- |
| **1** | **Stop downscaling: `max_side=None`** | **one argument** | easy case usable **36.4% → 81.8%**, CER **0.052 → 0.020**; all-Latin CER 0.195 → 0.112 | ~2× CPU (the docstring's own figure), and blank-frame hallucination 9.5% → 14.3% |
| **2** | **Add language packs via the existing `ocr_langs` config key** | **config only, no install** | untested, but the current non-Latin result is **0/10**, so the floor cannot be lower | first use downloads weights to `~/.EasyOCR/` — a model cache, **not** a package change. Packs cost load time and can reduce Latin precision, so scope per campaign |
| **3** | Post-process the three confusions (`@`→`G`, `,`→`;`, lost apostrophe) | a few lines | recovers most word-match failures that CER shows are near-misses | none |
| 4 | Crop to the detected bar before OCR | moderate | **no gain** over #1 on the easy case, and *worse* across all Latin (CER 0.219) | **do not do this** |
| 5 | Swap engine | install | unmeasured | see below |

**`ocr_langs` is already wired end to end** — `repost_finder.py:98` declares the default `["en"]`, it is read at `:329` and `:969`, and `ocr_features.py:246` consumes it. **Fix #2 requires no code change at all**, which makes it the obvious first experiment for the non-Latin half.

### Engine swap — checked, not installed

All three candidates were dry-run through `pipguard --check-only`, which resolves the install and refuses on any protected-package downgrade across the numpy-2.0 ABI boundary:

| candidate | pipguard verdict |
| --- | --- |
| `rapidocr-onnxruntime` | **CLEAN** — no protected package moves backwards |
| `paddleocr` | **CLEAN** |
| `paddlepaddle` (the actual engine; **not** pulled in by `paddleocr`) | **CLEAN** |

**Nothing was installed; `--check-only` was set on every run.** So an engine swap is *available* without the BL-681/BL-682 numpy hazard — but it should be the **last** thing tried, because fix #1 is free, already measured, and recovers more than half the missing accuracy. `rapidocr-onnxruntime` is the better first candidate: this host already has `onnxruntime 1.22.1`, so it avoids pulling a second full DL framework.

## Honest limits

- **n=11 on the easy case**, CI [52%, 95%]. The downscale effect is unambiguous in direction and size; the exact level is not pinned down.
- **Ground truth is one transcriber, no second pass.** Emoji were excluded from truth by convention; two Malayalam posters carry dense tiny credit blocks I did not transcribe in full, which inflates their CER.
- **The corpus is the editor crawl** (`_vision_dataset`, tags `movieclips`/`movieedit`/`moviereview`/`capcutedit`) — the closest available population to the repost pages, but **not** the repost corpus itself. The 26 committed golden repost frames are 180×320, too small to re-measure the downscale question on.
- **Fix #1's CPU cost was not benchmarked here**, only inherited from the docstring's ~2× claim.

**No pipeline file was changed, nothing was installed, and no key appears in this document.**
