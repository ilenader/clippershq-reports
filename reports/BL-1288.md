## 4. Never re-buying what is already paid for

### The seen-set is locked across read AND write

`resolve_cache.save` is the seen-set writer and it does the right thing, verified by reading
it rather than assuming:

```python
with filelock.file_lock(path):
    merged = merge(load(path), cache or {})   # load INSIDE the lock (fresh)
    ... os.replace(tmp, path)
```

**The load is inside the lock**, so the read-modify-write pair is ordered, not just the write.
`os.replace` makes one write atomic but cannot order a pair — the lock is what does that. The
merge is newest-timestamp-wins, so a concurrent funnel's marks survive instead of being
clobbered, which is the failure that would cause a re-buy.

## 5. Written as it is found

`spotify_resume` is on, so every artist is appended to
`scratch/resume/spotify.BL1288_MAIN.jsonl` with `flush()` + `fsync()` **before the next artist
starts**. That is the durable record; the XLSX at the end is a convenience.

**This was not a hypothetical.** I stopped the run with `taskkill /F` at 20:26:20 — a hard
kill, which on Windows exits `0xC000013A` and runs no `finally` and no `atexit`. Measured
across it:

| | before the kill | after |
|---|---|---|
| SPOTIFY ledger | $0.693600 | **$0.693600** |
| checkpoint records | 4,163 | **4,176** |
| checkpoint emails | 358 | **362** |

**Not one cent of billed work was lost**, and the checkpoint had even gained 13 records in the
seconds between the snapshot and the kill — the per-artist fsync doing exactly its job.

**But the leads had NOT reached master, and that is the real finding here.**
`append_found_to_master` runs *after* `sp.run` returns, so at the moment of the kill
`master_leads.csv` still held only the 31 calibration rows while **362 paid-for emails sat in
the checkpoint alone**. That is precisely the shape of the round that "lost 810 already-paid
leads to a checkpoint that was never appended".

**The recovery path works and cost nothing**: re-running the same run-id replayed the
checkpoint and appended **+552 rows in 44 seconds for $0.000000**. So the incremental write is
genuinely durable — but *durable is not the same as delivered*, and a killed Spotify run needs
one resume before its leads are in the database.

**A killed run does say where it stopped**, though it says it by going stale rather than by
announcing it: `scratch/runs/BL1288_MAIN.json` froze at `status: "running"`, `leads: 361`,
`updated: 2026-08-15T20:26:35`. A reader must compare `updated` against the clock; there is no
`killed` state.
