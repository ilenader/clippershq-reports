## 0. The short version

**DIRECT_SEND.csv is not a deliberate list.** 2,394 distinct addresses, **2,393 of them already
in the primary**. Exactly **one** address is unique to it, and that address is unique *because
the primary correctly dropped it* — `noahfloersch.com` lost its mail route between 2026-08-11
and 2026-08-12. So the file offers no reach the primary lacks, and the whole of it is a
double-send. **Nothing is stale**: every one of the 2,394 still has a master row.

**The MX premise in the brief was already stale when it arrived.** All 791 domains the file
touches were probed before I started. I re-probed all 791 anyway: **zero verdicts changed**,
1 `NO_MX_A_ONLY` and 790 `MX_OK`. Suppression is not vacuous; it is right.

**The plugin's hooks do not exit non-zero.** I ran all six handlers: every one exits **0**. What
they cost is **latency** — ~2.0 s on *every tool call* and ~2.1 s on *every Read* — to write to
a database that contains **zero rows in every content table**. Not "frozen"; empty.

**I have not chosen** between sanctioning and quarantining, and §2 says why the numbers make
one branch structurally impossible rather than merely unattractive.

## 2. The two options, with their consequences. I have not chosen.

### Option A — SANCTION it into the partition, with a stated purpose

Add it to `SANCTIONED_SECOND_SEND_FILES` in `tests/test_send_superset.py` with a sentence
saying what audience it serves.

**Consequence, measured: it cannot be sanctioned as it stands.** The partition's defining rule is
`primary ∩ sanctioned = ∅`. This file's intersection with the primary is **2,393 addresses**, so
`test_a_sanctioned_second_file_is_DISJOINT_from_the_primary` would go from green to red naming
2,393 double-sends — each of those people mailed twice, once with editor copy and once with
whatever DIRECT's copy is. Sanctioning it as-is trades one red for a worse one.

Sanctioning therefore means **sanction *and* rebuild it disjoint from the primary**. And a
rebuild that is disjoint from the primary and passes suppression contains, by the numbers above,
**2,394 − 2,393 − 1 = 0 addresses.** The purpose the file would be sanctioned for would have to
be a purpose it does not currently serve, supplied by you.

### Option B — QUARANTINE it

`git mv`-free move of the file into `output/quarantine/`, with a line in that directory's
README saying what it was and why it stopped.

**Consequence:** the operator loses the ability to double-click a file holding 2,393 people who
are already in the primary, plus one address measured to have no mail route. **Nothing else is
lost** — 0 addresses become unreachable, because the 1 unique one is a measured dead end and the
other 2,393 are in `ALL_BOT_READY.csv` today. It also joins its own 2026-07-31 predecessor, which
is already there for the same reason.

**Why I am not choosing.** The measurement kills the "deliberate list" hypothesis for the 2,393
but it does **not** tell me what the file was *for*. §1.3 could not identify its author or its
campaign. If DIRECT was a real audience with different copy, Option A plus a genuine rebuild is
the right answer and quarantining discards the intent; if it was an ad-hoc export, Option B is
right. That is your knowledge, not mine, and the last round refused this same call correctly.

## 5. The `.bak` pile — 6.43 GB, not 8.40, and a rule that takes 5.14 of it

**Re-measured: 264 files, 6.43 GB.** (All `*.bak` at the repo root is 266 files / 6.43 GB —
`master_leads.csv.*.bak` is essentially the whole of it.) The brief's 8.40 GB does not reproduce
today. Separately, `backups/` holds another **1.8 GB** and `config.backups/` holds **23,764 files**
— out of scope here, but the same shape.

**A trap I had to route around, and it is in `docs/PRECONDITIONS.md` §2.** `shutil.copy2`
preserves the *source's* mtime, so a backup's mtime is when master was last written *before* the
copy. The oldest file's mtime says 2026-07-22 18:58 while its name says 2026-07-23 16:46. **A
retention rule keyed on mtime deletes the wrong files.** The rule below reads the timestamp out
of the filename, which is why the timestamp is required to be there.

### The proposed rule

| | keep |
|---|---|
| **R1** | everything stamped within the last **48 h** — the undo window |
| **R2** | the **newest per (day, label)** for the last **14 days** — one restore point per funnel per day |
| **R3** | the **newest per label, forever** — every funnel's last-known-good survives |
| **R4** | the **newest 3 overall**, unconditionally — a floor the rule cannot cut through |
| **R5** | anything a **live claim** covers |
| **R6** | anything whose **filename does not parse** — never a deletion candidate |

**Dry run on today's tree** (`scratch/bl1236_bak_retention.py`, which has no delete path at all):

```
parsed            263 files   6.43 GB
UNPARSED (kept)     1 file    0.02 GB   master_leads.csv.bl806.bak
WOULD DELETE      211 files   5.14 GB
WOULD KEEP         52 files   1.29 GB
```

**What goes:** 184 `repost`, 10 `twitch`, 5 `spotify`, 5 `googleplay`, 3 `youtube`, 3
`bl1176_meme`, 1 unlabelled. The concentration is the finding — **178 of 264 files, 4.36 GB, were
written on 2026-08-01 alone**, nearly all by the repost funnel, which backs up on every write.

**What stays:** the last 48 h in full, one restore point per funnel-day for a fortnight, and every
funnel's most recent backup no matter how old — oldest kept
`master_leads.csv.20260724_150048.pre_cleanup.bak`, newest kept
`master_leads.csv.20260812_210235.bl1176_meme.bak`.

**I have deleted nothing.** And the argument for the rule is not really disk: INFRA-024 already
established that a copy on the same disk inside the same OneDrive folder **is a copy, not a
backup**. 6.43 GB of same-disk copies buys far less protection than one offsite copy of the eight
files in `BACKUP_THESE_6_FILES.md`. The rule trades redundancy nobody can restore from for space —
it does not trade away safety, because that safety was never there.

**One rule this must inherit if it is ever implemented:** an unreadable claim registry must
**RAISE**, never resolve to "nothing is claimed". The dry-run script prints that refusal path
rather than assuming — that is `docs/PRECONDITIONS.md` §13, on a path that deletes files.
