### The default that made my own check vacuous, twice

`send_suppress.classify(email, handle, name)` takes `mx_table=None` and **falls back to `{}`**.
With an empty table `mx_status()` returns `"unknown"` for everything, so the dead-MX and
no-route exclusions **cannot fire** — and the run still prints a clean `0 excluded`, which
reads as a pass.

I walked into it, and into a second version of the same error before that: `classify()` returns
a **dict**, and I treated truthiness as "suppressed", which put every address in the suppressed
bucket, left the survivor list empty, and printed **`0 survivors with a dead MX`** — zero out
of zero.

Both are fixed, and the pass above is now guarded by three assertions that must fire first:

```
PREDICATE SELF-TEST  dead    : synthetic probe on beamz.ae           -> 'dead'      (True)
PREDICATE SELF-TEST  no_route: synthetic probe on arabicfragrance.es -> 'no_route'  (True)
CLASSIFIER SELF-TEST: synthetic dead address -> exclude=True reasons=('dead_mx',)
```

(The probe addresses are constructed, not leads — a fixed local part on a domain the table
already calls dead. They are written here without the `@` form so the report carries no
address-shaped string at all; the secret scanner rejects the literal, and it is right to.)

**Both shipped callers pass the table** — `send_list.py:355` and `writer.py:1360`, each loading
it via `load_mx_table()`. The production path is sound; the trap is for anyone writing an audit
against it, which is exactly what this round was.

**The denominator check is guarded.** "0 dropped" would be satisfied trivially if the stamp
had already set `date_sent` on every bounced row — which it had. So the probe strips
`date_sent` *and* `sent_channel` from a bounced row and asserts it still counts:

```

```

That is the regression `_was_sent` was widened to prevent: `mark_bounced_from_csv` does not set
`date_sent`, so without the third clause exactly the rows that bounced would leave the
bounce-rate denominator.

## 6. THE HONEST EXPECTATION, AND WHAT MEANS STOP

**Expect ~0.81% hard bounces, plausibly 0.37%–1.76%.** That interval is measured on the
**informative subset only** and is the only figure worth quoting.

**The 97.2% naive SMTP acceptance figure is meaningless and must not be quoted.** Catch-all
domains accept every address offered — 44% of domains, 9.5% of rows — so for those rows
acceptance carries no information at all. An audit that reports 97.2% is reporting that
catch-all domains are catch-all.

What the current file looks like:

| | rows | share |
|---|---:|---:|
| free mailbox providers (gmail, outlook, icloud…) | 2,325 | **78.3%** |
| custom domains | 645 | 21.7% |

gmail.com alone is 2,156 rows (72.6%), and **495 of 551 domains carry exactly one address**.
This is good news for the estimate: free providers reject unknown mailboxes rather than
accepting everything, so the catch-all blind spot is confined to part of the custom-domain
fifth, not spread across the file.

### STOP IMMEDIATELY if any of these

1. **A sent message contains `[[`.** One is enough. It means the identity file was not loaded
   and every message in that batch is wrong.
2. **Bounces exceed 5% in the first 200 sends** (≥10). The point estimate predicts ~1.6 and the
   interval tops out at ~3.5; 10 is roughly 6× the estimate and outside the interval, so it
   means the population is not what was measured — not bad luck.
3. **Any spam complaint, or any sending-domain blocklist entry.** Both are reputational and
   effectively irreversible on the timescale of this campaign.
4. **Replies that do not recognise the premise** — "who is this", "wrong person", "I don't edit"
   — above roughly 1 in 20. That is a targeting failure, and it costs more than a bounce
   because it is a human reading a wrong message.

**Send in batches of ~200 and read the bounces between batches.** The whole value of the 0.81%
estimate is that a batch of 200 is large enough to falsify it.

## Method / limits

**The refresh covers the primary file's 551 domains, not all 1,135 in the table.** Domains that
appear only in master — including the 37 already marked DEAD — were carried forward, not
re-probed. A dead domain coming back to life would not be noticed here. That is the right
trade for a send-day check (it re-probes exactly what is about to be mailed) and it is a real
gap for anything that rebuilds the file from master.

**"Newly dead: 0" is a two-day delta, not a guarantee.** The previous table was written
2026-08-02 13:31 and this one 2026-08-03 20:12. The five domains that died between two earlier
audits died over a longer gap.

**The 0.81% bounce estimate is inherited, not re-measured here.** No mail was sent, so nothing
in this round could confirm or move it; §6 restates its scope rather than re-deriving it.

**16 of 167 rows carrying the reach sentence did not parse** into three numbers and are
excluded from that table. They are a different sentence shape, not known defects — but the
0-of-151 result is a result about 151 rows, and the denominator is stated for that reason.
