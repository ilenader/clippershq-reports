## The fix: merge inside the lock, and treat the caller's rev as a staleness signal

I was offered two options and took the first, because the second does not actually fix
anything:

> **Changing `>=` to `>` only flips WHICH row wins.** The winner still carries whatever its
> author knew and drops the rest. The collision is the symptom; **the field loss is the
> disease**, and only merging cures it.

So `append_many` now, inside the shard lock it already held:

1. reads the current latest for the clip_ids in the batch — **at write time, not read time**
2. merges the incoming row over it, so no field any prior writer set is dropped
3. allocates the rev in the same place, `max(caller_rev, latest_rev + 1)` — **never equal**

A caller's snapshot may be arbitrarily stale and the write is still correct.

### The refinement two existing tests forced, and they were right

My first version threw the caller's `rev` away entirely and always wrote `latest + 1`. Two
tests in `test_clip_library.py` went red:

```
test_lower_rev_arriving_late_does_not_win    500 != 1
test_index_is_the_dedup_key_and_is_rebuilt   3 != 2
```

**Both were real regressions.** The caller's rev carries information — *"this is built on
version N"* — and I had discarded it, so a deliberately **lower** rev arriving late could
overwrite a newer value. That property exists on purpose.

The reconciliation: **rev is a staleness signal, not a request.**

| caller's rev | conflict resolution | new rev |
|---|---|---|
| **higher** than stored — genuinely ahead | incoming wins | `caller_rev` |
| **equal or lower** — read before someone else wrote | **existing wins; incoming fills gaps only** | `stored + 1` |

Either way the row is merged, so nothing anyone wrote is dropped. That holds both properties
at once, and I would not have found it without those two tests.

## The race, with a control that fails

BL-867 raced the append lock and *measured* 5 rows lost. Same standard here — two writers,
each from its own stale snapshot, each writing fields the other has never heard of:

```
FIXED      BOTH writers' fields visible : 40 of 40
           rev collisions               : 0
           -> NO FIELD LOST, NO COLLISION

CONTROL    (the pre-BL-919 append, no merge, caller's stale rev)
           BOTH writers' fields visible : 0 of 40
           rev collisions               : 40 clips
```

**The control is the part that makes the race mean anything** — a race that passes on broken
code proves nothing, which is the lesson BL-883's vacuous shrink guard taught the hard way.

One thing the harness showed by accident and is worth recording: **threaded, the field loss
is nondeterministic** — sometimes both writers' fields survive by pure ordering luck. That is
precisely why this survived a whole round unnoticed. The control above is therefore
*sequential and stale*, which is exactly how BL-895 collided with BL-899: both read at rev 1,
the speech pass wrote first, the vision pass wrote second from its original snapshot.

### Why `rev_collisions` still reads 236, and why that is correct

**A collision is permanent in an append-only file.** Once two rows share a rev they always
will, because nothing is ever deleted. Repair appends a merged row at a higher rev, so the
*value* becomes visible again while the historical collision stays forever.

So there are two functions and only one of them is a bug report:

- `rev_collisions()` — **forensic**. Answers *"did two writers ever tie here"*. Permanent,
  and it will never return to zero on this library.
- `hidden_by_collision()` — **actionable**. Answers *"is a value on disk that a consumer
  cannot see"*. **This is the one that must read zero, and it does.**

A detector keyed on collisions alone would cry wolf about history forever, which is how a
real signal gets muted.

## The design limit, recorded at the site

In `clip_library.py`'s own docstring, beside the rule it qualifies:

> **...AND THAT RULE WAS RIGHT AND INCOMPLETE.** BL-849's labeller stated the other half
> correctly — *"THE ROW IS MERGED, NOT REBUILT"* — and followed it. What nobody anticipated
> is that `base.rev + 1` computed from an INDEPENDENT SNAPSHOT collides.
>
> **THE GENERAL SHAPE**, worth carrying to any other append-only store here: a version number
> derived from a read is **a lock you did not take**. If two writers can compute it
> independently, they will eventually compute the same one.

## Limits

- **The 236 historical collisions stay.** Append-only cannot remove them and I did not try.
  Only their *effect* is repaired.
- **Recovery merges oldest-to-newest by rev**, so on a genuine disagreement the later row
  wins. Where two rows collided at the same rev the file order decides, which is arbitrary —
  it is the same arbitrariness that caused the bug, and for these clips there is no better
  source of truth left.
- **`merge_over` cannot express a deliberate deletion.** No caller needs one today; if one
  ever does, `None` will not do it.
- **The fix only helps processes that import it.** BL-895's already-running process kept the
  old code until it exited — a live round cannot be patched underneath itself.
- **I did not re-verify BL-895's or BL-849's own outputs**, only that their fields are visible.
- **`config.json` is 161 keys**, was 162 earlier today. Not mine, and gitignored, so no diff.

## Method

`claims_read.py` first, then `git status --porcelain` on the target and a read of the 84
uncommitted lines before touching it. The fix is in `append_many` inside the lock it already
took. Raced against a deterministic control on the old code path, because a race that cannot
fail is decoration. The two red tests that followed were treated as evidence rather than
noise and produced the staleness rule. Recovery is free — every value was already on disk —
and was verified through `read_all`, the consumer's own reader, not through the writer.
