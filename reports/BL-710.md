# BL-710 — Clip library and catalogue walk: the storage and filtering halves, built and proven offline

**Date:** 2026-07-29 · **Type:** Build, NEW FILES ONLY · **Spend:** **$0.0000** (no paid call made)

**Scope was cut by the owner mid-task, and correctly.** The tree was not quiet, so the
assembly was split: everything that could be built and proven without touching a contended
file was built; the wiring that requires editing existing files was not. This report says
exactly which is which.

Two preconditions in the brief failed at 17:27:

- **`main.py` was running a live PAID funnel.** PID 4024, up 2 h 08 m, 5,120 CPU-seconds

  `api.hikerapi.com "GET /v2/user/by/username..." 200`, a billed resolve, at 17:12.
- **Another agent held the file this build must edit first.** `clippershq/repost_finder.py`

  `clippershq/content_genre.py`, `clippershq/artist_genre_map.py` and
  `tests/test_content_genre.py` continuously through 17:29.

`repost_finder.py` is where BL-697's `iter_medias` fix goes — *"fix that first or nothing

was touched**, since backing up `master_leads.csv` mid-append only captures a torn snapshot.

## Two real bugs, both found by building rather than reasoning

### 1. The two copies of a media are NOT equivalent — richest must win, not first

This is the important one, and it is not in any prior report.

BL-684 established that each media appears twice in `stream_rows` and that only `id` is
stable across both passes. What that understates: the two copies carry **wildly different
field sets**. Measured on `_probe_samples/ig_gql_user_clips_clipcapture_tv_sorted.json`:

| copy | keys | has `code` | `caption` | `taken_at` | `clips_metadata` |
|---|---|---|---|---|---|
| inside row 0's `1$xdt_user_clips_graphql(data:$data)` wrapper | **35** | no | no | no | no |
| its own `XDTMediaDict` row | **170** | yes | yes | yes | yes |

A first-occurrence-wins dedup — the obvious implementation, and the one this build shipped
first — hits the thin copy first and produces a library where **every clip is missing its
permalink, caption, timestamp and audio metadata.** Nothing errors, because each of those
fields is individually optional. The first dry run wrote 22 clips into a single
`clips-unknown.jsonl` shard with `permalink: None` and `content_genre: None` throughout, and
it looked like a successful run.

`iter_stream_medias` now keeps the copy with the most keys, preserving view order.
Pinned by `test_dedup_keeps_the_RICHEST_copy_not_the_first` and
`test_real_envelope_yields_the_rich_copy_for_every_clip`.

### 2. OCR is 1.34 s per IMAGE, not per clip

Comparing the per-image figure against `speech_frac`'s 1.6 s per clip puts the two most
expensive stages in the wrong order. BL-682 measured a 12-frame clip at ~16 s of OCR — ten
times the transcription. `STAGE_COST_S["ocr"]` is now
`OCR_S_PER_IMAGE * OCR_FRAMES_PER_CLIP` = **16.08 s per clip**, and a test asserts
`STAGE_ORDER` is non-decreasing in cost so the ladder cannot silently invert again.

### And one trap that was in the data, not the brief

The gql envelope prefixes some scalars with a type tag: `taken_at` arrives as
**`1ltaken_at`**, `lat`/`lng` as `1flat`/`1flng`. A plain `.get("taken_at")` returns None and
every clip lands in the `unknown` shard. `clip_library.mget()` matches on suffix then
validates the prefix — stripping a prefix pattern is ambiguous, because the tag is one digit
plus one *or two* letters and a greedy strip of `1ltaken_at` eats the `t` and yields
`aken_at`.

## Proof

Four of the five proofs the brief asked for are delivered. The fifth needs the tree.

### stream_rows dedups to 12, not 24 — on the real envelopes

```
clipcapture_tv      naive deep recursion 24 -> unique by id 12
culturemeetsonline  naive deep recursion 24 -> unique by id 12
decibeldrops        naive deep recursion 24 -> unique by id 12
```
`sort_by_views=true` confirmed strictly descending on all three (21,579,646 → 2,185,695 on
clipcapture.tv).

### The view floor stops pagination, and the patience window survives the inversion

BL-684 measured one adjacent inversion, so stopping on the first sub-floor item truncates a
catalogue on a blip. With `patience=3` and a floor of 20,000 against
`[90000, 80000, 100, 70000, 60000, 50000]`:

| patience | kept |
|---|---|
| 1 | `[1]` — the blip ended the walk |
| **3** | **`[1, 2, 4, 5, 6]`** — the blip is skipped, the walk continues |

Three *consecutive* lows do stop it. `stopped_on` reports `floor` / `no_more` / `max_pages` /
`empty` so a truncated walk is never silent.

### Nothing expensive runs on a clip that failed the view filter

From the dry build across three real accounts:

```
views          entered  22   passed  22     0.0 s
content_genre  entered  22   passed  22     0.0 s
valence        entered  22   passed  22     0.0 s
layout         entered   0   speech_frac   0   ocr   0
walked off the wire: 28   cleared the view floor: 22
```

Six of the 28 walked clips fell below the floor and **entered no downstream stage at all**.
The unit test asserts the stronger form directly — that `layout`, `speech_frac` and `ocr` each
saw exactly the ids that cleared the floor, and that a stage rejecting everything leaves the
next two at zero.

## Design notes worth carrying

- **Provenance has four rungs now.** `caption_parser` established declared/derived/absent;
  `measured` is added for values produced by running a detector on the media (speech_frac,
  layout). **Asymmetry to know about:** `caption_parser.field()` does not know `measured` and
  returns None for it. Consumers of this library must use `clip_library.field()`.
- **`arousal_audio` and `affect_conflict` are ABSENT, not False.** The audio axis is not
  ready (BL-682, BL-705); the module will not invent a negative.
- **No page-level format field exists, deliberately.** BL-705 measured that it does not
  exist. `format` is per clip, from `speech_frac` at the 0.30 threshold that sits in a real
  trough. A test asserts `account_format` / `page_format` are absent from the schema so
  nobody adds one back.
- **JSONL, not SQLite,** because this repo is under OneDrive and a daemon copying
  `.db`/`-wal`/`-shm` at three different moments yields a file that opens cleanly and is
  wrong. A torn JSONL line costs one clip — proven by a test that appends a half-written line
  and reads the library back intact.
- **`walk_account` takes an injected `fetch_page`.** That is what made every walk property
  above testable with no client and no key, and it means wiring the live call later is a thin
  adapter rather than a rewrite.

## Limits

- **Nothing here has made a network call.** Every number above comes from saved envelopes or
  synthetic fixtures.
- **One saved page per account**, so multi-page pagination is exercised only against
  synthetic envelopes.
- The three fixtures are the **same three accounts** BL-682 and BL-700 used, so the
  `content_genre` fill rate of 10/22 reflects clipcapture.tv's caption template, not a
  population rate.
- **`OCR_FRAMES_PER_CLIP = 12` is an assumption** carried from BL-682's "12-frame clip", not a
  measurement of what this pipeline would actually sample.
- The cost model's `keep_rate` default of 0.5 is a **guess**, not measured; the dry build's
  22-of-28 (79%) came from three accounts against a deliberately high floor and should not be
  used to replace it.
