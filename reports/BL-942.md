## 1. The options, each with what it clears and what it blinds

Corpus: **484 published reports, 43 failing.** Of those 43 — **8 fail on emails** (true
positives, they contain a real address), **12 fail only on CUIDs**, and **23 fail on CUIDs
*and* something else. So the ceiling for ANY cuid-specific fix is about 12–13 reports**, not
35: the rest carry other flagged literals and would still fail.

| option | clears | blinds |
|---|---:|---|
| **A** require an uppercase character in the run | **32 / 43** | **`api.key`, `ig_api.key`, `twitch_api.client_id`, `twitch_api.client_secret`, `openrouter_api.key`** |
| **B** exempt the cuid2 grammar `c[a-z0-9]{23,31}` | 13 / 43 | none *today* — see below |
| **C** cuid2 grammar **and** the line names an id | 6 / 43 | none |
| **D** change nothing | 0 / 43 | none |

**The attractive option is the disqualified one.** A clears three-quarters of the residual
and blinds the gate to **five of the eight credentials this config actually holds**, because
they are all-lowercase alphanumeric:

```
api.key                  len 32  lower 27 upper 0 digit  5   ALL-LOWERCASE-ALNUM
ig_api.key               len 32  lower 24 upper 0 digit  8   ALL-LOWERCASE-ALNUM
twitch_api.client_id     len 30  lower 22 upper 0 digit  8   ALL-LOWERCASE-ALNUM
twitch_api.client_secret len 30  lower 22 upper 0 digit  8   ALL-LOWERCASE-ALNUM
openrouter_api.key       len 73  lower 24 upper 0 digit 46   (has separators)
```

That is BL-935's hex trap one alphabet over, and it would have been just as invisible.

### B looks safe and is safe by luck, not by structure

B blinds nothing *in this config*. But `api.key` and `ig_api.key` are 32 lowercase
alphanumerics, and B exempts anything matching `c` + 23–31 more of them. **They are one
rotation away from matching.** Tested directly against a synthetic key that is not in config
and has no credential-named word beside it — the only case rule 3b exists to guard:

```
all-lowercase 32, like api.key/ig_api.key   scanner: CAUGHT   A exempts: yes  B exempts: no
all-lowercase 30, like twitch client_id     scanner: CAUGHT   A exempts: yes  B exempts: no
leading c, 32 lowercase (a ROTATION away)   scanner: CAUGHT   A exempts: yes  B exempts: YES
```

For a 32-character lowercase-alphanumeric key the chance of starting with `c` is **1 in 36**.
With five all-lowercase keys in periodic rotation that is a recurring, **silent** exposure —
and the trade being bought with it is **13 reports out of 484**.

## 2. Both directions, and a methodological trap in the test itself

Every candidate was run through the **real scanner** against a planted credential from all
seven secret blocks, in a report body, a code diff and a commit message:

```
A require uppercase    24/24 still caught
B cuid2 grammar        24/24 still caught
C cuid2 + line ctx     24/24 still caught
D do nothing           24/24 still caught
```

**That table is necessary and it is not sufficient, and reading it alone would have shipped
option A.** The planted keys come from config, so the **secret-block rule catches them
regardless of what rule 3b decides**. The matrix therefore cannot see a rule-3b blind spot at
all. The blindness only appears when the key is *not* in config — a rotated key not yet
saved, a key from another deployment, one pasted from a chat — which is exactly the case
rule 3b exists for, and exactly the case the table cannot reach.

**A green matrix does not mean a gate can see.** The direct test above is what discriminates.

## 3. Recommendation: **D — change nothing**

Not because the options are unfinished, but because the trade is bad in both directions that
matter:

- **A** buys 32 reports for a blind spot covering **62% of the live credentials**. No.
- **B** buys **13 reports out of 484 (2.7%)** for a ~1-in-36-per-rotation chance of silently
  exempting a live key shape. The exposure recurs forever; the benefit is 13 documents.
- **C** is structurally sound — it is the hash fix's shape — and buys **6 reports**. Real work
  and a permanent new exemption to maintain, for 1.2% of the corpus.

**The cost of D, stated honestly**, is that a report quoting raw CUID row IDs must truncate
them: `cmoaa70j…` instead of the full 25 characters. **BL-935's own report had to do exactly
that**, at a cost of one character of fidelity, and the report reads no worse for it. A full
database row ID in a public report is arguably a small data exposure in its own right, so the
convention is not merely a workaround — it is what the report should have done anyway.

**35 reports needing a reworded line is the better trade**, and it is a legitimate answer.

If automation is wanted later, **C is the one to take** — it is safe by construction rather
than by luck, and it is the same shape as the fix that already works.

## 4. Correcting the record on the three "never fails" rules

I was told these three had never produced a false positive, and BL-935 found two classes that
had. **Measured across all 484 published reports, it is worse than that:**

| rule | FALSE | TRUE | FP rate |
|---|---:|---:|---:|
| **secret-block** (`key_env_var`) | **20** | **0** | **100.0%** |
| **credential-named** (`API_KEY=DISABLED`) | **10** | **0** | **100.0%** |
| email | 0 | 30 | **0.0%** |

**Two of the three have never once fired correctly.** Every firing of the secret-block rule
in the entire published corpus was on `api.key_env_var` = `LAMATOK_KEY` or
`youtube_api.key_env_var` = `YOUTUBE_API_KEY` — the *names* of environment variables, which
appear in this repo's own setup docs. Every firing of the credential-named rule was
`API_KEY=DISABLED`, a report documenting that a key was turned off.

The email rule is the only one of the three with a clean record, and it is clean in the other
direction: **30 firings, all real addresses, no false positives.** Those reports should fail
until the address is redacted.

This does not mean the two rules are useless — they are the floor that catches a key too
short or too shapeless for rule 3b, and the planted-credential matrix above shows all seven
blocks still caught. It means **the belief that they were quiet was never checked**, and a
rule that has only ever cried wolf is one nobody reads.

## 5. The design principle, recorded because it generalises

> **Exempt by LINE CONTEXT, never by ALPHABET.**
>
> A literal cited as a hash passes; the same literal bare is caught. An alphabet-based
> exemption blinds the detector to every real key sharing that alphabet — and keys are drawn
> from exactly the alphabets that non-secrets use, because both are just identifiers.

Three attempts in two rounds are the evidence:

| attempt | shape of the rule | outcome |
|---|---|---|
| exclude 40/64-char hex | alphabet | **blinded hex keys** — a pinned test caught it |
| require an uppercase character | alphabet | **blinds 5 of 8 live keys** — measured here |
| exempt when the LINE names a hash | context | **works**, and cleared 50 reports |

The context test asks a different question: not *"could this be a secret?"* — which for any
opaque identifier is always yes — but *"is this presented as something else?"* A leaked key
does not sit on a line reading `IDENTICAL  <hash>  earnings-calc.ts`. Corroboration is
available in the document and it is not available in the string.

## Limits

- **The 1-in-36 figure assumes a uniform lowercase-alphanumeric first character.** Real key
  generators may not be uniform, and I did not test the vendors' formats — the direction of
  the argument does not depend on the exact odds.
- **The FP rates are for the published corpus only.** A rule that has never fired correctly
  here may still be the thing that catches the next leak; the number measures noise, not
  worth.
- **Option C's context list is a first draft** (`id`, `row`, `record`, table pipes, SQL
  words). It clears 6 of 43; a better list would clear more, and I did not tune it because
  the recommendation is D.
- **`bl942_options.py` initially matched the full literal rather than the longest run**, so
  `clip=cms5yt…` was missed and option B under-counted at 12. Corrected to 13; the tables
  above are the corrected run.
- **I did not measure how many FUTURE reports would hit the cuid rule** — only the existing
  corpus. Dashboard rounds quote row IDs often, so the recurring cost of D is real.

## Method

`claims_read.py --holders` on every path this round could have touched, then
`git status --porcelain`, before reading anything else. Each option was modelled as an extra
exemption applied on top of the **real scanner's** output, so detection is measured against
the live gate and only the candidate filter is simulated. Blindness was tested twice: once
through the planted-credential matrix, which cannot see a rule-3b blind spot, and once
directly against synthetic keys that are *not* in config, which can. No key value appears in
this report; shapes are reported as counts.
