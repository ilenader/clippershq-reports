## 6. The atexit guard does NOT fire on a kill — and the fix is not a guard

The first kill test **failed**, and it is the most useful result in this round.

```
exit code            : 3221225786          <- 0xC000013A, STATUS_CONTROL_C_EXIT
ledger after         : $7.9793  (+$0.0000)
new ledger rows      : 0
atexit warning fired : False
FAIL: the run spent money and the ledger gained nothing
```

**Windows terminated the process outright. Neither the `finally` flush nor the atexit handler ran**, and 50 seconds of paid calls reached the ledger as nothing. That is not a Windows curiosity: `taskkill /F`, `kill -9`, an OOM kill and a power cut all have the same shape. **Paid runs are exactly the ones that get killed**, and an interrupted run is where a missing row is *least* likely to be noticed — nobody expects a number from a run that "didn't finish".

So the fix is not another exit-path guard. `IgClient.configure_autoflush()` **bounds the exposure** instead of trying to catch every way a process can die.

> **And the first version of that still failed.** With `every=10` the ledger was again $0.0000: the vision runner makes ~1.5 IG calls per clip at ~20 s a clip, so a 55-second run never reached a 10-call threshold. **A count bounds the exposure in dollars but not in time.** `max_seconds` bounds the window; whichever trips first wins.

Third run, hard-killed identically:

```
exit code       : 3221225786
new ledger rows : 1
   2026-08-01 20:59:30  BL876_VISION  calls=6  ig_usd=0.0036
PASS
```

The atexit warning is still absent and **that is not a pass** — at this exit code atexit never runs and *cannot* warn. Autoflush is what held the line. The kill script now says so rather than crediting the guard; an earlier version of my own script called the silence "nothing to complain about", which was flattering and wrong.

## Limits

- **`row_usd` fixes every READER; the two WRITERS still build their totals from components.** `_record_spend_locked` sums three vendors and `_record_aux_spend_locked` five, each spelled out. A new vendor still needs both writers updated — the test catches a reader that re-lists the vendors, not a writer that forgets one. Closing that means a bigger refactor of both recorders than this round should attempt.
- **`_record_spend_locked` writes rows with no `link_usd` or `vision_usd` key at all.** Harmless today because main runs have neither, and `row_usd` reads missing keys as zero. It is latent, not active.
- **The residual's upper bound assumes one call per unlabelled clip.** Clips never reached by any pass cost nothing, so the true figure is nearer the $0.0168 floor than the $0.1854 ceiling; I cannot say where.
- **Autoflush is bounded, not free.** At `every=10, max_seconds=30` a hard kill can still lose up to 10 calls or 30 seconds of spend. It converts an unbounded loss into a bounded one.
- **`_maybe_autoflush` swallows ledger errors** so a spend hiccup cannot kill a paid run. The debt stays owed and the next call retries, but a persistently failing ledger would stay silent until exit.
- **I did not measure whether main-run `stats` counters diverge from receipts.** The mechanism exists (a receipt can report `reqs>1`), but BL-861 made 429s unbilled, so the common retry case may not diverge at all. Unmeasured, and I did not rewrite the core funnel's vendor split on a hunch.
- **The kill test is Windows-only as written.** It sends `CTRL_BREAK_EVENT`; the POSIX path (`SIGINT` to the process group) is coded but unexercised here, and SIGINT is *catchable*, so POSIX would likely take the `finally` path and prove something different.
- **Three short proof passes spent real money on live clips.** The two killed passes' OpenRouter spend is partly unrecorded — the first predates the vision-recording fix, which is the leak being closed.
