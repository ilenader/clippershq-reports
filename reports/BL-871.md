## 1. The question you asked me to settle: flaky, or broken?

**Both. At different times. Neither explains the other.**

Three full runs on a **working** runner:

| run | result | the red suite, run alone |
|---|---|---|
| 1 | 1 of 81 red — `test_killed_runs` | **passes** → genuine flakiness under load |
| 2 | **ALL GREEN — 81/81, 3,560 checks** | — |
| 3 | 1 of 84 red — `test_dashboard` | **fails** → a *real* break in INFRA-014's in-flight work |

**Disjoint failure sets with a working runner.** That settles it: BL-856's contention diagnosis was **correct**, and my BL-867 suspicion that the broken runner explained it was **wrong**.

The timeline confirms it independently. The `NameError` line was touched at **18:06** (`a6fdb48`); BL-856's runs were at **16:30–16:50**. The runner BL-856 used produced real output with real failure lists — a `NameError` would have crashed it exactly as it crashed for me two hours later.

So there were **three** distinct things, and the day's confusion came from treating them as one:

1. **Genuine flakiness under load** — `test_killed_runs` red in run 1, green alone and in run 2. It writes markers to its own temp dir, so this is timing on an atomicity assertion under heavy concurrent I/O on a OneDrive-synced tree, not shared state.
2. **Genuine transient breakage** — another round's file caught mid-edit. `test_dashboard` in run 3 fails *alone*, so it is a real defect in INFRA-014's in-flight work, not contention at all.
3. **A broken runner**, 18:00–18:06 only, which is what stopped BL-867.

**"The suite is flaky under load" has not been excusing red tests all day.** Of the three reds I could reproduce, one was flakiness and one was a real failure that a load excuse would have hidden. The distinction is the finding.

## 2. The runner was already fixed, and already exit-code based

```python
return p.returncode == 0, time.monotonic() - t0, out
```

plus a deliberate second gate — a suite reporting **zero checks is failed**, because exit code 0 proves the file ran and never proves it verified anything.

**The bug was mine.** BL-867's ad-hoc shell sweep grepped for `OK`, while several suites print `RESULT: N passed, 0 failed`. Ten passing suites were reported as failures — wrong in the alarming direction, and it nearly became a finding.

`tests/test_runner_contract.py` (8 tests) now pins the properties that are load-bearing and invisible from outside: exit code is the only pass signal, `run_suite` must not match output text, zero-check suites are failed, both reporting styles are counted, and `run_all.py` parses — that last one because it was once committed mid-edit and left the suite unrunnable.

## 4. The `.lock.lock` assertion, widened from four directories to the whole tree

BL-821 already had a global net. It had three holes, and all three were reachable:

| hole | why it matters |
|---|---|
| **indirection** | `p = lock_path_for(x)` then `file_lock(p)` — and **six real call sites already pass a bare variable**, which a textual check reads as safe |
| **concatenation** | `file_lock(path + ".lock")` never mentions `lock_path_for` at all |
| **unscanned code** | `os.listdir` skips subdirectories (`scratch/caption_tpl/…`), and `dashboard/` was never in the list despite using `file_lock` |

The new AST check walks the whole tree (`clippershq`, `scratch`, `tools`, `tests`, `dashboard`, `memebot`), resolves one level of local assignment, and catches the concatenation and literal forms. **No offenders found** — but the point is that the previous net could not have found them either.

A companion test plants each of the four bad shapes and asserts the checker catches every one, plus asserts the correct form is *not* flagged. A guard that cannot fail is worse than no guard.

### The rule, written down

`docs/PRECONDITIONS.md` **§8 — Stage by explicit path**, with both commits cited as evidence, plus a new row in the **GENUINELY UNSAFE** table beside `git reset --hard`:

## Honest limits

- **`test_dashboard` is left red.** It is INFRA-014's file, actively being edited, and its failure is real rather than flaky. Fixing it would have collided with a live round.
- **The flakiness is characterised, not fixed.** I showed `test_killed_runs` passes alone and green in run 2, and located it in an atomicity assertion rather than shared state — but I did not make it deterministic. Under this much concurrent I/O another suite will occasionally do the same.
- **The lock audit is a point-in-time snapshot.** It proves every process running *at that moment* either takes the lock or does not write the library. A round started before 17:41 that begins writing later would still bypass it; the exposure decays as those processes exit, and all six current writers are on the right side.
- **The AST check resolves ONE level of assignment.** `a = lock_path_for(x); b = a; file_lock(b)` would slip through. That shape does not exist in the tree today and the check has no way to prove it never will.
- **I did not edit `run_all.py`** despite it being in my claim — MEMEBOT-026 had already repaired it and holds the same path. The contract test constrains it from outside instead, which is weaker than owning the file but does not race another writer.
- **The three-run sample is small.** Two reds across three runs is enough to show the failure sets are disjoint and enough to distinguish flaky from broken by re-running each alone. It is not enough to estimate a flake *rate*.
