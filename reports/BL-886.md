## 1. The retrieval leg meters itself now

The counting was never wrong. `IgClient.http_requests` has been an accurate, receipt-based count since BL-863 — it reads HikerAPI's own `x-hiker-info: {"reqs":N}` rather than inferring from status codes. **Nothing ever wrote it down.**

That is why this survived every pass ever run: **a counter that is discarded looks exactly like a counter that is zero.** Three changes make the two distinguishable.

```python
IgClient.flush_spend(path, *, campaign, label)   # idempotent, no-op at zero
IgClient.unflushed_requests                      # what is owed to the ledger
```

- **Idempotent**, so a flush in a `finally` plus an explicit flush cannot double-charge.
- **Marks flushed only after the ledger write returns.** A failed write leaves the debt *owed*, because losing money quietly is the bug being fixed, not an acceptable failure mode for the fix.
- **The runner flushes in a `finally`**, so a Ctrl-C or a budget break still records what was already spent. The paid loop was split into `_label()` purely so the caller's `finally` always reaches the ledger.
- **An `atexit` guard** warns on stderr if any client exits still owing:

```
ig_client: WARNING -- 9 billed request(s) were never written to spend.json.
Call client.flush_spend(path, campaign=..., label=...) in a finally. This is
the BL-876 leak: the money was spent and the ledger does not know.
```

The runner also **reads the IG price from `record_aux_spend`'s own default** rather than restating `0.0006`, so its printed figure cannot drift from what the ledger actually bills.

**Proved on a real pass**, not a mock — 5 selected, 3 labelled, and the runner wrote its own ledger row:

```

2026-08-01 19:41:38  BL876_VISION  calls=8  ig_usd=0.0048  label=bl872_ranked_speech_pool
```

`ig_billed=8, ig_flushed_to_ledger=8, ig_unflushed=0`. Nothing was recorded by hand.

## Limits

- **$0.8196 of the $0.9210 correction is an estimate, and it is deliberately low.** Unreachable-but-fetched clips are unrecoverable. Treat the ledger as *still* slightly light on the clip path, not as settled.
- **The `max_pages=1` floor assumes each labelled clip cost exactly one call.** That follows from the cap, but I verified the cap by reading the two retired runners' source, not by observing their traffic — no per-call log survives from those passes.
- **The 1,366 figure depends on my attribution of which clips belong to unmetered passes.** It is `labelled_in_library − accounted`, and `accounted` leans on run summaries plus one hardcoded 7 for BL-863's first pass. If another ranked pass ran and left no summary, its clips are wrongly in the estimate — at $0.0006 each, a hundred misattributed clips is $0.06.
- **The proof pass was 5 clips and 3 of them labelled, with 2 failures.** Its own $5.29/1,000 loaded is not a usable rate; the restated figures in §3 come from BL-873's 32-clip pass and bl849's 436-clip log, which is why I did not quote the proof pass as a cost measurement.
- **`$1.96` for the unranked path assumes 1.00 calls per labelled clip exactly** — the same floor as the backfill, so §2 and §3 share an assumption and are not independent confirmations of each other.
- **The atexit guard is best-effort.** It cannot fire on `os._exit`, a hard kill, or a segfault, and it writes to stderr during interpreter shutdown, where output can be lost. It narrows the silent-loss window; it does not close it.
- **`flush_spend` takes the ledger's `filelock` via `record_aux_spend`** while holding the client's flush lock. Single-flush-at-end is the only pattern used, but a caller flushing from several threads would serialise on a file lock, which I have not load-tested.
- **I did not audit every other IG caller for the same leak.** The vision runners are fixed and the walk already meters via `CLIP_LIBRARY` rows; whether every aux flow flushes is unverified.
