## 2. Hole two — and why the prescribed fix was wrong here

`default_fetchers` kept the `IgClient` inside itself, and **a caller cannot flush a client it does not hold**. The module contained **zero** occurrences of `flush_spend`, `unflushed` or `http_requests`: the client's own count of what the vendor billed was unobservable.

`default_fetchers_with_client` hands it back. Both builders share **one** client through `_build_fetchers` — a receipt is authoritative only if the calls went through that client, and my first version built a second one to hand over, which would have reported on a client that made no calls.

### It reconciles. It does not re-record.

The brief says to copy `editor_brief.live_fetchers`: autoflush every 5 calls, `flush_spend` in a `finally`. **That is right there and wrong here**, because the two modules count differently:

- `editor_brief` has **no meters**. Its client is the only counter, so flushing it *is* the record.
- `_run_batch_inner` **already meters every retrieval call** through `meters["ig"]`. Flushing the client as well writes the same calls a second time.

I shipped the literal copy, and the spending proof caught it on the first run: a run that billed **2** requests and reported **$0.0012** put **4** calls into the ledger — a `clip_pipeline_ig` entry of 2 *and* a new `aux` entry of 2. `aux` had never appeared in the ledger's 670-entry history before.

The wrapper now reads `client.http_requests`, compares it with `metered_calls`, and **reports a disagreement**. Nothing in it writes money; `_run_batch_inner`'s own `flush(force=True)` remains the only writer. That is asserted on the **AST**, not on the text — the docstring names `flush_spend` in order to explain why it is *not* called, and a substring check reads that as a call.

Five cap defects in this project have been found by running and none by reading, so the code above is not the evidence. This is:

| cap | spend | billed calls | videos | reconciliation |
|---|---|---|---|---|
| $0.0012 | **$0.0012** | 2 | 0 | *(pre-fix run — this is the one that double-charged)* |
| $0.0030 | **$0.0024** | 4 | 0 | `client 4 == metered 4` |
| $0.0060 | **$0.0060** | 10 | 2 | `client 10 == metered 10` |

Every run **stopped on its cap** and reported it:

```
STOPPED ON THE CAP: $0.0060 spent, the next clip could cost $0.0012, cap is $0.0060.
produced 2   spend $0.0060 of $0.0060 cap   wall 130.4s
  retrieval leg reconciled: client 10 == metered 10
```

**Spend moves with the cap** — $0.0012 → $0.0024 → $0.0060 — and never exceeds it. That is the check that exposed the last defect, where one leg stayed flat at $0.014400 across three different caps.

**The reserve holds.** Under a $0.0030 cap the run stopped at **$0.0024**, not $0.0030: the next call could cost $0.0012 and only $0.0006 remained, so it declined rather than overshooting. A per-call price that is unknown until the reply arrives is exactly what the reserve exists for.

**The copied-tree trap, checked.** `clip_pipeline.__file__` and `spend_ledger.__file__` both resolve inside the real tree; the ledger checked is `clipper finder\spend.json`, and its **mtime moved** on every run. The other `spend.json` files in the tree are dated backups under `backups/` and `scratch/bl855_backups/`, not stray redirects.

**Attribution, honestly.** The ledger delta is *not* my round's spend — other rounds write the same file. The attributable figure is each run's own `Spend this run` line, which meters the calls that went through that run's client. Total **$0.0096 of the $0.05 declared cap**.

## 5. What I got wrong

**Three faults, all mine, all caught by running rather than reading.**

1. **The double charge (§2).** The literal copy of the prescribed fix wrote the same calls twice. Caught by the first capped run, before the second.

2. **I broke four tests by renaming.** Six places introspect `run_batch`'s *source* — three test files and a tracer — asserting the batch computes `bias_for(` and handles `"dry_run"`. Wrapping it meant they read the wrapper and found neither. `inspect.getsourcelines` calls `unwrap()`, so `run_batch.__wrapped__ = _run_batch_inner` restores every one of those reads. A metering wrapper must not silently rewrite what the module looks like to its own tests.

3. **`or` where it should have been `and`.** My wrapper built a live `IgClient` whenever *either* fetcher was absent, so a test injecting only a fake retrieval leg reached for real credentials and a real network on a deliberately stubbed path. Only a call injecting **nothing** is a live run. `test_clip_pipeline_entrypoint` failed immediately.

I also mis-set the `__wrapped__` assignment above the definition it referenced, which raised `NameError` at import — caught at once, moved to module end.
