## 3. The limit, and then the control that used it

**8 positives, 4 judges, a moving bar.** BL-950 found 0 of 25 postable; MEMEBOT-098 found 13 of
30. That supports a large effect and nothing subtle.

So the two apparent winners were re-measured **within each judge** — the same discipline as the
prior finding that 40 clip features were flat against view count *within an account*:

| judge | field | n_post | n_not | med POST | med NOT | **P** |
|---|---|---:|---:|---:|---:|---:|
| BL-950 | `play_count` | 0 | 24 | — | 21,567,469 | *no contrast* |
| MEMEBOT-074 | `play_count` | 3 | 27 | 1,079,382 | 1,295,968 | 0.30 |
| MEMEBOT-086 | `play_count` | 5 | 2 | 798,541 | 646,884 | **0.50** |
| MEMEBOT-074 | `duration_s` | 3 | 27 | 9 | 58 | **0.01** |
| MEMEBOT-086 | `duration_s` | 5 | 2 | 37 | 32 | **0.60** |

**`play_count` is batch composition.** Median play_count per audit: BL-950 **21,567,469**,
MEMEBOT-074 1,295,697, MEMEBOT-086 798,541 — a **27× spread**. BL-950 also contributed 24
negatives and zero positives. Pooled, "postable clips have fewer views" is just *"the
all-negative audit happened to sample much more popular clips"*. Held fixed: 0.30 at n=3, and
**0.50 — exactly chance** — in the other.

**`duration` is circular.** P=0.01 inside MEMEBOT-074 looks decisive until you read that
audit's own verdict column: *"**No** — 58s"*, *"**No** — **74.6s**"*, *"62s"*. Length **was**
the disqualifier. The label encodes duration by construction, and it does not replicate:
**P=0.60** in MEMEBOT-086.

## 5. The loop — the durable deliverable

`clippershq/audit_labels.py`:

```python
from audit_labels import record_verdicts
record_verdicts("MEMEBOT-120", [
    {"clip_id": "...", "verdict": "post"},
    {"clip_id": "...", "verdict": "no", "defects": ["caption cut mid-word", "58s"]},
])
```

It **refuses** what this assembly proved unusable, each refusal a bug already paid for:

- an unrecognised verdict word — `Near miss` was a third word for one axis;
- a `no`/`fix` with **no defect named** — a refusal without a reason is the count nobody can
  act on (`decision_log`'s rule, applied to labels);
- a `clip_id` not in `clip_library` — a label that names nothing fails silently at join time;
- `strict=True` refuses the **whole batch**, so no round half-records an audit.

A clip judged by two rounds keeps **both** rows: the bar moved, and collapsing them would hide
the one thing this file has to preserve. An unreadable library **skips** the check rather than
refusing everything — *"I could not check"* is not *"nothing matched"*.

`tests/test_audit_labels.py` (15 tests) covers the loop and acts as a tripwire on the set:
it must not shrink below 61, every row must name its judge and commit, every refusal must name
a defect, and the `_limits`/`_gap` text must stay attached to the data.

## 6. The real prize: what changes when outcomes exist

`bias_map` biases **song hook windows**, not clips, and is correctly inert at `{}` because no
video has been posted. Three things stand between here and an outcome-driven ranker:

1. **The join already exists.** `LEDGER_JOIN_FIELDS = ("output", "song", "start_sec",
   "end_sec", "clip_id")` — `clip_id` is on every ledger row, so a posted video is already
   traceable to the clip that made it. Nothing needs building here.
2. **`outcome_loop` must receive the view counts** the operator types, keyed to that `clip_id`.
3. **A clip-side term must exist at all.** `bias_map` is song-side; `rank_score` reads clip
   fields and has **no outcome input**. That is the piece that does not exist — and it should
   be built when there are outcomes to feed it, not before, for exactly the reason this round
   found: with 8 positives and a moving bar, anything built now would be fitting noise.

**Real outcomes also fix the flaw that killed both candidates here** — one measurement
instrument instead of four judges and a drifting bar.

## What I got wrong

**My extractor silently dropped an entire audit.** `REPORTS = "/tmp/clippershq-reports/reports"`
is a Git Bash mount; CPython on Windows reads it as `C:\tmp\...`, which does not exist. So
`os.path.exists` returned False, `rows_of` returned `[]`, and **BL-950 contributed zero rows**
to a label set whose entire purpose is not losing labels — the first run reported "35 rows"
and looked fine. Fixed by resolving the clone through `tempfile.gettempdir()`, and the
extractor now **refuses to write** if BL-950 parses to zero rows rather than quietly shipping
a set that lost an audit.

**I shipped the exact defect this repo has a test for, and the test caught it.**
`audit_labels._head_commit()` read `r.stdout` from `git rev-parse` **without checking the
return code** — so a crashed git would have stamped `judged_at_commit` as `"unknown"`… or
worse, an empty string, on every row of a batch. That field exists precisely so a label can be
tied back to the state it was judged at. `tests/test_no_unchecked_stdout.py` flagged it at
`clippershq/audit_labels.py:71`. Fixed by checking `returncode` first. It is the same
"an empty output is not a value" rule I had just written into the module's own docstring for
the library check, applied one function away and missed.

**My first tests passed the module's own validator by accident.** They used synthetic
clip_ids and hit the real `clip_library` check, which correctly refused them. Fixed with an
explicit `known=` injection point rather than by weakening the check.
