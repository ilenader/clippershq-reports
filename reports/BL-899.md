## The method changed, and that is a correction to my own BL-883

I was asked to use BL-883's rewrite-merge. **I used append-with-rev instead**, because the
library says so in its own docstring:

> APPEND-ONLY, WITH `rev` FOR UPDATES. A line is never rewritten. To correct a clip, append
> a new line for the same `clip_id` with a higher `rev`; readers resolve LAST-WINS by
> (clip_id, rev).

and in a comment on its own contents: *"a third of the store is rev-2 rows from the vision
passes"*. Every other backfill in this library appends. BL-883's tool re-reads inside the
lock and byte-verifies, and it works — I re-raced it today at **38 concurrent appends /
12 merges / 0 rows lost**, and the **shrink guard still fires on a planted byte loss**,
refusing and leaving the original untouched. It is still the wrong instrument for an
append-only store that already has the mechanism. Appending needs no shrink guard at all,
because no bytes are ever removed.

## The bed gap, on 830 clips instead of 12

```
n=830 dialogue clips with both levels measured
  mean 12.2 dB   median 8.1 dB
  p10 -0.2   p25 2.7   p50 8.1   p75 15.7   p90 26.3

  speech BELOW its own bed : 88 (10.6%)  -> the duck runs BACKWARDS
  under 3 dB of contrast   : 213 (25.7%)
```

**MEMEBOT-020 found 1 backwards clip in 11 (9.1%). The library says 10.6% of 830.** That is
a prediction from n=11 holding at n=830, and it is the single strongest confirmation in this
line of work: the duck is not merely weak on average, it is **actively inverted on one clip
in ten**, and no parameter can fix a clip whose dialogue is quieter than its music.

The `mean` of 12.2 is dragged by an artifact and the **median 8.1 is the number to use**: ten
clips have `bed_dbfs = −180.0`, `clip_speech._dbfs`'s digital-silence floor, and a "gap"
measured against silence is not a contrast.

## Method

Ran `claim.py brief` first. Re-raced BL-883's tool and re-plant-tested its shrink guard
before deciding not to use it, and stated why. Free pass from the stored `audio_type`, paid
pass through `clip_walk`'s own `iter_stream_medias` and `paging_token` — the envelope is
`{"stream_rows": [...]}` and each media appears twice, so a hand-rolled shallow read takes
the poorer copy (BL-710). Every VAD result checkpointed to disk as produced. Phase B appends
rev+1 rows through `clip_library.append_many`, which takes each shard's lock once. Row counts
asserted before and after. No key printed.
