## 1. The cap: why it was a no-op, and the proof it binds

The governor was never missing. `_drain_source._over_budget()` has always halted the page loop against `stats.run_budget_usd`. What was missing is the number:

```python
stats.run_budget_usd = round(float(spend_cap) - total_spent, 6) if spend_cap else None
#                            ^^^^^^^^^^ config["spend_cap_usd"] — the LIFETIME ceiling
```

`run_budget_usd` was **lifetime ceiling minus everything ever spent**. On BL-914's run that armed it at **$40.83**. The per-run key `--cap` writes, `tiktok_max_run_usd`, appeared exactly once in the tree — in `run.py`'s own FUNNELS table — and was read by no code at all.

The fix is `min()`, which is the only safe way to combine them: a per-run cap must never raise the lifetime ceiling, and the lifetime ceiling must never override an operator asking for a smaller run.

**Proved on a real run, not by reading:**

```
Run cap         : $0.0200  (per-run; lifetime room $40.83)
Draining #editfootball… pulled 3 pages, 90 candidates, 22 qualified so far
Stopping — this run reached your spend cap. Everything found is saved.
ClippersHQ · #editfootball (TikTok) · Leads: 22 · Spent: ~$0.02
tiktok … 92s
```

Target 500 editors, capped at $0.02, **stopped after 92 seconds**. The same command before this round ran 20+ minutes and was still going when a timeout killed it.

## 2. The meter: three vendors, two bounds, and rows written *during* the run

The campaign path — the one tiktok runs — metered only in the tail of `_execute_run`, which a kill never reaches. It now installs **three `IncrementalMeter`s, one per vendor**, because the ledger splits by vendor at three prices and a single blended row would destroy that split.

**Both bounds, as BL-897 established.** `flush_every` bounds *dollars* (25 × $0.0006) and nothing else; a run that makes 24 calls then spends ten minutes in deep-checks holds all 24 unflushed. So the meter also flushes on a **clock** — 30s since its last write — and `tick()` exists for phases that make no metered call at all.

The rows this run wrote **while it was running**:

```
22:54:36  DAYLIGHT/DAYLIGHT_tt_live  calls=1   $0.0006
22:54:36  DAYLIGHT/DAYLIGHT_th_live  calls=14  $0.0140
22:55:08  DAYLIGHT/DAYLIGHT_tt_live  calls=2   $0.0012
22:55:08  DAYLIGHT/DAYLIGHT_th_live  calls=8   $0.0080
                                              = $0.0238
```

A 1-call batch can never fill a 25-call quota: **those are clock flushes**, the exact case a count bound cannot cover. BL-914's killed run wrote `$0.0000`.

The tail is now **remainder-only** (`already_metered=`), clamped at zero, because live rows plus a full tail row is precisely the BL-839 double-count.

## 3. The display — and a correction to my own BL-914 report

Three places priced the same counters differently: the live display charged every call at the LamaTok rate, the governor did its own arithmetic, and the ledger split three ways. `_spent_so_far(stats)` is now the single pricing function all three use.

**All four numbers now reconcile on the proof run:**

| | |
|---|---|
| display | `~$0.02` |
| `_spent_so_far` | 3 × $0.0006 + 22 × $0.0010 = **$0.0238** |
| ledger rows | **$0.0238** |
| LamaTok vendor balance | **3 requests** — exactly `tt_live`'s 3 calls |

### The correction

**BL-914 reported the display was "4x high" — $0.27 against a "vendor-measured $0.0668". That comparison was wrong, and it was my error.**

`$0.0668` was the movement in **LamaTok's** balance. It was never the run's cost. TikHub deep-checks are a *different vendor with a separate balance*, which I did not sample. This round's run makes the shape obvious: 25 data_calls split 3 LamaTok / 22 TikHub, and LamaTok's balance moved by exactly 3 requests.

Applying that split to BL-914 — 450 data_calls, LamaTok billed 111:

```
LamaTok  111 × $0.0006 = $0.0666    <- what I measured and recorded
TikHub   339 × $0.0010 = $0.3390    <- never sampled
                       = $0.4056 true cost, inferred
BL-914 recorded          $0.0668  ->  UNDER-recorded by ~$0.34
```

So the display was closer to the truth than my correction was. The real display fault was blended pricing (charging TikHub calls at the LamaTok rate), not inflation — and BL-914's ledger row understates that run. **`tikhub_client.py` exposes no balance endpoint**, so the TikHub share cannot be sampled the way LamaTok's can; that is why this stands as an inference with its arithmetic shown rather than a second hand-entered correction. Recording another figure I cannot measure is how the first error happened.

## 6. A regression from my own BL-900 change, found by this round's run

The proof run reported **FAILED** despite stopping correctly on its cap:

```
! tiktok reported success but logged 23 error(s); recording FAILED.
Error importing huggingface_hub.hf_api: cannot import name 'BaseFileLock' from 'filelock'
  (C:\...\clippershq\filelock.py)
```

BL-900 moved the error-watch to the root logger so it could finally hear `control`. That was right — and it swept in every third-party library too. `huggingface_hub` cannot load because the repo's own `clippershq/filelock.py` **shadows the PyPI `filelock` package** on `sys.path`, and its 23 import errors were being counted as funnel failures.

Filtering by logger name would be a denylist that grows forever. The honest test is **where the code lives**: a record emitted from inside `site-packages` is a library's problem. Nothing in this tree ships from site-packages, so the filter cannot mask an application error — verified both ways in one probe (a `control` ERROR still counts; a site-packages ERROR is ignored).

The `filelock` shadowing itself is left alone: renaming a module 30+ files import is not this round's work, and it now degrades to a logged warning rather than a false FAILED.
