## 3. The sheet

`clippershq/review_sheet.py` → **`output/REVIEW_100.html`** (754 KB, opens offline).

Per row, numbered 1–100: verdict; **one plain sentence naming the deciding rule** ("rejected
by Views too low: latest 10 posts average 212 views, below the 2,000 floor"); **all nine
rules with their own pass/REJECT and the number each tested**; average views and every post's
own count; post count, followers, recency; bio; email **with its source**; a clickable
profile link; and for each of the 10 posts a thumbnail, its view count, **the drawn line the
filter judged**, and **the caption, labelled NOT judged**.

The rules are shown in a fixed order on every row, so he can scan one rule down 100 rows and
judge that rule on its own — which is the question "which rule is weak" actually is.

**Two ways to open it.** `OPEN_REVIEW_SHEET.bat` starts a local server and marks POST to it.
Opening the HTML directly still works, but there is nothing to POST to, so the page says so in
a banner and keeps marks in `localStorage` with a Download button. A page that silently
dropped training data would be worse than one that never offered to save it.

**Marks are append-only.** A second mark on row 47 is a second line with a later timestamp;
the reader takes the newest. A changed mind is data. Verified end to end before delivery —
served, POSTed, appended with timestamp — then the self-test line was removed so his ground
truth starts empty.

### Why the caption is shown separately, measured

Of the 659 posts carrying **both** a drawn line and a caption, **639 (97%) have a drawn line
that does not appear in the caption at all.** They are not two views of one thing. Judging the
caption is how two earlier filters failed, and the sheet puts them side by side so he can see
it himself rather than take the claim on trust.

### Base rate: **31.0% of the 100 passed**

A filter's precision is meaningless without it, and this project has twice shipped a "signal"
that was the base rate wearing a threshold's clothes.

**And the fresh judgment disagrees with the stored one, which is a finding, not noise.** 20 of

## 6. The ratio rescue: the data does not support it

Reported, **not shipped** — the gate is not opened.

BL-1182 found ~7.5% real editors in the 619 UNSURE rows, all three examples with huge
view-to-follower ratios. The question is not whether editors have high ratios; it is whether
a high ratio is **more common among editors than among what it would drag along**.

| cut | fires on | editors caught | precision | 95% CI |
|---|---:|---:|---:|---|
| ≥10× | 18 | 2 | 11% | [3%, 33%] |
| ≥25× | 12 | 2 | 17% | [5%, 45%] |
| ≥50× | 9 | 2 | 22% | [6%, 55%] |
| ≥100× | 4 | 1 | 25% | [5%, 70%] |
| ≥200× | 2 | 1 | 50% | [9%, 91%] |
| *base rate* | *40* | *3* | *7.5%* | *[3%, 20%]* |

**Every cut's interval overlaps the base rate's.** Three further facts kill it independently:
precision is non-monotonic as the cut moves (overfitting, not signal); the highest ratios in
the sample include **non-editors at 186× and 107×**; and one of the three confirmed editors
has a ratio of **0**, so the rule misses a third of the population it is meant to rescue. A
≥50× rule would fire on **133 of 619** rows to reach an estimated ~29 editors.

Settling this needs labels on the order of 300, not 40 — which is exactly what the review
sheet is built to produce.

## 7. What I got wrong, and what is off-brief

- **A test fixture that disagreed with the producer.** I spelled `verdict["hooks"]` as a list;
  `judge_page` returns an int. All 21 tests passed and the **first real page raised
  `TypeError`**. Fixed both ways — a `_count()` helper that accepts either, and a test that
  reads the real judge's return type rather than my guess.
- **The CSS broke `%`-formatting.** `_SHELL % {...}` read `width:100%` as a format spec and
  died. Doubling every `%` would have "worked" and left a stylesheet nobody could paste in or
  out of; it uses `{{token}}` replacement instead.
- **I shipped a raw `os.replace` into the sheet writer**, and the repo's own guard caught it:
  `tests/test_atomic_io.py` flags every unguarded `os.replace`/`os.remove` in shipping code,
  because on Windows both **fail while another process holds the file open** — measured at up
  to 85% of `master_leads.csv` finalises (BL-927). A review sheet is opened in a browser,
  which is exactly a process holding the file open, so this would have failed on the second
  rebuild while he had it on screen. Now `atomic_io.replace`. The guard did its job; I should
  not have needed it.
- **I ran the suite on the wrong interpreter first**, and `test_ocr_environment.py` caught it.
  Under `py -3.11` (the SYSTEM 3.11) it fails: `rapidocr_onnxruntime` resolves from
  `AppData\...\Python311\Lib\site-packages`, not from `.venv`. Under
  `.venv\Scripts\python.exe` it passes. That test is BL-1185's and it is doing exactly its
  job — this box has two 3.11s and only one of them is the one the brief names. The suite
  result below is the venv run. Worth flagging that earlier rounds' suite runs were on the
  system interpreter, so their greens covered a slightly different environment than they
  implied.
- **I nearly refused a build over a resolver hiccup** in the previous round's code and
  repeated the pattern here in reverse — worth stating that the MX and OCR paths both treat
  *unknown* as unknown, never as bad.
- **Two guards of my own went red on the role decision and I did not silence either.**
  `test_send_superset.py` and `test_meme_send_list.py` both asserted "no non-primary file may
  carry a suppressed address", and `role_inbox` is a suppression reason. The fix is the
  distinction the guard's own docstring already implies: its question is *"can an operator
  reach a certain bounce?"*, and a `contact@` address is perfectly deliverable. A sanctioned
  file is now checked against **the policy it was built with** (`exclude_role=False`), while
  dead-MX and no-route stay absolutely refused for every file — asserted separately, on the
  real classifier, so the exemption cannot widen unnoticed.
- **Off-brief:** the sheet is standalone rather than in the dashboard, because
  `dashboard/server.py` is held by BL-1159. The brief allows this explicitly. Nothing was
  added to the dashboard.
- **Not done:** the sheet shows the frame the OCR read, not Instagram's cover image. That is
  deliberate — the question is whether the OCR read the drawn line correctly, and only the
  pixels it saw can answer it — but it means the thumbnails look like video stills, not like
  the grid he sees on Instagram.
