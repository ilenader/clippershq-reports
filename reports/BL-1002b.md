## 3. The measurement

**One-frame OCR (midpoint), scored on hand labels:**

|---|---|---:|---:|---:|---:|---:|---:|
| **@handle card** | OCR contains an `@handle` | 4 | 1 | 0 | 30 | **80.0%** | **100.0%** |

**The same rules on `vision_on_screen_text`, same labels:**

| signal | TP | FP | FN | TN | precision | recall |
|---|---:|---:|---:|---:|---:|---:|
| third-party watermark | 0 | 0 | **7** | 28 | — | **0.0%** |
| any watermark | 0 | 0 | **17** | 18 | — | **0.0%** |

**The field finds none of them.** Not fewer — none. Seven third-party watermarks are visible on
these frames and the term meant to catch them fires zero times. BL-988 measured the same rule at
P=81.8% / R=45.0%, but against labels derived from the field itself.

### Why the watermark rule fails — and it is not that OCR missed the mark

My first pass reported six misses with the OCR text truncated to 60 characters, which cut off the
evidence. Reading the full strings, **OCR read the brand on 5 of the 6**, garbled:

```
12  'No one, me this winter . Lphanat'                              (ALPHANATIV)
16  '... after using mobile for 7 years: alphanatv'                 (ALPHANATIV)
18  "Who's your favourite ? Isi , 4LPHAnATIV rorite Superhero ..."  (ALPHANATIV)
19  '... but hit the side frame instead trille'                     (TRILLERTV)
26  "... he left that for the panda alpmAMAT"                       (ALPHANATIV)
23  (no brand token in the OCR output)
```

**The signal is in the pixels; the exact-token matcher is what fails.** A small low-contrast corner
logo survives OCR with character errors most of the time, and `@handle`/domain regexes need an
exact token.

Fuzzy-matching against a known brand list gives **P=100% / R=71.4%** — but that list was written
from my own labels, so **it is circular and is an upper bound, not a result.** It shows a better
matcher is worth building, not that one exists. Building it properly needs a brand list learned
from frequent non-account tokens across the corpus, which requires the full pass — the thing this
measurement was gating. **That circularity is the finding, not a footnote.**

### The one clean false positive is instructive

Clip 08 (`matheuxmendex`): field empty, OCR text present, rule fired on `@saprutd`. There is no
handle on that frame — it is OCR mangling the Portuguese subtitle **"asaprata"**. A phantom handle
invented by the reader, which only frame-reading catches.

## 4. Item 2's gate: NOT MET, so no full pass

The condition was *"IF IT CLEARS ~80% PRECISION, run the full pass."*

* **@handle card — 80.0% precision, 100% recall. CLEARS.**
* **third-party watermark — 50.0% precision. DOES NOT CLEAR.**

The watermark signal is the one the gate term needs, so **the 2,661-clip pass was not run,
`ocr_gate_text` was not declared, and no rows were appended.** Two independent sufficient reasons:
the measurement failed its own gate, and `clip_library/` is held by BL-1000 mid-rehearsal where
appended rows would move another round's measurements.

**When it is run, the field must be declared in BOTH `CLIP_FIELDS` AND the provenance map
(MEASURED tier).** An undeclared key reads as `None` through `field()`, and five rounds here have
shipped one half of that pair. `vision_on_screen_text` is never overwritten.

## 6. Item 4: what is now independent

`vision_on_screen_text` and the OCR text are genuinely **independent instruments** — one is a vision
model's description, the other reads pixels. This round shows it two ways:

* **Confirming.** Of 12 clips whose field is empty, **OCR found text on 11 (92%)** — reproducing the
  published 92.3% figure from an instrument sharing no code path with it.
* **Contradicting.** The field's watermark recall is 0.0% against frame labels where BL-988 measured
  45% against field labels. Only an independent instrument produces that disagreement, and the
  disagreement is the useful part.

But independence is not accuracy. **Today the gate gains an independent signal only for the @handle
card.** For the watermark term the independent instrument is currently *worse* on precision (50%),
so **BL-988's drift warning stands: every term still reads the fields it was validated on.**

## 7. What a follow-up needs

1. **Wire the @handle-card signal** — the one thing that cleared. `clip_postable.py`, BL-1004.
2. **Build the brand list non-circularly**: run the pass, collect non-account alphanumeric tokens by
   frequency; the recurring ones (`ALPHANATIV`, `TRILLERTV`, …) are the list. Then fuzzy-match. Cost
   **5.6 CPU-hours**, once.
3. **Re-label at n=60+ with an enriched positive set.** Seven positives fails a gate; it does not
   tune a threshold.
4. **The three-frame variant was not measured.** It was to be priced *if a single frame missed
   watermarks appearing later*. That is not the observed failure mode — the mark was present in the
   sampled frame and misread — so 3× the cost (16.8 CPU-hours) buys nothing against this defect.
