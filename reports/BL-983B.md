## The finding that shaped the round

`clip_pipeline.gate()` **already returns a named reason for every refusal**, and
`gate_report()` **already aggregates them into `{reason: count}`**. Most of the naming this
brief asks for already exists.

**Nobody ever sees it.** `gate_report()` is called in exactly one place —
`clip_pipeline.py:2114` — on the **`no candidates` early-return path only**, and its result
goes into a returned dict that nothing prints:

| what happened | what the operator learns |
|---|---|
| the run produced candidates | **the reasons were never computed at all** |
| the run produced none | they were computed, put in a dict, and **shown to nobody** |

Both failure shapes this project keeps finding, in one function: a guard that could not fire,
and a count whose reason reaches no one. So the work was not inventing reason strings — it was
**building the last mile**, and giving every other stage the same treatment.

### Two rules the module enforces rather than documents

**1. A count without a reason is not actionable.** `drop()` *requires* a reason — there is no
anonymous form, so the API enforces it rather than review. `emitted` is **derived**
(`took − Σdrops`); when a caller also declares `out()`, the difference surfaces as
`unaccounted`. A stage that loses rows without saying so cannot balance its own books:

```
dict_of                          242        0       224   <- 224 row(s) vanished
                                                             with no reason recorded
```

That is the 224-of-242 loss, as it would have looked the day it happened.

**2. Completing is not succeeding.** A stage that took input and emitted nothing, or was
handed no input at all, is flagged `SILENT` — the render at returncode 0, the scanner that
passed on zero files, the poller that read eleven live claims as zero. An **errored** stage is
deliberately *not* also called silent: it already has an explanation, and two lines for one
event is how a summary stops being read.

## What I got wrong

**My first harness proved nothing about planted failure #3.** It routed matching on
`franchise`/`content_genre` and dropped **all 246** clips, so the planted one was
indistinguishable from the background. The log is what showed me — a stage flagged `SILENT`
with a single reason at 246. Re-keyed on `audio_class`, the planted clip became the **only**
drop.

The cause is a real property of the corpus and corroborates MEMEBOT-067's 86.1% park: across
those 400 rows, **`franchise` is None on 373 and `content_genre` on 399**. Any franchise-keyed
rule parks essentially everything. Recorded as a stage `note`, not a drop — those clips *did*
match on `audio_class`; they were never refused, there was simply nothing franchise-specific
to fire on.

**A test of mine passed for the wrong reason and left litter.**
`test_a_write_failure_never_takes_down_the_run` used an absent absolute path; on Windows
`os.makedirs` cheerfully created it at the drive root, so the write **succeeded** and the
assertion failed — after creating `C:\nonexistent-zz`, which I removed. An unwritable path has
to be *made* unwritable (parent is a file), not merely unlikely.
