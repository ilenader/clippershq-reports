**Round:** BL-1551 · **Spent: $0.055251** against a $1.00 cap (80 paid profile calls, the

## THE PARAGRAPH AT THE TOP

**The plan this round was written to execute cannot be executed, and the measurement that
killed it took 80 calls and five minutes.** The free logged-out Instagram profile page —
measured at **76.5% [52.74, 90.45]** in BL-1545 — now returns an **auth wall**: **0 of 80**
real unscoreable rows, and **0 of 5** large institutional accounts that cannot be dead,
across **four different client strings**, every one a 200 carrying ~500 KB with
`loginForm` present and every content marker absent. Backfilling the 15,958 Instagram rows
by *paid* call would cost **$11.02** against a $1.00 cap. **Refused, and the number is
stated so the decision is his.**

**What did work cost nothing.** The bio was never missing from the *paid* response — it
was being thrown away. Three lead-row builders read it, use it for one containment test,
and drop it; and **seven of the nine master appenders never wrote a `bio` column at all,
eight never wrote `secuid`**. That is now closed at **nine call sites through one helper**,
every one proved to resolve at runtime by AST with a planted bound/unbound control. **Every
future row gets a bio and a stable cross-funnel id for $0.00 and no extra call.**

**And 508 bios were already sitting on disk.** Scoreable unjudged rows went from **13 of
13,178 (0.10%)** to **482 (3.66% [3.35, 3.99])** — a 37× increase, and still nowhere near
the ~12,000 the arithmetic promised. **21 of the 482 are likely editors (4.36% [2.87,
6.57])**, far below the harvester corpus's 31%, which is information rather than a failure.

**Of the seven outstanding defects, three were already fixed by BL-1549** — verified by
driving them, not by reading them — one is measured and written into `docs/FACTS.md`, one
is confirmed and named, one is deliberately left with a reason, and the bounced write-back
is driven clean end to end. **10,873 Spotify-family rows remain unanswerable and this round
does not have an answer for them.**

## 3. WHERE THE BIO WAS BEING THROWN AWAY — NINE SITES, NOT ONE

AST over 169 `clippershq/` modules found 28 functions that read a bio-ish key and never
write one. Most are **consumers** — scorers and judges that correctly read a bio without
storing it. Narrowing to functions that also build a **lead row** gave 5, of which 2 were
false positives on inspection (one reads an author dict that already carries the bio; one
writes it as a keyword argument, which a dict-key scanner cannot see).

**THE THREE REAL PRODUCERS:**

| site | writes rows for |
|---|---|
| `clippershq/email_finder.py:440` `find_email` | `instagram:*`, `tiktok:*` |
| `clippershq/meme_finder.py:3156` `_contact_from_enriched` | `instagram:*` |
| `clippershq/twitch_finder.py:957` `find_contact` | `twitch:*` (833 unjudged) |

**AND THE APPENDERS WERE WORSE.** Of the nine functions that write rows into
`master_leads.csv`, **seven never wrote `bio` and eight never wrote `secuid`** — so even
where the value survived the producer, the row template dropped it again.

**Both halves were required. Fixing one alone is a fix that changes nothing** — which is
exactly the trap `writer.py` sets: master's column is `bio`, but `writer.py:2110` fills it
from **`bio_from_feed`**, and `writer.py:2114` fills `secuid` from **`secUid`**, camel
case. The helper writes both spellings on the in-memory result and only master's own names
on the CSV row.

**The fix is one module, `clippershq/profile_fields.py`, called at nine sites.**
`secuid` — present on 99.9% of the bio side and 9.2% of the address side — is now written
too. That is the stable cross-funnel key this project has never had, and it costs nothing.

**Every call site was proved to resolve AT RUNTIME**, because *"the module imports" is not
proof the fix works*: a name looked up only when a function runs raises `NameError` while
the module imports cleanly. The checker was itself proved on planted source — one file
where the name is bound, one where it is not, and one where it is bound only inside a
`try` — and it caught all three correctly before being pointed at real code. **9 of 9 call
sites resolve; 0 would raise.**

## 8. WHAT YOU GOT WRONG

**I ran a patch script twice and it double-applied every edit.** The first run wrote two
files and then refused on the third — but `write_all` validated-and-wrote **per file**, so
a refusal left a half-applied change across the package. Re-running the non-idempotent
script then inserted a **second copy of every call**. Caught by counting call sites, not by
reading the diff. The script now (a) skips an edit whose marker is present, and (b)
**validates every file before writing any**. A half-applied edit across nine modules is far
worse than a refusal.

**My import anchor put an `import` inside a multi-line `from x import (a,\n b)`** and the
file stopped parsing. That is the third time a textual anchor has broken in this repo. It
now locates the insertion point by **parsing** — `ast` gives the statement's real end line,
continuation lines included.

**Two of my own detectors returned the defect they went looking for.** The two-clocks check
searched for a method named `report`, found nothing, and reported **STILL BROKEN** — while
the renamed keys were plainly in the file under `summary_fields`. Then its sub-check for a
shipped note tested for an **exact key** named `note` and missed `summary_clock_note`. Both
were false negatives that would have had me "fix" something already correct. **A detector
that cannot find the thing it judges will confirm whatever you suspected.**

**I over-narrowed a site census and had to widen it back.** Filtering the 28 bio-readers to
"lead-row builders" gave 5, and 2 of those were false positives — a keyword argument and an
author dict that already carried the value. The published figure is **3 producers**, after
inspection, not the scanner's 5.

**And I nearly stated something false about the Spotify rows.** My script printed "carrying
a TikTok handle at all: 10,873" under a heading claiming they have no TikTok identity —
because `tiktok_handle` is the universal handle column and holds an Instagram handle for
Instagram rows. The honest statement is that **no TikTok bio row matches them** (BL-1550
measured that join at 0 of 16,555), not that the column is empty. Corrected here rather
than repeated.

**What I did not do:** I did not buy the 15,450 remaining profile calls. At $11.02 that is
11× the cap, and a round that quietly blows its budget by an order of magnitude to finish a
plan is worse than one that prices the plan and stops.
