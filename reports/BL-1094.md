## Item 4 — every count, verified against an independent hand-count

Twelve counts, each produced twice by routes sharing no code: once the way an application
reads the file, once by a dumb route (raw line split, regex over bytes, directory listing).
Calling the same helper twice is not verification.

**Ten agree. Two disagree, and both disagreements are real.**

### The sixth instance of rows-versus-records, stated exactly

```
memebot/runs.jsonl:  985 lines  ->  518 records   (1.90x)
   385 records carry 2 rows, 41 carry 3, 33 carry 1
   59 legacy rows carry no render_id and no schema at all
   status: pending=421, ok=411, failed:render=61, failed:unretrievable=33, none=59
```

A `pending` row and its terminal row are **the same render, by design**. Of 459 schema-1
records, **365 are OK** — not 411, which is the row count, and not 985, which is the file.
The brief said 747 lines / 355 records; it is now 985 / 518, because rounds are rendering.

The same trap sits in the clip library: **9,212 lines carry 2,731 distinct clips.** 6,481
rows are re-writes of a clip already present (`rev: 1` then `rev: 2`, vision fields filled in
on the second pass). A browser that counts lines reports a library 3.4× its real size.

### Disagreement 1 — the provenance block poisons every text scan

Hand route found 2,732 clips; the parser found 2,731. **The parser was right.**

Every clip row carries a `provenance` sub-object keyed by the *same field names* as the clip,
whose values are the words `declared` / `absent` / `derived` / `measured`:

```json
"provenance": {"account": "declared", "clip_id": "declared", "caption": "declared", ...}
```

So a regex for `"clip_id": "..."` returns a clip whose id is the string `declared`, and
`"account": "..."` returns two accounts named `declared` and `absent`. **Any grep-based
feature over this library — a search box, a filter, a count — picks up the provenance block
unless it parses.** That is worth knowing before someone writes a fast search.

### Disagreement 2 — last-row-wins silently loses four accounts from the filter list

After removing the two provenance ghosts, the routes still differ by four:

```
accounts on the LAST row per clip : 240
accounts on ANY row               : 244
lost: cinemaelevate, darknightjoe, memetheoryhub, theelitescense
```

No clip's account ever *changes* between rows (checked: 0). The four are lost because the
**final** row for those clips has a blank account while an earlier row carried one, and
merging last-row-wins takes the blank. A "filter by account" dropdown built on the merged
records is missing four accounts, and their clips answer to no filter at all.

I measured the same things twice, fifteen minutes apart, on an unchanged HEAD:

caches a count, or prints one without a timestamp and a commit, will show the operator a

## Item 5 — missing media, honestly

### Render outputs

```
470 distinct output paths across 985 ledger rows
   in-repo      EXISTS   353
   in-repo      MISSING   76
   OUT-OF-REPO  EXISTS    40
   OUT-OF-REPO  MISSING    1
-> 393 of 470 (83.6%) would render today; 77 rows must say MISSING
```

The 41 out-of-repo paths point into an **agent scratchpad**
(`AppData/Local/Temp/claude/…/<session-uuid>/…`). That is the batch of 40 the brief names.
They exist today; that directory is session-scoped and is swept. One has already gone.

### Clip media — the ceiling on what can be watched

```
2,731 clips in the library
1,875 .mp4 files in the repo -> 336 distinct library clips (12.3%) have any local file
2,395 clips (87.7%) can only ever be shown as NAME AND METADATA
```

And of the 336 that can be watched:

```
295 have their media ONLY under scratch/   (9.4 GB)
 41 have durable media
 82 of the 295 are ALREADY past the 36h scratch_gc.py sweep age (BL-1065)
```

**The browser can durably show 41 of 2,731 clips.** Everything else is either absent or
borrowed. So the browser must resolve a path *at read time* and label a miss — never cache a
path and trust it.

### Four row states, not two

| state | clips |
|---|---|
| no media — metadata only | 2,395 |
| playable (scratch, may vanish) | 295 |
| playable (durable) | 41 |
| file recorded but MISSING | 77 render outputs |

*"No media"* and *"missing"* are different facts. A browser that draws both as an empty tile
teaches the operator to score both as a bad clip — and that wrong label goes straight into
`clip_verdicts.json`, the one file the entire quality programme depends on. The empty tile is
not a cosmetic problem; it is a data-corruption path.

### The judging queue that actually exists

```
watchable now                    336
  already judged                 242
  UNJUDGED AND WATCHABLE          94   <- what a browser could offer the operator today
  unjudged AND durable             37
```

The brief's premise — *"if he can judge 50 clips while waiting"* — holds, but **only 94 clips
deep**, and 57 of those 94 sit on media that the garbage collector may take. Past 94, judging
needs re-fetch, which needs money, which is a different round. This is the number that should
size the feature, and it is not 2,728.
