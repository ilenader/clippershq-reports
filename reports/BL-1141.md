# BL-1141 — the three wiring defects are fixed, and the system matches songs now

**2026-08-05. $0.0144 spent against a declared $0.30 cap (4.8%). Two real videos rendered
through the production path, both `tier=matched`, both verified off their own pixels.
`scratch/songs.json` untouched. Campaigns unchanged.**

BL-1137 measured this system matching **zero** songs across 2,748 clips at every batch size, and
located three defects without fixing them. This round fixes all three in production, re-measures
the funnel against BL-1137's own numbered prediction, and renders real files.

## Defect 1 — the matcher was called 216 lines before its input existed

`pick_song` ran at `clip_pipeline.py:3680`. `clip_label_text.read_source_line`, which produces
`source_line`, ran at `:3896` and assigned to `rec` (the ledger row), not to `clip` (what the
matcher was handed). `source_line` is not a clip-library field — 0 of 9,723 rows carry one — so
`song_library.hook_line_text()` read `""` on every clip, forever.

**The fix is an ordering.** The render loop's steps are now:

```
a. RETRIEVE                 (the only paid leg)
b. STAGE                    -> src, real_len
c. THE FILE'S OWN EVIDENCE  no-speech · ink band · card · strip · read_source_line   <-- moved up
d. SONG                     pick_song(clip + source_line)
e. config   f. pending row   g. render   h. completion row
```

`clip` is **copied**, not mutated — `clip_for_song = dict(clip); clip_for_song["source_line"] =
src_line.text` — because `clip` is the ranker's own object and a later stage reading a
`source_line` this loop injected would be reading a value the library never wrote.

**It is also strictly cheaper than what it replaces.** Every refusal in step c used to fire
*after* a song had been picked and *after* a `pending` row had been appended, so the ledger
carried planned songs for clips that were never going to render.

### It was seen twice and fixed neither time

```
scratch/bl1130_render.py:200   "`pick_song` reads the LIBRARY record, which has no
                                source_line. Re-run the match on the line we actually read"
scratch/bl1136_render.py:254   "the first version of this script left the line off ...
                                so it fell through to the `none` tier on all five renders"
```

BL-1136's sentence *is a description of production*. Both rounds recognised the bug, fixed their
own throwaway script, shipped, and moved on. `tests/test_source_line_reaches_matcher.py` exists
for that failure mode more than for the ordering itself, and it guards two things, over the AST
so a comment cannot satisfy it:

* **order** — `read_source_line` must be called at a lower line than `pick_song`;
* **wiring** — `pick_song`'s first argument must be a name something assigns `["source_line"]`
  into. Order alone is not enough: BL-1136's first draft had the order right and still handed
  over the untouched record.

**Run against the real pre-fix file from HEAD, the guards catch it at the exact reported lines:**

```
HEAD (pre-fix) order : read_source_line first called at line 3896, pick_song at line 3680
HEAD (pre-fix) wiring: pick_song is handed 'clip' and nothing ever assigns 'clip'["source_line"]
working tree   order : CLEAN
working tree   wiring: CLEAN
```

Each guard is also run against a planted defect in the suite, so it proves it can fail.

## Defect 2 — the format gate judged a field the renderer stopped drawing

`meme_format.classify(caption=…)` convicted clips on the reposter's Instagram caption.
`render_one(label=…)` has taken a `SourceLine` since BL-1130. BL-1137 measured 766 clips (27.9%)
refused for a field nothing draws — and `meme_format.py:89` had predicted it in a comment:
*"A pipeline that drew the SOURCE's line instead of the reposter's caption would keep it."*

`classify()` now takes `line=` and judges **that**; `caption=` remains as the fallback for a clip
whose line has never been read. One helper, `drawn_text()`, decides which string is on trial so
the three text verdicts cannot drift apart about it, and every verdict carries `judged_on` —
because "PROMOTIONAL on the caption" and "PROMOTIONAL on the drawn line" are different facts and
only one is a reason not to ship.

**All three text verdicts moved together, deliberately.** Keeping PROMOTIONAL on the caption as
a proxy for "this page posts catalogue prose" would have kept 833 refusals alive for a signal
about the *page* dressed as a verdict on the *clip*.

`clip_pipeline.source_line_of()` resolves the line in priority order — `source_line` (the
5-frame consensus that will actually be drawn) then `vision_on_screen_text` (the vision model's
read of the same words, stored on 1,929 of 2,748 rows, and all the SELECTION gate has). It never
falls back to `caption`. **Absence returns `""` and callers must read that as UNKNOWN, not
EMPTY**: 819 clips have never had their text read by anything, and refusing them for having no
line would refuse them for never having been looked at.

## Defect 3 — the blank-frame check measured the thumbnail; its reason accused the clip

`cover_frame_is_blank` reads `layout`, measured from the **cover frame**. The refusal printed
*"no imagery to read"* — a claim about the clip. BL-1137 hand-read 135 such refusals and found
**116 carry a vision-model description of real footage**.

Both halves are fixed. The reason now says what was measured:

> `cover frame is a flat field of colour and nothing has described the video behind it`

and the refusal **withdraws** when a reader that watched the video describes it
(`has_seen_imagery`, which reads `vision_scene`). It still fires unchanged on a clip nothing has
ever looked at — the case the term was written for. Absence is never a verdict: `has_seen_imagery`
can only ever *withdraw* a refusal, never make one.

`tests/test_clip_pipeline.py::test_blank_cover_frame_is_gated_out` asserted the old semantics and
**went red on this change, which is the right outcome** — its fixture defaults
`vision="an epic fight scene"`, so silence there would have meant the new rule was never
exercised. It now asserts both arms.

## A fourth thing, found by fixing the first three

The first production run after the fix printed:

```
UNACCOUNTED  render   5 row(s) vanished with no reason recorded (in 8 - dropped 0 - out 3)
```

Clips refused on their own file — speech, no card, unreadable line — `continue` between the
render stage's `took` and its `out`, and **nothing ever counted them**. That is `decision_log`'s
own rule 1 ("a count without a reason is not actionable") failing on the module that consumes it.

**It is pre-existing, not a regression** — I checked HEAD, where those refusals also `continue`d
uncounted. It had gone unseen because the gate admitted 89 clips and almost none got that far;
admitting 592 made it fire immediately. It is now bucketed by reason and dropped in the `render`
stage, and the run reports `no silent stages, nothing unaccounted for`.

BL-1137 predicted, by *substituting* a field into the old code: **622 gated, 7 matched.**
Running the **fixed** code over the same library:

**The match count hit on the nose. The gate is 30 lower, and the 30 are fully decomposed:**

```
in arm D (the simulation), NOT in the fixed gate : 30
in the fixed gate, NOT in arm D                  :  0
   26  the line is too long to be a hook, or to be drawn legibly
    4  text is hashtags, a handle or a credit, not a hook
```

These are clips whose **caption** was a clean hook — so BL-1137's simulation, which only
re-asked on the line when a caption reason had already fired, left them passing — but whose
**drawn line** is 124–239 characters against a 90-character label, or a credit fragment (`*Me`,
`FD`). The fixed code judges the line always, so it refuses them. **The simulation was wrong, in
one direction, for a nameable reason, and the fix is the stricter and more correct of the two.**

## The walk cap — should `MAX_GATE_PER_TAG` move?

**Yes, and it costs nothing but minutes.** BL-1137 found 103 of 219 walked clips (47%) were never
gated at all — not refused, unexamined — because `scratch/bl1133_walk.py:72` sliced
`walked[:MAX_GATE_PER_TAG]` at 8 per hashtag (BL-1136 used 16). The cap exists because the media
gate is "free but slow".

**Priced this round:** the library-side gate is 0.65 ms/clip, and the media gate — download,
speech measurement, OCR — runs about 3 s/clip from the render run's own wall clock. So the 103
unexamined clips are **roughly five minutes of local CPU and $0.00**, against clips whose
retrieval has *already been paid for*. That is the wrong side to economise on.

**Two caveats, stated rather than buried.** The constant lives in the scratch walk scripts of past
rounds; **production `clip_walk.py` has no such cap**, so there is nothing in the shipped code for
me to raise. And I did not raise it in those scripts: they belong to closed rounds, and changing a
finished round's instrument would silently invalidate the numbers it published. **The next walk
round should set it high enough not to bind, and say what it set.**

## The honest uncertainty

`source_line_of` returns `vision_on_screen_text` at SELECTION time and the renderer reads the
5-frame OCR consensus. **The two can disagree**, and this round shows it doing so: the ranker
offered 7 servable clips, and the real OCR of the ones that reached it did not always fire the
same rule. That is why `servable_by` is documented as ADVISORY — it orders and drops nothing, so
a false positive costs one wasted retrieval while a false negative costs the batch its matchable
clips. **The agreement rate between the two reads is still unmeasured.** It is the obvious next
measurement and it needs no new code.

`592` and `7` are counts on that proxy at selection. The two rendered videos are not a proxy.
