## 1. THE GATE — I counted the pages first, as instructed, and the count kills the experiment

Instrument: `scratch/bl1246_gate.py` (selftest **18/18**, with both controls).

The brief: *"Report the count of such pages first; if it is tiny, say so and stop rather than
building machinery for six clips."*

**Inputs, every one read from a file and reported before use:** `bl1240_iter{1,2,3}.jsonl` (50/52/50),

### Where vision cannot decide

| | n |
|---|---:|
| browser returned **UNSURE** | 11 |
| chipped "Too much dialogue" **and zero caption band on any tile** | **18** of 36 dialogue chips judged |
| in both | 3 |
| **population** | **26 pages** |

The 18 include the three the brief names — `roastoday`, `crustytrap`, `memezar` — and fifteen
more. So it is not six clips. It is 26.

### The base rate, computed before any system number

25 of the 26 carry a mark. **He wants 3 of them** — `hexamv`, `logicpov.ig`, `scenevault01` —
so the incumbent rule *"reject everything in this bucket"* scores **22/25 = 88.0% [70.0, 95.8]**.

### And now the number that ends it

The registered bar is: a test ships only if its interval's **lower** bound clears the base rate's
**upper** bound — here **95.8%**.

> **A PERFECT 25 of 25 has a lower bound of 86.7%. It does not clear 95.8%.**
> **At n=25 there is no score — not even a flawless one — that could ship.**

A perfect test would need **n = 89** pages of this kind. There are 26. And the ceiling on the
whole idea is **3 pages**: that is everything audio could rescue even if it were perfect.

**So the experiment was not run.** Measuring it would have produced a number with no decision
attached — which is precisely the failure mode the brief cites in MEMEBOT-085 and asks me to
check for. Applying that check to a *proposed* experiment costs nothing; applying it afterwards
costs the round.

**This is not "audio does not work".** It is "this population cannot answer the question". The
dialogue category as a whole (n=31, base 52.6% [37.3, 67.5]) **is** winnable — a perfect score
there clears easily. It is the vision-blind sub-bucket, with its 88% incumbent, that is not.

## 7. WHAT I GOT WRONG

**I crashed the first supply run after one billed call, and the ledger never got it.** I read
`suggested_profiles`' return as a list of raw API dicts; it returns `(dict_keyed_by_handle, err)`
and does not raise. The client warned exactly as designed — *"1 billed request(s) were never
written to spend.json … the money was spent and the ledger does not know."* **That call is real:
true attempts are 79 and true cost $0.0474, of which $0.0468 reached the ledger and $0.0006 did
not.** Fixed by reading the documented shape and by moving the flush into a `finally`.

**I filed my claim without declaring `spend.json`.** `IgClient` arms autoflush by default
whenever a real config loads, so the first call would have written a file I had not declared —
the same class of error as the round that wrote `suppress_mx.json` undeclared. Caught before any
call and re-filed with `--force`; re-filed once more to add the `.tsv` and `.xlsx` the brief
requires. Three filings for one round is noisy, and the alternative was an undeclared write.

**I raced another round for an id.** I checked `BL-1245` was free, spent thirty seconds building
the claim command, and by then another round held it. Re-filed as BL-1246. The registry refused
correctly; had it not, two rounds would have shared a report id.

**Two of my own assertions were wrong and the code was right.** A perfect 8/8 *does* clear a
67.5% bar (0.6756 > 0.675) — 7/7 is the real boundary, and both sides are now pinned. And I
transcribed BL-1240's iteration 3 as 50 rows when it is 48 scoreable; my own reproduction guard
caught it by refusing to accept 84.0% as 83.3%.
