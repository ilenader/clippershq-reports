# BL-666 — The reviewer note layer: the machine writes a note, the human still decides

**2026-07-24** · Base `origin/main` `5c667b25` · Branch `checkpoint/BL-666` @ `d24e689`, **verified pushed** · Tags `pre-BL-666` / `post-BL-666`

**One line:** every pending clip now carries a note, written by the evaluator and read by the reviewer, that says what the machine found, what it could not check and why, why it thinks what it thinks, and (for a machine-certain rejection) a clipper-language draft the reviewer can edit and send. **The bot decides nothing.** Nothing changes a clip's status, earnings or payout; nothing is ever shown to a clipper; auto-reject stays off.

The point is time, not automation: clip review costs roughly 32 owner-and-reviewer hours a month across ~2,300 clips. A note that pre-gathers the facts and pre-writes the rejection text takes a bite out of that without touching a single decision. It is worth building even if auto-rejection never arrives, and R-2's 11.05% false-rejection rate says it may not.

## PART 1 — the note layer (`src/lib/reviewer-note.ts`, pure)

`composeReviewerNote(rules, results, meta, platform)` consumes the verdicts `campaign-rules.ts` already produces (`would_reject` / `would_pass` / `cannot_evaluate` / `rank_review`) and returns a note with:

* a **headline**, a **suggestion** (`likely_reject` / `look_closer` / `nothing_flagged`) and a **confidence** (high / medium / low);
* **MACHINE CHECKS** — each checkable rule with its verdict and a one-sentence reason;
* **FOR YOUR EYES** — the human-only requirements, surfaced not hidden (78 of 86 production rule lines are `HUMAN_ONLY`, so a note silent on them would be silent on most of the rulebook);
* **WHAT I COULD NOT SEE** — every `cannot_evaluate` listed separately with its reason, because a clip whose sound was unreadable and one whose sound was wrong are entirely different situations and are never collapsed;
* **MY THINKING** — why it thinks what it thinks, and for every certain rule that fires, the failure mode that could make it wrong;
* **METADATA HEALTH** — when nothing reached the evaluator, it says so as a pipeline gap on our side, never as a signal about the clip. This is today's live case: all shadow rows have `captionPresent = false`, so most notes currently say exactly this, and that is correct.

**Two corrections over a naive port, forced by the REAL evaluator.** The reference `reviewer_note.py` assumed `HUMAN_ONLY` rules return `rank_review`; the production evaluator returns `cannot_evaluate` for them. Ported blindly, all 78 human-only lines would have been dumped into "WHAT I COULD NOT SEE" — collapsing "a human must judge this" with "I couldn't read the data", the exact collapse the brief forbids. So the composer routes human-only rules to FOR YOUR EYES by their enforcement, and keeps only genuine machine blind spots in WHAT I COULD NOT SEE. Second, a campaign whose rules are *all* human-only now reads **"No machine-checkable rules on this campaign; every requirement here is human judgement"** (`look_closer`), never a false "nothing flagged", and the metadata-gap line is suppressed because no machine rule needed the metadata. **This second bug was found by running the composer against a real live clip** (a 6-rule all-human-only campaign was reading `nothing_flagged` with a contradictory gap line); it is now covered by a regression test.

## PART 2 — the draft reply (`buildDraftReply`, id-free by construction)

For a machine-certain rejection it composes a clipper-language draft the reviewer edits and sends by hand. **It never contains a raw id.** A caption rejection names the `#`/`@` tokens (which the clipper is meant to include); a sound rejection uses a fixed phrase ("the clip isn't using the campaign sound…"), never the evaluator reason, which carries the 19-digit sound id. The test asserts `/\d{7,}/` is absent from every draft it produces. **Nothing is sent by the system; the clipper never sees it until a human sends it.**

## PART 3 — storage (additive, on the shadow table, never on Clip)

Four **nullable** columns on `rule_shadow_decisions`: `noteText` (the rendered plain-text block, for audit), `noteJson` (the structured note the card renders), `noteSuggestion`, `noteConfidence`. Added to `prisma/schema.prisma`, client refreshed with `npx prisma generate` only, and applied to production with `ADD COLUMN IF NOT EXISTS` through `scripts/run-schema-sql.js` (never `prisma migrate`). The `Clip` model is untouched; every existing row keeps null and is byte-identical.

## PART 4 — render (owner + reviewer only), grep-proven

`ReviewerNoteCard` renders on **PENDING clips only** in `/admin/clips`, fetching the note from the `CLIP_VIEW`-gated endpoint. There is no clipper route to any of it:

```
grep for reviewer-note / ReviewerNoteCard / composeReviewerNote outside owner/reviewer surfaces:
  NONE outside owner/reviewer surfaces
ReviewerNoteCard imported by any non-admin page:
  NONE outside admin
endpoint gate: requireOwnerOrCapability("CLIP_VIEW")
```

**Accessibility (reviewed by accessibility-lead, all applied).** It is static advisory furniture, so it carries **zero** live-region semantics (no `role="alert"`, no `aria-live` on the card) — the one exception is the polite copy-confirmation. One heading per card (the headline, `h4`); section labels are `<p>` associated to their `<ul>` via `aria-labelledby`, never headings; the suggestion pill and every verdict marker carry three redundant channels (word + distinct-silhouette lucide icon + border) so they survive grayscale; the draft reply is a real editable `<textarea>` inside a collapsed `<details>` (zero tab stops until opened) labelled "Draft reply (not sent automatically)" with an `aria-describedby` hint. Grep gate on the component: **0 positive tabindex, 0 `role="alert"`, 0 bare `outline-none`, 0 dashes-as-bullets.**

## PART 5 — runs on every submit

The submit block's `if (rules.length === 0) return` is gone: the evaluator and note now run for **every** submit. A campaign with no machine rules gets a note that says so plainly ("No machine-readable rules on this campaign"), which is useful to a reviewer, rather than being absent. This widens BL-659's write gate — `rule_shadow_decisions` now takes a row per submit — but the false-rejection query filters `wouldReject = true`, so the extra no-rules rows (`wouldReject` false) do not affect the rate.
