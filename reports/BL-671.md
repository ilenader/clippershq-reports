## PART 1 — the movement was MOVED, not re-typed

**The file the owner likes: `src/app/preview/preview-campaign-row.tsx`** (the signed-out landing carousel, BL-370/374/377/385). Its drag works like this: mouse-only pointer handlers (`pointerType !== "mouse"` returns early, so touch keeps the browser's own momentum); a press records `startX` + `startLeft`; a move past **8px** flips it to a drag, takes pointer capture and sets `scrollLeft = startLeft - dx`; pointer velocity is low-passed 0.7/0.3 as you move; on release, if the flick is faster than 0.15 px/ms it glides on under rAF with 0.9 friction per 16ms frame until it drops below 0.02 px/ms; the glide is cancelled by any new press, wheel, keydown or focus, and never runs at all under `prefers-reduced-motion`, read live at release. Native image and link dragging is killed by `draggable={false}` plus a `dragstart` preventDefault on the scroll container.

**The port.** That entire block was lifted out into a new shared module, **`src/lib/use-drag-scroll.ts`**, and BOTH rows now import it. Not a copy: one engine.

```
preview-campaign-row.tsx   -145 lines   const { dragHandlers, grabbing, scrollByDir } = useDragScroll(scrollerRef, updateEdges);
CampaignsRedesign.tsx       +12 lines   const { dragHandlers, grabbing, scrollByDir } = useDragScroll(scrollRef,   updateEdges);
```

Both spread `{...dragHandlers}` and `dragScrollClassName(grabbing)` onto their scroller. The feel is identical **by construction** and cannot drift apart later, because there is only one copy of the physics left in the repo. The harness asserts this from the source text: both files import `@/lib/use-drag-scroll`, both spread the shared handlers, and **neither retains any private drag physics** (no `requestAnimationFrame`, no `setPointerCapture`, no `pointerType` anywhere in either component).

**The bug, killed.** Dragging the Completed row grabbed a card's **photo** and dragged the picture because native image/link dragging was never suppressed there. The engine calls `e.preventDefault()` on `dragstart` at the container. `dragstart` **bubbles**, so one handler cancels the drag of every descendant `<img>` and `<a>` and `MiniCard` needed no edit at all. Belt-and-braces `select-none` and `[&_img]/[&_a]:[-webkit-user-drag:none]` — verified present in the shipped CSS bundle, not just in the source:

```
.[&_a]:[-webkit-user-drag:none] a,.[&_img]:[-webkit-user-drag:none] img{-webkit-user-drag:none}
.cursor-grabbing{cursor:grabbing}   .[&_*]:!cursor-grabbing *{cursor:grabbing!important}
```

**Drag threshold: 8px.** A press that moves **more than 8px** scrolls the row and its trailing click is swallowed; a press that moves **8px or less** stays a plain click. So a tap does not need a perfectly still finger, and a drag never opens a card.

## The a11y review, and what I did NOT fix

The accessibility lead ruled on the **shipped** code. Two blocking findings, both **fixed**:

* **M1 — a real bug I introduced by porting.** `endDrag` is bound to `pointerCANCEL` as well as `pointerup`, and a cancel (right-click mid-drag, alt-tab, browser gesture takeover) is followed by **no click**, so the click-suppress latch stayed armed and could silently swallow a later **keyboard Enter** on a card link (SC 2.1.1). Now disarmed first and guarded by `e.detail === 0`, so only a click a pointer actually made is ever swallowed. My harness had passed this for the wrong reason (synthetic clicks carried no `detail`); it now defaults `detail: 1` and carries three explicit regressions for it.
* **M2 — a contrast regression I introduced.** Moving the `+2%` pill onto the new card surface took it to **4.17:1** at rest and **3.90:1** on hover, under the 4.5:1 SC 1.4.3 bar for 10px text. Now solid accent with the app's established dark-on-accent ink at **5.86:1**, theme independent.

Also applied: `py-3` (44px target, SC 2.5.5 AAA) and an sr-only `+2%` so the visible glyph survives into the accessible name (SC 2.5.3). Confirmed passing as written: label 18.40:1, icon tile 4.50:1 rest / 3.59:1 hover against the 3:1 bar, focus ring 5.64:1 on the `--bg-secondary` offset (the lead independently found `--bg-page` is referenced 38 times in this repo and **defined nowhere**, so a ring offset using it would silently do nothing — both buttons use `--bg-secondary`, the aside's real background). `select-none`, `cursor-grab` and killing the glide outright under reduced motion were each ruled correct with no criterion breached.

**Deferred to BL-672, consciously, NOT cleared.** The lead raised two findings on the arrows: `opacity-0` at the extremes leaves a fully named button in the accessibility tree with nothing saying it is unavailable (SC 4.1.2), and `hidden sm:grid` leaves a sub-640px or 400%-zoom **mouse** user with a live drag, a suppressed scrollbar and no visible non-drag affordance (SC 2.5.7). Its fix is `aria-disabled` + `opacity-35`, rendered at every width. **Both are inherited from BL-651 and both would visibly change the arrow behaviour this brief explicitly ring-fenced**, so I did not touch them. The overstating "a11y (reviewed)" header comment in the file has been corrected to say so rather than imply the arrows were cleared. Also deferred and logged: scoping `select-none` to the drag (it blocks copy and select-to-speak on the only surface rendering these figures, but unconditional is exactly what the landing carousel does, and parity was the explicit ask); `aria-describedby` on the group; a `document`-level pointerup fallback if `setPointerCapture` throws; and the light theme, where the accent glyph on a tint reads 2.88:1 — latent only, since `toggleTheme` is destructured at `navbar.tsx:54` and never called anywhere, so light mode is unreachable without hand-editing localStorage. Three of the six specialists the lead dispatched never returned; it ruled on their questions itself and said so rather than withholding.
