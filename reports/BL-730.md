## The answer

**It is not network variance, and the floor is not the cause — it is a consequence.**

The mechanism: **individual website fetches run to 85s, 141s, 165s and 218s despite a
10-second timeout.** One such fetch exhausts the 30s per-channel watchdog
(`DEFAULT_MAX_SECONDS_PER_CHANNEL = 30.0`), which records `filter_reason='timeout'`. In the
759s run, **20 slow fetches account for 2,076 of 2,287 total fetch-seconds.**

The floor matters only because it changes *which sites get fetched*: lower-viewer streamers
lean on link aggregators and affiliate smart-links, and those are redirect chains.

## The mechanism, in the code

`clippershq/enrich_links.py:266-281`. The function already splits the timeout and documents
why:

```python
_t = timeout if isinstance(timeout, tuple) else (
     min(5.0, float(timeout or 10.0)), float(timeout or 10.0))
resp = getter(url, timeout=_t, headers={"User-Agent": _UA},
              allow_redirects=True)
```

Its comment states a scalar timeout "is really 'up to 10s connecting PLUS up to 10s reading'
= 20s per page … scrapes of 214s and 215s were measured on 2026-07-28", and claims the split
"caps a page at ~13s".

**That cap does not hold, for two reasons, and `allow_redirects=True` is the first:**

1. **In `requests`, a timeout applies per request in a redirect chain, not to the chain.** A
   20-hop affiliate chain gets 20 × (5s connect + 10s read). "~13s per page" is true only for
   a single hop — which is exactly why the slow hosts are redirectors.
2. **The read timeout is per socket read, not total.** A server trickling one byte every 9
   seconds resets the clock on each read and holds the connection open indefinitely.
   `requests` has no total-elapsed bound.

A 218s fetch is fully explained by either; the host list points at the first.

**Both BL-728 candidates collapse into one causal chain:**

> lower floor → thinner streamers → more link-aggregator and affiliate URLs in bio → longer
> redirect chains → per-hop timeout multiplies → 30s watchdog fires → `filter_reason='timeout'`

Network variance is the *third* factor, not the first: it decides whether a given chain stalls
on a given day, which is why the same categories vary run to run.

## Recommendation — diagnosis only, as asked

Nothing was changed. If you want the smallest next step, it is not a floor decision and not a
timeout tune:

1. **Bound the whole fetch, not each hop.** Either `allow_redirects=False` with a manual hop
   loop under one shared deadline, or a wall-clock deadline checked between hops. The per-hop
   budget is the defect; the 10s value is fine.
2. **Then** re-measure the floor question. On present evidence a lower floor costs timeouts
   *because* of the unbounded chain — fix the chain and the floor's cost may largely vanish,
   which would change the decision you are about to make.
