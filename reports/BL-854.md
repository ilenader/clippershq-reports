## 2. Where money leaks

I swept for the four shapes named in the brief. Two are real, one is structural, one is closed.

### LEAK 1 — a paid vision response that is written nowhere, and therefore re-paid forever

`bl849_label.py`:

```python
got = parse(raw)
if not got:
    logf.write(...)     # logged
    continue            # <- the library is NOT touched
```

The call has already completed and `spent += cost` has already run. Because nothing reaches the library, `vision_scene` stays empty — and the next run's `todo` filter is *exactly* `not CL.field(rec, "vision_scene")`. **Those clips are selected again and paid for again, every run, forever.**

Measured from the pass's own log: **23 of 380 responses were unparseable — 6.1% — costing $0.0570.** At scale that is **$0.15 per 1,000 clips, recurring on every re-run**, and it is the precise shape the brief asked me to look for: a billable outcome with no negative cache.

The same `continue` guards `HTTPError` and a bare `except Exception`. A 429 or a timeout after generation is billed by the provider and recorded nowhere.

### LEAK 2 — a retrieval that cannot reach its clip pays in full and returns nothing

With `max_pages=2`, a clip deeper than page 2 costs **two calls and yields no video**. From §3 that is **8.1% of the library**, i.e. **$0.10 per 1,000 clips** of pure waste. Small, but it is the one cost that grows as the library ages.

### STRUCTURAL — paying before filtering, and it cannot be fixed

The walk's three skips (`have`, `seen`, library index) filter clips *inside a page that has already been fetched*. If page 1 of an account is entirely clips you already hold, you paid $0.0006 for nothing. This is not a bug: there is no way to know a page's contents without buying it. Worth knowing, not worth fixing.

### 404s and zero-payloads are billed — already proven, and the counter is honest

`_request()` increments `http_requests` **before** the response is seen, so a 404, a 429 and every retry all count and all bill. The ledger carries a `PROBE:TRACK_404_BILLING` entry, so someone has already paid to confirm this. There is **no negative cache anywhere on the clip path** — a dead id is re-bought on every run that reaches it.

## 3. Retrieval depth — measured, and `max_pages=2` is about right

The 55/40/5 projection has never fired because MEMEBOT-010's 13 retrievals all hit page 1. Modelled instead over all 2,003 clips, by counting how many library clips from the same account are newer:

```
page 1    1530   76.4%          cum  76.4%
page 2     311   15.5%          cum  91.9%
page 3+    162    8.1%   <- unreachable at cap=2
```

Ages: p50 **33 days**, p90 362, max **2,045**, and **10% older than a year**.

| cap | calls / attempt | success | calls / success | $ / success |
|---|---:|---:|---:|---:|
| **2 (current)** | 1.236 | **91.9%** | 1.345 | **$0.00081** |
| 5 | 1.376 | 95.7% | 1.438 | $0.00086 |

**Keep `max_pages=2`.** Going to 5 buys 3.8 more percentage points of reachability for 6% more per success — defensible either way on money, and the real argument against it is wall clock, not cash. What actually matters is that **the ~8% of clips you cannot reach should be excluded by the selector before retrieval is attempted**, not discovered by paying twice for nothing.

**This is a lower bound.** Rank is computed over clips *in the library*; the live feed also contains posts we never stored, so true depth is worse. Measured 76/16/8 against a projected 55/40/5: more page-1 than feared, but a **deeper tail than projected** — 8.1% versus 5%.

## 4. Rate limits

### HikerAPI — no limiter at all, only a per-call sleep

There is no token bucket and no shared limiter. `_request()` sleeps `polite_delay_ms` (150 ms) then fires. Discovery, walk and retrieval are all **single-threaded**, so within one process that self-paces to about **6.7 requests/second**.

**Two concurrent clip rounds do throttle each other, and nothing notices.** Each process has its own `IgClient` with its own 150 ms delay, so two rounds simply double the rate against a shared quota. This is the MusicBrainz shape the brief asked about — and it is **worse here**: `musicbrainz.py` at least has a real process-local limiter (`_state_lock`, `_inflight`, reserved slots ≥ `min_interval` apart). `ig_client` has a `threading.Lock` that guards **only the counter increment**, not the request.

**On a 429:** raise `_RetryableHTTP` → tenacity retries up to `max_retries=3`, honouring `Retry-After` capped at `max_retry_after`. **Every retry is billed**, because the counter increments before the send. So one rate-limited call can cost 3× and still fail. Under two concurrent rounds, 429s become likely and each one costs money.

### OpenRouter (vision) — no pacing, no retry, no 429 handling whatsoever

Grepping `bl849_label.py` for `sleep`, `retry`, `429`, `Retry-After` returns **nothing**. A rate-limit response is caught by the bare `except HTTPError: continue`, the clip is silently skipped, and — per LEAK 1 — it is re-paid next run. Two concurrent vision passes would collide with no backoff and no coordination.

## 5. The vision pass

**It never re-labels.** `todo` is built as `[... if not CL.field(rec, "vision_scene")]`, so an already-labelled clip is skipped before any call. Confirmed in source and consistent with the library: 380 labelled, no clip carries two different `vision_model` values.

**An interrupt is safe, and deliberately so.** It appends per clip — the row is written and flushed immediately after each response — so a kill loses at most the one in flight. The file header says exactly this: *"Appends per clip, so a kill keeps everything already paid for."*

**Declines are stored, so they are not re-paid.** 356 of 380 declined to date a clip, and every one still writes `vision_scene`, `vision_beats` and `vision_control_declined`. Only the 23 **unparseable** responses fall through the gap (LEAK 1).

## 6. The duplicates are not paid waste

On the snapshot: **2,509 rows, 2,003 distinct clips, 506 duplicate rows (20%)**. INFRA-007 saw 32% on a smaller library; the shape is the same.

They are **rev bumps, not re-fetches** — rev 1: 2,030, rev 2: 462, rev 3: 17. Comparing each clip's first and latest revision:

| what changed between rev 1 and latest | clips |
|---|---:|
| `vision_scene` / `beats` / `title` / `model` filled | **344** |
| `franchise` filled | 138 |
| `media_renditions` changed | 19 |
| `play_count` changed | 14 |
| **any immutable core field changed** | **none except the below** |

**344 of 492 (70%) are the vision pass writing labels back — free, local, zero API calls.** The append-only log with last-wins-by-rev is doing exactly what it was designed to do; counting those rows as "duplicates" over-states the problem.

Only **19–33 clips** show evidence of an actual re-walk (renditions and view counts legitimately change on a re-fetch). At ~12 clips per page that is a couple of page buys — the page-1-all-known structural cost, not a dedup failure. **The walk does not re-retrieve clips it already holds.**

One genuine anomaly: **one clip's `posted_at` changed between revisions.** That field is immutable; a post cannot change when it was posted. One row, so not a cost issue, but it means some path is overwriting an identity field. BL-855 is separately diagnosing the row/clip gap and should be told.

Ranking *before* the vision pass rather than after would cut both the dominant cost and the dominant delay by the selection ratio.

## Limits

- **Nothing was changed and nothing was run.** No paid call, no network request. Every figure is from the ledger, the library snapshot, or source.
- **The retrieval depth model is a lower bound**, computed over library-internal rank. The live feed contains posts we never stored, so real depth is worse than 76/16/8. It is a model, not 2,003 measured retrievals — the 55/40/5 projection remains unfired and so does mine.
- **Cost per finished video is a projection**, because only 3 finished videos exist. The marginal figure is solid; the fully-loaded ones depend entirely on a selection ratio nobody has fixed yet.
- **Vision wall time is derived from file timestamps** (`ctime` → `mtime` on the run log), not from instrumentation inside the pass. 13.3 s/clip is an average over a run that may have stalled.
- **The 23 unparsed responses are counted from the pass's own log**, so they are what that run recorded. If an earlier pass had a different parse rate, the 6.1% moves.
- **Three rounds are appending to `clip_library/` as I write.** The snapshot is `2,509 rows / 2,003 clips` at read time and is already stale.
- **I did not verify the 429 path against a live 429.** The billing claim follows from the counter incrementing before the send, which is source-evident, not observed.
- **I did not audit memebot's render stage for cost** beyond confirming it makes no API calls; its ffmpeg wall time is not in the table.
- **BL-855 is separately diagnosing the row/clip gap.** I answered only the paid-waste question and did not duplicate their cause analysis.
