The table gained two columns — the original filename and **what we changed** — alongside the
permalink, `record_id`, song and applied hook window it already had.

**The change line is MEASURED from the two files**, by `ffprobe` on each half, not restated
from the plan. The ledger records what was *intended*; a plan that silently failed to apply
is exactly the class of defect this project keeps finding, so the column answers the second

02  trim 17.3s -> 15.2s; 1080x1920 unchanged;        template white_frame; audio mute-and-replace

Two things fall straight out of reading the column, neither of which was visible before:

- **8 of 12 land on exactly 20.0s** — the duration ceiling is binding on two thirds of the

- **7 of 12 are upscaled** from a 720×1280 source to 1080×1920. The source rendition, not our
  render, is the resolution floor on those. Worth knowing before blaming the renderer for a
  soft frame.

**Every existing property is intact.** The original is served through the *same* endpoint and
the *same three gates* as the render — token is a hash so no path can be spelled in the URL,
the resolved file must sit inside the batch directory, the extension must be a video one.
Adding a second, looser endpoint would have been the easy version and would have put a path
back into a URL. No external requests, no credential on any endpoint, per-pid liveness and
independent panels untouched, and nothing here advances rotation.

**Accessibility, applied inline:** each half is a real `<video controls>` (native keyboard
operation), inside a `<figure>` with a `<figcaption>` naming which half it is — **text, not a
colour or a border**, so it survives greyscale and a screen reader. `aria-label` distinguishes
"Original source clip" from "Our render" per rank. The pair collapses to one column below
620 px rather than shrinking, because a sliced caption is invisible at 120 px wide and that
would defeat the entire point.

### The count check would have cried wolf

`videos` counts files, and the folder now holds two per row. Compared against 12 rows that
reads **24 vs 12** and would have fired the "counts disagree" banner on a *correctly paired*
batch. The check now compares rows against **renders**, reports `renders`/`originals`
separately, and gained an `unpaired` list. A check that cries wolf gets ignored, and this one
exists to catch a video shipping under another creator's permalink.

## 4. AUTOMATIC, NOT A ONE-OFF

`clippershq/operator_pairs.py` ships the naming, the pairing, the measurement and the row
format. `place_pair(folder, rank, handle, render, original)` writes **both** halves in one
call — accepting either a path or raw bytes, because a source is sometimes still staged and
sometimes re-fetched — so a batch script has to go out of its way to forget the original.

`tests/test_operator_pairs.py` (**15 tests**) is the enforcement:

- `unpaired()` is asserted empty on the live folder, **and** the batch is asserted non-empty,
  so a green result cannot come from an empty directory;
- the check is **symmetric** — an orphan original is also a defect, because it means a render
  was deleted and the operator is being offered a source with nothing to compare against;
- `START_HERE.md` must name **both halves** of every pair on disk, since the markdown is what
  the dashboard parses and an unnamed pair is one the operator cannot play;
- `test_this_check_can_actually_fail` plants a render with no original and requires the
  detector to fire before any green result on the real folder is believed.

## THE SUITE FOUND TWO THINGS I HAD MISSED

The first full run was **4 red of 219**. Two were concurrency artefacts that passed in
isolation (`test_dashboard_operator`, `test_doc_citations`). The other two were real:

**`clippershq/operator_pairs.py:115` read ffprobe's stdout without checking its return code.**
`test_no_unchecked_stdout` is right and the hazard is exactly this function's: a crashed
ffprobe writes nothing, an empty document parses cleanly into "no streams, no duration", and
that reads as a *measured* fact rather than a failed measurement — so a pair would silently
report `1080x1920 unchanged` for a file nothing could read. It now returns `{}` on a non-zero
exit, which `changes()` renders as `unmeasured`.

**`test_scratch_gc::test_a_live_claim_keeps_a_directory` asserted on ambient state it does not
create.** It skipped only when the claim registry was *empty*, but its assertion needs a live
claim covering a scratch **directory**. With rounds in flight that all claim scratch *files*
— `scratch/bl1119_pair.py`, `scratch/BL-1119.md` — there was nothing for the guard to keep and
a working guard went red. The precondition now matches the assertion, and it still **fails**
rather than skips whenever a covered directory exists and is not kept, which is the regression
it was written for.

## Method / limits

**The originals are what the CDN serves today, not what was fetched on render day.** Instagram
re-encodes and the rendition ladder is not stable between fetches — 7 of the 11 came back at
720×1280 where the render consumed a taller rendition. So the pair is honest about *content*
and approximate about *bitrate*: a compression artefact visible only in the original may be a
property of today's fetch. Anything structural — a caption, a crop, a band, a cut — is exact.

**One original is a staged copy, not a re-fetch.** `01_songss` still had its source under
`scratch/`, so it was copied rather than paid for. It is the one pair whose original is
byte-for-byte what the renderer actually consumed.

**`record_id` is carried, not verified.** The ids come from the previous manifest, which a
human wrote after watching. This round did not re-derive them from the ledger, so a wrong id
there is still wrong here — the pairing work did not touch that column.

**The change line describes the file, not the intent.** `trim 73.3s -> 20.0s` is the measured
difference between two files; it does not distinguish a trim from a speed change, and the
transform roll (zoom, rotation, shift) is per-render and never written to the ledger, so it is
not in the column at all.
