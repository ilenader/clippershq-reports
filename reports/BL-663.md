**The platform in one paragraph.** ClippersHQ connects content clippers with brand campaigns; clippers post short videos on TikTok, Instagram Reels and YouTube Shorts and earn CPM payouts on views. A clip is submitted as a URL, tracked for view counts, and reviewed (approve/reject) by a human. The stack is Next.js 14 (App Router, TypeScript), Postgres (Supabase) via Prisma, hosted on Railway. Providers: LamaTok (TikTok metadata/stats), HikerAPI (Instagram), the YouTube Data API (YouTube). Apify is retired and its key emptied.

## PART 1 — what is running right now, silently: the structured-rules shadow evaluator

### The evaluator, completely

* **The rule engine (pure, decides nothing):** `src/lib/campaign-rules.ts`. It imports no DB, no network, no money code. Key exports: `parseRulesJson(value)`, `extractClipMetadata(raw)` (returns `{caption, soundId, hashtags}`), `evaluateRuleShadow(rule, meta, platform)`, `evaluateRulesShadow(rules, meta, platform)`. Verdicts are `"would_reject" | "would_pass" | "cannot_evaluate" | "rank_review"`.
* **Where and WHEN it runs:** only at clip submit, inside a post-response `after()` block in `src/app/api/clips/route.ts` (approximately lines 912 to 962). It does NOT run on a tracking tick and NOT on human review. It reads `campaign.rulesJson` plus the provider `raw` metadata already fetched at submit for the freshness/view check (BL-552), extracts `{caption, soundId, hashtags}`, and evaluates each rule.
* **What it does with the result:** two things, added in two rounds. BL-602 (shipped 2026-07-20) wrote a single `console.log('[RULES-SHADOW] ...')` line to Railway's ephemeral log stream. BL-659 (merged to main 2026-07-24 12:58 UTC) ALSO writes one row to the `rule_shadow_decisions` table, but only when `rulesJson` parses to at least one rule. `wouldReject` is set true ONLY when a rule whose enforcement is `auto_reject` returns `would_reject`.
* **What it changes: nothing.** It never sets a clip status, never writes earnings, never notifies anyone. The clip was already created `PENDING` by the submit core (`src/lib/clipper-submit-core.ts`) before this block runs. It is invisible to clippers: `rule_shadow_decisions` has NO read route anywhere in the app (owner or clipper). This is enforced by design per BL-518 and BL-521 (PART 5).

### What it has actually DONE since going live (reconciled plainly)

This is the single most important operational fact for the other team, so it is stated exactly:

* **2026-07-20 to 2026-07-24 (the BL-602 era): nothing durable.** The shadow ran at every qualifying submit but only `console.log`ged to Railway's ephemeral logs. BL-656 established this decisively: "the shadow is not in the database... it writes nothing to any table," and because the clips table stores no caption, "a retrospective rate is NOT computable here." That period's decisions are gone.
* **2026-07-24 12:58 UTC onward (the BL-659 era): a brand-new durable write.** The `rule_shadow_decisions` table was created directly in prod (via `CREATE TABLE IF NOT EXISTS`, no `prisma migrate`) during BL-659 development, and the CODE that writes to it deployed with the BL-659 merge to main at 12:58 UTC today.
* **Current table contents (live-measured for this report, 2026-07-24 17:47 UTC): 7 rows, and every one is empty of the data that matters.** BL-662 measured **0 rows** at 12:40 UTC (which was BEFORE the 12:58 write-code deploy). This report re-measured at 17:47 UTC and found **7 rows** (first `2026-07-24 16:09:38`, last `17:31:17`, `::text`), of which **`wouldReject` = 0, `captionPresent` = 0, `soundIdPresent` = 0**. So the write path IS firing (7 rows in ~5 hours since deploy), but every row so far recorded NO caption and NO sound id, meaning the evaluator had nothing to test and returned `cannot_evaluate` (fail open) on all of them.
* **Reconciliation, plainly, in two parts.** (a) The table was empty at BL-662's 12:40 UTC reading because the durable write had not yet deployed (it deployed at 12:58 UTC); it is now accumulating, so the other team inherits a WORKING write path that has just begun, not a broken one. (b) But a second, important gap is now visible: all 7 rows have `captionPresent = false` and `soundIdPresent = false`, so the caption/sound metadata is NOT reaching the evaluator at submit for these clips. That is consistent with BL-662's findings that the Instagram sound path is not extracted and that the submit `raw` may be a summary rather than the full item. **Consequence: zero would-reject decisions are being generated, so the false-rejection rate remains unmeasurable not only for lack of time but because no caption is currently being captured to judge.** The other team should treat "why is `captionPresent` false on live shadow rows" as a first-order question; until it is fixed, the shadow accumulates rows that decide nothing.

## PART 2 — the rules system, complete

### Two layers: prose for humans, JSON for machines

* **`campaigns.requirements`** — Postgres type `text` (Prisma `String? @db.Text`). Free-text prose. This is the clipper-facing SOURCE OF TRUTH: it is what clippers read and what reviewers enforce. In the admin form it is authored as a repeatable list ("Add each requirement as a separate item") and then flattened to one blob with `join("\n")` on save and split back on load (R-6, `admin/campaigns/page.tsx` around lines 174 and 290). Sibling free-text fields: `description`, `captionRules`, `hashtagRules`, `bannedContent`, `soundLink` (all `text`), and `videoLengthMin`/`videoLengthMax` (`int`).
* **`campaigns.rulesJson`** — Postgres type `jsonb` (Prisma `Json?`). The machine layer, designed in BL-596 and shipped in BL-602. It is read ONLY by the shadow evaluator and by NO money-path file. NULL on most campaigns; populated on 11 (below). Also relevant: `campaigns.sounds` (`jsonb`, an array of approved sound links) and `campaigns.platform` (`text`, comma-separated allowed platforms).

### The `rulesJson` shape (with a real redacted example)

`rulesJson` is a JSON array; each element is one rule:

```
{
  "id":          "<stable rule id>",
  "text":        "[REDACTED verbatim requirement line shown to the clipper]",
  "type":        "REQUIRED_CAPTION_TOKENS",
  "platforms":   [],                      // lowercased; empty = all platforms
  "params":      { "tokens": ["@[REDACTED]", "#[REDACTED]"] },
  "enforcement": "auto_reject"
}
```

`params` may carry `tokens?: string[]`, `soundId?: string`, `position?`, `coverage?`, `minSec?`, `maxSec?` depending on type. `parseRulesJson` is tolerant: any malformed shape returns `[]` (fail open). Tokens for caption rules are extracted LITERALLY from the requirement text, never invented (BL-602).

### Every rule TYPE in code vs in production

Types defined in `src/lib/campaign-rules.ts` (`RuleType`), with enforcement `auto_reject | rank | human_only`:

| Type | Answering data | Machine-certain or judgement | Default enforcement | In production? |
|---|---|---|---|---|
| `REQUIRED_CAPTION_TOKENS` | caption text | MACHINE-CERTAIN (NFKC-casefold literal substring) | auto_reject | **YES: 8 rule lines** |
| `REQUIRED_SOUND` | TikTok `music.id` / IG `audio_cluster_id` | machine-certain on TikTok canonical only | auto_reject | **NO (0 in production)** |
| `VIDEO_LENGTH` | video duration | would be certain, but duration is not fetched/stored | auto_reject-capable, dormant | NO |
| `POSTING_WINDOW` | post timestamp | certain if timestamp stored; already enforced at submit for freshness | rank | NO (as a rulesJson rule) |
| `LOGO_PRESENT_THROUGHOUT` | video pixels | JUDGEMENT (cover frame proves t=0 only) | rank | NO |
| `EDIT_QUALITY` | none | JUDGEMENT | human_only | NO |
| `HUMAN_ONLY` | none (catch-all) | JUDGEMENT | human_only | **YES: 78 rule lines** |

**Live-confirmed counts (BL-662, 2026-07-24):** across **11 campaigns** carrying any `rulesJson`, there are exactly **8 `REQUIRED_CAPTION_TOKENS` (all `auto_reject`)** and **78 `HUMAN_ONLY`**, and **zero `REQUIRED_SOUND`**, even though the type exists. The 8 auto_reject caption rules sit on **6 of those 11 campaigns** (BL-656, BL-659); the other 5 campaigns carry only human-only rules. A re-confirmation query for this report could not run (pool timeout, PART 1); the BL-662 counts are ~40 minutes old and are the authority here. **So the only machine rule that can fire live today is "a required caption token is literally absent from the caption."**

## PART 3 — the data available, per platform (the foundation)

Full detail is in BL-662; its headline facts, re-stated:

* **Stored in the `clips` row:** only `clipUrl` and `normalizedUrl` (100%), plus `thumbnailUrl` (a re-hosted cover frame, on ~30% of clips), plus a `clip_stats` row per tick holding `views/likes/comments/shares`. There is NO caption, sound id, hashtag, duration, dimensions or platform column on `clips`.
* **Fetched at submit and DISCARDED on every platform:** the sound id, caption and hashtags are returned by the provider at submit and thrown away, except that caption + soundId are written to `rule_shadow_decisions` when the campaign has a `rulesJson` (PART 1; currently no retained rows).
* **TikTok (LamaTok):** returns a STABLE `music.id` (live-probed 2026-07-24: e.g. a 19-digit numeric id), so sound matching is machine-certain on a canonical `/@handle/video/<id>` URL. BUT a `/t/<code>` short link returned HTTP 500 from LamaTok's `by/url` endpoint, and **69% of TikTok clips are short links** (must be redirect-resolved to canonical before any sound id, caption or duration is reachable). Treat a 500 as fail-open (never "no sound"), as it can also be transient.
* **Instagram (HikerAPI):** returns a usable `clips_metadata.music_info.music_asset_info.audio_cluster_id`, but the current extractor `extractClipMetadata` only checks `r.music?.id` / `r.music_info?.id` and does NOT reach that nested path, so the IG sound id is present at the provider yet not captured by today's code. It also returns `caption.text`, `video_duration`, `taken_at`, and a `caption_is_edited` flag.
* **YouTube (Data API):** exposes NO sound/music id at all, and the submit path fetches only `snippet.publishedAt` + `statistics` (no `contentDetails`, so no duration; `title`/`tags`/`description` present in the API but not fetched). A sound rule can NEVER work on YouTube.

**Free to start storing today (already fetched, just discarded):** TikTok `music.id`, caption, hashtags, duration, `createTime`; Instagram caption, `taken_at`, `video_duration` (and, with a nested-field fix, the sound id). Cost: a schema add plus a few lines at submit; NO new vendor call. **Needs a new call:** YouTube caption/tags/duration (one extra Data API call with `part=snippet,contentDetails`; the Data API is free within quota, so ~$0 at ~2,300 clips a month, only a quota cost). **Needs a paid model:** sampling frames from inside the video (pixels over time) is priced by R-6 at roughly $5.98/month for 3 frames or $55.22/month for one-per-second at ~2,300 clips, on a batched vision model, but those figures are UNVERIFIED (R-6's own token-count check hit HTTP 401). The cover frame at t=0 is free (already stored).

## PART 4 — the other machine systems (do not collide with these)

### BL-599 — peer-relative bot-detection RANK (2026-07-20)

* **What it is:** an independent signal that compares a clip's like-rate (likes/views) to the NORMAL band for its platform and niche, computed from live data, and ranks outliers for the OWNER's eyes. It fires on both suspiciously HIGH engagement (too many likes for the views) and suspiciously LOW (bought views with no likes).
* **Files:** `src/lib/peer-engagement.ts` (pure, no DB, no network, never mutates); `src/lib/peer-engagement-bands.generated.ts` (bands baked from 3,195 live clips, regenerate with `node scripts/gen-peer-bands.mjs`); `src/app/api/admin/fraud-review/route.ts` + `src/app/(app)/admin/fraud-review/page.tsx` (surface, read-only, owner-only); `scripts/bl599-verify.ts` (validation).
* **How it scores:** two-sided like-rate vs the most specific peer band that exists (platform+niche at 40+ samples, else platform, else global). Active from ZERO views. HIGH fires when a clip has at least 8 likes in absolute terms AND at least 3x the peer-expected likes AND a rate above the peer p90. LOW keeps a 2,000-view floor and is suppressed on YouTube.
* **Measured fire rate: 3.2%** (BL-599, 2026-07-20): of 2,707 live APPROVED clips, 87 surfaced (63 HIGH = 2.3%, 24 LOW = 0.9%).
* **It RANKS and never rejects, never freezes, never changes status or earnings, and the clipper never sees it.**

### BL-650 / BL-636 — the analytics screenshot reader (owner-only, INERT)

* Rebuilt in BL-650 (owner-only, in the Creator Scan Review Panel). It detects the platform, parses K/M/B suffixes and locale separators, keeps decimal percentages, flags uncertain values as "Unverified" beside a crop of their source pixels, and is structurally incapable of accusing anyone (grep-proven: it is imported by no scoring/fraud/review path and writes no clip status/earnings).
* **It is INERT: the env flag `OCR_SPACE_API_KEY` is unset**, so the OCR step never runs and the feature degrades to store-only (BL-636). **Its OCR image-to-text accuracy is UNMEASURED** because it has never run on a single production screenshot (0 uploads, BL-636). Route: `src/app/api/admin/creator-scan/[accountId]/screenshot/route.ts`; OCR client `src/lib/creator-scan/screenshot-ocr.ts`; parser `src/lib/creator-scan/screenshot-metrics.ts`.

### R-5 — `fraudScore` has NO predictive power (2026-07-17)

The aggregate `clips.fraudScore` column (int, present) is measurably worthless as a gate: score-0 clips reject at **19.0%** (2,920 clips) and score-40+ at **19.5%** (82 clips), statistically identical. **Nothing may be gated on `fraudScore`.** 439 clips scored above zero, 0 ever dismissed.

### The human review queue (R-5, 2026-07-17)

* Reviewers are OWNER, ADMIN, and a scoped REVIEWER role. One active REVIEWER already carries **52.6%** of decisions (1,206 decisions, 17.0 h/mo). Clip review is the owner's top time drain at **14.9 owner-hours/month (76%)**.
* **Scope gap:** 4 campaigns have NO reviewer scoped (BAD BITCH ANTHEM x2, Deja Shoe, CROCS), forcing those decisions onto the owner. An auto-reviewer must not assume every campaign has a human reviewer attached.

## PART 5 — the hard constraints (non-negotiable)

1. **No automatic system may change a clip's status (BL-518), and a clipper must NEVER see a machine's suspicion (BL-521).** Every machine output RANKS for a human or INFORMS one; it never rejects, approves, flags-to-the-clipper, or notifies. The shadow evaluator, the peer-rank, and the screenshot reader all obey this today, and any new system must too.
2. **Only MACHINE-CERTAIN violations may EVER auto-reject.** R-2 measured **11.05% false rejection** on a caption gate over 240 human-reviewed clips and the owner rejected it as far too high (R-2 also found humans approved 85% of clips that broke the hashtag rule, so automating it would invent a policy reviewers do not enforce). At ~2,300 clips a month against a base of ~127 clippers, even a **1% false-rejection rate is about 23 honest clippers wrongly rejected every month.** A "certain" check is only certain if you can state what would make it wrong (PART 3 lists those failure modes: edited captions, short-link 500s, truncation, zero-width characters, per-post original-sound ids).
3. **FAIL OPEN, always.** An unevaluable rule must never reject; a missing signal is never a strike. The current evaluator returns `cannot_evaluate` on a missing caption, null sound id, empty params or unparseable `rulesJson`, and never sets `wouldReject` in those cases.
4. **Never write a prose parser for the free-text `requirements`.** R-2 proved what that produces. The structured layer is authored as discrete typed items (`rulesJson`), not parsed from prose.
5. **The clipper-facing `requirements` text stays the source of truth; `rulesJson` is a machine layer beneath it.** The two must not diverge in a way that shows a clipper one thing and judges them by another.

## PART 7 — the ordered path forward, as this platform sees it

1. **First, persist the metadata already being fetched and discarded (free, no new vendor call).** Above all the TikTok `music.id` and the post timestamp, plus caption and duration, on every submit. Reasoning: this is the only way the live false-rejection rate ever becomes measurable, it costs nothing (the data is already in hand at submit), it is reversible, and it does not touch any money or status path. Fix the Instagram nested-sound extraction while doing this. For TikTok short links (69% of clips), add a redirect-resolution step so the sound id is reachable.
2. **Then add a `REQUIRED_SOUND` rule to a few TikTok campaigns.** Reasoning: a stable `music.id` equality is the one genuinely machine-certain AND safe-to-automate check available, and there are currently zero such rules in production, so no sound data is being gathered at all. Starting shadow collection here builds the evidence base honestly.
3. **Auto-reject NOTHING until a real, owner-accepted false-rejection rate exists** and a reject path is built behind the `RULES_AUTO_REJECT_LIVE` flag (which currently defaults off and gates nothing). Reasoning: R-2's 11.05% and the ~23-clippers-per-month-at-1% math make a premature gate worse than no gate. Enabling needs BOTH the measured rate AND a new reject code path that does not yet exist.

**Before you design around this, know:** the shadow write is hours old and the table is empty (you are not inheriting data); only caption-token and human-only rules exist in production; sound matching is certain only on TikTok canonical URLs, partial on Instagram, impossible on YouTube; every existing machine system ranks and never rejects, and that boundary is the product's core trust promise, not a technical detail.

### Open questions this platform cannot answer for you (where your decisions begin)

* What false-rejection rate is acceptable to the owner as the threshold to enable any auto-reject (a product/risk decision, not a measurable fact).
* Whether to re-check caption/sound on a later tick to catch post-submit edits (PART 4 of BL-662), and how much per-clip re-fetch cost that is worth.
* Whether the reviewer capacity gap (4 unscoped campaigns) should be closed by config before or instead of automation.
* Which campaigns should carry structured `auto_reject` rules at all, given reviewers do not currently enforce the caption rule uniformly (R-2).
* Whether pixel-level review (logo/overlay) is worth a paid vision model at all, given a cover frame proves only t=0.
