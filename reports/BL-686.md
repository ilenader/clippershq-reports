## 1. The headline: a belief the project had held for months is wrong

The repo has long recorded that **"Instagram hides views on roughly 40–60% of accounts."** Filters, gates and design decisions were built around it, including the assumption that a view-count threshold could not be relied on.

It is false. It was never a privacy setting and never a property of accounts.

**The deprecated `/v2/user/medias` serializer simply omits `play_count`.**

Proven on 20 real accounts with **93% post overlap** between the two endpoints — the *same* post id, the same `product_type=clips`, fetched both ways within seconds of each other:

| post id (`pk`) | `/v2/user/medias` | `/v2/user/clips` |
|---|---|---|
| 3949922360000411865 | `play_count = None` | **20,764** |
| 3949920785819438414 | `play_count = None` | **6,491** |
| 3949919904948454496 | `play_count = None` | **6,255** |
| 3949919120689139115 | `play_count = None` | **121,957** |

Aggregate over the 20 accounts:

| metric | `/v2/user/medias` | `/v2/user/clips` |
|---|---|---|
| posts returned | 238 | 237 |
| **views present** | **92 (39%)** | **237 (100%)** |
| `clips_metadata` present | 233 (98%) | 237 (100%) |
| `product_type` mix | clips 233, carousel 4, feed 1 | clips 237 |

That **39%** is precisely where the "~40% of accounts" folklore came from. It was a per-response serializer gap being read as a per-account privacy setting.

Two secondary corrections fell out of the same evidence:

- **`like_and_view_counts_disabled` does not predict missing views.** Items carrying the flag still returned `play_count`. The flag hides *likes*.
- **`view_count` is the wrong key for reels.** It is absent on clips; the real fields are `play_count` / `ig_play_count`. (The same trap exists in the TikTok payloads, where `view_count` appears dozens of times and is non-null zero times while `play_count` is fully populated.)

**Why this matters beyond one endpoint:** anyone reading the old note would design around a constraint that does not exist — for example abandoning a view threshold in favour of likes as a proxy. No such compromise is needed.

## 2. The flip, and the coupling that was measured before accepting it

`ig_api.medias_endpoint` → `/v2/user/clips`. **No code change was required** — the path has been config-driven since `ig_client.py:64-65`.

The endpoint is a drop-in: identical parameters (`user_id`, `page_id`, `safe_int`), the same `PageResponse` envelope, and the normalized v1 Media schema (all five markers `pk`, `taken_at`, `media_type`, `product_type`, `code` present; no raw GraphQL shape).

**The coupling was the real risk.** `self._medias_path` is read once in `IgClient.__init__` with no per-caller override, so the flip moves **both** call sites together:

- the repost account gate — strictly better, it wants reels
- the niche check — the denominator silently changes from all-posts to reels-only

That second one is a recalibration, not a bug, so it was measured rather than assumed. Same 20 accounts, same niche keywords on both sides:

- mean `niche_fraction` **0.710 → 0.714**
- mean delta **+0.004**, max |delta| **0.091**
- **0 of 20 accounts moved by more than 0.10**
- no account became UNKNOWN on either side

**Conclusion: no per-caller override is warranted.** The denominator barely moves because these accounts already post almost exclusively reels — on the *old* endpoint their `product_type` mix was already 233 clips out of 238.

**Stated limitation:** the sample is reels-heavy by construction (repost/meme pages). A photo-heavy creator account would shift more, and that case is untested. If the niche check is ever pointed at photo-led accounts, re-measure before trusting it.

**A note for anyone cloning the repo:** `config.json` is gitignored because it holds credentials, so **the flip is not in the commit and a fresh clone still has the old default**. The commit message says so explicitly and gives the key to set. This was called out deliberately rather than left as a silent environment difference.

## 3. Hardening: an empty clips page no longer reads as a dead tag

`hashtag_medias_clips` falls back to the `/top` surface when the clips surface fails. The existing guard triggered when the request helper returned `None`, which covers 404/410/422 and any unexpected status.

It did **not** cover a **200 with an empty body**. In that case the response is a real dictionary, no fallback fires, the media extractor returns an empty list, and the run reports a confident zero yield that is indistinguishable from a genuinely dead tag. A whole campaign could quietly produce nothing and look like bad tag selection.

The fix tests emptiness with **the caller's own extractor**, so "empty" means exactly "the caller would get nothing" and the two can never disagree about it. An empty page **mid-pagination** is deliberately excluded — that is the normal end of a tag, not a broken surface.

Visibility was the other half of the problem. The fallback now logs at **WARNING** (not info) and increments `clips_fallbacks` / `clips_fallback_tags`, so a run can state that it spent its budget on the degraded surface instead of whispering it into a log file.

`tests/test_ig_clips_fallback.py` — 9 checks, fully offline (no key, no network, no cost):

| case | falls back | warns |
|---|---|---|
| error / 404 (the case that always worked) | yes | yes |
| 200 + empty body | **yes** | yes |
| 200 + empty envelope | **yes** | yes |
| 200 + empty item list | **yes** | yes |
| 200 **with** media | no | — |
| 200 empty on page 2 (mid-pagination) | **no** | — |

### The fallback got more expensive, and the number in the code was corrected

Re-measured live on the same tags:

| tag | clips surface | top surface |
|---|---|---|
| #batman | 30/30 video (100%) | 22/33 (**67%**) |
| #moviefacts | 30/30 video (100%) | 25/33 (**76%**) |

**~29% non-video on the fallback, against the ~18% previously recorded.** The fallback still works — the caller filters to video — but it now costs about a third of the page. The docstring and the warning text were corrected to 29% rather than shipping a figure this round had just disproved.

## 4. The time bomb, and why re-basing the date would have been the wrong fix

`test_auto_requeue` failed 8 checks. It was proven pre-existing by running a pristine worktree at the previous commit, which failed the identical 8.

The fixture pinned an instant (`NOW = 2026-07-16`) and wrote every well's age relative to it. With a 14-day refresh threshold, the fixture crossed its own threshold on 2026-07-28 and the ranking flipped. It would have started failing on a date nobody chose, in a test nobody had touched.

**The root cause was better than a test bug.** Three functions already accepted an injectable clock — but **both calls to the due-check dropped it**:

- the staleness *score* honoured the injected instant
- the *due-check* silently used the wall clock

So any caller pinning a clock got hybrid behaviour: half frozen, half live. That is a genuine defect in product code, not merely a test inconvenience. It was invisible because the only caller that pinned a clock was the test, and the test had been passing.

**Fixed structurally** by threading the clock end-to-end through the ranking key, the ranking entry point and the projection, down to the due-check. The pinned constant stays — which is now safe, because both halves read it.

Re-basing the constant to today was explicitly rejected: it reloads the same bomb for a fortnight's time.

A guard was added that pins two future instants (+5 years, +500 years) and asserts the specific correct behaviour at each. **The guard caught an error in its own first draft:** the initial assertion was "the order never changes as the clock moves", which is wrong — the 14-day threshold is absolute, so a fresh well eventually becomes due and its richness legitimately wins. The corrected guard asserts that flip explicitly, which is exactly the proof that the clock now reaches the due-check.

The fixed block passes at simulated dates of 2031-03-01 and 2045-11-20.

## 5. Scanning the rest of the suite for the same pattern

This is where an intermediate result was wrong and is worth recording honestly.

A first harness shifted the clock for the product modules only and reported **nine further failures**. Those were **artifacts of the harness, not real bombs**: tests that build fixtures from the current time were left on the real clock while the code moved, so the two disagreed. In reality both advance together.

A second harness that shifted the clock globally hit a hard wall: the spreadsheet library strictly type-checks the datetime class, so a substituted subclass breaks it. Global clock patching is not viable in this repo.

The remaining literals were therefore classified analytically:

| location | verdict |
|---|---|
| `test_auto_requeue` — fixed instant | **this was the bomb — fixed** |
| dormancy/language block — fixed instant | safe: every call passes the instant explicitly |
| Google Play finder — fixed timestamp | safe: pinned on both sides, fixtures derived from it |
| filelock test — fixed instant | safe: used as a backup-filename argument, never compared to a clock |
| "2020-01-01" staleness fixtures | safe: only gets staler, assertion stays true |
| recency-columns date strings | safe: verbatim-migration check, not time-compared |
| seven fixed-timestamp constants | safe: passed explicitly as the injected instant |

**The rule, now written into the docs:** a test expires only when **absolute fixtures meet a real clock**. Fixtures derived from the current time move with it and are fine. Injecting the clock on both sides is the fix; re-basing a constant never is.

## 6. An operational hazard worth publishing

During an A/B test of whether the flip caused the funnel failures, a PowerShell round-trip (`Set-Content -Encoding utf8`) wrote a **UTF-8 byte-order mark** to `config.json`. The JSON parser then failed outright and **the application would not start** — preflight reported the settings file as broken.

This was caught and repaired in the same session: the mark was stripped, the file rewritten atomically, and the result verified as **exactly two changed lines** against the pre-flip backup (the single endpoint change), with the campaign hash intact.

It is recorded in the docs as a standing hazard because it is silent, easy to repeat, and fatal to startup:

- **never** round-trip `config.json` through PowerShell on Windows
- verify with a 3-byte read of the file head
- repair by stripping the first three bytes and rewriting
