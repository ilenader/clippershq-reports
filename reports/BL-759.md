## 3. The config problem — you could NOT rebuild it from the repo

`config.json` is correctly gitignored (it holds live keys). The question is whether `config.example.json` can stand in for it. It cannot.

| | keys |
|---|---|
| `config.json` (real) | **161** |
| `config.example.json` | **95** |
| **present in real, absent from example** | **67 (42%)** |
| present in example, absent from real | 1 (`tt_deep_check`) |

**Four of seven credential blocks are missing from the example entirely** — not blanked, absent:

| block | in example |
|---|---|
| `api`, `ig_api`, `tikhub_api` | YES |
| **`youtube_api`, `twitch_api`, `gemini_api`, `openrouter_api`** | **NO** |

A rebuilder would not know those blocks exist, let alone their shape. Also missing: whole funnel configurations (`repost_finder`, `gp_finder`, `caption_finder`, `clip_*`, `ig_crawl_*`, `spotify_allowed_countries`, `resolve_cache_file`, `send_list_include_biolink_custom`).

**Load-bearing keys with no default.** 360 distinct keys are read through `.get()` and degrade gracefully. But roughly 30 are read by **bracket access**, which raises `KeyError` if absent — the most used being `campaigns` (8 sites), `default_hashtags` (4), `page_cap`, `max_post_age_days`, `ig_crawl_enabled`, `extra_red_flags`, `ig_extra_caption_cues`, `spend_file`, `run_default_target/platform/mode`, `target_split_tiktok/instagram`.

**Answer to "could I rebuild it from the repo alone?" — No.** You would be missing 42% of the keys, four credential block structures, and several keys whose absence is a hard crash rather than a default. `config.json` is as irreplaceable as the data, and it is 97 KB.

## 5. The OneDrive hazard — and the finding that matters most

**`OneDrive.exe is NOT running.**

The client is configured — `HKCU:\SOFTWARE\Microsoft\OneDrive\Accounts\Personal` has `UserFolder = C:\Users\Game Centar\OneDrive`, and the project sits at `C:\Users\Game Centar\OneDrive\Desktop\clipper finder`, inside that root — but the process is not up.

**The consequence is the single most important line in this report: there is currently no cloud copy either.** The mental model "it's under OneDrive, so it's backed up" is not true right now. Every irreplaceable file above exists exactly once, on one disk, on one machine.

That is also, perversely, why the *corruption* hazards are quiet at the moment. When the client is running again, these are the exposures:

| exposure | why it bites |
|---|---|
| `logs/run.log` — **15.7 MB, append-heavy** | a previous round already found OneDrive locking it during rotation |
| **5 `.lock` sidecars** (`master_leads.csv.lock`, `spend.json.lock`, `resolve_cache.json.lock`, and duplicates under `clippershq/`) | `filelock.py` takes a kernel lock on these. They are 0 bytes, so sync sees them as trivially "changed" constantly, and a synced lock file is meaningless across machines — it protects nothing and generates churn |
| `master_leads.csv` — 23 MB rewritten whole on every append | temp→fsync→`os.replace` is atomic *locally*; a sync client can still capture the `.tmp` or the post-rename file mid-flight and upload a torn version as the newest |
| `state.json` — 6.65 MB, rewritten wholesale | same shape as above |
| `backups/` — **1.4 GB** | re-uploaded churn for files that by definition never change |

The SQLite decision an earlier round made — ruling it out because a sync daemon copying `.db`/`-wal`/`-shm` at different moments corrupts it — was right, and the reasoning generalises: **any multi-file or rewrite-in-place format under a sync root is exposed.** No `.tmp` or `.partial` artefacts are present right now, so nothing is caught mid-write today.

## 6. Rebuild cost — the money is trivial, the time and tuning are not

From `spend.json`, 92 metered runs between 2026-07-11 21:41 and 2026-07-30 17:01:

| | |
|---|---|
| total metered spend | **$3.53** |
| — Instagram | $2.65 |
| — TikHub | $0.61 |
| — TikTok | $0.27 |
| metered calls | 5,476 |
| master rows | 57,386 |
| **cost per row** | **$0.00006** |

**Taken at face value this says master is worth $3.53 and is not worth protecting. That reading is wrong, and the number understates the loss badly:**

- **The ledger meters only paid resolves.** Discovery — TikTok and Instagram hashtag crawling, Twitch GQL, Spotify web scraping, YouTube `/about` — is free and unmetered, and it is where the 57,386 rows actually came from.
- **19 days of elapsed running**, across 92 runs, several of which took hours.
- **`config.json` is the tuning**, 161 keys of calibrated thresholds accumulated across dozens of measurement rounds. That is the real intellectual property and it is not in git (§3).
- **`state.json` records which wells are drained.** Losing it means re-draining hashtags already known to be exhausted — paying and waiting for nothing.
- **`resolve_cache.json` is the negative cache** that stops re-paying for known-bad handles.
- **The leads are not reproducible.** Hashtag feeds move. Re-running the same crawl in August returns a *different* population, not this one. The 483 recovered Spotify handles alone are gone if master is gone.

**Honest figure: under $5 to re-spend, but realistically a week or more of elapsed time, and the result would be a different lead set with the tuning lost.**

## 7. Minimum backup discipline — small enough to actually do

**Everything that matters is 30 MB.** That is the whole point: `.git` is 6.4 MB, master is 23 MB, config is 97 KB. The 1.4 GB of backups and 31 MB of logs are not worth copying.

**Do these three things.**

**(1) Commit the code. Today.** Four suites fail on a fresh clone purely because the fixes are not in git, and `clip_runner.py` exists in exactly one place on Earth. This costs nothing and closes the largest gap in the report.

**(2) One command, whenever you finish a session.** Copy the six irreplaceable files to a *different physical device* — a USB stick or any external drive:

```
master_leads.csv   config.json   state.json
resolve_cache.json   spend.json   repost_seen.json
```

Roughly 30 MB. Not `backups/`, not `logs/`, not the clones. If you want one line, a dated zip of just those six into `E:\clipperhq-backup\` is the entire discipline.

**(3) Turn OneDrive back on — but move `backups/` and `logs/` out of the synced tree first.** Right now the sync client is off, so you have no offsite copy at all; that is the worst of both worlds. With it on, exclude the 1.4 GB of backups and the append-heavy logs so the sync surface is small and the lock/rotation hazards mostly go away.

If you only ever do one of these, **do (1)** — it is free, it takes a minute, and it is the only gap where the loss is already irreversible for one file.

## Honest limits

- **The fresh-clone test used `git archive HEAD`, not a network clone.** That tests exactly what is committed, which is the question asked, but it does not verify the remote is reachable or current. I did not check whether `origin` has everything `HEAD` has.
- **`tests/run_all.py` was run without `config.json` deliberately** — that is the real recovery condition. Two of the six failures would presumably clear if a config were reconstructed, but §3 shows it cannot be reconstructed from the repo, so they stay red in practice.
- **I did not test restoring from a backup**, only inventoried them. A backup that exists is not a backup that restores.
- **OneDrive's cloud state was not inspected** — I can see the client is not running locally, but not whether an older copy exists server-side from a previous sync. There may be a stale cloud copy of unknown age.
- Config "load-bearing" classification is a static grep for bracket access; a key read behind a `try/except KeyError` would be miscounted as fatal.
