**Date:** 2026-08-01 · **Type:** Fix + measurement · **Spend:** **$0.0000 · 0 paid calls** of a

## The correction first, because it changes what item 1 could be

BL-877 — mine — reported the biggest leak in the pipeline as a two-line reorder: 86.6% of
vision labels bought for clips no song can match, and *"the mood check is free, local and pure,
and it currently runs after the paid call instead of before it."*

**That reading was wrong, and measuring it before implementing it is the only reason it did not
ship as a filter that destroyed the pipeline's entire yield.**

| measured over all 2,003 clips | |
|---|---|
| matches from the **VISION** tier | **202** |
| matches from walk-time tiers (franchise) | 7 |
| mood-match rate, **labelled** | **13.54%** (209 of 1,544) |
| mood-match rate, **unlabelled** | **1.31%** (6 of 459) |
| labelling changes the match rate by | **+12.23 points** |

The label is not something applied to a matchable clip. **The label is what makes a clip
matchable.** The mood check cannot run before the paid call because its input does not exist
until the call is paid.

I built the gate that was asked for and measured what it would have done:

```
THE GATE AS SPECIFIED ("does a song match this NOW?")
  would exclude              1,780 of 2,003 clips
  successful labels destroyed  217 of 217   (100%)
```

It would have cut every clip that was going to succeed. The round's own warning — *"do not
over-filter… confirm on a sample that nothing labellable is dropped"* — is exactly the test
that catches it, and it fails at 100%.

## 1. What `select()` consults instead, and what it excludes

`clip_vision.song_reach(clip, store)` answers the only question honestly answerable before
paying: **could a song serve this clip?** — not *does one now*.

**The rule, stated exactly.** A clip is excluded when, and only when, its mood is already
determined from walk-time evidence **and** the store holds no song for that mood. A clip
routed to an unstocked mood is dead however good its label turns out to be. Everything else
survives: no mood yet, a matcher error, or no store passed all return *reachable*.

**What it excludes today: nothing.** All four reachable moods (hype, warm, melancholy,
triumphant) have a song, so the gate is a no-op on the current store. That is the correct
answer rather than a broken one — it goes live the moment a mood loses its last song or a map
routes somewhere unstocked, and it can never cut a clip vision would have rescued.

```
clips the gate EXCLUDES                                    0
UNLABELLED clips (the only ones a pass pays for)         427
  of those, excluded by the gate                           0
  -> nothing labellable is dropped:                     True
```

`song_store` is optional and defaults to off, so a caller that cannot supply one gets the old
selection rather than a quietly different one.

**And the number that does change a decision is now quoted at the point of spending.**
`projected_yield()` reports a pass in **expected videos**, not labels: 1,000 clips buys ~135
videos, so the true price is 7.4× the sticker. Cost per label was always the wrong unit — a
label is not the deliverable.

## 2. The ledger can hold vision — and a second blind spot underneath it

`record_aux_spend()` now takes `vision_usd` and `vision_calls`, with a `vision_spent_usd`
ledger field.

**It takes DOLLARS, not a count times a price**, and that is the design decision worth
recording. The other four vendors are calls × a fixed rate. OpenRouter bills per token, and
two clips of the same length do not cost the same — a calls × price model would have rebuilt
the very fiction BL-873 refuted when ranked labelling came out 15% dearer per clip.
`vision_calls` rides along for rate reporting and never enters the arithmetic.

**Then the cap.** The global reader sees it immediately, because it reads `total_spent_usd`:

```
run._spend_now(global)                    $7.9769   <- includes $2.1409 of vision
main pre-flight guard reading             $7.9769
```

**But the per-campaign reader did not.** `run.py:183` re-sums the vendors by hand —
`ig + tiktok + tikhub + link` — so a headless run's own cap stayed blind to vision even after
the global total saw it. **The same omission, one level down, and invisible: the number still
looks like money, just less of it.** Fixed, and measured either side:

```
campaign-scoped cap, before   $0.0000
campaign-scoped cap, after    $2.1409
```

`run.py` was unheld when I found this (BL-866 had released it); I extended the claim to cover
it mid-round rather than editing an unclaimed file, and said so in the claim.

## 3. The backfill, marked and idempotent

$2.1409 recovered for 1,579 labelled clips at the measured $0.001355/label.

- **`estimated: true` as a FLAG, not a label substring.** BL-877 found the label heuristic
  misclassifying `CORRECTION_killed4_was_not_killed_double_count` as estimated because its
  label contains "killed". `reconcile()` already honours the flag; a row written today should
  not need the fallback. It is the only row in the ledger currently carrying the real flag.
- **Idempotent.** A second `--apply` refuses and says why. A backfill that can run twice is a
  double-count waiting to happen, and this ledger has had one — BL-842, up to 100% overstated.
- **Honest about its range.** $0.001355 is BL-854's n=380 sample, the largest clean one of the
  five in circulation; across the full published spread the same 1,579 labels are
  **$1.08 to $2.50**. That range is printed by the tool every run.
- It does **not** touch the retrieval leg. BL-876 went live 17 minutes before this round doing
  exactly that and holds `spend.json`; the two backfills are disjoint vendors, mine is
  idempotent, and the write goes through the existing locked merge-on-save path.

Ledger after: **$7.9769 total, $4.8250 measured, $3.1519 estimated (39.51%)** across 179 rows,
header and entries agreeing to $0.000000.

## 4. The denominator, settled

Measured on **this** library rather than modelled from a published table — 2,003 clips, the
real `estimated_pages` function, cap = 2:

| page | clips | share | cumulative |
|---|---|---|---|
| 1 | 1,530 | 76.4% | 76.4% |
| 2 | 311 | 15.5% | **91.9%** |
| 3 | 27 | 1.3% | 93.3% |
| 4 | 24 | 1.2% | 94.5% |

```
pages PAID per clip attempted    1.236
reachable within the cap         91.9%
pages PAID per clip RETRIEVED    1.345   <- THE DENOMINATOR
```

**1.345 is the number.** 1.00 was a single unranked run, not a library figure. 1.18 does not
follow from the distribution it was quoted alongside. Every per-clip retrieval cost in this
project should use **1.345 pages × $0.0006 = $0.000807**, and the depth correction (ranked
labelling measured 1.55, *worse*) holds against it.

## 5. Render time — measured for the first time

Ten real encodes, the shape memebot ships (1080×1920, libx264 veryfast crf 23, AAC audio,
faststart) on ten real downloaded clips:

| | seconds |
|---|---|
| mean | **3.33** |
| median | **2.54** |
| min / max | 1.43 / 11.62 |
| **per 1,000 videos** | **0.92 hours** (mean) · 0.71 h (median) |

**Render is not a rounding error but it is close to one.** Against 3.7 hours per 1,000 for
vision it is under 25 minutes. Every hours-per-1,000 figure previously published here was a
labelling floor with this stage missing; the floor was very nearly the ceiling. The mean is
pulled by one 11.62 s outlier — the median is the better central figure.

## Honest limits

- **The headline finding of this round is that my own previous headline was wrong.** BL-877
  called the 86.6% a reorderable leak. It is not reorderable. It is a *coverage* problem in
  the mood rules, and the only lever on it is more songs and more rules — which is what the
  recorded headline now says.
- **The gate excludes zero clips today.** It is correct and it is also, right now, inert. If
  you want it to do something, that is a signal about the store, not about the gate.
- **The backfill is an estimate and its range is wide** — $1.08 to $2.50 for the same 1,579
  labels, because the five published per-label costs span 2.3×. Exact figures need OpenRouter
  receipts, which are behind an API this tool deliberately does not call; a backfill should not
  require a credential.
- **1,579 labelled clips is a moving number.** Four rounds are labelling as I write; it read
  1,505 at the start of my measurements and 1,579 by the backfill. Each figure comes from one
  frozen copy, so no ratio mixes versions, but the ledger row is a snapshot.
- **I did not verify the $0.001355 against a receipt.** It is BL-854's measurement, carried.
- **Render was timed on ten clips on a loaded machine** — 27 python processes were running.
  The figure is an upper bound, and the 11.62 s outlier is unexplained.
- **`vision_usd` accepts a negative amount** so a correction can reverse an over-recorded
  charge. Nothing validates that it is small; a fat-fingered backfill would land silently.
- **The dashboard's `/api/spend` has not been checked against the new vendor.** Its per-row
  `dollars` reading will be right; whether it names vision separately, I did not test — that
  is `dashboard/` and outside this claim.
