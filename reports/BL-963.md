# BL-963 — The LOW-resolution A/B, and the first clip-time ground truth

Acts on BL-960, which recommended buying nothing and named two things worth doing. Both were
done. **Both came back negative, and the second one overturns a result this repository has
been quoting for weeks.**

**Spend: $0.1209 of a $0.40 budget.** 258 model calls. No paid retrieval — the 86 clips used
already had video on disk. Read-only on all shipping code; writes confined to `scratch/`.

---

## THE HEADLINE

| question | answer |
|---|---|
| Does `media_resolution=LOW` work? | **Yes — 3.43× fewer input tokens, measured across 59 clips** |
| Is it safe? | **No. It costs 15 points of on-screen-text accuracy above the noise floor** |
| What would it save? | **$0.47 per 1,000 clips. On the whole library, $0.94** |
| Verdict | **Keep default.** Under a dollar is not worth the library's most-populated text field |
| Do scene cuts beat vision beats at drop placement? | **No. Against hand labels it is a 12–12 tie** |

The 4.15×-versus-0.98× result that made scene cuts look decisive was an artefact of scoring
against pixel change, exactly as BL-960 suspected. Measured against 28 clips a human labelled
by eye, the two signals are indistinguishable.

---

## 1. The A/B — three arms, because two cannot be read

A two-arm test (default vs LOW) yields a disagreement rate that **cannot be interpreted**,
because the model is non-deterministic: some disagreement is the resolution change and some
is the model answering differently the second time. Nobody had measured the vision label's
run-to-run variance. So the run was:

| arm | resolution | purpose |
|---|---|---|
| **A** | default | reference |
| **B** | `MEDIA_RESOLUTION_LOW` | the treatment |
| **C** | default, **again** | **the noise floor** |

`|A−C|` is what the model costs you for free. `|A−B|` has to beat it to be a finding.

### The parameter provably took effect

BL-960 found that `extra_body` and `generationConfig` return HTTP 200 and change nothing, so
token counts were checked **per pair, before any output was read**:

```
token ratio default:LOW    median 3.35x   min 2.54x   max 4.18x   (n=59)
summed prompt tokens       379,844  ->  110,739      = 3.43x fewer
```

**The silent no-op is real and it appeared in this run.** Three of 62 otherwise-good pairs
returned HTTP 200 on both arms with **no token reduction at all** (~5%). They were excluded
before any quality number was computed. Had the guard not been there, three calls that never
went to low resolution would have been scored as evidence that low resolution is harmless.

### Per-field agreement

Analysis set: **58 clips** with all three arms parsed.

| field / measure | A vs B (LOW) | A vs C (noise) | verdict |
|---|---:|---:|---|
| `on_screen_text` — saw text at all | **79.3%** | 87.9% | **LOW worse by 8.6 pt** |
| `on_screen_text` — exact match (n=44/47) | **59.1%** | 74.5% | **LOW worse by 15.4 pt** |
| `on_screen_text` — word Jaccard | **0.692** | 0.811 | **LOW worse by 0.119** |
| `vision_scene` — word Jaccard | 0.265 | 0.313 | within noise |
| beat count — median abs difference | 2.0 | 2.0 | within noise |

Mean beats: A 7.91, **B 6.97**, C 6.78 — LOW sits *between* the two default runs. Beat count
is unaffected.

**The risk BL-960 flagged is confirmed, and it is specifically on-screen text.** Scene text
and beat counts survive LOW; burned-in text does not. That is the expected physics — 66
tokens per frame against 258 — and it lands on the field populated on 80.7% of the library.

**The noise floor is the surprise, and it is large.** Default disagrees *with itself* on
25.5% of text-bearing clips and scores only 0.313 Jaccard on free-text `vision_scene`. LOW
roughly 1.6× the text error rate rather than introducing it. Anyone comparing two vision runs
in this repo should assume a ~25% baseline disagreement on `on_screen_text` and ~0.69 Jaccard
on `vision_scene` before concluding anything.

### The fabrication control held perfectly

`posted_date` cannot be known from pixels. Across **174 calls (58 clips × 3 arms): zero
answered it.** Not one arm, not one clip. LOW does not induce fabrication, and BL-960's
0.2% figure is if anything conservative.

### Cost, measured rather than modelled

On this sample (mean clip 23.7 s — shorter than the library's 38.6 s):

| | vision | retrieval | **per 1,000** |
|---|---:|---:|---:|
| default | $0.000850 | $0.000807 | **$1.66** |
| LOW | $0.000379 | $0.000807 | **$1.19** |

**55% off the vision leg, 28% off the fully-loaded cost — $0.47 per 1,000 clips.** Retrieval
is now 68% of a LOW-resolution clip, so the remaining headroom is not in the model at all.

### The hybrid does not rescue it

"Run LOW, re-read at default only when LOW reports no text" sounds like it should work. It
does not:

- LOW reported no text on **7 of 58 clips (12%)**; default found text on 5 of those 7
- but **18 of 44 clips where BOTH arms report text disagree on what it says**

The hybrid can only detect the *absence* failure, which is the smaller one. The *accuracy*
failure is invisible to it by construction — nothing in the response says "this text is
wrong". And it saves **22% instead of 28%**, for a re-read path and a heuristic.

## 2. Clip-time ground truth — 28 clips, by hand

`hookmark/` marks hook windows in the **song**. Nothing marked where the interesting moment
sits in the **clip**. That gap is now partly filled.

**Method.** Every clip was rendered to 1 fps frames and a contact sheet with the second burned
into each tile. Each sheet was read and one second chosen: *the second at which the clip
delivers its payoff — a hard cut, a reveal, a reaction, or an impact.* Frames, sheets and
labels are saved, so any disagreement is checkable against the same evidence.

30 clips were selected across the duration range; **2 were unreadable** (truncated downloads,
no `moov` atom) leaving **28**. Confidence: **9 high, 16 med, 3 low.**

Examples, so the rule is auditable rather than asserted:

- *"Bro waited 9 months for this"* — ten seconds of belly shots, **baby reveal at 11 s**
- *"Emma Stone's scream was never in the script"* — **hard cut out of the scene at 7 s**
- Kung Fu Panda — **green energy burst at 5 s**
- Death at a Funeral — **the body opens her eyes at 10 s**

**Honest limits.** One labeller, one pass, so there is **no inter-rater agreement figure** and
the labels carry that labeller's bias. Resolution is 1 s. 3 clips are flat montages with no
real peak and are marked `low` — the label there is the strongest available change, not a
claim a drop belongs there. This is ground truth in the sense that a human looked at the
pixels and decided; not in the sense that it is the only defensible answer.

## 3. Cuts versus beats, scored against the humans

MEMEBOT-038 scored both signals against frame-to-frame **pixel change** — and
`clip_cuts.find_cuts` *is* a frame-difference detector on that same region. Here the target
is a second a human chose, which neither detector can see.

**Density is controlled.** A signal firing 45 times in a 17-second clip lands near anything.
Each signal is scored against a random baseline with the **same number of events in the same
clip**: `P(hit) = 1 − (1 − 2·tol/duration)^n`. Lift 1.00 means the signal told you nothing
its own event count did not.

| tolerance | signal | hit rate | expected | **lift** | median \|Δt\| | events/clip |
|---|---|---:|---:|---:|---:|---:|
| ±1 s | scene cuts | 78.6% | 51.9% | **1.52×** | 0.3 s | 10.9 |
| ±1 s | vision beats | 67.9% | 49.0% | **1.38×** | 0.9 s | 7.2 |
| ±2 s | scene cuts | 85.7% | 67.7% | 1.27× | 0.3 s | 10.9 |
| ±2 s | vision beats | 82.1% | 71.0% | 1.16× | 0.9 s | 7.2 |

On the 25 high+med clips: cuts 1.54×, beats 1.42×. On the 9 high-confidence clips at ±2 s,
**beats score 100% and cuts 88.9%.**

**Per clip, restricted to the 24 clips where both signals exist: scene cuts closer on 12,
vision beats closer on 12. An exact tie.**

> A correction to my own first pass, because it changes the sentence. I initially counted the
> 4 clips with **no cuts at all** as wins for beats, which produced "beats win 16–12". A clip
> with no cuts is a coverage gap, not a win. Restricted to clips where both exist it is 12–12.

### What this means

| | MEMEBOT-038 (pixel target) | BL-963 (hand labels) |
|---|---|---|
| scene cuts | **4.15×** | **1.52×** |
| vision beats | **0.98×** | **1.38×** |
| per-clip | cuts 17–0 | **12–12** |

**The gap was the metric.** Cuts scored 4.15× against pixel change because cuts *are* pixel
change. Beats scored 0.98× because beat timestamps carry no pixel information — which is
true, and remains true, and is simply not the same claim as "beats cannot find the moment".
Against what a human picked, **the beats you have already paid for are as good as the cuts**.

Two further measured facts:

- **Neither signal is strong.** 1.38–1.52× lift, on signals firing 7–11 times per clip where
  a density-matched random guess already hits ~50% of the time. Nothing here supports an
  automatic drop placer.
- **4 of 28 clips (14%) have no usable cut at all.** Beats exist on all 28. A cut-based rule
  cannot serve those clips; a beat-based one can.

**This does not reinstate beats as a timeline.** BL-844 and MEMEBOT-038 measured `t_end_s`
and `t_start_s` as unreliable against pixel change and that stands. The narrower finding is
that against a *human* target the two signals are equivalent, so the recorded 4× advantage
should not be used to justify work.

## 4. Recommendation

### On resolution: **keep default.**

LOW works, cuts input tokens 3.43×, and is safe for `vision_scene` and beat counts. It costs
**15 points of exact on-screen-text agreement above a 25-point noise floor** and 8.6 points of
detecting text at all.

The saving is **$0.47 per 1,000 clips**. Re-reading the entire 2,003-clip library at LOW
instead of default saves **$0.94**. That is not a trade worth making against the field BL-960
identified as the one real gap in the labelling.

**Where LOW *is* the right answer** — the brief's third option, with the evidence for it:
any pass that does **not** read `on_screen_text`. Scene descriptions and beat counts came
back within the noise floor. A cheap first-pass scene/beat label, a re-label sweep after a
tooling fix, or any bulk pass that only needs `vision_scene` should use LOW and take the 55%
cut on the vision leg. It should be a **per-call parameter, not a config default**, so the
choice is made where the caller knows which fields it needs.

### On drop placement: **use what is already paid for.**

Scene cuts and vision beats are equivalent against hand labels (12–12), beats cover 100% of
clips against cuts' 86%, and beats cost nothing extra because they are already stored. There
is no case for building a cut-based placement path on the strength of the 4.15×.

There is also no case for an **automatic** placer yet. 1.5× lift is not a placement rule.

### What would actually move this

**More hand labels.** 28 clips with one labeller is enough to overturn a 4× claim — that is
what it did — and not enough to build on. The next useful increment is **a second labeller on
the same 28**, which costs $0 and yields the inter-rater number this round cannot report. If
two humans agree with each other far more than either agrees with cuts or beats, that gap is
the real size of the prize. If they do not, the question is not worth more money.
