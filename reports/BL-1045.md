## 3. What created them

`ClippersHQ\docs\PROJECT-MAP.md` says it outright:

> *"Concurrent sessions share the working dir — prefer an **isolated git worktree**
> (`git worktree add`) to avoid branch-flip races."*

Same pressure as this repo: many rounds, one tree. The convention is sound; **the
destination is the defect.** And there is already a proper home — `ClippersHQ\.claude\worktrees\`
— which holds **2** worktrees against **93** at the drive root.

### The 260-character hypothesis does not survive measurement

The brief proposes rounds used short root paths to dodge Windows' `MAX_PATH`. **Measured
against the real trees, that is not necessary:**

```
deepest ACTUAL path in C:\b707        150 chars
  (…\@prisma\instrumentation\node_modules\@opentelemetry\instrumentation\build\esnext\…)
the same file under the proper home   227 chars   -> still under 260
```

So `MAX_PATH` does **not** force a root path for the trees that exist. It is defensible as a
*precaution* — 227 leaves only 33 characters of headroom, and one deeper transitive
dependency would break it — but it is not the cause, and a report that repeated the
hypothesis unchecked would have sent the fix in the wrong direction.

**`C:\c` is separate and is a real bug:** it contains nothing but `Users`, i.e. something
wrote `C:\c\Users\…` from a mis-joined `/c/` Git-Bash prefix. 0 MB, harmless, diagnostic.

## 6. Prevention — the defect is the missing lifetime, not the location

A round that creates a 1.16 GB worktree and never removes it is the defect; 93 of them is
the symptom. Three changes, cheapest first:

1. **One owned home, gitignored.** `ClippersHQ\.claude\worktrees\<round>` already exists and
   already works — 2 trees live there today. Add `.claude/worktrees/` to `.gitignore` and
   make it the only documented destination. Measured headroom: 227 of 260 characters, so it
   fits; if a deeper dependency ever threatens that, the answer is enabling long paths
   (`core.longpaths=true` plus the registry switch), not a root directory.
2. **A lifetime, enforced by the thing that creates them.** A worktree should not outlive
   its round. `claim.py end` already refuses to release while a claimed path is uncommitted;
   the same hook can refuse while the round's worktree still exists, which turns cleanup from
   a habit into a gate.
3. **A weekly sweep that reports before it acts** — list worktrees whose round has been
   released for more than 7 days, with dirty-file counts, and let the operator confirm. The
   same audit this round did by hand, on a timer.

**And the bigger lever is not here at all.** These 123 folders are 8% of the disk.
`scratch/` alone is 11.73 GB inside OneDrive and growing by a `*_work` directory per render
round; `backups/` is 1.79 GB; `config.backups/` 0.91 GB. Those are inside the tree this
session actually owns, and none of them has a documented lifetime either.

## 7. What I got wrong

1. **I trusted the brief's disk figure.** It said 930/931 GB. I measured first and found
   61.94 GB free — so I corrected the premise before claiming rather than writing an
   emergency report about a condition that had already eased.
2. **My first sizing pass used `du` across 120 folders and timed out at 10 minutes**, then
   `Get-ChildItem -Recurse` returned **0 GB for `C:\Users` and `C:\Windows`** — a permissions
   failure that reads exactly like "these are empty". I switched to `Scripting.FileSystemObject`
   and marked the still-unreadable paths as unreadable instead of small.
3. **I nearly reported the `MAX_PATH` hypothesis as the cause.** Measuring the deepest real
   path (150 chars → 227 in the proper home) disproved it.
4. **My first worktree scan double-counted** — the glob `/c/b*` also matches `/c/bl632`, so
   four `bl*` trees appeared twice. Deduplicated before any count was published.
