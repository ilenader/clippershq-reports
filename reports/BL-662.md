### Q2 — does the stored submission include the audio/sound id, or only the URL?

**Only the URL, on every platform.** The `clips` row stores `clipUrl` + `normalizedUrl` + (30% of the time) `thumbnailUrl`. The sound id, caption and hashtags are **fetched at submit and discarded**, with one narrow exception: when the campaign has a `rulesJson`, the caption and soundId are written to `rule_shadow_decisions` (currently 0 rows). Side by side, per platform, STORED versus what the provider RETURNS at submit:

| Platform | Stored in DB today | Provider returns at submit (live-probed) | Sound id STORED? |
|---|---|---|---|
| TikTok (LamaTok) | `clipUrl` (often a `/t/` short link), `normalizedUrl`, sometimes `thumbnailUrl`; a `clip_stats` row (views/likes/comments/shares) | full item: `music.id` (stable), `desc` (caption), `challenges` (hashtags), `video.duration`, dims, cover, `stats`, `createTime` | **No** (extracted into `raw`, only reaches the shadow table if a rule exists; else discarded) |
| Instagram (HikerAPI) | same shape | full item: `clips_metadata.music_info.music_asset_info.audio_cluster_id`+`id`, `caption.text`, `video_duration`, dims, `taken_at`, `caption_is_edited` | **No**, and worse than TikTok: our extractor path does not even reach IG's nested music id (see PART 1) |
| YouTube (Data API) | same shape | only `snippet.publishedAt` + `statistics` are fetched; `title`/`description`/`tags`/`contentDetails.duration` are NOT requested; YouTube has no sound-id concept | **No, and not obtainable** (no sound id exists in the API) |

Real redacted rows: a stored TikTok clip = `{clipUrl:"http://www.tiktok.com/t/ZTAY5tAxx/", normalizedUrl:<canonical>, thumbnailUrl:null, postedAt:null}` plus a `clip_stats` row `{views, likes, comments, shares}`. The matching live LamaTok response for a canonical TikTok = `{id, desc:[REDACTED 91], music:{id:7621960336325446431, title:[REDACTED 14], original:true, duration:29}, challenges:[4], video:{duration:20, width:720, height:1280}, stats:{...}, createTime:1784873106}`. The gap is everything except the URL and the counts.

### Q3 — can `bot_verdict` and `bot_reasons` columns be added for shadow mode?

Technically trivial (`bot_verdict` would be a boolean or a small enum text; `bot_reasons` a `text[]` or `jsonb`), but **you should NOT add them, because `rule_shadow_decisions` already serves this purpose and serves it better.** That table already carries the verdict (`wouldReject`), the reasons (`wouldRejectRuleIds` + `results` JSONB evidence), the caption and sound the machine judged, the platform, and an `autoRejectLive` audit flag. Adding `bot_verdict`/`bot_reasons` to `clips` would (a) duplicate all of that, (b) put a machine signal on the load-bearing money model that BL-518/BL-521 keep clean, and (c) store one verdict per clip whereas the shadow table can hold the full per-rule breakdown. **Recommended shape: rows in the existing `rule_shadow_decisions` table, not columns on `clips`.** Nothing needs adding. If anything, the gap is that the table is empty and captures nothing for campaigns without a `rulesJson`.

## PART 1 — the full per-platform data inventory (live-probed)

### TikTok via LamaTok — the richest, and the only reliable sound id

Live probe, canonical `/@handle/video/<id>`, HTTP 200. Fields, redacted:

| Group | Field | State |
|---|---|---|
| IDENTITY | `id` (7665...413), `author.id` (7512...246), `author.uniqueId` [REDACTED 8] | PRESENT |
| TEXT | `desc` [REDACTED 91], `challenges` (4 hashtags), `textExtra` | PRESENT |
| **AUDIO** | **`music.id` = 7621960336325446431**, `music.title` [REDACTED 14], `music.authorName` [REDACTED 11], `music.original` = true, `music.duration` = 29, `isCopyrighted`, `is_commerce_music` | **PRESENT and RELIABLE** |
| MEDIA | `video.duration` = 20, `720x1280`, cover PRESENT, `play_addr` PRESENT (video file reachable) | PRESENT |
| METRICS | `stats` / `statsV2` (play/digg/comment/share), `collect_count` (saves) | PRESENT |
| TIMING | `createTime` = 1784873106 | PRESENT |

**Can we tell with certainty a TikTok clip used a specific sound? YES.** `music.id` is a stable numeric id; comparing it to a campaign's required sound id is a machine-certain equality. Two caveats: an "original sound" (`original:true`) has a per-original id, so the campaign must specify that exact id; and the STORED url is usually a short link (below).

**Short link vs canonical (69% are short links).** Live probe of a `/t/<code>` short link through the same LamaTok `by/url` endpoint returned **HTTP 500** (after 15.5s), while the canonical `/@/video/` returned 200 with the full item. So LamaTok does not resolve `/t/` short links directly; the short link must be redirect-resolved to canonical before any sound id, caption or duration is reachable. Marked **UNRELIABLE for short links as stored**: the sound rule on a short-link clip needs an extra resolution step, and a single 500 could also be transient, so this must not be treated as "clip has no sound" (fail open).

### Instagram via HikerAPI — sound id EXISTS in the response but is not captured

Live probe, `/reel/<code>` by code, HTTP 200. Fields, redacted:

| Group | Field | State |
|---|---|---|
| IDENTITY | `pk`/`id` (3947...600), `code` | PRESENT |

| MEDIA | `video_duration` = 20.735, `720x720`, `video_versions` (3, file reachable), `image_versions2` (thumbnail), `media_type`=2, `has_audio`=true, `carousel_media`=0 | PRESENT |

**Can we tell with certainty an IG clip used a specific sound? PARTIALLY, and NOT today.** HikerAPI returns a music id (`audio_cluster_id` for reused/licensed audio, matchable across posts; a per-post id for original audio). But our extractor `extractClipMetadata` (campaign-rules.ts:153) only checks `r.music?.id` / `r.music_info?.id`, which do NOT reach IG's nested `clips_metadata.music_info.music_asset_info.id`, and the IG submit `raw` is a summary rather than the full body. So the IG sound id is **present at the provider but not captured by the current code**. It is obtainable with a code change (extract the nested field), not free today.

## PART 2 — already-have-for-free vs costs-money

**Tier A: ALREADY FETCHED AND STORED (free, queryable today).** The submitted URL (`clipUrl`/`normalizedUrl`); the metric snapshot `clip_stats` (views, likes, comments, shares) refreshed every tick; the cover frame `thumbnailUrl` for ~30% of clips; account-level `followerCount`/`lastVerifyBio`; `fraudScore`. Machine layer `rulesJson` on 11 campaigns.

**Tier B: ALREADY FETCHED BUT DISCARDED (free to store, needs only a column or a shadow row) — the highest-value tier.** Every one of these is already returned by the provider at submit and thrown away:
* TikTok: `music.id` (the sound id), caption (`desc`), hashtags (`challenges`), `video.duration`, dimensions, `createTime`.
* Instagram: caption (`caption.text`), `taken_at` (post timestamp), `video_duration`, dimensions, `caption_is_edited`, and (with a nested-field fix) the `audio_cluster_id` sound id.
* Cross-cutting: the platform post timestamp is discarded for 98% of clips (`postedAt` populated on only 88/4055) even though both TikTok `createTime` and IG `taken_at` are returned at submit.
The cost to start keeping these is a schema add plus a few lines in the submit path; **no new vendor call.** BL-659 already proved this for caption+soundId (it stores them in the shadow table at no extra fetch).

**Tier C: NOT FETCHED (an extra call or model run).**
* YouTube caption/tags/duration: one extra Data API call per YT clip with `part=snippet,contentDetails`. The Data API is free within quota, so ~$0 at 2,300 clips/month, only a quota cost.
* Sampling frames from inside the video (pixels over time): priced by R-6 below.

**The video pixels, specifically.** The cover frame is already stored on your own Supabase (`clip-thumbnails/`); R-3 probed 15 of 15 reachable, though platform-wide only ~30% of clips currently have a stored `thumbnailUrl`. R-6's frame-sampling prices, at 2,301 clips/month on a batched vision model:

| Frames per clip | R-6 monthly cost |
|---|---|
| 3 (first / middle / last) | **$5.98** |
| 30 (one per second) | **$55.22** |

**Marked UNVERIFIED here.** I ran no vision model this round; these are R-6's calculations from documented vision-model + batch-API pricing, and R-6 itself notes the `count_tokens` verification returned HTTP 401 so the token count was never confirmed against real thumbnails. R-6's stronger point stands and is free: the top pixel rules (a fixed logo box, burned-in text) are **$0** via local OpenCV template matching + Tesseract/PaddleOCR, no vendor. **What is achievable for free before any vendor: the cover-frame check at t=0 on the already-stored thumbnail.** A cover frame can only ever prove presence at the first frame, not "throughout," which is the honest limit on every temporal pixel rule.

## PART 3 — which campaign rules are actually checkable, and how certain

Production `rulesJson` carries only **two rule types**: `HUMAN_ONLY` (78 lines) and `REQUIRED_CAPTION_TOKENS` (8 lines, all auto_reject). **There is no `REQUIRED_SOUND` rule in any campaign**, even though the sound rule is the owner's key ask and TikTok exposes a reliable id. So the only machine-certain rule live today is caption-token presence.

| Rule type (code) | In prod? | Answering field | Certainty | What would make a "certain" check WRONG |
|---|---|---|---|---|
| `REQUIRED_CAPTION_TOKENS` | 8 rules | caption (`desc`/`caption.text`) | MACHINE-CERTAIN (NFKC-casefold literal substring) | caption fetched at submit but edited seconds later; provider truncated the caption; a required tag present with a zero-width char the NFKC fold does not strip; token authored with a different @handle spelling than the rule |
| `REQUIRED_SOUND` | none live | TikTok `music.id`; IG `audio_cluster_id` | MACHINE-CERTAIN on TikTok canonical; PARTIAL on IG (not wired); IMPOSSIBLE on YouTube | short-link clip whose id was never resolved (500); original-sound per-post id vs a licensed cluster id; IG nested field not extracted; comparing against the wrong required id |
| `VIDEO_LENGTH` | dormant | `video.duration` / `video_duration` | Would be certain, but the duration is not fetched/stored, and never fetched for YouTube | a duration signal that is discarded today; YouTube has none fetched |
| `POSTING_WINDOW` | ranked | `createTime`/`taken_at` (discarded) or `postedAt` (2% populated) | Certain IF the timestamp is stored; already enforced at submit for freshness | timestamp discarded for 98% of clips; local-offset confusion |
| `LOGO_PRESENT_THROUGHOUT` / overlay / burned-text | ranked | video pixels | JUDGEMENT (cover frame proves t=0 only) | a logo present at t=0 but gone later; OCR miss on 480p |
| `EDIT_QUALITY` | human | none | JUDGEMENT | n/a |

**The owner's absolute rule (BL-518): only machine-certain violations may auto-reject.** The one certain class in production, caption tokens, is exactly the class **R-2 measured at 11.05% false rejection** on 240 human-reviewed clips (required_hashtag 8.95%, caption_text 9.47%), which the owner rejected as far too high. R-2's reason was not a checker bug: humans approved 85% of the clips that broke the hashtag rule, so automating it would invent a policy the reviewers do not enforce. **So even the one machine-certain rule we can run is not safe to auto-reject on today's evidence.** For every rule called certain above, the stated failure modes are what would have to be true for it to wrongly punish an honest clipper.

## PART 4 — the timing problem

**Caption and sound are captured exactly once, at submit, and never refreshed.** The provider `raw` is fetched in `clipper-submit-core.ts` at submit; `extractClipMetadata` + the shadow write run only in the submit route's `after()` block (`clips/route.ts:912-962`). The tracking cron (`tracking.ts`, and the YouTube/TikTok/IG stats-batch paths) re-fetches only the numeric counts into `clip_stats` (views/likes/comments/shares); it does **not** re-read caption, sound, or the raw item, and it never re-runs the shadow evaluator.

Consequences for a rule engine:
* A clipper who fixes a caption a minute after posting is judged on the submit-time caption, not the fixed one, and would be wrongly flagged.
* A clipper who removes a required tag or swaps the sound after approval is never re-checked, so the rule is silently unenforced post-approval.

**What this means: judge at submit for ranking, but any auto-reject or enforcement must re-check on a later tick, not trust the submit snapshot.** A re-check needs one full-item provider call per clip per re-check (LamaTok/HikerAPI media, ~$0.001 to $0.10 each; YouTube free within quota), on top of the count-only fetch the cron already does. Re-checking every clip every tick is the expensive extreme; a single re-check a few hours after submit (catching same-day caption edits) is the cheap middle. The cover-frame check is a submit-time snapshot only and cannot see later edits at all.

## PART 5 — what is missing, ranked by how much it blocks

1. **Storing the fields already fetched (highest value, lowest cost, unblocks everything).** Persist caption, sound id, hashtags, duration and the post timestamp at submit. Today only the shadow table captures caption+soundId, and only when a `rulesJson` exists, and it holds 0 rows. Columns/rows to add: extend `rule_shadow_decisions` capture to all submits (or a small per-clip metadata row), and fix IG sound extraction (nested `clips_metadata.music_info.music_asset_info.id`).
2. **A measured false-rejection rate (blocks turning anything on).** `rule_shadow_decisions` is empty; BL-659 estimated 2 to 3 months at current volume to accumulate enough would-reject cases (roughly one or two a day). **Broadening structured rules gathers data faster:** only 6 campaigns carry an auto_reject caption rule; adding `REQUIRED_CAPTION_TOKENS` (and, for TikTok, a `REQUIRED_SOUND`) rule to more active campaigns would reach a judgeable sample in weeks. That is a product choice, not a code gap.
3. **The reject code path itself (deliberately absent).** `RULES_AUTO_REJECT_LIVE` exists, defaults off, and gates nothing; there is no code that rejects/flags/status-changes a clip from a verdict. Enabling needs a measured accepted rate AND a new path built behind the flag.
4. **Short-link resolution for TikTok (blocks the sound rule on 69% of clips).** The stored `/t/` link 500s at LamaTok; resolving it to canonical before matching a sound id is required.
5. **Duration for YouTube and for all platforms into the DB (blocks VIDEO_LENGTH).** Add `contentDetails` to the YT call; store the duration the other two already return.
6. **Post timestamp into the DB (blocks reliable POSTING_WINDOW and re-check timing).** `createTime`/`taken_at` are returned but `postedAt` is populated on only 2% of clips.
7. **Cannot be known from any provider:** whether a logo stays visible for the WHOLE video from a single cover frame (needs frame sampling, Tier C); a YouTube Short's sound identity (no id exists); a clipper's intent behind a caption edit.

## PART 6 — the verdict

**The three answers in one place.** (1) The submission model is `Clip`/`clips` and stores only the URL, the cover frame (30%), and metric snapshots in `clip_stats`; requirements live as prose in `campaigns.requirements` and as machine rules in `campaigns.rulesJson` (11 campaigns), and BL-659's `rule_shadow_decisions` holds the shadow verdicts (0 rows so far). (2) The sound id is NOT stored on any platform; it is fetched at submit and discarded, though TikTok returns a reliable `music.id` and Instagram a usable `audio_cluster_id`, while YouTube exposes none. (3) Do not add `bot_verdict`/`bot_reasons` columns to `clips`; `rule_shadow_decisions` already records the verdict, reasons, evidence, caption and sound, and adding columns would duplicate it and pollute the money model.

**Build FIRST:** start persisting, on every submit, the metadata the providers already return and we throw away, above all the TikTok `music.id` and the post timestamp, by extending the shadow capture to all submits and fixing the IG nested-sound extraction. This is free (no new vendor call), reversible, and it is the only way the false-rejection rate ever becomes measurable. In parallel, add a `REQUIRED_SOUND` rule to a few TikTok campaigns so the one genuinely machine-certain-and-safe check (a stable sound id equality) starts generating shadow data.

**Do NOT attempt yet:** auto-rejecting on caption tokens (R-2 measured 11.05% false rejection, and humans do not enforce the rule); any sound rule on YouTube (no id exists); any "throughout the video" pixel rule from the cover frame alone (it proves only t=0); and any auto-reject at all until a real, owner-accepted false-rejection rate exists and a reject path is built behind `RULES_AUTO_REJECT_LIVE`.

**Said plainly where a rule class cannot be checked reliably:** sound matching is certain on TikTok canonical URLs, only partial on Instagram (id present but not wired, and short of a code fix), and impossible on YouTube. Caption-token matching is machine-certain but has proven too false-positive-prone to auto-reject. Everything about the video's pixels beyond the first frame requires paid sampling and is a judgement, never a certainty.
