# BL-1182 — meme pages are sendable: 53 repost partners in their own file, and the "4 stranded addresses" were never sendable at all

**2026-08-08.** The operator's decision landed: meme pages get their own send file, because a
repost partner we *pay to post* is not an editor we *hire*, and the copy must differ. This
round built that file and audited what the verdict gate cuts alongside it.

Six things were asked for. Five are done. **The sixth — recovering the 4 stranded addresses —
is a refusal, and the refusal is the finding**: all four are role inboxes, and two independent
guards reject them for the same correct reason. That corrects BL-1179, which called them
"real, recoverable addresses" worth writing.

**$0.0060 of $1.00.** Master is byte-identical (md5 `c468b624…` before and after).

## 1. The meme-page send file

`clippershq/meme_send_list.py` → **`output/MEME_PAGES_BOT_READY.csv`, 53 rows**, plus
`MEME_PAGES_BOT_READY.meta.json`.

### 1.1 MX first, and it was not a formality

`tools/refresh_mx.py --from-master` ran before the build: **1,594 domains in 10.5s**, 45
certain-bounce entries. The table went 1,416 → 1,594.

That mattered more than the headline suggests. Of the **13 domains this file actually sends
to, 9 were not in the pre-refresh table at all**:

| | before refresh | after |
|---|---:|---:|
| domains in this file covered by the MX table | **4 of 13 (30.8%)** | **12 of 13 (92.3%)** |

All 9 came back `ok-MX`, so nothing was cut — but for 9 of 13 domains the suppression would
have been *vacuous*, which is exactly the BL-1002 shape (141 domains probed, 561 in the
export, five dead ones caught by nothing). A build refuses on a stale table.

The 13th, `massdrop.com`, came back `UNRESOLVED (rcode=2, SERVFAIL)` on a fresh probe — the
resolver failed, which is **not** the same as the domain being dead. This project's rule is
explicit that an absent domain is unknown and **unknown is never cut**, so blocking the whole
file on one SERVFAIL would be the worse failure. My first draft did refuse; that was wrong and
is now a loud warning, and the row travels with an `mx_unknown` flag so a sender can see it.

### 1.2 The ladder, with nothing weakened

Every address is re-classified through the same `send_suppress.classify` the main list uses.
Nothing is read off a snapshot column.

| stage | rows |
|---|---:|
| master rows | 61,079 |
| meme-funnel rows | 62 |
| …carrying an address | 58 |
| cut: **role inbox** | 4 |
| cut: duplicate address (one network, two pages) | 1 |
| **KEPT** | **53** |

**Re-verified as a second pass over the finished 53** — not by re-reading the counters that
produced them, because a build that filters correctly and a build that *reports* filtering
correctly are different claims:

```
0 dead_mx     0 no_route     0 role     0 invalid
```

The selector is **positive**: `lead_kind=clipper` AND `source_hashtag` carries the
`meme_pages` tag. It is deliberately *not* "a clipper row whose verdict is blank" — that would
also sweep in 10 `asilentvoiceedit` / `5centimeterspersecond` rows, which are ordinary
hashtag-funnel clippers. A send file defined by a missing value is one schema change away from
mailing the wrong population.

The one duplicate is real and worth knowing: `themovie_lab6.0` and `screenjunkiebe` share a
single address. That is a network running two pages from one inbox, so it is **one send**.

### 1.3 The superset property

| | rows |
|---|---:|
| `ALL_BOT_READY.csv` (primary) | 3,977 |
| `MEME_PAGES_BOT_READY.csv` | 53 |
| **addresses in both** | **0** |

Checked twice: during the build (the primary wins every collision, and the count is recorded)
and again **on the files on disk** afterwards, because the property that matters is the one
true of the artifacts, not of the intent. `check_no_overlap()` is also a test that runs on
every suite pass.

Both files' metadata carries row count, build time and staleness — `this_file` and
`primary_file` side by side, so the operator can see the state of the *pair*. Staleness is
computed on render, never stored as a flag, per `all_bot_ready.staleness_of()`.

### 1.4 …and two existing guards fired, correctly, against the new file

Building the file turned **two suites red**, and both were right to go red:

```
tests/test_send_superset.py      53 address(es) in output/ are outside ALL_BOT_READY.csv
                                 and were never classified
tests/test_send_list_rebuild.py  addresses reachable outside the primary = a double-send:
                                 {'MEME_PAGES_BOT_READY.csv': 53}
```

Both encode the old world's rule — **"`ALL_BOT_READY.csv` is a strict SUPERSET of every other
send file"** — which was correct while there was one audience: any second file was then a pure
double-send. The operator's decision changes the invariant, and the brief states the new one
in its own words ("no address may appear in both files"). Written out:

```
old:   primary  ⊇  every other output CSV
new:   primary  ∪  sanctioned second file  =  everything sendable
       primary  ∩  sanctioned second file  =  ∅
```

**I did not silence the guards.** Adding 53 fingerprints to `KNOWN_EXCLUDED` would have been
the easy red-to-green move and a lie — that list means "correctly excluded stale-export
residue", and these are a live, sanctioned send file. Instead both guards learned the concept:
`SANCTIONED_SECOND_SEND_FILES` in `test_send_superset.py` (the authority;
`test_send_list_rebuild.py` imports it rather than keeping a second list that must agree), and
**listing a file buys it exactly one thing** — the right to hold addresses the primary lacks.
Three properties are asserted rather than assumed:

- **disjointness** — a sanctioned file sharing an address with the primary is still a failure
- **not a blanket exemption** — it stays inside `_live_suppressed`'s scan, so it may not carry
  an address suppression excludes. This is the exact hole `DIRECT_SEND.csv` sat in for weeks
  (BL-1099): recorded, and still one double-click from ten certain bounces
- **the detector still detects** — `test_this_check_can_detect_a_new_file` plants an unknown
  file every run and requires the guard to catch it. If the new allowlist ever swallowed an
  unknown file, that test is where it shows

## 2. The 4 stranded addresses: re-resolved, and correctly refused

They were re-resolved (5 targets, derived from the defect's shape rather than hard-coded —
"a page the seen-set says yielded an address, whose master row carries none"):

| handle | address | path |
|---|---|---|
| `meysamderis` | `contact@` its own domain | business button |
| `rascals` | `team@` its own domain | business button |
| `songss` | `hello@` a company domain | bio text |
| `stayunsupervised` | `team.` + handle, free provider | bio text |
| `bccoberlin` | SoundCloud site boilerplate | bio-link — quarantined, not written |

`crossdedup.append_leads` reported **"4 merged"** and landed **zero**. Master was byte-identical
afterwards. The verify step caught it precisely because BL-1179's lesson was that a merge count
is not evidence — so this round checked the field on disk rather than the counter.

**The cause is not a bug.** All four are role inboxes:

```
contact@…   team@…   hello@…   team.<handle>@…      ->  role_policy.quality() == "role"
```

Two independent guards refuse them, both correctly and both by design:

- `crossdedup.fill_missing_email` **rule 3** — "never promote a role inbox". A role address
  produces no identity keys, so it cannot be written as one. Its docstring calls this out as
  the thing that "must not become the back door that admits it". Forcing them in would be
  exactly that back door.
- `send_suppress.classify` returns `exclude=True, reasons=('role_inbox',)` for all four — so
  even if written, they would be cut from *both* send files, including the one this round
  just built.

**This corrects BL-1179**, which reported them as "real, recoverable addresses" and framed the
non-write as blocked by the verdict gate. They are real addresses; they were never sendable,
and the gate was not what stopped them. I did not override either guard.

**The decision this leaves the operator**, priced: a meme page is a *business*, and for a
business `contact@` or `team@` is often the correct address — `email_finder.find_email`
already argues exactly this for creator profiles, passing `keep_role=True` so a `support@`
address on a band's own domain is kept-and-flagged rather than dropped. The brief required "0 role
addresses survive" and that is what shipped. Relaxing it **for this file only** is one flag:

| | rows | risk |
|---|---:|---|
| current — `--include-role` off | **53** | none; matches the main list |
| `--include-role` on | **57** (+4) | role inboxes are shared and unattributable; a reply may come from anyone |

The four recovered addresses are in `scratch/bl1182_recover.json` and land the moment that
flag flips.

## 3. The other 1,211: 40 UNSURE leads, hand-read

The gate cuts four populations. Meme pages now have a file. The question left is whether the
**619 UNSURE** rows (`editor_pct` 20–39) are a bigger loss than everything else here.

Sample: **every 15th row of the handle-sorted population** — reproducible, and spread across
every funnel, tag and date rather than clustered on one day. All 40 read individually
(`scratch/bl1182_unsure_labels.json` carries a one-line reason for each).

| verdict | n | share | 95% CI | implied population of 619 |
|---|---:|---:|---|---|
| **EDITOR** — positive evidence | 3 | 7.5% | 2.6–19.9% | **46** [16–123] |
| **POSSIBLE** — edit hashtag + high view ratio, bio silent | 11 | 27.5% | 16.1–42.8% | 170 [100–265] |
| **NOT-EDITOR** — bio states another business | 26 | 65.0% | 49.5–77.9% | 402 [306–482] |

**The verdict on that population: the classifier is mostly right, and the gate is not hiding a
second catastrophe.** Two thirds are plainly other businesses — booktok, travel, beauty,
podcasting, cosplay, astrology, photography, a Real Madrid fan community, an AI dance
character. This is not the meme-page situation, where 58 rows were cut for failing a question
nobody asked them; these were asked the right question and answered it.

But it is not zero either. The three clear editors are unambiguous:

- `elisabethedit_` — handle ends `-edit_`, the classifier itself logged `core_edit`, scored 35
- `haikynal` — anime edits at a 62.4x view ratio on 51k followers, **selling presets via payhip**
- `thevespertinne` — "📧 for commissions !!", `#lalalandedit`, a **506.3x** view ratio

Each is a working editor sitting five points under an arbitrary threshold. At the point
estimate that is ~46 editors; the interval runs 16–123.

**What I am not claiming.** This is a *bio* read, not a video read. Editors frequently never
say "editor" anywhere, so NOT-EDITOR is reliable (a stated other business is real evidence)
while POSSIBLE is genuinely unresolved — not a soft yes. **The EDITOR count is a floor and the
NOT-EDITOR count a ceiling.** Settling the 11 POSSIBLE means watching their posts, which is a
clip-walk, not a bio read.

**Recommendation, not an action:** do not open the gate to UNSURE wholesale — that mails ~400
people whose business is something else. The 506x/62x view ratios are the signal that
separated all three confirmed editors from the noise, and `editor_pct` already records them.
A ratio-based rescue of the top band is worth measuring; this round did not, and it is not
what the brief asked for.

## 4. The email-source labels are split

`meme_finder.resolve_contact` stamped both sources `instagram:bio`, which is why every report
this funnel produced said "17%, all from the bio" — when the measurement was **button 40 hits,
bio text 30, and the button the SOLE source for 31 of the 61 addresses (51%)**.

```
instagram:bio   ->   instagram:business-field   (the Professional-account contact BUTTON)
                     instagram:bio-text         (an address typed into the caption)
```

Recovered the way `email_finder.find_email` already does it: if the chosen address appears
verbatim in the lowercased bio it was typed there, otherwise it came from the structured
field. Visible immediately in this round's own recovery output — `meysamderis` and `rascals`
came from the button, `songss` and `stayunsupervised` from bio text.

**Nothing downstream changes.** The quarantine keys off `bio_parser.is_biolink_source`, and
both new labels sit outside it exactly as `instagram:bio` did (`bio-link` still inside).
Pinned by test, because 61 addresses would be quarantined if that ever stopped being true.

Also recorded, so nobody re-proposes a path that has already been measured and closed:
**230 of the 300 addressless pages publish no link at all.** 17% is a ceiling, not a gap.
Aggregators were worth **+1 real address (+0.28pp)** and name search **0 for 6** (six
namesakes; the one address found belonged to a stranger at a transit authority). Not
re-attempted.
