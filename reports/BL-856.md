**Why that is a hard stop rather than a caution.** `clip_library.append()` takes **no lock** — it relies on `O_APPEND` atomicity for single lines, which is exactly right for appending and useless for rewriting. A migration must read a whole shard and write it back, so anything appended between the read and the write is **lost**. There is no lock to take that an appender would respect. Running under a live writer does not risk a torn file; it risks silently deleting another round's rows.

So item 1 is delivered as **measurement + a tested tool, ready to run**, and everything else is complete.

## 4. The mechanism: derivation versioning

Nothing existed to answer *"which rows were computed under the old constant?"* — the only options were rewrite everything or miss rows. Now:

```python
DERIVED_FROM = {"format": ("SPEECH_MUSIC_MAX",)}

def derivation_token(name):   # short hash of the constants' CURRENT values
def stale_fields(record):     # which versioned fields were computed under different ones
```

Every record carrying a versioned field is stamped: `{"derivation": {"format": "f25f8f13"}}`. Change the constant and the token changes; a migration selects exactly the affected rows.

**An unstamped row reads as stale, deliberately.** It predates the marker, so its provenance is genuinely *unknown* — and treating unknown as current is precisely how a migration misses rows. A test pins that:

```python
def test_a_row_predating_the_marker_is_stale_not_assumed_good(self):
```

The pattern is borrowed from **BL-849's `vision_model`**, which already stores which model produced a row so a later model change is visible. This generalises it from models to constants.

**Only constant-backed fields are versioned**, and a test enforces it: versioning pure arithmetic would invite a pointless migration, and it cannot express a *detector* change — which is why the vision fields keep their own `vision_model` instead.

**8 new tests**, including that the token moves when the constant moves and moves back when it is restored.

## Honest limits

- **The migration has not been run on the live library.** 60 rows still store a `format` that routes a dialogue clip to muting. Nothing downstream is protected from that until it runs; the tool is ready and refuses to run unsafely.
- **The liveness guard narrows a race, it does not close one.** It requires 20 s of quiet plus a 6 s sampling window, and the per-shard size/mtime check aborts a shard that grew mid-computation. A writer that starts in the gap between the check and the rewrite would still be at risk. The guard is a safety interlock, not a lock — the real protection is not running concurrently.
- **`stale_fields()` only knows about constants in `clip_library`.** If the Silero VAD threshold, `repost_layout`'s constants, or `caption_parser`'s lexicon change, `speech_frac`, `layout` and `valence_text` go stale and this mechanism will not notice. Extending it means each of those modules exposing its own token.
- **The 60 stale rows are counted from a frozen snapshot** taken while the library was being appended to. The true number is ≥ 60 and rises with every row the live walk writes at the old threshold — though rows written *now* use the new constant, so the count is bounded by what was written before `bf53dc7`.
- **`clip_library.py` in this commit also carries BL-855's `CLIP_FIELDS` comment rewrite** — 85 of the 97 added lines. Mine are the 12 derivation lines. Same situation as BL-848 and BL-853: concurrent edits to one file, committed together rather than surgically separated under a live writer.
