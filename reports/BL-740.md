## What I could do without the gate, and did: build the fix and prove it

`enrich_links.py` has been untouched since 11:33:26 — over five hours — so file contention is
no longer the live risk. But applying an unverified-in-production change to the scrape path
*while a funnel process is misbehaving* is the wrong moment: if that process dies and anything
restarts the funnel, it picks up a change whose live behaviour has never been measured.

So the fix was written **outside the repository** and grafted onto the real module for
testing, so that every helper it calls (`_UA`, `log`, `MAX_PARSE_CHARS`, `_host_of`) is the
shipping one. It lives at `scratchpad/fixed_fetch.py`.

### Verification — BL-738's own harness, both verdicts flipped

| test | before (BL-738) | **after (this round)** |
|---|---|---|
| **A. 10-hop redirect chain** | 7.17s, *no chain deadline present* | **4.19s — BOUNDED**, stopped at hop 6 |
| **B. trickling server** (1 byte / 1.5s) | 40.52s, returned `len 0` | **15.00s — BOUNDED**, returned `len 11` |
| C. control, single hop | 0.61s, html + email parsed | 0.61s, html + email parsed — **unchanged** |

Case B is the one worth pausing on. The old code held a worker for **40.5 seconds and returned
nothing at all**. The new code stops at exactly the 15s deadline **and returns the bytes it had
already paid for**. Strictly better on both axes.

### The redirect cap does not cost recall — measured, not assumed

`DEFAULT_MAX_REDIRECTS = 5` drops chains, so I measured which ones, old versus new against the
same server:

| chain depth | old | new |
|---|---|---|
| 0, 1, 2, 3, 4, 5 hops | html returned | **html returned — identical** |
| 6, 8 hops | html returned | **None (cap fires)** |

**Nothing changes up to 5 redirects.** Only 6+ are abandoned, which is the intended trade and
the reason BL-738 picked 5. A legitimate artist site behind six redirects would now be lost;
on this evidence that population is the affiliate chains (`kqzyfj.com`, `ffm.to`, `strms.net`)
BL-730 identified, not real sites.

### One deliberate departure from the brief, and why

The brief says *"when remaining <= 0, log and return None."* That is correct **before** a
request is issued — there is nothing to return. But when the deadline expires **part-way
through reading a body**, this implementation returns the bytes already received instead of
None.

Reasoning: the module already truncates every page at `MAX_PARSE_CHARS`, so a partial page is
the *normal* parsing case, and an email near the top of a slow page is still a real email.
Discarding a body already paid for would be buying speed with recall, which the brief
explicitly forbids. Case B shows the effect: `len 0` before, `len 11` after. **Flagging it
because it is a judgement call, not something the brief asked for** — say the word and it
becomes a hard `None`.
