## Part 1 — where your reasons went

**They never reached the file, and they are not recoverable.** I am sorry to open with that,
but it is the true answer and you should not be left hoping.

### Two independent measurements say the same thing

**1. The counter inside the sheet.** Every time the sheet saves a field it increments a
counter and stamps it on the row. So the highest number in your file is the total number of
saves your session performed:

| what happened | counter would read |
|---|---:|
| verdict only, one click per page | **100** |
| verdict **and** reason | ~200 |
| verdict and reason, both events firing | ~300 |
| **your file actually reads** | **101** |

One save per page. The reason box never saved, not once, on any of the 100.

**2. Your browser's own memory.** I found the sheet's saved state still sitting in Chrome
(`Profile 28`, key `bl1296_marks_v1`) and read it back:

```
{"seq":101,"downloadedThrough":101,"marks":{"goet":{"handle":"goet",
 "verdict":"WANT","reason":"", …
```

An empty reason stored against a page you marked WANT — and the counters match your delivered
file exactly. So the loss happened **before anything was saved**, not in the download, not in
the merge, and not in my handling of it afterwards.

### That eliminates every cause on the list, including the likely-looking ones

| candidate | eliminated because |
|---|---|
| the field is never read on save | the download does read it; the column exists and was written, empty |
| the mark is built before the field is read | the save merges into the existing row rather than replacing it |
| a later write overwrote an earlier one | one save per page, and a save preserves the other fields |
| the download serialises a subset | `his_reason` is column three and it was written |
| the merge dropped the column | the raw bytes you sent already had it empty |
| written under a different name than the reader expects | writer and reader both use the same name |

### What I could not do, said plainly

**I could not reproduce it in a live browser.** The browser tool refuses `file://` URLs, and
when I served a harness carrying the sheet's own JavaScript over `127.0.0.1` the tool's own
context returned `SecurityError` on local storage and could not see the page. So I do not have
a keystroke-level reproduction, and I will not claim one.

What remains, and I am telling you it is unproven: the text never reached the box the sheet
was listening to. Either the copy you typed into was not the copy that saves, or the typing
produced no event on that element. **The fix below is built so that it no longer matters which.**

### The fix, and why it closes the hole whatever the cause was

Three changes to `scratch/bl1296_sheet.py`:

1. **It saves on every keystroke.** The old sheet only saved when the box **lost focus** — so
   a reason typed and never clicked away from was never stored, and nothing said so. The two
   old events are kept as well, because a paste is not always reported as typing.
2. **Every row now shows a receipt for the reason**, not just the verdict: *"reason saved
   (94 chars)"* in green, or **"REASON NOT SAVED — 94 chars on screen, 0 in the file"** in red,
   on the row where it happened. The old counter went up when the **verdict** landed, so a
   page with a lost reason looked identical to a finished one.
3. **The download reconciles the screen against the store before writing.** If any box has
   text the file does not, it saves it and says so in the blocking banner. That check would
   have caught this on the day, whatever the input-time cause.

### The multiplications, shown

**The unit price is ledger-confirmed to the cent:**

```
spend.json label bl1300_receipt, 9 rows
  calls   8+3+5+5+4+6+4+4+6                                    = 45 billed requests
  dollars 0.0048+0.0018+0.0030+0.0030+0.0024+0.0036+0.0024+0.0024+0.0036 = $0.027000
  $0.027000 / 45                                               = $0.000600 per request
```

**Instagram, per page fetched:**

```
0.043 discovery (amortised) + 1.000 profile + 0.880 posts = 1.923 calls
1.923 x $0.000600 x 1.062 billing multiplier               = $0.0012253 per page
$0.0012253 / 0.280 want rate x 1000                        = $4.38 per 1,000 wanted
```

**Pages fetched is not pages judged, and they are kept apart.** On Instagram they happen to be
**1 : 1** — the discovery payload carries no free kill signal, so every page fetched is judged.
On **TikTok it is 1.75 : 1**: per 1,000 wanted, **4,722 pages discovered → 2,703 judged**,
because the free 62-day freshness gate discards 43% before anything is bought.

## Part 3 — the want rate: different pool, not worse supply

**Verdict: DIFFERENT POOL.** Four facts point the same way and none points at degradation.

**The decisive one: hold the marker constant.** The *judge* looked at both Instagram draws, and
its own want rate moved **20/100 → 13/100** — overlapping intervals, **p = 0.25. No measurable
movement.** If supply had genuinely halved, the judge would have seen it too. It did not.

**And "supply halved" is not statistically supported anyway:** 9% [4.8, 16.2] against
19% [12.5, 27.8] **overlap**, Fisher p = 0.065.

### The four rates are four different questions

| draw | rate | what it actually is |
|---|---:|---|
| **BL-1296 fresh 100** | **9%** | 0/100 overlap with anything; 100/100 from `suggested:<seed>`; 0/100 in the enriched pool; no email, no follower count in source; median 85,300 followers |
| BL-1257 | 19% | **not independently marked** — see below |
| BL-1298 Instagram | 28% | **not a fresh draw at all**: 100/100 are **re-marks** of pages already shown to him (33 from BL-1257 + 67 from the 623) |
| BL-1298 TikTok | 37% | his own hand |
| TikTok "63%" | — | **the judge grading itself.** On the 24 handles the two sets share, the judge wants 66.7% and he wants 33.3%, McNemar p = 0.021 |

**Why the 19% cannot be used for anything.** That file has no field in which he wrote WANT. It
stores GOOD 97 / BAD 3 beside the judge's own WANT 20 / REJECT 80, and the only route to a rate
is combining them. Because he pressed GOOD on 97, **97 of the 100 rows are the judge's verdict
copied verbatim** — the derived rate is arithmetically trapped in [17, 21] around the judge's
own 20% whatever he thought. It cannot fail. (It is not *wrong*: on 33 of those pages he later
re-marked from scratch, the derivation gives 6 and his own hand gives 7. It is *not independent*.)

**Two more facts against degradation.** Restricting the fresh draw to BL-1257's exact follower
range still gives **5/60 = 8.3%**, so it is not account size. And the two captures are **30
hours apart** — nothing halves in 30 hours.

**One real depletion mechanism does exist and I will not dismiss it:** the fresh draw came from
the residue after excluding 5,003 already-seen handles, so the best pages may already have been
skimmed. But it is perfectly confounded with the route change, and seed re-use is small (9 of
63 traceable pages, 5 shared seeds of 39). **It cannot be attributed.**

### Which rate to plan with

| question | rate | pages judged per wanted page |
|---|---|---:|
| **new discovery** — find pages I do not have | **9.0% [4.8, 16.2]** | **11.1** (6.2–20.8) |
| **the enriched backlog** — work the send list | **28.0% [20.1, 37.5]** | **3.6** (2.7–5.0) |
| never use | 19.0% | 5.3 — 97% the judge's own answer |

The 11.1-vs-3.6 spread is **3.1x between populations, not a change over time**. And note
judged ≠ fetched: the fresh draw captured **135** pages to get 100 judgeable, so it is really
**15.0 pages fetched** per wanted page there.

**Caveat on the 9%:** it rests on an n of **nine**. A second unselected hundred is worth more
than any further re-analysis of these five rates.

**No pre-judge gate is proposed.** Every one tested kills wanted pages.
