### 1.1 The 480-minute rule does not do what the brief asked of it

The brief said to "end the dead ones under the 480-minute takeover rule". That rule cannot
end a claim, and the tool says so in capitals:

> `THIS ESCALATES. IT DOES NOT EXPIRE ANYTHING.` … What crosses 480 minutes is the path's
> PROTECTION, not the claim.

It also has **two** conditions, and the second has the teeth: the path must be **clean in
git**. BL-1138 and BL-1162 were both dirty, so takeover was refused by design — and
`claim.py end` independently refuses while a round's own declared paths are dirty, because
"released is NOT committed".

So the sequence the tree actually required was the inverse of the brief's: **land the work
first, then release.** That is what was done, and it is why §1 and §2 are one piece of work
rather than two.

- **BL-1195** was clean and published — released directly, no force, nothing to land.
- **BL-1162** and **BL-1138** were landed (§2.1, §2.2) and *then* released.

**No claim was force-released and none was ended while dirty.** Three cleared; four rounds
remain in flight, all genuinely live.

### 2.3 The real attribution hole — and it is growing

`round_of_path()` reads the file's **basename**. Measured:

```
scratch/bl1178_ocr.py     -> BL-1178      (prefix pattern, basename)
reports/BL-1137.md        -> BL-1137      (literal pattern, basename)
scratch/bl1223/defects.py -> None         <-- the hole
scratch/bl1223            -> None         <-- even the directory itself
scratch/bl1232/sized.jsonl-> None
```

`scratch/bl1223` maps to nobody because `_PATH_ROUND_PREFIX` requires a separator *after*
the digits (`^(bl|mb|memebot|infra)(\d+)[_.\-]`), and a bare directory name has none.

**Every round currently in flight uses that convention.** BL-1232, BL-1233, BL-1234 and
BL-1235 all declared `scratch/blNNNN` directories. The moment any of them departs, its
scratch work is unattributable — which is precisely how BL-1223's hand audit sat invisible.

This is *not* the "0 of 62,529 product files" the brief quoted. That figure is the
docstring's own evidence that the convention **cannot misfire on product code**, which is
what makes the guard safe to act on. The hole is the directory form, and it did not exist
when the measurement was taken.

**Not fixed here.** `tools/claim.py` was held by no round, but changing `round_of_path` is a
change to the guard every round's commit passes through, on a day with four rounds in
flight and a suite already carrying reds. It is written down instead, with the one-line
shape of the fix: consult the path's **directories** as well as its basename, most-specific
first. That belongs to a round that can watch the suite alone.

## 3. `verify_claims.py` reads HEAD — the gap was that nothing held it there

Probed against a throwaway git repo (`scratch/bl1234/probe_verify.py`):

```
func  pkg/m.py::shipped_thing   working tree only  -> FAIL
file  pkg/new_file.py           untracked          -> FAIL
func  pkg/m.py::shipped_thing   after commit       -> PASS
```

Every symbol check routes through `head_text()` → `git show HEAD:<path>`.

**The real defect the brief was circling:** the property was true by inspection only. One
edit swapping `head_text()` for `open()` would have made the brief's claim true, turned
every manifest in `docs/claims/` into a check of its own author's working tree — and gone
green.

`tests/test_verify_claims_head.py`, **9 tests, all green**:

- uncommitted FAILS *and* committed PASSES, for `func`, `const`, `file`, `column`, `menu`.
  The pair matters — an "always FAIL" bug satisfies either half alone.
- the **inverse**: a committed claim keeps verifying while the shared tree is mid-edit, and
  a tracked file keeps verifying when its working-tree copy is deleted outright. This is
  why HEAD-reading is a guarantee, not a preference: otherwise one round's half-finished
  refactor turns another round's published manifest red.
- the **two** documented live-file exceptions are pinned so they stay two: `check_config`
  reads the live `config.json` for key *presence* (untracked, holds credentials — only the
  READ side is HEAD-verified), and `check_column … +master` reads the live
  `master_leads.csv` header.

Real repos throughout, not mocks: the property under test is what `git show HEAD:` does, so
mocking the git call would test the mock. The finding is also written into the tool's own
docstring, where the next round arriving with this brief will read it.

**One cosmetic defect found, not fixed:** `tools/commit.py` prints its unclaimed-paths
warning as a literal `%d path(s)` — an unformatted placeholder. Cosmetic only; the path
list beside it is correct.

## 4. The `claude-mem` plugin — how to remove it, and what depends on it

**Nothing in this project depends on it.** Zero references to `claude-mem`, `thedotmack` or
port `37777` in `tools/`, `docs/`, `clippershq/`, `tests/` or `dashboard/`. The project's
own `.claude/settings.json` declares exactly one hook — `pipguard.py` on `PreToolUse:Bash` —
and it is unrelated. The `memory/MEMORY.md` the operator relies on is Claude Code's native
auto-memory, a different system entirely.

### 4.1 It has not stored anything since April

`~/.claude-mem/claude-mem.db` was last written **2026-04-20 15:31** — nearly four months
ago. It is not a memory system that occasionally fails; it is a memory system that has been
storing nothing while still executing a hook on **every single tool call**.

### 4.2 Its own log names the cause

```
[2026-08-12 20:47] [WARN ] Worker unavailable on Windows — skipping spawn
[2026-08-12 20:47] [WARN ] Worker failed to start before hook, handler will proceed gracefully
[2026-08-12 20:36] [ERROR] Worker failed to start (health check timeout)
```

Confirmed live during this round: `curl http://localhost:37777/health` → **exit 7, connection
refused**; nothing is listening. Today's log alone is **21,198 lines — 20,669 WARN and 270
ERROR** — and the log directory holds **61 MB across 115 files**.

### 4.3 Why `SessionEnd` specifically is the one that kills sessions

The plugin registers **seven** hook points, not one: `Setup`, `SessionStart` (×3),
`UserPromptSubmit`, `PostToolUse` (matcher `*`), `PreToolUse` (matcher `Read`, timeout
**2000 s**), `Stop`, `SessionEnd`.

`SessionStart`'s worker calls are guarded **twice** — wrapped in `if curl -sf …/health;
then … || true; fi`. **`SessionEnd` has neither guard:** it calls the worker
unconditionally, with no health precondition and no `|| true`, on a 30-second timeout.
That asymmetry is the whole failure. The worker never runs on Windows, so the one hook that
does not tolerate its absence fires at exactly the moment a session is trying to close.

### 4.4 Removal — least invasive first

**Option A (recommended, reversible, no data loss).** Disable it; keep everything on disk.
In `~/.claude/settings.json`, under `enabledPlugins`, change:

```json
"claude-mem@thedotmack": true      →      "claude-mem@thedotmack": false
```

That single edit stops all seven hooks and the MCP server. Restart Claude Code. Nothing
else in that file needs to change; the other six plugins are independent.

**Option B (full removal).** After A is confirmed good:

```bash
# 1. remove the marketplace entry from ~/.claude/settings.json:
#    extraKnownMarketplaces -> delete the "thedotmack" key
# 2. remove the plugin record from ~/.claude/plugins/installed_plugins.json:
#    plugins -> delete the "claude-mem@thedotmack" key
# 3. delete the payload and the store
rm -rf ~/.claude/plugins/cache/thedotmack        # 572 MB
rm -rf ~/.claude/plugins/data/claude-mem-thedotmack
rm -rf ~/.claude/plugins/data/claude-mem-inline
rm -rf ~/.claude-mem                             #  63 MB  <-- the DB; back up first if wanted
```

**Reclaims ~635 MB**, which is not nothing on the machine that hit 100 % disk on 2026-08-03.

**What is lost, stated honestly.** Removing it withdraws seven skills (`claude-mem:do`,
`make-plan`, `mem-search`, `smart-explore`, `knowledge-agent`, `timeline-report`,
`version-bump`) and the `mcp-search` MCP tools. None is used by this project, and all of
them query a database frozen since April, so what is withdrawn is already empty. Keep
`~/.claude-mem/claude-mem.db` if the pre-April observations are wanted; nothing else in the
tree reads it.
