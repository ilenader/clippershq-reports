## 1. THE RULE, IMPORTED

### Where it went, and why not into the scanner

`scratch/scan_report_for_secrets.py` **cannot be imported**: it parses `sys.argv`,
`sys.exit()`s when there is no argument, and scans a report at import time. It is a script.
So "import the scanner's rule" needs a shared home, and this repo already decided where that
is — `control.py:39` records that the scanner *"used to keep a hand-copied duplicate"* of
`SECRET_BLOCKS` and now imports it from `secrets_guard`. Same problem, same answer.

So `RUN_MIN`, `ENTROPY_MIN`, `entropy`, `longest_run`, `looks_like_credential`,
`is_cited_hash`, `is_definition_name` and a new `credential_tokens` live in `secrets_guard`,
with the full measured rationale carried over rather than summarised. `decision_log` imports
`credential_tokens` and calls it. **No number and no regex is re-typed on the consumer side**,
and a test asserts that structurally, because a copy passes every behavioural test on the day
it is made and drifts the week after.

### The scanner still has its own copy, and that is now SELF-REPORTING

Its file is BL-1035's. So instead of taking it, the duplication is made loud:
`tests/test_decision_log_redaction.TheTwoImplementationsAgree` extracts the scanner's own
`_looks_like_credential` (compiling only the rule, never the top level) and compares it to the
canonical one **literal by literal** over the whole plant corpus, plus asserts both floors are
the same number.

```
14 literal(s) compared, 0 disagreement(s)
```

**Three lines close it for good** — the same `try/except` the scanner already uses for
`SECRET_BLOCKS`, ten lines above where the rule sits. When that lands, the agreement test keeps
passing and becomes trivially true, which is the right way for it to retire.

### And it refuses rather than degrading

If the import fails, `redact()` raises `RedactionUnavailable`. There is no safe fallback for a
missing rule: quietly restoring the old behaviour restores exactly the gap BL-1029 found, and
nothing says so. Both directions are tested — it raises when the rule is gone, and it works
again when it is back.

## 3. THE FIX I WROTE, MEASURED, AND THREW AWAY

**A CUID2 row id IS credential-shaped** — 24-32 lowercase alphanumeric, letters and digits,
entropy well over 3.0. Both deciders flag it; verified by running the scanner over a report
containing one, which exits `FAIL: credential-shaped literal`. **A gap the rule already had,
surfaced by the plants rather than introduced by importing it.**

So I wrote the exemption, by LINE CONTEXT exactly like `is_cited_hash` — the shape plus a
row/record/id word on the line. Then I measured what it would cost, counting and never
printing:

```
18 live values under the secret blocks, lengths 11..73
 3 MATCH THE ROW-ID SHAPE EXACTLY, and all three are credential-NAMED leaves:
      api.key                   32 chars
      ig_api.key                32 chars
      twitch_api.client_secret  30 chars
```

`decision_log` writes `clip=<id>` beside nearly every drop reason, so the id word is on the
line constantly. **The exemption would have let three real keys through in precisely the place
this round exists to seal.** It is the same trap as "require an uppercase letter" — which
blinds the rule to 5 of 8 live all-lowercase keys — wearing a line-context costume.

**Removed.** The measurement is recorded where the code was, the cost is stated (a CUID2 in a
log or a report is redacted; currently free, since no real id here is credential-shaped), and
a test asserts the conjunction: *the exemption must not exist while the count is non-zero*. If
a future round adds it anyway, that test goes red and makes them read the number first.

## 4. THREE MORE GAPS, ALL IN THE FUNCTION I WAS ALREADY FIXING

### (a) The needle floor was a FOURTH number, and it was corrupting live log lines

`_secret_values()` used a hardcoded **`>= 8`**. This repo documents three credential-length
numbers and explains why they differ; this was a fourth nobody had reconciled. **Four live
config values sit under it**, and `secrets_guard`'s own comment predicted what happens next —
*"as redaction needles they matched unrelated source text"*.

Measured on the real stage, not imagined:

```
before:  retry with [REDACTED-SECRET]: Bearer ...     <- a 13-char config value ate `Authorization`
after :  retry with Authorization: Bearer ...
```

**That is the mirror defect**, and it is not harmless: a redactor that corrupts ordinary lines
trains the reader to ignore the markers, and the operator loses the detail that would have told
him why a stage dropped rows. Fixed the same way — `floor = sg.CREDENTIAL_MIN_LEN`, imported.
Needles went 18 → 14.

### (b) `drop()`'s REASON was the one string on the class that was never redacted

`note()` was scrubbed. The stage `error` was scrubbed. The drop EXAMPLE was scrubbed two lines
below. **The reason sat between them untouched** — and it is the field most likely to be built
from an exception (`st.drop("upstream said: %s" % exc)`), where a 401 body routinely echoes the
key it rejected. Found by a test written to be thorough, not by reading.

Redacting it does not disturb aggregation: the reason is the grouping key, and the same secret
always renders to the same marker.

### (c) `run_id` and the stage `name` were unredacted too

The last two caller-supplied strings on the record. Realistically both are short literals and
the shape rule never touches them — asserted in both directions, so an ordinary `gating` and
`clip_render-1785681097` are untouched. **The point is that the rule is now "every
caller-supplied string" rather than "the ones somebody thought of"**, which is precisely how
(b) survived a review.

### The disagreements, demonstrated rather than asserted

**1. `secrets_guard.redact` vs `decision_log.redact` — a rotated key.** `secrets_guard` has
**no shape rule**: only config values and six vendor PREFIXES (`AIza`, `sk-`, `ghp_`, `hf_`,
`xox`, `Bearer`). A rotated key with no vendor prefix **survives** it. So `logs/run.log` can
still carry a key that the decision log now scrubs. **This is BL-1029's finding one module
over, and it is still open** — `credential_tokens` is now sitting in that very file, waiting
to be called by its own `redact()`.

The patch is three lines and it is **demonstrated, not proposed**:

```
secrets_guard.redact today  : key=<the 64-char key, verbatim and unredacted>
with the three lines added  : ***REDACTED***
and an ordinary log line    : GET /api/v1/clips?cursor=abc          (untouched)
```

Not applied here. That function backs the live `SecretRedactingFilter` on every handler in
the process, so widening it is a decision with its own blast radius and its own round —
naming it with a verified patch is the honest handoff, applying it under a different round's
brief is not.

> The first draft of this section pasted that transcript **with the key in it**, and the
> publish gate refused the report: `FAIL: credential-shaped literal`. The rule works on its
> own author, which is the only test of a gate that counts.

**2. Same pair — an env-var key.** Same gap, different door.

**3. scanner/public vs scanner/private — a lead address.** **AGREE BY DESIGN.** The private
repo is where lead data belongs. `decision_log` scrubs it regardless, because its output is
quoted publicly.

**4. `decision_log` vs the scanner — a CUID2 row id.** **AGREE, and both are wrong in the same
direction.** A stated, measured cost rather than a disagreement — see §3.

## 6. ARTEFACTS, NOT JUST REPORTS

The standing precedent: a redacted REPORT beside an unredacted ARTEFACT has happened twice.

| writer | scrubbed by | covered |
|---|---|---|
| `decision_log.write` → `dashboard/static/runs.json` | `redact()` at record time | **yes** |
| `publish_report.py` → the public clone | the scanner, public profile | **yes** |
| **`logs/run.log`** | `SecretRedactingFilter` — values + vendor prefixes, **no shape rule** | **NO** |
| **any `scratch/*.json` a round commits** | **nothing automatic** — the private-profile scan is a step a round must remember | **NO** |

**The two uncovered rows are the two that leaked before.** Naming them is what this round can
do without taking two other rounds' files; the first is three lines in `secrets_guard.redact`,
and the second is a pre-commit hook question, not a redaction one.

### And this round's own artefacts pass the rule it ships

Item 5's precedent applied to me, not just quoted. **Every file this round writes was run
through the private-profile scanner** — the report, the two JSON artefacts, the stage log, the
two harnesses and the test suite:

```
scratch/BL-1038.md · bl1038_plants.py · bl1038_plants.json
bl1038_audit.py · bl1038_audit.json · bl1038_stage.log
tests/test_decision_log_redaction.py                       all PASS (private profile)
```

**Three of them failed the first time**, and the reason is worth keeping: a suite that tests a
credential detector cannot carry a credential-shaped literal, because the scanner cannot tell
a synthetic key from a real one — correctly. So the fixtures are **derived at run time** from
a seed rather than written down: still a real 64-character mixed-class high-entropy run when
the test executes, and no such run in the file on disk. Same trick the repo already uses for
lead fingerprints — prove the property without storing the thing.

Had I only scanned the report, three committed `scratch/` files would have carried key-shaped
literals. **That is the precedent, reproduced in miniature inside the round that was told
about it.**
