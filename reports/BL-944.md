## 5. Item 6: a true statement that answers a different question reads as coverage

Recorded in `docs/CORRECTIONS.md`, and it is the reason the last unguarded `os.replace` survived every audit that went looking for exactly it.

`main.safe_write_json` promised:

> *"CORRUPTION-PROOF write… **The live file can never be left corrupted.**"*

**Every word true, throughout.** It never corrupted anything. It **failed to write** — a complete, validated, fsynced temp file that was never installed, the caller's change absent from a file that parsed perfectly. Anyone auditing "is this write safe?" met a confident, accurate answer to *"can this leave a corrupted file?"* The question at issue was *"can this silently not happen?"*, and the docstring was **silent on it**. Silence beside a confident claim reads as coverage.

The same shape, twice more in the same sequence:

| the true statement | the question it does not answer |
|---|---|
| *"`os.replace` is atomic — never a torn row"* (`PRECONDITIONS.md`) | whether the **writer** succeeded. Measured: **up to 85%** of master rewrites did not land. |
| *"piping `publish_report.py` is harmless"* (BL-906, mine) | whether the operator still sees the refusal. Piped exits 0, direct exits 1. |

**The rule:** when a docstring makes a confident guarantee, ask what failure it is **not** claiming to prevent. A guarantee on one axis is not a guarantee on every axis, and the absence of a second guarantee is not its presence.

**And the entry names an example of doing it right** — BL-933's own cap docstring, from this round:

> *"At the shipped price of $0.00/call this can never fire, and that is the honest behaviour: a cap on a funnel that spends nothing should not invent a limit."*

A reader cannot mistake that for a working dollar governor. It states its own inertness, which is precisely what the tiktok cap never did.
