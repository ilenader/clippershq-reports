# BL-1057 — the tool survey: 61 candidates, 3 adoptions, 45 rejections with numbers

**No product code modified. No lead data uploaded. No credentials entered anywhere. $0.00
of the $2.00 paid budget spent** — every trial ran on free, locally-installed software.

## The one number

> **RapidOCR is 168.3x faster than the shipped EasyOCR at IDENTICAL accuracy** on the 11
> frames where `vision_on_screen_text` says "empty" and a human found real text.
> Same machine, same load, same frames, same hand labels.
> A library-wide OCR sweep goes from **121.19 CPU-hours to 0.72**.

**The reframe that drove the ranking.** BL-1033 measured that selection fixes reading a
field filled 94–99.9% moved the output, and fixes reading a field filled 3.4–70.6% did not.
So the question is not "which tool detects watermarks best" — it is **which tool fills a
field that is currently blank**. Problems 2 and 3 are *the same field*
(`vision_on_screen_text`, read by three gates). That is why OCR economics, not OCR accuracy,
turned out to be the lever.

## 3. The top 3, with integration sketches

### 3.1 RapidOCR → `clippershq/clip_ocr.py`  (ADOPT)

**Where it plugs in.** `clip_ocr.py:59-66` builds a module-level `easyocr.Reader(["en"],
gpu=False, download_enabled=False)` behind a `reader()` singleton, and `ocr_frame(png)` is
the only call site. The swap is confined to those two functions; `gate_text_for`,
`handles_in` and `union_text` above them are untouched.

**What changes.** `SECONDS_PER_CLIP = 7.53` — the module's own declared cost — becomes
~0.95. That constant is read by callers budgeting sweeps, so it must change with the engine.

**What it buys, precisely.** *Not accuracy* — both engines scored 5/5 brand tokens and 11/11
any-text on our hand labels. It buys the ability to run OCR on the whole library in under an
hour instead of five days, which is what turns `vision_on_screen_text`'s 70.6% fill into
something that can approach 100%. By BL-1033's rule, fill is the gate on the entire loop.

**What could break.**
* `clip_ocr.py`'s stated **P=80.0/R=100 (handle cards)** and **P=50.0/R=14.3 (watermarks)**
  were measured with EasyOCR. They are a property of the *engine*, and this round only
  re-measured recall on 11 frames. **Those figures must be re-derived on the new engine
  before the module header is allowed to keep claiming them**, or the module lies.
* RapidOCR ships its own ONNX models (~80–300 MB) and resolves them at first call; the
  `download_enabled=False` posture that keeps EasyOCR offline needs an equivalent.
* The dependency guard exists because heavy vision packages drag numpy across the 2.0 ABI
  boundary. My install went to `--target`, not site-packages; a real adoption must go
  through `pipguard` and confirm numpy stays ≥2.0.

### 3.2 Buy a music catalogue  (ADOPT — a purchase, not a project)

**Where it plugs in.** `scratch/songs.json` — the operator's hand-marked store. Nothing in
code changes; the store grows from 4 entries to ~24.

**What it buys.** Park rate is **83.8% against four songs**. A rule matcher cannot place a
clip it has no candidate for; this is arithmetic, not an algorithm. Against a **$11.28
lifetime spend**, $13.99/mo (Uppbeat) or ~$20 one-off (AudioJungle, ~$1/track) is the
highest outcome-per-dollar in this survey.

**What could break.** Each new track needs a hand-marked hook window, which is the actual
labour. And the licence must be checked **per track** for short-form commercial reuse —
ccMixter and parts of Free Music Archive carry **NC clauses** that this system cannot use.

### 3.3 maigret → email discovery  (TRIAL FURTHER, not adopt)

**Where it would plug in.** After the bio parse fails to yield an address — the fallback the
operator described, but keyed on **identity rather than name**. A clipper exposing no
contact on TikTok often exposes one on a platform that does; maigret takes one username
across 3,000+ sites with no API key and "extracts all available information about the
account owner… including links to other accounts."

**Why it is not an ADOPT.** I have not measured it on our data, and I deliberately did not:
running it means touching real creators' profiles across thousands of sites, which is both a
data-egress question and a courtesy question the operator should answer first. **Rate limits,
false-positive rate on common handles, and yield are all unmeasured.** A real trial needs a
consented sample and a decision about traffic.

| **PySceneDetect / librosa / madmom / BeatNet / aubio for drop placement** | Cuts vs beats measured **1.52x vs 1.38x, a 12–12 per-clip tie** (BL-963). The famous 4.15x was **circular**. Hook windows are already hand-marked; MEMEBOT-105 landed a fixed 5 s. |
| **Essentia, Windmill, Reacher, MailSherpa** | **AGPL-3.0** — commercial-use flag. |
| **madmom, multi-delogo, aubio, Surya** | **GPL / academic-restricted** licences. |
| **n8n** | **Sustainable Use Licence** (restrictive); complex flows balloon past 2 GB. |
| **Temporal / Prefect / Airflow** | Permissive, but solve a problem we do not have — one box, one menu. A daemon and a database for nothing. |
| **facebookresearch/videoseal** | **Wrong problem.** It *embeds* invisible watermarks in our output; it does not detect a rival's visible brand card. |
| **All "watermark" removal tools** | Removal, not detection. The category name is misleading. |
| **Qwen2.5-VL / InternVL local** | No GPU. Paid vision is **$1.50–2.00 per 1,000 clips**; a 7B model on a loaded CPU box cannot beat that on wall clock, never mind electricity. |

| **Scrapfly / Apify / Bright Data / commercial verifiers** | **Data-egress**: the lead list or clip frames would leave this machine. |
| **PaddleOCR (direct)** | RapidOCR *is* PaddleOCR's models on ONNX Runtime without the PaddlePaddle dependency — adopting both is adopting the same thing twice. |

## 5. What I could NOT test, and why

**My own best idea — temporal persistence — is UNPROVEN, and I will not dress that up.**
`scratch/bl1057_persist.py` runs and is correct; the corpus defeated it:

```
frame dirs with >=4 frames        : 28
...of which carry a human verdict :  6
...of which are watermark positives: 0
```

The 30 multi-frame directories and the 61 hand verdicts barely intersect, and the
intersection contains **no watermark positives at all**. The four hand-labelled watermark
clips in `clip_verdicts.json` ("another page's watermark", "republishes a rival page's logo
+ verified tick", "it is another page's brand", "a rival's verified tick") have **no
multi-frame media on disk**; of BL-1027's 11, only 3 have an mp4 and only 2 of those are
watermark positives.

**Two positives cannot produce a precision figure.** With n=2 a Wilson interval spans almost
the entire range, and this project has already been burned by a confident number on a small
sample. The honest output is: *the experiment is built, the labels are missing, and the next
round should extract 8 frames for the four labelled positives before reading anything into
it.* Dead-canvas gating died at precision 0.23 against a 0.80 bar; this idea has not yet
earned the right to be compared to that.

**Also not tested:** maigret on real data (courtesy/egress decision belongs to the operator);
any paid API (would require entering a credential — forbidden, and none was entered);
Instaloader and curl_cffi against live Instagram (would mean scraping real profiles from this
machine mid-session with 8 rounds live).

## 7. Disk, and the cleanup

| | |
|---|---|
| C: before | **931 G total, 794 G used, 138 G free (86%)** |
| install size | `scratch/bl1057_work` = **307 MB** (rapidocr + onnxruntime + deps, via `pip --target`) |
| C: after cleanup | **795 G used, 137 G free (86%)** — `scratch/bl1057_work` **deleted, confirmed gone** |
| main environment | **untouched** — numpy stayed **2.3.2**; nothing entered site-packages |
| written to drive root | **nothing** (root folder count 146, none mine) |

**The drive shows 1 G MORE used after I deleted 307 MB, and that is not my accounting being
wrong — it is eight other rounds writing throughout.** A disk delta over a five-hour window
in a shared tree cannot attribute a single round's footprint, the same way a ledger delta
cannot attribute a round's cost (BL-995). What I can state exactly: my directory measured
307 MB, it is gone, and `ls -d` confirms it.

The install went through `clippershq/pipguard.py` rather than around it. A bare
`pip install` is blocked in this repo because two near-misses would have dropped numpy below
the 2.0 ABI boundary; `--python <venv>` is rejected by pip (the flag must precede the
subcommand, which pipguard cannot do), so `--target` was the isolated route that still let
the guard run its resolution check.
