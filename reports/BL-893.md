abandoned. It was the opposite: BL-849 had finished four hours before either of them looked.

## 4. A staleness signal that would actually work

The failures are now all documented, so the spec can be written against evidence rather than
intuition:

| candidate | why it fails | seen on |
|---|---|---|
| **age** | cries wolf immediately; BL-891 is live at 22 min, BL-849 is done at 361 | every round |
| **pid** | `claim.py` records the CLI's own pid, which exits at once — always dead | BL-880 |
| **literal declared path** | a rename or a sibling file makes real work invisible | **BL-849, above** |
| **instantaneous process scan** | rounds work in bursts of tool calls, not as daemons | this round |
| **completion marker only** | only **11 of 74** `scratch/*.log` files carry one (15%) | measured here |

**Spec — `claim.py brief --watch SECONDS`:**

1. **Resolve each round's own files by ROUND-ID PREFIX GLOB, not by literal path.**
   `scratch/bl849_label.py` → `scratch/bl849*`. One-line change, and on its own it fixes the
   false marker above.
2. **Sample content hashes** at `t0` and `t0+SECONDS`. Hash, not mtime: this tree is under
   OneDrive, where a sync daemon moves mtime without moving bytes.
3. Classify:
   - **MOVING** — any hash under a declared path changed in the window.
   - **IDLE** — nothing changed, newest write younger than `STALE_AFTER_MIN`.
   - **SETTLED** — nothing changed, newest write older than that. *Probably* done; ask.
   - **UNSTARTED** — no file has ever existed under any declared path or its prefix glob.
     This is the honest version of today's marker, and BL-849 would not have matched it.
4. **Bonus, never required:** if `scratch/<round-id>.log` exists and its tail matches
   `^(DONE|FLUSHED|COMPLETE)\b`, append `finished: <that line>`. **Measured at 11/74 logs**,
   so it can confirm a verdict and must not gate one. On BL-849 and BL-867 it would have
   printed the answer outright.
5. **Still never expire anything.** The tool's existing note is right: a long round is not an
   abandoned one, and only a human should decide which it is.

`tools/claim.py` is held by **BL-889** (16 min, live), so this is a spec and not a patch.

- **I did not contact either owner.** Recommending is as far as this goes.
- **The `DONE` lines are self-reported.** BL-849 says it processed 436 clips; I did not verify
  that against the library, which would mean reading rows a live writer is appending to.

  21:23, eight quiet samples in.

  modes, not a patch with a test behind it, and `tools/claim.py` is held by BL-889.
- **Who performed the 21:09:25 tidy-up is inferred**, not proven — BL-849's and BL-867's
  files share that timestamp to the second, which is consistent with one operation
  superseding one with the other, but no log states it.
- **The report number and the claim id diverge again**: I hold claim BL-893 and BL-892 was
  taken 30 seconds before I first tried it. Report numbers are being consumed faster than
  claims are.
