## 1. The amend guard

`tools/guard_amend.py`, wired as `tools/githooks/prepare-commit-msg` — git's only reliable amend signal is that hook being called with `$2="commit"` and a non-empty `$3`. A normal commit never triggers it, which I verified.

**The BL-820 scenario, reproduced in a throwaway repo and blocked by real `git commit --amend`:**

```
  AMEND REFUSED - this would take work that is not yours.

  THE INDEX CONTAINS FILES THAT ARE NOT IN THE COMMIT YOU ARE AMENDING.
  Amend commits the whole index, so these would be absorbed into
    "Another round's commit"
  under that message, attributed to that round, invisible to both:
      + my_file.py
```

HEAD stayed put; the amend did not happen; a subsequent ordinary commit went through untouched. The escape hatch `GUARD_AMEND_OK=1` is deliberate — BL-818 measured that a gate which cannot be bypassed gets bypassed by being uninstalled.

### Two defects found by testing it, both mine

- **It inspected the wrong repository.** The guard derived the repo from its own file path, so when the hook fired in the test repo it listed *this project's* staged files and *this project's* HEAD subject. It still refused — for the wrong repo's reasons. Now `git rev-parse --show-toplevel`. A guard that reports another repository's state is worse than none, because the message is confidently wrong.
- **`core.hooksPath` REPLACES `.git/hooks`; it does not add to it.** Installing silently disabled this repo's existing `pre-push` guard — BL-807's push protection. `--install` now migrates existing hooks first, and `pre-push` is version-controlled for the first time (`.git/hooks` is never cloned, so it was one fresh clone from being gone anyway).

### The false positive that mattered — caught by pointing it at myself

After committing, I ran the guard against my own round:

```
  HEAD MOVED SINCE BL-823 STARTED.
  HEAD is now 'Amend guard + a one-call measuring entry point'
  Amending it rewrites a commit that is very likely not yours.
```

**It was my own commit, from this round, made ninety seconds earlier.** A round's own commit makes HEAD newer than the round's start, so "newer than my start" flags *the commonest legitimate amend there is* — fixing a typo in the message of the commit you just made.

**That is exactly the cry-wolf failure BL-818 measured for the quiet-tree rule** (1 of 40 adoption). A guard that refuses normal work gets uninstalled, and then it protects nothing. Shipping it would have been worse than shipping nothing.

The corrected check refuses only when HEAD touches **files the round never declared** in its claim. A round that declared no files is skipped with a note, not blocked.

### And then the corrected check caught real drift — mine

Re-run, it refused again, for a better reason:

```
  HEAD IS NOT BL-823's COMMIT.
  it touches files BL-823 never claimed:
      ~ tests/test_lock_and_snapshot.py
      ~ tools/githooks/pre-push
```

**Both true.** I declared `tests/test_read_snapshot.py`, then extended BL-821's existing `tests/test_lock_and_snapshot.py` rather than adding a rival snapshot-test file — the better engineering call, and a divergence from what I had announced. `pre-push` I picked up during the hooksPath migration, unforeseen. I corrected the claim to match what I actually wrote rather than widening the guard.

## 2. The read snapshot, wired

BL-821 built `snapshot()`, proved it holds still while the source is rewritten by the exact `os.replace` pattern `append_leads` uses, and noted nothing forced its use. **Three lines of ceremony per round is how a good tool goes unused.** So `read_snapshot` now has a one-call entry point:

with measure_master() as m:

    hits  = sum(1 for r in m.rows if r.get("email"))

Against the live, currently-moving master:

```
rows       : 58,324
with email : 4,692  (8.0%)
provenance : measured on master_leads.csv, 24,415,263 bytes, mtime 2026-07-31 22:38:05
```

That provenance line is the point. BL-818 found **five different master row counts quoted as current** across 40 reports, with two rounds quoting two different totals in a single report — none wrong when written, all unverifiable afterwards. A figure carrying its byte-size and mtime can be checked later by anyone.

A test pins the actual bug: a numerator and a denominator read either side of a concurrent `os.replace` now agree, and the live file is proven to have changed underneath.

**The secret scanner blocked this report, correctly by its own rule and wrongly in substance.** `tools/githooks/prepare-commit-msg` is 36 characters of `[A-Za-z0-9/_-]` and tripped the opaque-literal check. The existing allowlist was prefix-based (`http`, `reports/`), which cannot keep up with new directories. Rather than bypass the gate, I made the rule stricter *and* correct: a literal is exempt only if it names a file that **actually exists in the repo**. A credential is not also a file on disk. Verified it still fails on a synthetic `sk_live_…` token and on a path that does not exist.

## Limits

- **Items 3 and 4 are BL-822's, not mine.** I verified they exist and that the claim tool works by using it; I did not review their implementation, and their report is the authority on them.
- **The HEAD-ownership check depends on an accurate `will_write`.** It caught my drift, but a round that declares nothing gets skipped entirely, and a round that over-declares gets no protection. It is as good as the claim.
- **The guard only fires where `core.hooksPath` is set.** A fresh clone has no protection until `python tools/guard_amend.py --install` is run — the same gap `.git/hooks` always had, now at least with the hooks under version control.
- **`GUARD_AMEND_OK=1` bypasses everything**, on purpose. This raises the cost of a bad amend; it does not prevent one.
- **I did not verify the guard against a rebase, cherry-pick or `commit --fixup`**, which reuse commits by other paths and may or may not trigger `prepare-commit-msg` the same way.
- **`measure_master` is available, not enforced.** 60 scratch scripts still read master directly; I did not rewrite them, and nothing stops the next round doing the same.
- **`bl806_grow.py` was still running throughout** and its final total is unknown at publication. 27 accepted is a snapshot, not a result.
- **I could not attribute the `speech_frac`/`ocr` zero-entry finding** — I read it out of the walk log and did not investigate.
