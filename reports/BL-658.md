## PART 2 — proving nothing dies (honest boundary)

**This round did NOT deploy, so it cannot paste post-deploy fire times, and I will not claim a deploy I did not do.** The change ships to `checkpoint/BL-658`; Railway auto-deploys only `main`, after a separate merge round. Until then the change is inert and production keeps running the current code (header still present). So there is zero production risk from this round alone.

**Why the change is safe to deploy, argued from evidence rather than a post-deploy guess:** the live caller (the Railway scheduler) already authenticates lifecycle and watchdog through the bearer branch, which is exactly the branch kept. Removing the header branch changes the outcome only for a request that sends `x-vercel-cron:1` WITHOUT a valid bearer, and the only thing that ever did that was Vercel Cron, which stopped firing at 09:30 UTC today (BL-654; re-confirmed here: the current fires carry the Railway ~9s signature, and there is exactly one fire per 15-minute slot, so no second Vercel caller exists).

**The exact post-deploy verification for the merge round or the owner**, to run after Railway redeploys `main`:

```sql
-- every live cron still firing on cadence after the deploy (times ::text):
SELECT kind, MAX("firedAt")::text AS last_fire, COUNT(*) AS fires_last_hour
FROM cron_runs
WHERE "firedAt" > now() - interval '1 hour'
GROUP BY kind ORDER BY 2 DESC;
-- expect lifecycle ~4/hr (last within 15 min), watchdog ~2/hr (last within 30 min),
-- tracking ~6/hr (last within 10 min), all with a fire timestamped AFTER the deploy.
```

If any of lifecycle, watchdog, or tracking shows no fire after the deploy, roll back immediately: `git revert` the merge (or `reset --hard pre-BL-658`), which restores the `isVercelCron` branch. `retire-dead-clips` writes no heartbeat by design (BL-593), and is bearer-only so unaffected by this change; it cannot be confirmed via `cron_runs` and is not touched here.

**Tracking, independently:** the separate Railway tracking service is unaffected because it runs in process and never authenticates over HTTP (PART 0). Its heartbeat (last 12:10:13 today) confirms it is healthy now; it will keep running regardless of this change.
