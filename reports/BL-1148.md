# BL-1148 — a Desktop icon, and the reason his dashboard would not start

**One sentence:** there are two Pythons on his machine and they are not the same machine as
far as packages are concerned — `python` is 3.11 with everything, `py` is 3.13 with almost
nothing — so a double-click that resolved to the wrong one gave him the two missing-module
errors; the icon now scores every interpreter it can find, picks one that can actually run
the dashboard, takes a free port, waits for a real HTTP 200 before opening a browser, and
holds the window open with a plain-English reason when it cannot.

**Spend: $0.0000 of a $0.00 hard cap.** No paid call was made or attempted.

## 1. Why it would not start, measured rather than guessed

```
python  ->  3.11.9   fastapi YES  uvicorn YES  requests YES  tenacity YES  openpyxl YES  rich YES
py      ->  3.13.14  fastapi NO   uvicorn NO   requests YES  tenacity NO   openpyxl NO   rich NO
```

Agent rounds run `python` and see a complete environment. The Windows `py` launcher picks the
**newest** install, which here is a 3.13 with essentially nothing in it. The errors were real
and his environment was the odd one out.

**And nothing in the repo said what the dashboard needs.** `requirements.txt` declares the
lead tool's four packages — requests, openpyxl, tenacity, rich — and **does not mention
fastapi or uvicorn at all**, which are the two the dashboard cannot start without.

So the launcher does not pick "a Python". `pick_python()` scores every interpreter it can find
(`sys.executable`, `python`, `py -3`, `py`, `python3`, de-duplicated by real path) by **how
many required modules it is missing**, and takes the fewest. First-found is exactly how he
ended up on the bare 3.13.

**The declaration gap is BL-1147's, deliberately.** That round is live on
`requirements.txt`, `requirements-dashboard.txt`, `docs/ENVIRONMENT.md` and its own
`START_DASHBOARD.bat`, and it had already written `tools/env_audit.py` when this round
started. Rather than collide, this round took a different id and a disjoint file set, and the
launcher installs from `requirements-dashboard.txt` **if that file exists** and from its own
list otherwise — so the icon works whether or not BL-1147 has landed, and neither round waits
for the other. `claim.py` reported **no path conflicts**.

## 2. What the icon does

| file | what it does |
|---|---|
| `OPEN_DASHBOARD.bat` | finds any Python, hands over. **Every exit path goes through `:hold` → `pause`.** |
| `tools/dashboard_launcher.py` | the work. **Stdlib only.** |
| `STOP_DASHBOARD.bat` | `dashboard_launcher.py --stop` |
| `tools/make_icon.py` | draws the .ico |
| `tools/make_shortcut.ps1` | (re)creates both shortcuts |

**Stdlib only, and that is the whole point.** The one case this exists for is the machine
where fastapi and uvicorn are missing. A launcher that dies on `import fastapi` while trying
to say fastapi is missing is worse than no launcher — a traceback is what he was already
getting. `clippershq/preflight.py` follows the same rule; this is the dashboard's half of it.

**"Could not start" must never look like "started".** This project has ~18 recorded instances
of a failure reading as a benign success, and there is an obvious one waiting here: spawning
uvicorn succeeds even when the app dies half a second later on an import error, so a launcher
that opens the browser straight after `Popen` reports success on a page that will not load.
`wait_until_answering()` is the gate — it polls until `/api/health` answers **as ours**, and
if that never happens it prints the server's own captured last words and exits non-zero.
Nothing opens a browser on a process that was merely started.

**The port.** `port_free()` **binds** rather than connects, because a connect-test says
"nothing answered", which is also what a firewall says; and `SO_REUSEADDR` is deliberately not
set, because it makes an in-use port look free on Windows. **The already-running check is not
pid-based** — it asks whether `/api/health` answers as ours — so it works against an instance
started any other way, including one typed by hand.

**The stop is one pid, never a sweep.** `taskkill /PID <recorded pid> /F`, never
`taskkill /IM python.exe`, which would also kill the ~10 agent rounds sharing this machine.
And **the recorded port is checked before the pid is trusted**: Windows reuses process ids, so
a stale `.running.json` could otherwise become a random kill.

## 3. Tested by double-clicking it, not by reasoning about it

Every case below was `Start-Process` on the real `.lnk` on the real Desktop, then the machine
inspected from outside for what actually happened.

| # | case | observed |
|---|---|---|
| 1 | **cold double-click** | `127.0.0.1:8787 LISTENING pid 16540`; `.running.json {port:8787,pid:16540}`; `curl /` = 200, `/api/health` = 200; Playwright: title *ClippersHQ — operations*, 11 sidebar entries, **0 page errors** |
| 2 | **8787 taken by something else** | a decoy that 404s everything held 8787; launcher took **8788** (pid 19832) and recorded it; `curl 8788/` = 200; `curl 8787/api/health` = **404**, so the decoy was correctly *not* mistaken for the dashboard |
| 3 | **a dependency missing** | *"SOME PIECES ARE MISSING … Missing: a_module_that_is_not_installed_anywhere"*, names the interpreter it checked, exit 3, then *"THE DASHBOARD DID NOT OPEN. (code 3)"* and the final line **`Press any key to continue . . .`** — that line is `pause` |
| 4 | **double-clicked twice** | listeners before 1, after 1, **same pid**; *"It is ALREADY RUNNING on port 8787 … Nothing new was started"* |
| 5 | **the stop shortcut** | nothing listening afterwards; `.running.json` removed; *"STOPPED."* |
| 6 | **a foreign instance** *(unplanned)* | BL-1147 started its own dashboard on 8787 mid-round. The launcher detected it and started nothing — the check is not pid-based, so it respects an instance this round never created |

**On the window staying open.** Case 3's captured output ends at `Press any key to continue`,
which is `pause` being reached. Separately, an earlier run of the same `.bat` **with a real
console attached never returned at all** — the same `pause`, blocking as intended. Both halves
were needed: the redirected run proves the message, the console run proves the block.

### What was NOT tested, and why

* **Every port 8787–8796 in use.** Would mean holding ten ports while other rounds are
  running. The branch is three lines and shares the `say()` + non-zero-exit shape that case 3
  proved reaches `pause`.
* **The operator's own Chrome opening on it.** Chrome could not reach the loopback server in
  two prior rounds and its extension is not connected at all now. The page **was** verified to
  render at the launched URL through Playwright's bundled Chromium — real engine, real CSS and
  JS. Whether *his* Chrome opens on it is the one thing here nobody has verified, and this
  round is not going to claim otherwise.
* **The "every interpreter is missing something" branch by double-click.** It only fires when
  every Python on the machine lacks something, and this one has a working 3.11 that ten
  concurrent rounds depend on; uninstalling fastapi to prove a message would have broken their
  work. It was driven through the real `.bat` with `CLIPPERSHQ_LAUNCHER_NEEDED` naming a module
  genuinely absent everywhere — real code path, real absent module, real batch file, real
  `pause`. That environment variable is a documented test seam and nothing in the product sets
  it.

## 4. The icon

Drawn, not stock: a dark rounded tile (folders are pale and horizontal, so a dark square reads
as *not a folder* instantly), the left rail this dashboard now has with its top entry in cyan,
and the cyan play triangle from the page's own accent token. Six sizes in one file — 16 for
the taskbar through 256 for the preview pane — drawn once at 256 and resampled, because
drawing each size separately gives four subtly different icons and the small ones turn to mud.

**One naming caution:** his Desktop already carries `Clippers HQ.lnk` and
`ClippersHQ CEO.lnk`, both Chrome PWA shortcuts. The new one is **ClippersHQ Dashboard** and
is visually distinct — those two use Chrome's own icons — but it is a third similar name and
worth knowing about.

## 5. What I got wrong

* **`test_no_unchecked_stdout` caught me.** `stop()` read `taskkill`'s output without checking
  its return code, and the guard is right: taskkill printing nothing because it failed reads
  exactly like taskkill printing nothing because it worked. Access-denied is realistic — the
  dashboard can be started elevated or by another user — and swallowing it would have produced
  a "Stopped." message beside a port that was still taken. **That is the exact
  failure-reads-as-success shape this round is supposed to be preventing**, and I wrote one
  into the stop path. Now the return code is read first and reported.
* **`make_shortcut.ps1` printed nothing the first time.** A PowerShell function's
  `Write-Output` goes to the pipeline, so `$a = New-Shortcut …` captured the progress lines:
  two shortcuts were created and the script appeared to say nothing about them. `Write-Host`
  now.
* **The `--port` flag did not scope the already-running check**, so forcing a port still
  scanned the whole range and could report a neighbour as the answer. Fixed while testing —
  an explicit `--port` means *that* port.
