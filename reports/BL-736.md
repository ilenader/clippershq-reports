# BL-736: The downscale fix works exactly as measured — and changes nothing this module actually outputs

**Date:** 2026-07-30 · **Type:** Code change + re-measurement · **Spend:** $0.00 (local CPU only, no API calls)
**Suite:** 50/50, **2,249 checks** (was 2,235 — +14 new). **Campaigns SHA:** `8e02f8d6f6307ae8` unchanged. **config.json byte-identical to the pre-round backup — never written.**

Builds directly on [BL-733](BL-733.md) and re-uses its committed ground truth and its scoring functions verbatim.

---

## Headline

Item 1 reproduces BL-733's numbers **to three decimal places**: easy-case usable match **36.4% → 81.8%**, CER **0.052 → 0.020**. It is a real and large transcription win, and it shipped.

But the honest result of this round is a negative one that the brief did not anticipate:

> **Neither item 1 nor item 2 changes a single cue flag that this module emits.** 29/29 Latin images produce identical `text_features()` output before and after. All 6 measurable non-Latin images produce identical output with and without language packs. At 512px the flag counts **already match the oracle exactly**.

`ocr_features.py` does not ship transcriptions — it ships six 0/1 cue flags into the quality gate. The cues are short, high-frequency, romanised phrases (`wait for end`, `part 8`, `whatsapp`, phone digits) that were already surviving the downscale. Every character the fix recovers lands on the *long tail* of caption prose that no cue matches.

Two of the three confusions in item 3 also dissolved on contact, and the third rule I built had to be **deleted after it corrupted real text**. Details below.

## Item 1 — `max_side=None`. SHIPPED, reproduces exactly

`ocr_features.ocr_one()` no longer downscales. Measured on BL-733's 11 easy-case images (`A06–A19`, `C43`), same corpus, same scorer:

| | usable match | mean CER | s/image |
|---|---|---|---|
| `max_side=512` (old) | 4/11 = **36.4%** | 0.052 | 0.60 |
| `max_side=None` (new) | 9/11 = **81.8%** | 0.020 | 2.60 |
| `+ repair_ocr_text` | 9/11 = 81.8% | **0.015** | 2.60 |

BL-733 committed 36.4%/0.052 and 81.8%/0.020. Reproduced identically — the harness is directly comparable, not merely similar.

**Correction to the brief:** the CPU cost is **4.3×**, not the ~2× stated (0.60 → 2.60 s/image; 3.8× measured across all 29 Latin images). Still accepted, but it is double the assumed price.

`max_side` is retained as a parameter, so a CPU-bound caller can trade back and the old behaviour stays reachable for A/B work. Both directions are now asserted in tests.

## Item 2 — language packs: a large CER win, zero usable matches, and two hard engine gaps

Enabled via the existing `ocr_langs` key — no code change, as specified. Per script, on the same corpus:

| script | pack | n | usable | CER before → after |
|---|---|---|---|---|
| hangul | `ko+en` | 1 | 0 | **0.979 → 0.021** |
| devanagari | `hi+en` | 2 | 0 | 0.722 → **0.277** |
| arabic | `ar+en` | 1 | 0 | 0.667 → **0.476** |
| cyrillic | `ru+en` | 1 | 0 | 0.941 → **0.492** |
| devanagari+latin | `hi+en` | 1 | 0 | 0.851 → 0.581 |
| **gujarati** | `gu+en` | 1 | — | **NOT SUPPORTED BY EASYOCR** |
| **malayalam+latin** | `ml+en` | 3 | — | **NOT SUPPORTED BY EASYOCR** |
| **overall (6 measurable)** | | | **0/10** | **0.840 → 0.354** |

Character error more than halves. **Usable match stays 0/10** — and it fails by a hair, not by a mile:

- `A00` hangul, CER 0.021: one wrong syllable (`아이 엠 어` → `아이 임 어`). 98% of characters correct, word multiset broken.
- `A14` devanagari, CER 0.088: `1st` → `lst`, plus one spurious `2`.

### Three structural findings

1. **Gujarati and Malayalam are not supported by EasyOCR at all** — `ValueError: ({'gu'}, 'is not supported')`. Not a config problem; the engine has no model. That is **4 of the 10 non-Latin images**, so the "six scripts" framing overstates what is reachable. (`ta` also fails, with a state-dict load error — a separate landmine.)
2. **`ocr_langs` cannot express multi-script.** EasyOCR refuses every non-Latin pairing (`Korean is only compatible with English`, `Devanagari is only compatible with English`, …) and `get_reader(langs)` builds **one** reader from that one list. So the key can only ever select one script family + English — exactly what the module docstring already claimed. A general multi-script crawl needs per-script readers, which is a code change, not a config flip.
3. **The packs changed zero cue flags.** The Devanagari spam/clickbait flags were already firing on English-only output, because the money cues are romanised — the exact prediction in the module's own NON-LATIN LIMIT note.

### I did NOT flip the global default, and that is a deliberate deviation

`ocr_langs` remains absent (→ `["en"]`). Enabling a pack globally would mean picking one arbitrary script family for all campaigns, loading an extra model, and paying CPU, in exchange for **zero measured decision change**. The right use is per-campaign when a campaign is known single-script — which the config already supports. Enablement is verified working and measured; the default is left alone on the evidence.

## Item 3 — one rule earned its place, one was deleted, one is unexercised

BL-733 counted its three confusions **at production settings** — i.e. on the *downscaled* output. That is the detail that changes the answer. Re-counted on the same 29 Latin images at both resolutions:

| confusion | at 512 | at None | verdict |
|---|---|---|---|
| `,` read as `;` | 3 | **3** | **persists → rule KEPT** |
| `@` read as `G` | 2 | **0** | **fixed by item 1 → rule DELETED** |
| apostrophe dropped | 0 | 2 | persists but **not addressable** |

**The `@`→`G` rule was built, measured, and removed.** At 512 the cases read `Gmovie chusthava`; at full resolution the same images read `@movie.chusthava` exactly. So the rule had nothing left to fix — while a regex loose enough to catch a bare `G` before a word also rewrote **`Files by Google` → `Files by @oogle`** on image `A01`. Zero benefit, one regression. It cannot be rescued by requiring handle punctuation either: at 512 the handle's own dot is lost too, so there is nothing to key on. A repair that only fires where it is wrong is worse than no repair. Its non-return is now a test.

**The apostrophe table is kept but is honestly unexercised** — it fired on **0 of 29** rows. The only two real full-resolution instances are `IT'S`/`It's` read as `ITS`, and `its` is precisely the substitution that is *unsafe* to make: it is a real English word, so rewriting it would lose word matches on correctly-read text. Both rows are heavily garbled anyway (`ITS JST A MOVIE Sed`), so no apostrophe fix would have produced a word match. The table is retained on the argument that every entry is a non-word as spelled and therefore cannot damage a correct read — **not** on a measured gain.

**Net effect of the repair across all 29 Latin images:** CER 0.112 → 0.111, usable match 12/29 → 12/29. It fixes 3 rows by −0.017 CER each and harms none. That is the whole of it.

> The brief's premise — *"these barely move character error but destroy word match, which is what actually matters"* — did not hold. The comma rule moves CER slightly and word match not at all, because the rows it touches are wrong for other reasons too.

## Item 6 — the bar detector should NOT be tightened. The real defect is elsewhere

21 of 60 images carry no overlay text. The brief asked whether the bar detector should be tightened. **No — and geometry cannot do it:**

| | no-text (n=21) | text-bearing (n=39) |
|---|---|---|
| geometry finds a bar | 18 = **86%** | 34 = **87%** |
| median `bar_any_frac` | **0.310** | 0.266 |

The rates are indistinguishable and the no-text images have *more* apparent bar. Any geometric tightening cuts real captions at the same rate it cuts blanks. That is precisely why `text_in_band` exists.

**The pipeline mostly already handles it** — only **2 of 21** no-text images reach a hit. But the two that do expose a genuine, narrow defect:

```
A05  tier=confirmed  text_in_band=1.000  boxes=1  chars=5   ("ABLES")
B37  tier=confirmed  text_in_band=1.000  boxes=1  chars=1   ("8")
```

`text_in_band` is an **area ratio with no minimum-evidence floor**, so a single hallucinated box inside a bar scores a perfect 1.000 and promotes the frame to `confirmed`. Note the convergence: these are the *same* two images that hallucinate text in the blank-frame test — the false positive and the hallucination are one phenomenon.

**Recommended fix (report-only, not applied — outside this round's scope): require ≥8 in-bar characters for the `confirmed` tier.**

| floor | drops no-text FPs | costs true-text confirmations |
|---|---|---|
| **`min_chars ≥ 8`** | **2 of 2** | **0 of 16** |
| `min_chars ≥ 12` | 2 of 2 | 1 |
| `min_boxes ≥ 2` | 2 of 2 | **3** |
| `min_boxes ≥ 3` | 2 of 2 | 10 |

A character floor is strictly better than a box-count floor here: the smallest genuine confirmations are single-box but text-rich (`A10` 16 chars, `A14` 12, `A11` 8), while both false positives are single-box and text-*poor* (5 and 1 chars). **Caveat: n=2 false positives. Directional, and it should be re-measured on the labelled repost set before shipping.**

## The finding that matters most for the repost work

**`repost_finder` never calls `ocr_features.ocr_one`.** It goes through `repost_layout.frame_features` → `repost_layout.ocr_boxes`, which has its **own independent downscale, `OCR_MAX_SIDE = 640`**, and its own reader cache.

So item 1 improves the **IG editor crawl** and leaves the **repost path untouched** — even though BL-733's corpus is repost/meme covers and item 3's stated motivation was caption comparison. If the intent was to improve the repost pipeline, this fix landed in the other module.

I measured that second downscale rather than assume, driving the real shipped path (`frame_features` → `score_post`) with `ocr_boxes` wrapped to force `max_side`. **`repost_layout.py` was not modified.**

| `OCR_MAX_SIDE` | tiers | hits | OCR boxes | chars | wall clock (60 imgs) |
|---|---|---|---|---|---|
| **640** (shipped) | layout 20 · confirmed 18 · none 22 | **18/60** | 69 | 969 | **57 s** |
| **None** | layout 20 · confirmed 18 · none 22 | **18/60** | 131 | 1,468 | **162 s (2.9×)** |

**Zero tier changes. Zero hit changes.** Removing it nearly doubles boxes and characters, moves `text_in_band` on 8 images, and never crosses a threshold. It also makes `text_in_band` *noisier* in the wrong direction — `A19` 1.000 → 0.399, `C50`/`C51` 1.000 → 0.179 — because full resolution finds more text *outside* the bar, diluting the ratio.

> **Recommendation: keep `OCR_MAX_SIDE = 640`.** Removing it costs 2.9× CPU for no decision change. Given BL-732 measured the repost run at 31.9 s/candidate *dominated by thumbnail fetch and OCR*, this would have pushed the 2.7-hour full-run estimate toward 8 hours and bought nothing.

### Two harness bugs I caught in my own work, disclosed

1. **A vacuous quiet-tree check.** My snapshot stored backslash paths and the re-check normalised to forward slashes, so the "changed since snapshot" comparison matched nothing and would have reported `NONE` regardless. The mtime ages were the real evidence and are what is quoted above.
2. **A vacuous layout measurement.** My first Q1 script rebuilt features by hand, called `text_in_band(lay, boxes, size)` with the arguments in the wrong order (the real signature is `(boxes, lay)`), and returned a float into `feat.update()` — swallowed by a bare `except`. `text_in_band` was therefore never set, every tier read `None`, and "verdict changed on NO IMAGES" was meaningless. Rewritten to drive the real `frame_features`/`score_post` path; the table above is from the corrected run.

Both were caught before any conclusion rested on them, but a green-looking check that cannot fail is worth naming.

## Honest limits

- **n=11** on the easy case. BL-733's own 95% CI on 81.8% is roughly **[52%, 95%]**; this round inherits that, and reproducing the point estimate exactly does not narrow it.
- **n=29** Latin, **n=10** non-Latin, of which only 6 are measurable — per-script figures rest on 1–3 images each and are directional only.
- The item 6 recommendation rests on **2** false positives.
- Ground truth is one transcriber with no second pass (BL-733's own caveat).
- "No cue flag changed" is measured on this corpus. A larger corpus could surface cues that only full-resolution reading recovers; the claim is *no measured change at n=29*, not *no effect*.

## Bottom line

Item 1 shipped and is exactly as strong a transcription fix as BL-733 said, at double the stated CPU price. It buys nothing measurable for the flags this module currently emits — its value is latent, for any future consumer that reads `ocr_text` rather than the flags. Item 2's config path works but is capped at one script family and also moves no decision, with two of seven scripts simply unsupported. Item 3 reduced to a single rule worth keeping. The two most actionable things this round found were not on the list: **keep `repost_layout`'s 640px downscale**, and **put an 8-character floor under the `confirmed` tier**.
