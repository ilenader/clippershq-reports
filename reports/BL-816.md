## What I got wrong, and why it constrains the fix

My first automated sweep produced **34 phantoms**. After verification, **three** are real. The
false positives are instructive because any checker built for item 6 will hit the same rocks:

1. **I scanned only `clippershq/` and `tests/`.** `ADVISE` and `LOAD_BEARING` (BL-809) read as
   phantoms until I found them in **`tools/repo_guard.py`** — a directory my sweep never
   looked at. A checker must walk the whole tracked tree, never a hardcoded list.
2. **I checked `FULL_COLUMNS` only.** `fandom_display`, `fandom_is_character`, `clip_views` and
   `rank_median_views` (BL-790) read as phantoms; they are **export** columns in
   `BOT_READY_COLUMNS`, correctly shipped. A column claim must name *which* contract it targets.
3. **My "shipped" regex matched proposals.** BL-783's `last_activity_date` / `activity_source`
   appear in the sentence *"BL-767 §3 **proposes** replacing…"*, and BL-802's `caption_policy` /
   `music_policy` / `used_clip_ids` are fields in a spec for a bot that does not exist. Reading
   intent out of prose does not work — the author must mark the claim.

**A checker that infers claims from prose will cry wolf and be switched off** — the same failure
mode BL-809 identified for its own sweep.

## Recommendation: a claims manifest the round writes and a script verifies

Not prose parsing. Each report ends with a fenced block declaring **only** what it asserts is on
disk:

```
<!-- CLAIMS
func:   clippershq/outcomes.py::mark_sent_from_csv
const:  clippershq/outcomes.py::RECORDABLE_COLUMNS
menu:   control.control_panel::b
menu:   main.menu::B
config: youtube_finder.min_views
column: writer.BOT_READY_COLUMNS::fandom_display
column: writer.FULL_COLUMNS::lead_kind + master_leads.csv header
file:   tools/repo_guard.py
-->
```

`tools/verify_claims.py <report.md>` then asserts each line, and this is the part that matters:

- **`func` / `const`** — resolved by **AST** in the named module (a def or an assignment), not
  by substring. A mention in a comment does not count.
- **`menu`** — the key appears in the listing block **and** in the dispatch chain of the named
  function. BL-810's whole finding was a key in one and not the other.
- **`config`** — key present in `config.json` **and** read somewhere in the tracked tree. A key
  nothing reads is BL-775's dead-knob shape.
- **`column`** — present in the **named** contract, and for master columns also in the live CSV
  header.
- **Every check runs against `git show HEAD:<path>`, not the working tree.** This is the one
  that would have caught BL-797, and it is the difference between "I wrote it" and "it will
  survive".

Cheap to run (seconds, offline, no API), and it fails closed: an unparseable manifest is a
failure, not a pass. BL-801's AST config-contract test is the precedent — same mechanism, aimed
at report claims.

**It does not solve everything, and should not pretend to.** It catches (a), (b) and (d) —
a round cannot claim `LAST_CROSS_SHARD` without the grep failing, and cannot claim
`mark_sent_from_csv` while it is uncommitted. It does **not** catch a claim about behaviour
("the ladder holds", "94% survive"), and it does not stop a round writing a manifest that
omits the thing it lied about. It raises the cost of a phantom from zero to deliberate.

## Limits

- **Last 30 reports (BL-783 → BL-813), backtick-quoted code-shaped identifiers only.** A claim
  written in prose without backticks, or about behaviour rather than an identifier, is invisible
  to this method. The real phantom count is a floor.
- **The "later described it as existing" search is substring over report text**, so it counts
  any mention, including one that questions the claim.
- **Cause (c) is unproven, not disproven.** Finding it needs git history per identifier across
  concurrent branches; I checked the current tree and HEAD only.
- **`_archive_stale`'s folder is dated 2026-07-31** — consistent with BL-806, but I did not
  verify the 262 addresses it claims to have moved.
- **The working tree moved under me during the audit.** `outcomes.py` was uncommitted when I
  started and committed as `7bfd014` before I finished; the 231-line figure is a snapshot.
- **Three of my own four automated passes were wrong** before hand-verification. Treat the
  method, not just the corpus, as the finding.

## Method

Cloned the reports repo (312 files), took BL-783 → BL-813. Extracted backticked code-shaped
identifiers from lines containing a shipping verb, then **hand-verified every candidate** rather
than trusting the extraction. Existence was tested against all **126 tracked `.py` files**
(`git ls-files '*.py'`, after the first pass missed `tools/`), `config.json` keys,
`writer.FULL_COLUMNS`, `writer.BOT_READY_COLUMNS`, the live `master_leads.csv` header, and —
separately — `git show HEAD:<path>` to distinguish working-tree presence from committed
presence. Functions and constants were additionally resolved through `ast` so a comment mention
could not read as a definition. `git -C .` throughout; nothing was reset, staged or committed.
