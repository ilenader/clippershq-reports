## 1. The registry no longer has a single point of failure

`tools/claim.py` is the registry's writer, reader and CLI, which makes its *source file* a dependency for every round. It has failed twice in one session:

| incident | what happened |
|---|---|
| **BL-901** | `claim.py start` raised `SyntaxError` mid-save. For ~50 s no round could file or read a claim. |
| **BL-903** | a 60-minute poller read **`rounds=0` while eleven claims were live**, for the same reason |

The second is the dangerous one: **the failure did not look like a failure.** An import error is loud; a zero is a number, and the poller averaged it into a stillness measurement.

**Shipped: `tools/claims_read.py`** — standard library only, no code path through `claim.py`, parses `.claims/*.json` directly.

**VERIFIED against the exact incident.** With `claim.py` deliberately corrupted mid-file:

```
claim.py brief          -> SyntaxError: unterminated triple-quoted string literal
claims_read.py --count  -> 13
claims_read.py --holders tools/claim.py -> BL-897
```

And against BL-903's shape — a registry containing only a half-written claim:

```
count()       = None      <- must be None, never 0
unavailable() = 1 claim file(s) unreadable (being written right now): X.json
```

**`count()` returns `None`, not `0`.** A count that cannot distinguish *"nobody is working"* from *"I could not look"* is worse than no count, because nothing downstream can tell it from a real measurement. A torn file beside good ones is skipped **and named**, matching `claim.py`'s own never-fatal rule.

**NOT DONE, and it is the other half:** making `claim.py`'s own writes atomic (temp + `os.replace`). **BL-897 holds that file.** Until that lands, an editor saving in place will keep exposing a torn read — the fallback makes the *readers* survive it, not the cause.

## 2. The publish gate: a piped exit code can no longer publish anything

`PUBLISHING.md` has warned since BL-807/808 that `scanner | tail` reports `tail`'s status. BL-901 read that file **in its own session** and then did exactly that, pushing a report whose scan had **FAILED**. Third pipe-eats-exit-code incident here; second by someone who had read the warning.

**Documentation did not work three times, so the pipe is now impossible rather than discouraged.** `tools/publish_report.py` runs the scanner via `subprocess.run` and reads `.returncode` off the result object. No shell, no pipeline, nothing for a caller to interpose.

**VERIFIED, and this is the test that matters** — the full publish path, *piped*, on a report the scanner rejects:

```
clone HEAD before: 3e3fa362
  FAIL: long opaque literal in report
clone HEAD after:  3e3fa362   UNCHANGED -- nothing committed
BL-BAD.md in clone? NO -- never copied
```

Piping the *script* still loses its own exit status — that is inherent to pipes and I am not claiming otherwise. What changed is that **the decision was already made inside the process**: the scan runs before the file is copied, so a swallowed status can now only hide the refusal from the operator, never cause a publish. Under the old recipe the pipe *caused* the push.

It also **refuses when the scanner is missing** (`REFUSED: an absent gate is not an open gate`) and uses `git -C` throughout with no `reset`/`clean`/`checkout`/`--force`. `PUBLISHING.md` now points at the script and marks the shell recipe as documentation of what it does, not a thing to copy.

**This report was published with it.**

## 4. `--enrolling` is now a hook

BL-901 built the warning; nothing ran it, because nothing had to. `tools/githooks/pre-commit` now runs `verify_claims.py --enrolling` and **exits 1** on an unready enrolment.

**VERIFIED both ways:**

```
clean index          -> "no manifest would be newly enrolled"           EXIT=0
unready manifest     -> "[NOT READY] docs/claims/BL-906-selftest.claims"
                        "pre-commit REFUSED: ... enrolled into permanent enforcement
                         before the code it claims is committed"        EXIT=1
```

`git commit --no-verify` remains the deliberate override, with the instruction to say so in the report. Standing caveat, same as the other hooks here: **hooks are not cloned** — a fresh clone has no protection until `core.hooksPath` is set.

## 5. Why green did not reproduce, recorded where it is quoted

`run_all.py` now prints, on every run:

```
(101 suite file(s) discovered; 13 round(s) in flight at 22:14
 -- a suite count is a moment, not a property)
```

The count comes from `claims_read`, so it survives `claim.py` being mid-save, and says *"registry unreadable"* rather than a number it cannot stand behind.

The evidence for the note: BL-892 measured the first fully green run at **96/96**. BL-901 re-ran 40 minutes later: **97/98** — the suite had **grown by two files**. This round: **100 of 101**, grown by three more. BL-903 sampled the tree for 60 minutes and never saw two consecutive identical hashes. The thing being measured changes faster than the measurement takes to run, which is a better explanation than flakiness and stops a later reader comparing two numbers that were never like-for-like.

## Honest limits

- **Half of item 1 is not done.** `claim.py`'s own writes are still not atomic; BL-897 holds it. The fallback protects readers from the symptom, not from the cause, and an in-place save will keep producing torn reads until that lands.
- **My own sweep needed the fix it was looking for** — fifth instance this session of a text check matching prose about a bug rather than the bug.
- **The pre-commit hook is not installed anywhere by this round.** `core.hooksPath` already points at `tools/githooks`, so it is live here, but hooks are not cloned and nothing in this round changes that.
- **`claims_read.holders_of` is deliberately exact-match**, not the glob/directory overlap `claim.py::paths_overlap` implements. A second copy of that logic would drift; use the tool when it is importable and this when it is not.
- **The suite is not green and I am not calling it green.** One red, attributed to two live rounds' shared file, verified not to involve anything I touched — attribution is not diagnosis.
- **`publish_report.py` has no test file.** It was exercised end-to-end against a rejecting report and a passing one, and used to publish this report, but there is no suite entry pinning its refusals.

---

## Say it plainly

Three of this session's incidents came from the same place: a tool that answers a question, and a caller who cannot tell "the answer is no" from "the tool did not answer". A dead `claim.py` returned zero rounds; a piped scanner returned success; a poller wrote both into a measurement. The fix in each case is not more care — it is making the unanswerable case *representable*: `None` instead of `0`, a refusal decided inside the process instead of inferred from a pipeline, and a hook instead of a habit.
