## PART 1 — detect the platform BEFORE reading anything

BL-636's reader applied one flat TikTok label map to every image, so Instagram and YouTube numbers landed in the wrong slots. The rebuild decides the platform first.

`detectPlatform(text)` scores the OCR text against distinctive signatures for each surface (TikTok: "For you", "Traffic source", "Retention rate"; Instagram: "Accounts reached", "Accounts engaged", "Plays"; YouTube: "Impressions", "Average view duration", "Watch time (hours)"), avoiding generic words that appear on all three. The clear winner wins; a weak or tied lead returns **"unknown"**.

On "unknown" the UI does not guess — it shows a native radio group ("Platform not detected — pick the correct one") and, when the reviewer picks, re-maps the stored OCR text client-side with the chosen platform's label set (pure module, no re-upload, no second OCR call). A wrong platform slots every number wrongly, which is exactly how a false accusation starts, so the reader refuses to assume one.

```
PASS  detect TikTok / Instagram / YouTube
PASS  ambiguous text -> unknown (ask, never guess)
PASS  empty text -> unknown
```

Per-platform label maps also fix BL-636's specific wrong-slot captures: Instagram "Accounts reached" now maps to reach (the `\breach\b` word-boundary bug is gone), and YouTube "Average view duration" maps to average-watch-time and can no longer be stolen into video-length.

## PART 2 — the number parser (the 1000x bug and the 42-vs-4 case)

`parseMetricNumber(raw, kind)` is the safety core. Every class below is proven in `scripts/test-bl-650-screenshot-reader.ts`.

| Input | Output | Why it matters |
|---|---|---|
| `12.4K` | **12400** | BL-636 truncated this to 12, a 1000x error |
| `1.2M` | **1200000** | same class |
| `1,234` / `1,234,567` | 1234 / 1234567 | en thousands |
| `1.234,56` (EU) / `1,234.56` (US) | **1234.56** both | mixed separators, last one is the decimal |
| `1.234` (lone dot-3) | 1234 **but flagged UNCERTAIN** | the "OCR emitted 1.234 for 1,234" trap: parsed, but never trusted silently |
| `42.3%` | **42.3** (not 4, not 4.23) | the owner's fear |
| `42%` | **42** (never 4) | proven it cannot collapse to 4 |
| `4%` | 4 | a real 4 stays 4 |
| `420%` | **rejected** | out of 0..100, not clamped to something plausible |
| bare `42` where a % was expected | 42 **flagged uncertain** | no % sign means it might be an adjacent count |
| `1:23` / `1:02:03` / `9.3s` / `12 sec` | 83 / 3723 / 9.3 / 12 | durations |

The load-bearing property: **when a value is ambiguous, it is marked uncertain, never guessed.** A blank is safe; a wrong number is not. The parser cannot invent a digit the OCR dropped, so the defence against "42 arriving as 4" is the combination of this parser (which never itself creates the error), the visible source-region crop, and the human confirm gate.

```
43 passed, 0 failed
```

## PART 3 — confidence and human verification

Every read is shown in an owner-only card beside the video row (never clipper-facing). Reviewed by the accessibility-lead; built to its checklist.

* **Each value sits next to a CROP of the exact region of the screenshot it came from** (a real `<img>`, clipped to the OCR word box, whose alt names the *region* — "Source screenshot region the Retention value was read from" — never the number, so a machine guess is never laundered into an authoritative label).
* **Uncertain reads are flagged three ways, never colour alone:** an amber left-border block, a triangle icon, and the literal word "Unverified" plus the reason. Clean reads read "Read cleanly (N% match)".
* **Uncertain values are never pre-filled** into the form as if confirmed. Only clean reads pre-fill, and every pre-filled field still carries the existing "please confirm" marker.
* **Platform, when unknown, is a native radiogroup**, not a guess.
* Each value's accessible name carries "(unverified read)" so a screen reader never speaks a machine guess as fact.

No extracted value can reach BL-599's peer-engagement rank, the shadow scorer, a clip's status, or a clipper's view — proven in the table above.

Free + fast is what exists (OCR.space) and is weakest on 480p. Fast + highest-quality is a paid vision model at trivial cost. Pick per how bad the owner's 480p screenshots are, which is the UNMEASURED question below.
