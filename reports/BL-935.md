## There were TWO heuristics, and I had conflated them

- **Rule 1a** — config leaves `>= 12` chars, with `_is_plain_word` and `_is_repo_path`
  carve-outs. **This is the `>=12` rule BL-829 said to replace**, still live, 51 failures.
- **Rule 3b** — `_looks_like_credential`. The *opaque-literal* rule, and it had **already
  been replaced** by run-length + character-class + entropy, which is what cleared FP
  classes 4, 5 and 6. Its remaining 50 failures are a class newer than that work.

### Rule 1a: replaced, and both exemptions deleted

```python
candidates = [(p, v) for p, v in leaves if _looks_like_credential(v.strip())]
```

It now asks the same question the other rule asks — *does this value have the shape of a
credential* — of config values instead of report literals. **`_is_plain_word` and
`_is_repo_path` are not called from it any more.** Length was never the property being
tested; it was a proxy needing an exemption for every class of long string this codebase
contains, and the exemptions could not keep up. A film genre, a filename, a path and a
base URL all fail a shape test by construction.

### Rule 3b: the seventh class, and the two designs that were wrong

The 50 failures are **git blob OIDs and commit SHAs** — 60 distinct literals, cited as
integrity evidence, mostly from the outreach-dashboard repo (`earnings-calc.ts`, Railway).
**The gate was rejecting exactly the evidence a money-file report exists to show.**

Two designs were tried and are recorded, because the next person will consider them too:

1. **`git cat-file`** — existence-beats-pattern, the argument that carries `_is_repo_path`.
   **Wrong: 0 of 60 resolve**, because they are objects in a *different* repository.
2. **Exclude all 40/64-char lowercase hex.** **Wrong, and a test caught it** —
   `test_secrets_guard.CredentialShapeRule` pins that a 64-character hex *credential* is
   caught, and it is right to: hex is a perfectly good key alphabet. My blanket exclusion
   traded a real detection for a cosmetic one, and I would have shipped it.

So the exemption requires **corroboration from the line**, not from the literal: the hash
must be named as one, or stand beside a filename, the way all 60 do. A leaked key does not
appear on a line reading `IDENTICAL  <hash>  earnings-calc.ts`. Same literal, two contexts,
two answers — pinned by a test that asserts both halves.

### The class I did not fix, and why

**CUID2 database row IDs** — `cmoaa70j…` (25 chars), 107 occurrences, quoted as data in
dashboard reports. They are **structurally indistinguishable from a lowercase API key**: one
unbroken run, letters and digits, entropy in range. Every discriminator I could find that
clears them also weakens the gate against a lowercase key.

I am **not making that trade unilaterally**, because it is the same trade my hex exclusion
tried to make and a test correctly refused. The options, for whoever picks it up:

- require an uppercase character in the run — clears cuids, blinds the gate to lowercase keys;
- exempt only inside a fenced block or a table cell — contextual, like the hash fix, and
  probably the right shape;
- keep the 8 email failures as the floor: those reports contain a real address and **should**
  fail until it is redacted.

## Method

`claims_read.py` and `git status --porcelain` first, and the dirty file was left alone.
Then the scanner was **measured against all 472 published reports before a line was
changed**, which is what turned "seven remembered classes" into a ranked list with counts.
Two designs for the hash class were built and rejected on evidence — one by measurement
(0 of 60 git objects), one by an existing test that pinned a property my fix would have
broken. Every planted credential is synthetic and generated in the test; no real key appears
in any file this round wrote.
