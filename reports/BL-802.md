## 2. Getting the video

**The exact call** (`clip_media.retrieve`, verified in source):

```python
retrieve(clip_id, *, fetch_clips_page, http_get,
         prefer="best", max_height=None, kind="video", max_pages=1)
  -> {"ok", "bytes", "rendition", "clip_id", "pages_fetched", "error"}
```

Both fetchers are **injected**, so the bot supplies its own HTTP and its own paged-clips fetcher — it does not need this repo's client. `clip_id` splits to `(pk, user_id)`; on the real record below that is `('3941210953483232160', '227282247')`. **No URL is ever returned** — `rendition` is built as `{k: v for k, v in rend.items() if k != "url"}`, by construction.

**Cost: $0.0006 and ~2.6 s** for a page-1 clip — one billed `/gql/user/clips` call, then a **free, unmetered CDN download at any size**.

**Cost scales by page, not by byte.** There is no fetch-one-media-by-pk endpoint; the only source returns an account's clips newest-first, so an older clip costs one more billed call per page. `max_pages=1` is the default and bounds it explicitly.

### Failure modes, all of which return rather than raise

| `error` | cause | what the bot should do |
|---|---|---|
| `clip_id is not '<pk>_<user_id>'` | malformed id | skip, log — never retry |
| `clip not found in N page(s) — it may have been deleted` | deleted, or deeper than `max_pages` | retry once with a higher `max_pages`; then treat as gone |
| `no video_dash_manifest on this media` | image post, or a shape change | skip |
| `no video rendition with a url` | manifest parsed but empty ladder | skip |
| `download failed: <ExcType>` | CDN refused or timed out | **retry — the URL may simply have expired** |

### The instability rule — the most important line in this document

**BL-798 measured the same clip returning `720×1280 avc1` on one fetch and a `1080×1920 AV1` ladder seconds later.** The rendition ladder is not stable per clip.

> **The bot must call `retrieve()` fresh every time and must never store, cache or pass on a rendition URL.** `media_renditions` in the library is an *inventory of what quality has been seen*, for deciding whether a clip is worth fetching. It is **not** a pointer and must never be used as one.

Reinforcing that: measured URL expiry is **~105 hours** (`oe` decodes to 1785627020; BL-787 n=6 median ~105 h). Long enough to fetch within the week, far too short to store — which is exactly why the library holds no URL.

**One caller-side trap to specify explicitly.** `pick_rendition(prefer=...)` treats **only the literal string `"best"`** as "highest bandwidth"; **anything else — `'worst'`, `'low'`, `'min'`, a typo, `None` — selects the smallest.** That direction was chosen deliberately (a silent fallthrough to the most expensive stream was the old bug), but it means a bot passing `prefer="highest"` gets the *smallest* rendition and no error. Pass `"best"` or nothing.

## 3. Reading the library

**Format:** JSONL, one record per line, `ensure_ascii=False`, `sort_keys=True`, `\n` terminated. `append()` never rewrites. Records carry `rev` and `schema`; `read_all()` resolves **last-wins by `(clip_id, rev)`**.

### The polling contract

```
state: {shard_filename: byte_offset}

every poll:
  for shard in sorted(listdir(root)) where shard matches clips-YYYY-MM.jsonl:
      open shard binary, seek(offset[shard] or 0)
      buf = read()                       # to EOF
      if buf does not end in b"\n":
          buf = buf[:buf.rindex(b"\n")+1]    # DROP the trailing partial line
      offset[shard] += len(buf)              # advance only past whole lines
      for line in buf.splitlines():
          parse; skip unparseable; require a clip_id
  then apply last-wins by (clip_id, rev) over everything read this poll,
  merged against what you already hold
```

**Three rules that are not optional:**

1. **Poll every shard, never just the newest.** `append()` shards on `posted_at`, not on write time — `shard_for(field(record, "posted_at"))`. A clip posted in January and discovered today lands in `clips-2026-01.jsonl`. A consumer watching only the current month will silently miss it. There are already 6 shards spanning 2026-01 to 2026-07 in one store.
2. **Drop the trailing partial line and do not advance past it.** A concurrent `append()` can be mid-write. `iter_lines()` already skips unparseable lines, but a byte-offset consumer must also not consume half a record and then resume after it.
3. **Never assume one record per clip.** Updates arrive as a new line with a higher `rev`. The same `clip_id` will legitimately appear many times across shards.

### Knowing a clip is already used

**The library cannot tell you this and should not try.** It is append-only and has no send-state — the same gap the send path has with `date_sent`. The bot owns a `used_clip_ids` set keyed on `clip_id` (stable, never rewritten) and consults it *before* calling `retrieve()`, so a duplicate never costs $0.0006. `rev` is not a usage marker; a re-`rev`'d clip is the same clip with better metadata, not a new one.

## 4. What the bot must never trust

Every record carries a `provenance` block: `declared` / `derived` / `measured` / `absent`. `clip_library.field()` already enforces the rule — it returns `None` unless the tier is in `READABLE = (declared, derived, measured)`.

**The enforcement the bot must implement is the missing-entry case, and it is not theoretical.** Measured across the 42 stored clips, provenance slots break down as:

```
declared 347 · derived 63 · absent 304 · NO ENTRY AT ALL 588
```

**588 field slots have no provenance entry.** Under the contract those must read as `null`.

> **The bot must never read a record's raw dict.** It reads through an accessor that returns the value only when `provenance[field]` exists AND is in `READABLE`; in every other case — missing entry, `absent`, unknown tier — it returns `null`.

A raw-dict read is how a wrong `content_genre` gets treated as fact, and genre poisons everything downstream: it picks the music, which sets the energy, which drives the cut. The three-line accessor is the whole defence. **`clip_library.field()` already does exactly this** — the contract is simply that the bot must not bypass it.

One asymmetry worth stating: `caption_parser.field()` does **not** know the `measured` tier and returns `None` for it. Consumers must use `clip_library.field()`.

## 6. The offer gap — the fields the bot needs from you

BL-774 found no rate card, brief, turnaround, client name or payment terms anywhere. The bot needs a small, stable object — this is what to write:

```json
{
  "offer_id": "…",            "client_name": "…",
  "deliverable": "9:16 short-form cut",
  "duration_target_s": 30,    "aspect": "9:16",
  "turnaround_hours": 48,     "revisions_included": 1,
  "price_currency": "USD",    "price_per_clip": 0,
  "volume_tiers": [{"min_clips": 0, "price_per_clip": 0}],
  "payment_terms": "…",       "usage_rights": "…",
  "caption_policy": "rewrite|preserve|none",
  "music_policy": "replace|reuse_if_licensed|none",
  "watermark": true,          "brief_url": "…"
}
```

**Why each matters to the bot, not to you:**
- `duration_target_s` + `aspect` — the only two that gate **clip selection**. Without them it cannot tell whether a 14.9 s 1080×1920 clip fits the job; every other field is downstream of a clip already chosen.
- `caption_policy` — decides whether it needs `layout` (gap #3) at all. `none` makes the biggest blocker irrelevant.
- `music_policy` — decides whether `audio_type`/`track_*` matter. `replace` makes the 26% track fill a non-issue.
- `turnaround_hours` — must be **under ~105 hours**, or the media URL expires mid-job and the clip has to be re-fetched at another $0.0006.
- `price_per_clip` — the only way to know whether $0.0006 retrieval plus rework is worth it on a given clip.

**Write `duration_target_s`, `aspect`, `caption_policy` and `music_policy` first.** Those four change what the bot must be built to do; the rest are bookkeeping it can carry without understanding.

## Limits

- **Spec only. Nothing implemented, no file written outside this report.**
- **The minimum-record list in §1 is my judgement** of what "pick and rebuild" requires. Nobody has run a rebuild, so it is unvalidated by use.
- **42 clips in two scratch stores is a small, skewed sample** — seven accounts, one dominating. Fill percentages will move once a production run exists.
- **`retrieve()` is proven on a page-1 clip only** (BL-798). Deeper pages cost more calls and that path is untested end to end.
- **The ~105 h expiry is n=6 median**, not a guarantee; treat it as an order of magnitude.
- **The polling contract is specified, not tested.** No consumer exists, so the partial-line and back-dated-shard rules are reasoned from the append code rather than observed failing.
- **The offer object is a proposal.** I have inferred the fields from what the bot must decide; you may need terms it does not care about.
- **I did not verify BL-745's "29 shipping" field by field** — I reconciled the counts by what each was measuring, and re-measured only the on-disk number.
