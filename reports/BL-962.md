## 0. What "no email sent" means here, mechanically

Every probe runs `EHLO → MAIL FROM:<> → RCPT TO:<addr> → QUIT`. **`DATA` is never issued**,
and an SMTP transaction delivers nothing until DATA is accepted and terminated. This is
enforced in code, not by discipline: `Session.cmd` raises on the `DATA` verb, and
`assert_no_send()` drives four spellings of it through a fake socket and asserts each one
raises and that nothing reached the wire. Every run in this report begins with that guard
printing PASS.

The first version of that guard asserted on **substrings of its own source file**. That is
the proxy failure in `docs/PRECONDITIONS.md` §10 — it measured "the file contains some
text" and concluded "the code cannot send" — and it went red on an edit that changed no
behaviour. It now exercises the guard instead of grepping for it.

`MAIL FROM:<>` is the null reverse-path — what a bounce notification uses, and the honest
sender for a transaction that will never carry a message.

**And the guard is not the evidence — the transcripts are.** Every session records the verbs
it issued, and reading them back out of all four artifacts gives the same answer:

```
bl962_smtp.json            200 sessions   verbs = ['EHLO', 'MAIL', 'QUIT', 'RCPT']
bl962_smtp_freemail.json   210 sessions   verbs = ['EHLO', 'MAIL', 'QUIT', 'RCPT']
bl962_smtp_gmail2.json     250 sessions   verbs = ['EHLO', 'MAIL', 'QUIT', 'RCPT']
bl962_smtp_gmail3.json     160 sessions   verbs = ['EHLO', 'MAIL', 'QUIT', 'RCPT']
```

Those are the 820 **recipient** sessions. Adding the catch-all controls (642, including the
full 551-domain sweep) and the gate demo, this round opened **1,482 SMTP sessions in total,
issued no DATA in any of them, and has no message body anywhere in its code. 0 emails sent.**

## 1. The DNS re-run: 561 domains in 3 seconds, 5 newly dead, suppression catches 0 of 5

`scratch/bl962_dns.py`. **I did not re-run `scratch/bl763_dns.py`.** It resolves MX through
`dns.resolver` and silently falls back to `socket.getaddrinfo` — an A-record check — when
dnspython is missing. **dnspython is not installed on this machine today**, so re-running it
would have answered a weaker question in the same verdict vocabulary. This round resolves
MX with a raw stdlib DNS client (UDP, TCP fallback on truncation, compression-pointer
parsing) so the answer is the one the label claims.

| verdict | domains | addresses | certain bounce? |
|---|---:|---:|---|
| `MX_OK` | 551 | 2,970 | no |
| `NO_MX_A_ONLY` | 5 | 5 | **no — see below** |
| `NXDOMAIN` | 3 | 3 | **yes** |
| `NULL_MX` | 2 | 2 | **yes** |

**Every dead verdict is confirmed on a second, independent resolver** (1.1.1.1 primary,
8.8.8.8 confirm) before it is reported. A single resolver's NXDOMAIN can be local; naming a
live domain dead would delete a real lead, which is this layer's failure mode in reverse.

### The five certain-bounce domains, named

```
cea.agency               NULL_MX    1 row    absent from suppress_mx.json
loudmouth.pro            NXDOMAIN   1 row    absent from suppress_mx.json
mskd.com                 NULL_MX    1 row    absent from suppress_mx.json
thelocusgroup.co         NXDOMAIN   1 row    absent from suppress_mx.json
wraithsmusicgroup.com    NXDOMAIN   1 row    absent from suppress_mx.json
```

**Current suppression catches 0 of 5.** Not because the policy is wrong — because
`suppress_mx.json` is a **snapshot of 141 domains taken 2026-07-31**, and the export now
contains **561**. **470 of them (83.8%) have never been probed** and are UNKNOWN by
construction. `send_suppress` is explicit that absent means unknown, and that is the right
default; the table simply cannot keep up with a file rebuilt daily. This is the argument
for a gate at send time rather than a better table (§6).

Two checks that came back clean and are worth stating because they could have gone the
other way:

- **No domain the table calls DEAD/`noMX-Aonly` is still in the export.** Suppression is holding.
- **No status drift**: every domain the table calls `ok-MX` still resolves `MX_OK`.

### One correction to the existing policy: `noMX-Aonly` is not a certain bounce

`send_suppress` hard-excludes `noMX-Aonly` alongside `dead_mx`, on the grounds that both are
certain. **They are not the same.** RFC 5321 §5.1 makes an A record an *implicit MX* — a
domain with an A record and no MX still accepts mail at that host. The five such domains
here (`essosa.com`, `proxy.com`, `reydempto.tv`, `undrcntrl.com`, `vico.gg`, 1 row each) are
absent from the table so nothing cuts them today, and the exposure is 5 rows either way. It
is recorded as a **policy note, not a defect**: the treatment is defensible as caution, but
the docstring calling it a CERTAIN bounce overstates what DNS proves.

## 3. SMTP verification: 737 informative probes, 6 hard bounces, 0.81%

Four samples, 813 distinct addresses (27.3% of the file), all non-invasive, all `QUIT`
before `DATA`.

### The method, and the one place my first design was wrong

The catch-all control runs in **its own session, once per domain**. My first draft put the
control and the real recipient in one connection, and Outlook answered
`452 4.5.3 Recipients belong to multiple regions` — two mailboxes in different Exchange
regions cannot share a transaction. **That reply is an artifact of the probe, not a fact
about the address**, and it would have scored as a deferral on every Microsoft-hosted domain
in the sample. Caught in the pilot, before the run.

### The providers were verified to discriminate before their answers were trusted

This is the step that makes the number mean anything. For each provider, a **local-part that
cannot exist** (random 20 chars) was probed:

```
gmail.com     control -> 550 5.1.1 "account ... does not exist"    catchall = FALSE
outlook.com   control -> 550 5.1.1                                 catchall = FALSE
hotmail.com   control -> 550 5.1.1                                 catchall = FALSE
icloud.com    control -> 550 5.1.1                                 catchall = FALSE
```

**Gmail discriminates even for an unauthenticated residential client with no rDNS.** That
was not assumed — it was tested against three impossible addresses, all of which returned
550 5.1.1, and against 5 MX hosts. Since Gmail is 2,156 of 2,980 rows (72.3%), this is what
makes a real estimate possible at all.

### Results

| | probes | accepted | hard bounce | no information |
|---|---:|---:|---:|---:|
| stratified by domain (72 domains, cap 6) | 200 | 187 | 0 | 13 |
| freemail-weighted (gmail/outlook/hotmail/icloud) | 210 | 208 | **2** | 0 |
| gmail extended (disjoint) | 250 | 247 | **3** | 0 |
| gmail extended #2 (disjoint) | 160 | 159 | **1** | 0 |
| **pooled, deduplicated** | **813** | **635** | **6** | 13 (+63 catch-all) |

The four samples were drawn independently, and **7 addresses appeared in two of them** — the
domain-stratified sample caps 6 per domain and the freemail sample re-drew from the same
gmail/outlook pools. Pooling the raw lists counted those twice; the pooled row is
deduplicated by address, which is why 820 probes become 813.

**Naive acceptance rate: 97.2%.** That number is inflated and should not be
quoted. The denominator that means something excludes:

- **catch-all accepts** — 63 probes on domains that accept everything, which prove nothing;
- **13 probes that failed for reasons about *this client*** — 6 Yahoo rejections
  (`550 5.7.25 Forward-confirmed reverse DNS failed`, i.e. our residential IP has no rDNS)
  and 7 connection timeouts (`evolved.gg`, `starsmusic.id`).

```
INFORMATIVE (discriminating domain, clean accept or clean hard bounce) : 737
    of which HARD BOUNCE                                               : 6
    MEASURED RATE                                                      : 0.81%
    95% Wilson interval                                                : 0.37% – 1.76%
```

**All six hard bounces are Gmail** — 4 nonexistent, 2 disabled:

```
4 x  550 5.1.1  "The email account that you tried to reach does not exist"
2 x  550 5.2.1  "The email account that you tried to reach is inactive"  (DisabledUser)
```

**I initially mis-scored the 5.2.1 replies.** My classifier had no pattern for them and
labelled a real hard bounce `rejected_unspecified` — which on the two-event sample I had at
the time understated the rate by half. A disabled mailbox hard-bounces exactly like a
nonexistent one. Fixed, unit-checked against six reply shapes, and every sample was
**re-scored from its stored reply text** rather than re-probed.

### What this number is NOT

- **It is not a deliverability rate.** A 250 at RCPT means the mailbox exists, not that the
  message lands in an inbox. Content filtering, greylisting and reputation all act later.
- **It measures HARD bounces only** — the category that damages sender reputation. Soft
  bounces and spam-foldering are invisible to this method.
- **Yahoo cannot be verified from this machine at all** (18 rows). The rejection is about our
  IP's missing rDNS, not about the addresses.
- **The sample is 27.3% of the file.** It is stratified two ways precisely because
  neither shape alone is representative.

### The one new predictor this round found: addresses the export REWROTE

Not in the brief, and small, but it is a category nobody was looking at. **8 rows (0.27%)**
carry an address in the export that differs from every address in their master cell:

```
6   leading "'-" stripped     '-<local>  ->  <local>        (same domain)
1   leading "www." stripped   www.<local>  ->  <local>       (same domain)
1   local part otherwise changed

(local parts withheld — these are live leads, and the report is public.)
```

The six `'-` cases are **provably safe** — that prefix is a spreadsheet formula-injection
guard, never part of the address. The `www.` strip is a **guess**: plausible, but the
pipeline invented an address that no source ever asserted. One row. Recorded so the category
has a name and a count.

**This also corrects my own first pass.** A naive whole-cell join reported **15 orphan rows**
— addresses in the export with no master row. That would have been alarming, because
`send_suppress.classify(in_master=False)` hard-excludes an orphan, so it would have meant the
export was shipping rows the policy forbids. It was my join: master cells can hold several
addresses in one cell, semicolon-separated, and the export takes the first. **The real
orphan count is 0.**

## 6. The pre-send gate — specced, built, and measured

`scratch/bl962_gate.py`. A **prototype in `scratch/`**, not a pipeline change: it reads a
send CSV and writes a verdict, and edits nothing in `clippershq/` or `output/`.

```
python scratch/bl962_gate.py output/ALL_BOT_READY.csv              # tiers 1-2
python scratch/bl962_gate.py output/ALL_BOT_READY.csv --batch 20 --smtp   # + tier 3
```

| tier | what | cost, MEASURED | removes |
|---|---|---|---|
| 1 | syntax + typo blocklist, via the same `bio_parser` the build uses | **0.02 s**, offline | 0 |
| 2 | **re-resolve every domain**, two-resolver confirm on dead | **2.44 s** for 561 domains | **5** |
| 3 | SMTP RCPT probe **over the batch only** | ~3 s/address | see §3 |

**Full-file run, today: 2,980 in → 2,975 out, 5 removed (0.17%), 2.5 seconds total.**

Tiers 1–2 are cheap enough to run before **every** send, which is the requirement — a file
rebuilt today goes stale within the week, and 2.5 seconds has no reason to be skipped.

Tier 3 is deliberately scoped to the batch. Probing all 2,980 would take hours and would
connect to the same few providers thousands of times, which is itself a reputation risk.

**Measured on the recommended 20-row first send** (`--batch 20 --smtp`):

```
tier 1 syntax+typo    0.01s   removes 0
tier 2 DNS/MX         0.05s   removes 0   (4 domains)
tier 3 SMTP probe    58.77s   removes 0   (20 probed, 1 of 4 domains catch-all)
                                          19 accepted, 1 sender_refused (our rDNS)
GATE VERDICT          20 in -> 20 out          total 58.8s
```

**59 seconds for a full three-tier check of the first send.** There is no version of "too
expensive to run" here.

**What the gate may never do:** remove a row on an UNKNOWN. Unresolved DNS, a greylist, a
policy rejection aimed at the probing client, and a catch-all accept are all *no
information*. A gate that cut on those would delete deliverable leads to improve its own
number — the same error as treating an absent MX-table entry as dead.

**What it does not cover, stated plainly:** it validates addresses. It cannot see content
reputation, sending-IP reputation, SPF/DKIM/DMARC alignment, or whether the sending domain
is authenticated at all. Those decide whether a *delivered* message reaches an inbox, and
none of them are in this repo.

## 7. First send: size, shape, and the number that means stop

**The binding constraint is not deliverability — it is BL-956's finding that only 86 of
2,980 rows merge into a message you could read aloud.** The list is safe enough to send far
more than the message is ready for.

Sender reputation is built, not assumed. A cold domain that opens with 100 looks like a
different sender from one that opens with 20.

| day | volume | gate | proceed only if |
|---|---:|---|---|
| 1 | **20** | tiers 1–3 | 0–1 hard bounces, and all 20 read by eye first |
| 2 | 20 | tiers 1–3 | cumulative hard bounces ≤ 1 |
| 3 | 30 | tiers 1–3 | ≤ 2 cumulative |
| 4 | 40 | tiers 1–2, tier 3 on the batch | ≤ 2 cumulative |
| 5 | 50 | as above | bounce rate < 2% |
| 6–7 | hold | — | reply/complaint signal reviewed |
| week 2 | 60 → 100/day, +50%/day | tiers 1–2 every send | bounce < 2%, complaints ≈ 0 |
| week 3+ | 150 → 300/day | tiers 1–2 every send | as above |

**Stop rules, derived from the measured rate rather than a round number.** At the measured
0.81%, a 20-address batch expects **0.16** bounces:

| batch | P(≥1) at 0.81% | P(≥2) at 0.81% | P(≥2) if truly 2% |
|---:|---:|---:|---:|
| 20 | 15.0% | **1.1%** | 6.0% |
| 50 | 33.4% | 6.2% | 26.4% |
| 100 | 55.7% | 19.5% | 59.7% |

- **1 bounce in a 20-batch: normal.** Happens 15% of the time at the measured rate.
- **2 bounces in a 20-batch: STOP AND RE-MEASURE.** A 1.1% event if the list is as good as
  measured, and 6× more likely if the true rate is at the 2% throttle line. It is a signal,
  not proof — but at 20 addresses the cost of stopping to check is nil.
- **≥2% hard bounces in any batch of 50+: STOP IMMEDIATELY.** Gmail and Outlook throttle
  there, and the damage is the one cost in this project that fixing code does not recover.
- **Record every bounce.** `master_leads.csv` has a `bounced` column and it is empty on all
  59,006 rows. Fill it, or the next round is exactly as blind as this one was in §2.

## 8. The honest expected bounce rate

### The number

```
MEASURED, on 737 informative probes covering 813 distinct addresses (27.3% of the file):

    hard-bounce rate      6 / 737  =  0.81%
    95% Wilson interval              0.37%  –  1.76%
    file-weighted check   72.3% x 1.06% (gmail) + 27.7% x 0.00% (rest) = 0.77%
```

The pooled estimate and the file-weighted estimate agree to within 0.04 points, which is the
reassuring part: the two stratifications are not pulling against each other.

**Expected hard-bounce rate for the current file, after the §6 gate removes the 5 DNS-dead
rows: ~0.8%, and under 2% at 95% confidence.**

### Confidence: moderate-to-good, and here is exactly what it rests on

**What makes it strong:**
- 27.3% of the file was probed, not a token sample.
- The dominant provider was **verified to discriminate** before its answers were used —
  three impossible addresses, five MX hosts, all 550 5.1.1.
- 88.1% of rows sit on domains that give a clean answer.
- Four independently-seeded samples. The three gmail draws land at **1.33% (2/150),
  1.20% (3/250) and 0.62% (1/160)** — consistent, and none is doing the work alone.

**What keeps it from being strong:**
- **All six hard bounces are gmail, and gmail alone is 1.06% [0.49–2.30%]** — that interval
  does *not* exclude 2%. The pooled "under 2%" conclusion depends on the 172 non-gmail
  informative probes contributing zero, and their own interval is [0–2.18%]. **The corporate
  tail is not proven clean; it is unmeasured-and-so-far-blameless.**
- 283 rows (9.5%) are on catch-all domains and are **unverifiable in principle** by this
  method. If they bounced at 5%, that adds 0.5 points.
- The pooled interval treats 737 probes as one binomial. They cluster by domain, so the true
  interval is slightly wider than quoted.
- **RCPT acceptance is not delivery.** A 250 says the mailbox exists. Content filtering,
  greylisting, SPF/DKIM/DMARC alignment and IP reputation all act afterwards, and none of
  them are visible from here or present in this repo.
- This is a **snapshot**. Mailboxes are abandoned continuously; one of the six bounces was a
  *disabled* account, which is what an aging list looks like.

### What would have to be true for it to be under 2%

**It already is, and this round is what made that statement possible rather than aspirational.**
At the first sample size (334 informative) the 95% upper bound was 2.16% — above the line, so
the honest answer then was "probably, but not demonstrably". Extending the gmail sample twice
brought it to 1.76%.

For the claim to *fail*, one of these would have to hold:

1. **The catch-all tail is much worse than the verifiable mass.** 283 rows would need to
   bounce at ~13% to drag the file over 2%. Nothing suggests that, and nothing can rule it out.
2. **The list ages before it is sent.** At 0–33 days old this is not yet a factor; at six
   months it would be. Re-run the §6 gate on the day of the send, not on the day of the build.
3. **The send is not gated.** The 5 DNS-dead rows are only 0.17%, but they are *certain*
   bounces and free to remove.

**The honest bottom line: bounces are not what is dangerous about this send.** At ~0.8% the
file is comfortably inside Gmail's and Outlook's tolerance. **The real risk is that 2,980
rows carry a message that does not exist yet, and that only 86 of them merge into something
readable** (BL-956). A well-delivered bad message damages a sender domain about as
efficiently as a bounce does, and nothing in this round measures that.

## 9. What I got wrong

1. **The no-send guard was a string match on its own source** — the exact proxy failure
   `PRECONDITIONS.md` §10 describes. Replaced with a behavioural test that drives the guard.
2. **The catch-all control shared a session with the real recipient**, which made Outlook
   answer `452 4.5.3 multiple regions`. Would have scored every Microsoft domain as a
   deferral. Caught in the pilot.
3. **The reply classifier had no pattern for `5.2.1` (disabled account)** and scored a real
   Gmail hard bounce as `rejected_unspecified` — understating a two-event sample by half.
4. **A naive master join reported 15 orphan rows.** The real count is 0; master cells hold
   multiple addresses. Reported here rather than in the findings because I checked it before
   publishing, per §11.
5. **My typo detector flagged `outlook.dk/.ie/.pt`** — real Microsoft country domains. Kept
   in the report as detector false positives rather than quietly dropped.
