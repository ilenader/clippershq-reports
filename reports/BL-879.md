# BL-879 — What the operator actually does every day

**Read-only audit.** No code changed, no paid calls, no renders. Every number below is either
**MEASURED** (I ran it on this tree, today) or **INFERRED** (derived from stored run records
or knobs) and is labelled as such. Where I could not measure a stage I say so rather than
estimating quietly.

Claim filed as `BL-879` with repeated `--write` flags before any work began.

---

## 0. The headline

**The video half of this system cannot produce a single video today, and nothing says so.**

I ran the real song matcher over the real clip library:

```
song-matched 2003 clips in 1.09s
RENDERABLE TODAY:      0 / 2003   (0.0%)
PARKED:             2003
```

All four songs in the store are `enabled: false`, and **all 8 hook windows are placeholders**
— `"note": "PLACEHOLDER - mark by ear"`, `"window_is_placeholder": true`, `uses: 0` on every
one. `hookmark/` was built (MEMEBOT-012) precisely to mark them. It has never been used on a
single window.

Flipping `enabled` alone, in memory, changes the answer immediately:

| state | renderable |
|---|---|
| as shipped today | **0 / 2003 (0.0%)** |
| if `enabled: true` | **210 / 2003 (10.5%)** |

So roughly **25 minutes of ear-work** — mark 8 windows, enable 4 songs — moves the pipeline
from zero to 210 renderable clips. Everything else the operator does today (discovery, the
walk, retrieval, vision labelling) produces material that cannot become a video until that
one human task is done. This is the single highest-leverage unit of work in either project,
and nothing in any menu, banner or doc tells the operator it is outstanding.

This is consistent with BL-877, which landed while I was measuring: it found 86.6% of vision
labels are bought for clips no song matches, and that selection is set by the song store
rather than by ranking. Same wall, measured from the other side.

## 1. The daily loop, end to end, with real timings

There is **no orchestrator**. The operator drives eight separate tools by hand and must
remember the order. Nothing hands off to the next stage.

| # | Stage | What the operator types / clicks | Time | Basis |
|---|---|---|---|---|
| 1 | Open dashboard | `python dashboard/server.py --port 8787`, then open `127.0.0.1:8787` in a browser | ~10 s to start | INFERRED (import cost) |
| 2 | Launch menu | double-click `START.bat`, or `python clippershq/main.py` | **3.1 s** to menu | MEASURED |
| 3 | Run discovery | pick a funnel, read the BEFORE-YOU-SPEND block, answer `y`, then **wait** | **~14 min** per 200 leads (`4.1–4.3 s/lead`) | MEASURED (stored run rows) |
| 4 | Clip walk `[K]` | `[K]`, confirm | walks **239** confirmed pages, ≤5 pages each, $2 cap | INFERRED (knobs + `confirmed_accounts` = 4.9 s → 239) |
| 5 | Vision label | run a ranked labelling script from `scratch/` by hand | 1,544 / 2,003 clips labelled (77%) | MEASURED |
| 6 | Rebuild send list `[B]` | `[B]` | **~14 s** (3.5 s import + 10.1 s build) → 2,949 leads | MEASURED |
| 7 | Match songs | (no menu entry — happens inside the render path) | **0.5 ms/clip**; 2,003 in 1.09 s | MEASURED |
| 8 | Render videos | `MAKE_VIDEOS.bat`, paste links in Notepad, **verify every caption in Notepad**, save | **13.0 s** median per video | MEASURED (`runs.jsonl`, n=3, all `white_frame`) |
| 9 | Record outcomes `[O]` | `[O]` → `[4]`, give path + date + channel, read dry-run, confirm | ~2–5 min per batch | INFERRED |
| 10 | Export clips `[x]` | `[x]` in Control Panel | **3.7 s** → 3,814 rows (**see §5 — 47% are duplicates**) | MEASURED |

**The machine time is trivial. Every real cost is either a paid run the operator waits on, or
a human judgement the machine correctly refuses to make.**

Two traps sit inside stage 3 that a new person will hit. `docs/OPERATING.md` documents both
and they are still true: piping a live paid run through PowerShell `Select-Object -First N`
**terminates it** (it killed a live run on 2026-07-31), and `-replace` treats `$0` in the
replacement as a backreference, which matters because this repo's text is full of dollar
amounts. Redirect to a file, then read the file.

## 2. What genuinely requires a human

These are correct as human tasks. Each was closed as not-machine-doable on evidence, and the
code refuses to guess rather than guessing badly.

| Task | Unit | Real time cost | Why it cannot be automated |
|---|---|---|---|
| **Mark hook windows by ear** | per song | ~5–7 min/song (~25 min for the current 4) | BL-690: automatic drop detection scored **100% fabrication** — it returned a timestamp on all 36 clips including all 19 with nothing there, and its *most confident* outputs were the wrong ones. |
| **Judge captions** | per video | ~30–60 s/video; longer for `CHECK THIS` lines | A confident wrong caption ships a broken video. The pipeline deliberately stops and shows a photo of the source caption for every flagged clip. |
| **Buy songs** | per song | licensing + purchase, minutes to hours | Not a software problem. |
| **Fill mood maps / `targets`** | per song | ~10–15 min/song to write a target description that discriminates | BL-795 closed audio mood at **40% reproducibility**. The `targets` string is the human's substitute for a detector that does not work. |
| **Decide what to post** | per video | judgement | No signal in the system predicts it. |
| **Decide whether to spend** | per run | seconds, but must be deliberate | Every paid funnel shows cost per 1,000 and asks first. Correct design. |

One structural consequence worth stating plainly: **the mood map is the throughput ceiling,
not the clip supply.** 1,793 of 2,003 clips (89.5%) park with `no rule matched and no house
set`. The library the system has already paid to discover, walk, retrieve and vision-label is
~90% unusable *at the song gate*, and the only thing that widens that gate is a human writing
song rules and buying songs.

Measured mood distribution across the 2,003 clips:

```
None          1793   89.5%      <- parks, no rule matched
hype           183    9.1%
warm            24    1.2%
melancholy       3    0.1%
```

## 5. What silently needs doing

The premise is correct, and one instance is **live right now**.

**a) Rebuilding the send list — and it is stale as I write.** The system's own test:

```
output\ALL_BOT_READY.csv   rows 2949   mtime 2026-07-31 23:10:19
master_leads.csv                       mtime 2026-08-01 19:34:02
stale: true
```

~20 hours stale. Partial credit where due: `announce_send_file()` **does** fire after every
funnel run and does say *"New leads from this run are NOT in it yet — rebuild with [b]"*. So
the loop is not unguarded. But:

- It **never runs at startup**. Quit and come back tomorrow and the menu says nothing.
- It prints `last built <timestamp>` **unconditionally** — it never compares against the
  master and never says the word *stale*.
- `staleness_of()` and `_freshness_warning()` exist, are correct, and are called **only** from
  `all_bot_ready.main()` — i.e. only if the operator runs `python all_bot_ready.py` directly.
  Neither `main.py` nor `control.py` imports them.
- Worse: the one caller checks `LATEST_BOT_READY.csv` — the **decoy file** the operator is told
  never to send from — not `ALL_BOT_READY.csv`.

Honest footnote: rebuilding today yields the same 2,949 rows, because today's runs were repost
pages, which return handles and go to the DM list. So today's staleness cost nothing. **The
defect is that nobody could know that without running it.**

**b) The six-file backup. Nothing prompts it, anywhere.** I grepped every module: the only
"backup" code is `config.json` and `state.json` internal snapshots. The offsite ritual is
documented in `BACKUP_THESE_6_FILES.md` and referenced by `OPERATING.md`, and is triggered by
memory alone.

## 6. The honest answer

**How many hours per week does running this cost?**

At the current state — one funnel a day, ~10 videos a day — with assumptions stated:

| Activity | Per day | Per week |
|---|---|---|
| Discovery: start, watch, read the summary | ~20 min (≈14 min of it waiting) | 1.7 h |
| Clip walk + labelling: launch, wait, sanity-check | ~15 min | 1.3 h |
| `[B]` rebuild send list | 14 s | ~0.02 h |
| Caption verification, ~45 s × 10 videos | ~8 min | 0.9 h |
| Render + collect, 13 s × 10 | ~2 min compute | 0.2 h |
| Decide what to post | ~10 min | 1.2 h |
| Outcome stamping `[O]`→`[4]` | ~5 min | 0.6 h |
| Backup ritual (if actually done) | ~5 min | 0.6 h |
| Navigation, recall, "which tool next" | ~12 min | 1.4 h |
| **Total** | **~1.3 h/day** | **≈ 8 h/week** |

Plus one-off human work as songs are added: ~5–7 min per song to mark hooks, ~10–15 min per
song to write a `targets` rule.

**Caveat that dominates the table: today, the video rows produce nothing.** 0 of 2,003 clips
can render. So the ~8 h/week is the cost of running the loop, not the cost of a loop that
ships. The discovery half genuinely works and genuinely produces a 2,949-lead send file.

**The single change that would cut it most:**

> **Mark the 8 hook windows by ear and enable the 4 songs. ~25 minutes, one-off.**

It is the only thing standing between a fully-built pipeline and its first automated output.
It takes renderable clips from **0 → 210**. Every other hour currently spent on discovery, the
walk, retrieval and vision labelling is producing material that cannot become a video until
that is done — which is the same thing BL-877 measured as 86.6% of vision spend bought for
clips no song matches.

Second, once that is unblocked, the ceiling moves to the mood map: 89.5% of the library parks
with `no rule matched`. That is where the next hour of human work pays.

And if only one *engineering* hour is available, spend it on §3 items 1–3 — the staleness
warning, the export dedup, and adding `clip_library/` to the backup list. About an hour
together, and each removes a way to silently lose a day's work or a month's corpus.
