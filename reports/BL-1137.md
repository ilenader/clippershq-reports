# BL-1137 — the automatic path delivers ZERO song-matched videos, and it is wiring, not songs

**2026-08-05. Read-only round. $0.00 spent against a $0.50 cap — every measurement below is
local. `scratch/songs.json` was never opened for writing; `config.json`, the five campaigns,
the clip library and the render ledger are byte-identical to how this round found them.**

---

## The one-paragraph answer

You asked where else the funnel leaks. It leaks in one place harder than anywhere else, and it
is not a song problem. **The production render path calls the song matcher 216 lines before it
reads the field the song matcher matches on.** `pick_song` runs at `clip_pipeline.py:3680`;
`clip_label_text.read_source_line` — the OCR pass that produces `source_line` — runs at
`clip_pipeline.py:3896`. `source_line` is not a clip-library field: **0 of 9,723 library rows
carry it**. So `song_library.hook_line_text()` reads `""` on every clip, the text-first matcher
takes its first branch, and **every clip parks with "no source line"**. Measured over the whole
library: **2,748 clips → 89 clear the gate → 0 match a song.** Not one. The 1–3 videos you see
per batch do not come from this path; they come from the hand-driven scratch scripts of
BL-1130/1133/1136, which OCR first and match second. That is **6 renders ever matched on the
source's own line**, those three rounds combined.

The song library is still a real ceiling — with the wiring fixed the same library yields 7 —
but it has been standing behind a wall the whole time, and nobody has been measuring the wall.

## 1. The funnel, stage by stage, with counts and named reasons

### 1a. First: "440 → 140 → 6 → 1" is two funnels spliced together

I could not reproduce it as one chain, and the reason is worth a paragraph because it is why
"the 300" had never been broken down: **there is no stage that takes 440 in and emits 140.**

* **440** is a *walked-clips* total — clips pulled off Instagram pages across several rounds.
* **140** is `scratch/bl1133_render.json`'s `"candidates": 140` — the size of the pool BL-1133's
  render script drew **from the stored library**, not from that walk.

Two different populations. The 300 is a subtraction between a numerator and a denominator that
were never in the same funnel. Both halves are individually real; the arrow between them is not.

## 2. The three defects, each proven, none of them about songs

### Defect 1 — the matcher is called before its input exists (the expensive one)

The render loop's own step letters:

```
clip_pipeline.py:3633   -- a. RETRIEVE      (PAID)
clip_pipeline.py:3675   -- b. STAGE
clip_pipeline.py:3680   -- c. SONG          pick_song(clip, ...)      <-- reads clip["source_line"]
clip_pipeline.py:3830   -- g. RENDER
clip_pipeline.py:3896        read_source_line(src, ...) -> rec["source_line"]   <-- WRITES IT
```

216 lines apart, in the wrong order, and the write lands on `rec` (the ledger record) rather than
on `clip` (what the matcher was handed). Nothing between line 3594 (loop start) and 3680 assigns
`clip["source_line"]` — I checked every line in that range for a mutation of `clip`; there is
exactly one statement touching the name, `clip = cand["clip"]` at 3613.

**This was known and written down.** `scratch/bl1130_render.py:200`, in that round's own words:

> `pick_song` reads the LIBRARY record, which has no source_line. Re-run the match on the line
> we actually read […]

And BL-1136 hit it again from the other end, `scratch/bl1136_render.py:254`:

> `pick_song` IS CALLED ON THE RECORD PLUS THE LINE WE JUST READ, and the first version of this
> script left the line off. `pick_song` refuses a clip with no `source_line` outright […] so it
> **fell through to the `none` tier on all five renders** — returning an EMPTY `track_id` […]

**That is a description of production.** BL-1136 saw the exact behaviour the shipped path has,
recognised it as its own bug, fixed its own script, and moved on. Three rounds hit this wall,
three rounds patched around it locally, and `clip_pipeline.py` still has it. Every one of the 6 `TEXT_RULE` renders in
`memebot/runs.jsonl` came out of a scratch script carrying that workaround — 3 from BL-1130, 1
from BL-1133, 2 from BL-1136. **Zero came from the production path.** The only other matched
renders in the ledger are 51 `VISION_RULE` (all from BL-1127/1128) and 9 `FALLBACK`, every one of
them from before BL-1130 made the text the deciding signal.

This is the "a helper can be correct and called by nothing" shape again, one layer out: the
*fix* was correct and lived only in a throwaway file.

### Defect 2 — the format gate judges a field the renderer stopped drawing

`clip_pipeline.py:524` calls `meme_format.classify(caption=_f(clip, "caption"), …)`. That module's
docstring explains why: *"the reposter's caption, which is what reaches the white label."*

**That sentence was true when it was written and has not been true since BL-1130.**
`render_one(label=…)` now takes a `SourceLine` from `read_source_line` — the words burned into
the source's own frames. The caption is provenance and a progress label; it is not drawn.

`meme_format.py:89` predicted this exactly, in the comment beside `HOOK_MAX_CHARS`:

> A pipeline that drew the SOURCE's line instead of the reposter's caption would keep it.

Measured (`scratch/bl1137_wrongfield.py`), re-reading only the caption-derived verdicts against
the clip's own burned-in line:

```
verdict on the REPOSTER'S CAPTION (what the gate reads today)
   DIALOGUE 1,195 · PROMOTIONAL 833 · TOO-LONG 425 · MEME-HOOK 191 · HASHTAGS 102 · NO-TEXT 2

of the 1,362 caption-derived refusals, re-read on the SOURCE'S OWN LINE
   766  FLIP to MEME-HOOK          <- refused for a field the renderer does not use
   234  still refused (the line is a blurb / too long / a credit too)
   362  no line stored to re-read
```

**766 clips — 27.9% of the library — are refused for the reposter's caption while their own
burned-in words are a hook.** Twelve examples, unedited:

| caption (what convicted it) | the line it actually burns in |
|---|---|
| `#theboys #theboyz #homelander #relatable #viral #reels` | *When you try to be nice, but everyone is triggering you:* |
| `Real . . . . #ryangosling #fyp #viral #memes …` | *Me with girls in real life : / Me with the girl who lives 750 miles away :* |
| `📺 Movie ⭐ Genre: Crime, Drama, Biography 🎭 Starring: …` | *Teenager outsmarts arms dealer by identifying the fake Russian weapons* |
| `🎥 Justice League \| 2017 · Action/Sci-Fi · 2h 📜 Storyline …` | *When someone mention your past, but now you are a completely different person.* |
| 915 characters of Lupin III production history | *Didnt expect that ending* |

### Defect 3 — the blank-frame term reads the thumbnail and the reason names the clip

`gate_detail` refuses 118 clips with *"cover frame is uniform — no imagery to read."*
`cover_frame_is_blank` reads `layout.strip_frac` / `layout.bar_mid_frac` — features of the
**cover frame**. Across the library the term fires on 135 clips, and **116 of them have a
vision-model description of real footage inside the video**: Batpod chase sequences, a Harry
Potter scene with Russian subtitles, *"A werewolf is about to fight, but Nandor chooses a squeaky
toy as his weapon."* Nineteen have no scene description and nothing contradicts the refusal.

The term may well be right about the thumbnail. The reason it prints is a claim about the clip,
and for 116 of 135 that claim is false.

**Ten of the thirteen are one defect** (the caption/source-line mismatch) and three are the
cover-frame term. There is no third cause in the sample — which is the useful part: this is not
forty small problems, it is two, and both are a field substitution rather than a threshold.

Two things I checked and will **not** call false refusals:

* **`no audio class` (141 first-reason, 160 library-wide).** 98 of the 160 have a measured

* **The duration floor.** 233 clips sit below `MIN_DURATION_S = 7.626`, and **221 of them are in
  the 5.0–7.6s band** — one sampled clip misses by 0.126s. The floor is verified end to end
  (BL-1052) and I am not second-guessing it; I am telling you the band is crowded, so any future
  move there is worth more than it looks.

## 4. What a slightly broader subject would cost — four buckets

**`scratch/songs.json` was loaded, deep-copied in memory, and the copy widened. It was never
written. This is a measurement, not a proposal.**

**The widening, defined mechanically so you can argue with it:** *one weak phrase fires the rule
instead of two distinct ones.* It invents no phrase, moves no subject, and touches nothing but
the evidence bar on the words you already wrote.

**The universe:** the 1,929 library clips that carry a readable burned-in line. (The other 819
carry none at all and can never match a text-first matcher — that is its own ceiling and it is
30% of the library.)

| bucket | n | |
|---|---|---|
| **KEPT** — matched before, same song after | **28** | every current match survives |
| **MOVED** — matched before, a *different* song after | **0** | |
| **GAINED** — parked before, matches after | **94** | |
| **PARKED** — matched neither | **1,807** | |
| **sum** | **1,929** | = the universe, exactly |

`LOST` is a fifth bucket the instrument carries and it stayed at 0, as a pure widening requires.

**MOVED = 0 is a measured fact, not a blind spot.** A first-match-wins matcher reports one mood
and hides any second, so `scratch/bl1137_contention.py` asks each rule *independently*: across
1,929 lines, **exactly one** fires two rules even after widening — and that line was parked at
baseline, so it lands in GAINED. There is no contention to move.

**The second widening I measured is a no-op, and that is worth knowing.** Dropping
`tone_conflict_any` (the melancholy rule's `pov` / `when bro` / `lol` guard) changes nothing:
that list only sets `needs_review`, it never blocks a mood. **It costs you zero supply and buys
a review flag.** Keep it.

## 5. What the automatic path can deliver today

I measured four arms over the same 2,748 clips (`scratch/bl1137_ceiling.py`). Each is a superset
of the one above, so the increments are attributable. Arms C and D are counterfactuals measured
by substituting a field — **nothing was changed in any gate.**

| arm | clears the gate | **matches a song** |
|---|---|---|
| **A — as shipped today** | 89 | **0** |
| B — matcher handed the line (defect 1 fixed) | 89 | **2** |
| C — B + the format gate reads the line (defect 2) | 578 | **7** |
| D — C + the cover-frame term (defect 3) | 622 | **7** |
| E — D + the weak-once widening | 622 | 38 → **18 right by hand (47%)** |

### The plain statement you asked for

**At current settings the automatic path delivers zero song-matched videos per day, at any batch
size, from any batch of clips.** It is not "1–3 a batch"; that number is what your hand-driven
rounds produce, and it is **2 per round, 6 in total across BL-1130, BL-1133 and BL-1136.**

**With the three wiring defects fixed and no new songs: 7 videos from the entire 2,748-clip
library.** That is the whole standing inventory, not a daily rate. Fresh supply adds about 18
stored clips per walk at $0.12 (219 walked, 18 stored across the two measured walks), and at the
arm-D match rate of 7/2,748 those 18 clips are worth **0.05 of a video.**

So the honest sentence is worse than the one you offered me:

> **Without new songs, the automatic path is not "2–3 good videos a week". It is roughly seven
> videos total, once, and then it is done — and today it is zero, because the matcher has never
> been handed its input in production.**

**Cost.** $0.0006 per Instagram page. Lifetime spend $11.91 for 411 completed renders — but only
6 of those 411 carry a matched song, so the cost per *song-matched* video is dominated by the
rounds, not the API: the last three each spent $0.02–0.10 and produced 1–3. Call it **$0.05–0.10
per song-matched video in API terms**, and the real cost is a hand-driven round.

**The postable share I cannot give you, and that is itself a finding.** Nothing in
`memebot/runs.jsonl` records whether you posted a render. The `posted_at` field on 926 records is
the *source clip's* Instagram timestamp, not ours. The only outcome signals that exist are prose
in round reports: two batches rejected for forced matches, and BL-1133's own shipped file
described by that round as *"not a good video."* On the record, **the number of renders you have
confirmed as postable is zero, because there is nowhere to write it.**

## 7. Where the honest uncertainty is

`source_line` is not a library field, so every library-wide count here uses
**`vision_on_screen_text`** — the vision model's read of the same burned-in words, present on
1,929 of 2,748 clips — as a stand-in. The render path uses `read_source_line`'s 5-frame character
consensus instead. BL-1130 measured the *assembly* as the defect and the eyesight as sound, so
the two should agree on content and not on formatting, but **they are not the same read and I
have not measured their agreement.** Treat 766, 94, 7 and 38 as estimates on a proxy field.

What does **not** depend on the proxy: defect 1 (an ordering, read off line numbers), the 0 of
9,723 rows carrying `source_line`, the 103 walked-but-never-gated clips, MOVED = 0, and arm A's
zero.
