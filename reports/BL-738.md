## Item 3 answered: NOT fixed — and I proved it offline, no gate required

The brief asked whether the 11:33:26 edit already fixed this. **It did not.** That edit was
the `is_junk_scrape_host` skip-list work (BL-712's finding). `fetch_link` at
`enrich_links.py:266-281` still reads:

```python
_t = timeout if isinstance(timeout, tuple) else (
     min(5.0, float(timeout or 10.0)), float(timeout or 10.0))
resp = getter(url, timeout=_t, headers={"User-Agent": _UA},
              allow_redirects=True)
```

`DEFAULT_TOTAL_FETCH_SECONDS` and `DEFAULT_MAX_REDIRECTS` are both **ABSENT** from the module.

Rather than assert the mechanism, I built two adversarial localhost servers — no network, no
spend, no gate needed — and ran the real `fetch_link` against them.

**A) Redirect chain, 10 hops, 0.6s server delay per hop, `timeout=6`:**

```
elapsed        : 7.17s
per-hop floor  : 6.00s
verdict        : no chain deadline present -> per-hop only
```

It completed only because each hop was fast. Nothing bounded the chain — the cost scales
linearly with hops, and `requests.Session.max_redirects` defaults to **30**. With the config's
`enrich_links_timeout = 6`, the arithmetic is:

> **30 hops × (5s connect + 6s read) = 330 seconds for one fetch.**

That comfortably contains every figure BL-730 measured — 85s, 141s, 165s, 218s.

**B) Trickling server, one byte every 1.5s, `timeout=6`:**

```
elapsed        : 40.52s
got html       : False  (len 0)
verdict        : unbounded by construction (no total deadline)
```

**A 6-second timeout held a connection open for 40.5 seconds and returned nothing at all.**
Every socket read reset the read clock, so the read timeout never fired. Had I not shortened
the test, it would have run 600s. This is item 2 demonstrated exactly: a per-read timeout
cannot bound a trickling server, and the wasted time buys zero recall.

**C) Control, single hop:** 0.61s, HTML returned, and the fixture's synthetic mailto address
parsed correctly. The fetch path itself is healthy — only the unbounded cases are pathological.

So the diagnosis in BL-730 is now confirmed by direct experiment rather than inference, and
**both axes are broken: no chain deadline and no total-elapsed bound.**

## The fix, specified so the next round is mechanical

Not applied. Written down so it does not need re-deriving:

1. **`allow_redirects=False`, walk the chain manually under ONE shared deadline.** Compute
   `t_end = monotonic() + total_seconds` once, then per hop pass
   `timeout=(min(connect, remaining), min(read, remaining))`. When `remaining <= 0`, log and
   return `None`. This is the actual fix — the per-hop budget is the defect, the 6s value is
   fine.
2. **Cap hops explicitly** (`DEFAULT_MAX_REDIRECTS = 5`), not 30. A legitimate artist site does
   not need six redirects; an affiliate chain does.
3. **Bound the body read too** — `stream=True` plus `iter_content` with the same deadline
   checked between chunks, so case B above cannot hold a worker.
4. **Config keys**, matching the module's existing convention (`enrich_links_timeout` is
   already read by callers in `control.py:1899` and `:2124`): add
   `enrich_links_total_seconds` (default 15) and `enrich_links_max_redirects` (default 5) as
   module constants overridable per call.

The re-measurement then runs three invocations of `bl731_audit.py` at target 40 / cap $0.05
(≈$0.15): `BL731_FLOOR=20` twice back-to-back, then `BL731_FLOOR=10`, compared against
BL-728's `run_final` (759s, 23 timeouts) — checking that **emails delivered does not fall**.
