## 1. WHAT WAS FALSE

### 1.1 "the postable rate is 13 of 30" — **superseded mid-round**

`MEMEBOT-098` measured **13 of 30** and it was the standing figure all session. **While this
pack was being written, `MEMEBOT-108` published `775008e`: 10 of 30**, re-audited at the same
bar with BL-988's selection gate applied in-harness, every sheet read at **full frame**
(MEMEBOT-102's instrument trap: a 30% crop cut a caption line and nearly produced a false
verdict).

**The rate went DOWN when the audit was repeated, not up.** And the failures split exactly:

| class | n | meaning |
|---|---:|---|
| `SELECTION` | **10** | the clip should not have been chosen |
| `RENDER` | **10** | the renderer damaged an acceptable clip |

That split is load-bearing for the operator: **half the failures will not be fixed by better
music**, which is where actions 5 and 6 of the pack put their effort.

The pack now reads the audit from `scratch/mb108_verdict.json` rather than from a report, and
`bl1021_verify.py` prints the superseded figure next to the current one so the next round can
see which way it moved.

### 1.2 "the hook re-marking takes within-2s from 2 to 16 of 28" — **needs a code change that has NOT landed**

Measured here through the **real `place_at_detail`**, against `ground_truth/clip_drop_labels.json`
(28 hand labels), at the 20 s ceiling:

| | windows placeable | within 2 s | median error |
|---|---:|---:|---:|
| today — the music starts at 0 | **4 of 21** | **2 of 28** | 7.00 s |
| 4 s cores, code as it is today | 21 of 21 | **8 of 28** | 3.60 s |
| 4 s cores **+ a fixed 5 s target** | 21 of 21 | **16 of 28** | 2.00 s |

**`PLACE_AT_FRACTION` is still `0.43` at `clippershq/song_library.py:80`.** MEMEBOT-105 asked
for a fixed 5 s constant and it has not landed. So **re-marking alone buys 2 → 8, not 2 → 16.**
The two changes are multiplicative and the pack now says so, in the operator's own terms:
*ask for the constant when you re-mark.*

The "4 of 21" half **is** confirmed: 17 of the 21 windows exceed 10 s, and
`place_at_detail` refuses to move a hook when `clip_len < 2 * hook_len` with the clip capped at
20 s.

### 1.3 "4.55% of the ledger is reconstructed" — **it is 30.65%, and the figure should never have been a constant**

`docs/OPERATING.md` hard-codes *"$0.1902 of $4.1782 (4.55%)"* as of 2026-08-01. BL-879
reconciled it the next day at **17.44%**. Measured now:

```
ESTIMATED  $3.3149 of $10.8148 = 30.65%   over 13 of 633 ledger rows
METERED    $7.4999            = 69.35%
```

**A document that hard-codes a moving number is wrong within hours.** The pack therefore ships
the **command**, not the constant, and labels the value as of the sha.

## 2. A DEFECT ON THE DAY-ONE PATH THAT FIXED ITSELF UNDER ME

`docs/FINAL_STATE.md` action (f) tells the operator to run:

```bash
python -m clippershq.outcome_loop analyse
```

**It crashes.** `_cli_analyse` iterates the whole result dict as if every key were a question,
then calls `.items()` on the `confounds` **list**:

```
AttributeError: 'list' object has no attribute 'items'
```

Two things made this worth reporting rather than noting:

**It is not an empty-data path.** I planted four records carrying real `views` and re-ran it:
same crash, exit 1. `docs/TESTING.md` rule 5 — *"I cannot see it" must not look like "it is not
there"* — cuts the other way here: an empty-ledger crash reads exactly like a no-data guard.

**Forty minutes later it ran clean.** Not because I fixed it — because **BL-1022 fixed it in
the working tree and has not committed**. So:

| where | result |
|---|---|
| **the working tree** | exit **0**, prints the report |
| **`git archive HEAD` extract** | exit **1**, `AttributeError` |

`clippershq/outcome_loop.py` is `M` in porcelain, held by **INFRA-025, BL-1022**. **A fresh
clone at this sha still crashes.** The pack states both, and tells the operator to run it once
before trusting it. `bl1021_verify.py::section_analyse_defect` measures HEAD and the worktree
**separately**, permanently, because the two disagreeing is the normal state of this repo.

This is the same shape as MEMEBOT-107's checkpoint finding, inverted: there a clone was
*greener* than the worktree; here it is *redder*.

## 3. THE MEME-TRACK TRADE, RE-DERIVED

Simulated at HEAD by prepending the pending rule to `vision_rules` and adding an enabled
`goofy` song — the packet's own steps 3 and 4, in that order, because **step 3 without step 4
parks every clip it matches**.

| | stored `_activation_impact` | BL-1002 | **this round** |
|---|---:|---:|---:|
| library size | 2,003 | 2,661 | **2,728** |
| clips **unparked** | 130 | 120 | **123** |
| clips that **change song** | **1** | 16 | **9** |
| clips that lose a song | 0 | 0 | **0** |

Matchable supply **452 → 575, +27.2%** for one track. The four buckets sum to 2,728 —
asserted, because a bucket accounting that does not sum is the failure mode MEMEBOT-109 hit.

**The zero-regression assertion is FALSE and stays false**, and the number it is false by moves
every time the library grows or a phrase rule changes — MEMEBOT-104's narrowing and
MEMEBOT-111's vision guard both landed during this round and both moved it. **A membership
check cannot see a MOVE** (`docs/TESTING.md` rule 12): a clip going `hype → goofy` is in the
"has a mood" set before and after. This measures the mood itself, per clip id.

Still a good trade — 123 unlocked against 9 moved. **Not the trade the packet promises**, and
the pack tells the operator to re-derive it before spending money.
