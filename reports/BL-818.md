# BL-818 — **Half the last 40 rounds carry a documented concurrency cost.** The quiet-tree rule has been used once in 40; the per-file mtime guard eight times. The rule everyone is told to follow is the one nobody uses.

**Date:** 2026-07-31 · **Type:** Meta-audit, READ-ONLY · **Spend:** $0.00 · **Paid calls:** 0
Corpus: BL-777 → BL-817 (40 reports). Nothing changed.

---

## 1. The waste

**20 of 40 rounds (50%)** document at least one concurrency cost — a deferred measurement,
duplicated work, or destroyed work.

| cost | rounds | share |
|---|---:|---:|
| **concurrent writer noticed / worked around** | **15** | **37%** |
| **duplicated or re-derived work** | 13 | 32% |
| **measurement deferred as unreproducible** | **8** | **20%** |
| **work destroyed** | 4 | 10% |
| **union — rounds carrying at least one** | **20** | **50%** |

**The single largest destruction event:** BL-807's `git reset --hard` in the wrong repository —
**49 commits, 135 files, and seven modules' uncommitted in-flight work**
(`clip_media.py`, `crawl_suggested.py`, `discovery.py`, `outcomes.py`, `quality_gate.py`, +2),
recorded as **UNRECOVERABLE**. BL-808 then found two contract failures whose *fixes had existed*
in that destroyed work.

**The moving-target problem, quantified.** Five different master row counts are quoted as current
across these 40 reports:

```
57,386  BL-777, 783, 797
58,000  BL-812
58,065  BL-796, 797, 800
58,324  BL-814, 815, 817
58,325  BL-803, 810, 811, 814, 817
```

**BL-797 quotes two different totals. BL-814 and BL-817 each quote two.** Not sloppiness —
master moved mid-round. Any cross-report comparison of a percentage silently compares different
denominators.

**Honest caveat on the 32%:** the duplication figure is a keyword proxy. Only one chain is
hand-verified end to end — and it is the one that matters.

## 2. Why duplication happens: nobody can see anyone

The outcome marker, traced through the corpus:

| round | what happened |
|---|---|
| **BL-797** | **SHIPPED** the bulk marker — 2,787 keys in 0.18s |
| **BL-807** | `reset --hard` **destroyed it** (uncommitted) |
| **BL-812** | found it half-shipped, wrote a full specification, recommended a rebuild |
| **BL-815** | rebuilt it — and found *"Another agent had started rebuilding this same module and stopped partway. It had written the constants block…"* |
| **BL-816** | found it present on disk but **absent at HEAD**; a third round committed it mid-audit as `7bfd014` |

BL-815 names the mechanism itself:

> *"two agents were independently rebuilding the same module, probably both acting on BL-812's
> recommendation."*

**That is the whole cause.** A published report is a broadcast to every future agent
simultaneously. Two or three read the same recommendation, each correctly concludes the work is
outstanding, and each starts. **There is no way for a round to say "I am doing this now."**
Reports record what *was* done; nothing records what *is being* done.

This is not a locking failure. A lock would not have helped — the agents were not writing the
same file at the same instant, they were spending hours duplicating each other's reasoning.

## 3. Every quiet-gate variant in use, and which to keep

Measured by how many of the 40 reports name each mechanism:

| mechanism | rounds | verdict |
|---|---:|---|
| **backups before writing** | **14 / 40** | **keep — the most-adopted practice in the project** |
| **per-file mtime guard** | **8 / 40** | **KEEP AS THE STANDARD** |
| process check (no funnel running) | 5 / 40 | keep, cheap, orthogonal |
| `filelock` in code | 5 / 40 | keep — this is the real protection for master |
| `git show HEAD` comparison | 2 / 40 | **adopt — see below** |
| disposable copy of master | 2 (both outside this window) | adopt for reads |
| **10-minute zero-write quiet tree** | **1 / 40** | **retire** |

**The quiet-tree rule has failed by disuse, not by being wrong.** One round in forty invoked it,
and that round reported it failing. Earlier rounds recorded three *other* agents simultaneously
running their own quiet-watchers waiting for the same window that never came. A rule that cannot
clear in a busy tree is a rule that gets skipped, and skipping it silently is worse than not
having it.

**Recommend the per-file mtime+size guard as the single standard**, because it is the only
variant with real adoption and it asks the right question: *not "is anything happening?" but
"is anything happening to the files I am about to write?"* Eight rounds converged on it
independently, which is the strongest signal in this audit.

**Add one thing it lacks: a `git show HEAD` check.** BL-816 found BL-797's restored symbols
present on disk and absent from HEAD — one `checkout` from destruction. mtime cannot see that.

## 4. Real clobber risk versus noise

**Genuinely unsafe — every confirmed loss in this corpus is one of these:**

| hazard | evidence |
|---|---|
| **`reset --hard` / any whole-tree git operation** | BL-807: 49 commits, 135 files, 7 modules |
| **Uncommitted work, full stop** | the *only* thing BL-807 could not recover; 231 lines were in this state during BL-816 |
| **Unlocked full-file rewrite of a shared file** | `crawl_suggested.py` reads master, works for minutes, rewrites every row from a stale snapshot — latent only because `ig_crawl_enabled = False` |
| **A lock on the wrong path** | BL-817: `master_leads.csv.lock.lock` — a lock held, protecting nothing |

**Noise — rounds have deferred work for these, and should not:**

| signal | why it is not a risk |
|---|---|
| **"file modified on disk since you last read it"** | BL-813 stopped and checked: the size delta matched its own insertion exactly. It fires on a stale *read*, not a concurrent *write* |
| **Another agent editing a different file** | disjoint files never conflict; `git` merges them trivially |
| **Master growing while you read it** | only matters if you compare across time — and then a snapshot fixes it |
| **A test going red in another module** | BL-813 left `test_funnel` red because `writer.py` changed at 22:40:42, after its own last edit at 22:39:27. Correct: report it, do not adopt it |
| **Working on a file with another round's uncommitted edits** | BL-815 built successfully on another agent's partial constants block |

**The rule that falls out:** contention on *files you will write* is the only thing worth
blocking on. Everything else is reportable context. Rounds have been deferring on category two,
which is pure loss.

## 5. Should reads default to a snapshot? **Yes.**

Five different row counts (§1) is the answer on its own. Two rounds could not measure a block
boundary because master moved; BL-814 built its sample against a 22:34 backup *precisely
because* the live file was moving, and said so.

BL-817 already proposed it and costed it correctly:

> *"**Cheapest fix: a read snapshot.** One line at the top of any measurement… no coordination,
> no lock held… A snapshot also survives the `crawl_suggested.py` hazard, because it is immune
> to *how* the writer writes."*

**It should be the default, not an option.** A measurement against a moving file is not a
measurement. The snapshot costs one `shutil.copy2` (~24 MB, well under a second), holds no lock,
blocks nobody, and makes every number in a report reproducible by construction — the snapshot
can be kept next to the report. This also fixes what BL-816 could not: a stated row count that
another agent can verify later.

**It does not help writes at all**, and should not be confused with a solution to §2.

## 6. The cheapest coordination mechanism

**A claim file. One per round, plain text, advisory, no locking semantics.**

```
.claims/BL-818.json          written at start, deleted at end
{
  "round": "BL-818",
  "started": "2026-07-31T23:10:00Z",
  "intent": "meta-audit of the concurrency model",
  "will_write": [],                        # [] = read-only round
  "reading_snapshot": "scratch/_snap/master_leads.csv"
}
```

The whole protocol is two lines at the start of a round — `ls .claims/` and write your own —
and one at the end. It answers the only question §2 showed is unanswerable: **who is doing what
right now.**

**Why a claim file rather than a lock directory or a manifest:**

- **A lock would not have prevented a single failure in this corpus.** The duplications were
  hours apart in reasoning, not milliseconds apart in writing. Locks solve write races; `filelock`
  already does that for master and works.
- **A manifest of in-flight work needs maintaining**, and BL-775 measured what happens to
  hand-maintained lists here: they drift, then mislead.
- **A claim file is self-cleaning by convention and harmless when stale** — a leftover claim
  costs one glance. Compare with a stale *lock*, which blocks real work.

**Design constraints, from what this audit actually measured:**

1. **Advisory, never blocking.** The quiet-tree rule proves a blocking gate gets skipped. A
   round that sees a conflicting claim should be free to proceed and say so.
2. **`will_write` is the field that matters** (§4) — file paths, not prose. An empty list means
   read-only and needs no attention at all.
3. **One file per round, named for the round.** No shared file to contend on — which would be
   the same bug in miniature.
4. **Pair it with the BL-816 claims manifest.** That verifies what a round *finished*; this
   declares what a round *started*. Together they close both ends.

**What it will not fix:** a round that does not write one. It is a convention, not a mechanism,
and its adoption will look like the mtime guard's (8/40 and rising) rather than the quiet-tree
rule's (1/40). That is still a large improvement over zero.

## Limits

- **The 32% duplication figure is a keyword proxy.** Only the outcome-marker chain is
  hand-verified. The true figure could be materially lower; the 50% union inherits that
  uncertainty. The deferral count (8) and destruction count (4) are hand-checked.
- **"Rounds carrying a cost" is not "wasted rounds."** Most of the 20 shipped their main
  deliverable and lost an edge — BL-814 shipped and deferred one question. I did not attempt to
  price the loss in hours.
- **Report text is the only evidence.** A round that duplicated work silently, or deferred
  without saying so, is invisible here. All three counts are floors.
- **Adoption counts measure what reports *mention*.** A round that used a mtime guard without
  writing it down is uncounted, so 8/40 understates the practice.
- **This audit was itself run against a moving tree** and quotes no master row count of its own,
  deliberately.
- **The single incident (BL-807) dominates the destruction column.** One event is not a rate.

## Method

Cloned the reports repo (316 files), took BL-777 → BL-817. Signals were extracted by regex over
report text, then **every count that carries weight was hand-verified** by reading the matching
passage: the outcome-marker chain across BL-797/807/812/815/816, BL-807's damage table, the
deferral sentence in each of the 8 rounds, and each named safety mechanism. Master row counts
were extracted by pattern and grouped to expose the moving denominator. Adoption counts are
per-report mentions, not per-use. No repository file was read for state, nothing was written,
no API call was made.
