# BL-1035 — the backup runs on a schedule, and the history decision is written for the operator

**Both remaining items closed as far as they can be without the operator.** The backup is
scheduled and **verified through the real Task Scheduler in both directions**. The PII history
decision is a one-page document with exact commands and honest limits — **and nothing in it
was executed.**

**The one number: a scheduled run with no drive attached exits 2, writes `RESULT: ATTACH THE
DRIVE`, and leaves a marker that makes `-Status` exit 1.** That is the failure this whole
piece exists to make impossible to miss.

**And the wrapper's first draft reproduced the exact bug it was written to prevent.** §1.

---

## 1. The schedule

```
powershell -File tools/backup_schedule.ps1 -Install -Dest E:\clippershq-backups -At 20:00
powershell -File tools/backup_schedule.ps1 -Status
powershell -File tools/backup_schedule.ps1 -RunNow -Dest E:\clippershq-backups
powershell -File tools/backup_schedule.ps1 -Remove
```

### Verified through Task Scheduler, not by calling the script

| run | task `LastTaskResult` | what happened |
|---|---:|---|
| **destination attached** | **0** | archive written (3rd on the device), log ends `RESULT: PASS`, failure marker **cleared** |
| **destination absent** | **2** | nothing written, log ends `RESULT: ATTACH THE DRIVE`, marker **created** |

`-Status` then exits **1** and prints the marker, so *"did the last backup work"* is one
command with a non-zero exit — not a log to read.

The attached-destination run used a `subst` drive to stand in for a device, because **there is
exactly one volume on this machine**. That proves the **wiring**, not redundancy: a `subst`
drive is the same physical disk. The real device is still the operator's to plug in.

### Why the missing-device case gets its own exit code

`backup.py` used to die on an absent destination with
`FileNotFoundError: [WinError 3] ... 'E:/'` — exit 1, correct, and in a scheduler log
indistinguishable from noise. It now raises `DestinationMissing` and prints one line:

```
DESTINATION NOT ATTACHED: E: does not exist, so 'E:/clippershq-backups' cannot be written.
Plug the backup device in, or pass a --dest on a device that is mounted.
NOTHING WAS BACKED UP -- this run did not silently succeed.
```

**Exit 2, not 1**, so the wrapper can say *attach the drive* rather than *the backup is
broken*. Different problems, different responses. All four exit paths read **directly**, never
through a pipe:

| case | exit |
|---|---:|
| drive not attached | **2** |
| same volume, no `--force-same-device` | **1** |
| backup written | **0** |
| verify a good archive | **0** |

**No silent retry.** If the drive is missing the run fails and says so. Retrying on a schedule
is what turns "unplugged for three weeks" into a log nobody reads.

### The wrapper's first draft was the bug it exists to prevent

Under PowerShell 5.1 with `$ErrorActionPreference = "Stop"`, **any stderr line from a native
executable becomes a terminating error**. `backup.py` writes its refusal to stderr, so the
first draft died right there:

> exit **1** instead of 2, **no RESULT line**, and **no failure marker**

— a scheduled run that failed and left nothing saying so. Exactly the silent failure the file
was written to eliminate, introduced by the file. The native call is now inside `try/finally`
with the preference relaxed, and the failure path is re-verified end to end.

**Also measured:** the first scheduled trigger **hung for over two minutes**, task stuck
`Running` (`LastTaskResult 267009` = `SCHED_S_TASK_RUNNING`), no log. The second completed in
25 s. Load, not a hang in the backup — 12 rounds were in flight. Recorded in `docs/BACKUP.md`
so the next person does not debug the backup for it.

**4 new tests** (19 total in `tests/test_backup.py`): the absent device raises
`DestinationMissing`, it is a `SystemExit` subclass so an unhandled one still exits non-zero,
it is a **distinct type from the same-device refusal**, and a missing *leaf* under a *present*
device is fine — only the device must exist, or every first run would be refused.

**Still not solved, and it cannot be from here:** the task is installed pointing at `E:`,
which **is not attached**. Every scheduled run will exit 2 and say so until a device is
plugged in. That is correct behaviour and it is not a backup.

## 2. The history decision — written, costed, not executed

`docs/PII_HISTORY_DECISION.md`. **Nothing in it was run.**

It states the situation (3 blobs, 3 paths, **19 people**, tree clean, exposed 2026-07-31 →
2026-08-02), then the fact that inverts the usual intuition:

> **All 102 raw-URL citations point at `/main/`, not at a commit SHA.**
> A rewrite changes SHAs and does not move `main` — **it breaks none of them.**
> **Making the repo private breaks all 102 immediately.**

And the limit that applies to every option: **a rewrite cannot un-disclose.** Anyone who
cloned still has the data, GitHub serves unreachable objects by SHA for a period afterwards,
and forks, caches and archives may keep them indefinitely.

Each option carries its exact commands — `git filter-repo` with the `--invert-paths` caveat
and the follow-up `git gc` that is a **support request, not a command**; `gh repo edit
--visibility private`; and for "leave it", the honest test of whether you would be comfortable
explaining it to one of the 19.

## 3. Re-verified at publication, under both profiles

Fixture built from **one real row of `master_leads.csv`**, never printed, deleted in a
`finally`. A synthetic address would prove only that the regex fires; the live-lead **join**
needs something real to match.

| | join ran | matched | exit |
|---|---|---:|---:|
| `--profile public` | yes | 1 | **1** |
| `--profile private` | yes | 1 | **1** |

**Discrimination check, because a scanner that fails everything is broken, not strict:** a
report with no address **passes under both** (exit 0).

**Public tree at publication: 0 files with a live address across 678 artefacts.**

> **The ceiling, stated wherever that zero is quoted:** the join knows only the **4,729**
> addresses in `master_leads.csv` plus the export **today**. An address that was in a lead
> file and has since been removed — a bounce purge, an unsubscribe, a re-export — is not in
> the index and **will not be caught. Zero never means "no PII".**

Every exit code above was read from `subprocess.run(...).returncode`. **There is no pipe
anywhere in `scratch/bl1035_verify.py`.**

## 4. The stale docstring, fixed

`scratch/scan_report_for_secrets.py` said `--profile private` means *"every CREDENTIAL check,
no LEAD-DATA check"*. Untrue since BL-1017; BL-1019 named it and left it.

Rewritten to the measured behaviour: **both profiles run the live-lead join and both block on
it**. What `private` drops is the undifferentiated **count of email-shaped strings** — the rule
that produced BL-974's `FAIL: 81 email addresses` on legitimate lead rows. That rule now
reports under `private` and does not fail the run.

The distinction is the point, and the docstring now says it: an address-*shaped* string in the
private repo is its reason for existing; a string that **joins a real lead** in something being
published is a disclosure wherever it is going, because the private repo is one visibility flip
from public.

`tests/test_secret_scanner.py` green (direct exit 0).

## 5. Exit codes read directly, every time

The brief called this out because BL-1019 did it three times. This round: **every** exit code
in every check above came from a direct read — `subprocess.run(...).returncode` in Python,
`$LASTEXITCODE` captured before any pipe in PowerShell, `$?` on an unpiped command in bash.

It caught a real one. `powershell ... -RunNow | tail` reported **0**; the direct read gave
**2**. Had I trusted the pipe I would have reported the failure path as passing — which is the
mechanism `publish_report.py`'s own docstring records for how a failed scanner once let a
publish through.

930.6 GB.** This is the disk that holds `master_leads.csv`, `clip_library/`, the ledger, the

Freeing 1.1 GB of my own artefacts (three staged 26 MB archives, restore dirs, the full

copies, not backups, and the round was finished with them.**

Worth stating plainly because it compounds everything above: a nearly-full volume is how a
write fails halfway and leaves a truncated `master_leads.csv`, and the only copies are on the
same volume. It is one more argument for the device that is not attached — and one the
scheduled task cannot make for itself, because on a full disk **the backup writes nothing and
exits non-zero**, which at least is now loud.
