**Date:** 2026-07-31 · **Type:** Investigation + live run, READ-ONLY · **Spend:** $0.00
**Quota: 101 of 10,000 free daily units.** No paid calls, no writes to master, spend or config.

## 3. Where everything dies

| gate | dropped | % | example |
|---|---:|---:|---|
| **size (subs AND views both below floor)** | **43** | **86%** | `Impact Online Fitness Coaching` 855 subs / 785,569 views; `ReleStrong` 1,120 / 65,070 |
| non_target_country | 1 | 2% | `Om Bisht Fitness Coach` — IN, 45,400 subs |
| non_target_language | **0** | 0% | never fired |
| too_many_subscribers | 0 | 0% | — |
| **PASSED** | **6** | **12%** | — |

**86% die on size, and they deserve to.** These are not near-misses: the median dropped channel is in the low thousands of subscribers with under a million lifetime views. `search.list` on a commercial query returns a long tail of tiny channels, and the floor is doing exactly its job.

**The country gate is nearly idle here** — one drop, versus five on BL-748's podcaster query. That is the niche change working: `fitness` does not surface the Balkan/South-Asian channels `podcaster` did. **The language gate fired zero times in both runs** and remains a gate with no measured effect.

**Country is unknown on 25 of 50 channels (50%)** — below BL-748's measured 76% fill. All 25 are **kept and flagged**, never cut, which is correct and matches Spotify. But it means half this population is passing a geo gate that cannot see them, and **3 of the 6 survivors have no country at all**.

**Description-email rate, re-measured:** 6 of 50 raw (12.0%), matching BL-755/BL-762's 12.5% almost exactly. On the six survivors, 2 carried a usable address and both passed the boilerplate guard. This is now the third independent confirmation of that figure.

## 4. The six fixes — all live, all firing

| # | fix | status | evidence |
|---|---|---|---|
| 1 | **view floor at 2M** | **LIVE, load-bearing** | `DEFAULT_MIN_VIEWS = 2_000_000`, config `min_views: 2000000`; gate at :317 is `subs >= min OR views >= min`. **4 of 6 survivors are rescues.** |
| 2 | **description email after the country gate** | **LIVE** | parsed post-gate; 6 raw hits → 2 on survivors. `_guarded_pick` kept both. |
| 3 | **`hiddenSubscriberCount` honoured** | **LIVE, untested here** | read at :331, distinct reason `low_views_hidden_subs` at :336. **0 of 50 channels had it set**, so it did not fire. Wired, unexercised. |
| 4 | **fitness / gaming presets** | **LIVE — and it is the default** | `NICHE_QUERIES` now leads with `fitness` and `gaming`; `podcaster` is retained but comment-marked DEMOTED. Live config `niche: "fitness"`. |
| 5 | **config keys surfaced** | **LIVE** | `youtube_finder` block now carries `min_subscribers`, `max_subscribers`, `min_views`, `per_query`, `run_target`, `cap`, `enrich_website`, `resolve_handles`, `max_run_usd` |
| 6 | **`customUrl` / `publishedAt` persisted** | **LIVE** | written at :283-286; `published_at` feeds `quality_note` as "channel created …; N lifetime views", deliberately **not** `last_post_date` |

**Six for six.** This is the best-implemented funnel in the repo by this measure, and it has never produced a lead.

One note on fix 6: the comment explains `publishedAt` is deliberately kept out of `last_post_date` because that column means "last activity". Correct reasoning — and it is also the reason nothing YouTube writes can ever be `ALIVE`. See below.

## 5. Can a YouTube lead export? **No. Zero. Same wall.**

I built the exact master rows `append_found_to_master` would write for the six survivors — giving each one a valid email, the most favourable case possible — and ran the real exporter:

```
simulated YouTube master rows : 6
  verdict on each             : '' '' ''      <- never set
  last_post_date on each      : '' '' ''      <- never set
  -> ALL_BOT_READY rows produced : 0
  -> activity classification     : {'UNKNOWN'}   (send_list requires ALIVE)
```

`append_found_to_master` starts from `rec = {c: "" for c in fieldnames}` and **never assigns `verdict`**. So:

- **`bot_ready_rows` / `dm_list_rows`** require `verdict in {EDITOR, LIKELY}` → **blocked**.
- **`send_list.build`** requires `activity == ALIVE`, which needs `last_post_date`, which YouTube deliberately does not write → **blocked**.

**Blocked twice, by two different gates, on two different paths — bit-for-bit the Spotify/Google Play/Twitch/Kick failure from BL-765 §2.**

**Six perfect leads. Two with free emails. Zero exportable.** Had the funnel been run every day since it was built, master would hold thousands of YouTube rows and the send list would still be 1,620.

## 6. Is it worth keeping? **Yes — and retiring it would fix nothing.**

The tempting read is "it finds fitness coaches, and this business recruits editors." **That read is wrong, and `docs/STATE.md:4` says so:**

> *"a lead-generation pipeline that finds (a) **editors/clippers** to hire (Instagram + TikTok discovery) and (b) **creators with money** who would pay for clipping (Twitch, Spotify, YouTube, Google Play)"*

YouTube is a **client-finder by design**. Fitness coaches with 12M views are exactly the intended target — people who would pay for clipping. The module docstring says the same in its first line. The persona is not the problem.

**The problem is that the export path was built for clipper rows and no client funnel can pass it.** YouTube, Spotify, Google Play, Twitch and Kick — **953 rows and 888 deliverable addresses** between them (BL-771 §4) — all fail the same `verdict` gate. Retiring YouTube removes one of five funnels from the wrong side of a wall that would still be standing.

**The honest economics, if the wall came down:**

| | |
|---|---:|
| quota per query of 50 channels | 101 units |
| queries per free day | 99 |
| channels seen per day | 4,950 |
| qualified at the measured 12% | **~594/day** |
| with a free description email at 4% of channels | **~198 free emails/day** |
| marginal cost | **$0** |

~198 free, deliverable client addresses per day at zero cost is not a funnel to retire. It is the cheapest client acquisition surface in the repo — Twitch and Spotify both need paid resolves for most of their contacts.

**Recommendation: keep it, do not run it yet.** Running it today appends unexportable rows to master and burns quota to no end. The sequence that makes sense is: decide what a client-funnel row's `verdict` should be (or teach the exporters to accept an empty one for funnels that do not produce verdicts) — then run all four client funnels, not just this one.

**If the wall is not going to be addressed, then retire all four**, not YouTube alone. Keeping four funnels that cannot deliver, and maintaining them round after round, is the actual cost being paid here — and this funnel has now absorbed four rounds of attention while never having been executed once.

## Limits

- **One query, one niche, 50 channels.** The 12% pass rate, 50% country fill and 12% description rate are from that sample. BL-755's n=200 across four niches is the better-evidenced source for the rate; this run reproduces it, it does not supersede it.
- **`hiddenSubscriberCount` was not exercised** — 0 of 50 channels had it set. Fix 3 is confirmed wired, not confirmed working.
- **The `/about` figures are n=6.** The 1-in-6 IG rate is too small to overturn the docstring's 42% from n=444; it is flagged, not concluded.
- **No paid step ran.** `ig_fn`/`tt_fn` were passed as `None`, so the paid handle-resolve — the funnel's main email path for the no-listed-email tail — is untested here. Its yield is unmeasured on this niche.
- **The export test used simulated rows**, built to match `append_found_to_master`'s output exactly. No YouTube row has ever existed in master to test against, which is the point.
- **Logs cover 2026-07-24 → 07-30.** "Never run" is proven for that window and for all of `spend.json` and `master_leads.csv`; a run before 07-24 that wrote nothing anywhere cannot be excluded, though it would have had to leave no trace in master or spend.

**One correction from my own work:** my first `/about` probe read `parse_about()` for keys named `emails` and `links`, which it does not return, and reported 0 links on all six channels. The parser is fine — the keys are `ig`/`tt`/`website`/`listed_email`. Section 2's table is from the corrected run.

## Method

Scanned all four `logs/run.log*` files (182,258 lines) for ten finder-specific signatures, `spend.json` for any YouTube ledger entry, and all 57,386 master rows for YouTube provenance. Ran one live `search.list` (100 units) and one `channels.list` (1 unit) — **101 of 10,000 free daily units, $0** — through the funnel's own `make_search_fn`, then applied the shipping gate logic (`youtube_finder` thresholds from live config, `market_filter.classify_market`) to the payload. Six free keyless `/about` fetches via the module's own `make_about_fn`, parsed with its own `parse_about`. The export test built rows matching `append_found_to_master` and ran the real `all_bot_ready.build` against a temp file. The API key was read from config into the client only and never printed. Nothing was written outside the session scratchpad.
