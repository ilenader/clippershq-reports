## 1. Item 5 — nine rows were estimates by prose alone

`reconcile()` calls a row estimated if `estimated is True` **or** if a substring search over its label says so. Nine rows relied entirely on the second.

| | rows |
|---|---:|
| explicitly flagged, before | 2 |
| **relying only on the label substring** | **9** |
| **now explicitly flagged** | **11** |

```
total_spent_usd  $8.4973 -> $8.4973   unchanged
estimated_usd    $3.1567 -> $3.1567   unchanged — same rows, said out loud
```

**Those two invariants are the point, not a side effect.** The sweep removes a *dependence*; it must not reclassify anything.

> **Getting the gate right is the whole correctness argument, and my first version got it wrong.** It matched my own word list over label **and campaign**, which would have flagged three `BL897_BACKFILL` rows whose labels are `probe`, `probe2` and `speech_backfill_paging`. `_label_is_estimated` reads the **label only**, so two of those are currently **MEASURED** — real metered probe calls sitting in a campaign that merely has "BACKFILL" in its name. Flagging them would have moved counted money into the estimated column, which is exactly what `spend_ledger` warns against: *calling measured spend "estimated" discredits a number that was actually counted.* The gate is now the fallback itself, so classification cannot move.

Three categories, and only the first is written:

- **FLAG (9)** — the fallback already catches them; making it explicit changes nothing.
- **MISLABELLED (1), left alone** — a row labelled `CORRECTION_killed4` (…`was_not_killed`) trips the fallback on the word "killed". This is BL-877's exact trap. Auto-flagging it would turn a correction into a guess.
- **POSSIBLY UNDER-CLASSIFIED (2), reported not touched** — the `probe`/`probe2` rows above. Flagging them would *move money between columns*, which is a judgement about what the row means, not a fix to how it is stored. **They are BL-897's rows and their owner should say.**

`tests/test_estimated_flag.py` (6 tests) pins it, including a **live canary** over the real `spend.json` that names any new offender and the one command that fixes it.

## 3. Item 2 — blocked all round, and here is the exact patch

`main.row_usd` fixed every reader. The two writers still build their totals from components:

```python
_record_spend_locked      run_cost = round(tt_cost + ig_cost + tikhub_cost, 6)              # 3
_record_aux_spend_locked  run_cost = round(tt_cost + ig_cost + tikhub_cost
                                           + link_cost + vision_cost, 6)                    # 5
```

Each also hand-writes its five `d["X_spent_usd"] = ... + X_cost` accumulator lines, and **writer 1's row omits `link_usd` and `vision_usd` entirely** — latent today because main runs have neither and `row_usd` reads missing keys as zero.

The fix is one helper both writers call, iterating the single list:

```python
VENDOR_TOTAL_KEY = {"tiktok_usd": "tiktok_spent_usd", "ig_usd": "ig_spent_usd",
                    "tikhub_usd": "tikhub_spent_usd", "link_usd": "link_spent_usd",
                    "vision_usd": "vision_spent_usd"}

def apply_vendor_costs(d, costs):
    """Accumulate per-vendor totals AND the grand total from ONE list. Returns run_cost."""
    run_cost = 0.0
    for k in VENDOR_USD_KEYS:
        c = round(float(costs.get(k) or 0.0), 6)
        tk = VENDOR_TOTAL_KEY[k]
        d[tk] = round(float(d.get(tk, 0.0)) + c, 6)
        run_cost += c
    run_cost = round(run_cost, 6)
    d["total_spent_usd"] = round(float(d["total_spent_usd"]) + run_cost, 6)
    return run_cost
```

Both writers then emit all five `*_usd` keys, and the guard test extends `test_vendor_sources.py`'s existing rule from readers to writers: **no hand-written sum of three or more `_cost` terms**.

**I did not apply it.** `main.py` carries another round's 51 uncommitted lines and BL-900 holds it. That is the hazard this project keeps paying for, and your own gate exists because of it.
