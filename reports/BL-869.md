## 2. BRINGING main CURRENT — and the one thing I would not do

**I did not check out `main`.** That is the obvious way to fast-forward a branch and it would
have been the wrong move here: the working tree carries **267 modified/untracked entries**
belonging to eight concurrently-running rounds. `git checkout main` rewrites the working tree.
Doing that to fix a *ref* problem would have caused a far worse version of the incident this
round exists to prevent.

Instead the ref was moved without touching the working tree:

```
$ git -C . push origin <checkpoint>:main
   4cc7790..a6fdb48  <checkpoint> -> main
```

The `..` is the proof it was a fast-forward — a forced update prints `+` and `...`. No
`--force` was passed, so git itself would have rejected anything else. Then
`git branch -f main origin/main` synced the local ref, which is safe precisely because `main`
was not checked out.

### It drifted again mid-round, which is the real finding

Between the fast-forward and the verification sweep, another round committed `51ffd1b`
("Language before payment, no duplicate first writes, no unmetered path"). `main` was stale
again within minutes. Re-checked ancestry, fast-forwarded a second time, and pushed the
checkpoint branch too so both remote refs agree.

**Final state — all four refs identical:**

| Ref | |
|---|---|
| `HEAD` | `51ffd1b` |
| `main` | `51ffd1b` |
| `origin/main` | `51ffd1b` |
| `origin/<checkpoint>` | `51ffd1b` |

Divergence `main` ↔ checkpoint: **0 / 0**. No merge commit — every ref points at the same
commit.

**This will drift again.** Ten rounds were in flight during BL-865; eight during this one.
BL-809 fixed this once, it drifted, and it drifted once more inside this round's own runtime.
A periodic fast-forward is a chore, not a fix; the durable fix is for rounds to push to `main`
or for CI to fast-forward it. That is a policy decision, not a git operation, so it is flagged
rather than taken.

## 4. THE GUARD RE-TESTED

The command that caused the 2026-07-31 incident, run against the current remote.

**Run only in a disposable clone.** Running `reset --hard` in the live repository would have
destroyed 267 uncommitted working-tree entries belonging to eight live rounds — reproducing
the incident while testing for it.

```
$ git reset --hard origin/main          # in the throwaway clone
HEAD is now at 51ffd1b

HEAD before/after  : 51ffd1b / 51ffd1b
files before/after : 1999 / 1999
NO-OP              : YES
```

And proven non-destructively for the **live** repository, without running it:

```
HEAD                                    51ffd1b
origin/main                             51ffd1b
identical                               YES
commits that would be lost              0
tracked files that would change         0   (git diff HEAD origin/main is empty)
```

### What this does NOT fix, stated plainly

`reset --hard` would **still destroy 267 uncommitted working-tree entries**, 7 of them
tracked-and-modified and recoverable only from OneDrive version history. That is inherent to
the command and is exactly what cost seven modules on 2026-07-31: committed work came back
from the reflog, never-staged edits did not.

What this round removed is the **amplifier** — the 26-commit gap that turned a survivable
mistake into a catastrophic one. The command is not safe. It is no longer *catastrophic*.
`PUBLISHING.md`'s rule stands unchanged: it has no business in a publish path.
