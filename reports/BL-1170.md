# BL-1170 — the send list is current again, and it cannot be sent

**544 people who could be emailed today were not in the send file. They are now.** The file
went from 2,970 rows built four days ago to **3,513 rows** built from current master, and the
other 105 of the 649 missing addresses are each suppressed for a named reason rather than
lost.

Two things found by looking rather than by testing, and the second is the one that matters:

**The file is correct and it is UNSENDABLE.** `send_identity.json` does not exist, so all
3,513 messages render with `[[SENDER_NAME]]`, `[[RATE]]`, `[[PRICE]]` and `[[REPLY_TO]]`
unfilled. `render()` refuses to produce those by default — the BL-1091 guard working exactly
as designed — so nothing can go out until the operator copies
`send_identity.example.json` to `send_identity.json` and fills in five fields. **That is a
two-minute job and it is the only thing between this file and a send.**

**One in seven messages opens by greeting a username.** 501 of 3,513 (14.3%): 377 begin
`Hi @…,` and 123 contain a dot or underscore. That is the "Hey Cykl0psFilm()" family, alive
in today's file.

## 4. The metadata the page needs

```json
{ "row_count": 3513, "generated_at": "2026-08-06T22:06:44",
  "master_mtime": "2026-08-06 20:06:19", "master_rows": 60241,
  "stale_at_build": false, "stale_rule": "stale = os.stat(master).st_mtime > generated_at; …" }
```

`master_rows` reads **60,241**. The file it replaced said **133,474** for the same master —
the line-count bug, visible in a shipped artefact rather than in a code comment.

**There is deliberately no `stale` field, and that is a design decision worth stating.** At the
instant of writing, a file derived from master is never stale — so a stored `stale` would be
`false` here and would *stay* false while master moved underneath it. That is the same shape
as the literal string `"derived-from-master"` this timestamp replaced: a value that reads like
an answer and cannot change when the answer does. What is stored is `stale_at_build` plus both
operands, and `stale_rule` names the comparison in the file itself so the next reader does not
have to invent one.

**Handing over the rendering.** Staleness is computed live and correctly today —
`staleness_of()` returns `{rows: 3513, stale: false, age_days: 0}`, and `dashboard/server.py`
already calls it. The page renders none of it. `dashboard/static/app.js` and `server.py` are
held by **BL-1159**, so the facts are written correctly here and the rendering is theirs.

## 7. The honest expectation

**Bounce: 0.81%, 95% interval [0.37, 1.76] — measured on the informative subset only.**

**Naive SMTP acceptance of 97.2% is meaningless and must not be quoted as a deliverability
figure.** Catch-all domains accept every address offered, so an acceptance is not evidence the
mailbox exists. Measured (BL-962, no mail sent): **243 of 551 domains are catch-all (44.1%)**,
covering **283 of 2,970 rows (9.5%)**.

**Applied to the rebuilt file, stated with its coverage rather than assumed to carry over:**

| | |
|---|---:|
| rows whose domain BL-962 actually measured | 3,322 of 3,513 — **94.6%** |
| rows on a known catch-all domain | 290 — **8.3%** |
| domains not covered by that measurement | 189 — **191 rows, 5.4%** |

So the interval above still applies to the great majority of this file, and 5.4% of it is
genuinely unmeasured — a smaller caveat than the rebuild's size might suggest, and it is a
