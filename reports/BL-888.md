## 1. The render blocker is now on the page

**The gap.** `no_mood` answers *"could a song ever be chosen for this clip"* — a question
about the **rules**. Nothing answered *"can this system make a video right now"* — a question
about the **store**. On 2026-08-01 those had opposite answers: 10.5% of clips matched a mood
and **0.0% could render**, because all four songs were `enabled: false` with every hook
window an unmarked placeholder. The card showed clips, accounts, vision coverage and the
no-mood share — every figure healthy, none of them saying the pipeline was dead.

`/api/library` now carries `songs_enabled`, `hooks_total`, `hooks_marked`, `renderable`,
`renderable_pct` and `render_blocked`. The Now tab leads with it, above the no-mood sentence,
because it outranks it.

**Rendered in a real browser** (Playwright — Claude-in-Chrome cannot reach localhost here):

> **Blocked:** 0 of 2,003 clips can be rendered right now. 0 of 4 songs enabled, 7 of 11 hook
> windows marked. Until a song is enabled with a window marked by ear, every clip parks and
> no video can be made.

Both halves of the remedy are named because both are the operator's own work and neither is
discoverable from the card otherwise. When it unblocks, the same line reports the count
instead of the blockage.

**`count=False` is load-bearing, and this was nearly a real bug.** `render_plan()` defaults to
`count=True`, which **increments the rotation counters** on the song and hook it picks. The
page polls every 5 s and recomputes up to once a minute, so the default would have advanced
the least-used rotation ~1,440 times a day against clips nobody rendered — corrupting the
exact fairness the counter exists to provide. There is now a test that hashes
`scratch/songs.json` and compares every `uses` counter across a `_compute_library()` call.

**Accessibility.** A hook demanded I delegate to an accessibility team; the brief said RUN
ALONE, so I applied the existing card's own discipline inline rather than spawning agents.
Severity travels on four channels — the leading word **"Blocked:"**, first position in the
card, prose rather than a token, and a wider left rule — never colour alone. It is **not** a
live region and not `<output>`, matching the reasoning already written into `index.html`: four
figures on a 5 s poll would be ~2,880 screen-reader announcements a day. `forced-colors`
already covers `.figflag`, which `.figblock` extends.

## 4. The export emits one row per clip

`load_library()` appended every line of an append-only, revisioned store: **3,814 rows for
2,003 clips, 1,811 rows (47%) superseded, some clips five times**, while the menu entry and
the file header both promise *"one row per clip"*.

The rows were not duplicates but **contradictions** — an early rev with no vision label and a
later one with it, and nothing saying which was current, because `rev` was not even an
exported column. The consumer could not have fixed this.

Collapsed with `clip_library.read_all()`'s exact rule, including the `>=` tie-break —
**deliberately identical rather than merely similar**, because two collapse rules that
disagree is the same bug in slower motion.

```
load_library   3,814 -> 2,003 records      duplicates: 0
               agrees with read_all on every surviving revision: 2,003/2,003
               and it got faster: 3.01s -> 1.09s
```

Decisions worth naming: **first-appearance order is preserved**, so the export stays diff-able
run to run even when a newer revision lands in a later shard. A record with **no `clip_id`**
is kept, not dropped — there is no identity to collapse on, and losing rows is not the safer
failure. A missing `rev` reads as 1, matching what the writer stamps.

Side effect: `fill_report()` was being diluted by low-fill superseded revisions and understated
column coverage by 1–2 points (`franchise` 33% → 35%, the `layout_*` family 89% → 90%).

**Seven regression tests, proven to fail against the old code.** I rebuilt the previous
implementation and ran the fixture through both: old gives 5 rows and keeps `rev` 3 (last line
wins), new gives 2 rows and keeps `rev` 4. The fixture deliberately writes rev 4 *before*
rev 3 so file order cannot be mistaken for the rule.
