## 1. THE PANEL THAT LIES ABOUT EVERY BATCH — fixed, and it was worse than reported

`dashboard/paste_routes.py` reported **0 links and 0 done for every batch ever run**. He read a
finished batch as a failed one and stopped. That batch — `outputs_paste_20260812_170819` —
holds **22 links, 17 done**.

The brief named one bad line. **An AST audit of every key the panel pulls out of a batch state,
checked against all 14 real `_batch.json` files on disk, found three**, all inside the same
seven lines:

| read | at | writer actually writes | present in |
|---|---|---|---|
| `state['links']` | `paste_routes.py:139` | `items` | **0 of 14** |
| `item['status']` | `paste_routes.py:140` | per-item key is `state` | **0 of 14** |
| `state['running']` | `paste_routes.py:145` | no such key — `finished_at` | **0 of 14** |

The second one matters as much as the first: fixing `links` alone would have made the panel
report *22 links and still 0 done*, because the filter compares the wrong key. The third meant
a live batch could never show as running.

**The fix** reads the writer's own maintained `counts` block (`paste_batch.py:1352-1357`) and
falls back to counting `items` when a torn state carries items without a refreshed summary;
per-batch liveness is derived from `finished_at` plus whether any item is still non-terminal.
Deliberately **not** `_running_pid()` — that is the one last-launched pid for the whole
dashboard, so it would mark every old batch running whenever any batch was.

**After the fix, from the live endpoint:**

```
outputs_paste_20260813_180421   links=16  done=11
outputs_paste_20260812_211716   links=22  done=0
outputs_paste_20260812_170819   links=22  done=17   <- the batch he thought had failed
```

### The audit is the deliverable, not the one-line fix

This is the same shape as three prior defects: a field name that stopped matching its writer,
failing silently at exit 0. A one-line fix leaves the next rename to be found the same expensive
way. So `scratch/bl1249_audit.py` (selftest **11/11**) parses the reader with `ast`, extracts
every key it takes off a batch state, and checks each against the real files. It reports
**MISMATCHES: 0** now, and `tests/test_bl1249_panel_fields.py` (**17 tests**) fails the suite if
that ever stops being true.

Text matching would not do this: `grep '"links"'` hits comments, docstrings and unrelated dicts.
The AST knows it is a subscript on the state. Both negative controls are asserted — a key on an
unrelated dict is not reported, and a docstring mention is not a read — and one test re-runs the
extractor over the **pre-fix source** to prove the guard can still fail.

**Every other field the panel reads checks out**: `batch`, `billed_calls`, `cap_usd`, `counts`,
`dry_run`, `estimate_usd`, `finished_at`, `folder`, `items`, `problems`, `reason_legend`,
`spent_usd`, `started_at` — 14 of 14 — and `zip`/`zip_bytes` at 1 of 14, which is correct
because only a zipped batch has them.

## 2. THE FRESHNESS BANNER WAS ON A HIDDEN TAB

The brief says keep it. It was there and he could not see it.

`#serverAge` was declared at `index.html:186`, **inside `<section id="p-over" hidden>`** — the
"All numbers" tab. So the one banner whose job is to say *"this page is showing old logic,
restart the server"* only rendered on a tab he had to go and open. A running Python never
re-imports a module, and that alone hid four rounds of fixes from him; a warning about that
cannot itself be behind a click.

**Moved to line 118, directly below `#offlineBanner` and `#blockingBanner`** — the two banners
that are always visible. No JavaScript changed: `renderServerFreshness()` resolves it by id.
There is still exactly **one** `#serverAge` in the whole `static/` tree, and the old location
carries a comment saying why a second copy would leave one of them permanently blank.

**Verified in the browser: `serverAge_visible: true` at both 1440px and 700px.**

### And two things the brief asked for that were already right

**Batch sorting is already by `started_at`, never by folder name.** `_batch_folders()` sorts on
`PB.batch_started_at(f)` with the basename only as a deterministic tie-break, and the endpoint
publishes its own `sort_key` so a reader can verify the order. The response even carries the
reason in prose, citing BL-1212. I added two tests pinning it rather than changing it.

**Run identity is already pid AND creation time AND boot epoch**, via `OpenProcess` and never
`tasklist` — `clippershq/proc_identity.py:169-220`, with a 120 s boot-slack and a 2 s
creation-time match. That is what stops a recycled pid being displayed as a live funnel.
