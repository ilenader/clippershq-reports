## 1. The four real gaps, and the third one is the worst

### (a) `post_url` — the record had every measurement and no address

`OUTCOME_FIELDS` carried `posted_to` (platform) and `posted_at` (date) and nothing identifying the post. Without it three things are impossible: **re-reading** (views move for weeks; a row with 12,400 and no way back gets one sample, taken whenever the operator happened to type it), **verifying** (a number with no address is unfalsifiable), and **de-duplicating** (two sheet rows for one post are indistinguishable from two posts of one video — which doubles a window's apparent n and halves its apparent median).

Added to `OUTCOME_FIELDS`, to the export columns, and to the import. **Optional, not required** — `import_csv` still writes an outcome whenever any metric is filled, because a loop that refuses numbers for want of a url collects nothing.

**The import reads its text columns from one tuple** (`OUTCOME_TEXT_FIELDS`) rather than a hand-written literal. A third hand-kept copy is exactly how a column gets written into the sheet, filled in by the operator, and dropped on the way back.

### (b) No operator entry point — the whole reason nothing was ever recorded

**The module had no `__main__`.** Everything was built and an operator who wanted to record a view count had no command to type.

```
python -m clippershq.outcome_loop status
python -m clippershq.outcome_loop export  --csv outcomes.csv
python -m clippershq.outcome_loop import  --csv outcomes.csv
python -m clippershq.outcome_loop analyse --metric views
```

Read-only by default; only `import` appends, and it says how many lines it wrote. Both zero-cases say **which** zero they are — an export of 0 distinguishes "everything is recorded" from "nothing is rendered", and an import of 0 says a blank row is skipped rather than written as zeros. Live:

```
render records: 133      with a METRIC: 0      awaiting numbers: 133
NOTHING HAS BEEN RECORDED YET. Until a metric exists, every question this module can
answer returns NOT_ENOUGH_DATA and bias_map stays empty -- which is correct, not broken.
```

### (c) A filter on the wrong field hid 22 videos from the sheet, permanently

`export_csv(only_missing=True)` filtered on **`has_outcome`** — true for *any* `kind: "outcome"` line. The 22 join-diagnostic rows made 22 rendered videos invisible to the hand-entry sheet **forever**, silently, in the direction where nothing errors: the sheet is simply shorter, the operator fills in what is offered, and those videos are never asked about again.

**"Missing" has to mean missing NUMBERS.** New `has_numbers()`, and the filter uses it. **VERIFIED: the sheet now offers all 133, up from 111.**

### (d) `posted_at` on the sheet was pre-filled with someone else's timestamp

Found by reading the generated file rather than by testing it. The render record carries its own `posted_at` — **the SOURCE clip's** timestamp, when the page we borrowed from posted the original — and `resolve()` merges it into a column whose meaning is *when we posted our video*. Every row shipped with a plausible epoch (`1785238468`) in it. The operator either leaves it, recording a wrong date on all 133 rows, or clears it 133 times by hand.

Two different facts wearing one name, which is the `view_count`-as-a-decoy shape. Fixed by making `resolve()` record **which keys the outcome line itself supplied** (`outcome_fields`) and blanking every colliding column that did not come from one. `has_outcome` could not do this job: it answers "does an outcome line exist", not "did the outcome supply this field".

## 4. `vision_control_declined` reaches a consumer

New `song_library.vision_suspect(clip)`, **tri-state on purpose**: `False → True` (the model answered an unanswerable question, so every vision field on that row is suspect), `True → False`, **absent → None**. Collapsing None to False would assert that 18 clips whose control was never recorded are known-good.

Carried on `match_detail` and `render_plan` (so it reaches the ledger), and shown in `clip_export` next to the text it qualifies — as **`vision_control_ok`**, not `_declined`, because the stored field is one where *True is good*, which reads backwards in a spreadsheet and is exactly how a human filters the wrong way round. `vision_scene` ships with it and is flattened to one cell, because free model prose with a newline splits a CSV row.

It forces `needs_review` only on the **VISION** tier: a franchise match is made from the caption, so a fabricating vision row does not make it wrong, and flagging it would put noise on the one field people filter on.

### CORRECTION to my own BL-967, and it is the honest half of this item

BL-967 ranked this the **third** most valuable gap in the system on the strength of its 99.1% fill. **I never measured the rate.** Measured now: **1,982 True / 3 False / 18 None.**

**The flag fires on THREE CLIPS.** It is worth wiring because it is free and those three rows really are suspect — not because it is a large correction. Ranking a signal by how often it is *populated* rather than how often it *fires* was the error, and it is the same shape as quoting a 90%-fill field that comes from two accounts.

### GAP — through `dict_of` it is always None, and the guard caught me

`tests/test_matcher_boundary.py` went red the moment `song_library` started reading the field: `clip_pipeline.dict_of()` does not pass `vision_control_declined`, so on the pipeline path the flag is None on every clip. **The guard did exactly its job on a change of mine.**

`clip_pipeline.py` is held by BL-899, so this is recorded in the test's own `EXEMPT` map — which takes a reason, never a bare name — with the one-line patch ready:

```python

```

**It degrades safely, which is why it is exempt rather than reverted:** absent → None, and None never forces `needs_review`. A missing field cannot flip a clip to suspect; it can only fail to flag one. What is deferred is a flag on three clips.

## 5. `views_hidden` carried into the clip library

Declared in `CLIP_FIELDS`, passed by `build_record`, read by `clip_runner` from `like_and_view_counts_disabled` — **with `mget`, not `.get`**, because the gql envelope type-tags scalars and a plain get would silently read None on every gql clip, i.e. exactly the failure the line exists to close. $0.0000: the response is already bought.

**Why this field and not another of the seven BL-967 found dropped.** `play_count` is what the ranker sorts on — `clip_runner` orders by it, `estimated_pages` weights on it, the walk's view floor cuts on it. An account with counts disabled still returns a number, and a low one from such an account is indistinguishable from a genuine flop, so every one of those accounts is ranked to the bottom for a reason that has nothing to do with its clips.

**Tri-state, and `None` is not `False`** — False *asserts* the count is trustworthy. `put()` files an absent flag as ABSENT, never as a confident declared-False. **VERIFIED: two clips at `play_count=0` are now distinguishable**, and it survives a disk round trip.

**GAP: 0 of 2,003 stored clips carry it, and that is expected** — the wiring is on the WRITE path and no walk has run since. It is not a backfill; the flag is not on any stored payload.

## Honest limits

- **No outcome has been recorded, so nothing downstream is exercised on real data.** Every statistic in §3 is synthetic. The first real number the operator types is the first live test of this path.
- **`views_hidden` is on 0 of 2,003 stored clips** and will stay there until a walk runs. The write path is proven on temp libraries only.
- **The vision flag does not reach the pipeline's matcher** and will not until BL-899 releases `clip_pipeline.py`. Three clips.
- **I could not make the tree fully green** — `test_funnel` is red on another round's in-flight file. I attributed it rather than fixing it, because `writer.py` is claimed.
- **`export_csv`'s colliding-column list is hand-written.** `_COLLIDING` names the outcome columns whose meaning differs from the render record's. A future outcome field added without adding it there re-opens exactly the `posted_at` bug.
- **`record_id` is the output PATH.** Move or rename a rendered file and its outcome history detaches. That predates this round and I did not change it, but adding `post_url` makes it sharper: the url is now the more durable identifier and nothing keys on it.
- **The 22 join-diagnostic rows are still `kind: "outcome"`.** I changed the reader rather than the writer, which is right — that round's rows are its own — but any future consumer that trusts `has_outcome` to mean "has numbers" inherits the same trap. `has_numbers()` is exported so it does not have to.
- **The bias path has never run with a non-empty map in production.** `pick(bias=...)` is proven on a synthetic store, not on a live render.
