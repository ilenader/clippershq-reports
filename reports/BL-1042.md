## 4. The reserve is measured, and the first call is the honest part

`_expected(leg_spent, leg_calls, prior)` returns **this leg's own observed mean**, falling
back to a named prior only until the first real price arrives — so a constant that has
drifted from the vendor's pricing costs **one call**, not the run.

**Per leg, never pooled.** A pooled mean is `(retrieval + model) / model_calls`, which
over-estimates the model call by the retrieval:model ratio and stops the run early for the
wrong reason. This became a live risk the moment retrieval started charging `spent`.

**On the first call there is no history, and a prior of 0.0 is the bare rule again.** Driven
at cap $0.03 with a $0.04 call — small enough that the first call *is* the decision:

| prior | spent | |
|---|---:|---|
| exact | $0.0000 | inside |
| **zero** | **$0.0400** | **over by $0.0100** |
| half | $0.0400 | over by $0.0100 |
| double | $0.0000 | inside (stops early) |

So `TwoLegBudget.expected_next` **raises** rather than defaulting to zero, and too *low* is
the only dangerous direction. *(My first version of this table used cap $0.10 at $0.04 and
every prior returned $0.0800 — with room for two calls the prior is corrected by measurement
before it can matter. It proved nothing and is replaced.)*

## 5. Both legs — charged, capped, recorded

**Every attempt is charged, not every success.** Retrieval runs first and BL-999 measured it
failing two calls in three; the pages are billed before the vendor can say the media is
unreachable, so charging only successes rebuilds the identical hole one layer in. Tested
directly (`test_failed_retrievals_are_charged_too`).

**Charged from `pages_fetched`, not a per-clip constant.** 1.345 pages/clip is a library-wide
average; `pages_fetched` is what this call actually bought.

**Recorded to the ledger, not just to the cap.** The retrieval leg now reports through
`record_retrieval_spend_fn` and appears as `retrieval_usd` / `retrieval_calls` in the
summary. Reporting the legs separately matters: "spent $0.03" on a two-leg run is what made
BL-1000 read a $0.6031 spend as a $0.25 one.

**Driver audit:** `control._label_clips` flushes its ig_client in a `finally` — correct.
`clip_pipeline.run_batch` **does not**: zero occurrences of `flush_spend`, `unflushed` or
`http_requests` in the file. My own MEMEBOT-116 render printed *"21 billed request(s) were
never written to spend.json"*. **The gap BL-1025 recovered $0.0030 from by hand is still
open.** `clip_pipeline.py` is BL-1036's live claim — read, never edited.

## 6. What I got wrong

Three things, all caught before they reached a number in this report:

1. **The fake vendor billed what it did not report.** It charged $0.000807 (the 1.345
   pages/clip average) while returning `pages_fetched: 1`, which the code correctly booked
   at $0.0006. The residue showed up as "invisible spend" and was **the harness being
   inconsistent, not the code**. One page fetched, one page billed.
2. **A fail-rate that never failed.** `i % int(round(1/0.74))` is `i % 1`, never non-zero —
   so the 74%-failure rows came back byte-identical to the 0% rows and I nearly reported
   them as evidence.
3. **I leaked $0.0096 of real spend.** The BEFORE run imported `clip_label` from
   `scratch/bl1042_head`, which moved `_REPO_ROOT` and sent the ledger write to a stray
   `scratch/spend.json`. Recovered to the live ledger via `record_aux_spend` (16 IG pages,
   label `bl1042_stray_ledger_RECOVERY`), following BL-1025's precedent. **Running from a
   copied module tree silently redirects the ledger** — the same `_REPO_ROOT` trap
   MEMEBOT-108 recorded.
